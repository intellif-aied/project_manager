# V2 生产发布流程与测试服边界验收

## 1. 目的

本文用于本次 Session 增量上传、报告来源、Token 统计与成本功能的测试服验收和生产发布。

固定原则：

- 先完成 14.157 测试服真实验收，再发布生产；
- 自动化只通过单元测试、集成测试和真实接口模拟行为，不做前端 E2E；
- 前端页面由人工验收；
- 新版 Aida CLI、后端、数据库迁移必须作为同一次发布；
- 生产短暂停机只用于阻止新旧上传混写、完成迁移和服务切换；
- 历史 Session 回填必须在维护窗口内完成并对账；新 Token 页面不得在历史 Ledger 不完整时开放；
- 任一 P0 用例失败即停止发布。

## 2. 本次发布内容

1. 新版 Aida CLI：Session 分页发现、增量读取及 Prepare/Chunk/Finalize 上传。
2. 后端 Session 增量同步、内容切片、处理任务和幂等控制。
3. 报告来源按用户上传形成的切片查询和选择。
4. Token Usage Ledger、日期归属、组织范围统计和成本快照。
5. 数据库由 `016` 一次升级到合并后的 `017`。
6. 历史 Session 回填工具 `migrate-session-ledger`。
7. 更新后的系统 Report MCP 和 Report Skill。
8. 用户指南和新版 Aida CLI 安装说明。
9. Agent 模型列表通过 AIDA 后端代理查询，测试服和生产统一连接模型目录服务。
10. 管理端价格基础数据，包括价格手册、模型映射、模型价格、USD/CNY 汇率及首次成本重算。

### 5.2 增量上传和切片

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| UP-01 | 首次上传 Session | 当前全部有效内容形成 1 个切片 |
| UP-02 | 原文件无变化再次上传 | `unchanged`，Chunk、切片、Token、成本均不增加 |
| UP-03 | 同一 Session 追加内容后上传 | 仅上传新增内容，形成 1 个新切片 |
| UP-04 | 连续追加并分别上传两次 | 每次各形成 1 个切片，内容互不重复 |
| UP-05 | 一次新增内容横跨多天 | 仍形成 1 个切片，不按自然日拆分 |
| UP-06 | 文件末尾是不完整 JSON 行 | 不上传未完成行；补全后再次上传可接续且不重复 |
| UP-07 | Prepare 响应丢失后重试 | 返回同一服务端进度，不重复生成数据 |
| UP-08 | Chunk 请求超时后重试 | 相同 hash 的 Chunk 只保存和计量一次 |
| UP-09 | Finalize 响应丢失后重试 | 结果幂等，只形成 1 个切片 |
| UP-10 | 同一账号并发上传同一 Session | 只存在一条有效推进链路，不重复切片和 Token |
| UP-11 | 两个账号上传相同 Session ID | 数据按用户隔离，互不可见 |
| UP-12 | 本地缓存丢失或更换电脑 | 以服务端 checkpoint 接续，不重传已确认内容 |
| UP-13 | 本地文件截断、重建或前缀改变 | 不把旧 cursor 套到新内容；返回明确可恢复结果 |
| UP-14 | 超大 Session、500 事件边界、4 MiB Chunk 边界 | 分块完整，无事件丢失或重复 |
| UP-15 | 单行超过 8 MiB | 明确失败并指出 Session，不推进 cursor |
| UP-16 | 多选、跨页选择、`all`、取消 | 只上传最终选中的 Session；终端页面原位刷新 |
| UP-17 | 上传中断后重新执行 CLI | 从已确认位置继续，未确认内容可重试 |
| UP-18 | 无网络或服务端 5xx | 明确失败，不形成可选择切片 |

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| TOK-01 | input/cache read/cache write/output 同时存在 | 总量等于四类 Token 之和 |
| TOK-02 | 重复 Chunk、重复 Finalize、重复上传 | Token 和成本均不重复 |
| TOK-03 | Session 跨日持续活动 | Token 按真实事件活动日期归属，不按 Session 启动时间归属 |

| TOK-11 | 切片 Token 与统计页 Token | 各自遵循产品口径，不要求数值相等，不互相覆盖 |

### 7.2 价格基础数据准备与导入

价格基础数据不能直接从 14.157 复制数据库表到生产。测试服包含测试记录，且 `created_by`、`published_by` 关联的用户 ID 在不同环境不一致；已发布价格和汇率又是不可变记录，错误导入后只能新增修正版，不能原地覆盖。

当前系统没有整套价格的批量导入接口。`POST /api/v1/admin/pricing/import-suggestions` 只会导入待审核的模型映射，不会导入价格手册、模型价格或汇率。因此生产发布前必须准备一份经过双人复核的版本化清单，并使用生产管理员 Token 通过现有 Admin API 顺序导入。执行脚本或操作记录必须支持 dry-run、逐项 GET 比较和重复执行跳过；在该步骤准备完成前不得靠临时手工连续调用完成生产初始化。不得直接执行未经审计的 SQL，也不得把测试服整库数据作为生产价格来源。

生产清单至少包含：

1. 唯一启用的“官方 API 等价”价格手册，源币种为 USD，展示币种为 CNY。
2. 每个实际 `provider + raw_model` 对应的标准模型及审核结论。
3. 每个标准模型和计费变体的五类 USD/百万 Token 单价：Input、Cache Read、Cache Write 5m、Cache Write 1h、Output。
4. 每条价格的生效区间、官方来源链接、来源核对时间和备注。
5. 从最早需计价活动日期开始连续覆盖的 USD/CNY 汇率区间、权威来源和核对时间。
6. 明确不计价的内部模型、测试模型或无法确认模型，并记录排除原因；不得用全零价格伪装成已计价。

导入顺序固定如下：

```text
完成 016 -> 017 数据库迁移和全部历史 Ledger 回填
-> 等待处理任务清零
-> 盘点生产 session_usage_components 中实际 provider/raw_model 和最早 activity_date
-> 创建 draft 价格手册
-> 导入并审核模型映射
-> 发布覆盖历史活动日期的 USD/CNY 汇率版本
-> 向 draft 价格手册发布模型价格版本
-> 校验价格和汇率区间无重叠、无日期缺口
-> 将价格手册切换为 active
-> 查看未计价模型并处理或登记排除项
-> 执行成本重算 preview
-> 人工核对影响数量和抽样公式
-> 填写原因后执行成本重算 apply
-> 复查未计价清单、成本汇总和重算审计
```

导入使用以下现有接口，调用人必须是生产 `admin`：

| 顺序 | 接口 | 用途 |
| --- | --- | --- |
| 1 | `POST /api/v1/admin/price-books` | 创建草稿价格手册，全部价格校验完成后再切换为 `active` |
| 2 | `POST /api/v1/admin/model-aliases` | 按 `provider + raw_model_pattern` 幂等写入并审核映射 |
| 3 | `POST /api/v1/admin/exchange-rate-versions` | 发布按活动日期匹配的 USD/CNY 汇率版本 |
| 4 | `POST /api/v1/admin/model-price-versions` | 发布模型和计费变体对应的不可变价格版本 |
| 5 | `POST /api/v1/admin/pricing/recalculate/preview` | 只读预览可计价数量、变化数量和未计价数量 |
| 6 | `POST /api/v1/admin/pricing/recalculate/apply` | 带明确原因应用重算并形成审计记录 |

导入工具或人工操作必须先 GET 现有记录并逐项比较，重复执行时跳过完全相同的记录；发现同一模型、变体和生效区间已有不同的已发布值时必须停止，不得继续插入。已发布记录如需纠错，必须通过管理端“修正”创建 `supersedes_id` 关联的新版本，再单独预览和重算。

完整性验收标准：

1. 生产实际出现的每个模型要么能匹配“已审核映射 + 已发布价格”，要么存在经批准的排除记录。
2. 价格和汇率从生产最早待计价活动日期起连续覆盖，不只覆盖发布日期之后的数据。
3. “未计价模型”中不存在遗漏配置；测试模型和内部模型不得为了清空列表而配置虚假零价格。
4. 抽取至少 3 个模型、2 个活动日期，按五类 Token 公式人工复算 USD 和 CNY，结果与系统一致。
5. 重算 apply 后再次 preview，相同范围应返回 `changed_components=0`；重算审计中能看到操作人、原因和影响数量。
6. Token 总量在价格导入和重算前后不变，只有成本状态和成本快照按预期变化。

`生产环境一期模型价格配置清单-20260715.yaml` 是本次生产初始化的唯一候选清单，但不能直接假定完整。旧 `token_usage` 盘点已经发现清单外模型；最终模型集合必须以历史 Ledger 回填完成后的 `session_usage_components` 为准。每个实际 `provider + raw_model` 必须进入已审核映射或明确排除清单后，才允许执行成本重算。

### 7.3 短暂停机切换

当前不能承诺 10 至 20 分钟。历史回填约有 4732 条候选，维护窗口必须以生产数据副本全量回填实测耗时为准，并额外预留核对和失败处理时间。

```text
提前 pull 已冻结的 API/Web 镜像，不切换服务
-> 停止 Web 和 API，阻止旧上传和业务写入
-> 再确认数据库无新增写入
-> 创建停机时最终数据库备份并校验可恢复
-> 更新生产镜像标签、显式环境变量和系统 Skill 版本配置
-> 只启动新版 API，自动执行 016 -> 017
-> 核对 migration=017 和迁移前后核心表行数
-> preview 并分批完成历史 Ledger 回填，等待处理任务清零
-> 核对旧表未变、新 Ledger 完整且重复回填为 0
-> 按最终模型盘点导入价格清单并执行成本重算
-> 发布新版 Aida CLI 0.1.4 到生产下载地址并执行真实上传验证
-> 启动新版 Web
-> 验证健康检查、登录、Token、成本、报告来源和核心接口

```

生产部署目录固定为 `/home/luoxian/aida`。所有 Compose、配置、备份和日志命令均从该目录执行。

### 7.4 历史数据维护窗口回填

先 preview，确认候选数、缺失原始日志数和失败清单，再执行 apply。

```bash
docker compose exec api migrate-session-ledger
docker compose exec api migrate-session-ledger --apply --limit 50
```

规则：

1. 每批最多 50 条。
2. 等待本批内容处理和计量任务全部完成，再开始下一批。
3. 每批核对成功、失败、pending、Token 增量和重复数。
4. 缺失或损坏原始日志只记入清单，不伪造数据。
5. 回填可暂停；不得为了追求速度并发启动多个回填进程。
6. 回填结束后再次 preview，候选应为 0 或仅剩已记录的不可回填项。
7. 回填前后旧 `sessions`、`session_activity_slices`、`token_usage` 行数和旧 Token 汇总必须保持不变。
8. 新 Ledger 与旧统计可能因解析修正而存在差异，不以两套总数绝对相等作为通过条件；必须按 Session 核对来源、五类 Token、日期归属和幂等性。
9. 生产页面在回填、处理任务和首次成本重算完成前保持维护状态。

2. 使用空临时 HOME 全新安装，确认版本和 API 地址指向生产；再从 `0.1.3` 覆盖升级，确认原 Token 未丢失。
3. 上传一个小型固定 Session，再原样重复上传；确认首次产生一个切片，原样重传不新增切片、不增加 Token 或成本。

12. 全部通过后才开放 Web 入口并通知用户维护结束。

## 8. 回滚和停止条件

### 8.1 立即停止发布

出现任一情况立即停止：

- `017` 迁移失败或核心表数量异常；
- 旧 CLI 仍能写入旧链路；
- 新 CLI 无法接续或发生重复 Token；
- 新上传的处理任务持续 pending；
- Token 明细与汇总不一致；
- MCP 越权、报告来源混入未选切片；
- 系统 Skill/MCP 绑定错误；
- 模型目录服务不可访问，或 Agent 页面无法获取模型列表；
- 生产价格清单未经审核、价格或汇率存在日期缺口，或实际模型未计价且没有批准的排除说明；
- API 持续 5xx。

### 8.2 回滚边界

1. 尚未接受任何新版上传时，可回退应用镜像和配置。
2. 已经接受新版上传后，旧应用不认识新链路，优先修复并向前发布，不做简单镜像回退。
3. 只有确认必须恢复到维护前状态时，才使用维护前数据库备份；这会丢失维护后写入，必须先停止全部写入并明确影响。
4. 历史回填失败只停止后续批次，生产入口继续保持维护状态；修复后从未完成项继续。
