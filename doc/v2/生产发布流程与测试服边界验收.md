# V2 生产发布流程与测试服边界验收

## 1. 目的

本文用于本次 Session 增量上传、报告来源、Token 统计与成本功能的测试服验收和生产发布。

固定原则：

- 先完成 14.157 测试服真实验收，再发布生产；
- 自动化只通过单元测试、集成测试和真实接口模拟行为，不做前端 E2E；
- 前端页面由人工验收；
- 新版 Aida CLI、后端、数据库迁移必须作为同一次发布；
- 生产短暂停机只用于阻止新旧上传混写、完成迁移和服务切换；
- 历史 Session 回填在恢复服务后分批执行；
- 任一 P0 用例失败即停止发布。

## 2. 本次发布内容

1. 新版 Aida CLI：Session 分页发现、增量读取及 Prepare/Chunk/Finalize 上传。
2. 后端 Session 增量同步、内容切片、处理任务和幂等控制。
3. 报告来源按用户上传形成的切片查询和选择。
4. Token Usage Ledger、日期归属、组织范围统计和成本快照。
5. 数据库由 `016` 一次升级到合并后的 `017`。
6. 历史 Session 回填工具 `migrate-session-ledger`。
7. 更新后的系统 Report MCP 和 Report Skill。
8. 用户指南和新版 Aida CLI 安装说明。

## 4. 测试服账号和数据准备

使用 6 个专用测试账号，覆盖四类角色和至少 2 个小组。禁止使用真实业务人员账号制造测试报告。

建议分配：

| 账号 | 角色 | 组织 |
| --- | --- | --- |
| A、B | 工程师 | 小组 1 |
| C | TL | 小组 1 |
| D | 工程师 | 小组 2 |
| E | TL 或 PM | 小组 2 |
| F | 总监 | 管理小组 1、2 所属部门 |

准备两类数据：

1. 固定 JSONL：Token 数值、模型、事件时间和跨日边界均已知，用于精确对账。
2. 本机真实 Codex Session：用于验证真实发现、分页、增量读取、上传和报告生成。

每次测试记录：提交 SHA、镜像标签、CLI 版本及 SHA256、API 地址、账号、Session ID、上传前后 cursor、Chunk 数、切片 ID、Token/成本结果和 Agent run ID。

## 5. 测试服边界测试

### 5.1 CLI 安装、升级和鉴权

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| AUTH-01 | 全新安装测试包 | `aida` 指向 14.157，版本和 SHA256 与发布产物一致 |
| AUTH-02 | 旧版本覆盖升级 | 配置和原 Token 保留，新二进制生效 |
| AUTH-03 | 合法但 `exp` 已过期的 Token 上传 | 三个 CLI 专用上传接口可用 |
| AUTH-04 | 过期 Token 调用普通 Web API | 返回 401 |
| AUTH-05 | 错误签名或非 HS256 Token | 返回 401 |
| AUTH-06 | `nbf` 尚未生效 | 返回 401 |
| AUTH-07 | 用户未同步 | 返回 401 |
| AUTH-08 | 用户已禁用 | 返回 403 |
| AUTH-09 | 旧 CLI 调用 `/sessions/batch` | 返回升级提示，不写 Session、切片或 Token |
| AUTH-10 | Linux、macOS arm64、Windows 安装产物 | 均能校验 SHA256；至少 Linux 执行完整真实上传 |

### 5.2 增量上传和切片

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| UP-01 | 首次上传 Session | 当前全部有效内容形成 1 个切片 |
| UP-02 | 原文件无变化再次上传 | `unchanged`，Chunk、切片、Token、成本均不增加 |
| UP-03 | 同一 Session 追加内容后上传 | 仅上传新增内容，形成 1 个新切片 |
| UP-04 | 连续追加并分别上传两次 | 每次各形成 1 个切片，内容互不重复 |
| UP-05 | 一次新增内容横跨多天 | 仍形成 1 个切片，不按自然日拆分 |
| UP-06 | 文件末尾是不完整 JSON 行 | 不上传未完成行；补全后再次上传可接续且不重复 |
| UP-07 | Prepare 响应丢失后重试 | 返回同一服务端进度，不重复生成数据 |
| UP-08 | Chunk 请求超时后重试 | 相同 hash 的 Chunk 只保存和计量一次 |
| UP-09 | Finalize 响应丢失后重试 | 结果幂等，只形成 1 个切片 |
| UP-10 | 同一账号并发上传同一 Session | 只存在一条有效推进链路，不重复切片和 Token |
| UP-11 | 两个账号上传相同 Session ID | 数据按用户隔离，互不可见 |
| UP-12 | 本地缓存丢失或更换电脑 | 以服务端 checkpoint 接续，不重传已确认内容 |
| UP-13 | 本地文件截断、重建或前缀改变 | 不把旧 cursor 套到新内容；返回明确可恢复结果 |
| UP-14 | 超大 Session、500 事件边界、4 MiB Chunk 边界 | 分块完整，无事件丢失或重复 |
| UP-15 | 单行超过 8 MiB | 明确失败并指出 Session，不推进 cursor |
| UP-16 | 多选、跨页选择、`all`、取消 | 只上传最终选中的 Session；终端页面原位刷新 |
| UP-17 | 上传中断后重新执行 CLI | 从已确认位置继续，未确认内容可重试 |
| UP-18 | 无网络或服务端 5xx | 明确失败，不形成可选择切片 |

### 5.3 Token 和成本准确性

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| TOK-01 | input/cache read/cache write/output 同时存在 | 总量等于四类 Token 之和 |
| TOK-02 | 重复 Chunk、重复 Finalize、重复上传 | Token 和成本均不重复 |
| TOK-03 | Session 跨日持续活动 | Token 按真实事件活动日期归属，不按 Session 启动时间归属 |
| TOK-04 | 第二天补传前一天内容 | 归属原活动日期，不归属上传日期 |
| TOK-05 | 累计计数器回退或重置 | 不产生负数；新计数段可继续累计 |
| TOK-06 | 一个 Session 使用多个模型 | 按模型拆分，明细合计等于总量 |
| TOK-07 | 未知模型或没有有效价格 | Token 正常统计，成本标记未计价，不显示为 0 元已计价 |
| TOK-08 | 价格或汇率之后发生变化 | 已生成 Component 使用原价格快照；只有显式重算才改变历史成本 |
| TOK-09 | 最近 7 天边界和本地时区跨日 | 汇总、排名、明细使用同一时间范围和时区口径 |
| TOK-10 | 个人、TL 小组、总监部门范围 | 明细合计等于汇总；管理者只能看到授权组织和成员 |
| TOK-11 | 切片 Token 与统计页 Token | 各自遵循产品口径，不要求数值相等，不互相覆盖 |
| TOK-12 | 后台处理尚未完成 | freshness/pending 明确显示；完成后变为 ready 且值稳定 |

### 5.4 报告来源、MCP 和 Skill

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| RPT-01 | 日期不传 | 候选切片不被默认日期过滤 |
| RPT-02 | 日期与跨日切片活动范围相交 | 返回完整切片，不裁剪内容 |
| RPT-03 | 同一 Session 多次上传 | 多个切片可独立选择，Summary 分别描述自身内容 |
| RPT-04 | 手动个人报告选择一个或多个切片 | MCP 只读取所选切片；未选切片不混入 |
| RPT-05 | 选择后 Session 又产生新切片 | 已开始的报告不读取后续新切片 |
| RPT-06 | 读取他人切片或越权组织 | 拒绝访问 |
| RPT-07 | 小组日报/周报 | 汇总本组成员已保存的个人报告，不逐个读取原始 Session |
| RPT-08 | 部门日报/周报 | 汇总所管小组已保存的小组报告 |
| RPT-09 | 测试服 MCP 直接调用 | 返回来源、人员名称、时间和正文符合约定，权限正确 |
| RPT-10 | 测试服真实 Agent 六类报告 | 个人日报、个人周报、小组日报、小组周报、部门日报、部门周报均成功保存 |
| RPT-11 | Agent 运行历史 | 六类 run 均能关联到最终报告，失败时保留真实错误 |
| RPT-12 | 定时任务回归 | 只验证现有任务仍能触发和保存，不修改定时任务取数或配置 |

### 5.5 数据库迁移和历史回填

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| MIG-01 | 空数据库执行迁移 | 最终只登记到 `017`，表、约束、索引完整 |
| MIG-02 | 生产数据副本由 `016` 升级 | 用户、组织、Session、旧 Token、报告数量不变 |
| MIG-03 | 迁移中故意制造 SQL 失败 | 整个 `017` 回滚，不登记版本，不留下半迁移对象 |
| MIG-04 | 两个 API 同时启动迁移 | advisory lock 保证只执行一次 |
| MIG-05 | 已登记旧 `017-025` 的测试库启动 | 不重复执行合并后的 `017`，启动正常 |
| MIG-06 | 回填不带 `--apply` | 只输出统计，不写数据库和 MinIO |
| MIG-07 | `--apply` 不带正数 `--limit` | 拒绝执行 |
| MIG-08 | 单 Session 回填并再次回填 | 首次成功；再次候选为 0，不重复 Token |
| MIG-09 | 原始日志缺失或损坏 | 记录失败，不伪造切片或 Token |
| MIG-10 | 每批 50 条回填 | 本批处理任务清零、对账完成后才进入下一批 |
| MIG-11 | 回填过程中有新版 CLI 上传 | 新上传与回填不相互覆盖、不重复计量 |
| MIG-12 | 回填进程中断后重启 | 已完成项不重复，未完成项可继续 |

### 5.6 人工前端验收

前端不执行自动 E2E。人工只确认产品交互，不用页面截图代替数据对账：

1. Aida 用户指南可找到，并包含新版安装、升级和上传说明。
2. Token 页面默认最近 7 天，时间不可清空，汇总和明细同步刷新。
3. Session 选择抽屉默认不带日期筛选，宽度和分页正常。
4. 列表只保留既有核心信息；活动时间正确；Summary 过长可 hover 查看。
5. 跨页选择不会丢失；关闭抽屉后选择结果符合当前交互。
6. 四类角色看到的菜单、个人数据和组织范围正确。
7. Token、成本、未计价状态、处理状态没有空白或误导文案。

## 7. 生产发布流程

### 7.1 维护前

1. 测试服所有 P0 门禁通过并形成测试报告。
2. 确认生产数据库当前 migration 为 `016`，记录核心表行数。
3. 记录当前生产镜像标签、配置文件和系统 MCP/Skill 绑定。
4. 构建并 push API、Web 的不可变镜像标签。
5. 构建正式 Aida CLI，固化生产 API 和下载地址，校验 `SHA256SUMS.txt`。
6. 准备 `10086/aida-report@1.0.3` 和生产 Report MCP，但暂不切换业务流量。
7. 备份生产 PostgreSQL；确认备份可读取并记录文件校验值。
8. 发布维护通知，明确旧 Aida CLI 必须更新。

### 7.2 短暂停机切换

建议维护窗口 10 至 20 分钟，目标不可用时间 5 至 10 分钟。

```text
停止 API，阻止旧上传和业务写入
-> 再确认数据库无新增写入
-> 更新生产镜像标签和系统 Skill 版本配置
-> 启动新版 API，自动执行 016 -> 017
-> 核对 migration=017 和迁移前后核心表行数
-> 启动/更新 Web
-> 发布新版 Aida CLI 到生产下载地址
-> 验证旧 CLI 被拒绝、新 CLI 可上传
-> 验证健康检查、登录和核心只读接口
-> 恢复服务并发布升级完成通知
```

生产部署目录以服务器实际目录为准；当前标准模板目录为 `/data/ai-coding-console`。不得在未确认目录和 `.env` 的情况下直接执行 Compose 命令。

### 7.3 恢复服务后的验证

使用生产专用测试账号，不使用真实业务人员账号：

1. 全新安装生产 Aida CLI，核对版本和 API 地址。
2. 上传一个小型固定 Session，再重复上传一次。
3. 确认只形成一个切片，重复上传 Token/成本不增加。
4. 生成个人日报并保存，核对 Agent run 和报告来源。
5. 验证 Token 页面、成本、未计价状态和处理 freshness。
6. 验证系统 Agent 绑定生产 `10086/aida-report@1.0.3` 和正确 MCP。
7. 检查 API 日志无持续 5xx、迁移错误或任务堆积。

### 7.4 历史数据在线回填

先 preview，确认候选数、缺失原始日志数和失败清单，再执行 apply。

```bash
docker compose exec api migrate-session-ledger
docker compose exec api migrate-session-ledger --apply --limit 50
```

规则：

1. 每批最多 50 条。
2. 等待本批内容处理和计量任务全部完成，再开始下一批。
3. 每批核对成功、失败、pending、Token 增量和重复数。
4. 缺失或损坏原始日志只记入清单，不伪造数据。
5. 回填可暂停；不得为了追求速度并发启动多个回填进程。
6. 回填结束后再次 preview，候选应为 0 或仅剩已记录的不可回填项。

## 8. 回滚和停止条件

### 8.1 立即停止发布

出现任一情况立即停止：

- `017` 迁移失败或核心表数量异常；
- 旧 CLI 仍能写入旧链路；
- 新 CLI 无法接续或发生重复 Token；
- 新上传的处理任务持续 pending；
- Token 明细与汇总不一致；
- MCP 越权、报告来源混入未选切片；
- 系统 Skill/MCP 绑定错误；
- API 持续 5xx。

### 8.2 回滚边界

1. 尚未接受任何新版上传时，可回退应用镜像和配置。
2. 已经接受新版上传后，旧应用不认识新链路，优先修复并向前发布，不做简单镜像回退。
3. 只有确认必须恢复到维护前状态时，才使用维护前数据库备份；这会丢失维护后写入，必须先停止全部写入并明确影响。
4. 历史回填失败只停止后续批次，不需要停止在线业务；修复后从未完成项继续。
