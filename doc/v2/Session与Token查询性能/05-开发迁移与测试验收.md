# 05：开发、迁移与测试验收

> 本文只规定开发和验收方法。生产发布必须另行填写 [完整发布清单](./09-完整发布清单.md)；任何工作包单独通过，不代表完整版本可发布。

## 1. 总体执行规则

- 一次只实施一个发布单元；
- 新表/新路径先在 14.157 测试服完成回填、全量对账、功能回归和性能验收；
- 对账差异不可静默忽略；
- 验收通过后按当前发布单元整体切换，不做用户灰度、百分比 rollout 或运行时双路径配置；
- 当期不做破坏性清理，异常时回滚上一 Git 提交/已验证镜像；
- 任何生产删除必须另行审批；
- 生产不执行压测，不使用真实用户内容做调试输出；
- 迁移编号在开始开发时基于主分支最新状态分配，文档不预占编号。
- 任何工作包开始前必须登记本次发布范围、明确不包含项和完成证据；范围中若包含“PG/MinIO 去重”，必须同时登记内容消费者、写入路径和历史清理门禁。
- 发布前必须逐项检查完整清单；不能用“代码已合并、镜像已构建、健康检查正常”替代功能、数据和消费者验收。
- 长时间回填不是发布完成证明；回填必须单独报告 eligible、active、failed、pending、building、dead job、耗时、暂停次数和最终对账。

## 2. R1：Report Source 切片目录

### 开发内容

1. 新增 `report_source_slice_catalog` 和索引；
2. projection 异步维护目录状态、时间、摘要与事件数；
3. 提供幂等 reconcile/backfill 任务；
4. 保持现有 API 参数和响应结构；
5. 候选 SQL 只读取 catalog 与必要权限表。

### 历史回填

- 按 `slice_id`/revision 小批量推进，不做全表长事务；
- 只读取事件元数据列，不读取 `content_payload`；
- 设置较短 lock timeout、批次上限和可暂停游标；
- 使用独立低优先级 worker；数据库或前台延迟越过保护阈值立即暂停；
- 在线新写与历史回填使用同一 upsert 规则；
- 回填可重复运行，不重复创建目录行；
- 记录 scanned/succeeded/failed/lag，不以日志人工猜进度。

### 切换前全量对账

在测试服以后台校验任务对已回填数据做全量比较，禁止在前台请求里同步跑两套查询：

- total；
- slice key 集合及顺序；
- activity start/end；
- summary、cwd、models 等当前响应字段；
- ready/权限过滤结果。

差异必须带原因分类：旧路径异常、回填缺失、在线漏写、摘要算法差异、revision 状态变化。

### 切换与回滚

- 14.157 完成 catalog 全量回填、对账、接口回归和性能验收；
- 生产先部署附加式准备版本，保持旧候选读路径不变，以低优先级任务完成 catalog 回填和离线对账；
- 通过后将生产候选读取代码整体切换为 catalog，不增加灰度配置；
- 异常时部署上一已验证镜像；保留 catalog 附加表和旧事件数据，不需要做反向数据迁移。

## 3. R2：轻量事件索引与 MinIO Reader

### 开发内容

1. 盘点 `sessions.raw_log_url` 与 `session_upload_chunks.raw_object_key` 的对象覆盖；
2. 对 legacy 对象先完成可重复的 V2 ledger 迁移和 cursor/hash 校验；
3. 新增 `session_content_event_index`；
4. 开发迁移期内，projection 临时同时维护旧事件和轻量索引；这是过渡兼容逻辑，不建设运行时模式开关；
5. 实现按 revision/cursor 流式读取 MinIO 的统一 Reader；
6. 迁移 Digest V2、冻结报告读取、Session 内容消费者；

### 测试服离线比较

同一冻结切片比较：

- 事件数量、顺序和 cursor；
- event type、occurred_at、summary/excerpt；
- Payload hash；
- Digest source hash、included/omitted count、最终 digest hash；
- 大对象内存峰值与读取耗时。

比较任务只在测试服或后台离线任务执行，不在用户请求中把同一大切片读取两遍。失败进入指标和抽样诊断，不输出原始内容。

### 故障处理

| 故障 | 预期行为 |
| --- | --- |
| 对象不存在 | 明确失败、可重试，不返回空成功 |
| legacy 对象没有分块账本 | 不允许整体切换 MinIO Reader，先完成 ledger 迁移与校验 |
| object/event hash 不一致 | 标记完整性错误并停止生成 |
| cursor 越界或断裂 | 标记来源损坏，不读取“最新内容”补齐 |
| MinIO 超时 | 尊重请求取消与超时，后台任务退避重试 |
| projection 重试 | 索引 upsert 幂等，不重复事件 |

### 回滚

测试服全量验收后，将 Digest/冻结报告/Session 内容消费者在同一 R2 版本整体切换到 MinIO Reader。异常时回滚上一已验证镜像；R2 期间仍保留并维护旧事件数据，不删除新索引和 MinIO 对象。

## 4. R3：停止新增 PostgreSQL 全 Payload

进入条件：

- 全部 `content_payload` 消费者清单归零；
- MinIO Reader 全量读取稳定；
- 测试服全量对账通过；
- 对象备份与可用性确认；
- 回滚演练通过。

动作：在 R3 代码中直接停止新增 PostgreSQL 完整 Payload，只写轻量索引与 Catalog，不增加 `dual/index_only` 运行时开关。此阶段仍保留旧历史表，不做空间回收。

回滚：部署上一个 R2 已验证镜像，恢复对旧完整 Payload 的兼容写入，且继续使用 MinIO Reader。禁止回滚到完全不认识轻量索引的 R1 之前版本。

R3 通过前不得发布任何“PG 只保留 MinIO 地址”的结论；该结论必须有代码检索、测试服新上传验证和数据库写入审计证据。

## 5. R4：历史载荷下线

### 前置门槛

- MinIO 全量对象清单、大小、hash/etag 与数据库引用校验完成；
- 历史冻结报告和 Digest 抽样重放通过；
- `index_only` 经过人工确认的完整观察期；
- 数据库备份和恢复演练通过；
- 评估 drop/rename、WAL、磁盘峰值与备库影响；
- 单独获得生产变更和数据清理授权。

### 执行原则

- 不批量 UPDATE 7GB JSONB；
- 优先通过旧表只读封存、备份后整体下线回收空间；
- 每一步记录对象数、事件数、hash 覆盖和空间变化；
- 旧表下线后，回滚边界是恢复备份或继续使用 MinIO Reader，不承诺旧二进制直接读取。

## 6. R5：Token Contribution、三维 Rollup 与轻量快照

R5 的 Token 查询性能通过，不解除 R2/R3/R4 的内容存储门禁。只有 [完整发布清单](./09-完整发布清单.md) 全部通过，才能将本专项标记为完成并发布生产。

### 环境验收边界

- 14.157 是可丢弃测试环境，既有 Session、对象和 Rollup 均为测试数据。R5B 在该环境的门槛是代码回归、接口性能、当前可用数据口径和新上传链路正确，不要求为历史测试数据补对象或修复所有异常 revision。
- 测试服允许保留并记录无法回填的旧测试来源后继续切换，但不得伪造 Contribution、强制激活 conflict/incomplete revision，或把不完整测试统计描述为生产级完整数据。
- 生产迁移是另一条验收边界：必须重新执行完整来源检查、三维/成本对账和异常处置；测试服的 13 个旧数据异常及本次放行结论不能直接继承到生产。

### R5A：Contribution 与 Session Family

本次正向迁移固定使用 `023_token_contribution_and_rollups.sql`。14.157 当前已有
`schema_migrations.version=22`，但 Contribution/Family 表并不存在；不删除、不改写该历史记录，
也不复用编号 `022`，避免 API 启动时将本次建表迁移误判为已执行。R5A 部署后必须同时验证
`schema_migrations.version=23` 和全部目标表/索引，不能只检查版本号。

1. 新增版本化 `session_family_memberships`，解析 root/member/parent/depth；
2. 新增不可变 `session_usage_contributions`；
3. Claude Observation Advance 写 `next - previous`，Codex 写 checkpoint delta；
4. 新增绑定 Contribution 的版本化成本记录；
5. 新增 family total、family daily、member chunk 三套 Token/成本 Rollup；
6. 每个 Rollup Version 写入明确的 Source/Generation/Metrics Revision/cursor 引用，不只保留不可反查的 hash；
7. 在 Metrics Revision 激活前验证三维等式；
8. 旧 Component/Daily/API 继续作为在线读路径，新模型在测试服完成历史回填、全量对账与三维等式验证，不引入运行时 Shadow 模式。

回填期间同一 Family 可能同时存在旧 parser revision 和新 parser revision。中间 Rollup 只能引用与
本次候选 revision 相同 `parser_version + normalizer_version` 的 active revision，禁止把没有
Contribution 的 v4 Component 混入 v5 对账。这些中间 Rollup 在 R5A 期间不供在线查询；只有
`active_revisions = eligible_sources` 后才允许 R5B 切换。

历史回填按目标 parser/normalizer 创建新 Metrics Revision：按 Logical Event 的 Observation 顺序重放 Contribution，按确认的 parent 元数据构建 family relation，再生成三套 Rollup。缺少可信 Subagent baseline、parent 冲突或对账不平的数据只标记 pending/conflict，不自动猜测归属或补数。新 revision 全部验收后才原子替换旧 revision。

实现使用 `token-contribution-backfill`：默认仅检查，显式 `--apply` 才按小批次排队；
当前台数据库存在锁等待、超过 1 秒的活动查询，或全局 pending/leased/retry usage job 达到
50 个时，回填命令必须暂停继续排队；这是对现有上传和用户查询的固定压力保护，不是灰度开关。
`unsafe_sources` 表示原始 Chunk 游标不连续，或数据库已标记对象不可用且没有已验证
Metering Envelope。`object_status=available` 但 MinIO key 物理缺失无法仅由 SQL 预判，Worker 首次读取时
必须进入 dead job 并阻止完成，禁止因 dry-run 的 `unsafe_sources=0` 就忽略后续 I/O 失败。
该值不为零时只跳过异常来源并继续处理安全来源，但禁止判定回填完成或进入 R5B。
原始 Chunk/Envelope 安全的来源不依赖旧 metrics state 必须为 `ready`；即使旧状态缺失、error 或
rebuilding，也允许生成独立 v5 revision。新 revision 仍必须通过语义 quality gate 和替换覆盖检查；
conflict/incomplete/回退事实不强制激活，并会继续阻止 R5B。
已有 building/validated 目标 revision 如因旧代码缺陷留下 dead job，新一次 `--apply` 只重置该
revision 的 dead parse/rebuild job 并从 checkpoint 继续，不删除 revision、不重写已成功 Contribution；
quality gate 导致的 failed revision 仍需人工审查，不自动复活。
生产迁移的最终完成条件还必须满足 `active_revisions = eligible_sources`，不允许用“没有 missing/building”掩盖一个未被统计的 superseded/异常状态。可丢弃测试环境按上方“环境验收边界”执行。

### R5B：Snapshot、API 与 MCP ad-hoc 切换

1. `query_snapshot_token` 冻结 active revision set、family relation、Rollup 和成本版本；
2. Snapshot 只物化范围内 source/revision/family/Rollup/成本版本引用，禁止再写入逐 Component `token_query_snapshot_items`；
3. `/token-analytics/summary`、`trends`、`rankings`、`sessions` 改读同一 Rollup Snapshot；
4. `/tokens`、`/tokens/sessions` 改为同一 Token Analytics 服务的兼容入口，禁止继续读取 `session_activity_slices`；
   `/tokens/sessions` 首页返回可选 `query_snapshot_token`，后续分页必须复用，不得每页重新物化全部 Rollup 引用；
5. Session API 明确输出 self/subagent/family/lifetime/range 字段；本内测协同版本中
   `/tokens/sessions.total_tokens` 明确作为 `range_total_tokens` 的兼容别名，并用
   `token_slice_strategy=family_rollup_v2` 标识，全部已知消费者必须同步迁移；
6. 默认 Session 列表按 root family 去重，`total` 和 `session_count` 均表示不重复 root Session，不能使用日期切片行数冒充 Session 数；
   `component_count` 必须由当前筛选后的 Daily Rollup `contribution_count` 直接求和，不得回读高基数明细；
7. 工作台删除 `fetchAllSessionTokens` 全量翻页和浏览器侧汇总，改读 summary、trends、rankings 及服务端 `session_count`；
8. 需求/任务“关联工作记录”不再把日期切片 ID 当 Session：family v2 行保存 root Session ID，旧切片关联仍可解除；
9. Snapshot 过期删除和 superseded Rollup 回收从 HTTP 请求移到后台，每五分钟最多处理 2 个 Snapshot、5 个 Rollup，锁等待 100ms、SQL 最长 5s；
10. 在 14.157 同时回归 Token API、工作台、前端 Token 页面、需求/任务关联和 MCP ad-hoc `get_sessions`；
11. 通过后按同一内测版本整体切换 API/前端/MCP，不引入独立灰度开关；异常时回滚上一已验证镜像，R5C 前旧数据路径继续保留。

### R5C：兼容路径下线

- 旧 Snapshot 自然过期后停止物化高基数 Component items；
- 确认无消费者后再评审旧字段/旧表，不与 R5B 同时删除；
- 保留 Observation、Logical Event、Contribution、Revision 和成本审计。

Token 回填不得从 `session_content_events` 中的内容事件估算 Token，必须从 Usage Observation/Logical Event 按目标 parser/normalizer revision 重建。详细数据模型和等式见 [Token 三维统计与对账模型](./07-Token三维统计与对账模型.md)。

## 7. 功能测试矩阵

### Report Source

| 用例 | 预期 |
| --- | --- |
| 只传 `period_start/end` | 返回全部可选切片，period 不过滤 |
| 显式传 `activity_from/to` | 只返回活动范围相交切片 |
| 不传任何日期 | 与 period-only 的候选语义一致 |
| 日报/周报 | 候选规则一致，报告上下文不同 |
| q 命中 session_ref/summary | 只在 catalog 内搜索 |
| page 1/中间页/末页 | total、顺序、无重复/遗漏 |
| 同 Session 多次上传 | 多个切片独立可选 |
| 选择后 Session 再上传 | 已冻结报告不自动加入新切片 |
| processing/failed | 不进入候选 |
| 用户越权 slice | 不可见、不可冻结 |

### 内容读取

- 跨多个 MinIO chunk 的 slice；
- 单行超大事件与大量小事件；
- UTF-8、换行、边界 cursor；
- 对象缺失、hash 错误、超时、取消；
- revision superseded 与冻结 revision 并存；
- Digest V1/V2 与当前基准结果对账；
- 用户显式清理后对象和派生索引均不可再读。

### Digest、MCP 与其他接口

[Digest 与接口影响回归矩阵](./06-Digest与接口影响回归矩阵.md) 中 `REG-UP-*`、`REG-DIG-*`、`REG-RS-*`、`REG-MCP-*`、`REG-API-*` 全部属于发布门槛，不能只抽测代表用例。

### Token Analytics

- 根 Session 自身 + 多层 Subagent 家族关系；
- Subagent 父历史、baseline 和 `trigger_turn` 边界不重复；
- Claude Logical Event 跨 Chunk Advance 只记录 Delta；
- family total = daily sum = chunk sum = active contribution sum；
- 生命周期总量与日期范围小计字段不混用；
- summary = trends/rankings/sessions 且 root Session 行不重叠；
- 日期/模型筛选后 `component_count` 与同范围 Contribution 数一致，执行计划不访问 Contribution/Component 明细；
- 输入/输出/cache Token 分项；
- 多模型、多供应商、跨日期；
- 组织权限与成员变更；
- 价格版本、汇率和历史成本；
- 重复上传、重试、修正与清理；
- snapshot 过期、并发同条件构建和回滚。
- `/tokens` 与 `/tokens/sessions` 不再读取 `session_activity_slices`，结果与同范围 Token Analytics 对账；
- `/tokens/sessions` 第 2 页及后续页复用首页 Snapshot，Snapshot 过期时服务端自动重建一次；
- 工作台不再全量拉取 Session 分页后自行计算总量、趋势、成员排行和 Session 数；
- 需求/任务关联弹窗分页、全选、保存、取消关联均使用 root Session；已有旧日期切片关联可正常迁移；
- MCP ad-hoc 日期查询继续按天返回，Token 来自 family daily Rollup，活动起止时间来自该日真实 Contribution 最小/最大时间，attached digest/full 路径完全不变；
- Snapshot/Rollup 后台回收不进入 HTTP 链路，仍被未过期 Snapshot 引用的 Rollup 不得删除；
- 64 个 Session/18,030 个 Component 的真实高基数样本，首次查询只读取 Rollup 和轻量版本引用。

[Token 三维统计与对账模型](./07-Token三维统计与对账模型.md) 中 `TOK-3D-001` 至 `TOK-3D-018` 必须逐项执行并保存对账结果。

## 8. 性能验收

### 数据集

隔离测试环境至少准备：

- 321 万级事件、7GB 级 Payload 的事故等量数据；
- 单用户 37、1,000、5,000 个候选切片；
- 少量超大 Session 与大量普通 Session；
- 有无显式活动日期、q、不同页码的组合。
- 单用户串行、10 个并发用户和 20 个并发用户三档负载。
- 至少一个 root Session、三层 Subagent、跨日且包含 1,000 个以上 Chunk 的 Token 家族数据。

### Report Source 指标

| 指标 | 目标 |
| --- | ---: |
| p50 | ≤ 100ms |
| p95 | ≤ 300ms |
| p99 | ≤ 800ms |
| 单次冷查询 | ≤ 1s |
| 超时/错误率 | < 0.1% |

硬门槛：

- `EXPLAIN` 不出现 `session_content_events`、`session_content_event_index` 或 Usage 明细；
- 页大小改变只影响返回/当前页成本；
- 原始事件从 321 万增加到更高规模时，固定候选集合延迟不应显著增长；
- 有无显式日期使用相同执行路径；
- 连接池、临时文件和数据库 I/O 不出现明显放大。
- 开启回填/离线对账任务后，现有前台接口 p95 回归不超过 5%；超过即自动暂停专项任务。

### Content Reader 指标

- 内存随流式窗口而不是对象总大小增长；
- 读取字节与命中 chunk/slice 大小相符；
- 不重复下载无关对象；
- 测试服全量对账身份/游标/hash 100% 一致；
- MinIO 故障不会拖垮 Report Source 列表。

### Token 指标

Token Analytics 允许随活动日期范围内的分析事实数量增长，但不得随内容事件 JSON 大小增长。隔离测试环境的交互目标为：

| 场景 | p95 | p99 |
| --- | ---: | ---: |
| 默认 3 天首次快照 | ≤ 1.5s | ≤ 3s |
| 默认 3 天复用快照的单模块查询 | ≤ 500ms | ≤ 1s |
| 31 天首次快照 | ≤ 3s | ≤ 5s |
| 31 天复用快照的单模块查询 | ≤ 1s | ≤ 2s |

同时验证首次快照、复用快照、并发相同条件和四模块并发，不能只测单条 SQL。Rollup 查询不得访问完整内容事件，也不得在请求内递归构建 Session family。若现有生产基线与目标差距过大，必须在 R5B 评审时显式拆阶段，不能降低指标后直接宣称通过。

Token 在线查询的 `EXPLAIN` 还必须证明未访问 `session_usage_components`、
`token_query_snapshot_items` 和 `session_activity_slices`。分页只能发生在 Rollup 结果集上；
`page_size=10` 时不得先物化范围内全部 Component。

## 9. 发布验收与停止条件

### 可以继续

- 功能、测试服全量对账和性能指标全部通过；
- 数据增长、失败率和延迟可观测；
- 上一 Git 提交/已验证镜像与当期数据兼容性已在目标环境演练；
- 无未分类差异；
- 获得当前发布单元的明确授权。

### 必须停止

- catalog 与旧结果存在未解释差异；
- MinIO 对象缺失、hash 覆盖不完整；
- 任一消费者仍直接依赖完整 `content_payload`；
- 迁移需要大表长锁、磁盘空间不足或备份不可恢复；
- Token/成本口径发生非预期变化；
- 三维 Token 等式不成立或 Subagent family 存在未解释冲突；
- Digest/MCP/其他接口回归矩阵存在未通过项；
- 未获得生产迁移或清理授权。
