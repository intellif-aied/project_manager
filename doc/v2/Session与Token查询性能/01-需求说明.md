# 需求说明

## 1. 背景

Session 原始 JSONL 已保存在 MinIO，解析后的完整事件 JSON 又保存在 PostgreSQL `session_content_events.content_payload`。内容列表、Digest 和 MCP full 曾直接依赖大事件表，Token 查询也曾在请求时扫描高基数明细。

专项需要同时解决：

1. Report Source 候选分页不得受事件数和 JSONL 大小影响；
2. Token 统计在后台固定，查询只读预计算事实；
3. Session 原始内容只保留在 MinIO，PostgreSQL 不再保存完整 Payload；
4. Digest、MCP full 和 Session 内容在更换数据源后保持外部契约不变。

## 2. 交付目标

- MinIO 成为 Session 原始内容的唯一事实源；
- PostgreSQL 只保留关系、cursor、状态、摘要、Digest、Usage、Token、成本和审计数据；
- Report Source 只读 Catalog，Token API 只读 Contribution/Rollup/Snapshot；
- Digest V1/V2、MCP attached full 和 V2 Session 内容统一通过 MinIO Content Reader 读取；
- 新上传不再写入 `content_payload`；
- 历史 Payload 完成完整性对账、数据紧凑和 PostgreSQL 空间回收。

## 3. 产品契约

### 3.1 Session 与 Report Source

- 每次成功增量上传形成一个可追溯切片，Session 无需结束；
- Report Source 只展示已就绪切片，不显示或计算 Token；
- `period_start/period_end` 是报告周期，不过滤候选；
- `activity_from/activity_to` 才按活动时间过滤；
- 选择报告来源后冻结 slice、generation、revision 和 cursor，后续上传不影响已冻结报告。

### 3.2 Token

- Token 与成本在上传后的异步 Usage/Metering 流程中固定，查询不重新解析 JSONL 或计价；
- 顶层 Session 统计包含自身及所有 Subagent，Subagent 继承的父历史不重复计数；
- Session family total、daily sum、chunk sum 必须来自同一组 active Contribution；
- summary、trends、rankings 和 sessions 必须共享同一查询快照。

### 3.3 Digest 与 MCP

- Digest 在切片 fully indexed 后由后台异步生成，不在用户点击 AI 生成时现场扫描；
- Digest 未就绪返回 `REPORT_SOURCE_DIGEST_NOT_READY`；
- attached digest 继续读已冻结 Digest，不依赖实时 MinIO；
- attached full 的 MCP Schema、cursor、权限与返回结构不变；
- `write_report_result` 的完整读取、版本和 hash 门禁不变。

## 4. 数据保留边界

必须保留：MinIO JSONL/Chunk、Session 与上传身份、轻量事件索引、Report Source Catalog、冻结 Digest、Usage/Contribution/Rollup、成本、价格、汇率和审计数据。

需要移除的是 `session_content_events.content_payload` 这份重复 Session 内容，不是 PostgreSQL 中所有 JSONB。

用户显式清理 Session 内容后，原文、可重建内容索引和 Digest 按既有生命周期处理；已确认的 Token、成本和审计事实继续保留。

## 5. 非功能要求

- Report Source p95 ≤ 300ms、p99 ≤ 800ms；
- Token summary/sessions p99 ≤ 3s，不物化高基数 Component；
- Content Reader 流式处理，内存不随对象总大小线性增长；
- 后台迁移不得使前台 p95 回归超过 5%，不得造成长锁或磁盘/WAL 风险；
- 对象缺失、hash 不符、cursor 断裂必须明确失败，不得返回空内容成功。

## 6. 范围限制

- 不改 Aida 增量上传协议；
- 不改 Report Source、Digest、MCP 和 Session 的外部 Schema；
- 不重新设计已上线的 Token 统计口径；
- 不强制修复无法证明 counter 边界的历史冲突数据；
- 不建设用户灰度、百分比 rollout 或运行时双读开关；
- 不在生产环境执行压测或未演练的破坏性数据操作。
