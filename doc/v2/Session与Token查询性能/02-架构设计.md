# 架构设计

## 1. 系统边界

```text
user
  -> session
    -> source
      -> generation / projection revision
        -> upload chunk + MinIO object
        -> content slice [start_cursor, end_cursor)
          -> report source selection / digest revision
```

Catalog、Content Reader、Digest、Usage 和 Token 必须使用同一组 source/generation/revision/cursor 身份，不得用 `session_ref + 日期` 推测内容版本。

## 2. 当前架构

```text
Aida 增量上传
  -> MinIO JSONL / Chunk
  -> Content Projection
  -> session_content_events
       |- cursor/time/type/summary/hash
       `- content_payload (完整 JSONB)
            |- Digest V1/V2
            `- MCP/report full

MinIO Chunk
  -> Usage/Metering
  -> Observation -> Logical Event -> Contribution
  -> Session Family / Daily / Chunk Rollup
  -> Token API / Web / MCP
```

`report_source_slice_catalog` 已承担 Report Source 候选分页，Token 已读 Contribution/Rollup/Snapshot。剩余的架构缺口是内容消费者仍读 PostgreSQL Payload。

## 3. 目标架构

```text
Aida 增量上传
  -> MinIO JSONL / Chunk (唯一原文)
  -> Content Projection
  -> session_content_events (轻量索引)
  -> report_source_slice_catalog

MinIO Content Reader
  |- Digest V1/V2
  |- MCP/report full
  `- Session 详情/导出

MinIO Chunk
  -> Usage/Metering
  -> Contribution / Rollup / Snapshot
  -> Token API / Web / MCP
```

| 数据 | 权威位置 | 用途 |
| --- | --- | --- |
| Session 原始 JSONL | MinIO | 字节级恢复和完整内容读取 |
| 事件定位与摘要 | PostgreSQL `session_content_events` | cursor、时间、类型、摘要、hash |
| Report Source 候选 | `report_source_slice_catalog` | 权限、筛选、排序、精确总数和分页 |
| 报告上下文 | Digest revision / selection payload | 冻结内容和 Agent 读取门禁 |
| Token 与成本 | Contribution / Rollup / Snapshot | 汇总、趋势、排名和 Session 列表 |

## 4. Content Reader

代码位置：`api/internal/contentreader/`。

输入：已冻结的 content revision、`start_cursor`、`end_cursor`。

处理流程：

```text
解析 revision 与 cursor 范围
  -> 查询相交 upload chunks
  -> V2 读 raw_object_key / legacy 读 raw_log_url
  -> 复用 sessionsync.ParseContentChunk 按 cursor 流式解析 JSONL
  -> 校验 Chunk 边界、完整行和 SHA256
  -> 输出有序事件流
```

输出事件包含 cursor 范围、`occurred_at`、`event_type`、summary/excerpt、payload 和 `content_sha256`。Reader 必须支持跨 Chunk、context 取消、超时和背压，不一次将大对象载入内存。

Reader 提供两种明确的完整性模式：Digest 等后台消费者使用完整对象模式并核对 Chunk SHA256；MCP full 等分页消费者先用轻量索引确定不超过 100 条事件的 cursor 范围，再通过 MinIO Seek/Range 只读该字节段，并逐事件核对 cursor 与 `content_sha256`。分页禁止从对象头重复扫描，存储实现不支持 Seek 时才退化为完整流式读取。

Reader 与 Content Projection 必须复用 `api/internal/sessionsync/content_parser.go` 的 `ParseContentChunk`，保持 cursor 计算、坏行处理、单行上限和 PostgreSQL 非法字符清洗规则唯一。禁止在 Reader 中实现第二套事件解析器。

错误分类必须至少包括：对象不可用、完整性错误、cursor 错误、JSONL 解析错误、取消/超时。任何完整性错误都不能转换为空结果。

## 5. 轻量事件索引

最终沿用 `session_content_events` 表名，保留：

```text
id, content_projection_revision_id, chunk_id
source_start_cursor, source_end_cursor
occurred_at, event_type, summary, excerpt
content_sha256, created_at
```

唯一键保持 `(content_projection_revision_id, chunk_id, source_start_cursor, source_end_cursor)`，保持 revision+cursor 和 revision+occurred_at 索引。最终表不包含 `content_payload`，不长期维护两张功能重复的事件索引表。

## 6. 主要读写时序

### 6.1 上传与后台处理

```text
上传请求
  -> 保存 MinIO Chunk 并记录 cursor
  -> 立即返回接收结果
  -> Content Projection 写轻量索引/Catalog
  -> Digest Worker 通过 Reader 生成 Digest
  -> Usage/Metering 生成 Contribution/Rollup/成本
```

上传、内容投影、Digest 和 Token 是独立状态，不能用一个 `Done` 互相推导。

### 6.2 报告生成

```text
Report Source Catalog 选择切片
  -> 冻结 slice/revision/cursor
  -> 校验 Digest ready
  -> Agent/MCP attached digest 读冻结 payload
  -> write_report_result 校验完整性后写入
```

attached full 使用同一冻结 revision/cursor，PostgreSQL 只规划轻量 cursor 边界，内容通过 Reader 的 Indexed Range 模式分页读取。page cursor 仍保存 item offset 和下一个事件 cursor，既有权限、冻结和重试语义不变。

### 6.3 Token 查询

```text
active Usage revision
  -> immutable Contribution
  -> family / daily / chunk Rollup
  -> query snapshot
  -> summary / trends / rankings / sessions
```

查询路径不读 JSONL、`session_content_events`、Observation 或 Component 明细。

## 7. 消费者架构

| 消费者 | 目标读写路径 |
| --- | --- |
| Content Projection | 只写轻量 `session_content_events` 和 Catalog |
| Digest V1/V2 | Reader 事件流经现有脱敏/截断投影后生成 Digest |
| MCP attached digest | 继续读已冻结 Digest |
| MCP attached full | 按冻结 revision/cursor 读 Reader |
| Session 详情/导出 | legacy 单对象保持原路径；V2 由 Reader 按 active revision 顺序校验并拼接原始 Chunk，能力字段控制下载入口 |
| Report Source 列表 | 只读 Catalog |
| Usage/Metering | 继续读 MinIO Chunk，不变 |
| Token API/Web/MCP | 继续读 Rollup/Snapshot，不变 |

## 8. 内容清理与恢复

```text
clear-content
  -> content_status = clearing，content_epoch 递增
  -> Reader、Report Source 和未完成 Digest 立即拒绝继续读取
  -> Metering Envelope 固化已确认 Usage 事实
  -> 删除 MinIO 对象
  -> 同一事务内清空 active projection、删除轻量事件索引、
     将 Projection/Digest 标记 superseded、Catalog 标记 cleared
  -> content_status = cleared，保留 Token、成本、Rollup 和 Tombstone 审计

restore-content
  -> 新 content_epoch
  -> 用户重新上传并形成新 generation / projection / digest
  -> 新 Projection 激活后 content_status = available
  -> 旧 selection 因旧 epoch/revision 永久失效
```

清理不删除已确认的 Usage、Contribution、成本和 Token Rollup。旧 Digest 状态必须失效，不能在清理后继续作为 `ready` 内容读取；Tombstone 记录操作人、原因和对象删除完成时间。

## 9. 历史数据迁移架构

不对 321 万历史行执行大批量 `UPDATE content_payload = NULL`。使用紧凑表切换：

1. migration 只创建不含 Payload 的紧凑表、完整约束/索引和迁移状态表，不复制历史数据；
2. 独立命令默认 dry-run；`copy` 每次必须有 batch size 和 max batches，按主键游标复制轻量字段并保存断点和批次指纹；
3. bulk copy 完成后，为旧表安装短期 INSERT/DELETE mirror trigger，再执行 missing/extra 双向 reconcile；
4. 对账行数、主键集合及全部轻量字段，任何 missing、extra 或 mismatch 都阻止切换；
5. `cutover` 在短事务内锁定新旧表、重复最终对账并交换表名；排队中的旧表写入继续由 mirror trigger 同步到新表；
6. 旧 Payload 表固定保留为 `session_content_events_payload_archive`；回滚窗口内新旧表双向镜像 INSERT/DELETE，回滚只做精确校验和表名交换，不在排他锁内全表回灌；
7. 回滚窗口结束、备份恢复和接口验收全部通过后，只有显式输入 archive 表名才能执行 `finalize` 删除旧表并回收空间。

迁移命令禁止一次无边界运行：`apply` 时 `batch_size`、`max_batches` 必填且为正数，单批最多 10,000 行、单次最多 20 批；普通进度报告使用统计估值，只有显式 `verify` 和切换门禁执行精确对账；`cutover` 必须带人工核对的 expected source rows；cutover/rollback/finalize 除锁等待超时外还有默认 5 秒、最高 30 秒的单 SQL statement timeout，超时整笔事务回滚；`finalize` 是唯一不可逆动作。

## 10. 异常与退化

| 异常 | 系统行为 |
| --- | --- |
| MinIO 不可用 | 未生成 Digest/full 读取失败或重试；已冻结 Digest 和 Token 查询不受影响 |
| 对象缺失/hash/cursor 错误 | 标记完整性错误，阻止 Digest/full 结果 |
| Digest 未就绪 | 返回既有 NOT_READY 错误，不现场扫描 |
| Token Rollup 未就绪 | 返回质量/可用性状态，不现场重算 |
| 迁移任务异常 | 停止新批次，保留进度、旧表和备份 |

## 11. 运行保护

- Reader 不进入 Report Source 或 Token 列表路径；
- 后台盘点/迁移使用独立并发上限，前台 p95、数据库 CPU/I/O、连接池或磁盘达阈值时自动停止；
- 监控 MinIO 读取失败/hash 错误、Reader 耗时/字节、Catalog 就绪延迟、Digest 队列、Token Snapshot 耗时、PostgreSQL Heap/Index/TOAST 大小与增长。
