## 1. 本次目标和结论

目标：

1. 先让 Digest V1/V2、MCP full、Session 详情/导出统一通过 MinIO Content Reader 读取；
2. 再让新上传只向 PostgreSQL 写轻量事件索引，不再写 `content_payload`；
3. 发布后使用 192.168.14.159 本机真实 Session 和生产测试账号，完成“上传 -> 日报 -> 周报”真实链路验收；
4. 上述验收通过后，再对历史事件做可暂停、可续跑的后台分批复制与对账。

本次结论：

- **代码可以上线**；API 启动只新建空紧凑表和状态表，不会自动搬运 318 万历史行。
- **历史迁移不得和服务发布同步绑定**；只能在真实用户链路验收后单独启动。
- **本轮历史任务最远只做 `copy -> mirror -> reconcile -> verify`**；不执行 `cutover`、`rollback` 或 `finalize`。
- `cutover/finalize` 当前在 `ACCESS EXCLUSIVE` 锁内做全表精确对账，生产规模下存在超时和锁影响，必须改造并重新验收后另行安排。

### 5.9 HISTORY_COPYING：后台分批复制

1. 先执行 `compact-session-events --action plan`，记录 source 估值、source bytes 和 state。
2. 每个受控轮次执行：

   ```bash
   docker compose exec -T api compact-session-events \
     --action copy --apply --batch-size 5000 --max-batches 10
   ```

   每轮最多 50,000 行，生产当前规模预计约 64 轮。命令内部按 UUID 游标记录断点，中断后从 state 续跑，不从头扫描。
3. 外层后台 runner 必须具有：最大轮数、每轮独立日志、轮次间隔、停止文件和 health/DB/disk 门禁；禁止无上限 `while true`。
4. 当夜未完成时正常停止，下一个窗口继续；不得为了“一晚跑完”放大并发或批次硬上限。

### 5.10 HISTORY_RECONCILED / VERIFIED：追平与对账

copy 完成后按顺序执行：

```bash
docker compose exec -T api compact-session-events --action mirror --apply
docker compose exec -T api compact-session-events \
  --action reconcile --apply --batch-size 5000 --max-batches 10
# 重复有界 reconcile，直到 missing/extra 游标都 complete
docker compose exec -T api compact-session-events --action verify
```

最终必须：

- `row_counts_exact=true`；
- `missing_rows=0`；
- `extra_rows=0`；
- `mismatched_rows=0`；
- 旧表仍名为 `session_content_events`，旧 Payload 仍存在；
- 前台业务继续读旧表/MinIO，用户无需等待切换。

完成后立即停止。不执行文档中的 `cutover`、`rollback`、`finalize` 命令。

## 6. 迁移运行停止条件

任一条命中就停止新批次，保留 state 和日志：

- `/health` 非 200，或 API/DB/MinIO 容器状态异常；
- API 持续出现 5xx、panic、Digest/Usage dead job 或对象完整性错误；
- PostgreSQL 出现超过 10 秒的 blocked query 或持续锁等待；
- 前台关键接口 p95 相对发布后基线回归超过 5%；
- 主机剩余磁盘低于 100 GB，或 WAL/磁盘 I/O 持续异常；
- 单个 50,000 行轮次超过 10 分钟且无可解释的资源原因；
- 任一批 source/target fingerprint 不一致；
- 运维人员创建停止文件或人工要求暂停。

停止后不需要回滚已复制的 shadow 行；生产仍使用旧表。只需记录最后成功 cursor，下次续跑。
