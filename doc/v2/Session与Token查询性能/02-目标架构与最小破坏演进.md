# 02：目标架构与最小破坏演进

> 发布边界：本文的 R1～R5 阶段是工程实施顺序，不是生产发布清单。Token Rollup、Reader 迁移、停止 Payload 写入和历史 JSONB 清理必须分别有实现证据；任何单一阶段通过都不能被描述为“完整版本已发布”。生产发布统一使用 [完整发布清单](./09-完整发布清单.md)。

## 1. 设计原则

1. 原始内容只保留一份：MinIO 是字节级事实源。
2. PostgreSQL 数据必须面向关系查询，且可由 MinIO/上传事实重建。
3. 用户请求只读预计算目录或分析事实，不承担内容投影工作。
4. Report Source 与 Token Analytics 共享身份，不共享读模型。
5. 迁移只做附加式变更：先在测试服全量回填与对账，再按独立发布单元整体切换，最后清理。

## 2. 共享身份层

以下关系必须稳定且可追溯：

```text
user
  -> session
    -> source
      -> generation/revision
        -> upload chunk + MinIO object
        -> content slice(start_cursor, end_cursor)
          -> frozen report source / digest revision
```

所有目录、索引、Digest、Usage 事实都必须带上足够的 source/generation/revision/cursor 信息，禁止仅靠 `session_ref + 日期` 猜测来源。

## 3. Report Source 切片目录

### 写入时机

- 新切片创建时写入 building 记录；
- projection 处理事件时增量维护首尾活动时间、摘要候选和事件数；
- projection 覆盖 `end_cursor` 后标记 ready；
- revision 被替代、清理或恢复时同步状态；
- 维护失败进入可重试任务，不阻塞上传接口。

### 读取路径

```text
GET /report-source-sessions
  -> user/status
  -> optional activity overlap
  -> optional q
  -> indexed order
  -> count + page
```

该路径不得 JOIN：

- `session_content_events`；
- `session_usage_components` 或其他 Usage 明细；
- Digest JSON；
- MinIO 对象。

### 一致性规则

- ready 目录行必须引用仍有效的 active projection revision；
- `activity_start_at <= activity_end_at`；
- cursor 边界必须与切片一致；
- summary 使用当前列表逻辑的版本化结果，回填和在线写入使用同一算法；
- revision 变化不得原地污染已冻结报告的引用。

## 4. 轻量事件索引与 MinIO Reader

### 写入模型

`session_content_event_index` 保存事件级定位信息，不保存完整 Payload。在线 projection 仍解析事件，但只持久化元数据与哈希。

建议唯一键：

```text
(content_projection_revision_id, chunk_id, source_start_cursor, source_end_cursor)
```

建议索引：

```text
(content_projection_revision_id, source_start_cursor, source_end_cursor)
(content_projection_revision_id, occurred_at)
```

### 读取模型

Content Event Reader 以冻结的 revision + cursor 为输入：

```text
查相关 chunk/object
  -> 流式读取 MinIO
  -> 按 byte cursor 解析 JSONL
  -> 校验 object/event hash
  -> 应用现有脱敏/截断规则
  -> 返回稳定事件流
```

Reader 必须支持取消、超时和背压，不能把大对象一次性加载进内存。MinIO 故障不能回退成“空内容成功”。

生产历史数据必须先盘点两种对象引用：旧 `sessions.raw_log_url` 全量对象与 V2 `session_upload_chunks.raw_object_key` 分块对象。Reader 的正式读取边界以分块账本为准；只有完成 legacy ledger 迁移并在测试服证明 cursor/hash 覆盖完整的 Session 才能进入 MinIO 正式读取，不能假设所有旧对象天然具备分块索引。

### 消费者迁移顺序

1. Digest V2；
2. 冻结报告来源读取；
3. Session 内容详情/导出；
4. Digest V1 或兼容路径；
5. 其他通过代码检索确认的 `content_payload` 消费者。

所有消费者迁移完成后，才能停止写 PostgreSQL 完整 Payload。

## 5. Token 分析事实

Token 方案沿用当前 Usage Observation、Logical Event、Metrics Revision、幂等 Claim 和价格快照规则，但增加“Observation 推进增量”这一可加总事实层。不能从内容 projection 事件表统计 Token，也不能直接按当前 Component 的 `chunk_id` 计算新增 Chunk Token。

新增 `session_usage_contributions` 后，同一 Contribution 具有实际生产 Token 的 member Session 归属；root family 在 Rollup 构建时通过指定 family relation version 解析：

- 实际生产 Token 的 `member_session_id`、用户和组织快照；
- `chunk_id`、业务日期、模型/供应商；
- input/output/cache 等 Token 分项；
- cost、currency、price_version、exchange_rate；
- usage revision、from/to observation、source identity 和幂等键；
- quality、parser/normalizer/family relation version。

它派生三套 Rollup：

1. root Session 自身 + 全部 Subagent 的家族总量；
2. root Session 家族按上海业务日汇总；
3. 每个实际 member Session 的新增 Chunk Delta。

快照只固定查询边界、active revision set、family relation version、Rollup/成本版本和权限。不得让四个页面接口分别重建等价范围，也不得为了复用快照擅自延长产品新鲜度。完整模型见 [Token 三维统计与对账模型](./07-Token三维统计与对账模型.md)。

## 6. 开发期切换与回滚边界

当前仍是内测开发期，不建设用户灰度、百分比 rollout、双读 Shadow，也不新增 `legacy/shadow/new` 这类读写模式配置。

每个独立发布单元统一执行：

1. 在 14.157 测试服完成全量回填、离线对账、功能回归和性能验收；
2. 如果生产历史数据需要回填，先部署不改变在线读路径的附加式准备版本（新表、新写入、低优先级回填/离线对账）；这是数据迁移步骤，不是用户灰度；
3. 数据就绪后部署切换版本，将该发布单元按一个明确实现路径整体切换，不在生产长期并行两套读路径；
4. 异常时回滚到上一个 Git 提交/已验证镜像；当期不删旧表、不做破坏性数据清理；
5. 等观察期和消费者迁移完成后，再以单独发布单元下线旧数据。

需要保留的 `revision/version` 只用于数据正确性和可追溯性，例如报告冻结、Usage 重算、Session family 关系和价格快照；它们不是发布灰度配置。删除旧表后，不再承诺回滚到不支持 MinIO Reader 的旧二进制。

## 7. 数据生命周期

### 迁移期间

- MinIO 原始对象：保留，不设置自动 TTL；
- 旧 `session_content_events`：只读保留，用于测试服全量对账和旧镜像回退；
- 新目录/索引：可回填、可重建；
- 清理请求：继续按现有显式生命周期同时清理对象和派生数据。

### 稳定后

- 新上传不再生成 PostgreSQL 完整 Payload；
- 历史旧表在备份、完整性、消费者和观察期全部通过后整体下线；
- 不通过大批量 UPDATE 回收空间；
- MinIO 是否转冷、保留多久属于独立数据保留决策，本专项不擅自设定期限。

## 8. 容量与可观测性

至少监控：

- MinIO 对象数、字节数、上传/读取失败、哈希错误；
- PostgreSQL 各相关表 Heap/Index/TOAST 大小与日增长；
- catalog ready/building/failed 数与延迟；
- Report Source p50/p95/p99、扫描行数、超时；
- Content Reader 延迟、读取字节、失败对象；
- Token 快照创建耗时、事实行数、复用率、清理耗时。

容量告警用于提前发现增长，不替代数据保留策略。

回填和离线对账任务必须设置独立并发上限，并在数据库 CPU、I/O、连接池等待或前台 p95 超过阈值时自动暂停。专项任务的优先级始终低于现有上传、报告和页面请求。

## 9. 明确不采用

- 通过默认三天/七天日期限制解决 Report Source；
- 在现有 7GB 表上批量置空 Payload；
- 仅删除 superseded revision 作为主体治理；
- 让 Report Source 查询直接读 MinIO；
- 用内容事件中的 Token 文本替代规范化 Usage；
- 删除 Token 查询快照改成多个接口实时各算一次；
- 同一版本同时迁移目录、Payload、Digest 和 Token 事实。
