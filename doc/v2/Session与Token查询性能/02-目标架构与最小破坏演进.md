# 02：目标架构与最小破坏演进

## 1. 设计目标

目标不是一次性重写 Session 系统，而是在保持现有产品契约的条件下，让读取成本从“与历史明细量近似线性增长”变成“与当前筛选和返回结果规模相关”。

架构上采用：

> 一个规范化写入事实源 + 一套共享身份/生命周期契约 + 两套面向产品问题的读模型。

## 2. 目标全景

```text
                           ┌──────────────────────────────┐
                           │ 共享身份与生命周期契约       │
                           │ user / session / upload      │
                           │ slice / cursor / revision    │
                           └──────────────┬───────────────┘
                                          │
Aida 增量上传 ──> 规范化内容与 usage 事实 ─┼──────────────────────────┐
                                          │                          │
                                 内容处理与投影               usage 规范化与计费
                                          │                          │
                                          ▼                          ▼
                                 报告切片读模型               Token 分析事实模型
                                          │                          │
                                Report Source API             查询快照与分析 API
                                          │                          │
                                  冻结 slice/revision          页面一致性视图
                                          │
                                     Digest / 报告
```

共享的是身份、版本和可追溯性，不是同一张查询表。

## 3. 报告来源读模型

### 3.1 权威粒度

一个稳定的上传切片，即一次成功增量上传所形成的报告候选单元。

如果本地 Session 继续产生内容并再次上传，应形成新切片；之前已就绪的切片继续存在，不因 Session 尚未结束而失效。

### 3.2 读模型职责

只承载当前产品所需的稳定结果：

- 用户权限与 Session / slice 身份；
- 活动开始、结束和排序时间；
- 选择器摘要；
- 切片 Token 提示值；
- 内容就绪状态及其版本；
- 来源冻结需要引用的 generation/revision。

候选接口只做：

- 权限过滤；
- 活动日期相交判断；
- 关键词过滤；
- 排序；
- 分页和总数。

候选接口不做：

- 全量内容事件扫描；
- 现场生成摘要；
- 全量 usage 重算；
- Digest 构建；
- 上传失败修复；
- 报告来源冻结之外的状态推进。

### 3.3 维护方式

读模型应由异步处理增量维护，不能让 Aida 上传请求等待所有读取模型完成。

允许以下状态短暂存在：

```text
上传已接受 -> usage 已可统计 -> 内容仍处理中 -> 内容就绪 -> 可进入候选
```

也允许内容先于 usage 就绪。关键是所有状态通过同一上传切片身份关联，最终可以收敛和修复。

### 3.4 为什么不使用 Token Analytics 作为候选数据源

Token Analytics 按活动日期和分析过滤条件组织数据，不保留报告所需的上传切片和冻结版本语义。直接复用会造成：

- 跨日切片被错误拆分；
- 同一 Session 多次上传被错误合并；
- 报告无法冻结准确内容边界；
- 分析筛选条件意外改变报告来源。

因此只能共享底层 usage 身份，不能共享最终读模型。

## 4. Token Analytics 读模型

### 4.1 保留快照的原因

页面包含多个独立接口。若全部直接读取实时数据，即使每条查询更快，也可能出现：

- summary 与 sessions 总数不同；
- trends 与 rankings 使用不同截止时间；
- 页面加载期间组织成员变化造成权限范围不同；
- 价格或数据修正导致同一页面无法对账。

所以保留 `query_snapshot_token` 契约是最小风险选择。

### 4.2 可选架构

| 方案 | 做法 | 优点 | 风险/上限 | 当前判断 |
| --- | --- | --- | --- | --- |
| A. 优化现有组件级快照 | 保留当前明细复制，仅优化 SQL、索引、计数与并发 | 改动最小 | 数据量继续增长后上限有限 | 可作为近期止血 |
| B. 稳定分析事实 + 轻量快照 | 预先形成可聚合事实，快照引用版本或只物化必要范围 | 查询成本更稳定，保留一致性 | 需要定义事实粒度、历史回填和对账 | 推荐目标方向，待证据确认 |
| C. 去掉快照直接实时聚合 | 每个接口直接查当前事实 | 表面结构简单 | 多图表一致性和权限快照语义丢失 | 不建议 |

### 4.3 分析事实粒度

候选粒度是：

```text
Session × 业务自然日 × 模型 × 必要的 usage/计费维度
```

但在确认以下能力前不能锁定：

- 当前所有筛选条件能否准确下推；
- 缓存 Token、输入/输出 Token 等分项是否保留；
- 历史价格和价格快照如何计算；
- 组织成员与管理权限是否按查询时还是快照时解释；
- Session 搜索需要哪些字段；
- 修正、清理和重复上传如何反映。

### 4.4 快照优化原则

- 相同过滤条件的并发请求不能重复构建等价快照；
- summary、trends、rankings、sessions 必须读取同一个快照；
- count 和分页不应各自重建相同中间集合；
- 快照应记录明确的数据截止版本、权限范围和过期时间；
- 快照清理不能与前台查询争抢关键资源；
- 是否复用十五分钟内的已有快照，必须结合“新鲜度承诺”决定，不能只为性能私自延长。

## 5. 最小破坏原则

### 5.1 外部契约不先动

第一阶段保持：

- Report Source URL、请求参数和返回结构；
- Token Analytics 的接口集合及 `query_snapshot_token`；
- 前端页面、菜单、字段和日期交互；
- Aida 增量上传协议；
- Digest、报告生成、MCP 和 Skill 的冻结来源契约。

### 5.2 数据结构只允许附加式演进

后续若需要新增读模型：

- 先双写或离线回填；
- 新旧查询并行对账；
- 新查询通过开关灰度；
- 随时可切回旧查询；
- 稳定期结束前不删除旧字段、旧表或旧读取路径。

### 5.3 不把异步重新变成同步

性能优化不能通过让上传请求等待以下任务来实现：

- 内容全量投影；
- Digest 生成；
- Token Analytics 快照；
- 历史聚合；
- 报告候选索引全量重建。

Aida 只应等待本次上传协议定义的服务端确认；其余完成状态由服务端异步推进和观测。

## 6. 演进阶段

以下是架构演进边界，不是当前开发任务拆分。

### 阶段 0：冻结语义

- 确认两套读模型的粒度；
- 确认状态机及对用户暴露的最小语义；
- 确认 Token 对账公式；
- 确认 Digest 与候选可见性的关系；
- 确认 SLO 和新鲜度目标。

### 阶段 1：建立基线

- 记录接口与页面级 p50/p95/p99；
- 记录数据库执行、扫描行数、等待和连接池排队；
- 记录快照大小、创建次数、复用率和清理成本；
- 覆盖小、中、大历史数据账号以及并发场景。

### 阶段 2：契约内止血

- 保持 API 不变，优化重复 count、排序、聚合和当前页读取；
- 避免同条件并发创建等价快照；
- 增加超时、慢查询和关联日志；
- 不在这一阶段改变统计口径。

### 阶段 3：影子读模型

- 附加维护报告切片读模型；
- 附加维护稳定 Token 分析事实；
- 对历史数据回填；
- 新旧结果持续对账，但用户仍读取旧路径。

### 阶段 4：灰度切换

- 按环境或请求开关切换新读取路径；
- 观察正确率、延迟、数据库资源和异常恢复；
- 不满足条件时立即回旧路径；
- 完成稳定期后再评估旧路径下线。

## 7. 产品层面的最小变化

优先不增加新交互。

如果 Report Source 空列表仍容易让用户误解，可评审一个最小文案：

> 仅显示已完成内容处理、可用于报告的上传切片。刚上传的内容可能需要短暂处理。

该文案可以放在现有空状态或帮助说明中，不新增不可选行、不增加状态列，也不把选择器改造成任务中心。

Token Analytics 同样不建议在每个 Session 行新增“报告可用”字段。需要追查内容状态时，应进入 Session 管理入口，而不是让分析页面承担运维职责。

## 8. 兼容性与回滚

| 变化 | 兼容策略 | 回滚边界 |
| --- | --- | --- |
| Report Source 内部查询 | 响应契约不变 | 切回旧查询实现 |
| 报告切片读模型 | 双写、回填、影子对账 | 停止读取新模型，不影响写入事实 |
| Token 分析事实 | 保留原组件事实和旧快照 | 切回旧快照构建 |
| 快照复用策略 | token 契约不变 | 关闭复用或缩短有效期 |
| 前端空状态说明 | 不改变业务行为 | 直接回退文案 |

## 9. 当前不建议的方案

- 强制用户先选择日期；
- 把 Report Source 与 Token Analytics 合并为一个 API；
- 用 Token Analytics 的 Session 行生成报告候选；
- 把 processing/failed 项混入可选择列表；
- 删除快照并让各图表实时查询；
- 在没有查询计划和数据量证据前先上缓存、分区或读副本；
- 直接改变 Token 口径后以“性能优化”名义上线；
- 用一次破坏性迁移同时替换写入、读取、报告和 MCP 全链路。
