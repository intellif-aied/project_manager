# 04：Review 记录

> Review 日期：2026-07-16
> Review 目标：确认专项是否偏离现有产品形态，并把破坏性升级风险降到最低
> 结论：专项方向成立，但原草案存在多处产品语义扩大，需要先纠偏；暂不进入开发方案

## 1. Review 依据

本次对照了以下现有设计和实现：

- Session 增量上传与报告来源产品需求；
- Token 统计与成本产品需求；
- Session Digest 第一阶段需求和架构设计；
- Report Source 前端调用和选择交互；
- Token Analytics 前端快照复用流程；
- 服务端内容状态、usage 快照和分析查询结构。

## 2. 原方案中保留的判断

- 性能问题不是简单的分页 Bug；
- Report Source 不应在列表请求现场扫描全部历史明细；
- Token Analytics 的快照构建和多维聚合需要专项治理；
- 页面并发会放大单接口之外的数据库资源问题；
- 不应通过强制日期条件掩盖架构问题；
- 应先明确产品状态、数据边界和读取职责，再讨论迁移；
- 新读模型必须可回填、可双读、可回滚。

## 3. 必须纠正的内容

### 3.1 纠正：Session 未结束不代表不能用于报告

原方案容易把 Session 生命周期和报告候选生命周期绑定。

现有产品的固定语义是：

- 每次成功上传形成一个切片；
- Session 可以继续运行；
- 后续新增内容再次上传后形成新切片。

所以读模型的权威粒度应优先围绕上传切片，而不是“已结束的 Session”。

### 3.2 纠正：不在 Report Source 混入 processing/failed 行

原方案提出在选择器中区分可用、处理中、失败，并增加等待或重试操作。这会把报告选择器扩展成 Session 运维页面，也与既有“字段不增加、只选择候选切片”的产品约束冲突。

修订为：

- 列表只展示可选切片；
- 状态排查仍由 Session 管理入口承担；
- 如确有认知问题，只在现有空状态增加简短说明或入口；
- 不新增不可选行和状态列。

### 3.3 纠正：两处 Token 不是同一展示口径

原方案把“Session、Token Analytics、Report Source 的 Token 总数口径一致”写成验收目标，容易被理解为页面数字必须相等。

实际应该是：

- 报告切片按上传边界表达规模；
- Token Analytics 按活动日期和分析过滤聚合；
- 两者共享规范化 usage 来源并可以按规则对账；
- 跨日、多个切片和过滤条件会产生合理差异。

### 3.4 纠正：前端已经复用 snapshot token

原方案把“前端保存并复用 `query_snapshot_token`”列为待实施优化，但当前实现已经由 summary 创建快照，并由后续模块复用。

因此后续重点应转向：

- 快照首次创建成本；
- 快照明细粒度和行数；
- 快照内 count、分页和多维聚合；
- 相同条件并发构建；
- 清理和数据库资源争用。

### 3.5 纠正：不先承诺统一状态 API 或统一查询表

状态语义必须统一，但不等于立即新增一个统一状态 API 或一张万能表。

更稳妥的原则是：

- 先统一身份、状态含义和版本关系；
- 两个产品域保留独立读模型；
- 是否新增接口由实际页面缺口决定；
- 是否新增表由查询计划、数据量和回填成本决定。

### 3.6 纠正：Digest 就绪不自动成为候选门槛

Digest 是报告生成链路的稳定内容输入，但现有产品没有明确规定候选列表必须等 Digest 完成后才可见。

如果擅自增加该门槛，会让上传后候选出现得更晚。因此该问题保留为产品决策，不能在性能方案中默认改变。

## 4. 最小影响评估

| 范围 | 是否需要改变产品 | 推荐处理 |
| --- | --- | --- |
| Report Source 查询实现 | 否 | 保持接口与交互，内部逐步切到切片读模型 |
| Token Analytics 查询实现 | 否 | 保留 snapshot token，优化事实与快照内部结构 |
| Report Source 页面字段 | 否 | 不增加状态列 |
| Token Analytics 页面字段 | 否 | 不增加报告可用状态列 |
| Session 管理 | 暂无 | 继续作为内容状态排查入口 |
| Aida 上传协议 | 否 | Done 语义 Bug 单独修复 |
| 报告生成与 Digest | 否 | 保持冻结来源和 Digest 读取 |
| MCP / Skill | 否 | 不改变工具和内容契约 |
| Token/成本口径 | 否 | 性能版本禁止混入统计口径修改 |
| 数据库 | 后续可能 | 只接受附加式、双写、影子对账和可回滚变更 |

## 5. 风险排序

### 高风险

- 为统一数据而合并两种统计粒度；
- 让新汇总模型丢失模型、计费、权限或历史价格维度；
- 一次迁移同时替换上传、projection、查询和报告生成；
- 把异步处理改成上传同步等待；
- 新旧模型未对账就直接切换生产读取。

### 中风险

- 快照复用时间过长导致新鲜度下降；
- 历史回填与在线写入边界处理不严造成重复或缺失；
- 只优化单接口，页面并发和连接池问题仍存在；
- 切片摘要来源变化导致用户感知不一致。

### 低风险

- 保持契约的 SQL/索引优化；
- 慢查询、扫描量、快照大小和关联 ID 观测；
- 现有空状态中的说明文案；
- 通过只读影子查询进行新旧结果对账。

## 6. Review 后的方案定位

本专项最终被定位为：

> Session 上传数据读取架构的渐进式治理，而不是 Session 产品重做。

它包含两个相互协调、但不能合并的方向：

1. 报告来源：从查询时聚合转为上传切片读模型；
2. Token 分析：从高成本组件快照和重复聚合，演进为稳定分析事实加一致性快照。

共同基础是上传切片身份、版本、状态和 usage 可追溯性。

## 7. 当前 Review 结论

- 产品形态：保持现状，不做破坏性改版；
- 架构方向：一个事实源、共享身份契约、两套读模型；
- Report Source：切片读模型是长期方向；
- Token Analytics：保留快照，分析事实粒度待评审；
- Aida Done P0：单独修复，不等待本专项；
- Digest / MCP / Skill：保持兼容；
- 开发方案：暂缓，先完成关键问题和性能基线评审。
