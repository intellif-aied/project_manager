# Session 与 Token 查询性能专项

> 状态：产品与架构评审中
> 当前阶段：只确定产品边界、目标架构与演进原则，暂不进入表结构、迁移和开发排期
> 更新时间：2026-07-16

## 一句话结论

这不是要把 Report Source 和 Token Analytics 合并成一个模块，而是要在不改变现有产品形态的前提下：

- 统一上传数据的身份、版本和生命周期；
- 为“报告来源选择”和“Token 使用分析”分别建立适合自身统计粒度的读模型；
- 保留现有页面、接口和报告生成链路，通过双写、影子校验和可回滚切换逐步替换重查询。

## 为什么是一个专项、两套读模型

两个问题共享同一批上传数据，也会共同争用数据库资源，因此需要放在一个专项中治理；但它们回答的问题不同：

| 领域 | 用户问题 | 核心粒度 |
| --- | --- | --- |
| Report Source | 哪些已上传内容可以作为本次报告来源 | 一次成功上传形成的切片 |
| Token Analytics | 在某个活动日期和筛选范围内使用了多少 Token、产生多少成本 | usage 事实按活动日期、Session、模型等维度聚合 |

两者应当可以从同一批 usage 事实进行对账，但不要求页面上的单行 Token 数字相等。

## 当前明确不做

- 不强制给 Report Source 增加默认日期条件来掩盖慢查询；
- 不合并 Report Source 与 Token Analytics 的产品语义；
- 不改变现有选择器字段、日报生成入口和 Token 页面结构；
- 不让上传请求同步等待内容投影、Digest 或分析汇总全部完成；
- 不先确定新表、新迁移、缓存、分区或读副本；
- 不把本专项扩展成 MCP、Skill、Aida 上传协议的重写。

## 进入开发方案前的门槛

只有以下内容评审完成，才继续输出开发方案：

- 两套读模型各自的权威粒度和数据口径；
- “上传完成、内容可用、usage 可统计、Digest 可用、报告来源已冻结”的状态边界；
- Token Analytics 快照的保留方式；
- 新旧结果的对账规则；
- 性能目标、数据新鲜度、灰度和回滚要求。
