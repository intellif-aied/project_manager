# Session 与 Token 查询性能：完整发布清单

> 本文是本专项唯一的生产发布门禁。R1～R5 只是开发工作包，不是可以单独对外宣称“专项完成”的生产版本。

## 1. 强制规则

1. 每次生产发布必须有一份独立、可审计的完整清单；不得用聊天记录、日志或口头结论替代。
2. 清单中的每一项必须标记为“通过”，并附代码、迁移、数据对账、测试或部署证据。
3. 任一核心项为“未完成、进行中、未验证、仅测试服通过”，禁止生产发布。
4. 开发工作包可以分阶段完成，但在专项最终版本发布前，必须汇总为一次完整验收；不能把 R5B 的 Token 优化单独包装成“PG/MinIO 去重已完成”。
5. 历史数据回填、空间清理和生产发布必须分别记录。长时间任务必须有进度、暂停条件、失败数和最终结果，禁止无说明地持续运行。
6. 任何删除 PostgreSQL 内容 Payload 的动作，都必须在所有内容消费者迁移并完成全量对账后执行；没有清单通过不得删除。

## 2. 本专项完整版本的必选范围

以下四个领域缺一不可：

| 领域 | 必须完成的内容 | 不能用什么替代 |
| --- | --- | --- |
| Report Source | 切片目录、权限、排序、分页和显式活动日期过滤全部走轻量目录 | 只证明分页参数存在 |
| 内容存储 | Digest、冻结报告、MCP full、Session 详情统一从 MinIO Reader 读取；新写入不再保存完整 `content_payload` | 只把 Token 查询改快 |
| 历史清理 | 历史 Payload 完成对象/哈希/游标对账后，按批准的清理方案下线并回收 | 只生成 Token Rollup |
| Token Analytics | Contribution、Session family、按天、按 Chunk、成本、Snapshot、API/Web/MCP ad-hoc 同版本切换 | 只通过单个 Summary 接口 |

Digest、MCP、Session 内容详情、内容清理/恢复和 Token API 必须全部通过 [Digest 与接口影响回归矩阵](./06-Digest与接口影响回归矩阵.md)。

## 4. 生产发布判定

只有同时满足以下条件，发布状态才能写为“完成”：

```text
范围完整
  AND 内容消费者已迁移
  AND 新写入已停止完整 Payload
  AND 历史数据全量对账通过
  AND Token 三维对账通过
  AND Digest/MCP/Session/Token 回归通过
  AND p95/p99 达标
  AND 备份、镜像、配置、回滚证据齐全
```

否则只能写“部分开发完成/未发布”，不能写“生产已完成”。
