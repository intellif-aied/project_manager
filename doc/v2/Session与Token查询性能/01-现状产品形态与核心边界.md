# 01：现状产品形态与核心边界

> 后续实现必须遵守本文。性能优化不得偷偷改变产品结果。

## 1. 五个相关入口

| 入口 | 用户问题 | 权威对象 |
| --- | --- | --- |
| Aida CLI | 本地新增内容是否已上传 | 上传分块、游标、服务端确认 |
| Session 管理 | 平台收到了什么、处理到哪里 | Session 内容生命周期 |
| Report Source | 哪些内容切片可用于报告 | 已就绪上传切片 |
| Token Analytics | 指定范围用了多少 Token/成本 | Usage 与计费事实 |
| Digest / 报告 | 本次报告实际读取什么 | 冻结切片及其版本 |

它们共享 Session、上传和版本身份，但不能共享一个模糊的 `Done`，也不能使用一张万能查询表。

## 2. Session 与切片语义

```text
Session 持续工作
  -> 增量上传成功：形成切片 A
  -> Session 继续工作
  -> 再次增量上传成功：形成切片 B
```

固定规则：

- 一次成功增量上传形成一个切片；
- Session 不需要结束；
- 一个 Session 可以有多个切片；
- 切片按上传游标形成，不按自然日强拆；
- 内容投影与 Usage 处理可先后完成，但必须关联到同一上传身份。

## 3. Report Source 产品契约

它回答：“哪些内容已就绪的上传切片，可以作为这份个人日报/周报的来源？”

当前边界：

- 只展示可选择切片，不混入 processing/failed 运维记录；
- 展示活动时间、Session/切片摘要等已有信息；
- 不展示 Token，也不为列表计算 Token；
- 支持关键词和分页；
- 用户选择后冻结具体 slice、generation、revision 与 cursor；
- Session 后续上传的新切片不会进入已经冻结的报告。

### 日期契约

- `period_start`、`period_end` 只描述当前报告周期，不过滤候选；
- 默认展示用户全部可选切片；
- 用户显式传 `activity_from`、`activity_to` 后，按切片活动范围相交过滤；
- 日期过滤不是上传时间过滤；
- 命中日期的切片仍作为完整切片被选择和冻结。

### 分页契约

- `page_size` 限制返回条数；
- total 是满足权限和显式筛选条件的切片数；
- 列表读取不得因某个切片包含几十万事件而变慢；
- 日期参数只能改变候选集合，不能改变底层数据源。

## 4. Token Analytics 产品契约

它回答：“在活动日期、权限和筛选范围内，发生了多少 Usage、Token 和成本？”

固定规则：

- 活动日期是 Usage 发生日期；
- 支持汇总、趋势、排名和 Session 列表；
- Session 行是在当前条件下的聚合结果，不是报告切片；
- summary、trends、rankings、sessions 读取同一 `query_snapshot_token`；
- 统计必须保留现有 Token 分项、模型、价格、汇率和权限口径。

当前实现的 Session 行按实际 `session_id` 聚合，`session_daily_usage` 按实际 Session/日期聚合，尚未形成“顶层 Session 包含全部 Subagent”的家族总量，也没有可靠的新增 Chunk Delta Rollup。这是本专项明确需要补齐的产品缺口，不属于纯 SQL 优化。

新增的固定产品语义：

- 顶层 Session 总量包含自身及全部层级 Subagent；
- Subagent 复制的父历史不计入子 Agent 新增量；
- 同一顶层 Session 同时具备生命周期总量、按上海业务日、按新增 Chunk 三个维度；
- 日期筛选得到的是 `range_total`，不能冒充生命周期总量；
- 默认 Session 列表按 root Session 去重展示，成员明细不得再与父行重复求和；
- 三个维度必须从同一 Contribution 事实对账，不允许各自使用不同估算逻辑。

Report Source 不再展示 Token，因此不再存在“两个页面单行 Token 必须相等”的产品要求。两者只要求能追溯到同一上传/Usage 事实，便于事故排查和数据对账。

## 5. MinIO 与 PostgreSQL 当前状态

当前链路中：

- MinIO 保存上传的原始 JSONL/分块对象；
- projection 逐行解析并写入事件时间、类型、摘要、游标和哈希；
- 同时把清洗后的完整事件 JSON 写入 PostgreSQL `content_payload`；
- Digest V1/V2 和部分内容读取直接查询该 JSONB；
- Report Source 仍从事件表读取活动时间和摘要。

这解释了为什么不能直接删 `content_payload`：它虽然是重复载荷，但当前仍有消费者。必须先完成读取器迁移与一致性验证。

## 6. 必须保护的状态边界

| 状态 | 含义 | 不能推导 |
| --- | --- | --- |
| 上传已接收 | 服务端接受本次分块 | 内容、Usage、Digest 已就绪 |
| 内容投影就绪 | 内容可稳定读取 | Usage 已计价 |
| Usage 就绪 | Token/成本事实可统计 | 内容可生成报告 |
| Digest 就绪 | 冻结内容摘要可读取 | 已被某份报告选择 |
| 来源已冻结 | 报告绑定确定切片版本 | Session 已结束 |

## 7. 本专项不得改变

- Aida 增量上传协议；
- 一次上传一个切片的语义；
- 报告来源的完整切片冻结；
- Report API、Agent、MCP、Skill 对冻结来源的契约；
- 除 [Token 三维统计](./07-Token三维统计与对账模型.md) 已明确的家族/日期/Chunk 语义外，不得顺带改变 Token/成本口径；
- Token API、前端与 MCP ad-hoc 在同一内测版本协同切换；新字段语义必须显式，旧 `total_tokens` 不得静默改义；
- Report Source、报告生成和 MCP 的现有页面/工具操作流程；
- 用户数据清理的显式授权与审计语义。
