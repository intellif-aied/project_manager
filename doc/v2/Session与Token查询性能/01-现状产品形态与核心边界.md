# 01：现状产品形态与核心边界

> 本文只描述系统当前已经形成的产品语义。后续架构优化必须兼容这些边界，除非另立产品需求明确变更。

## 1. 当前产品不是一个 Session 列表

围绕 Session，系统实际上有五个不同产品入口：

| 产品入口 | 用户目的 | 当前权威对象 |
| --- | --- | --- |
| Aida CLI | 把本地新增内容和 usage 上传到平台 | 上传批次、游标和服务端确认 |
| Session 管理 | 查看平台接收到的 Session 及处理状态 | Session 内容生命周期 |
| Report Source | 选择可用于报告的内容来源 | 已就绪的上传切片 |
| Token Analytics | 查看 usage、Token 和成本 | 活动日期范围内的 usage 事实 |
| Digest / 报告 | 基于冻结来源生成报告 | 冻结切片及其版本 |

这五个入口共享 Session 身份，但不能共用一个模糊的“Session 完成”概念。

## 2. 当前主流程

```text
本地 Session 持续产生内容
  │
  ├─ 第一次上传当前已有内容 ──> 成功后形成切片 A
  │
  ├─ Session 继续运行
  │
  └─ 再次上传新增内容 ───────> 成功后形成切片 B

服务端异步处理每次上传
  ├─ 内容投影 ──> 切片可读取 ──> Report Source / Digest
  └─ usage 处理 ─> usage 可统计 ─> Token Analytics
```

固定语义：

- 一次成功上传形成一个切片；
- 本地 Session 不需要结束才能形成可选切片；
- 一个 Session 可以对应多个上传切片；
- 切片不按自然日强制拆分；
- 内容处理和 usage 处理可以并行完成，短时间内状态不同是允许的。

## 3. Report Source 当前产品形态

### 3.1 它回答的问题

“哪些已完成内容处理的上传切片，可以作为这份报告的来源？”

### 3.2 展示和交互

当前选择器的核心信息是：

- 活动日期；
- Session ID / 切片摘要；
- Token 提示值。

当前产品已明确不通过增加大量展示字段或展开行，把它变成 Session 运维页面。

### 3.3 日期语义

- 默认不要求用户先选择日期；
- 用户选择活动日期范围后，只要切片活动范围与其相交，就显示整个切片；
- 日期过滤不是上传日期过滤；
- 日报周期和用户手动选择的候选日期是两个不同概念。

### 3.4 冻结语义

- 用户显式选择后，冻结具体切片；
- Session 后续新增并再次上传形成的新切片，不自动进入已经发起的报告；
- 未显式选择时，由服务端按报告周期选出相交切片并冻结；
- 生成链路使用冻结版本，避免报告过程中来源漂移。

### 3.5 当前加载行为

前端在用户打开来源选择器时才请求候选列表，不会在 Dashboard 每次渲染时无条件加载该接口。

因此，单独调用接口已变快但浏览器仍等待很久时，需要区分：

- 该接口自身耗时；
- 浏览器连接受前序请求或连接数限制；
- Dashboard 其他慢请求对数据库和网络连接的争用。

## 4. Token Analytics 当前产品形态

### 4.1 它回答的问题

“在所选活动日期、权限范围和过滤条件内，发生了多少 usage、Token 和成本？”

它不回答“哪些内容已经可生成日报”。

### 4.2 统计粒度

现有产品包含：

- 汇总；
- 趋势；
- 排名；
- Session 维度列表。

其中活动切片的基础语义是 `Session × 业务自然日`；Session 列表则把当前查询范围内属于同一 Session 的 usage 聚合为一行。

实际统计还会受到用户/组织权限、模型、日期、搜索和价格口径等条件影响。

### 4.3 快照语义

Token Analytics 先确定一个查询快照，再让 summary、trends、rankings 和 sessions 读取同一快照，目的是避免：

- 页面加载过程中新增上传导致不同图表时间点不同；
- 组织权限或过滤范围在多个请求之间漂移；
- 同一页面的汇总与明细无法对账。

当前前端已经保存并复用 `query_snapshot_token`。因此现有慢点主要位于：

- 首次快照构建；
- 快照包含的明细数量；
- 对快照重复执行的聚合、排序、计数和分页；
- 多个用户或页面并发时的数据库资源消耗。

## 5. 两种 Token 口径的关系

### 5.1 Report Source 切片 Token

服务于“识别这次上传切片的规模”，理想边界是本次增量上传对应的 usage 范围。

### 5.2 Token Analytics Session Token

服务于“分析指定活动日期和过滤条件内的 usage”，可能聚合一个 Session 的多个上传切片，也可能只覆盖某个切片的一部分活动日期。

### 5.3 一致性要求

要求：

- 都能追溯到规范化后的 usage 事实；
- 给定同一截止版本和可比过滤条件时能够对账；
- 重试和重复上传不能重复计数；
- usage 已持久化但内容处理失败时，状态差异必须可解释、可恢复。

不要求：

- 两个页面单行数字始终相等；
- 为了让数字相等而改变现有日期语义；
- 用 Token Analytics 快照直接充当报告来源切片。

## 6. 不能合并的状态

| 状态维度 | 成功意味着什么 | 主要消费者 |
| --- | --- | --- |
| 上传接收 | 本次数据已被服务端接受 | Aida、上传 API |
| 内容投影 | 切片内容已形成稳定读取结果 | Session、Report Source |
| usage 处理 | usage 事实已规范化并可统计 | Token Analytics |
| Digest | 冻结内容对应摘要已生成 | 报告生成 |
| 来源冻结 | 某份报告已绑定确定切片和版本 | Report API、Agent、Skill |

同一次上传的不同维度可以短暂先后完成，但不能永久失联。

## 7. 当前性能问题的真实形态

### 7.1 Report Source

分页发生在候选集合形成之后。如果候选集合需要从大量内容事件和 usage 明细实时计算，那么 `page_size=5` 仍可能先处理用户的全部历史数据。

### 7.2 Token Analytics

快照保障了一致性，但如果每次快照都复制大量组件级明细，随后多个接口又各自做大范围聚合，页面仍会慢。

### 7.3 页面级放大

当 Dashboard、Token Analytics 和其他统计请求并发时，即使某个接口单独测试很快，仍可能因为以下原因在页面上表现为卡顿：

- 连接池排队；
- 数据库 CPU / I/O 争用；
- 大快照写入和清理；
- 多个 count、排序和聚合同时执行；
- 浏览器同源连接排队。

所以专项验收不能只看单个 curl。

## 8. 当前必须保护的兼容边界

- 不改变一次上传形成一个切片；
- 不要求 Session 结束后才能用于报告；
- 不强制默认日期；
- 不新增选择器业务字段；
- 不把处理中或失败记录伪装成可选择来源；
- 不改变显式选择和服务端默认选择的冻结语义；
- 不把 Token 页面变成内容处理状态页；
- 不让 MCP、Agent 或 Skill 读取未冻结的动态来源；
- 不以性能优化名义改变 Token 和成本统计口径。
