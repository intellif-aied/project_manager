# 00：生产事故复盘（2026-07-17）

## 1. 事故定性

这是一次生产查询性能与存储边界设计事故，未发现数据丢失或越权读取。事故暴露了两个问题：

1. 分页接口在分页前扫描内容事件，`page_size=10` 并没有限制实际处理量；
2. MinIO 已保存原始 JSONL，PostgreSQL 又把几乎完整的事件 JSON 写入 `JSONB`，形成长期双份大载荷。

止血 SQL 已降低当前接口耗时，但它仍依赖事件表，不是最终架构。

## 2. 生产证据快照

| 指标 | 2026-07-17 排查结果 | 说明 |
| --- | ---: | --- |
| `session_content_events` 行数 | 约 321.4 万 | 事件级投影长期累积 |
| PostgreSQL 表总大小 | 约 7.1GB | Heap 约 2.96GB、索引约 0.92GB、TOAST 约 3.27GB |
| MinIO 原始 Session 内容 | 约 7.48GB | 已保存原始 JSONL/上传分块 |
| 问题用户候选切片 | 37 个 | 分页仅请求 10 条 |
| 旧查询读取事件 | 约 18.18 万条 | 分页前先形成全部候选、摘要和统计 |
| 旧接口耗时 | 约 16 秒 | 与返回 10 条不匹配 |
| 止血后耗时 | 约 50～115ms | 仍会从事件表取切片首尾时间及当前页摘要 |
| superseded 事件占比 | 约 4.4% | 只删除旧 revision 无法解决主体容量问题 |

补充观察：少量超大 Session 占据大部分事件与原始对象容量，因此不能用“平均 Session 大小”估算风险。

## 3. 根因链路

```text
MinIO 保存原始 JSONL
  -> projection worker 逐行解析
  -> 将清洗后的整行 JSON 再写入 content_payload JSONB
  -> Digest / 内容读取直接依赖 PostgreSQL JSONB
  -> Report Source 候选查询又从事件表计算活动时间和摘要
  -> 先扫描/聚合，再排序/计数，最后才 LIMIT/OFFSET
```

因此：

- PostgreSQL 同时承担了元数据索引、全文载荷仓库和在线列表计算；
- TOAST 与原始对象规模接近，存储增长不可控；
- 分页只能减少响应行数，无法减少分页前的事件扫描；
- 日期条件看似能减少数据，但那是在改变产品结果掩盖错误的数据读取层级。

## 4. 为什么不是索引不足

索引可以让“在一个 revision 内找首尾事件”更快，但无法把错误的读取职责变正确：

- 候选列表所需字段本来就应在切片完成时写好；
- 列表请求不应读取事件载荷；
- exact total 最多扫描候选切片目录，不能扫描原始事件；
- 即使某条 SQL 已经降到百毫秒，事件数量继续增长后仍会重新恶化。

## 5. 已完成的止血与剩余风险

当前止血将工作限制为：

- 每个候选切片利用索引读取首尾事件；
- 先完成候选分页，再只为当前页读取摘要；
- `period_start`、`period_end` 不再被当作隐式活动日期过滤；
- 只有显式 `activity_from`、`activity_to` 才过滤候选。

剩余风险：

- 无日期请求仍需逐个候选触碰事件表；
- 搜索摘要仍可能读取事件；
- Digest V1/V2 仍读取 `content_payload`；
- PostgreSQL 与 MinIO 的全载荷重复仍在增长；
- 直接批量 `UPDATE content_payload=NULL` 会制造大规模 WAL 和表膨胀，不能作为清理方案。

## 6. 事故后的强制规则

1. 候选分页执行计划不得出现事件表或 Usage 明细表。
2. 未完成 MinIO 完整性校验与消费者迁移前，不删除任何生产载荷。
3. 不以默认日期、减少返回字段以外的语义变化来掩盖性能问题。
4. 不对 7GB 表做一次性批量更新、重写或无回滚删除。
5. 压测只能在隔离测试数据集执行，生产只做低风险观测与抽样校验。
6. 存储治理、Report Source、Token Analytics 必须拆成独立发布单元；每个单元在测试服全量验收后整体切换，并能通过上一 Git 提交/镜像回滚。
