# 03：关键决策与待评审问题

> 本文用于控制方案不跑偏。已确认项是后续开发方案的约束；待评审项未确认前，不确定表结构和迁移。

## 1. 已确认的产品决策

| 编号 | 决策 | 原因 |
| --- | --- | --- |
| D-01 | 一次成功增量上传形成一个报告切片 | 与现有 Session 增量上传产品定义一致 |
| D-02 | 本地 Session 不需要结束才能形成切片 | 支持长 Session 分阶段上传和生成日报 |
| D-03 | Report Source 只展示可选择的已就绪切片 | 保持选择器职责，不混入运维列表 |
| D-04 | Report Source 默认不强制日期 | 性能问题不能通过缩小产品范围掩盖 |
| D-05 | 切片与日期相交时展示和冻结整个切片 | 保持现有报告来源语义 |
| D-06 | Token Analytics 按活动日期和分析条件统计 | 维持既有 usage/成本产品口径 |
| D-07 | 报告切片 Token 与分析 Token 不要求逐行相等 | 两者统计粒度和过滤条件不同 |
| D-08 | Token Analytics 保留查询快照语义 | 保证页面多个模块同范围、同截止时间 |
| D-09 | Report Source 和 Token Analytics 使用不同读模型 | 两者不能互相替代，但需要可追溯对账 |
| D-10 | 第一轮保持 API、页面、MCP、Skill、上传协议兼容 | 控制破坏面和发布风险 |
| D-11 | 新读模型采用附加、双读、可回滚方式演进 | 避免破坏性升级 |
| D-12 | 纯性能优化不改变 Token/成本统计口径 | 便于验证、回滚和事故归因 |

| A-01 | 共享上传身份、切片、游标和版本契约 | 采用 |
| A-02 | Report Source 建立上传切片粒度读模型 | 目标方向 |

## 3. 开发方案前必须回答的问题

### Q-01：切片摘要的权威来源是什么

候选：

- 内容投影阶段形成的稳定摘要；
- Digest 的标题/摘要；
- 现有列表的摘要逻辑预计算结果。

判断标准：

- 是否需要等待 Digest；
- 是否能增量维护；
- 历史回填成本；
- 与当前用户可见文本是否兼容。

在该问题确定前，不应把 `summary` 固定到某个新表生成流程。

### Q-02：Report Source 切片 Token 的精确边界是什么

需要明确：

- 按上传游标区间归属，还是按内容事件范围归属；
- 一条 usage 组件跨越切片边界时如何处理；
- 重试、重复前缀和补传如何去重；
- usage 晚于内容到达时如何补记；
- 清理或重建内容是否影响历史 Token。

目标是稳定和可解释，不是强行与 Token Analytics 每一行相等。

### Q-03：Token 分析事实的最小保真粒度是什么

需要用现有全部查询条件反推，而不是先拍板为日汇总：

- 是否需要保留模型、提供方、缓存 Token 和计费类型；
- 管理员的组织/用户筛选如何支持；
- Session 搜索和排名如何支持；
- 价格变更后历史成本是否重算；
- 数据修正如何覆盖已聚合结果。

### Q-04：查询快照的新鲜度承诺是什么

需要确定：

- 页面打开后多长时间内应看到新上传数据；
- 同过滤条件快照是否允许复用；
- 当前十五分钟有效期是产品承诺还是内部实现；
- 用户主动刷新是否强制新快照；
- 管理员权限变更是否立即让旧快照失效。

### Q-05：组织权限按哪个时间点解释

快照构建后，若用户加入或离开组织：

- 旧快照是否继续有效；
- 快照记录成员集合还是只记录查询条件；
- 管理员查看历史数据时使用当前权限还是快照权限。

这是正确性和安全边界，不能只按性能选择。

### Q-06：Digest 是否成为候选可见性的前置条件

当前应先区分：

- 内容已经可读取；
- Digest 已经生成；
- 报告生成启动时可以等待或触发 Digest。

不建议未经产品确认就让 Report Source 必须等待 Digest，否则会扩大“上传后不可见”的时间窗口。

### Q-07：状态需要暴露到什么程度

最小方案是：

- Report Source 仍只显示可选切片；
- 现有空状态增加说明；
- Session 管理页面继续承担处理状态和失败排查。

只有用户研究证明仍无法理解时，再考虑跨页面状态提示，不应直接新增选择器列。

### Q-08：性能目标是什么

开发前至少需要分别确定：

- Report Source 单接口冷/热查询 p95；
- Token Analytics 首次快照 p95；
- 已有快照下各子接口 p95；
- 页面全模块可交互时间；
- 单用户大历史量和多用户并发目标；
- 数据库连接、CPU、内存和临时空间上限。

暂不在没有生产基线时填写一个看似精确的毫秒数字。

## 4. 对账规则需要单独产出

进入影子读模型阶段前，应形成可执行的对账规范：

```text
同一用户/权限范围
+ 同一数据截止版本
+ 可比的活动日期和模型过滤
+ 相同的 usage 去重规则
= 新旧 Token 统计可对账
```

对账结果至少分类：

- 完全一致；
- 因粒度差异可解释；
- 因处理延迟暂时不一致；
- 因重复、丢失、权限或版本错误不可解释。

不能只比较页面总数，也不能把所有差异都归结为“异步最终一致”。

## 5. 与其他事项的边界

### 5.1 Aida Done 与服务端状态不一致 P0

相关原因是状态边界模糊，但它是独立正确性 Bug：

- 应单独修正客户端成功提示的定义；
- 应验证服务端 finalize、内容和 usage 的最终状态；
- 不需要等待本专项新读模型才能修；
- 本专项不能用性能重构掩盖该 Bug。

### 5.2 Session Digest V2

本专项依赖 Digest 的冻结来源语义，但不重写 Digest：

- Digest 继续服务报告内容压缩；
- Token Analytics 不读取 Digest；
- Report Source 的摘要是否复用 Digest，仍是待决策项；
- 候选可见是否等待 Digest，仍是待决策项。

### 5.3 MCP、Agent 与 Skill

最小演进不改变它们的工具契约：

- 它们消费冻结报告来源或 Digest；
- 不直接消费 Token Analytics 查询快照；
- 不允许因为候选列表优化改为读取动态 Session 全量内容。

## 6. 评审通过标准

产品与架构方案可以进入开发设计，需要满足：

- 已确认决策没有与现有产品需求冲突；
- Q-01 至 Q-08 有明确结论或被拆成独立前置事项；
- 两套读模型的权威粒度和对账边界明确；
- 没有隐含改变日报来源、Token/成本或权限口径；
- 可以双写、影子验证、灰度和回滚；
- P0 正确性 Bug 与长期性能架构的发布边界清晰。
