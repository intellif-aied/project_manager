# 旧归档表保留与最终清理专项方案

## 1. 目的

明确 `session_content_events_payload_archive` 的保留、观察和最终清理方式，避免误删线上新表或因残留同步触发器影响新数据写入。

## 2. 当前生产状态

- `session_content_events`：瘦身后的新表，线上业务正在使用。
- `session_content_events_payload_archive`：旧表，仅作为回滚备份保留。
- 新旧表切换已完成，之前的生产数据校验和接口验收已通过。
- 旧表上的两个同步触发器已关闭，旧表现在是静态备份，不再接收新增数据。
- compaction state 暂时保持 `swapped`，不标记为 `finalized`，因为旧表仍然保留。
- 当前不执行任何全量或增量数据对比。

## 3. 保留期间的影响

### 3.1 业务影响

- 日报、周报、Session、Token、MCP 等接口继续读取新表。
- 旧表不参与普通业务查询。
- 关闭同步后，新数据不会写入旧表。

### 3.2 运维影响

- 旧表继续占用数据库磁盘空间。
- 旧表只能回滚到关闭同步之前的状态，关闭同步之后产生的数据不在旧表中。
- 旧表统计中的历史扫描/写入次数是累计值，不代表当前仍在使用。

## 4. 观察期要求

观察期间只做只读检查，不修改数据：

1. 首页、日报、周报、Session、Token、MCP 接口正常；
2. `session_content_events_payload_archive` 没有新的写入；
3. PostgreSQL 当前活动连接中没有业务 SQL 查询旧表；
4. 新表持续接收正常业务数据；
5. 数据库磁盘空间保持可用。

不要求重新扫描或对比 321 万条历史记录。

## 5. 最终清理前提

运维和项目负责人确认以下事项后，才允许清理：

- 不再需要回滚到旧表；
- 观察期内新表业务稳定；
- 已确认存在可用的生产数据库备份；
- 已安排短维护窗口；
- 明确接受删除后无法恢复旧表。

## 6. 最终清理动作

清理必须在一个受控事务和维护窗口内完成：

1. 确认当前 state 为 `swapped`；
2. 确认新表存在且无 `content_payload`；
3. 确认旧表存在；
4. 确认相关同步触发器已经关闭；
5. 删除旧归档表；
6. 删除不再使用的镜像函数；
7. 更新 compaction state 为 `finalized`；
8. 执行空间回收/分析；
9. 验证核心业务接口和上传链路。

禁止：

- 删除 `session_content_events` 新表；
- 在未确认备份和维护窗口前删除旧表；
- 重新启用已关闭的旧表同步后直接删除；
- 用手工命令绕过上述检查并直接删除生产表。

## 7. 清理后验收

- `session_content_events` 存在；
- `session_content_events_payload_archive` 不存在；
- compaction state 为 `finalized`；
- 新表无 `content_payload`；
- 新增上传成功；
- 日报、周报、Session、Token、MCP 接口正常；
- 数据库磁盘空间较清理前明显下降。

## 8. 回滚说明

观察期间：不删除旧表，可继续保留现状。

完成最终清理后：旧表无法通过应用层回滚，只能依赖清理前的数据库备份恢复。因此最终清理必须获得运维确认。
