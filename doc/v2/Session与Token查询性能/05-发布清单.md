## 2. 发布单元

这是有数据依赖的三次明确发布，不是用户灰度。

### 2.1 内容读链路

范围：Content Reader、Digest V1/V2、MCP full、V2 Session、清理/恢复兼容。Payload 写入暂时保留。

门禁：Reader 和所有消费者测试通过，全仓已无未登记 Payload 读取者。

回滚：回退到本次发布前 API 镜像；因 Payload 仍持续写入，数据兼容。

### 2.2 停止 Payload 写入

范围：Content Projection 不再写完整 Payload。

门禁：内容读链路已发布并通过生产冒烟；新上传端到端回归通过。

回滚：只能回退到上一个 Reader 版本，不得回到依赖 Payload 读取的版本。

### 2.3 历史数据紧凑

范围：MinIO 盘点、紧凑表 migration、分批复制/对账、表切换、回滚窗口后删旧表。

> 下面保留的是专项最终完整序列，不代表每次生产都可以执行到结尾。2026-07-18 本次执行只能以《06-生产发布与历史迁移执行单》为准，最远到 `verify`，不得执行 `cutover/rollback/finalize`。

门禁：新 Payload 已停止；等量副本演练和备份恢复验证通过。

回滚：旧表在回滚窗口内保留；旧表删除是最后的不可逆操作。

固定执行序列：

```text
audit-session-content plan（冻结 MinIO 盘点快照）
  -> audit-session-content scan --snapshot-through-revision-id S --limit N --max-bytes B（N ≤ 50、B ≤ 10 GiB，反复到 complete=true 且 failures=0）
  -> compact-session-events plan（只读估值，不全表 COUNT）
  -> copy --apply --batch-size N --max-batches M（有界，可续跑）
  -> mirror --apply
  -> reconcile --apply --batch-size N --max-batches M（反复到完成）
  -> verify（missing=0、extra=0、mismatch=0）
  -> cutover --apply --expected-source-rows X
  -> API/报告/Token 冒烟与观察
  -> 双向镜像回滚窗口；按清单执行一次 rollback 演练或保留旧表
  -> finalize --apply --confirm-drop session_content_events_payload_archive
```

`copy/reconcile` 的 `batch-size` 最大 10,000、`max-batches` 最大 20；MinIO 单次最多 50 revision，默认字节预算 1 GiB、硬上限 10 GiB。禁止跳过 `verify`，禁止把命令包装成无停止条件的常驻任务，禁止在切换当天直接执行 `finalize`。

容器内命令模板（`S/A/X` 必须来自上一条命令的 JSON 输出，不能手填猜测）：

```bash
docker compose exec api audit-session-content --action plan
docker compose exec api audit-session-content --action scan --snapshot-through-revision-id S --limit 50 --max-bytes 1073741824 --after-revision-id A
docker compose exec api compact-session-events --action plan
docker compose exec api compact-session-events --action copy --apply --batch-size 5000 --max-batches 10
docker compose exec api compact-session-events --action mirror --apply
docker compose exec api compact-session-events --action reconcile --apply --batch-size 5000 --max-batches 10
docker compose exec api compact-session-events --action verify
docker compose exec api compact-session-events --action cutover --apply --expected-source-rows X --lock-timeout 5s --statement-timeout 5s
docker compose exec api compact-session-events --action rollback --apply --expected-source-rows X --lock-timeout 5s --statement-timeout 5s
docker compose exec api compact-session-events --action finalize --apply --confirm-drop session_content_events_payload_archive --lock-timeout 5s --statement-timeout 5s
```

首批 scan 不传 `--after-revision-id`；后续批次使用上一批 `next_after_revision_id`。`byte_budget_exhausted=true` 时，该批不会推进 `budget_blocked_revision_id`，应在硬上限内提高 `--max-bytes` 后从原 cursor 重跑。任一批 `failed_revisions > 0` 时，以 `--revision-id <失败 revision> --max-bytes B` 单条复验，未清零不得进入 compact。`verify` 的 `row_counts_exact=true` 且 missing/extra/mismatch 均为 0 后，其 `source_rows` 才能作为 cutover 的 `X`；cutover 后重新执行 `verify`，其 `target_rows` 才能作为 rollback 的 `X`。实际生产 Compose 文件名/目录按当次完整发布清单填写，不得默认猜测。
