# AIDA-BUG-20260716-004：日报来源候选切片列表查询性能事故

> 优先级：P0  
> 状态：第一阶段已修复，14.157 已验证，待生产发布观察  
> 发现时间：2026-07-16  
> 发现环境：测试服 `192.168.14.157`  
> 影响接口：`GET /api/v1/report-source-sessions`  
> 主要责任边界：服务端 Report Source 候选列表查询与分页实现  
> 当前原则：第一阶段 Bug 修复已实施；本文件记录发布验收和后续待定方案。

## 1. 问题结论

日报来源候选切片列表接口虽然提供 `page/page_size`，但当前实现会先对用户全部候选切片执行完整事件聚合、摘要计算和 Token 统计，再分别执行总数查询和分页查询。`LIMIT 5` 只限制最终返回行数，不能限制前置计算量。

这会造成：

- 首次或缓存未命中时列表请求耗时 18～30 秒；
- 并发请求可能在 30 秒上下文/网关超时并返回 HTTP 500；
- 用户只是打开选择列表，却触发日报生成前才应执行的重计算；
- 用户候选切片数量和事件量增长后，耗时线性恶化。

这是 P0 级生产可用性问题。它不是默认日期条件的功能错误：前端未选择自定义日期时不传 `activity_from/activity_to`，产品语义就是返回全部候选切片；`period_start/period_end` 是日报周期上下文，不承担默认列表过滤。

## 2. 真实取证

测试账号 uid `303`，请求：

```text
GET /api/v1/report-source-sessions?report_type=personal_daily
    &period_start=2026-07-16&period_end=2026-07-16&page=1&page_size=5
```

观测结果：

| 项目 | 结果 |
| --- | ---: |
| 用户 sessions | 61 |
| session content slices | 20 |
| active projection revisions | 19 |
| 相关事件量 | 约 168,842 |
| 默认无日期候选总数 | 18 |
| 冷查询耗时 | 约 18.7 秒 |
| 并发/超时请求 | 约 30 秒后 HTTP 500 |
| 缓存变热后 | 约 1.2～1.5 秒 |
| 加自定义活动日期筛选 | 约 3.4 秒，候选总数 11 |

直接请求后端 `18090` 与经过前端 `5173` 的耗时基本一致，问题不在 Vite 代理或前端转发。

## 3. 根因分析

`api/internal/reportsource/service.go` 当前构造 `all_candidates` CTE，对每个切片执行：

1. 扫描 active projection 的事件并做 `MIN/MAX` 活动时间聚合；
2. 通过相关子查询计算摘要；
3. 通过相关子查询聚合上传 Token；
4. 再按关键词和可选活动时间筛选。

随后同一个候选 CTE 被完整执行两次：

```sql
SELECT COUNT(*) FROM candidates;
SELECT ... FROM candidates ORDER BY ... LIMIT $page_size OFFSET $offset;
```

因此当前 P0 Bug 的直接修复范围是：`COUNT` 和分页结果重复计算候选集合，以及列表接口统计了不影响列表展示的 Token 字段。摘要、活动时间等现有返回字段本轮暂不改变，避免扩大接口和数据模型变更。

## 4. 设计判断

本轮不做完整数据流重构。保持现有 API 返回结构、默认日期语义、Session Token 统计口径和日报生成流程不变，仅修复列表查询的重复计算和无必要 Token 统计。

保留以下产品语义：未选择自定义日期时默认不按日期过滤；传入 `activity_from/activity_to` 时按活动区间重叠筛选；`page/page_size` 应真正限制查询成本，而不只是限制响应行数。

## 5. 修复方案

### 5.1 本次实施：P0 列表查询 Bug 修复

1. 将候选集合只构造一次，优先采用 `COUNT(*) OVER()` 随分页结果返回总数，或使用同一物化候选结果完成 count 与 page 查询；
2. 从候选列表查询中移除不用于列表展示的 Token 汇总子查询；
3. 保持现有摘要、活动时间、关键词、日期筛选、排序和响应字段不变；
4. 保持默认无日期过滤的行为不变；
5. 增加请求耗时和 HTTP 5xx 观测，便于验证修复效果。

本次不新增数据库迁移，不修改 MCP、Aida 客户端、上传协议、Session Token 统计口径或日报生成流程。

### 5.2 后续方案：待定，不纳入本次 Bug 修复

以下内容不作为本次上线前置条件，待第一步上线并取得性能数据后再单独评估：

1. 切片级活动时间、摘要和 Token 预聚合字段/表；
2. 列表与 Digest/报告生成流程的彻底解耦；
3. 历史数据回填和候选快照缓存；
4. 更大范围的 Session、MCP、Skill 和 Token 数据流重构。

### 5.3 防回归

- 验证 count 查询和分页查询不再各自完整执行候选 CTE；
- 验证移除 Token 汇总后列表响应字段和前端展示不受影响；
- 对当前真实账号做冷查询、重复查询和并发请求基准；
- 验证默认无日期与自定义日期筛选的候选数量和重叠语义；
- 验证第一页、深分页、空结果、关键词搜索和重复请求；
- 记录修复前后 SQL 耗时、扫描量和 HTTP 5xx。

## 6. 发布验收门槛

## 7. 临时规避

在代码修复前，不应通过强制默认日期过滤改变产品语义来掩盖问题；可暂时限制单次候选列表的最大可查询范围或对高负载账号提示稍后重试，但这只能作为保护措施；同时持续监控该接口 5xx 和 p95/p99。

## 8. 关闭条件

只有同时满足以下条件才可关闭本 P0：列表查询不再重复执行候选 CTE；列表查询不再执行不必要的 Token 汇总；默认无日期、活动日期筛选、分页和响应字段通过回归；AI 生成流程现有 Token 统计和日报生成未受影响；测试服和生产完成真实账号验收并保留监控与回滚记录。
