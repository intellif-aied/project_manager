# AIDA-BUG-20260716-001、003 生产上线与回滚手册

## 1. 发布范围

本批次只包含两个 P0 修复：

- `AIDA-BUG-20260716-001`：Codex fork/subagent Session 继承父历史，导致 Token 和成本重复统计；
- `AIDA-BUG-20260716-003`：Aida 客户端遇到 4MB～8MB JSONL 单行时上传中断，并在服务端残留 staging。

Session Digest 和“选择大切片后日报生成失败”不属于本批次，不应以该功能作为本批次发布阻塞项或回滚依据。

涉及产物：

- API 镜像：迁移 `027`、fork 防御性解析、上传状态和 abort 清理接口；
- Aida 客户端：fork 元数据、fork 后增量统计、8MB chunk、上传前全文件预检和失败 abort；
- Web：本批次无代码变更，不需要因这两个修复单独发布。

## 2. 上线前强制门禁

### 2.1 代码与构建

发布提交必须固定为同一个 commit，并保存 API 镜像 digest、客户端版本和 `SHA256SUMS.txt`。执行：

```bash
cd api && go test ./...
cd ../daemon && go test ./...
```

以下用例必须通过：

- fork 文件首条根 `session_meta` 不被后续复制的父 metadata 覆盖；
- fork 边界前累计量只建立基线，边界后只计算子 Session 增量；
- 缺少继承基线时跳过第一个累计值，并标记 estimated，不能把累计总量计入；
- 4,325,340 B 和 4,363,901 B 两条真实量级单行能够分块；
- 超过 8MB 的单行在 `/session-syncs/prepare` 之前失败；
- prepare 后上传失败会调用 `/abort`，staging 和对象进入清理流程；
- 至少一个超过 300MB 的多行 JSONL 完整上传、finalize、解析成功。

### 2.2 生产变更清单与备份

上线前建立变更单，至少记录：发布时间窗、Git commit、旧/新镜像 digest、客户端版本、执行人、复核人、数据库备份路径及校验和。

数据库必须做可恢复备份，并在独立数据库完成恢复演练。事故 001 的历史修复还要按事故批次备份以下记录：

- `sessions`；
- `session_metrics_revisions`；
- `session_usage_components`；
- `session_daily_usage`；
- `session_activity_costs`；
- `session_usage_event_claims`；
- 受影响用户未过期的 `token_query_snapshots` 及其 items。

禁止执行 `docker compose down -v`、清卷、清库、`DROP`、`TRUNCATE` 或无事故清单约束的业务数据删除。

### 2.3 发布前只读盘点

先记录当前异常基线，发布后使用相同 SQL 对比：

```sql
SELECT content_status, count(*)
FROM sessions
GROUP BY content_status
ORDER BY content_status;

SELECT status, count(*)
FROM session_source_generations
GROUP BY status
ORDER BY status;

SELECT object_status, count(*)
FROM session_upload_chunks
GROUP BY object_status
ORDER BY object_status;
```

事故 001 候选清单只是排查入口，候选 Token 不能作为扣减值。只有取得根 metadata、父引用、fork 时刻和继承基线，并经双人复核的 Session 才能进入正式重算。

## 3. 发布顺序

### 3.1 第一步：先发布 API

先构建并推送 API 镜像，再滚动替换 API。API 启动会自动执行迁移 `027_codex_fork_and_upload_abort.sql`，发布日志中必须确认迁移成功：

- `sessions` 存在 `forked_at`、`fork_source`；
- `sessions.content_status` 允许 `uploading`、`upload_failed`；
- `session_parser_checkpoints` 存在 fork 基线和冲突字段；
- `POST /api/v1/session-syncs/{generation_id}/abort` 已注册。

API 必须先于新客户端发布，否则新客户端在失败清理时无法调用 abort。不要同时替换所有 API 实例；先单实例观察健康检查、5xx 和数据库连接，再继续滚动。

API 上线后先用测试用户完成一次小文件上传和一次故意失败的 staging abort，确认：

- 正常上传最终为 `available` 且有 active generation；
- 新建但未完成的上传为 `uploading`，失败清理后为 `upload_failed`；
- 有旧 active generation 的 Session 追加失败后，旧内容仍保持 `available`；
- abort 后 generation 为 `abandoned`，对象最终为 `deleted`，无持续增长的 `delete_pending`。

### 3.2 第二步：发布生产 Aida 客户端

必须使用生产发布目录，不能把测试服默认地址打进生产包：

```bash
make release-prod-dir \
  AIDA_RELEASE_URL='https://<生产静态域名>/statics-live/aida' \
  AIDA_API_URL='https://<生产API域名>/api/v1'
```

发布前检查 `aida-releases-release/install.sh`、`install.ps1` 和 `aida-latest.txt` 中的地址/版本，并校验 `SHA256SUMS.txt`。禁止用 `release-test-dir` 生成的包覆盖生产目录。

客户端按小批量灰度发布：内部账号 -> 已知大文件账号 -> 10% -> 50% -> 全量。每一档至少验证一次普通 Session、fork Session 和大单行 Session；上一档出现持续上传失败或 abort 清理积压时停止扩量。

旧客户端仍可能产生重复 fork 统计或 staging 残留，因此 API 的防御和清理能力不能等客户端全量后再上线。

### 3.3 第三步：处理事故 003 的历史 staging

新代码只保证新失败流程自动 abort，不会自动删除历史遗留 staging。按事故清单逐 generation 处理：

1. 确认 generation 不是 active，也未被当前客户端继续上传；
2. 记录 session/source/generation/chunk/object key 和当前状态；
3. 通过受鉴权的 abort 接口清理，不能直接删除数据库行；
4. 确认 generation=`abandoned`、chunk object_status=`deleted`；
5. 无 active generation 的 Session 应为 `upload_failed`，随后由新客户端重新上传并转为 `available`；
6. 有旧 active generation 的 Session 必须继续保留旧可用内容。

若对象存储删除失败，接口返回 `ABORT_CLEANUP_PENDING`。此时保留数据库 `delete_pending` 状态并重试清理，不能把它人工改成 `deleted`。

### 3.4 第四步：重算事故 001 历史数据

代码发布不会自动纠正已激活的旧 metrics revision。生产历史修复必须遵循原事故方案：

1. 固化经过确认的 Session 清单和修复前 Token、成本、component 数；
2. 回填可证明的 `parent_session_ref`、`forked_at` 和 metadata 来源；
3. 从原始 JSONL 重新构建 metrics revision，禁止直接用候选 Token 总数做减法；
4. 时间边界冲突、计数回退、父引用冲突或无法建立基线时停止自动激活，转人工复核；
5. 新 revision 校验通过后再原子激活，旧 revision 保持 superseded，不能硬删除；
6. 重建相关 `session_daily_usage` 和成本，失效受影响用户的旧查询快照；
7. 保存修复前后差异和复核人。

先处理已确认案例用户 1066，再分批处理其他候选。候选用户和候选 Token 只用于排查，不代表已确认影响。

## 4. 发布后验收

### 4.1 功能验收

- 在 14.157 或等价预生产环境用真实 4,325,340 B、4,363,901 B 单行文件重传成功；
- 普通 Session 增量续传、断网重试和 incomplete tail 行为不变；
- 上传失败不会新增“available 但无 active generation”的 Session；
- fork Session 的 `parent_session_ref`、`forked_at`、`fork_source` 正确；
- fork 边界前父累计量不进入子 Session，父子合计与原始新增量一致；
- Token 汇总、Session 明细、模型、组织和成本维度一致，无负数和日期漂移；
- 未修复用户、普通 Codex Session 和 Claude Session 的统计不变。

### 4.2 观察指标

发布后至少持续观察一个完整业务高峰，重点记录：

- `/session-syncs/prepare`、chunk、finalize、abort 的请求数和 4xx/5xx；
- `uploading`、`upload_failed` Session 数量和最长停留时间；
- staging/abandoned generation 数量；
- `delete_pending` chunk 数量和最老时间；
- usage 解析 conflict/estimated 数量；
- fork Session 重算前后 Token、成本差异；
- API CPU、内存、数据库事务和对象存储删除错误。

出现以下任一情况立即停止客户端扩量：API 5xx 持续升高、`delete_pending` 持续积压、正常 Session 无法 finalize、普通非 fork Token 明显变化、成本与 Token 汇总不一致。

## 5. 回滚

### 5.1 API 回滚

迁移 `027` 是前向、加列迁移，不在事故窗口内删除列或回滚 DDL。优先通过新镜像的 forward fix 恢复。

旧 API 不认识 `uploading`、`upload_failed`。如必须回滚旧镜像，先停止新客户端扩量，盘点这两种状态，并确认没有正在上传的 generation。不能为了兼容旧 API 把未完成 Session 批量改成 `available`；需保留新 API 清理实例，完成 abort/恢复后再评估旧镜像回滚。

### 5.2 客户端回滚

客户端可回退到上一版本，但会重新暴露大单行失败和 fork 元数据缺失。回退期间：

- API 新版本及迁移必须保留；
- 暂停已知大文件和 fork 高频用户升级/重传；
- 继续监控并清理 staging；
- 修复版本重新发布后再恢复全量更新。

### 5.3 历史数据回滚

历史修复以 metrics revision 和事故批次为单位回滚：恢复旧 revision 的有效期/active 指向、恢复批次备份的日聚合和成本、失效修复后生成的查询快照。禁止反向执行估算加法，也禁止硬删除新旧 revision。

每个回滚 Session 都要再次核对 Token、成本、component 数和日期范围。代码回滚与历史数据回滚是两件事，不能因镜像回滚自动撤销已验收的数据修复。
