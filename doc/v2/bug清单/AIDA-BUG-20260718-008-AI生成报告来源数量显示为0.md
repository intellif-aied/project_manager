# AIDA-BUG-20260718-008：AI 生成报告来源数量显示为 0

> 优先级：P2  
> 状态：未修改  
> 环境：14.157 测试服  
> 发现日期：2026-07-18

## 1. 现象

个人日报和个人周报通过 Report Context V1 正常生成并成功回写，但工作台使用的来源数组为空：

- 日报明确选择 3 个来源切片，生成后 `daily_reports.session_ids=[]`；
- 周报明确选择 4 个来源切片，生成后 `personal_weekly_reports.source_session_ids=[]`；
- 工作台继续根据上述数组计算关联数量，因此可能显示“已关联 0 条记录”。

报告正文、Agent Run、Report Context 和来源快照均正常，本问题仅表现为生成结果的来源数量及旧字段元数据不一致。

## 2. 测试服证据

| 报告 | 选择来源 | Report Context | 生成结果 | 报告来源字段 |
| --- | ---: | --- | --- | --- |
| 个人日报 | 3 个切片 | `report-context/v1`，`coverage_complete=true` | 成功，正文 1,732 字 | `session_ids=[]` |
| 个人周报 | 4 个切片 | `report-context/v1`，`coverage_complete=true` | 成功，正文 2,524 字 | `source_session_ids=[]` |

对应运行记录：

- 日报 Run：`d4a8c662-c821-4fd4-ae0d-04c46752b416`；
- 周报 Run：`1316a4d6-f611-47ce-9288-1c8105a5aa07`。

## 3. 根因

`api/handler/report_mcp_write.go` 的 `upsertReportContent` 在个人日报、个人周报回写时只保存正文和 Agent 元数据，没有把已验证 Selection 的来源映射写入：

- `daily_reports.session_ids`；
- `personal_weekly_reports.source_session_ids`。

工作台仍从这两个旧数组计算关联数量，所以 Report Context 已具备完整来源时，展示层仍会得到 0。

该回写逻辑来自 2026-06-30 的提交 `612171f3`。本次 PG 瘦身合并没有修改报告回写或工作台计数代码；本问题是完整回归中新发现的既有问题，不是 Content Reader、MinIO 单份原文存储或 PG Payload 清理造成的回归。

## 4. 影响范围

- 影响工作台日报、周报的“已关联记录”数量；
- 影响通过报告表旧字段直接追溯来源的完整性；
- 不影响 Report Context V1 的来源快照和完整性校验；
- 不影响报告正文生成、Digest、Token 统计、MinIO Reader 或 PG 瘦身流程。

## 5. 修复边界（尚未实施）

修复前需要先统一展示口径：

1. 如果展示“唯一 Session 数”，报告回写时应从 Selection Items 提取唯一 Session ID，并写入现有数组；本次日报和周报都应显示 1 个唯一 Session。
2. 如果展示“已选来源记录数”，应由接口返回 Selection Slice 数量；本次应分别显示 3 和 4，不能把 Slice Key 写入 UUID 类型的 Session ID 数组。
3. Report Context V1 继续作为报告生成的权威冻结来源，不能重新扫描 Session 或从报告正文反推来源。
4. 手填保存、AI 覆盖已有报告和重复回写必须保留既定防覆盖、幂等及版本语义。

## 6. 验收条件

- 选择多个切片生成个人日报、周报后，工作台关联数量不再显示 0；
- 数量严格符合最终确定的“唯一 Session”或“来源切片”口径；
- 报告详情和列表接口返回一致的来源元数据；
- Report Context、正文回写、重复生成和人工编辑保护回归通过；
- PG 瘦身数据流和在线查询性能不受影响。

## 7. 当前状态
