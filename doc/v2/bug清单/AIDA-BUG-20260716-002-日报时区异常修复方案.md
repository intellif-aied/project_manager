# AIDA-BUG-20260716-002：日报时区异常修复方案

> 优先级：P0  
> 状态：方案已确认，待开发  
> 发现时间：2026-07-16  
> 适用基线：`fea.0.0.1` / `ba20665`，开发前必须重新确认 HEAD  
> 影响范围：个人日报与周报的 Session 来源、报告 Agent、报告来源选择界面、任务与需求日期补充数据  
> 本文只定义修复方案，不代表代码已修改、测试已完成或服务已发布。

## 1. 问题结论

当前问题不是服务器时钟漂移，也不是 Session 时间被错误写入数据库。平台按 UTC 保存绝对时间、按 `Asia/Shanghai` 计算 Session 业务日期和默认报告来源范围，这两层基本正确。

真正的问题发生在“数据库时间 -> Report MCP -> Agent -> 报告正文”的输出边界：Report MCP 把 UTC `time.Time` 原样序列化为带 `Z` 的 RFC3339 时间，再依赖模型自行换算上海时间。模型有时换算、有时直接照抄，因此同一份来源可能生成不同时间，表现为：

- 上午工作被写成凌晨；
- 下午工作被写成上午；
- 上海时间已经进入当天，正文仍显示前一天；
- 同一来源在不同模型或不同运行中，一次正确、一次偏差 8 小时；
- 日报的 `report_date` 正确，但正文出现错误的“报告生成时间”或“前一日活动”。

这属于数据契约缺陷，不能只通过增加一句 Prompt 解决。

## 2. 已确认事实

### 2.1 正确的部分

- PostgreSQL 使用 `Etc/UTC`，相关时间字段使用 `TIMESTAMPTZ`；
- API 容器使用 `Asia/Shanghai`，宿主机使用 UTC，各进程 epoch 一致，不存在物理时钟漂移；
- Session 客户端和内容投影按绝对时间解析并统一保存 UTC；
- `session_activity_slices.activity_date` 按上海时间计算；
- 默认 Report Source 按上海日期判断切片是否与报告周期重叠；
- 定时报告按 schedule 的 `timezone` 计算报告周期，默认 `Asia/Shanghai`。

只读数据核验结果：

- 152 条 `session_activity_slices` 中，`activity_date` 与上海本地日期不一致的数量为 0；
- 65 条默认 Report Source item 中，按上海时间落在报告周期外的数量为 0；
- 其中 14 条 item 的 UTC 日期与上海日期不同，这属于正常的跨日事实，必须正确展示而不能丢弃。

### 2.2 可复现证据

案例一：

```text
数据库 UTC：2026-06-08 02:10 ～ 02:42
上海时间：  2026-06-08 10:10 ～ 10:42
错误正文：  凌晨 02:10 ～ 02:42
```

案例二：

```text
数据库 UTC：2026-07-15 15:40 ～ 16:11
上海时间：  2026-07-15 23:40 ～ 2026-07-16 00:11
错误正文：  15:40 ～ 16:11，或描述为“前一日活动”
正确正文：  23:40 ～ 00:11，并明确跨越上海自然日
```

同一来源曾生成过正确和错误两类正文，证明模型换算行为不稳定。

## 3. 根因

### 3.1 P0：Report MCP 输出原始 UTC 时间

`api/internal/reportsource/service.go` 中的 `ContentItem`、`ContentEvent` 使用 `time.Time`，从 PostgreSQL 读取后保持 UTC。`api/handler/report_mcp_read.go` 将这些结构直接交给 `mcpTextResult`，`api/handler/report_mcp.go` 再直接执行 `json.Marshal`，最终返回：

```json
{
  "activity_start_at": "2026-07-15T15:40:00Z",
  "activity_end_at": "2026-07-15T16:11:00Z"
}
```

返回体没有权威的 `timezone`、上海本地日期或本地时间字段。模型必须自行理解 `Z` 并加 8 小时。

### 3.2 P0：Skill 只约束“报告日期”，没有固定小时换算

当前生效的 `aida-report@1.0.5` 已包含“按 Asia/Shanghai 解释报告日期”的说明，但没有明确规定：

- 每个 RFC3339 时间必须先转换为上海时间；
- 时间分布只能基于转换后的本地时间；
- “今日/当天”只能等于 `period.date`；
- 禁止把 UTC 系统日期作为报告日期；
- 禁止在正文直接展示 `Z` 时间对应的小时。

自然语言约束无法替代结构化的权威本地时间。

### 3.3 P1：写回校验不能识别错误时间

`report_content_validation.go` 当前主要校验内部 ID 泄漏、日期与星期关系、来源覆盖等内容，不校验：

- 日报正文中的报告日期是否与 `period.date` 一致；
- 时间分布是否使用上海小时；
- “昨日/今日”是否与 `calendar_context` 一致；
- 跨午夜区间是否被错误归类。

因此错误正文仍能通过 `write_report_result` 保存。

### 3.4 P1：任务和需求查询使用数据库 UTC 日界

`get_tasks` 和 `get_requirements` 使用日期字符串直接比较 `TIMESTAMPTZ`：

```sql
updated_at >= $1 AND updated_at < ($2::date + 1)
```

在 PostgreSQL `TimeZone=Etc/UTC` 下，查询 `2026-07-16` 实际对应上海时间 `2026-07-16 08:00` 至 `2026-07-17 08:00`，可能遗漏当天 `00:00～08:00`，并混入次日 `00:00～08:00`。

### 3.5 P1：前端存在两个独立的日期格式化问题

- `ReportAIGenerateControls.tsx` 对 RFC3339 直接使用 `.slice(0, 10)`，会把上海时间次日凌晨显示成 UTC 前一天；
- `AgentRunPage.tsx` 使用未指定 `timeZone` 的 `toLocaleString`，显示结果依赖浏览器操作系统时区。

## 4. 修复目标

1. 数据库继续保存 UTC，不修改既有时间数据，不新增 migration；
2. 所有进入报告模型的业务时间均由服务端确定性转换为 `Asia/Shanghai`；
3. Agent 不再承担 UTC 到上海时间的计算；
4. 日报的“今日/当天”固定指向 `period.date`；
5. Session、事件、任务、需求和前端来源选择采用同一业务时区；
6. 跨午夜完整切片仍完整保留，但日期和时段必须正确展示；
7. 修复不得改变 Session 上传、Token/成本计算、来源冻结和权限语义。

## 5. 统一时间契约

### 5.1 存储层

- PostgreSQL 中的 `TIMESTAMPTZ` 继续保存绝对时间；
- Session 客户端、Session Sync、内容投影继续统一写 UTC；
- 不回填、不重写历史时间字段；
- 不修改 `session_activity_slices.activity_date` 的既有上海日期语义。

### 5.2 Report MCP 模型边界

Report MCP 对模型返回的所有业务时间必须使用显式 `Asia/Shanghai` Location 格式化，RFC3339 字符串携带 `+08:00`：

```json
{
  "timezone": "Asia/Shanghai",
  "activity_start_at": "2026-07-15T23:40:00+08:00",
  "activity_end_at": "2026-07-16T00:11:00+08:00",
  "activity_start_date": "2026-07-15",
  "activity_end_date": "2026-07-16"
}
```

约束：

- 既有 `activity_start_at`、`activity_end_at`、`occurred_at` 字段保持 RFC3339 和同一绝对时刻，只改变输出 offset，不改变语义；
- 不同时向模型暴露一组 UTC 字段和一组本地字段，避免模型选错；
- 顶层响应增加 `timezone: "Asia/Shanghai"`；
- item 增加确定性的本地开始/结束日期；
- `content_snapshot_at` 属于系统元数据，不得被 Agent 当作报告日期；如继续返回，也转换为带 `+08:00` 的 RFC3339；
- legacy `get_sessions` 路径与新的 Report Source snapshot 路径必须保持相同时间契约；
- 任务和需求的 `updated_at` 也输出带 `+08:00` 的 RFC3339。

实现必须调用 `api/internal/biztime.Location()`，不得依赖 `time.Local`、容器 TZ 或数据库 Session TimeZone。

### 5.3 报告日期上下文

`calendar_context` 增加：

```json
{
  "timezone": "Asia/Shanghai",
  "report_date": "2026-07-16",
  "today_means": "period.date"
}
```

周报提供 `week_start`、`week_end` 和 `timezone`，不虚构某一天为“今日”。报告生成时间默认不进入正文；确需展示时，必须由 Aida 注入 `generated_at` 本地值，Agent 不得使用模型或 UTC 系统日期自行生成。

## 6. 修改方案

### 6.1 后端业务时间工具

涉及文件：

```text
api/internal/biztime/biztime.go
api/internal/biztime/biztime_test.go
```

新增确定性工具：

- `InLocation(time.Time) time.Time`；
- `FormatRFC3339(time.Time) string`；
- `DateBounds(dateStart, dateEnd) (startUTC, endExclusiveUTC)`；
- 空值指针转换辅助函数可放在 Report MCP 局部，避免通用包承载业务 DTO。

`DateBounds` 使用上海自然日构造边界，再转换为 UTC 作为 SQL 参数。

### 6.2 Report MCP 输出 DTO

涉及文件：

```text
api/handler/report_mcp_read.go
api/handler/report_mcp_tools.go
api/handler/report_mcp_test.go
api/internal/reportsource/service.go（仅在确有必要时修改类型，不改变存储语义）
```

实施要求：

1. 在 handler 边界建立专用输出 DTO，不直接把数据库层 `time.Time` 结构交给 `json.Marshal`；
2. 转换 snapshot 中的 item start/end、每个 event 的 `occurred_at` 和 snapshot time；
3. 转换 legacy Session 路径的 started/ended/activity start/activity end；
4. 增加 `timezone` 和本地日期字段；
5. MCP tools/list 描述明确日期范围采用 `Asia/Shanghai`，返回时间已完成本地化，Agent 禁止二次换算；
6. 保持分页、来源冻结、hash、cursor 和内容完整性不变。

### 6.3 任务与需求日期边界

涉及文件：

```text
api/handler/report_mcp_read.go
api/handler/report_mcp_test.go
```

将字符串日期先通过 `biztime.DateBounds` 转为两个绝对时间参数：

```sql
updated_at >= $1::timestamptz AND updated_at < $2::timestamptz
```

禁止继续依赖数据库的 `::date + 1` 和 Session TimeZone。

### 6.4 Agent、Skill 与校验

涉及文件：

```text
api/service/daily_report_skill.go
api/service/daily_report_skill_test.go
api/handler/managed_agent.go
api/handler/managed_agent_test.go
api/handler/report_content_validation.go
api/handler/report_mcp_write.go
api/handler/report_mcp_test.go
```

Skill 和 Agent 指令固定：

- MCP 的时间字段已经是上海时间，禁止再次加减时区；
- 时间分布必须使用本地字段；
- 日报中的“今日/当天”只能等于 `period.date`；
- `content_snapshot_at`、模型系统时间和运行机器日期不能作为报告业务日期；
- 默认不输出“报告生成时间”；
- 跨午夜区间按真实本地开始/结束时间展示，不裁剪完整来源。

写回校验至少增加：

- 明确的“报告日期/报告时间”字段若存在，日报日期必须等于 `period.date`；
- `今日/昨日` 与显式日期同时出现时，检查是否与 `calendar_context` 冲突；
- 校验规则只拦截明确的报告元信息，不扫描并拒绝任务正文中的合法历史日期。

Skill 发布不得覆盖现有版本内容。使用新版本，例如 `aida-report@1.0.6`，并验证默认 Agent 实际引用的新 owner/slug/version 和 Skill Markdown；不能只修改本地 `daily_report_skill.go` 后宣称生效。

### 6.5 前端统一格式化

涉及文件：

```text
web/src/shared/utils/businessTime.ts（新增）
web/src/features/aidashboard/reports/components/ReportAIGenerateControls.tsx
web/src/features/aidashboard/ai-assets/pages/AgentRunPage.tsx
web/src/features/aidashboard/reports/components/DailyReportGenerateModal.tsx
web/src/features/aidashboard/dashboard/DashboardPage.tsx
对应测试文件
```

实施要求：

- 使用 `Intl.DateTimeFormat` 并显式指定 `timeZone: "Asia/Shanghai"`；
- 禁止对 RFC3339 使用 `.slice(0, 10)` 获取业务日期；
- 禁止用未指定时区的 `toLocaleString` 展示报告来源；
- 日报默认日期通过统一业务时间工具生成，不依赖浏览器本地时区；
- 输入日期和服务端 `period.date` 保持 `YYYY-MM-DD`，不在前端做隐式 UTC 往返。

## 7. 测试方案

### 7.1 后端单元测试

必须覆盖：

| 输入 | 期望上海输出 |
| --- | --- |
| `2026-07-15T01:00:00Z` | `2026-07-15T09:00:00+08:00` |
| `2026-07-15T16:00:00Z` | `2026-07-16T00:00:00+08:00` |
| `2026-07-15T15:40:00Z` ～ `16:11:00Z` | `2026-07-15 23:40` ～ `2026-07-16 00:11` |
| 上海日报 `2026-07-16` | SQL UTC 边界 `[2026-07-15T16:00Z, 2026-07-16T16:00Z)` |

同时断言：

- MCP snapshot JSON 的全部业务时间携带 `+08:00`；
- event、item、legacy Session 使用同一契约；
- 同一时间转换前后 Unix 时间戳相同；
- 跨日完整切片仍被返回且事件数量不变；
- `get_tasks/get_requirements` 不遗漏上海当天 `00:00～08:00`，不混入次日该时段；
- tools/list 和 Skill 文案包含统一时间语义。

### 7.2 前端测试

- `2026-07-15T16:11:00Z` 显示为 `2026-07-16 00:11`；
- 来源日期范围正确显示 `2026-07-15 至 2026-07-16`；
- 将测试进程时区分别设为 UTC 和其他时区，输出仍一致；
- 日报默认日期始终按上海当天生成；
- 不再存在报告来源 RFC3339 `.slice(0, 10)`。

### 7.3 真实 Agent 回归

使用隔离测试账号和固定来源，至少执行：

1. 上午来源：UTC `01:00～04:00`，正文必须为上海 `09:00～12:00`；
2. 下午来源：UTC `08:00～10:00`，正文必须为上海 `16:00～18:00`；
3. 跨午夜来源：UTC `15:40～16:11`，正文必须为上海 `23:40～00:11`；
4. 上海凌晨来源：UTC 日期为前一天，日报仍归入正确 `period.date`；
5. 同一来源连续运行至少 3 次，时间分布必须一致；
6. 个人日报、个人周报各执行一次；小组/部门报告验证下级报告日期不被二次改写。

验收必须读取最终保存的报告正文，不能只验证 MCP 返回或构建成功。

## 8. 开发顺序与停止点

### TZ-001：后端时间契约与日期边界

- 只修改 biztime、Report MCP 和对应测试；
- 不修改 Skill、前端或部署；
- 停止点：Go 单测、跨日集成测试和 MCP JSON 契约 Review。

### TZ-002：Skill、Agent 与写回校验

- 依赖 TZ-001；
- 使用新的 Skill 版本，不复用已发布内容；
- 停止点：Prompt 契约测试和测试环境默认 Agent 资产核验。

### TZ-003：前端统一业务时间

- 可在 TZ-001 契约冻结后实施；
- 不改变来源选择和报告运行的业务交互；
- 停止点：前端单测、typecheck、build 和真实浏览器跨日展示。

### TZ-004：真实 Agent 与发布验收

- 在隔离测试账号执行固定输入；
- 测试服连续验证后再发布；
- 不自动重写历史报告。

共享工作树中一次只执行一个 Task。开始每个 Task 前重新检查 HEAD、`git status` 和文件白名单；发现其他会话修改同一文件时立即停止。

## 9. 发布与回退

发布顺序：

1. 发布后端本地时间 DTO 和查询边界修复；
2. 验证 MCP 实际返回 `+08:00`；
3. 发布新 Report Skill 版本并更新默认 Agent 引用；
4. 发布前端格式化修复；
5. 使用固定跨日来源做最终报告回归。

回退原则：

- 数据库存储没有变化，不需要 schema 或数据回滚；
- MCP 时间 offset 变化不改变绝对时刻，标准 RFC3339 客户端应保持兼容；
- Skill 可切回上一版本，但若上一版本仍依赖模型换算，只能作为故障回退，不能视为问题解决；
- 前端可独立回退；
- 已保存的错误历史报告不自动批量覆盖。需要修正时通过正常的报告重新生成/编辑流程完成，并保留 `managed_agent_run_id` 审计关系。

## 10. 验收标准

- 数据库 UTC 存储、Session 上传、Token/成本统计均未改变；
- Report MCP 面向模型的业务时间全部显式为 `Asia/Shanghai` / `+08:00`；
- 用户示例中的 `01:00～04:00` 和 `08:00～10:00` 不再被当作上海本地小时；
- 上海自然日跨界前后的 Session、任务和需求都进入正确报告周期；
- 前端在任意浏览器系统时区下显示一致；
- 同一固定来源重复生成的日期、时段和时间分布一致；
- 错误的报告日期或明确的错误“今日/昨日”元信息不能通过写回；
- 新 Skill 内容在实际 Managed Agent 平台中可读取、版本唯一且默认 Agent 引用正确；
- 测试、浏览器交互、真实 Agent、测试服发布和生产发布状态分别如实记录。

## 11. 明确不做

- 不修改数据库和容器的全局时区来掩盖问题；
- 不把 PostgreSQL 改成上海时区作为修复；
- 不重写 Session 历史时间或 `activity_date`；
- 不通过给所有 UTC 时间机械加 8 小时后再当作新绝对时间保存；
- 不只修改 Prompt 就结束；
- 不扫描或批量修改历史报告正文；
- 不在共享生产库执行破坏性跨日测试；
- 不与运营中心、Agent 摘要优化或多客户端开发合并实施。
