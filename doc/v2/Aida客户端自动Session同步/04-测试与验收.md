## 1. 测试原则

- 产品验收全部从 AS-AC-001 至 AS-AC-021 派生。
- 技术风险测试从已确认的架构决策 A-01 至 A-09 派生。
- 时间、文件、进程、systemd 和 executable 必须可注入或可替换，单元测试不得真实等待到次日。
- 上传链路优先复用现有公开入口和 fake HTTP server；不得为测试新增生产接口。
- 构建成功不能代替终端交互、进程恢复或真实 Session 上传验收。
- 测试服和生产严格分离；真实链路只使用测试账号、测试发布目录和测试 API。
- Aida 必须形成自己的测试和运行记录，外部参考实现不能作为 Aida 已通过的证据。

## 2. 测试层级

| 层级 | 目标 | 主要方法 |
|---|---|---|
| 单元 | 时间、状态、交互、锁和命令编排 | Go tests，注入时钟、文件目录、systemctl runner 和输入输出 |
| 集成 | 更新、隐藏 execute、现有全部上传、安装 ensure | `httptest.Server`、临时 HOME、测试二进制 |
| 进程 | A-02 批准的后台机制、崩溃恢复、关闭和版本恢复 | 专用 Linux 测试用户/隔离 HOME，真实进程和 user unit |
| 真实链路 | 用户引导、每日执行、补传和 Session 最终可见 | 测试服账号、真实 Claude/Codex Session、测试发布目录 |
| 回归 | 手动上传、自更新和多平台构建 | 现有 daemon tests、host Go toolchain 跨平台编译 |

## 3. 需求追溯矩阵

| 用例 | 需求引用 | 场景 | 输入 | 可观察结果 | 层级 |
|---|---|---|---|---|---|
| T-01 | AS-AC-001 | 用户未明确开启 | login 引导直接回车或 `N` | 配置保持 disabled，无后台进程，无自动上传 | 单元/真实 CLI |
| T-02 | AS-AC-002 | 未选择时间 | enable 后在时间输入阶段取消/EOF | 不完成开启，不保存无效时间，不启动后台 | 单元/真实 CLI |
| T-03 | AS-AC-003 | 检查配置复杂度 | 完成 enable | 只要求一个 `HH:MM`，无时间段、频率和多时间点 | 交互验收 |
| T-04 | AS-AC-004 | 到达用户时间 | 时钟推进到当天目标时间 | 正常成功时当天只执行一次隐藏 execute | 单元/进程 |
| T-05 | AS-AC-005 | 自动与手动全部上传口径一致 | 同一临时 HOME 分别执行自动 execute 和 `upload --all` | 扫描到相同根 Session/sub-agent，服务端增量结果一致 | 集成 |
| T-06 | AS-AC-006 | 自动上传前存在新版本 | fake release 提供合法 vNext | 先完成校验和替换，再由 vNext 执行全部上传 | 集成/进程 |
| T-07 | AS-AC-007 | 版本检查或更新失败 | release 不可达、checksum 错误、替换失败 | 日志记录更新错误，随后仍调用全部上传 | 单元/集成 |
| T-08 | AS-AC-008 | daemon 进程退出或设备重启 | enable 后 kill daemon 或重启测试环境 | enabled 仍为 true；按 A-02 批准的 Linux 范围自动恢复，无需重新 enable | 进程 |
| T-09 | AS-AC-009 | 设备/进程/网络错过时间 | 今日目标时间已过且当天未成功，启动 daemon 或恢复网络 | 启动后第一轮立即触发；网络失败后恢复的下一次分钟检查补传 | 单元/进程/真实链路 |
| T-10 | AS-AC-010 | 开启后手动上传 | enabled=true 时执行 `aida upload` 和 `aida upload --all` | 手动选择和全部上传继续可用，结果语义不变 | 回归/真实链路 |
| T-11 | AS-AC-011 | 修改每日时间 | 已开启时执行 set-time 并输入新时间 | 原子保存新时间；原时间不再触发；新时间生效 | 单元/进程 |
| T-12 | AS-AC-012 | 主动关闭 | 执行 disable 后再执行普通命令、installer ensure 和 update | 无自动上传、无后台复活；手动上传正常 | 单元/进程/集成 |
| T-13 | AS-AC-013 | Linux 完整链路 | Linux/amd64 安装、登录、enable、调度、重启 | A-02 批准的 Linux 范围内全流程可用 | 进程/真实链路 |
| T-14 | AS-AC-014 | 无平台监控 | 阻断任何非现有 API，仅保留 Session Sync | 自动同步完整通过；无新 API/表/服务依赖 | 静态检查/集成 |
| T-15 | AS-AC-015 | 登录后直接引导 | 交互式 login 成功且尚未开启 | 登录结果后立即出现 `[y/N]`；回车不启用 | 单元/真实 CLI |
| T-16 | AS-AC-016 | enable 是完整引导 | 执行 `aida auto-sync enable` | 依次出现作用说明、确认、时间选择和成功反馈 | 单元/真实 CLI |
| T-17 | AS-AC-017 | 两个入口时间交互一致 | login 引导与 enable 分别开启 | 使用同一 24 小时制、本机时间校验和成功文案 | 单元 |
| T-18 | AS-AC-018 | 管理动作均有反馈 | status/set-time/disable 成功、失败、取消 | 每条命令都有产品文档定义的反馈，网络断开仍能看本地状态 | 单元/真实 CLI |
| T-19 | AS-AC-019 | 自动执行无选择器 | 隐藏 execute 在非 TTY 运行 | 固定 `--all`，不读取 stdin、不出现 Session 选择器 | 单元/集成 |
| T-20 | AS-AC-020 | 开启或改时选择今天已过去的时间 | 用方向键分别选择立即、明天，并覆盖取消 | 不出现编号输入；Enter 后进入对应分支；取消不保存 | 单元/真实 CLI |
| T-21 | AS-AC-021 | 开启时检测 Linux 后台能力 | 分别构造 systemd user manager 可用与不可用环境 | 可用时继续开启；不可用时明确提示暂不支持且不写 enabled=true | 单元/进程/真实 CLI |

## 4. 单元测试设计

### 4.1 配置和时间

| 编号 | 场景 | 通过条件 |
|---|---|---|
| U-01 | `00:00`、`09:05`、`23:59` | 校验通过并规范保存为 `HH:MM` |
| U-02 | 空值、`9:5`、`24:00`、`12:60`、额外字符 | 明确报错，不写配置 |
| U-03 | enable 时间尚未来到 | 到点前不 due，到点后 due |
| U-04 | enable 时当天时间已过去并选择立即 | 保存每日时间并把本次调度标记为立即到期 |
| U-04A | enable 时当天时间已过去并选择明天 | 保存每日时间，今天不 due，次日到点 due |
| U-04B | enable 时当天时间已过去并取消 | 不开启、不保存本次时间 |
| U-05 | 已开启 daemon 错过当天时间 | 启动第一次检查立即 due |
| U-06 | 当天已成功 | 后续 tick、daemon 重启均不重复 due |
| U-07 | 修改为未来时间 | 原时间不触发，新时间触发 |
| U-08 | 修改为当天已过去时间并选择立即 | 原子保存新时间并把本次调度标记为立即到期 |
| U-08A | 修改为当天已过去时间并选择明天 | 原子保存新时间，今天不 due，次日到点 due |
| U-08B | 修改为当天已过去时间并取消 | 保留原时间和原调度状态 |
| U-09 | 本机时区发生 DST/偏移变化 | 每天按当日本机时区构造目标时间，不固定加 24 小时 |
| U-10 | config/schedule 写入中断 | 旧文件仍可读，无半文件；临时文件可清理 |
| U-10A | 到点时网络失败 | 记录 attempt、不记录 success；一分钟内不重试，下一次检查重新到期 |
| U-10B | 网络恢复后上传成功 | 写入当天 success，后续检查不再执行 |

### 4.2 交互

| 编号 | 场景 | 通过条件 |
|---|---|---|
| U-11 | login 输入 y + 合法时间 | 调用一次 enable，输出定稿成功文案 |
| U-12 | login 直接回车/N/Ctrl-D | 登录保持成功，AutoSync 不启用 |
| U-13 | enable 先拒绝 | 不写任何状态，不启动后台 |
| U-14 | enable 输入非法时间后再输入合法时间 | 先提示错误，再成功开启 |
| U-15 | enabled 时再次 enable | 不重复启动，展示当前时间和修改/关闭命令 |
| U-16 | disabled 时 set-time | 不保存时间，提示运行 enable |
| U-17 | repeated disable | 幂等告知已经关闭 |
| U-18 | 非 TTY login | 不阻塞、不自动开启，打印 enable 提示 |
| U-19 | status 时 API 断网 | 本地 enabled/time 仍输出，远程状态单独失败 |
| U-19A | 非 TTY enable | 有界时间内明确失败并提示使用交互终端，不写配置 |
| U-19B | status 时更新失败 | 更新错误之前已经展示本地 enabled/time |
| U-19C | 过去时间二次选择 | ↑/↓ 可移动选项，Enter 确认，q 取消；数字键不会被当作选项编号提交 |

### 4.3 进程和锁

围绕 Aida 自身的进程和锁实现覆盖以下用例：

| 编号 | 场景 | 通过条件 |
|---|---|---|
| U-20 | 两个并发 ensure | 只有一个 adapter launch |
| U-21 | 两个 daemon-run | 第二个因 `daemon.lock` 正常退出，不执行调度 |
| U-22 | disabled 与 ensure 并发 | 最终 disabled 且无进程 |
| U-23 | 固定 unit active | ensure 不重写 unit、不重启 |
| U-24 | 固定 unit inactive 或缺失 | enabled 时安装并 `enable --now`，disabled 时不创建 |
| U-25 | disable 时自动子进程运行 | `KillMode=control-group` 停止 daemon 和子进程 |
| U-26 | 显式 update 成功且 enabled | restart 固定 unit；disabled 时不创建 |
| U-27 | systemd 可用 | 写正确 unit，执行 daemon-reload、enable --now |
| U-28 | systemd 不可用 | 严格执行 A-02 最终结论，不得宣称未经支持的重启恢复 |
| U-29 | 批准的后台机制启动失败 | enabled 回写 false，不显示开启成功，保留输入时间 |

### 4.4 自动执行和更新

| 编号 | 场景 | 通过条件 |
|---|---|---|
| U-30 | execute 无新版本 | 启动当前磁盘二进制的隐藏 `upload-all`，再进入 `cmdUpload(--all)` |
| U-31 | 版本元数据不可达 | 记录 warning，仍启动隐藏 `upload-all` 继续上传 |
| U-32 | 已知新版本下载失败 | 记录 error，仍启动隐藏 `upload-all`；不同于手动命令门禁 |
| U-33 | 新版本合法 | execute 原子安装后重新解析磁盘二进制，启动隐藏 `upload-all`，由新版本完成上传 |
| U-34 | 自动 execute | 参数固定包含 `--all`，stdin 不参与 |
| U-35 | 手动 upload 更新失败 | 仍保持现有阻断行为，未被自动路径改写 |
| U-36 | 显式 update 成功且 enabled | best-effort 重启后台 |
| U-37 | 显式 update 成功且 disabled | 不创建后台 |
| U-38 | disable 时 execute/upload-all 正在运行 | 取消并等待自动子进程；退出后不再启动新自动上传；服务端已接受数据不回滚 |

## 5. 架构风险验证

| 用例 | 架构决策 | 风险 | 验证方法 | 通过条件 |
|---|---|---|---|---|
| R-01 | A-02 | systemd unit 写对但 user manager 不可用 | 注入和真实 Linux 两类测试 | 明确提示暂不支持、保持 enabled=false，不启动 fallback |
| R-02 | A-02/A-06 | disable 后普通命令或安装重新拉起 | disable 后连续执行 login/status/update/installer ensure | enabled 保持 false，无 daemon |
| R-03 | A-03/A-05 | 更新、重启或并发检查造成重叠上传 | 持有 run.lock 时模拟 daemon 重启和并发 tick | 同一时刻只有一个 executor；成功后当天不再执行 |
| R-04 | A-03 | 后台写状态覆盖 Token/服务地址 | 并发执行登录配置保存和 schedule attempt/success 写入 | `.aida.yaml` 与 AutoSync JSON 各自完整，互不覆盖 |
| R-05 | A-04 | fail-open 意外影响手动命令 | 同一更新错误分别跑自动 execute 和手动 upload | 自动继续，手动保持当前阻断 |
| R-06 | A-04 | 新版本替换后仍由旧进程上传或弹 TUI | fake vNext 记录版本、argv/stdin | vNext 收到隐藏 `upload-all`，最终固定走 `--all`，旧 execute 不直接上传 |
| R-07 | A-07 | 非 TTY 登录挂起 CI/安装脚本 | pipe/EOF/closed stdin 三种测试 | 有界时间内返回，登录结果不回滚 |
| R-08 | A-02 | 关闭操作影响无关进程 | 同一用户运行无关后台进程后执行 disable | 只操作固定 user unit，无任意 PID 信号 |
| R-09 | A-04 | 后台更新缓存覆盖登录配置 | 自动 execute 与 login 并发，检查 `.aida.yaml` | 自动路径不写更新缓存，最终 Token/服务地址来自 login |
| R-10 | A-09 | 更新门禁吞掉本地 status | 制造已知更新失败后执行 `aida status` | 更新错误之前已展示本地 enabled/time |
| R-11 | A-05/A-06 | disable 返回后自动子进程继续上传 | upload-all 阻塞在 fake API 时执行 disable | 子进程被取消并回收，disable 返回后无新请求；已接受请求不做补偿删除 |

## 6. 集成测试方案

### 6.1 Fake release + fake API

建立 `httptest.Server` 同时提供或分别提供：

- `aida-latest.txt`；
- `SHA256SUMS.txt`；
- 测试 Aida 二进制；
- `/auth/me`；
- 现有 Session Sync prepare/chunk/finalize/status；
- 用于记录请求顺序、执行版本、Session 数量和退出结果的测试探针。

必须覆盖：无更新、更新成功、metadata 失败、checksum 失败、下载失败、上传成功、无新增内容、上传失败和 readiness processing/failed。

请求顺序断言：

```text
版本检查/更新尝试
→ Session scan
→ prepare/chunk/finalize/status
```

更新失败时只允许缺少“更新完成”，不得缺少后续 Session 请求。

### 6.2 临时 HOME

所有 CLI 集成测试使用临时 HOME，构造：

- `.aida.yaml` 测试登录配置；
- `.claude/projects/` 与 `.codex/sessions/` 最小真实格式 Session；
- `.aida/auto-sync/` 配置和执行状态；
- 独立 systemd adapter fake，以及按 A-02 结论构造的非 systemd 环境。

测试不得读取开发者真实 Token、Session 或 `~/.aida`。

### 6.3 Installer

- `bash -n install.sh`；
- 已开启、未开启、disabled、无 Token 四种状态运行内部 ensure；
- ensure 失败只产生 warning，安装仍成功；
- installer 不写 AutoSync enabled=true；
- release 打包后的 `install.sh` 仍包含 ensure，SHA256SUMS 重新生成。

## 7. Linux 进程验收

在专用测试用户或可销毁 Linux 环境执行，禁止复用生产用户的 unit 和 HOME。

### 7.1 systemd 主路径

1. 安装测试构建并使用测试账号 login；
2. enable，选择当前时间后 2 分钟；
3. 验证 `aida-auto-sync.service` enabled/active，只有一个 daemon PID；
4. `kill -9` MainPID，验证 10 秒后 unit 恢复 active 且 MainPID 变化；
5. 等到目标时间，验证只上传一次；
6. 重启测试用户会话或测试机，在错过时间后恢复，验证立即补传；
7. disable，验证 unit disabled/inactive；
8. 执行 status、update 和 installer ensure，验证不复活。

### 7.2 非 systemd Linux

enable 必须检测 systemd user manager 并明确失败，不能保存 `enabled=true`，也不能启动 detached 或其他 fallback。若未来选择另一启动机制，必须先回到产品和架构评审。

### 7.3 更新对齐

1. vOld daemon 处于运行；
2. 测试发布目录切换到 vNew；
3. 触发自动执行；
4. 验证 vNew 完成上传、当天无第二次触发；
5. 再执行一个普通 Aida 命令，验证旧 daemon 被替换为 vNew；
6. 显式 `aida update` 路径验证更新完成后后台直接重启到新版本。

## 8. 真实链路验收

### 8.1 环境

- 测试服 Aida API 和测试静态发布目录；
- 专用测试账号和 Token；
- Linux/amd64 测试机；
- 至少一个真实 Claude Code 根 Session、一个 sub-agent Session、一个 Codex Session；
- 测试时间选择为当前时间后 2~5 分钟。

### 8.2 主流程

1. 安装测试版 Aida；
2. `aida login`，观察登录成功后直接出现引导；
3. 第一次选 `N`，验证 status 为未开启且没有后台；
4. `aida auto-sync enable`，完成完整引导并选择时间；
5. `aida auto-sync status` 与 `aida status` 核对 enabled/time；
6. 到点前新增真实 Session 内容；
7. 到点后核对后台日志、Session Sync 请求和平台 Session 最终可见；
8. 上传成功后再次等待一个检查周期，确认当天不重复执行；
9. 修改时间并验证新时间生效；
10. 模拟错过后恢复，验证第一时间补传；
11. disable 后验证不再自动上传；
12. 手动 `aida upload --all`，验证仍可上传。

### 8.3 证据

验收记录必须保存：

- CLI 完整交互输出（Token 脱敏）；
- `auto-sync status` 输出；
- systemd 及 A-02 批准后台机制的运行证据和 PID 变化；
- AutoSync 日志中的版本检查、触发时间和上传摘要；
- 测试服 Session ID、根/sub-agent 分组和 readiness 最终状态；
- 自动与手动上传的增量结果对照；
- 测试版本号和二进制 SHA256。

## 9. 回归范围

| 链路 | 不变要求 |
|---|---|
| `aida login` | Token 隐藏输入、`/auth/me` 验证、配置保存和错误码不变；引导取消不回滚登录 |
| `aida upload` | TUI/非 TTY 选择、根 Session 与 sub-agent 分组不变 |
| `aida upload --all` | Session 扫描、增量 cursor、重复跳过、readiness 和退出码不变 |
| `aida status` | 原有服务端身份结果保留；新增本地 AutoSync 状态不依赖服务端成功 |
| `aida update` | release manifest、SHA256、原子替换和现有输出不变；只增加已开启后台重启 |
| 未开启用户 | 除 login opt-in 和 status 提示外，不启动后台、不自动上传 |
| Release | Linux/amd64、darwin/arm64、windows/amd64 继续编译；非 Linux 自动同步明确不支持 |
| 服务端 | 无 migration、无新 API、无平台监控依赖 |
