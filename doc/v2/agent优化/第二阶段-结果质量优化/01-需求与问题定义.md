# Session Digest v2 需求与问题定义

> 状态：需求基线
> 需求前缀：`SDR2`

## 1. 背景

`session-digest/v1` 的目标是把数 MB 至数百 MB 的 Session 原文压缩成有硬上限的结构化来源，使报告 Agent 能在一次 MCP 读取内完成日报生成。该目标已经实现，普通大 Session 不再要求 Agent 分页读取全部原始事件。

上线后的用户反馈指出，日报虽然可以生成，但更像“对聊天内容的总结”，而不是“对工作结果的总结”。这不是单纯调整措辞能解决的问题：当前 Digest 没有表达结果与证据之间的关系，Report Agent 无法可靠判断哪些内容只是讨论，哪些内容已经实现、验证或发布。

## 2. 生产样本结论

样本 `019f4575-4fe7-72a1-86d8-b6a4c719a73e` 的 v1 Digest 有以下现象：

| 现象 | 根因 | 日报影响 |
| --- | --- | --- |
| `AGENTS.md` 内容进入目标 | 嵌套 JSON 字符串绕过简单前缀过滤 | 工作目标被系统上下文污染 |
| 最后两条问答成为结果 | budget 只保留最近 outcomes，且 outcome 主要来自 final/task_complete | 较早的代码、文档和验证结果被挤出 |
| “阻塞项展示”成为 blocker | blocker 使用关键词包含判断 | 把产品设计内容误写成实际阻塞 |
| 同类测试只有一个最终状态 | validation 按命令族合并，缺少尝试时间和所属任务 | 无法判断失败后是否已修复 |
| 文件和结果彼此独立 | 没有 Work Unit 和 evidence link | Report Agent 根据文件名推断成果 |
| 讨论与交付不区分 | 结果类型只有自由文本 outcome | 把方案建议写成已经实现 |

## 3. 根因

### 3.1 当前抽取单位不正确

v1 以整个完整切片为单位收集 `goals/outcomes/files_changed/validations/blockers`。对于包含数百轮交互的 Session，这些数组失去任务边界，不能说明某个文件、测试或结果属于哪一项工作。

### 3.2 最终消息不等于最终结果

长 Session 最后若处于需求澄清、方案问答或下一任务开头，最近的 Agent 回复只代表对话当前位置，不代表当天主要交付。

### 3.3 缺少环境真值

代码修改、测试退出码、Git commit、构建、部署、健康检查和 API 响应属于比自然语言更强的结果证据。v1 只抽取其中少量状态，没有把证据与结果声明绑定。

### 3.4 状态不是字符串分类问题

“失败后成功”“提出阻塞流程”“讨论未完成状态”都包含失败或阻塞词，但实际状态不同。必须根据事件顺序和同一工作单元的后续证据做状态归并。

### 3.5 Report Skill 缺少结果优先约束

当前 Skill 允许 Agent 使用 `goals/outcomes/files_changed/validations/blockers` 作为证据，但没有强制：

- 每项工作先写交付结果；
- 讨论和实现分栏；
- 完成状态必须由证据决定；
- 无证据时降低表述强度；
- 失败验证不能被笼统写成“验证通过”。

因此只修改 Digest 或只修改 Skill 都不完整。

## 4. 产品目标

第二阶段需要让个人日报稳定回答：

1. 今天实际完成或交付了什么；
2. 每项结果由什么文件、测试、提交、运行或决策证据支持；
3. 哪些只是讨论、方案建议或待确认问题；
4. 哪些任务部分完成、失败或仍被阻塞；
5. 哪些验证通过，哪些验证失败；
6. 日报日期与工作发生时间是否一致。

## 5. 功能需求

### SDR2-FR-001 Work Unit

服务端必须把完整 Session 切片划分为有时间范围的 Work Unit。一个 Work Unit 至少包含用户目标、相关 Agent 回复、工具调用和完成事件的边界。

### SDR2-FR-002 结果类型

每项结果必须明确标识类型，至少包括：

- `implementation`：代码或配置实现；
- `document`：文档产出；
- `decision`：明确达成的产品或架构决定；
- `investigation`：诊断、分析或结论；
- `verification`：测试、构建、运行或 API 验证；
- `deployment`：构建发布、服务切换或线上验证；
- `discussion`：仍在讨论或等待确认。

### SDR2-FR-003 完成状态

Work Unit 状态固定为：

- `completed`
- `partial`
- `blocked`
- `failed`
- `pending`
- `unknown`

状态必须由证据状态机计算，不能只匹配最终消息中的关键词。

### SDR2-FR-004 证据绑定

每条 `result_statement` 必须绑定一个或多个 `evidence_ref`。证据至少支持：

- 文件修改；
- 测试、lint、typecheck、build；
- Git commit；
- Docker/进程启动；
- 健康检查；
- API/浏览器结果；
- 明确接受的设计决定；
- Agent 最终声明。

### SDR2-FR-005 证据等级

结果声明必须携带证据等级：

- `A`：外部状态或可执行验证已成功；
- `B`：持久化变更证据存在，但未完成完整验证；
- `C`：只有 Agent 声明；
- `D`：提议、问题或讨论，没有交付证据。

日报不得把 C/D 级声明写成已验证交付。

### SDR2-FR-006 时序归并

同一 Work Unit 中，较早失败但随后成功的验证不得保留为最终 blocker；最终仍失败的验证必须保留。每个验证需记录 attempts、last_status 和最后发生时间。

### SDR2-FR-007 噪声与注入排除

环境上下文、系统/开发者指令、`AGENTS.md` 注入块、权限说明、压缩历史包装、reasoning、Token 遥测和工具原始正文不得成为目标或结果。

### SDR2-FR-008 完整覆盖

完整切片仍必须被完整遍历。低价值讨论允许聚合表示，但不得静默删除整个 Work Unit；coverage 必须记录总数、详细表示数、聚合数和省略事件数。

### SDR2-FR-009 报告周期关联

Digest Revision 保存 Work Unit 时间范围；selection assembler 根据报告周期标注 `before/overlap/after`。不得通过重新裁剪原始事件改变完整切片语义。

### SDR2-FR-010 结果优先 Report Skill

个人日报 Skill 必须：

- 优先输出已完成/交付结果；
- 把设计决定与代码实现分开；
- 把验证失败和未完成项单独列出；
- 避免“参与、推进、围绕、梳理”等无法说明结果的空泛表达；
- 不以文件清单替代成果；
- 不暴露 evidence ref、Session ref、内部 ID。

### SDR2-FR-011 版本隔离

`session-digest/v1` 和 `session-digest/v2.1` 必须能同时识别。新 run 明确冻结版本；历史 selection 和已附着 run 不得被新版本改写。

### SDR2-FR-012 14.159 评测集

14.159 当前全部可读取 Session 必须进入只读 manifest。全量语料执行结构回放，分层样本执行 v1/v2 日报 A/B，人工 Gold 集执行结果事实核对。

### SDR2-FR-013 可审计

每次评测必须记录：

- corpus manifest SHA256；
- Digest/Skill/代码版本；
- 模型与运行参数；
- 每个样本的输入 hash、Digest hash、报告 hash；
- 自动 grader 与人工结论；
- 失败样本和原因。

### SDR2-FR-014 保守的工具输出归约

服务端可以参考 RTK 等项目的“按命令类型使用专用解析器”思路，但首期必须采用保守边界：

- 只解析 Session 中已经持久化的工具调用和工具结果；
- 不安装或调用 RTK 二进制，不增加客户端 Hook，不重写或重新执行命令；
- 优先使用结构化事件、退出码和明确格式，不使用通用成功/失败关键词替代真实状态；
- 专用解析器无法确认格式时，降级为有界 `unknown` 证据，不回退原始输出；
- 初始只支持 14.159 真实语料中高频且有稳定格式的命令族，新增命令族必须带 fixture、Gold 和回归测试。

## 6. 非功能需求

### SDR2-NFR-001 确定性

相同输入、版本和预算必须生成逐字节一致的 Digest 与 hash。

### SDR2-NFR-002 容量

selection payload 继续以 64 KiB 为正常目标、128 KiB 为硬上限。任何质量增强不得恢复原文分页。

### SDR2-NFR-003 安全

生产 Builder 不调用 LLM、不执行命令、不访问 Session 中的 URL。敏感信息先脱敏再进入证据摘要。

### SDR2-NFR-004 性能

Digest v2 构建不得进入上传事务；报告 MCP 仍读取冻结 payload，不在请求时重扫原始事件。

### SDR2-NFR-005 兼容

Session 上传、Token/成本统计、六类报告来源层级、权限和写回语义保持不变。

### SDR2-NFR-006 质量

关键结果召回、结果支持率、完成状态准确率必须达到 [06-测试验收与质量门禁.md](06-测试验收与质量门禁.md) 的门禁。

### SDR2-NFR-007 运行隔离

Digest v2 必须使用独立版本、独立任务类型和独立 Worker claim 范围，默认关闭、限并发运行。它不得进入 Prepare/Chunk/Finalize 上传事务，不得写入 usage、metering、Token 汇总表；出现积压或失败时，最多影响 `digest_v2` 就绪，不得使 Session 上传失败、改变 Token 数值或阻止 v1 报告继续生成。

## 7. 非目标

- 不让 Digest 代替项目管理系统的正式任务状态；
- 不根据 Session 自动修改任务、需求或进度；
- 不把完整 reasoning、日志、源码或 diff 交给 Report Agent；
- 不用单次 LLM 总结作为不可审计的生产事实；
- 不在没有用户批准时做生产账号灰度；
- 不处理组织日报/周报的来源层级调整；
- 不改变 Aida 客户端上传协议；
- 不把 RTK 安装到 Aida 客户端，不增加 Shell Hook、命令代理或本地 tee 文件；
- 不修改 Session Token 的解析、归一化、计费和候选列表统计口径。

## 8. 完成标准

方案实施完成必须同时满足：

- 需求 `SDR2-FR-001` 至 `SDR2-FR-014` 均有自动或人工测试映射；
- 典型样本不再出现系统上下文 goal、误报 blocker 和末尾问答覆盖结果；
- 14.159 corpus 完成冻结和回放；
- 结果质量门禁与第一阶段 Token/容量门禁同时通过；
- 回滚到 v1 不需要恢复原文读取。
