# Session Digest 第二阶段：结果质量优化（归档）

> 归档日期：2026-07-17
> 当前生产实现基线：v2.8 低损耗成果投影
> v2.9 状态：未实施设计稿，不代表当前权威实现或生产能力
> 日期：2026-07-17
> 后续统一入口：[../总纲.md](../总纲.md)

## 1. 归档结论

第一阶段解决大 Session 原文分页、Token 超限和运行超时。第二阶段经过 v2.4～v2.8 多轮优化后确认：取消 Top-K 仍不足以保证结果完整，因为 v2.8 在进入 Report Agent 前依然会按 Work Unit、证据等级和字节预算筛选、截断用户可见内容。

本阶段曾提出以下历史设计方向：

```text
Digest Builder = 确定性安全清噪器 + 完整语义对话投影器
Report Agent    = 结果理解器 + 语义归并器 + 日报撰写者
```

服务端只删除系统/开发者注入、推理过程、工具调用与大输出、图片二进制、遥测和精确重复等可客观判定的噪音；所有用户可见的 user/assistant 文本按顺序完整保留，不做 Top-K、成果评分、证据门槛或逐字段静默截断。

上述 v2.9 方向没有完成开发与真实链路验收，不得作为当前生产契约。当前生产实际运行 `session-digest/v2.8.0`，后续是否继续语义保真方向必须重新依据总纲立项。

## 2. 版本关系

| 版本 | 状态 | 结论 |
| --- | --- | --- |
| v2.4～v2.7.9 | 历史方案与验收 | 固定成果上限和语义归并会漏内容 |
| v2.8 | 14.157 历史验收基线 | 无 Top-K、链路可用，但仍是 result-focused 投影，语义保留不足 |
| v2.9 | 未实施设计稿，已归档 | 只做确定性清噪的历史设想，需重新立项后才能开发 |

v2.8 文档和真实链路结果保持冻结，不把新规则回写为“v2.8 已验收能力”。

## 3. 历史目标流程

```text
本地 Session
  -> Aida 正常完整上传
  -> 原始事件、usage、Token 数据照常保存
  -> v2.9 确定性清噪
  -> 有序完整 Semantic Blocks
  -> 用户在页面手动选择一个或多个 Session
  -> 冻结选择级完整上下文
  -> 超过 1 MiB 时提示 Token/模型风险
  -> 用户返回调整或确认继续
  -> Report Agent 生成结果型日报
  -> 正文安全门禁
  -> MCP 真实写回
```

## 5. 不变边界

v2.9 不修改：

- Aida 客户端 prepare/chunk/finalize 上传协议；
- Session 原始事件、切片游标和内容存储；
- usage、metering、Session Token 数值和 Token analytics 口径；
- 用户手动选择 Session 的产品语义；
- 报告权限、目标身份和 MCP 写回身份；
- 已保存日报的编辑冲突保护。

有影响的模块包括 Digest Builder、来源冻结、Report MCP 返回契约、Report Skill、默认 Agent 指令、正文门禁，以及大上下文提示所需的 Web 前端交互。

## 6. 测试操作边界

真实验收必须由用户在 14.157 页面手动选择 Session。测试人员可以准备上传、等待 ready 和跟踪 Agent，但不得通过脚本替用户创建来源选择。

最终验收依据是持久化日报 Markdown 和用户人工校对，不是 Digest 自身计数，也不是 Agent run 的 `completed` 状态。
