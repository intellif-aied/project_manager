# Session Digest v2.9：语义保真清噪（未实施设计稿）

> 状态：已归档、未实施；不得作为当前生产或开发基线
> 目标 Digest 版本：`session-digest/v2.9.0`
> 环境边界：14.157 开发测试环境；本文不代表生产运行状态
> 测试操作边界：来源 Session 必须由用户在页面手动选择
> 后续统一入口：[../../总纲.md](../../总纲.md)

## 1. 本轮结论

v2.8 已经解决固定 Top-K、原文分页和长 Session 直接读取问题，但其服务端仍会先判断“哪些内容算成果”：用户和 Agent 文本会被逐条截断，只有文件变更或验证证据支撑的 Work Unit 才容易进入报告期 highlights，最终 Agent 无法恢复被提前省略的方案、决定、分析和长回复细节。

v2.9 将边界调整为：

```text
Digest Builder = 确定性安全清噪器 + 完整语义对话投影器
Report Agent    = 结果理解器 + 语义归并器 + 日报撰写者
```

服务端只删除能够客观判定为无意义或不适合进入模型上下文的内容，不再以证据等级、文件变更、测试状态或关键词判断业务重要性。允许保留更多噪音，优先避免关键内容遗漏。

## 2. 核心不变量

1. Session 原始事件、上传游标、切片、usage、metering 和 Token analytics 不变。
2. 所有用户可见的用户消息与 Agent 回复按原始顺序保留；不得按“是否像成果”决定去留。
3. 不做 Top-K、主题聚类、版本 supersede、成果评分或 LLM 预摘要。
4. 不对保留的语义块进行 768/512/160 bytes 静默截断。
5. 系统/开发者注入、推理过程、原始工具调用与大输出、图片二进制、遥测和精确重复事件可确定性删除。
6. 敏感信息继续脱敏；每个删除或脱敏动作必须有可审计原因码。
7. `1 MiB` 是用户成本提醒阈值，不是语义裁剪或运行硬阻断；用户确认继续后仍按完整清噪结果运行 Agent。
8. 用户界面只提示“所选会话内容较多”和可能的 Token/模型影响，不暴露 Digest、清洗、压缩等内部实现。
9. Report Agent 负责把完整语义上下文总结为结果，最终日报仍不得泄漏内部 ID、凭据、主机、路径和纯验证过程。
10. 真实验收不由脚本自动挑选 Session；用户在页面手动选择一个或多个 Session 后发起生成。

## 4. 与 v2.8 的关系

- `v2.8-低损耗Digest` 保持冻结，作为 14.157 已完成的历史容量与链路验收证据；
- v2.8 的原始数据保护、服务端冻结、版本 Hash、脱敏、单页读取和无 Top-K 设计继续沿用；
- v2.8 的 result-bearing Work Unit 门槛、逐字段截断、16/64/128 KiB 压缩链和“顶层条目数不少于 highlight 数”不再作为 v2.9 目标；
- v2.9 未完成真实链路验收前，不得把本文状态写成“已上线”或“生产运行”。
