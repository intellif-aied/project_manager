# 05 风险与三轮 Review

> Review 对象：v2.9 文档方案，不代表代码和真实链路已经通过。

## Review 1：语义完整性与规则边界

### 发现

1. v2.8 的“无 Top-K”只保证已识别 highlights 不被删，不能保证用户可见语义完整；
2. 768/512/160 bytes 截断会无条件删除长消息后半部分；
3. 文件变更和验证证据决定成果资格，会遗漏方案、决定和分析；
4. 只保留 final/最后回复会丢失用户可见的中间结论；
5. 以正文关键词判断系统注入存在误伤真实业务讨论的风险；
6. v2.8 coverage 分母来自自身提取结果，属于提取后自洽。

### 修正

- canonical 输入改为完整有序 Semantic Blocks；
- 分类前不截断，保留后也不截断；
- 以结构化角色和事件类型判断用户可见性；
- 证据和 Work Unit 只做可选诊断，不决定文本去留；
- coverage 分母改为全部候选用户可见块；
- 每个省略项必须有允许的确定性原因码。

### 结论

通过。该方向符合“Digest 只去无意义内容，重要性判断留给 Agent”。

## Review 2：容量、Token 与稳定性

### 发现

1. 取消 16/64/128 KiB 压缩后，Agent 输入会明显增大；
2. 1 MiB UTF-8 字节数不是精确 Token 数，不同语言和模型差异较大；
3. 只提醒不阻断可能导致用户主动产生较高 Token 成本或模型上下文失败；
4. 多 Session 组合可能超过底层 HTTP、数据库或 Agent 平台能力；
5. 如果超过阈值后重新构建快照，可能出现用户确认内容与实际运行内容不一致。

### 修正

- 1 MiB 定位为成本提醒，不宣称等于特定 Token 数；
- 提示同时说明 Token 成本和模型可能无法完整处理；
- 提供返回调整、换模型和继续生成三种用户决策；
- 用户确认绑定 selection id、payload Hash 和实际字节数；
- 确认后必须使用同一冻结 payload；
- 真实基础设施限制明确报错，不通过静默删内容绕过；
- 监控构建耗时、payload bytes、Agent 输入 Token、失败类型和真实写回率。

### 剩余风险

用户确认继续后仍可能因所选模型上下文不足失败。这是透明的用户选择和模型能力边界，不应重新引入服务端语义裁剪。

### 结论

有条件通过。开发和真实验收必须覆盖大于 1 MiB 的继续运行场景。

## Review 3：产品交互、模块影响与架构一致性

### 发现

1. 大上下文提示需要 Web 前端配合，不能再声称“前端完全无影响”；
2. 测试脚本自动创建 selection 会绕过用户真实选择和提示交互；
3. Skill 的“按 highlight 数生成 bullet”与自然语义合并冲突；
4. 写回正则过宽可能拒绝合法的质量能力和用户可见结果；
5. 仓库仍有未调用的 Top-K、priority、supersede 和产品专用改写代码，妨碍规则审计；
6. 14.157 测试状态不能表述为生产运行状态。

### 修正

- 前端列为中等影响模块，只新增选择后的提示与确认，不改变手动选择语义；
- 真实测试在候选来源 ready 后暂停，由用户页面手动勾选；
- Skill 改为完整阅读和结果型总结，不再机械映射 block/bullet 数；
- 写回门禁只保留确定的安全、身份和日期校验，语义质量主要由 Agent 与人工验收判断；
- 实现完成后删除或隔离遗留死代码；
- 所有文档明确区分 14.157 测试环境与生产环境。

### 结论

通过。手动选择 Session 是正式验收的一部分，不是测试便利步骤。

## 4. 综合风险清单

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| 用户可见内容被错误分类为噪音 | P0 | 结构化分类优先、默认保留、原因码与回放测试 |
| 保留内容被静默截断 | P0 | `semantic_blocks_truncated` 必须为 0，写入与冻结双重校验 |
| 用户确认后 payload 被替换 | P0 | selection id + Hash + bytes 绑定确认 |
| run 成功但报告未写回 | P0 | 以 `write_report_result` 和 report id 为成功条件 |
| 旧 128 KiB 硬限制仍在生效 | P1 | 容量边界自动化和 >1 MiB 真实测试 |
| Agent 逐轮复述聊天 | P1 | Skill 结果型组织、真实日报人工校对 |
| 大上下文 Token 成本增加 | P1 | 1 MiB 提示、换模型/返回调整/继续 |
| 正文门禁误伤合法成果 | P1 | 收窄正则、退回重写、人工样本回放 |
| 多来源顺序或重复异常 | P1 | 来源级稳定排序、只做精确去重 |
| 规则死代码被重新接入 | P2 | 删除或隔离、调用链测试 |
| Aida/Token 链路被误改 | P0 | 明确不变边界和回归测试 |

## 5. 架构判断

v2.9 的合理架构边界是：

```text
服务端负责“什么不是对话”
Agent 负责“对话说明了什么结果”
用户负责“选择哪些 Session、是否接受大上下文成本”
```

不合理的边界是：

```text
服务端先判断什么值得写日报
再让 Agent 对服务端写好的短成果做二次改写
```

## 6. 开发准入结论

文档方案可以进入开发，但必须遵守以下准入条件：

1. 不在 v2.8 上继续堆关键词补丁；
2. 先建立 Semantic Blocks 和 coverage 测试，再切换 Agent 输入；
3. 不修改 Aida 上传和 Token 统计；
4. 前端提示接口需与正在进行的前端工作确认文件边界；
5. 14.157 部署后等待用户手动选择 Session；
6. 用户未看到最终持久化日报原文前，不得宣布验收通过；
7. 生产发布必须单独盘点和授权。

## 7. 文档一致性复核记录

### 第一轮：规则一致性

- 核对需求、架构、开发和测试文档均禁止 Top-K、证据门槛和静默截断；
- 修正未知事件处理：不能证明不含用户可见语义时必须阻止冻结，不能计入允许删除；
- 确认 v2.8 遗留关键词清洗和产品专用改写不被继承为 v2.9 规则。

结论：通过。

### 第二轮：容量与接口一致性

- 核对所有文档统一使用 `1 MiB` 作为提醒阈值而非硬限制；
- 核对用户确认继续后绑定同一 selection、Hash 和 payload，不重新压缩；
- 核对 Web 前端被明确列为影响模块，Aida 上传与 Token analytics 明确不受影响。

结论：通过。

### 第三轮：测试与环境一致性

- 核对全部状态均表述为“待开发与 14.157 验收”，没有将测试环境写成生产；
- 核对真实流程在候选来源 ready 后暂停，必须由用户页面手动选择 Session；
- 核对最终成功以 `write_report_result`、持久化 report id 和用户人工校对为准。

结论：通过。
