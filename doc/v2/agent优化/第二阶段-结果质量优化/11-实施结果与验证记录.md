## 1. 实施结论

本次已把第二阶段从方案落为独立服务端实现。核心变化不是继续压缩聊天文本，
而是把 Session 投影为有证据的 Work Unit：

```text
Session content events
  -> safe SQL projection
  -> deterministic Work Unit extractor
  -> result/change/validation/unresolved association
  -> 64 KiB Revision with daily summaries
  -> 16 KiB report-period projection
  -> selection-level cross-slice consolidation
  -> frozen digest_v2 selection
  -> single get_sessions response
  -> result-first Report Skill
  -> write_report_result completeness and content-quality guard
```

v2 不调用 LLM，不执行 Session 中的命令，不读取图片/base64/reasoning 原文，
不提供 raw fallback。

## 3. 数据与容量契约

- 单 Session v2.1 Revision 硬预算 64 KiB；
- 报告期单 item 投影预算 16 KiB；
- selection target/hard limit 保持 64/128 KiB；
- v2 payload 单页、`has_more=false`；
- 超预算先按结果优先裁剪，再聚合低优先级 Work Unit；
- 病理引用数量仍无法收敛时，退化为最小会话级结果计数，不返回原文；
- selection 总量超过 128 KiB 时明确失败，不自动切 full。

## 7. 八轮实施 Review 摘要

### Round 1：架构与兼容

修正 v2 模式下继续构建 v1；补齐 Compose 环境变量透传；确认 migration 使用
`020`，job type 完全隔离。

### Round 2：质量、安全与容量

修正 approval-assessment 整段忽略；确认无系统指令、reasoning、凭据和大工具
正文泄漏；发现并修复病理 `evidence_refs` 突破单 item 预算的问题。

### Round 3：数据库、并发与回滚

独立数据库、race、vet 和存量链路通过；v2 默认关闭、测试显式启用、Worker
batch 1；Skill 使用新不可变版本，v1 Revision 和 Skill 1.0.7 保留。

### Round 4：报告期优先级

真实 Agent 发现 v2.0 在 16 KiB 全会话压缩后才选择报告期，历史 Work Unit
可能挤掉当日结果。修正为 v2.1：先以 64 KiB Revision 保留按上海业务日期
生成的 `daily_summaries`，再以 16 KiB 预算投影报告期 highlights。

### Round 5：Agent 轨迹与输出质量

真实 trace 发现 selection UUID 被误填旧字段、混合状态被写成“全部完成”。
通过 MCP schema、Skill 和启动提示同步约束后，最终 trace 只调用一次
`get_sessions`，且报告使用中性“有结果工作项”表达。

### Round 6：跨切片选择级归并

真实上传会把同一个长 Session 拆成多个切片。新增 selection-level
`report_period_summary`，由服务端在冻结选择时只物化一次，并按主题、时间和
最终状态合并，Report Agent 不再枚举每个 item 的内嵌摘要。

### Round 7：正文产品化约束

Skill 将个人日报限制为通常 3 至 5 项、最多 6 项，只输出“今日完成”和
“进行中与待跟进”。文件名、路径、URL、主机、账号、Skill/Digest 版本、
测试、健康检查、Worker 和证据引用只作内部判断。

### Round 8：服务端写回质量门禁

模型仍可能忽略 Prompt，因此写回端增加确定性拒绝规则。最终真实 run 的前两
个草稿被拒绝，第三个草稿清除内部技术细节后保存，避免不合格正文落库。

详细记录见 [08-Review记录.md](08-Review记录.md)。

## 9. 剩余风险和下一步

尚未完成：

1. 14.159 全量 Session manifest 和完整 corpus；
2. Human Gold；
3. 正式 v1/v2.1 配对 A/B 和三次 trial；
4. 混合上传负载下的 API/数据库资源门禁；
5. 生产发布审批。
6. 真实 Agent 首稿通过率和 `write_report_result` 重试次数基线。

已知限制：

- 离线 evaluator 会整体物化单文件，不能作为生产 RSS 证明；
- v2 与其他 Worker 共享 API/数据库资源，回填必须限速监控；
- reducer 未识别的输出保持 unknown；
- selection 项过多可能明确触发 128 KiB hard limit；
- Agent semantic claim 不是无条件事实，最终报告仍必须服从 evidence source。
- 个别低价值 partial、汇总 pending/unknown 或文件计数仍可能进入正文，属于后续
  Gold/Pairwise 评测需要继续压低的展示噪声，不影响本次容量和写回正确性。
- 最终正文仍出现“Skill 版本已更新部署”这类轻微内部措辞，虽未暴露版本号，
  后续可在选择级摘要中进一步产品化为“日报生成能力已优化”。

生产发布前必须补齐正式配对 A/B、Human Gold 和混合负载资源证据，不能只凭
单样本 E2E 上线。
