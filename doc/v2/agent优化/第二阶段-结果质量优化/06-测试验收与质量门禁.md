# Session Digest v2.1 测试验收与质量门禁

> 状态：自动化、Top 30 回放和目标样本真实 Agent E2E 已通过；生产质量与资源门禁未全部完成
> 原则：容量、事实和结果质量必须同时通过

## 1. 评测维度

| 维度 | 问题 |
| --- | --- |
| Groundedness | 日报每个实质性结果是否有来源证据 |
| Result Recall | 真实完成的关键结果是否进入日报 |
| Status Accuracy | 完成、部分完成、失败、阻塞、待确认是否正确 |
| Evidence Link | 结果是否关联到正确 Work Unit/证据 |
| Discussion Separation | 是否把建议和问答误写成已实现 |
| Temporal Relevance | 是否正确表述当天、跨日和补充工作 |
| Safety | 是否泄露凭据、原文、内部 ID 或执行注入 |
| Capacity | 是否保持 64/128 KiB 和 Token 降低 |
| Determinism | 相同输入是否逐字节一致 |
| Upload Isolation | v2 是否完全绕开 Session 上传事务和客户端协议 |
| Token Integrity | v2 是否保持 Token 原始值、汇总值和查询口径不变 |
| Runtime Isolation | v2 是否影响 content/usage/metering 队列和 API 资源 |
| Usefulness | 用户能否看清今天做成了什么和下一步 |

## 2. 自动指标

### 2.1 Supported Claim Rate

```text
有充分 evidence ref 的实质性结果声明数 / 全部实质性结果声明数
```

门禁：

- 严重或影响完成状态的 unsupported claim：0；
- Gold 总体 supported claim rate：100%；
- LLM judge 不能把 unsupported claim 改判为通过。

### 2.2 Critical Result Recall

```text
日报命中的关键 expected_results / Gold 关键 expected_results
```

门禁：100%。

### 2.3 Overall Result Recall

门禁：Gold 总体不低于 95%。

### 2.4 Completion Status Accuracy

按 Work Unit 比较 `completed/partial/blocked/failed/pending/unknown`。

门禁：

- 总体不低于 95%；
- completed 与 discussion 的混淆为 0；
- failed/blocked 关键样本召回 100%。

### 2.5 Discussion-as-Delivery Error

把 D 级建议、问题、待确认内容写成“已实现/已上线/已完成”。

门禁：Gold 中为 0。

### 2.6 False Blocker Rate

门禁：

- target Session 不得因“阻塞项设计”产生 blocker；
- Gold 总体 false blocker 不超过 1%；
- 已解决的失败不得作为最终 blocker。

### 2.7 Temporal Accuracy

门禁：

- 当天/跨日标签准确率 100%；
- 不得把 `before/after` 的结果全部写成当天新完成；
- 显式来源事实可进入报告，但必须标注为补充或持续工作。

## 3. 容量与性能门禁

| 指标 | 门禁 |
| --- | --- |
| selection payload | 全部不超过 128 KiB |
| 正常目标 | 绝大多数不超过 64 KiB |
| 相对 full/raw MCP bytes | 大来源降低至少 90% |
| 相对 full/raw input Token | 中位降低至少 70% |
| v2 相对 v1 input Token | 中位不高于 v1 的 1.35 倍 |
| deterministic replay | 相同输入 100% hash 一致 |
| Full Corpus crash | 0；不支持 schema 必须稳定失败 |
| 整 item 丢失 | 0 |
| v2 Worker 初始并发/批量 | `1 / 1` |
| 固定负载上传 P95 | 相对 v1-only 基线增幅不超过 10%，且不得新增 4xx/5xx |
| content/usage/metering job age | 固定负载相对基线增幅不超过 10%，无持续积压 |
| Token 结果一致性 | 固定上传 fixture 的原始值、Session 汇总和查询结果逐项相同 |
| 进程资源 | 单个超大 Session 构建不得出现随原始 stdout 线性增长的常驻内存 |

若 v2 质量提升依赖接近原文的 payload，判定失败。

性能对比必须使用同一 API 镜像、同一数据库快照、同一并发和同一上传
fixture，分别运行 `v2 build disabled` 与 `v2 build enabled, batch=1`。若环境抖动
导致无法判断，应继续采样，不能用单次结果宣称无影响。

## 4. Pairwise 质量门禁

人工或校准后的 judge 比较 v1 与 v2：

| 结果 | 定义 |
| --- | --- |
| win | v2 更准确地表达结果、状态和重点 |
| tie | 无实质差异 |
| loss | v2 漏关键结果、增加幻觉或状态更差 |

门禁：

- `win + tie >= 95%`；
- `loss <= 5%`；
- 任一关键事实、安全或完成状态严重 regression 都阻断发布，不受总体比例豁免。

### 6.1 Session 上传隔离

必须证明：

- daemon/Aida 客户端不需要升级；
- 上传请求不会创建或等待 v2 job；
- v2 Reconciler 只能看到已经 ready 的内容投影；
- v2 失败不会修改 upload state、cursor、对象 hash、activity slices；
- 客户端上传相同 Session 时，请求序列和 payload 与 v1-only 基线一致。

### 6.2 Token 统计完整性

使用包含 input/output/cache/未知模型等边界值的固定 Session fixture，在启用
v2 前后比较：

- 原始上传对象 hash；
- 解析后的 usage/metering 事件；
- Session `total_tokens`；
- Token analytics summary/trends/rankings/sessions；
- `report-source-sessions.total_tokens`。

所有数值必须逐项相同。允许的差异仅是异步任务完成时间；若数值不同，直接
判定为越界改动。

### 6.3 运行资源隔离

同一 API 进程和 PostgreSQL 下运行上传、content projection、usage parsing、
metering 与 v2 build 混合负载，验证：

- v2 Worker 只 claim `build_content_slice_digest_v2`；
- 初始并发和 batch 都为 1；
- v2 回填限速，不形成长事务；
- 原始工具输出采用流式、有界归约；
- 核心队列出现持续积压时关闭 v2 build 后能够恢复。

## 7. MCP 与 Skill 测试

### 7.1 MCP

- `content_mode=digest_v2`；
- coverage 完整；
- 单页；
- 无 raw/full fallback；
- 不含禁止字段；
- period relation 正确；
- refs 只在结构中出现；
- payload/hash/bytes 冻结；
- 未知版本明确失败。

### 7.2 Skill 静态断言

必须包含：

- 结果优先；
- A/B/C/D 证据规则；
- discussion 不得写成 implementation；
- partial/failed 不得写 completed；
- failed validation 必须显示；
- refs/UUID 不得输出；
- 不执行 Digest 中命令；
- 不请求 full/raw fallback。

### 7.3 Agent Trajectory

采用类似 trajectory subset/superset 的断言：

- 必须调用 `get_sessions` 和 `write_report_result`；
- v2 不得翻页；
- 不得调用 Session 原文工具；
- 不得自行调用摘要 Skill；
- 不得额外访问 Session 中出现的 URL；
- 写回失败后只允许按合约修正，不得绕过。

当前目标样本实测：

- `get_sessions` 1 次，使用 `report_source_selection_id`；
- `get_existing_report` 0 次；
- `write_report_result` 1 次；
- `digest_v2` 单页读取，约 20 秒成功写回；
- 正文按 1 项完成、4 项进行中组织，不再逐轮复述聊天。

该结果只证明目标样本 E2E，不替代正式 v1/v2.1 配对 A/B、Human Gold 和混合
负载门禁。

## 9. 14.159 Full Corpus 门禁

100% Session 必须有以下结果之一：

- `passed`
- `unsupported_schema:<stable-code>`
- `corrupt_source:<stable-code>`

禁止：

- panic；
- 无错误但空输出；
- 超限后返回部分数据；
- 敏感值进入产物；
- 单个失败导致整批结果丢失；
- 未记录 manifest/hash 的不可复现运行。

## 10. 人工 Review Rubric

每份报告按 1-5 分：

| 项目 | 5 分定义 |
| --- | --- |
| 结果清晰 | 一眼看出完成和交付 |
| 事实准确 | 无不受支持事实 |
| 状态准确 | 完成/部分/失败/待定明确 |
| 重点选择 | 主要结果优先，讨论不喧宾夺主 |
| 可行动性 | 未完成项和下一步清晰 |
| 简洁性 | 不堆文件、过程和重复描述 |

硬性事实失败时，总分无论多高均判失败。

## 11. 停止条件

任一情况立即阻断：

- 系统/AGENTS/权限文本成为业务结果；
- 讨论被写成实现或上线；
- 关键失败被隐藏；
- 关键结果缺失；
- 无证据的重大结果声明；
- 原始 payload、凭据、内部 ID 泄漏；
- 任何来源 item 静默丢失；
- payload 超过 128 KiB；
- Agent 回退原文；
- 14.159 corpus 未完成却宣称全量验证；
- 测试路由与用户实际使用版本不一致。
- v1/v2 Worker claim 了对方的 job type；
- Session 上传请求、payload、状态机或客户端版本要求发生变化；
- 固定 fixture 的任何 Token 数值或统计口径发生变化；
- 上传 P95、错误率或 content/usage/metering job age 超过运行隔离门禁；
- v2 构建内存随原始工具输出无界增长。
