# 01 需求与产品方案

## 1. 问题定义

用户选择一个完整长 Session 后，期望日报能够覆盖当天真实完成的主要工作，同时避免 Agent 再读取几十 MB 原文。v2.7.9 虽然解决了原文分页和 Token 爆炸，但在服务端进行了过度语义筛选：

- 单 Session 日级成果最多保留 6 条；
- 多 Session 选择级成果最多保留 5 条；
- 同主题、版本号和产物启发式会把不同 Work Unit 合并；
- `Session Digest v2.1 方案、开发、部署` 可能被改写为单一的 `Aida Report 版本发布`；
- 最终 Agent 根本看不到被删掉的成果，模型能力再强也无法恢复。

因此，当前问题首先是输入信息损失，不应归因于 Agent 模型能力。

## 2. 产品目标

### 2.1 首要目标

在不让 LLM 阅读 Session 原文的前提下，以低损耗方式保留报告期内全部实质结果，降低 Agent 输入 Token，并让最终日报由 Agent 完成语义归并。

### 2.2 允许的取舍

- 可以多保留少量重复或技术噪音；
- 可以缩短单项文本和去掉证据路径、命令、文件清单；
- Agent 最终正文可以合并同一主线；
- 不允许服务端静默删除完整成果项；
- 不允许用 Top-K 代替容量治理。

## 3. 产品形态

用户操作保持不变：

1. Aida 上传本地 Session；
2. 用户在日报来源列表中选择切片；
3. 用户发起 AI 生成日报；
4. Agent 读取冻结的低损耗成果投影；
5. Agent 生成可编辑日报并回写。

用户不会看到 Work Unit、引用或覆盖率诊断字段。变化只体现在：长 Session 生成的日报不再固定只有 5～6 项，且更完整地覆盖当天成果。

## 4. 功能需求

| 编号 | 需求 |
| --- | --- |
| LL-001 | 每个结果型、失败型、阻塞型或有明确待跟进的 Work Unit 生成一个 highlight |
| LL-002 | 日级和选择级合并均不得使用 Top-K |
| LL-003 | 选择级仅按来源引用做精确去重，不做模糊主题或版本归并 |
| LL-004 | 每日输出显式 `outcome_coverage`，可证明成果项未丢失 |
| LL-005 | 压缩必须对所有条目均匀生效，不得按优先级删除条目 |
| LL-006 | Agent 必须读取全部 highlights，并在写回前完成引用级覆盖检查 |
| LL-007 | 个人日报正文不再限制最多 6 项 |
| LL-008 | 超过选择级硬上限时明确失败，不生成残缺日报 |

## 5. 非功能需求

- Digest 构建仍为确定性逻辑，不新增 LLM 调用；
- 不新增数据库迁移；
- 不修改 Session 上传协议和增量游标；
- 不修改 Token 采集、归一化和统计口径；
- 不读取或执行 Session 内命令；
- 保持 `digest_v2` 单页冻结读取方式；
- 失败必须可观测，不允许 `completed` 但没有真实报告写回。

## 6. 明确不做

- 本轮不调整 Work Unit 的业务日期归属；仍按现有 Asia/Shanghai 规则投影；
- 本轮不修改 Aida 客户端、上传 API、候选 Session 列表或切片语义；
- 本轮不引入向量检索、Embedding、LLM Map-Reduce 或二次 Agent Digest；
- 本轮不把 RTK 的命令输出压缩协议直接引入上传链路；
- 本轮不做生产发布。

## 7. 验收定义

使用完整 Session `019f668c-2eb5-7c92-b08f-358ee84af865` 生成 `2026-07-16` 日报，必须同时满足：

1. 上传从 cursor 0 到文件 EOF，不能只上传增量 chunk；
2. 选择的切片覆盖完整上传内容；
3. `digest_version=session-digest/v2.8.0`；
4. 报告期每天的 `outcome_coverage.complete=true`；
5. `source_count=represented_count=len(highlights)`；
6. 核心成果文本不再被 Aida Report 版本号替换；
7. Agent 实际调用 `get_sessions` 和 `write_report_result`；
8. 最终日报覆盖当天方案设计、开发实现、测试环境落地和质量优化等不同意义的成果；
9. 正文不泄漏内部 ID、主机、路径、命令或证据引用；
10. 将最终 Markdown 原文交给用户人工核对。
