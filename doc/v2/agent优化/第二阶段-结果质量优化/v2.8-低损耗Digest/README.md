## 1. 本轮结论

v2.7.9 的方向偏成了“服务端先生成一份短日报，再让 Agent 改写”。它通过 Top-K、同主题归并和版本启发式压缩成果，虽然节省 Token，却会把方案、开发、部署和质量优化等不同阶段误判成重复项。

v2.8 将产品边界改为：

```text
Digest Builder = 确定性清洗器 + 结构化投影器 + 字节压缩器
Report Agent    = 语义归并器 + 日报撰写者
```

服务端允许保留一定噪音，但不得替用户选择“最重要的 5 项”。所有有结果、失败、阻塞或明确待跟进的 Work Unit 都必须进入报告期成果清单；Agent 读取完整清单后再组织自然语言。

## 2. 核心不变量

1. 不做 Top-K，不设置 3～5 项或最多 6 项的成果上限。
2. 不按版本号、关键词、证据等级或时间顺序删除整个成果。
3. 只对完全相同的来源引用做确定性去重，不做模糊语义去重。
4. 字节预算不足时，先均匀缩短每项文本，再删除证据明细；不得静默删除成果项。
5. 每天必须满足 `source_count = represented_count = len(highlights)` 且 `complete=true`。
6. 如果完整成果在选择级硬上限内仍放不下，明确返回容量错误，不以不完整日报伪装成功。
7. digest_v2 个人日报每个 canonical highlight 至少对应一个顶层成果条目，顶层条目数不得少于 `outcome_coverage.source_count`。
8. 路径、内部标识、实现规模和纯验证证据由 Agent 改写为用户成果；回写校验只退回重写，不删除 Digest 成果。
9. `status=partial` 不足以单独生成待跟进；没有具体 `unresolved`/`blocked`/`failed` 时省略待跟进章节。
