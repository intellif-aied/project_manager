## 2. 当前 v1 Digest 问题

### 2.1 Goal 污染

第一个 goal 是 JSON content block，其中包含：

```text
# AGENTS.md instructions for ...
<INSTRUCTIONS>
...
```

原因不是简单未过滤 `<environment_context>`，而是该文本外层先被序列化为 JSON 数组字符串，当前 `isNoiseGoal` 看不到真实前缀。

v2 断言：

- 递归解析 content block；
- 自动注入的 AGENTS 不进入 Work Unit；
- 真正用户消息仍保留。

### 2.2 Outcome 被末尾问答支配

v1 最终只保留了近期两条：

- P0 能力 append-only 的讨论/调整；
- 平台 Skill/MCP 与本地同名时的优先级建议。

Session 中更早存在代码、文档和验证证据，但因为 outcome 是平铺数组且预算保留最近项，主要交付无法稳定进入最终 Digest。

v2 断言：

- 243 个 task complete 先归属于 Work Unit；
- A/B 级结果优先于末尾 D 级问答；
- 最后问题仍被表示，但不能成为唯一 primary result。

### 2.3 False Blocker

v1 blockers 包含：

- 本地运行时 Chat 与 Sandbox Chat 的持久化差异讨论；
- Runtime 页面展示“解绑被会话阻塞”占用项的产品建议。

它们是在设计“如何展示阻塞”，不是 Session 当前被阻塞。

v2 断言：

- 没有失败状态或“无法继续”证据时不创建 blocker；
- 设计问题进入 `discussion` 或 `pending`；
- blocker 必须能关联失败 evidence。

### 2.4 Validation 缺少任务归属

v1 有：

- `go test`: passed
- `npm run build`: passed
- `npm test`: failed

但看不出：

- 属于哪项工作；
- 命令是否多次运行；
- 失败后是否重试成功；
- npm test 失败是否影响对应交付完成状态。

v2 断言：

- validation 属于具体 Work Unit；
- 保留 attempts 和 last status；
- 相关实现最多标为 partial，除非 Gold 证明失败与目标无关；
- 日报不能笼统写“验证全部通过”。

### 2.5 文件清单不能表达结果

v1 抽取到：

- `CONTEXT.md`
- 展示名缓存相关 ADR/PRD
- gateway 数据库、存储、登录、当前用户和类型文件

这些文件是有价值的 B 级证据，但仅靠路径无法证明业务行为、验证范围或是否发布。

v2 断言：

- 文件归属于“AIHUB 展示名缓存/管理员刷新”等 Work Unit；
- 结果声明和验证状态分开；
- 日报主体写成果，不堆文件列表。

## 3. 建议 Gold Work Unit

以下是根据当前可见 Digest、用户反馈和报告正文形成的初始标注方向；在 14.159 原始 Session 可读后需由人工复核。

### WU-A：AIHUB 展示名缓存与管理员刷新

| 字段 | 初始期望 |
| --- | --- |
| category | implementation + document |
| status | partial |
| evidence | 相关 gateway 文件、ADR/PRD、go test、npm build、npm test |
| grade | A/B |
| result | 后端与设计文档发生变更 |
| unresolved | npm test 失败需定位 |

不得直接写“功能已上线”，除非存在部署/运行证据。

### WU-B：Chat Session 能力 append-only

| 字段 | 初始期望 |
| --- | --- |
| category | decision/document |
| status | completed 或 pending，由用户确认和文档写入共同判定 |
| result | P0 不支持移除能力；需要更小集合时新建 Session |
| evidence | 用户确认、ADR/文档变化 |

这是产品决定，不等同于运行时代码已实现。

### WU-C：Agent 能力权限边界

| 字段 | 初始期望 |
| --- | --- |
| category | decision |
| result | Agent 只能提出能力需求，不能自行启用或解析凭据 |
| status | 由明确确认决定 |

### WU-D：平台与本地同名能力优先级

| 字段 | 初始期望 |
| --- | --- |
| category | discussion/pending |
| status | pending |
| result | 形成“平台显式选择版本优先”的建议 |

最后回复仍在征求确认，不能写成已实现规则。

### WU-E：Runtime 解绑与会话持久化

| 字段 | 初始期望 |
| --- | --- |
| category | investigation/discussion |
| status | pending |
| result | 梳理本地与 Sandbox 生命周期差异，提出 UI 展示建议 |
| blocker | 无 |

## 5. 期望日报方向

日报应接近：

```markdown
### 今日完成与产出

- 完成 AIHUB 展示名缓存与管理员刷新相关后端及设计文档调整。`go test` 和前端构建通过；`npm test` 仍失败，因此该项按部分完成记录。
- 明确 Chat Session P0 能力采用 append-only：会话中可增加 Skill/MCP，但不能移除；需要更小能力集合时新建 Session。
- 明确 Agent 只能提出能力需求，不能自行启用能力或解析凭据。

### 待确认与后续

- 平台显式选择的 Skill/MCP 与本地同名配置的优先级仍待最终确认。
- Runtime 解绑占用项展示和本地/Sandbox 会话持久化边界仍需继续设计。
```

最终文字必须以 Human Gold 为准。关键是：

- 结果在前；
- 验证状态准确；
- 决定和实现分开；
- 待确认不伪装为完成；
- 没有 false blocker。

## 6. 发布前强制判定

该样本出现以下任一情况，v2 不得发布：

- goal 仍含 AGENTS/system 注入；
- blockers 仍含“解绑被会话阻塞”的设计文本；
- 日报只总结最后几轮问答；
- npm test 失败消失；
- 文件路径被直接当成功能结果；
- 把优先级建议写成已实现；
- payload 超过硬上限或重新请求原文；
- 报告正文出现 Session Ref、UUID、evidence ref。
