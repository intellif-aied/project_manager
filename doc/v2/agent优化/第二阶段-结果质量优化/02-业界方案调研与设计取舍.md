# 业界方案调研与设计取舍

> 状态：调研完成
> 原则：借鉴评测和证据建模方法，不引入不必要的平台依赖

## 1. 调研结论

行业内较成熟的 Agent 质量方案有一个共同点：不能只检查最后一段自然语言，而要同时检查任务结果、完整轨迹和环境真值。

本方案吸收以下原则：

1. 以任务和多次 trial 为评测单位；
2. 组合确定性 grader、LLM grader 和人工校准；
3. 结果尽量由可执行环境或持久化状态验证；
4. 对开放式轨迹不强求唯一正确路径；
5. 每个结论保留来源和推导关系；
6. 先用简单、可组合和透明的结构，再增加复杂度；
7. 工具输出优先按命令族解析，但任何解析失败都必须保守降级，不能恢复大原文。

## 2. 参考方案

### 2.1 Anthropic：Agent Eval 结构

Anthropic 将 Agent 评测拆为 task、trial、grader 和 transcript，并强调 Agent 会在多轮中调用工具、修改环境和根据中间结果调整，因此评测不能退化为单轮文本对比。其建议把 groundedness、coverage、确定性检查和 LLM rubric 组合，并用专家人工判断持续校准 LLM grader。

参考：

- [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

对 Aida 的映射：

| Anthropic 概念 | Aida 对应 |
| --- | --- |
| task | 一个 Session Work Unit 或一份日报生成任务 |
| trial | 同一来源、模型、Skill 版本的一次报告运行 |
| transcript/trajectory | Session 事件、工具调用和完成消息 |
| grader | 证据校验、结果召回、状态判断、人工 Review |
| environment ground truth | 文件变化、退出码、commit、服务和 API 状态 |

采用点：

- 同一高风险样本执行多次 trial；
- 自动 grader 不只给总分，而是分别检查 groundedness、coverage 和 status；
- LLM judge 只作为开放式表达质量评估，并定期对齐人工 Gold。

### 2.2 OpenAI：Dataset 与 Trace Grading

OpenAI AgentKit 的 Evals 能力强调 dataset、trace grading、自动 grader 和人工标注的组合，用端到端轨迹定位工作流缺陷，而不是只看最终回答。

参考：

- [Introducing AgentKit](https://openai.com/index/introducing-agentkit/)
- [Graders API](https://platform.openai.com/docs/api-reference/graders)

采用点：

- 14.159 Session corpus 固化为版本化 dataset；
- 每次 v1/v2 改动跑同一 dataset；
- 评分结果落到具体 Work Unit、result statement 和 evidence ref；
- 支持精确规则 grader、文本/模型 grader，但模型 grader 不覆盖确定性失败。

### 2.3 LangSmith：Trajectory Match 与 LLM Judge

LangSmith/AgentEvals 区分 strict、unordered、subset、superset trajectory match 和 LLM-as-judge。开放式 Agent 通常可能有多条正确路径，因此不应强制所有工具调用顺序完全一致。

参考：

- [How to evaluate your agent with trajectory evaluations](https://docs.langchain.com/langsmith/trajectory-evals)

采用点：

- 对固定报告流程使用 superset 断言：必须读取来源并写回；
- 对安全边界使用 subset 断言：不能请求 raw fallback、不能调用额外网络工具；
- 对结果表达使用 LLM judge；
- 不对 Codex/Claude 的所有工具顺序做 strict match。

### 2.4 SWE-bench Verified：可执行结果与人工验证

SWE-bench Verified 使用人工筛选的真实任务，并通过可执行测试判断代码是否解决问题。它说明对于软件工程结果，测试和环境状态比 Agent 自述更可靠；同时测试任务本身也需要人工审查，避免错误基准制造虚假结论。

参考：

- [SWE-bench Verified](https://www.swebench.com/verified.html)
- [Introducing SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)

采用点：

- 存在测试、构建、健康检查或 API 校验时优先作为 A 级证据；
- 人工 Gold 样本必须先确认任务定义清楚、证据可判定；
- 不能只因为 Agent 写了测试或声称通过就判定结果完成；
- 对历史 Session 无法重放环境时，明确降低证据等级。

### 2.5 W3C PROV：结果来源与派生关系

W3C PROV 将 provenance 定义为参与产出某个对象的实体、活动和主体信息，用于评估质量、可靠性和可信度，并强调版本、处理步骤和派生关系。

参考：

- [W3C PROV Overview](https://www.w3.org/TR/prov-overview/)
- [PROV-O](https://www.w3.org/TR/prov-o/)

本方案不引入 RDF/OWL，但采用最小思想：

```text
Result Statement
  wasDerivedFrom -> Evidence
  wasGeneratedBy -> Work Unit
  used -> Session Event / Tool Result
  belongsTo -> Digest Revision
```

这样可以回答“这条日报结果从哪里来”，也能在错误时定位到抽取、关联还是生成阶段。

### 2.6 RTK：按命令类型压缩工具输出

[RTK](https://github.com/rtk-ai/rtk) 是命令输出代理，不是历史 Session 总结器。它在命令执行时按工具类型选择解析器，并使用统计提取、分组、失败聚焦、去重、状态机和 NDJSON 解析减少进入模型的输出。其架构和具体命令实现可参考：

- [RTK Architecture](https://github.com/rtk-ai/rtk/blob/develop/docs/contributing/ARCHITECTURE.md)
- [Go command reducer](https://github.com/rtk-ai/rtk/blob/develop/src/cmds/go/go_cmd.rs)
- [Pytest reducer](https://github.com/rtk-ai/rtk/blob/develop/src/cmds/python/pytest_cmd.rs)
- [Log deduplication](https://github.com/rtk-ai/rtk/blob/develop/src/cmds/system/log_cmd.rs)

对 Aida 有价值的不是 RTK 的命令代理，而是以下解析原则：

| RTK 思路 | Aida Digest v2 借鉴 |
| --- | --- |
| 每类命令独立模块 | Evidence Reducer Registry，按命令族路由 |
| JSON/NDJSON 优先 | 存量输出确有结构化格式时优先解析 |
| 文本状态机 | 仅用于格式稳定的 pytest/test/build 摘要 |
| Failure Focus | 成功保留统计，失败保留有界关键详情 |
| Grouping/Dedup | 按测试、包、文件、错误模式聚合 |
| 保留退出码 | 退出码和结构化状态高于自然语言 |
| 原文和压缩视图分离 | 原始 Session 保留，Report Agent 只读 Digest |

明确不采用：

- 不安装、调用或依赖 RTK 二进制；
- 不在 Aida 客户端安装 Hook，不重写用户命令；
- 不为历史 Session 重新执行测试、Git、Docker 或 curl；
- 不采用 RTK 的 raw fallback；过滤失败必须返回有界 `unknown`；
- 不采用 tee 路径向 Report Agent 暴露完整工具输出；
- 首期不移植 RTK 的 100+ 命令支持，只实现语料证明必要的最小集合。

若未来直接复制 RTK 源码而不是独立实现，需要遵守其 Apache-2.0 许可证和归属要求。本期默认只借鉴设计与测试方法，自行用 Go 实现。

## 3. 最终设计取舍

### 3.1 使用确定性 Evidence Digest

生产服务端只做：

- 事件解析；
- Work Unit 分段；
- 证据抽取；
- 状态归并；
- 有界文本规范化；
- 稳定 JSON 和 hash。

不做：

- 调用模型重新总结全部原文；
- 执行 Session 中的命令；
- 自动访问文件、Git 远程或外部 URL；
- 根据语义猜测没有证据的完成结果。

原因：保持成本、确定性、安全和可回放。

### 3.2 结果表达由 Report Agent 完成

Report Agent 读取结构化结果与证据后负责中文合并和表述。Skill 强制区分：

- 已交付；
- 已验证；
- 已形成决定；
- 仅讨论；
- 未完成或失败。

这保留模型擅长的语言组织能力，同时不让模型自行从 47 MB 原始轨迹寻找事实。

### 3.3 使用混合评测

| 层级 | 方法 | 用途 |
| --- | --- | --- |
| L0 | schema/hash/预算规则 | 确定性与容量 |
| L1 | evidence/status 程序 grader | 结果是否有依据 |
| L2 | Gold 事实集合 | 关键结果召回与幻觉 |
| L3 | LLM judge | 表达、合并、重点和可读性 |
| L4 | 人工 Review | 校准与最终发布判断 |

任何 L0/L1 的严重失败不能被 LLM 高分覆盖。

### 3.4 使用保守的 Reducer Registry

首期采用“通用基线 + 少量专用解析器”：

1. 所有工具调用先经过通用 process reducer，提取命令族、call id、结构化退出码和时间；
2. 只有格式签名明确时，才进入 Go test、JS test/build、Git 等专用 reducer；
3. 专用 reducer 返回 `recognized=false` 时回到有界 `unknown`，不尝试模糊关键词猜测；
4. reducer 只生成标准 Evidence，不直接决定 Work Unit 是否完成；
5. Result Linker 和 State Resolver 继续负责跨尝试归并，避免“某次命令成功”等同于“整个任务完成”。

该结构把 RTK 的优势限制在 Evidence Extractor 内，避免扩大到上传、Token、MCP 或 Agent 运行链路。

## 4. 明确拒绝的方案

### 4.1 直接让第二个 Agent 总结原始 Session

拒绝原因：

- 再次读取大原文，恢复第一阶段已解决的 Token 问题；
- 结果不确定，难以 hash 和回放；
- prompt injection 风险增加；
- 需要为“摘要 Agent 的摘要”再做事实校验。

### 4.2 只调整日报提示词

拒绝原因：当前输入已经丢失 Work Unit 和结果证据关系，提示词无法可靠恢复被 compact 掉的信息。

### 4.3 只扩充 outcomes 数量

拒绝原因：更多最终消息仍可能是问题、建议和讨论，也会增加输入但不提升结果可信度。

### 4.4 文件修改即完成

拒绝原因：文件写入可能未编译、未测试、被回滚或只是临时草稿。只能作为 B 级证据。

### 4.5 关键词判断 blocker

拒绝原因：“阻塞项页面”“不支持停用”“失败场景设计”等文本不是实际阻塞。blocker 必须由事件状态和后续解决情况判断。

### 4.6 只用 LLM Judge

拒绝原因：模型 grader 会漂移，也可能偏好语言流畅但事实错误的报告。必须与确定性证据和人工 Gold 结合。

### 4.7 静默修改 digest_v1

拒绝原因：历史 selection、现有 Skill 和回滚语义依赖 v1。结果模型属于契约变化，应发布新的不可变版本；当前实现版本为 `session-digest/v2.1`。

### 4.8 擅自账号灰度

拒绝原因：会造成用户测试与实际生效版本不一致。测试路由和生产切换必须显式、可见、经确认。

### 4.9 直接把 RTK 接入 Aida 客户端或生产运行时

拒绝原因：

- 会改变用户真实命令和 Session 原始轨迹；
- Hook、二进制版本和平台兼容会扩大客户端发布面；
- RTK 会实际执行代理命令，而 Digest Builder 只能读取历史证据；
- raw fallback 和 tee 行为不符合 Aida 的 128 KiB、安全与不可泄密约束；
- 不能为了日报质量影响 Session 上传和 Token 统计。

## 5. 对本项目的最小可行路径

1. 先实现离线 v2 extractor 和 14.159 evaluator；
2. 用全量 corpus 修正规则，不动生产；
3. 固化人工 Gold 与质量门禁；
4. 先实现通用 process reducer，只在 Gold 证明有收益时增加专用 reducer；
5. 再接入独立 v2 Job/Worker、Revision、selection payload 和 MCP；
6. 发布新 Report Skill；
7. 测试环境显式 A/B；
8. 用户确认后生产全量切换；
9. 保留 v1 快速回退。
