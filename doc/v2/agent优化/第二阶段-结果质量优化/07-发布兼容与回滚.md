# Session Digest v2.1 发布、兼容与回滚

> 状态：发布方案
> 原则：显式版本、显式切换、不得隐藏灰度

当前测试环境实现基线：

- migration：`020_report_digest_v2.sql`；
- Digest：`session-digest/v2.1`；
- read mode：`digest_v2`；
- 测试 Skill：`100866/aida-report@1.0.10`；
- Skill artifact SHA-256：`82bc8e3724dfda76d52467d76b116476197e36ed4c9d167a035726744763211e`；
- Skill `SKILL.md` SHA-256：`39035627adf3868625a50a5ebd1e7895efa2b2d641c815d81fbda2cab80da0b9`；

- canary：空；shadow：未使用；
- 生产：未切换。

## 1. 版本资产

发布必须包含独立不可变资产：

- API 镜像；
- `session-digest/v2.1` 代码版本；
- 数据库 migration；
- Aida Report Skill 新版本；
- 14.159 corpus manifest/scorecard；
- 发布与回滚记录。

不得覆盖现有 Report Skill 版本内容，也不得让同一版本号在不同环境指向不同 Markdown。

## 2. 兼容矩阵

| Run mode | Digest Revision | Skill | 行为 |
| --- | --- | --- | --- |
| full | 无要求 | 兼容 Skill | 旧兼容/人工诊断能力；不得作为 v2 自动回退，大 Session 不使用 |
| digest_v1 | v1 | 当前线上 Skill | 第一阶段行为 |
| digest_v2 | v2.1 | `aida-report@1.0.10` | 报告期结果导向行为 |

规则：

- run 创建时冻结 mode/version；
- v1 Skill 不得收到 v2 payload；
- v2 Skill 可识别 v1 仅用于明确兼容场景，生产正式切换应精确匹配；
- 已附着 selection 不受后续全局配置影响；
- 写回必须验证读取完成 mode。
- `digest_v2` 失败时回退目标是 `digest_v1`，不是自动切换 `full`。

## 4. 测试环境发布

顺序：

1. 部署包含 v2 代码但 `SESSION_DIGEST_V2_BUILD_ENABLED=false` 的 API；
2. 执行 read mode/job type 隔离 migration；
3. 验证上传、Token、v1 报告和核心队列基线；
4. 发布 v2 Skill 到测试环境 owner，但不修改默认 Report Agent；
5. 显式启用 v2 Worker，固定 `worker batch=1`、并发 1；
6. 只对批准的测试样本构建 v2，同时继续构建 v1；
7. 等待选中 Session v2 ready；
8. 明确把测试默认 Report Agent 切到 v2 Skill；
9. 使用固定账号运行 v1/v2 A/B；
10. 核对 Agent 实际加载的 Skill、MCP content_mode 和写回结果；
11. 再次比较上传 P95、Token 数值、核心 job age 和 API/数据库资源；
12. 保存 run/report/Token/scorecard 和资源对比结果。

不得只根据配置文件判断生效，必须从实际 run trace 核对。

## 5. 生产发布

### 5.1 禁止隐藏灰度

本方案默认不使用未声明的 canary 用户、hash 分桶或 shadow 用户路径。

允许的切换方式：

- 测试环境显式 A/B；
- 生产在用户批准后全局切换新 run 到 `digest_v2`；
- 如确需分批，必须由用户明确指定账号/范围和开始结束时间，并在发布记录中可见。

### 5.2 建议顺序

1. 只发布 migration/API，保持 `digest_v1`，v2 build 默认关闭；
2. 验证 v1、上传、Token 统计和核心队列无回归；
3. 显式启用 v2 build，初始 batch/并发均为 1；
4. 观察 v2 ready/failed、上传 P95、核心 job age 和 API/数据库资源；
5. 限速回填生产近期报告来源需要的 v2 Revision，不做全库突发回填；
6. 发布生产 v2 Skill 并校验 hash，但暂不切换默认 Agent；
7. 用户确认后同时切换 read mode 与默认 Skill；
8. 用固定真实账号生成日报；
9. 核对 `content_mode=digest_v2`、coverage、报告正文和写回；
10. 观察至少一个完整业务周期，观察期内继续构建 v1；
11. 记录最终版本和状态。

## 6. 监控

新增或区分：

- v1/v2 Revision ready/failed/superseded；
- v2 build latency、source bytes、digest bytes；
- Work Unit detailed/aggregated 数；
- A/B/C/D evidence grade 分布；
- completed/partial/blocked/failed 分布；
- `unsupported_agent_claim_count`；
- `noise_excluded_count`；
- selection payload bytes；
- MCP latency/error；
- Report Agent input Token、总时延、写回失败；
- 用户人工改写率和反馈。
- Session Prepare/Chunk/Finalize 请求量、P95 和错误率；
- content projection、usage、metering job age 与失败率；
- 固定抽样 Session 的 Token 汇总一致性；
- PostgreSQL CPU/IO/连接、API CPU/RSS/GC；
- v1/v2 Worker 实际 claim 的 job type；
- v2 回填速率和待处理数量。

告警：

- v2 failed 持续增加；
- unsupported claim 或 unknown status 异常升高；
- payload 接近硬上限；
- Report Agent 请求 full/raw；
- write mode mismatch；
- 生产报告空内容或事实投诉。
- 上传 P95 或错误率相对基线异常升高；
- content/usage/metering 队列持续积压；
- Token 数值与发布前固定样本不一致；
- v2 Worker claim 非 v2 job；
- API RSS 随大工具输出持续增长。

## 7. 回滚

### 7.1 快速回滚

将新 run 的：

```text
MANAGED_AGENT_REPORT_SESSION_READ_MODE=digest_v1
MANAGED_AGENT_REPORT_SKILL_VERSION=<previous-version>
```

同时恢复到已验证组合。

注意：

- 不删除 v2 Revision；
- 不修改已附着 v2 run；
- 不回滚 Session 上传；
- 不自动切 full；
- v2 run 应继续按冻结契约完成或明确失败。

如果问题是资源竞争而不是报告读取质量，还应立即设置：

```text
SESSION_DIGEST_V2_BUILD_ENABLED=false
```

关闭 v2 Builder 不影响已完成上传、Token 解析、v1 Revision 和已冻结的 v2
selection。回滚顺序应为：先恢复新 run 到 v1 Skill/read mode，再停止新的 v2
构建；不得通过删除 job、Revision 或原始 Session 处理。

### 7.2 数据库

扩展 check constraint 的 migration 通常无需向后回滚，旧 API 可忽略 `digest_v2` 历史值的前提必须通过兼容测试。

若旧 API 无法读取含 v2 mode 的行，回滚前先：

- 停止创建新 v2 run；
- 等待/终止在途 v2 run；
- 部署支持读取但不创建 v2 的兼容 API；
- 再恢复 v1 默认。

不得直接删除 production selection 或 Digest 行。

## 8. 发布失败条件

- Skill 实际版本与配置不一致；
- 测试账号仍走 v1，却误报 v2 验证；
- v2 ready 不完整；
- target Session 回归失败；
- 结果质量 loss 超门禁；
- 讨论误写成实现；
- 关键测试失败被隐藏；
- Token/容量明显回归；
- 固定 fixture 的 Token 数值或查询结果发生任何变化；
- Session 上传协议、payload、状态机或客户端最低版本发生变化；
- 上传 P95/错误率或 content/usage/metering job age 超门禁；
- v1/v2 Worker 发生跨 job type claim；
- v2 默认开启或首期并发、batch 大于 1；
- 其他会话已发布更高版本且本次会覆盖；
- migration 编号或生产状态不一致。
