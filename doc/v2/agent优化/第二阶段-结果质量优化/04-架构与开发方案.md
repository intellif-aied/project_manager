# Session Digest v2.1 架构与开发方案

> 状态：v2.1 已在 14.157 测试环境实施；生产未启用
> 实施原则：服务端确定性归约、版本隔离、测试显式启用、生产门禁后切换

## 1. 总体架构

```text
Session 上传与内容投影（保持不变）
              |
              v
    v1 Digest Reconciler/Worker（保持不变）
              |
              +---------------------> session-digest/v1
              |
              v
    v2.1 Digest Reconciler
    job_type = build_content_slice_digest_v2
              |
              v
    Digest v2.1 Builder Worker
    ├─ Turn / Noise / Evidence Extractor
    ├─ Conservative Reducer Registry
    ├─ Result Linker / State Resolver
    ├─ Asia/Shanghai Daily Summaries
    └─ 64 KiB Budgeter / Serializer
              |
              v
 session_slice_digest_revisions
   version = session-digest/v2.1
              |
              v
 Report Source Selection Assembler
 ├─ period_relation
 ├─ 16 KiB report-period projection
 ├─ multi-item fair compaction
 └─ frozen payload/hash
              |
              v
 Report MCP get_sessions(digest_v2)
              |
              v
 Aida Report Skill 1.0.10
              |
              v
 write_report_result
```

生产路径继续复用已上线的“异步构建 + 冻结 selection”模式，但不让 v1/v2
Worker 竞争同一种任务。v2.1 使用独立 job type、独立 claim 范围和生产默认
关闭的 Worker；14.157 测试环境已显式启用，且只读取已经完成的内容投影，避免
进入上传事务、MCP 请求时延和 Agent 原文读取链路。

稳定性优先原则：

1. 不修改 v1 Extractor/Processor 的行为；
2. 不把 v2 逻辑塞入 v1 的大 switch；
3. 不让两个版本的 Worker claim `build_content_slice_digest` 同类任务；
4. 不引入 RTK 运行时依赖；
5. v2 失败只影响 v2 Revision ready，不影响上传、Token 和 v1；
6. 首期允许少量代码重复，待 v2 稳定后再评估公共抽象，避免为复用而重构已上线链路。

## 2. 组件设计

### 2.1 Turn Segmenter

职责：

- 按 cursor 和 turn 事件建立候选 Work Unit；
- 处理 task complete、abort、rollback 和 compaction；
- 标记 superseded 分支；
- 排除自动注入的非用户目标；
- 为后续证据关联提供 Work Unit 范围。

实现位置：

```text
api/internal/sessiondigestv2/extractor.go
api/internal/sessiondigestv2/extractor_test.go
```

### 2.2 Noise Filter

当前 `isNoiseGoal` 只检查平铺字符串前缀。v2 需要：

1. 对可能为 JSON 的字符串递归解析；
2. 识别 content block 的真实 role/type；
3. 对 AGENTS、environment、permissions、system/developer 包装做结构化排除；
4. 保留真正由用户输入的业务引用；
5. 记录排除原因计数，用于评测。

建议新增稳定 reason：

- `system_context`
- `repository_instruction`
- `environment_metadata`
- `reasoning`
- `token_telemetry`
- `binary_or_large_blob`
- `unknown_schema`

### 2.3 Evidence Extractor

在现有 SQL allow-list 思路上扩充有界证据，但由 v2 独立实现，不修改 v1 SQL 投影和提取规则：

| 命令/事件 | 提取内容 |
| --- | --- |
| apply_patch/Edit/Write | operation、规范路径 |
| test/lint/typecheck/build | 命令族、退出状态、短摘要 |
| git commit | 成功状态、短 commit SHA、subject |
| git status/diff --stat | 有界变更摘要，不保存完整 diff |
| docker build/push/compose | image/tag/digest、服务状态 |
| health/port check | 状态码或健康结果 |
| curl/API check | HTTP 状态、允许字段断言，不保留 Header/token/body |
| artifact create | 路径、hash、大小 |
| user confirmation | accepted/rejected decision |

必须先对命令和输出脱敏，再生成短 evidence summary。原始 stdout/stderr 不进入 Digest。

#### 2.3.1 Conservative Reducer Registry

参考 RTK 的“按命令类型选择解析器”结构，但只借鉴解析方式：

```text
Tool Event
  -> Command Classifier
  -> process_exit 基线 reducer
  -> 格式签名匹配
       ├─ go_test_ndjson
       ├─ test_summary
       ├─ git
       ├─ file_change
       ├─ runtime_check
       └─ generic_unknown
  -> Standard Evidence
```

实现限制：

- 不调用 RTK，不运行 Session 中的命令，不修改命令参数；
- 不使用 RTK Hook、tee、analytics 或 raw fallback；
- 优先读取事件已有的结构化字段和退出码；
- 只有格式签名和 fixture 均匹配才启用专用 reducer；
- 无法识别时输出 `unknown`，不能用文本关键词猜测成功；
- 每个 reducer 都是纯函数，输入为有界事件投影，输出为有界 Evidence；
- 首期只实现 14.159 corpus 高频命令族，低频命令使用通用 reducer。

#### 2.3.2 首期范围控制

首期不追求覆盖 RTK 的全部命令。建议按以下顺序开发：

1. `process_exit`、`file_change`；
2. 14.159 中实际出现频率最高的 test/build 命令；
3. Git commit/status/diff-stat；
4. Docker/health/API 等发布证据；
5. 其他命令仅在 Gold 证明影响关键结果召回后增加。

每增加一个专用 reducer，必须同时增加真实 fixture、畸形输入、敏感信息和 fallback 测试。

### 2.4 Result Linker

Result Linker 只在同一 Work Unit 内关联：

- goal；
- final claim；
- file changes；
- validations；
- deliveries；
- decisions；
- failures。

不做跨 Session 语义推理。无法证明的 Agent claim 保持 C/D 级。

### 2.5 State Resolver

按 Work Unit 和验证 key 处理：

- 尝试序列；
- 最后状态；
- failure 是否被解决；
- rollback/superseded；
- pending question；
- completed/partial/blocked/failed。

状态计算保持确定性并由 extractor/reducer 的 Golden 测试覆盖：

```text
api/internal/sessiondigestv2/extractor.go
api/internal/sessiondigestv2/reducer.go
```

### 2.6 Budgeter

现有 v1 `budget.go` 不修改，v2.1 在独立包实现：

- 先保留结果证据；
- 对 discussion 做 aggregate；
- 每个来源 item 都有 coverage；
- 持久化 Revision 硬预算 64 KiB；
- 报告期单 item 投影预算 16 KiB；
- selection 层公平压缩；
- 稳定序列化与 hash；
- 超限明确失败。

### 2.7 Selection Assembler

Assembler 新增：

- `report_period`；
- Work Unit `period_relation`；
- `daily_summaries` 与 `report_period_summary`；
- v2 coverage；
- `result_focused` compaction；
- v1/v2 version match 校验。

报告期投影必须先按 Asia/Shanghai 业务日期选择当天 summary，再执行 16 KiB
裁剪，不能先压缩完整 Session 后再选日期。完整切片选择、权限、content epoch
和 snapshot freeze 保持不变。

### 2.8 Report Skill

`api/service/daily_report_skill.go` 需要发布新不可变 Skill 版本。核心规则：

```text
先写结果，再写过程；
先写 A/B 级结果，再写决定和讨论；
完成、部分完成、失败、待确认必须区分；
测试失败不得被“验证完成”覆盖；
文件清单只作证据，不单独作为成果；
没有交付证据时写“完成讨论/形成方案”，不写“已实现”。
```

建议个人日报结构：

```markdown
### 今日完成与产出
### 验证结果
### 已确认的设计决定
### 未完成、失败与待跟进
```

结构可按实际内容省略空节，不强制生成冗余标题。

## 3. 数据库方案

### 3.1 复用现有表

继续使用：

- `session_slice_digest_revisions`
- `report_source_selection_items`
- `report_source_selections`

`digest_json` 为 JSONB，可承载 v2，不新增结果表。

### 3.2 必要迁移

现有数据库约束只允许 `full/digest_v1`，任务类型只允许 `build_content_slice_digest`。正式接入 `digest_v2` 需要一个小型 forward migration：

1. 扩展 `required_read_mode` check；
2. 扩展 `read_completed_mode` check；
3. 保留 completed mode 必须等于 required mode；
4. 增加 `build_content_slice_digest_v2` job type；
5. 为 v2 job 增加独立唯一索引和 content epoch 约束；
6. 不修改 v1 数据；
7. 不重写历史 selection。

本次实际迁移：

```text
api/db/migrations/020_report_digest_v2.sql
```

仓库已有 `019_session_upload_content_status.sql`，因此本次使用 020。14.157 已从
019 正常迁移到 020；生产发布前仍必须先确认生产最高版本，已经是 020 时不得
重复执行。

### 3.3 双版本构建

测试阶段允许同一切片同时拥有 v1/v2 Revision，现有唯一键已包含 digest version。

建议配置：

```text
SESSION_DIGEST_V2_BUILD_ENABLED=false|true
SESSION_DIGEST_V2_RECONCILE_BATCH=1..N
SESSION_DIGEST_V2_WORKER_BATCH=1
MANAGED_AGENT_REPORT_SESSION_READ_MODE=digest_v1|digest_v2
```

规则：

- 默认 `SESSION_DIGEST_V2_BUILD_ENABLED=false`；
- 离线评测阶段不启动生产 v2 Worker；
- 14.157 测试环境已显式启用，`api/main.go` 首期只启动一个 v2 Worker；
- `SESSION_DIGEST_V2_WORKER_BATCH` 首期只允许为 1，其他值配置校验失败；
- 生产先只准备 v2 Revision，报告读取仍保持 v1；
- 全局切换后的首个观察周期继续构建 v1，保证新增 Session 可快速回退；
- 是否停止新 v1 构建必须另行批准，历史 v1 Revision 永久保留。

## 4. 服务端代码改动

### 4.1 `api/internal/sessiondigestv2`

已新增独立包：

- `model.go`；
- `reconciler.go`；
- `processor.go`；
- `worker.go`；
- `extractor.go`；
- `reducer.go`；
- `daily.go`；
- `period.go`；
- `text.go`；
- `budget.go`；
- 对应单元与 PostgreSQL 集成测试。

现有 `api/internal/sessiondigest` 继续作为 v1 包，不修改其 Extractor、Budgeter 和 Worker claim 行为。v2 可以复用稳定的 hash/UTF-8 小工具，但不得为了抽公共层大规模重构 v1。

### 4.2 `api/internal/sessionsync` 与任务队列

- 新增 `JobBuildContentSliceDigestV2` 常量；
- v2 Reconciler 只创建 `build_content_slice_digest_v2`；
- v2 Worker 只 claim v2 job type；
- v1、content、usage、metering Worker 的 job type 集合保持不变；
- 不修改 Prepare/Chunk/Finalize 协议和事务；
- 不把 v2 job 添加到上传事务，仍由内容投影 ready 后的 Reconciler 异步发现。

### 4.3 `api/internal/reportsource`

- Config 接受 `digest_v2`；
- attach 前批量加载指定版本 Revision；
- selection assembler 支持 v2 schema；
- MCP 重复读取逐字节一致；
- 写回校验 required/read completed mode；
- v1/v2 路由只影响新 run。

### 4.4 `api/service`

- 更新 Report Skill 模板；
- 新增 v2 静态契约测试；
- 保留 v1 分支，未知 mode 明确失败；
- 新 Skill 使用独立 immutable version。

### 4.5 `api/handler` 与 `api/main.go`

- 配置校验；
- run input 冻结 read mode/version；
- 错误码映射；
- v2 Worker 默认关闭、单并发启动；
- 不改变用户调用 API 和报告写回结构。

## 9. Token、Session 上传与运行资源边界

### 9.1 Token 统计

Token/成本由 `api/internal/usage` 和 metering pipeline 从原始上传对象独立解析。Digest v2：

- 不读取或写入 usage/metering 汇总表；
- 不修改 `token_count` 原始事件；
- 仅在报告 Digest 中排除 Token 遥测，排除不等于删除；
- 不改变 `/report-source-sessions` 的 `total_tokens` 查询口径。

因此预期不会改变 Token 数值。剩余风险是 API/数据库资源竞争造成 Token projection 延迟，而不是统计错误。

### 9.2 Session 上传和 Aida 客户端

Prepare、Chunk、Finalize、MinIO 原始对象和内容投影保持不变。v2 Reconciler 只在完整切片已经投影完成后异步创建任务，因此：

- Aida 客户端不升级也能继续上传；
- 上传请求不等待 v2；
- v2 失败不回滚已接受上传；
- 不需要用户安装 RTK；
- 不改变 upload state、cursor、hash、activity slices 或 token_usage 字段。

### 9.3 间接资源风险

Digest、content、usage 和 metering Worker 仍运行在同一个 API 进程并共享 PostgreSQL，因此必须控制：

- v2 Worker 初始并发 1、batch 1；
- Reconciler 小批量、回填限速；
- 构建时只流式保留有界 Evidence，不在内存保存完整工具输出；
- 监控上传 API P95、content/usage job age、数据库 CPU/IO、v2 build latency；
- 任一核心指标回归时先关闭 v2 build，报告读取继续 v1。

## 10. 风险与控制

| 风险 | 控制 |
| --- | --- |
| v1/v2 Worker 抢同类 job | 使用独立 `build_content_slice_digest_v2` job type |
| 为复用重构 v1 引入回归 | v2 独立包，首期容忍少量重复 |
| RTK 行为不适合历史 Session | 只借鉴 reducer 方法，不接入二进制/Hook/命令执行 |
| reducer 误判成功或失败 | 结构化状态优先，格式不匹配降级 unknown |
| parser 崩溃或内存放大 | 纯函数、有界输入、fuzz、单并发和流式聚合 |
| 规则过拟合 target Session | 使用 14.159 全量 corpus + holdout |
| v2 输入变大 | 64 KiB Revision、16 KiB period item、128 KiB selection 硬上限 |
| 误把讨论当结果 | D 级限制 + discussion aggregate |
| 误判测试状态 | Work Unit 内按时间归并 attempts |
| 历史选择漂移 | attach 前冻结版本、payload 和 hash |
| LLM judge 自洽偏差 | 确定性 grader 优先、人工校准 |
| 生产版本混乱 | v1/v2 明确版本、immutable Skill、禁止隐藏灰度 |
| 14.159 数据泄密 | 本机只读运行、manifest 先行、脱敏产物 |
| Token projection 延迟 | v2 默认关闭、batch 1、监控 usage job age |
| Session 上传延迟 | 不进入上传事务；监控上传 P95，异常立即停 v2 Worker |
