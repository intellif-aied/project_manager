## 2. 数据采集原则

1. 先采 manifest，不先复制原文；
2. manifest 只包含 Session Ref、路径、大小、时间、hash、agent_type、cwd 等元数据；
3. 原始 JSONL 默认留在 14.159，只读处理；
4. 评测输出必须脱敏；
5. 不改动 Session 文件、Git 仓库和运行服务；
6. 不把 14.159 原文上传到生产；
7. 需要真实 Agent E2E 时，只向隔离测试账号上传明确选中的样本；
8. 所有样本使用 SHA256 固定身份，文件变化后视为新 corpus。

安全规则：

- Git 只读 `rev-parse/status --porcelain`，不 checkout/reset；
- manifest 自身计算总 SHA256，并写入评测报告。

## 4. Corpus 分层

### 4.1 Full Corpus

14.159 manifest 中 100% Session：

- 全部执行 parser、v1 replay、v2 replay；
- 验证无崩溃、无泄密、hash 稳定、预算和 coverage；
- 统计工具/命令族、专用 reducer 命中率、`generic_unknown` 比例和 Top 未识别格式；
- 生成结构指标，不调用真实报告 Agent；
- 单样本失败不阻断其他样本，最终输出失败清单。

这是“能处理一大堆 Session”的主要证据。

专用 reducer 的首期范围必须由该统计决定，不能因为 RTK 已支持某个命令就
直接移植。Top 未识别格式只有在影响 Gold 关键结果召回时才进入开发范围。

### 4.2 Stratified Benchmark

从 Full Corpus 按风险分层抽样，数量取 `min(60, corpus 总数)`；若总数不足 60，则全部进入。

必须覆盖：

| 分层 | 条件 |
| --- | --- |
| 大小 | `<1 MiB`、`1-10 MiB`、`10-50 MiB`、`>=50 MiB` |
| Agent | Codex、Claude Code；存在其他客户端时单列 |
| 轮次 | 单任务、多任务、超过 100 个用户轮次 |
| 时间 | 单日、跨日、跨周 |
| 工作类型 | 代码、文档、设计讨论、诊断、部署 |
| 状态 | 全成功、失败后成功、最终失败、待用户确认 |
| 轨迹 | rollback、abort、compaction、长工具输出 |
| 工具输出 | 结构化 JSON/NDJSON、普通文本、畸形输出、重复日志、未知命令 |
| 安全 | AGENTS、环境注入、凭据、MCP 输出、图片/base64 |

所有 `>=10 MiB` 和所有最终失败样本优先进入，不因配额被随机排除。

### 4.3 Human Gold

从 Stratified Benchmark 选择 `min(20, benchmark 总数)` 做双人或交叉人工标注。

每个 Gold 样本至少包含：

```json
{
  "session_ref": "...",
  "report_period": {"start": "...", "end": "..."},
  "expected_results": [],
  "expected_decisions": [],
  "expected_validations": [],
  "expected_unresolved": [],
  "forbidden_claims": [],
  "evidence_anchors": [],
  "reviewer": "...",
  "review_status": "approved"
}
```

Gold 不能由当前实现自动生成后直接接受。标注者必须查看原始轨迹的必要片段和环境证据。

### 4.4 Holdout

至少 20% Gold/Benchmark 样本在规则开发阶段隐藏，最终 Review 才运行，避免针对已知样本硬编码。

目标 Session 始终属于公开回归集，不属于 holdout。

## 6. 回放矩阵

### 6.1 结构回放

对 Full Corpus：

| Run | 输入 | 输出 |
| --- | --- | --- |
| R1 | 原始 JSONL + v1 代码 | v1 Digest/hash/metrics |
| R2 | 相同原始 JSONL + v2 代码 | v2 Digest/hash/metrics |
| R3 | 重复 v2 | 逐字节稳定性 |
| R4 | 安全扫描 | 敏感值、禁止字段和大正文检查 |

### 6.2 日报 A/B

对 Stratified Benchmark：

| 组 | Session 来源 | Report Skill |
| --- | --- | --- |
| A | `digest_v1` | 当前线上 Skill |
| B | `digest_v2` | 结果优先 Skill |
| C | full/raw 基线 | 结果优先 Skill，仅小中型或经过批准的样本 |

固定：

- 同一 Session/切片；
- 同一报告 period；
- 同一模型；
- 同一目标账号；
- 同一 tasks/requirements 辅助数据；
- 同一运行顺序策略；
- 同一超时与重试规则。

大 Session 的 full/raw 组若会重新触发容量事故，可以不执行，但必须写明 `baseline_not_run_due_to_capacity`，不能把缺失基线写成通过。

### 6.3 多次 Trial

模型输出存在波动。对至少 6 个高风险样本执行 3 次 B 组 trial，统计最差、最好和中位结果；不能只挑最好一次。

## 7. 环境真值

按证据强度使用以下 oracle：

### 7.1 Executable Oracle

- contemporaneous test/build exit code；
- health/API 状态；
- artifact/image digest；
- 服务状态。

有条件时在隔离 worktree/container 重放测试。禁止直接修改 14.159 共享工作区。

### 7.2 Repository Oracle

- commit SHA 是否存在；
- commit 中变更文件；
- Session 内 patch_apply/Edit/Write；
- Git status/diff stat。

未提交工作只能证明文件变化，不能自动证明功能正确。

### 7.3 Decision Oracle

产品/架构决定由用户明确的“同意、按此执行、否决、保留”等消息和对应文档变更共同判断。

### 7.4 Human Oracle

对开放式设计、分析质量和“日报是否抓住重点”使用人工标注。LLM judge 只能辅助，不能覆盖事实矛盾。

## 8. 真实 Agent E2E

选中的 Session 使用隔离测试账号和测试 Skill：

1. 核对测试环境 API、MCP、Skill 版本；
2. 使用当前受支持的 Aida CLI 上传，验证分块和最终 hash；
3. 等待 v1/v2 Revision ready；
4. 创建固定 source selection；
5. 分别生成 v1/v2 日报；
6. 获取 Agent run trace、MCP payload、报告正文和 Token；
7. 自动 grade；
8. 人工 Review；
9. 不把测试报告覆盖生产用户日报。

若大文件上传因客户端或服务端限制失败：

- 单独记录上传缺陷；
- 结构回放继续执行；
- 真实 E2E 标记 blocked；
- 不通过手工缩小文件伪装为原样本通过。
