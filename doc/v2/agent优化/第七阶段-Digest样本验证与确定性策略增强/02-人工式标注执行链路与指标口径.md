# 第七阶段：真实 Session 人工式标注执行链路与指标口径

> 状态：随第七阶段封板；保留为问题复现参考，不再作为持续执行计划

> 用途：把本机 Codex/Claude Session JSONL 转换为可复核的 Atomic Work Unit Golden Cases

> 边界：这是离线 Agent 辅助的逐段标注，不是在生产 Digest 中接入 LLM；Golden 冻结前需要人工抽检或确认争议项

> 封板校正：Digest 指标只评价确定性解析、关联、压缩和事实正确性，不替 Report Agent/Skill 判断某条命令是否值得写入日报。普通命令未进入 Digest 不能直接计为“日报证据漏召回”。

## 1. 标注目标

每个样本最终需要回答四类问题：

1. 哪些结构化用户文本应该形成 Atomic Work Unit；
2. 哪些 Agent 回答、文件操作、命令调用和命令结果属于该 Work Unit；
3. 哪些内容是 reasoning、系统/Skill 注入、镜像事件、大输出或其他噪音；
4. 当前 Digest 相对 Golden 存在哪些边界、证据、事实强度、去重和分批一致性偏差。

不标注多轮 Work Stream，不判断“继续”是否应该与上一轮合并，不写日报文案。

## 2. 输入与安全边界

### 2.1 输入分层

- **L1 完整真实 Session**：只读使用本机原 JSONL，用于事件分布、容量、噪音和完整回放。
- **L2 脱敏 Golden Case**：只保留复现问题必需的事件结构、cursor、工具类型、退出状态和短摘要，用于仓库评审与后续回归。

### 2.2 安全规则

- 不修改、重命名或补写原 Session JSONL；
- 不把完整 Session 上传到测试服务器或提交到 Git；
- 文档不保留凭据、内网地址、完整 remote、完整 commit hash、完整命令输出或长用户原文；
- 原文身份使用 session ID、原文 SHA-256、字节数和本机只读路径核对；
- 对不确定事实标记 `unknown`，不根据 final answer 反推工具实际成功。

## 3. 逐段读取流程

### Step 1：冻结样本身份

记录文件大小、行数、SHA-256、首尾时间、是否换行结尾、Agent 类型与事件 schema 特征。原文变化后不得沿用原 Golden。

### Step 2：先建立事件索引，不盲读长文本

逐行只提取：

- 行号和 `[start_cursor, end_cursor)`；
- outer event type 和 payload subtype；
- role/phase/tool name/`call_id`/`tool_use_id`；
- 单行字节数；
- 用户文本、final answer 和命令的有界脱敏摘要。

reasoning、world state、token_count、系统指令和大工具输出只记录类型/体积，不放入 Golden 正文。

### Step 3：确定 Atomic Work Unit 边界

一个有效用户 text event 是候选边界。以下内容不建新 Unit：

- 系统、developer、AGENTS、Skill、memory、environment 注入；
- 同一用户消息的 Codex 镜像事件；
- 图片传输 wrapper、turn aborted wrapper、subagent notification；
- 工具输出中的对话文本；
- 只用于审批/风险评估的嵌套会话。

“一条用户消息含多个业务要求”仍然是一个 Atomic Work Unit；不用语义规则拆成多个任务。

### Step 4：按结构关联客观证据

关联优先级：

1. `call_id/tool_use_id` 精确匹配；
2. 原生工具事件与文件路径；
3. cursor 顺序和当前开放 Unit；
4. 事件时间；
5. Agent final answer 仅作 claim，不用它补造缺失证据。

命令需分开标记“调用意图”和“客观结果”。一次失败、后续成功时保留两次 attempt，不用最后状态覆盖历史。

### Step 5：拆开事实维度

每个 Unit 至少标注：

```yaml
change_state: changed | no_change_evidence | unknown
validation_state: passed | failed | mixed | not_run | unknown
agent_claim_state: complete | partial | failed | unclear | absent
user_feedback_state: confirmed | rejected | no_feedback | unclear
evidence_level: claim_only | change_evidence | validation_evidence | no_evidence
unpaired_calls: []
unpaired_results: []
```

Golden 层不强制输出业务 `completed`。若现有 Digest 输出 `completed/partial/failed`，必须单独评估它是否超出客观事实。

### Step 6：回放当前 Digest 并做结构化 diff

对同一原文运行当前 `session-digest-eval`，对比：

- Work Unit 数量、边界和 goal；
- changes、validations、evidence、agent claims；
- pass/fail/unknown 和 evidence grade；
- 噪音泄漏、Digest 字节数和 coverage；
- `PrepareForPeriod` 后 Report Agent 可见 highlights 是否仍保留必需事实。

### Step 7：生成分批 cut-point 矩阵

优先在以下事件之间切分：

- user message / Agent action；
- function call / function result；
- file change / validation；
- failed attempt / successful retry；
- Agent commentary / final answer。

比较“一次 finalize”和“多次 finalize”的规范化 Atomic facts。比较时排除 Revision ID、Slice ID、created_at 等运行元数据，保留原事件 cursor、goal、证据类型、归属和状态。

### Step 8：复核和冻结

标注状态分为：

- `draft`：已逐段标注，未完成第二遍回查；
- `reviewed`：已回查 cursor/call/result，争议项已列出；
- `frozen`：人工确认或抽检通过，可作为回归门禁。

自动化测试不得直接依赖 `draft` 标注。

## 4. 单个 Golden Work Unit 记录格式

```yaml
case_id: GC-XXX
annotation_status: draft
source:
  session_id: <opaque-id>
  raw_sha256: <sha256>
work_unit:
  source_event:
    line: 0
    cursor: [0, 0]
    event_type: response_item.message
  goal: <bounded text>
  mirrored_events: []
facts:
  changes: []
  command_attempts: []
  validations: []
  agent_claims: []
  user_feedback: []
objective_state:
  change_state: no_change_evidence
  validation_state: unknown
  agent_claim_state: unclear
  user_feedback_state: no_feedback
  evidence_level: claim_only
current_digest_diff:
  boundary: match
  missing_evidence: []
  extra_evidence: []
  fact_errors: []
open_questions: []
```

## 5. 指标口径

### 5.1 边界与关联

| 指标 | 公式/口径 |
| --- | --- |
| Work Unit 边界精确率 | 匹配 Golden 源用户事件的输出 Unit 数 / 输出 Unit 总数 |
| Work Unit 边界召回率 | 已生成 Unit 的 Golden 源用户事件数 / Golden 期望 Unit 总数 |
| 证据归属准确率 | 挂到正确 Unit 的 evidence 数 / 已输出 evidence 数 |
| 关联保持率 | 按 call/tool ID 或原生事件正确关联的 Golden evidence 数 / 应关联 evidence 总数 |

边界指标不测量多轮业务主线是否归并；该语义属于 Report Agent。

### 5.2 证据和事实

| 指标 | 公式/口径 |
| --- | --- |
| 证据召回率 | 已提取 Golden evidence 数 / Golden evidence 总数，按 change/test/build/commit/runtime/api/repository 分类计算 |
| 证据精确率 | 真实且状态正确的输出 evidence 数 / 输出 evidence 总数 |
| 关键证据召回率 | 直接支持或否定用户目标的已提取 evidence / Golden 关键 evidence |
| 事实错误率 | failed→passed、no-change→changed、claim-only→verified 等错误数 / 输出客观事实数 |
| Report Agent 可见事实保留率 | 最终 report-period 投影仍可区分的 Golden 关键事实 / Revision Digest 已正确提取的 Golden 关键事实 |

失败识别成成功、无证据升级为已验证、证据挂错 Unit 属于硬错误，验收线为 0。

### 5.3 压缩、一致性和容量

| 指标 | 公式/口径 |
| --- | --- |
| 噪声压缩率 | `1 - digest_bytes / raw_jsonl_bytes`；同时记录 P50/P95/max，不单独作为质量结论 |
| 跨批次一致性 | 同一原文单 Slice 和任意合法 cut-point 多 Slice 的规范化 Atomic facts 完全一致 |
| 幂等性 | 同一输入+版本+配置的两个全新构建，规范化 Digest JSON 和 digest hash 字节级一致 |
| 容量稳定性 | 记录 raw bytes、event count、wall time、峰值 RSS、读取放大比、digest bytes、超时/重试/失败；先建基线后确定资源门槛 |

压缩率和速度不得覆盖事实错误或证据遗漏。

## 6. 首轮执行顺序

1. 短只读查询 Session：校准边界、镜像去重、外部验证和 claim 支持；
2. 修改+测试失败后成功 Session：校准 change/validation attempts；
3. call/result 可切在不同上传批次的 Session：建立 cut-point 基线；
4. 只分析、无修改 Session：校准 claim-only 与客观证据边界；
5. 超大、多图片/大日志 Session：测量噪声压缩和容量基线；
6. Claude Code 样本：对齐 `tool_use/tool_result` 与 Codex `function_call/function_call_output` 语义。

## 7. 修复准入和停止规则

- 每个规则修复必须先有一个 reviewed/frozen Golden 失败样本；
- 优先使用 event type、cursor、call/tool ID、exit status 和工具原生结构；
- 不为一条用户文案增加专用自然语言关键词；
- 新规则使其他 frozen Golden 发生未评审差异时停止；
- 如问题是 Digest 已保留事实但 Report Agent 写错，转交 Report Agent/Skill，不修改 Digest；
- 不在本链路中增加 LLM Digest Builder 或 Work Stream Consolidator。
