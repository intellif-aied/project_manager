# 第七阶段设计评审：Digest 样本验证与确定性策略增强

> 状态：已于 2026-07-21 评审封板；本文降级为历史分析材料，不再作为开发需求或验收依据

> 复核基线：2026-07-21，`session-digest/v2.9.0`

> 本阶段统一结论：不在上传阶段或 Digest Builder 中引入 LLM；多轮语义归并和报告写作仍由 Report Agent 完成

> 封板结论见 [99-封板结论.md](99-封板结论.md)。本文中的 Golden Case 扩充、指标建设和建议修复项均不再进入执行计划；其中仍有价值的已知风险只保留在总纲问题清单中，等待生产证据重新立项。

## 0. 评审结论

当前 Digest 是一个确定性的“Session 事实压缩器”，不是任务理解器。它的正确输出单位是可追溯的 Atomic Work Unit 和客观证据，而不是 Work Stream 或日报文案。

本轮源码复核得出四个必须先向评审会说清的事实：

1. **Session 上传和内容投影是增量的，Digest Builder 本身不是跨批次增量状态机。** `ContentProjectionProcessor.processChunk` 使用 `content_indexed_cursor` 按 chunk 推进；但 `Processor.Process` 每次新建 `Extractor`，完整重放当前 Slice 的 `[start_cursor, end_cursor)`。
2. **`pendingCalls` 、当前 Work Unit 和去重集合都只存在于一次 Extractor 内存中。** 同一 Slice 内的晚到命令结果会按 `call_id` 挂回原 Work Unit，不会挂到最新 Work Unit；跨 Slice 时映射丢失，结果会被忽略，而不是被正确关联。
3. **当前 `status` 存在过度下结论。** `resolveUnit` 明确使用“有文件修改、最后一次验证通过或用户确认”之一直接输出 `completed`；这不等于用户目标已完成。
4. **客观证据在 Revision Digest 中存在，但报告期投影会去掉详细 Work Unit。** `PrepareForPeriod` 把 `WorkUnits` 置空，Report Agent 的报告面清单是 `report_period_summary.days[].highlights`，主要保留 goal、result statement、status、evidence grade 和 unresolved，而不是完整 `Evidence/Changes/Validations`。因此“提取到了”和“Report Agent 实际看到了”必须分开验证。

所以，第七阶段不应建 LLM Work Stream Consolidator，而应先用真实 JSONL 和 Golden Cases 把上述边界、证据、分批一致性和状态误判变成可重复回归的问题。

## 1. 当前 Digest 的准确职责和非职责

### 1.1 职责

Digest 应且只应负责：

- 从 Codex、Claude Code Session JSONL 解析有明确结构的用户消息、Agent 回答和工具事件；
- 过滤 reasoning、系统指令、AGENTS/Skill 注入、完整日志、完整 diff、图片/Base64、Token usage 和凭据；
- 按有效用户消息的结构边界形成 Atomic Work Unit，保留时间顺序和来源引用；
- 提取用户目标、Agent 最终回答、文件修改、命令调用及结果、测试、构建、提交、运行变更和接口验证等客观证据；
- 以 cursor、event type、`call_id`、时间和退出状态做确定性关联，对无法确定的结果保守降级；
- 支持上传增量、重复事件去重和跨上传批次的最终事实一致性；
- 用版本、投影 Revision、Slice cursor、source hash 和 digest hash 为 Report Agent 提供压缩、稳定、可追溯的事实输入。

其中“支持跨上传批次的最终事实一致性”是 Digest 责任，但不能因此把当前实现误说成已有持久化增量 Extractor。

### 1.2 非职责

Digest 不负责：

- 理解多轮对话是否属于同一条工作主线；
- 把多个 Atomic Work Unit 语义归并成 Work Stream；
- 判断“继续”“再检查”“还是不对”与前一轮的业务关系；
- 在多条相互矛盾的方案中判断最终业务结论；
- 生成日报、周报文案，或决定“已完成、推进中、排查中”等报告表述；
- 使用 LLM 重新阅读完整 Session JSONL。

这些语义理解与写作职责统一留在 Report Agent。Digest 的模块 seam 停在“结构化事实契约”，不向上侵入写作层。

## 2. 现有实现链路梳理

### 2.1 上传、投影和 Slice

1. `api/internal/sessionsync/sync_service.go:createContentSlice` 从上一个 Slice 的 `end_cursor` 开始，在 finalize 时创建新的 `[start_cursor, end_cursor)` Slice。因此同一 Session 分多次 finalize 会形成多个不重叠 Slice；一次上传则可能只有一个大 Slice。
2. `api/internal/sessionsync/content_projection_processor.go:processChunk` 按 chunk 解析并用 `content_indexed_cursor == chunk.start_cursor` 作顺序 CAS；已索引到 `chunk.end_cursor` 时幂等返回。
3. `api/internal/sessionsync/content_parser.go:ScanContentChunk` 以完整 JSONL 行为边界计算 cursor。`readCompleteJSONLLine` 遇到无换行的尾部时返回 `ErrIncompleteJSONLLine`，并没有服务端尾部缓冲状态。正常 Daemon 路径会在客户端保留未换行残行，不上传、不推进 ack cursor，文件补全后再从原 cursor 上传（`daemon/session_chunking.go:streamSessionJSONLChunks`、`daemon/session_sync_client.go:uploadSessionGroupIncremental`）。
4. `api/internal/sessionsync/content_projection_processor.go:processActivation` 只在 `content_indexed_cursor` 追上 source high-water 后激活投影 Revision。

### 2.2 Digest Revision 的调度和构建

1. `api/internal/sessiondigestv2/reconciler.go:RunOnce` 只选择已完全索引的 Slice，以 `(slice, projection_revision, content_epoch, digest_version, redaction_version)` 唯一创建 Revision，并以 `(job_type, target_digest_revision_id)` 去重任务。
2. `api/internal/sessiondigestv2/processor.go:Process` 每次调用 `NewExtractor()`，通过 `ContentReader.Stream` 重放当前 Slice 的完整 cursor 区间。这是“对不可变 Slice 全量回放”，不是“从上次 Digest cursor 继续”。
3. `api/internal/contentreader/reader.go:Stream` 验证 chunk 覆盖、对象 hash、事件 cursor 边界和投影索引，再向 Extractor 施加自然背压。
4. `api/internal/sessiondigestv2/processor.go:commitReady` 在提交前再次核对 content epoch、active generation、active projection 和 indexed cursor，避免把旧源结果提交为 ready。

### 2.3 Atomic Work Unit 和证据提取

- `api/internal/sessiondigestv2/extractor.go:Consume/consumeGoal` 识别 Codex 的 `event_msg.user_message` / `response_item.message`，以及 Claude Code 的 `user.message.content`。一个有效 text block 会触发一个 Work Unit；“每条用户消息严格一个”并不是完整代码语义。
- `consumeGoal` 在新 goal 前 `finalizeCurrentUnit`，所以后续 Agent 事件默认归属最近的有效用户 goal。`OK/Agree/确认` 等少量固定值是例外，会被挂到前一个 Work Unit。
- `addAgentClaim/finalizeUnit` 保留 final answer；没有工具证据时仍保留为 `agent_claim`。
- `addFileChange` 目前覆盖 Codex `apply_patch`、`patch_apply_end` 和 Claude `Edit/Write/MultiEdit/NotebookEdit`。Shell 重定向、脚本写文件等其他持久化方式没有统一的结构化覆盖。
- `addCommandCall/completeCommand` 用 `call_id -> UnitIndex` 把命令结果挂回发起调用的 Work Unit。该 map 仅在当前 Extractor 内存中。
- `api/internal/sessiondigestv2/reducer.go:classifyCommand` 用固定命令子串识别 test/lint/build/commit/git/docker/http；`ReduceCommandOutput` 只通过结构化 exit-code 文本或 Go test NDJSON 确定 pass/fail，其他输出保守返回 `unknown`。
- `api/internal/sessiondigestv2/safe_projection.go:projectSafeEvent` 对事件类型和字段做 allow-list，命令输出只投影有界 head/tail，patch 只保留文件路径；`ReduceCommandOutput` 最终只输出状态摘要，不把原日志放入 Digest。

### 2.4 报告期投影和 Report Agent 输入

1. `api/internal/sessiondigestv2/daily.go:BuildDailySummaries` 每个报告相关 Work Unit 生成一个 `DailyHighlight`，只按 sequence 排序，不做跨轮主线归并。
2. `daily.go:PrepareForPeriod` 按 Asia/Shanghai 报告日期筛选，然后清空详细 Work Units，将当前 item 变成 `period_result_focused` 视图。
3. `api/internal/sessiondigestv2/consolidate.go:MergeReportPeriodSummarySources` 将多 Slice/多 Session highlight 按时间合并；去重 key 包含 `sourceRef`，不会把同一天多个 Session 的相似业务内容语义合并。
4. `api/internal/reportsource/digest_v2.go:freezeSelectionV2ForRun` 校验每个 Revision 的版本和 hash，合并成唯一报告期成果清单，再冻结 selection payload。Report Agent 在这个冻结事实上做多轮理解和报告写作。

### 3.2 高风险问题

**R1：完成状态过度推断（已有明确代码证据）。** `extractor.go:resolveUnit` 在 `hasChanges || hasPassed || hasConfirmation` 时输出 `completed`。一条用户消息可含多个要求，一个文件发生修改或一个测试通过，都不能证明整个 goal 完成。这是本阶段第一优先级。

**R2：跨 Slice 事实链断裂（已有结构性证据，待真实样本复现）。** 若命令调用在 Slice A、输出在 Slice B，A 会生成“命令结果缺失/unknown”，B 找不到 `call_id` 后丢弃结果。同理，Slice B 以 Agent 操作开头时可能生成“未识别的历史工作单元”。

**R3：一次上传与多次上传不一定等价（未覆盖）。** Slice 是 finalize 边界，而 Extractor 状态也在 Slice 边界重置。当前只有“同一 Slice 全量回放”的稳定性，没有“任意上传切分对最终事实无影响”的契约。

**R4：证据映射粒度过粗（已有代码证据）。** 任何 pass evidence 都使 Unit 达到 A 级，任何 change 都使 Unit 达到 B 级，然后该 Unit 全部 Agent claims 都成为 `partially_supported`。证据可能只支持 claim 的一部分，不能反证其他“已发布/已修复”声明。

**R5：证据提取与 Report Agent 可见事实之间有损投影（已有代码证据）。** `PrepareForPeriod` 丢弃 WorkUnit 详细 evidence，只保留 highlight。应先用 Golden Case 判断报告期视图是否足以支持 Report Agent 做保守表述，不能只测 Revision Digest。

**R6：命令和语义类别过度依赖字符串（已有代码证据）。** `classifyCommand`、`hasIncompleteAgentClaim`、`refineUnitCategory`、`isLowInformationGoal` 均使用内嵌词表/子串。其中命令 allow-list 用于限制证据范围是合理的；用自然语言词表推断 category/status 则容易被样本文案和工具版本影响。

**R7：去重契约不完整（部分实现）。** 当前去重针对镜像 goal、单 Unit claim 和 file change，并不是以统一 event identity 覆盖所有 Digest 输入。同事件不同 cursor、镜像 Session 或重复 `call_id` 的期望行为尚未被 Golden Case 固定。

## 4. 第七阶段新目标

第七阶段重新定位为：

> Digest 样本验证与确定性策略增强阶段。

本阶段不“训练模型”，也不以增加更多词表/正则为目标。所谓“训练 Digest”的可执行定义是：

1. 收集更多真实 Codex 和 Claude Code Session JSONL，固定原文 hash、工具版本、事件 schema 和报告日期；
2. 人工标注期望 Atomic Work Unit 边界、客观证据、未配对事件和噪音，不标注 Work Stream；
3. 离线生成当前 Revision Digest 和报告期投影，与 Golden 结构化比较；
4. 将误判分类为 parser/schema、Work Unit 边界、evidence 提取、call 关联、去重、状态过度推断、报告投影丢失或上传分片不一致；
5. 优先使用 event type、cursor、`call_id/tool_use_id`、时间顺序、工具类型和 exit status 修复；无法确定则输出 `unknown/unverified`；
6. 每个修复必须带至少一个失败样本和防回归测试，不对单个日报文案做特判。

## 5. 真实 JSONL 样本集和 Golden Case 设计

### 5.1 现有基础和缺口

- `testdata/v2_sessions/` 只有 `codex_session.jsonl` 和 `claude_session.jsonl` 两个约 1 KiB 的 parser fixture，可用于 schema 冒烟，不足以验证 Digest 语义和增量一致性。
- 第三阶段已经固定 10 个真实 Codex Session（S01-S10）的原文 SHA-256、规模、报告日期和基线 Digest。这些可作为回归种子，但原有标注重点是报告成果覆盖，不是本阶段的 call/cursor/分批 Golden。
- 现有真实基线以 Codex 为主，Claude Code 版本和工具事件差异必须新增真实样本。

### 5.2 样本形式

每个 Golden Case 至少包含：

```text
<case-id>/
  manifest.json             # 来源工具/版本、原文 hash、字节数、报告日期、隐私级别
  input.jsonl               # 可入库的脱敏最小重现，保留真实事件结构和 cursor 长度
  expected_atomic.json      # Work Unit 边界、goal、claim、change、validation、evidence
  expected_omissions.json   # 必须被过滤的事件/字段和泄漏禁止词
  partitions.json           # 一次上传、分批上传、中断/重试的 cut points
```

对超大或含敏感信息的真实原文，不强行把原文提交到 Git；在受控样本存储中固定不可变对象和 SHA-256，仓库只保留 manifest、脱敏最小重现与期望输出。所有 Golden 标注必须指向原 event type 和 cursor 范围，不只写一段人工总结。

### 5.3 状态和事实标注

Golden 不用一个 `completed` 代替所有事实，至少分开标注：

- `change_state`：`changed / no_change_evidence / unknown`；
- `validation_state`：`passed / failed / mixed / not_run / unknown`；
- `agent_claim_state`：`complete / partial / failed / unclear / absent`；
- `user_feedback_state`：`confirmed / rejected / no_feedback / unclear`；
- `evidence_level`：`claim_only / change_evidence / validation_evidence / no_evidence`；
- `unpaired_calls` 与 `unpaired_results`；
- 如仍保留综合 `status`，则不能强于上述客观维度，无法证明时必须是 `unknown/unverified`。

这些是本阶段要先验证的数据契约方向，不在本评审中预先决定表结构或直接开发。

### 5.4 必备场景和期望不变式

| # | 场景 | Golden 重点 |
| ---: | --- | --- |
| 1 | 单轮完成简单代码修改 | 一个 Unit；change 和 validation 分开；无日志/diff 泄漏 |
| 2 | 多轮持续处理同一问题 | 每个有效用户轮次仍是 Atomic Unit；不在 Digest 中强行归并 |
| 3 | “继续/再检查/还是不对” | 保留原文和顺序；不伪造业务关系；报告主线由 Report Agent 理解 |
| 4 | 一条用户消息多个要求 | 不得因完成一个子要求将整体输出 completed |
| 5 | 只分析、不修改 | 无 change 是正常事实；final answer 保留为 claim/分析结果，不伪造实现证据 |
| 6 | 修改后测试失败 | changed + validation failed + unresolved；不得 completed |
| 7 | 测试先失败后成功 | 保留 attempts 和最后状态；仍不自动证明整个 goal 完成 |
| 8 | Agent 声称完成但无修改/验证 | claim_only；不得升级为客观完成 |
| 9 | 命令 call/result 跨上传批次 | 结果回挂原 Unit，或明确 unpaired；绝不挂最新 Unit；分批/单次事实等价 |
| 10 | Session 中断、恢复、继续 | 已提交 cursor 不重复；开放 Unit 边界不造成证据错挂 |
| 11 | 同事件重复写入/镜像保存 | 事实不重复计数；不同真实操作不被错删 |
| 12 | JSONL 尾部不完整/字段截断/异常 | 分别锁定 Daemon 残行等待补全、服务端拒绝错误半行 Chunk、完整但非法 JSON 计入 malformed 三种语义 |
| 13 | 大量日志、diff、图片、Base64 | 大输出不进 Digest；必要状态/路径仍可恢复；体积有界 |
| 14 | 同一天多 Session 处理同一项工作 | 保留 source provenance；Digest 不语义归并；Report Agent 可见完整时序 |
| 15 | 前面方案被后续完全推翻 | 新旧事实都保留且时序正确；Digest 不自作主张删旧方案 |
| 16 | 普通查询命令与验证命令混合 | 查询不冒充 validation；真实验证保留 exit status；未识别则 unknown |
| 17 | apply_patch、文件写入、shell 命令等修改方式 | 分工具建立覆盖矩阵；未可观测写入不得被猜测为 changed |
| 18 | Codex 与 Claude Code 结构/版本差异 | 同类事实的规范化输出一致；未知 schema 明确记录而非静默误解 |

## 6. 自动化回归测试方案

### 6.1 四层测试

1. **Parser 层**：对 Codex/Claude 每个已知版本的 event type、timestamp、cursor、malformed count 做 fixture 断言；保留现有 `content_parser_test.go` 并扩展真实结构。
2. **Extractor 层**：对 Work Unit 边界、goal、claim、change、validation、evidence、unpaired call 做结构化断言；不只比较整个 JSON snapshot，避免无关字段掩盖错误。
3. **Slice/增量层**：对同一 JSONL 生成一次 finalize、多次 finalize、在 call/result 之间切分、在 user/final answer 之间切分和中断重试。将最终规范化事实集合比较，忽略 Revision ID/created_at 等预期不同的运行元数据。
4. **Report input 层**：实际跑 `PrepareForPeriod` 和 `MergeReportPeriodSummarySources`，检查报告期 highlights 是否保留 Golden 所需的事实强度和 provenance。这一层不运行 Report Agent，避免将模型波动归因给 Digest。

### 6.2 必须新增的不变式测试

- **重放幂等**：同一 input、版本和预算连续运行两次，规范化 Digest JSON 和 SHA-256 完全相同。
- **分批等价**：对每个候选 cut point 比较“单 Slice”和“多 Slice 合并后”的 Atomic facts；当前预计在 call/result 跨界时先失败，该失败应作为修复输入而不是放宽测试。
- **晚到结果归属**：原 Unit 、后续 Unit 和 result 三者并存；结果只能挂原 Unit 或标记 unpaired，不得挂后续 Unit。
- **尾部恢复**：正常 Daemon 首次扫描残行时不上传且不推进 ack cursor，补全后必须与一次读到完整行等价；另设非法客户端半行 Chunk 用例，断言服务端投影拒绝且不跨 Chunk 猜测拼接。
- **重复抗性**：原样本、重复一个事件和镜像保存样本分别检查；输出中客观事实数量符合 Golden。
- **保守状态**：只有 change、只有一个 pass、只有 claim、mixed validation、用户否定等组合均有表驱动测试，且无不支持的 `completed`。
- **Revision 不可变**：数据库集成测试验证 ready payload/hash/cursor/version 不可修改，允许的状态只能按契约转为 superseded。
- **无噪音泄漏**：对 reasoning、AGENTS/Skill、Base64、完整 diff、完整 log、Token usage 和凭据使用禁止词+大小上限双重断言。

### 6.3 离线评测器收口

现有 `api/cmd/session-digest-eval/main.go` 已能读取完整 JSONL，输出原文 hash、coverage、字节数、Work Unit/证据统计和 Digest。第七阶段应优先扩展这一个现有离线入口来运行 manifest、Golden diff 和 partition matrix，不新建一套事件平台或模型队列。

## 7. 质量指标和验收标准

### 7.1 硬性不变式

| 指标 | 验收线 |
| --- | --- |
| Golden 中 Atomic Work Unit 边界和顺序 | 全部通过；任何差异必须人工审查并更新版本，不能静默更新 snapshot |
| change/validation/call-result 客观证据 | Golden 精确匹配；无法判断的项显式 unknown/unpaired，不伪造成功 |
| 不支持的 `completed` | 0 |
| 晚到 result 误挂最新 Unit | 0 |
| 同输入重放 | 规范化 JSON 与 hash 100% 一致 |
| 一次上传 vs 分批上传 | 规范化 Atomic facts 100% 一致；Revision/Slice 运行元数据可不同 |
| JSONL 尾部恢复 | Daemon 残行不上传/不推进 ack cursor，补全续传后与完整输入等价；非法半行 Chunk 不得产生 ready Digest |
| 重复事件 | Golden 中不重复产生事实，不误删真实重复操作 |
| 噪音和敏感内容泄漏 | reasoning、系统/Skill 注入、Base64、凭据、完整 log/diff 泄漏数均为 0 |
| Revision 追溯 | 每个 ready Digest 都能回到 slice/projection/generation/epoch/version/source hash/digest hash；ready 负载不可修改 |
| Codex/Claude 兼容 | 18 类场景全部被样本覆盖，且两类 Agent 至少都覆盖 user/final/tool call/tool result/file change 主链路 |

### 7.2 观测指标

以下指标先在样本集上建立当前基线，再在每次规则变更后对比，不在无基线时伪造百分比目标：

- 按 evidence kind 的精确率、召回率和 unknown 率；
- 被错误当成用户 goal 的注入/镜像事件数；
- 结果缺失、误挂、重复证据数；
- 有 claim 但无客观证据的 Unit 数和其报告期表达强度；
- 原 JSONL/Digest/报告期投影的字节比和超目标情况；
- 未知 event type/schema version 计数，禁止静默吞掉新版本主事件。

第七阶段的验收以“全部硬性不变式通过，真实样本差异都已定性归因”为准，不以某一次 Report Agent 文案更好看作为 Digest 验收。

## 8. 建议优先修复项

以下是样本验证后的修复优先级，不表示本文已授权直接修改代码。

### P0：拆开客观事实和业务完成结论

先用 Golden 为 change、validation、agent claim、user feedback 和 evidence level 建立独立期望，再评审是否调整 `WorkUnit` 契约。立即需要消除的语义是“有修改或某次验证通过 = 整个用户目标 completed”。

### P1：用 cut-point Golden 确认并修复跨 Slice 关联

先对真实 call/result、user/final answer、中断/恢复边界建立失败测试。如确认为共性问题，再评审最小确定性 checkpoint，只保存继续解析必需的 cursor、开放 Unit 引用和 pending call 映射。本阶段不预先新建通用事件表或工作流引擎。

### P1：补全真正有报告价值的证据

通过真实样本建立工具类型覆盖矩阵，优先利用工具结构化字段和 exit status，而不是扩张自然语言关键词。重点核对 test/lint/typecheck/build、commit、deploy/runtime change、API 验证和不同文件写入方式。

### P2：统一去重和异常恢复契约

对每种事件先明确 identity（原 cursor + content hash + event type，或工具原生 ID），再分别定义“上传重试的重复”和“用户真实重复操作”。同时用端到端测试固定不完整尾部失败后的 cursor 与重试行为。

### P2：同时验证 Revision Digest 和 Report Agent 可见投影

每个 evidence 修复都必须回答两个问题：“Revision Digest 是否提取正确”和“`report_period_summary` 是否给 Report Agent 足够强度的事实”。如后者不足，只评审最小投影契约，不引入 LLM 中间层。

## 9. 明确不做项

本阶段不设计、不开发、不预埋：

- LLM Digest Builder；
- LLM Work Stream Consolidator；
- `semantic_view=preparing` 状态；
- 新的模型调用队列、超时/重试调度；
- Prompt 版本和模型版本缓存系统；
- Work Stream 数据表；
- 用户可编辑的语义归并结果；
- 为未来周报复用预先建设的复杂中间层；
- 基于大量自然语言关键词/正则的伪语义分类器；
- 与 Digest 样本、解析、证据和增量一致性无直接关系的通用事件平台或工作流引擎；
- 通过 Digest 预先删除“继续/还是不对”或覆盖旧方案来替 Report Agent 做业务语义判断。

## 10. 后续是否需要 LLM 语义归并的判断条件

默认结论是不增加独立 LLM 归并层。只有在本阶段样本与确定性问题全部收口后，仍用同一份冻结 Digest 反复证明以下任一问题稳定存在，才重新评估：

1. Atomic Work Unit 数量过多，Report Agent 输出在固定模型和 Skill 下仍明显重复；
2. Report Agent 无法稳定识别多轮工作主线、后续纠正和最终方案；
3. 日报、周报等多类报告确实需要复用同一份结构化 Work Stream，而不是由各 Report Agent 各自整理；
4. 归并结果需要独立展示、审核、编辑或审计；
5. 可量化地证明独立归并能降低总 Token 成本或提高报告稳定性，且收益大于新增延迟、重试和故障成本。

重新评估前必须先对照“只调整 Report Agent/Skill”的基线。即使未来最终引入 LLM 归并，它也只能读取已压缩的 Atomic Work Units/客观事实，不能重新读取完整 Session JSONL，不能修改底层证据和来源引用。
