# Session Digest v2 增量与一致性：当前实现证据清单

> 核查日期：2026-07-21
> 核查基线：远程测试仓库 `/home/intellif/dev/project_manager`，`main@d0f6193`
> 核查范围：仅 Session Digest v2 的增量 cursor、跨上传状态、幂等、Revision 追溯和 JSONL 尾部恢复
> 状态说明：`已实现` 表示代码路径和现有测试能够支持该判断；`部分实现` 表示局部保证存在但不覆盖完整场景；`未实现` 表示当前数据结构或控制流明确没有该能力；`未验证` 表示未找到足够的自动化或真实样本证据

## 1. 结论摘要

| 检查项 | 状态 | 当前真实行为 |
|---|---|---|
| Digest 是否按 cursor 增量处理 | 部分实现 | 上传链路按新增的不可变 Slice `[start_cursor,end_cursor)` 处理，不会为新 Slice 重读整个 Session；但每个 Slice 内都新建 Extractor 并从 Slice 起点完整重放，不存在可恢复的 Digest event cursor/checkpoint。 |
| 是否保存开放 Work Unit | 未实现 | `currentUnit`、Work Unit builder、去重集合都只存在于单次 `Extractor` 内存；`Result()` 会把当前单元完成化，没有开放单元持久化结构。 |
| `call_id -> work_unit` 是否跨上传批次恢复 | 未实现 | `pendingCalls` 是进程内 map。相同 Slice 内，即使后面已经出现新用户消息，晚到结果仍会回挂原 Unit；跨 Slice/跨构建时 map 丢失，孤立结果被忽略。 |
| 分批上传与一次上传最终 Digest 是否一致 | 未实现完整保证 | Slice 边界恰好落在完整 Work Unit 之间时可能得到等价事实；若边界切在 Work Unit、命令调用/结果或 Agent 最终回答之间，输出会不同。没有等价性回归测试。 |
| 同一输入重复执行是否幂等 | 部分实现 | 同一 ready Revision 重放会直接返回；Revision 与 Job 有唯一约束。未找到“相同事件重新构建为新 Revision，Digest JSON/hash 必须完全一致”的显式测试。 |
| Digest Revision 是否不可变、可追溯 | 已实现 | ready Revision 的事实字段由数据库触发器保护，只允许保持 ready 或转为 superseded；Revision 绑定 Slice、Projection Revision、Generation、content epoch、Digest/脱敏版本并保存 source/digest hash。报告 Selection 再冻结 revision id、hash 和版本。 |
| JSONL 物理尾部不完整后能否继续上传恢复 | 部分实现 | 官方 Daemon 不上传残行、不推进 ack cursor，文件补全后从原 cursor 再上传，已有专项测试；服务端不会拼接已经错误上传的半行 Chunk，Canonical uploader 则直接拒绝不完整尾部。 |
| 重复事件去重 | 部分实现 | 数据库对同一 Projection/Chunk/cursor 事件幂等写入；Extractor 对镜像用户目标、同 Unit claim/change 做局部去重。不存在跨 Slice 的通用事件去重状态。 |

最需要避免的表述是“Digest 已经持久化 cursor 并持续更新同一 Work Unit”。更准确的表述是：

> Session 上传是 cursor 递增的；Finalize 把本次新增区间冻结成不可变 Slice；Digest 为每个 Slice 独立、确定性地重放该区间。Extractor 状态不会跨 Slice 延续。

## 2. 实现链路

### 2.1 上传 cursor 和 Slice 的形成

1. `ChunkAcceptor.Accept` 用服务端 `expected_cursor` 和前缀 checkpoint 校验 append 顺序，接受后创建 `index_content_chunk` 任务。证据：`api/internal/sessionsync/acceptor.go:79-137`，`api/internal/sessionsync/protocol.go:198-220`。
2. `ContentProjectionProcessor.processChunk` 只接受 `indexedCursor == chunk.StartCursor` 的下一段数据，解析成功后把 `content_indexed_cursor` 推到 `chunk.EndCursor`；同一 Chunk 重放时，若已覆盖则直接标记 indexed 并返回。证据：`api/internal/sessionsync/content_projection_processor.go:58-105, 129-190`。
3. 每次 Finalize 调用 `createContentSlice`：从前一个 Slice 的 `end_cursor` 起，到当前 `expected_cursor` 止，新建不可变区间。重复 Finalize 且 cursor 未增长时返回最后一个 Slice，不新建。证据：`api/internal/sessionsync/sync_service.go:517-529, 604-612, 795-832`；现有集成测试验证连续两次 Finalize 形成 `[0,N)`、`[N,M)`，重复 Finalize 不再建 Slice：`api/internal/sessionsync/sync_service_integration_test.go:139-173`。
4. `session_content_slices` 的约束是 `start_cursor >= 0`、`end_cursor > start_cursor` 以及 `(generation_id,start_cursor,end_cursor)` 唯一。证据：`api/db/migrations/017_session_upload_report_source_and_token_analytics.sql:1237-1248`。

判断：上传与内容投影层的 cursor 推进是增量且有连续性门禁；这是 Digest 的上游保证，不等于 Digest 自身持久化了 Extractor cursor。

### 2.2 Slice Digest Revision 创建

1. `sessiondigestv2.Reconciler.RunOnce` 只挑选 active Generation、active Projection、已经完整 indexed 到 `sl.end_cursor` 的 Slice。证据：`api/internal/sessiondigestv2/reconciler.go:50-80`。
2. Revision 唯一键为 `session_content_slice_id + content_projection_revision_id + content_epoch + digest_version + redaction_version`；`ON CONFLICT DO NOTHING`。随后每个 Revision 只入一个 `build_content_slice_digest_v2` Job。证据：`api/internal/sessiondigestv2/reconciler.go:110-145`；唯一 Job 索引：`api/db/migrations/020_report_digest_v2.sql:23-26`。
3. 因为新增上传会形成新 Slice，Reconciler 为新增区间创建新 Revision，而不是修改旧 ready Digest。

### 2.3 Processor 对单个 Slice 的读取方式

`Processor.Process` 每次处理未 ready 的 Revision 都执行：

```text
NewExtractor()
  -> ContentReader.Stream(RevisionID, Slice.StartCursor, Slice.EndCursor)
  -> 对该 Slice 内每个事件 projectSafeEvent + Extractor.Consume
  -> Extractor.Result
  -> commitReady
```

证据：`api/internal/sessiondigestv2/processor.go:42-112`。其中 `StartCursor` 和 `EndCursor` 来自 Revision 绑定的 `session_content_slices`：`loadTarget` 位于 `processor.go:115-145`。

`ContentReader.Stream` 对请求区间使用 `[start,end)` 语义，并校验 Chunk 连续覆盖、事件不能跨请求边界、事件必须与索引匹配；它从不可变对象恢复原事件，而不是把数据库中的摘要当原文。证据：`api/internal/contentreader/reader.go:39-45, 82-155, 186-214, 298-325, 328-361`。

因此：

- 新 Slice 不重读旧 Slice，具备 Slice 级增量性；
- 当前 Slice 构建失败后重试，会从 `Slice.StartCursor` 重新读取本 Slice；
- `session_slice_digest_revisions` 没有 `processed_cursor`、Extractor checkpoint 或开放 Work Unit 状态字段；
- 不能把该实现描述为“事件级增量 Digest Builder”。

## 3. 开放 Work Unit 与跨批次状态

### 3.1 开放 Work Unit：未实现持久化

`Extractor` 的状态包括：

- `units []workUnitBuilder`；
- `currentUnit int`；
- `pendingCalls map[string]pendingCall`；
- `lastGoalKey/lastGoalCursor/lastGoalTime`；
- 每个 Unit 内的 `seenClaims`、`seenChanges`、`validationByName`。

这些字段全部是内存结构，见 `api/internal/sessiondigestv2/extractor.go:15-51`。`Extractor.Result()` 会调用 `finishPendingCalls()`，再 `finalizeUnit()` 所有单元，见 `extractor.go:132-158`。数据库 Revision 只保存最终 `digest_json`、计数、hash 和状态，不保存 builder/checkpoint，见 `api/db/migrations/018_report_digest_and_session_upload_hardening.sql:1-52`。

直接后果：Slice 末尾即使仍处于一个业务轮次中，该 Work Unit 也会在本次 Digest 中被结算；下一个 Slice 无法继续修改同一个 Work Unit。

### 3.2 `call_id` 关联：单 Slice 已实现，跨 Slice 未实现

单 Slice 内：

- 命令调用经 `addCommandCall` 保存 `call_id -> {UnitIndex, command, family, kind}`，见 `extractor.go:421-434`；
- 结果经 `completeCommand` 按 `call_id` 取回原 `UnitIndex`，而不是使用当前最新 Unit，见 `extractor.go:436-463`；
- 所以只要调用和结果在同一个 Extractor 生命周期内，结果即使晚于下一条用户消息，也会挂回命令发起时的 Work Unit。

跨 Slice/跨上传批次：

- 新 Revision 会调用新的 `NewExtractor()`；
- `pendingCalls` 无数据库持久化和恢复入口；
- 只有结果、没有本次内存中的调用时，`completeCommand` 在 `!exists` 分支直接返回 false，不创建证据也不挂到最新 Unit；
- 前一个 Slice 的 `finishPendingCalls()` 会把未完成的 validation 记成 `unknown/命令结果缺失`，并清空 map，见 `extractor.go:489-518`。

因此“晚到结果会误挂最新 Work Unit”在当前代码下不是主要风险：同 Slice 会回挂原 Unit；跨 Slice 会被丢弃。真实风险是跨 Slice 的结果无法修正前一 Slice 中的 unknown validation。

### 3.3 分批上传与一次上传不保证等价

可复现的最小 Golden Case：

```text
事件 1：用户要求修复问题
事件 2：function_call(call_id=test-1, go test ./...)
--- 上传/Finalize 边界 ---
事件 3：function_call_output(call_id=test-1, exit code 0)
事件 4：Agent 最终回答
```

- 一次上传：一个 Extractor 能把 passed validation 和最终回答放进同一 Work Unit。
- 分两次上传：Slice 1 先生成 unknown validation；Slice 2 不认识 `test-1`，命令结果被忽略，且没有前置用户目标时 Agent 最终回答也不会创建 Work Unit（`addAgentClaim` 在 `currentUnit < 0` 时返回 false，`extractor.go:321-343`）。

现有 `MergeReportPeriodSummarySources` 只按日期/时间排序并以 `sourceRef + workUnitRef` 去重，负责完整保留跨 Slice outcome，不会恢复开放 Work Unit 或 `call_id` 关系。证据：`api/internal/sessiondigestv2/consolidate.go:31-137`；测试 `TestMergeReportPeriodSummariesPreservesEveryCrossSliceOutcome` 只证明跨 Slice 结果不丢，见 `api/internal/sessiondigestv2/daily_test.go:255-345`。

未找到以下测试：

- 同一 JSONL 一次 Finalize 与多次 Finalize 后，合并后的 Work Unit/证据完全等价；
- `function_call` 和 `function_call_output` 跨 Slice；
- 用户消息、修改、最终回答跨 Slice；
- 前一个 Slice 的开放 Unit 被下一 Slice 恢复。

结论状态：`分批上传 vs 一次上传的一般一致性 = 未实现`；`跨 Slice outcome 列表完整保留 = 已实现并有单测`。两者不能混为一个保证。

## 4. 幂等与重复事件

### 4.1 已实现的幂等边界

- Chunk：相同已接收范围和 hash 返回 duplicate；`DecideChunk` 见 `api/internal/sessionsync/protocol.go:198-220`。
- 内容事件：数据库插入以 `(projection_revision, chunk_id, source_start_cursor, source_end_cursor)` 冲突忽略，见 `api/internal/sessionsync/content_projection_processor.go:152-166`。
- Digest Revision：Reconciler 的复合唯一键和 `ON CONFLICT DO NOTHING` 防止重复 Revision，见 `api/internal/sessiondigestv2/reconciler.go:113-127`。
- Digest Job：每个目标 Revision 唯一，见 `api/db/migrations/020_report_digest_v2.sql:23-26`。
- ready Revision 重放：`loadTarget` 标记 `Ready`，`Process` 直接返回 nil，见 `api/internal/sessiondigestv2/processor.go:47-59, 147-150`；集成测试 `processor_integration_test.go:258-267` 验证该行为。

### 4.2 仅局部实现的 Extractor 去重

- 镜像用户目标：同 canonical key 且 cursor 距离不超过 64 KiB，或时间不超过 3 秒时去重，见 `extractor.go:183-186, 253-268`。
- 同 Work Unit 内 Agent claim 按 canonical text 去重，见 `extractor.go:321-343`。
- 同 Work Unit 内文件修改按 `operation + lowercase(path)` 去重，见 `extractor.go:394-418`。
- stable ref 由 Digest 版本、事件 cursor、事件类型、content hash 和 suffix 计算，见 `extractor.go:845-870`。

局限：这些去重集合也不跨 Slice；同一逻辑事件如果以不同 cursor 再次写入，不存在通用 event id 去重。报告期合并又把 `sourceRef` 加入去重键，因此不同 Session 中相同工作不会被 Digest 自动语义去重，见 `consolidate.go:106-120`。

### 4.3 尚未验证的确定性

当前代码使用稳定的输入顺序、stable ref 和 `json.Marshal`，具备确定性实现基础；Processor 还保存 `source_sha256` 与 `digest_sha256`。但现有测试验证的是 ready Revision 重放“不再构建且不报错”，不是两次独立构建生成完全相同的 `digest_json/digest_sha256`。

建议 Golden Case 直接断言：同一事件集分别运行两个全新 Extractor，两份 canonical JSON 与 hash 字节级一致；同一 JSONL 经一次/多次上传后，应另设“允许的 Slice 表示差异”和“最终客观事实必须一致”两级断言。

## 5. Digest Revision 不可变与追溯

### 5.1 已实现

`session_slice_digest_revisions` 保存：

- `session_content_slice_id`；
- `content_projection_revision_id`；
- `generation_id`；
- `content_epoch`；
- `digest_version` 与 `redaction_version`；
- source/included/omitted event count；
- source/digest bytes；
- `source_sha256` 与 `digest_sha256`；
- created/build/ready/superseded 时间和错误码。

证据：`api/db/migrations/018_report_digest_and_session_upload_hardening.sql:1-52`；Go 映射：`api/internal/sessiondigestv2/model.go:212-242`。

`protect_ready_session_slice_digest_revision` 数据库触发器禁止修改 ready Revision 的来源绑定、版本、JSON、计数、hash 和 ready 时间；ready 只允许继续为 ready 或变成 superseded。证据：`018_report_digest_and_session_upload_hardening.sql:54-86`。

边界：Revision 对 Slice、Projection Revision 和 Generation 的外键均为 `ON DELETE CASCADE`（`018...sql:3-5`），所以这里的“不可变、可追溯”是记录存续期间的内容不可变，不等于独立于源数据生命周期的永久审计归档。

`commitReady` 在事务中再次确认 active Generation/Projection、content epoch 和 indexed cursor，再仅把 pending/building Revision 改为 ready；并发情况下如果已经 ready 则视为成功。证据：`api/internal/sessiondigestv2/processor.go:204-274`。

报告冻结时：

- Selection Item 保存 `digest_revision_id`、`digest_sha256_snapshot`、`digest_version_snapshot`；
- Selection 保存冻结的 Digest payload、payload hash、Digest/脱敏版本和预算参数；
- 读取时再次校验 Revision 状态、hash、版本和冻结 payload hash。

证据：`api/db/migrations/018_report_digest_and_session_upload_hardening.sql:120-145, 179-200`；`api/internal/reportsource/digest_v2.go:61-113, 158-228, 289-390`。

### 5.2 测试与剩余缺口

- `TestDigestV2ReconcilerAndProcessorIntegration` 验证 source/event 计数、Digest hash 和 ready Revision 重放幂等，见 `api/internal/sessiondigestv2/processor_integration_test.go:209-310`。
- 内容清理集成测试验证 ready Digest 可被转为 superseded，见 `api/internal/usage/metering_processor.go:546-566` 与 `metering_processor_integration_test.go:130-163`。
- `api/db/session_sync_migration_test.go:194-211` 先把 Revision 置为 ready，再尝试修改 `digest_json` 并断言约束违规，已经覆盖数据库触发器的核心不可变门禁。该测试需要隔离 PostgreSQL；本轮未配置 `AIDA_TEST_DATABASE_URL`，所以只核对了测试源码，未执行数据库用例。

## 6. JSONL 尾部截断与字段截断

这三个场景必须分开：

### 6.1 官方 Daemon 路径：保留本地残行，补全后续传（已实现）

`streamSessionJSONLChunks` 只 emit 读到换行的完整记录。EOF 时若存在残行，返回 `pendingTail=true`，既不把残行放入 Chunk，也不推进 cursor。证据：`daemon/session_chunking.go:70-151`。

`uploadSessionGroupIncremental` 从服务端确认的 `prepared.ExpectedCursor` seek，逐个上传完整 Chunk，并只在服务端 ack 后更新 `LastAckedCursor`；本次存在 pending tail 时，只 finalize 已上传的完整前缀。证据：`daemon/session_sync_client.go:180-250`。

现有专项测试证明：

- 第一次扫描只上传完整第一行，残缺第二行不推进 cursor；文件补全后第二次从原 cursor 上传完整第二行：`daemon/session_chunking_test.go:108-135`；
- 真实增量客户端第一次 finalize 完整前缀，文件追加尾部余量后第二次上传并 finalize 完整组合行：`daemon/session_sync_client_test.go:368-422`。

因此对官方 Codex/Claude Session 上传路径，准确结论是：`已实现本地残行等待补全后的续传`。这不是 Digest Builder 的能力，而是其上游 Daemon 切块契约。

### 6.2 服务端收到半行 Chunk：拒绝投影，不能与下一 Chunk 拼接

`readCompleteJSONLLine` 只有读到换行才返回一行；EOF 时已有残留字节则返回 `ErrIncompleteJSONLLine`。证据：`api/internal/sessionsync/content_parser.go:60-115`；单测：`content_parser_test.go:158-165`。

`ContentProjectionProcessor.processChunk` 对每个 Chunk 对象单独调用 `ParseContentChunk`，parse error 直接返回，不保存残行。证据：`api/internal/sessionsync/content_projection_processor.go:82-105`。`ChunkAcceptor.Accept` 本身只校验 cursor、size、line metadata、hash 和 checkpoint，并不读取内容确认末尾换行，见 `acceptor.go:79-137`。

如果绕过官方 Daemon，第一批仍以半行 Chunk 发到服务端：

- Chunk 可以先被接收；
- Projection Job 会失败且 indexed cursor 不前进；
- 第二批从下一个 cursor 上传剩余半行，不会与第一批残行拼接；
- 当前没有跨 Chunk residual buffer 或恢复 checkpoint。

该服务端补救能力状态：`未实现`。现有协议的实际要求是客户端只上传完整 JSONL 行；错误提示也要求“rebuild the chunk from complete JSONL lines”，见 `acceptor.go:165-171`、`protocol.go:198-205`。

Canonical uploader 不等待残行补全，而是在发现不完整尾部时直接报 `canonical source has an incomplete JSONL tail`，见 `daemon/internal/canonicalupload/uploader.go:311-345`。

### 6.3 有换行但外层 JSON 非法：按 malformed 跳过

`projectContentLine` 对无效 UTF-8、JSON 解码失败、缺少 type 或无有效时间的完整行返回 false；Scanner 增加 `MalformedEventCount` 后继续推进 cursor。证据：`api/internal/sessionsync/content_parser.go:82-90, 125-162`。后续上传不会补写或重解析这个已越过的坏行。

### 6.4 外层事件有效、字段内容被限长或内嵌序列化文本截断：已有局部处理

- `projectSafeEvent` 对消息/命令参数最多保留 8192 字符，对命令输出保留 head 1024 + tail 4096，对 patch 文件最多保留 200 个；见 `api/internal/sessiondigestv2/safe_projection.go:15-22, 43-103`。
- 单测覆盖字符和集合上限：`safe_projection_test.go:153-185`。
- 对“有效外层事件中的 multimodal 字符串被截断，但前部含用户 text”存在专项恢复测试：`TestExtractorRecoversTextFromTruncatedMultimodalPayload`，见 `extractor_test.go:131-149`。

这类字段级兼容不能证明物理 JSONL 尾部残行可以跨上传恢复。

## 8. 第七阶段应优先建立的 Golden Cases

以下不是新架构，而是直接验证当前实现边界的最小回归顺序：

1. `GC-INCR-01`：同一完整 JSONL，一次 Finalize 与在完整 Work Unit 边界多次 Finalize，比较最终客观事实集合。
2. `GC-INCR-02`：Slice 边界位于 `function_call` 与 `function_call_output` 之间；固定复现 unknown 无法被 passed 修正。
3. `GC-INCR-03`：Slice 边界位于用户消息、文件修改和 Agent final answer 之间；确认哪些事件成为 unattributed、哪些被直接丢弃。
4. `GC-LATE-01`：同一 Slice 内先发起命令、再出现下一条用户消息、最后收到旧命令结果；断言结果回挂旧 Unit，不得挂最新 Unit。
5. `GC-IDEMP-01`：相同事件集用两个全新 Extractor 构建，断言 canonical Digest JSON/hash 相同。
6. `GC-IDEMP-02`：同一 Revision Job 重放，不得修改 ready Revision 的 JSON、hash 和 ready time。
7. `GC-REV-01`：直接更新 ready Revision 的 `digest_json/source_sha256/digest_sha256`，断言数据库触发器拒绝；转 superseded 应成功且事实字段不变。
8. `GC-TAIL-01`：官方 Daemon 第一次看见半行、文件随后补全；锁定“不上传残行、不推进 cursor、下次完整上传”的已有行为。
9. `GC-TAIL-02`：完整换行但非法 JSON；断言 malformed count 增加、cursor 前进、事件不进入 Digest。
10. `GC-DUP-01`：同事件同 cursor 重放、镜像目标、不同 cursor 重复事件分别验证数据库与 Extractor 的去重边界。

## 9. 建议的最小修复优先级

在真实样本跑出结果前，不应先建设新的语义层。就本次证据，优先级是：

1. 先补 `GC-INCR-02/03`，确认跨 Slice 边界造成的实际事实损失频率和影响；
2. 补同 Slice 晚到结果回挂原 Unit 的单测，锁住当前正确行为；
3. 明确上传协议“Chunk 必须由完整 JSONL 行组成”，保留官方 Daemon 的残行等待补全测试；是否需要服务端拼接非法半行 Chunk，必须由真实失败样本决定；
4. 补独立构建确定性与 ready Revision 触发器测试；
5. 再根据样本决定是调整 Slice 边界、补最小跨 Slice pending-call/open-unit 状态，还是仅在 Report Agent 输入中保留边界事实。当前证据不足以直接选择实现方案。
