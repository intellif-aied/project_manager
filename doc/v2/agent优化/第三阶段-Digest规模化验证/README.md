# 第三阶段：Digest 规模化真实 Session 验证

> 状态：四轮验证与 Digest 语义契约加固均已完成；Agent Skill 问题转入下一轮清单
> 建立日期：2026-07-17
> 环境：14.159 本机真实 Session、14.157 开发测试环境
> 评测基线：`session-digest/v2.8.0`；本阶段候选：`session-digest/v2.9.0`（本文不声明生产版本）
> 上位约束：[报告 Agent 优化总纲](../总纲.md)

## 1. 阶段目标

本阶段先回答两个相互独立的问题：

1. Digest 是否忠实、完整地保留了真实 Session 中对日报有意义的信息？
2. 在 Digest 合格的前提下，固定 Skill、Agent Prompt 和模型生成的日报是否合理？

本阶段不以单份日报好坏直接判断 Digest。任何问题都必须沿以下证据链定位：

```text
原始 Session
  -> Digest
  -> Agent 输入
  -> 最终回写日报
```

只有原始 Session 中存在、但 Digest 缺失或失真的事实，才能判定为 Digest 问题。Digest 中已完整存在、最终日报却遗漏或误写的事实，应归因到 Skill、Agent Prompt 或模型生成层。

## 2. 为什么采用双层验证

Report Skill、Agent Prompt 和模型具有语义归并与写作自由度，同一 Digest 可能生成不同日报。如果只查看最终日报并反向调整 Digest，容易把模型波动、写作风格或 Skill 约束误认为服务端数据缺失，最终重新走向 Top-K、过度裁剪或为单一样本调规则。

因此本阶段固定为两层：

| 层级 | 输入 | 输出 | 是否允许受 Skill/模型影响 |
| --- | --- | --- | --- |
| A：Digest 内在质量 | 原始 Session 与 Digest | 事实覆盖、失真、噪音和容量报告 | 不允许 |
| B：真实 Agent 日报 | 同一份冻结 Digest | 持久化日报与运行日志 | 允许，但单独归因 |

层 A 未完成前，不修改 Skill 或 Agent Prompt。层 B 暴露的问题先记录，不得直接推动 Digest 改动。

## 3. 样本规模与选择原则

建议首轮固定 10 个 14.159 本机真实 Session。样本必须在查看日报结果前确定，避免挑选有利样本。

| 编号 | 样本类型 | 数量 | 主要验证点 |
| --- | --- | ---: | --- |
| S01-S02 | 超长、多轮、多主题 Session | 2 | 容量、跨阶段结果、遗漏风险 |
| S03 | 中等规模代码实现 | 1 | 需求、实现、验证和交付状态 |
| S04 | 方案/PRD/架构讨论 | 1 | 决策、边界、被否决方案和最终结论 |
| S05 | 故障定位与失败修复 | 1 | 失败、根因、重试、最终状态 |
| S06 | 未完成或存在 blocker | 1 | partial、unresolved、后续计划 |
| S07 | Codex fork/sub-agent 或多 Agent | 1 | 重复历史、父子会话和完成度 |
| S08 | 工具输出、日志、图片或大结果较多 | 1 | 确定性清噪与有效结论保留 |
| S09 | 短普通 Session 对照组 | 1 | 防止只针对大 Session 优化 |
| S10 | 跨午夜或时区边界 Session | 1 | Asia/Shanghai 日期归属 |

同一个 Session 可以具备多个特征，但不能用一个样本替代全部类别。若本机没有某类样本，应在样本清单中明确缺口，不人工伪造生产结论。

每个样本记录：

- Session ID、客户端类型和工作目录；
- 原始文件路径与 SHA-256；
- 事件数量、原始字节数、活动起止时间；
- 是否包含 fork/sub-agent、工具大输出、图片、压缩历史；
- 选定报告日期及选择理由；
- 上传后的 generation ID、slice key、selection ID 和 Digest SHA-256。

## 4. 测试数据流程

必须走用户真实使用路径：

```text
14.159 本机真实 Session
  -> 独立分支源码构建的临时 Aida 测试二进制正常扫描和选择
  -> prepare/chunk/finalize 完整上传到 14.157
  -> readiness 到 ready
  -> 用户在 14.157 页面手动选择 Session，或明确授权后调用同一业务 API 模拟选择
  -> 创建不可变 report source selection
  -> MCP get_sessions 读取 Digest
  -> 默认 Report Agent 生成
  -> write_report_result 持久化日报
```

禁止：

- 调用 14.159 本机已安装的 Aida 客户端进行测试上传；
- 读取或修改用户的 `~/.aida.yaml`、Session 索引及上传状态；
- 直接写数据库或 MinIO；
- 未经用户明确授权，通过测试脚本替用户选择报告来源；
- 只上传人为截取的增量 chunk 冒充完整 Session；
- 修改 Session 原文以迎合当前规则；
- 在同一轮中同时修改 Digest、Skill 和 Agent Prompt；
- 用 Agent `completed` 替代日报真实回写成功。

为避免重复上传造成样本混淆，执行前可清理测试账号中本轮同 Session 的历史测试副本，但必须只删除明确属于本轮测试账号和样本清单的记录，并记录清理范围。

测试上传必须使用从本阶段独立 worktree 当前提交构建的专用二进制，放在临时路径，并同时使用隔离 `HOME`、显式测试服 URL、测试账号 Token 和关闭自动更新。专用二进制的版本、SHA-256、源码提交和构建时间必须进入测试记录；即使版本号与本机安装版相同，也不得互换使用。

## 5. 层 A：Digest 内在质量验证

### 5.1 建立原始事实清单

逐个阅读原始 Session，建立与具体文本或事件引用关联的事实清单：

- 用户真实目标；
- 重要讨论与明确决策；
- 被否决或被替代的方案；
- 实际交付、代码或文档结果；
- 测试、失败、根因和恢复结果；
- blocker、unresolved 和后续承诺；
- `OK`、`Agree`、验收通过等完成度确认；
- 报告日期内与报告日期外的事实；
- 最终有效状态与被后续结果覆盖的历史状态。

原始事实清单是层 A 的基准，不使用 Report Skill 的格式要求，也不预先限制日报应有多少条。

### 5.2 对照 Digest

对每条原始事实标记：

| 结果 | 含义 |
| --- | --- |
| 完整保留 | 事实、主体、状态和时间均正确 |
| 部分保留 | 核心事实存在，但限定条件或最终状态缺失 |
| 失真 | Digest 改变了完成状态、因果、主体或日期 |
| 遗漏 | 原始事实存在，Digest 无对应内容 |
| 合理去噪 | 被删除内容属于可客观判定的技术噪声 |

`OK`、`Agree` 等确认信息不得仅因文字短而判为噪声；应检查它是否能与前一实质工作单元共同证明完成度。空 `output_text`、二进制、图片编码、完整工具大输出和精确重复事件可以判为合理去噪。

### 5.3 指标

| 指标 | 首轮目标 |
| --- | --- |
| 关键事实召回率 | 100% |
| 一般事实召回率 | 不低于 95% |
| 状态、主体、日期准确率 | 100% |
| Digest 虚构事实 | 0 |
| 所选 Session coverage | 100% |
| `source_count = represented_count` | 每个报告日成立 |
| 技术噪声压缩 | 记录比例，不设越高越好的目标 |
| Digest 字节数与模型估算 Token | 完整记录 |

压缩率只作为成本指标，不能凌驾于事实召回率。允许多保留一些上下文，不允许为了漂亮的压缩率删除关键事实。

### 5.4 人工总结

每个 Digest 由当前评测人员独立写一份“不使用 Report Skill 格式”的事实摘要，用来回答：

- 从 Digest 能否理解用户当天真正做了什么？
- 是否能区分讨论、决定、实现、验证和发布？
- 是否能看到失败、阻塞和最终状态？
- 是否需要返回原始 Session 才能恢复关键事实？

该摘要用于评估 Digest 可读性，不直接作为最终日报模板。

## 6. 层 B：真实 Agent 日报验证

### 6.1 固定变量

同一轮必须固定并记录：

- Digest 版本和 Digest SHA-256；
- Report Skill owner/slug/version/SHA-256；
- 默认 Agent ID、Agent Version 和 Prompt 哈希；
- 模型 ID；
- report type、period、selection ID；
- MCP 版本和生产/测试环境地址边界。

Digest 评测期间不修改 Skill 或 Agent Prompt。若发现 Skill 问题，记录为独立缺陷，待本轮 Digest 基线完成后再处理。

### 6.2 日报校对维度

- 是否覆盖 Digest 中所有重要成果；
- 是否把讨论或用户目标误写为已完成；
- 是否正确合并同一主线的阶段性结果；
- 是否保留失败、blocker 和明确待跟进；
- 是否出现 Digest 中不存在的事实或计划；
- 是否泄漏不必要的内部路径、主机、凭据、ID 和纯技术证据；
- 是否可供用户直接编辑和发送；
- 是否真正调用 `write_report_result` 并保存成功。

### 6.3 模型波动对照

10 个样本各执行一次完整日报。再从超长、方案讨论、故障修复三类中各选一个样本，在完全相同的 selection snapshot、Skill、Prompt 和模型下重复运行一次。

如果同一 Digest 两次日报差异明显，而 Digest 事实清单稳定，应判为模型生成波动，不修改 Digest。需要比较模型时，必须新建独立对照轮次，不能与 Digest 规则改动混在同一轮。

## 7. 问题归因矩阵

| 原始 Session | Digest | 日报 | 归因 |
| --- | --- | --- | --- |
| 有 | 无 | 无 | Digest 遗漏 |
| 有 | 有且准确 | 无 | Skill/模型归并遗漏 |
| 有 | 有但失真 | 任意 | Digest 提取或状态推断错误 |
| 无 | 无 | 有 | Agent 幻觉或 Skill 诱导 |
| 有 | 有 | 有但表达内部化 | Skill/模型写作问题 |
| 有确认信号 | 确认信号存在但失去前文 | “已完成：OK” | Digest 关联表达不足，不能简单删除确认信号 |

问题归因必须附原始引用、Digest 字段和最终日报原文，禁止只凭主观印象分类。

## 8. 三轮执行方式

### 第一轮：现状基线

- 不修改代码；
- 完成 10 个样本上传、层 A 和层 B 评测；
- 输出跨样本问题分布和归因；
- 决定是否存在值得修改 Digest 的共性问题。

### 第二轮：最小规则修复

仅在以下任一条件满足时修改 Digest：

- 一个关键事实发生遗漏或状态失真；
- 同一种一般问题在至少两个不同类型 Session 重复出现；
- coverage、日期或选择快照契约不成立。

修复必须最小化，不引入 Top-K、固定条数、LLM 预摘要或大范围语义删除。全部 10 个样本重新离线回放，受影响样本重新走真实 Agent 流程。

### 第三轮：回归与结论

- 核对修复没有降低其他样本召回率；
- 复测超长、短对照、失败修复和时区样本；
- 固化 Digest 结论与剩余 Skill/模型问题；
- 只有达到验收标准后，才讨论新版本和发布。

## 9. 容量专项

本轮必须同时记录两个不同概念：

- 1 MiB：用户成本与模型上下文风险提醒阈值；
- 服务端 Digest hard limit：系统允许生成和传递的保护上限。

当前真实样本曾返回 64 MiB `target_bytes/hard_limit_bytes`。本轮需确认这是有意的服务端硬上限，还是与产品约定混淆。不得把 1 MiB 提醒阈值直接实现成语义裁剪或强制阻断。

## 10. 验收标准

第三阶段完成必须同时满足：

1. 10 个样本均完成正常上传、ready、人工选择或授权接口模拟、Digest 读取和日报回写；
2. 层 A 关键事实召回率、状态、主体和日期准确率达到目标；
3. 所有遗漏和失真均有原始证据与归因；
4. 层 B 的问题不被错误归因给 Digest；
5. 至少三个样本完成同条件重复运行或重点复核；
6. 未修改上传协议、Token 统计、权限、原始 Session 和用户自定义 Skill；
7. 形成可人工阅读的 10 样本汇总和是否需要修改 Digest 的明确结论；
8. 未经用户确认，不发布生产。

## 12. 当前结论

- `session-digest/v2.9.0` 的 Layer A 内在质量和 Layer B 真实链路均完成 10 样本验证；
- 第四轮 10/10 完整 Digest、10/10 报告期 Digest 与改动前整体等价，coverage 全部完整；
- 超过 1 MiB 的合成回归证明提醒阈值不会触发语义裁剪或结果丢失；
- 已移除未使用的语义排序、版本覆盖和 Report-facing 改写路径，coverage 不完整时固定 fail-open 保留；
- 10/10 Agent run succeeded，10/10 真实调用 `write_report_result`；
- 未发现需要为本轮样本继续引入 Top-K 或更激进语义裁剪的证据；
- 剩余共性问题主要是默认 Skill/模型对内部证据、最终状态、数字统计和环境术语的写作处理，不应直接归因给 Digest；
- 本阶段未执行生产发布。
