## 4. 最小目标架构

```text
/api/task/list?scope=all
  -> ai_run.id <-> external_session_id <-> Langfuse trace
  -> Session + Thread Events + Aida Context/写回结果
  -> Context / Agent-Skill / MCP / Model / Platform-Writeback 归因
  -> 同输入同模型对照
  -> 已确认的最小代码改动
```

报告输入的固定模块链路：

    原始 Session
      -> 确定性 Digest：结果型 Work Unit 事实、证据引用与非结果覆盖计数
      -> Report Context Builder
      -> 确定性 Report Projection：去重、自描述列式结构、引用与覆盖校验
      -> 冻结单份紧凑 Report Context
      -> get_report_context(run_id) 一次读取
      -> 最终 Report Agent：语义归并和报告写作

Report Projection 是 Report Context Builder 的内部 seam。调用方只获得一份不可变 Context，不感知去重规则。该模块为纯本地计算，不访问模型、不写新表、不投递任务。

该 seam 只承载确定性结构收敛，不承载业务重要性判断。

原始响应只保存在权限为当前用户可读的临时目录。仓库只记录脱敏后的样本编号、统计值、事件摘要和结论。

## 6. 数据流与失败边界

固定取证顺序：

1. 从 Aida 目标 `ai_run` 取得 `external_session_id` 和任务所属生产用户 ID；
2. 为该用户生成仅存在于单次采集进程内的 Agent Platform Token；
3. 使用该用户 Token 读取 `/api/session/{external_session_id}`；
4. 从 Aida 查询对应 Context 元数据和写回结果；
5. 使用已验证的关联字段查询 Langfuse 模型调用；
6. 依次检查 Context、MCP、Skill/Prompt、模型、平台执行与写回；
7. 命中明确根因后停止向后猜测。

缺少三方关联时记录为观测缺口；缺少精确 usage 时 Token 标记未知；事件不完整时使用 Archive 或只读 diagnosis 补证，仍不完整则不形成通用优化。

## 7. 安全、容量与兼容性

- 每次分页最多 100 条，按固定时间范围采样，不做无界全库导出；
- 生产只调用 GET，不调用任何运维写接口；
- Bearer Token 不写入脚本、文档或 Git；
- Token 通过进程内管道传给 HTTP 请求，命令输出和错误信息不得回显 Token；
- Aida CLI Token 的 `exp` 过期不影响接口访问，这是固定产品规则；取证过程仍不得输出或持久化 Token；
- 不改变上传、Digest、Selection、Token analytics 和报告写回协议；
- `report_context_representation` 在 Run 创建时写入 `execution_input_json`：值为 `work_evidence` 才启用 Projection；历史 Run 没有该字段时继续生成旧 `sessions + sources` 结构；
- 生产 `aida-report@1.0.16` 明确依赖旧路径。先发布但不启用经批准的新 Skill 资源，再在同一次后端部署中切换镜像和 `MANAGED_AGENT_REPORT_SKILL_VERSION`；不得提前切换生产默认 Skill；历史在途 Run 因没有新表示标记而不受影响；
- Subagent Thread 独立统计，并通过父调用关系归属根 Session。
- Digest Worker 的 Job 类型、Worker 数量、Claim SQL、重试和 urgency 均不因 Projection 改变；
- Projection 只消耗 Report Context Builder 当前 Worker 的本地 CPU 时间，必须通过最大样本基准验证；
- 任意代码路径出现 Digest/Projection 模型 Client、模型配置或新异步 Job，均视为偏离方案并停止开发；
