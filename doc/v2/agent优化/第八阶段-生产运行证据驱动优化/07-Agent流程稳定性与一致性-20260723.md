# Agent 流程稳定性与一致性（2026-07-23）

> 状态：首轮生产全量样本分析完成
> 范围：最近 14 天内真实调用过 `get_report_context` 的 68 个 Report Agent Session
> 排除：只走 `get_sessions/get_tasks/...` 的旧流程不进入本统计

## 1. 样本证据契约

每个样本在本机 Git 仓库外的受控目录保存三份对照证据：

| 文件 | 内容 | 用途 |
| --- | --- | --- |
| `report-context.json` | MCP `get_report_context` 实际返回的完整 JSON 文本 | 确认 Agent 收到的冻结事实 |
| `session-raw.jsonl` | Agent Engine 原始 Session JSONL | 还原 Claude Code/Codex 原生模型、工具和 Token 事件 |
| `session.json` | Agent Platform 结构化 Session 和完整事件时间线 | 稳定统计工具顺序、状态和写回 |

每份文件都在本地 manifest 记录 SHA-256、字节数和样本标签。缓存文件权限为 `600`，目录权限为 `700`，授权 Token 只在内存中生成，不落盘。完整性检查结果：

- 68/68 个样本均已保存 Context、JSONL 和结构化 Session；
- 68/68 个 Context 可解析；
- 68/68 个 JSONL 逐行可解析；
- 68/68 个样本的文件 SHA-256 验证通过；
- 缓存中未扫描到 JWT 格式的授权 Token。

### 1.1 失败 Session 的原始日志缺口

62 个成功 Session 的 Agent Archive 包含引擎原生 JSONL。全部 6 个 `terminated` Session 的 Archive 状态为 `partial`，压缩包只有 `events/thread_events.jsonl`、运行元数据和 manifest，缺少 Claude Code `session/projects/*.jsonl`。

这 6 个样本的 `session-raw.jsonl` 保存平台持久化的 `thread_events.jsonl` 作为 fallback，并在单样本 manifest 明确记录：

```text
raw_engine_jsonl_available = false
raw_session_source = platform_thread_events_fallback
```

不得将这 6 份 fallback 描述为引擎原生 JSONL。这是生产失败任务的可观测性缺口。

## 2. 总体结论

当前流程必须分成两个结论：

1. **编排契约稳定且一致**：Skill、Context、写回、Run 状态之间没有重复提交、前端驱动或向用户追问的证据；
2. **业务内容正确性未与技术成功绑定**：已发生 Digest 完整存在，但 Agent 读错 JSON 路径并将报告写回为成功的 P0 事故；
3. **大 Context 执行不稳定**：68 个 Session 中 22 个进入本地文件绕行，其中 6 个失败。故不能将整个 Agent 流程定性为“已稳定可靠”。

简化表达：

```text
run_id -> Skill -> get_report_context -> write_report_result
```

这条业务顺序是一致的；但 `get_report_context` 输出过大后的模型消费过程不可靠。

## 3. 编排一致性

| 检查项 | 结果 | 结论 |
| --- | ---: | --- |
| `get_report_context` 调用次数 | 68/68 均为 1 次 | 无重复 Context 读取 |
| Skill 加载 | 67 个 Claude Code Session 显式调用 1 次 `Skill`；1 个 Codex Session 通过 `command_execution` 读取 Skill | 无 Skill 重复加载 |
| 成功 Run 写回 | 62/62 均为 1 次 `write_report_result` | 无重复写回 |
| 失败 Run 写回 | 6/6 均为 0 次 | 未在失败后写入伪成功报告 |
| Run/Session 状态 | 68/68 一致 | Session 成功对应 Run 成功，Session terminated 对应 Run 失败 |
| 相同入参工具重复调用 | 1 个 Session 的 `Read` 重复 2 次 | 不涉及 Skill、MCP 或写回，属于大文件绕行 |

68 个 Session 中：

- 67 个只使用 Context V1 报告读取路径；
- 1 个 Skill `1.0.14` 历史样本在 `get_report_context` 前额外调用了 1 次 `get_existing_report`；
- Skill `1.0.15` 和 `1.0.16` 样本中未再出现旧报告读取工具。

上述 `1.0.14` 样本保留为历史流程偏离证据，不将其扩大成当前 Skill 仍在反复取数。

## 4. 是否存在 Skill 反复询问

本次对三类信号进行了全量检查：

1. `AskUserQuestion` 或同类交互工具调用；
2. Session 最终输出中的“请提供、请确认、请选择、请回复、请补充”类追问；
3. 全部 Agent message 中的同类交互语句。

结果均为 0。

因此，当前生产样本没有“Skill 反复询问用户、等待用户回复后才继续”的证据。页面关闭或用户不在线不会因 Skill 交互导致这批 Run 停止。

## 5. Digest 内容识别一致性

### 5.1 已发生技术成功、业务内容错误

2026-07-22 的 P0 事故对应本地样本 `S0229`：

| 项目 | 事实 |
| --- | --- |
| Skill | `aida-report@1.0.15` |
| Engine / Model | Claude Code / MiniMax-M2.5 |
| Context | 1,985,584 bytes |
| 技术状态 | Session 成功、Run 成功、报告已写回 |
| 业务结果 | 错误声称详细工作内容未能展开 |

该 Context 的 Digest 完整，权威报告事实位于：

```text
sessions[].digest.report_period_summary.days[].highlights
```

但 Agent 在大 MCP 结果落盘后，检查了 `items[].digest.work_units`，没有读取上述正确路径。`period_result_focused` 下的 item `work_units=[]` 是正常投影结构，Agent 却将它误判为 Digest 内容缺失。

因此，下列状态都不能单独证明报告正确：

```text
Session completed
Run succeeded
write_report_result saved
```

### 5.2 Skill `1.0.16` 是止血，不是底层闭环

Skill `1.0.16` 明确增加了：

- 固定的 `sessions[].digest.report_period_summary.days[].highlights` 路径；
- 大结果落盘后必须解析完整 JSON，不得使用 preview 判定事实缺失；
- item 下的空 `work_units`、`daily_summaries` 和 `discussion_aggregates` 是正常投影结构；
- 禁止根据覆盖统计或空数组推断 Digest 缺失。

生产已有 4 个 `1.0.16` 样本：

| Context | Engine / Model | 路径证据 | 结果 |
| ---: | --- | --- | --- |
| 1,985,584 bytes | Claude Code / GLM-5.2 | 已使用正确 highlights 路径 | 仍在文件绕行中失败 |
| 1,985,582 bytes | Codex / gpt-5.5 | 直接 Context 到写回 | 成功，未命中内容缺失文案 |
| 273,551 bytes | Claude Code / GLM-5.2 | 已使用正确 highlights 路径 | 成功，未命中内容缺失文案 |
| 14,072 bytes | Claude Code / GLM-5.2 | 直接 Context 到写回 | 成功，未命中内容缺失文案 |

这批证据只能确认 Skill 已修正已知 JSON 路径误判，不能关闭 P0：

- `1.0.16` 只有 4 个生产样本；
- 其中唯一个 Claude Code 1.99MB 大 Context 样本仍失败；
- 当前仍由模型自行用 Bash/Read 处理临时文件；
- 尚没有将“正确读取 highlights 并产出具体事实”固化为自动化质量验收。

## 6. 执行稳定性

| 执行形态 | 数量 | 结果 |
| --- | ---: | --- |
| Context 后直接写回 | 45 | 成功 |
| Context 后使用 Read/Bash/Grep/Write 绕行 | 16 | 成功，但成本和质量不稳定 |
| Context 后使用本地文件绕行 | 6 | 失败 |
| 历史混合路径 | 1 | 成功，Skill `1.0.14` 额外读取 `get_existing_report` |

20 个 Session 的 Context Tool Result 明确出现“超过最大 Token/字符并保存到临时文件”事件。按实际后续工具序列统计，总共 22 个 Session 进入本地文件绕行。

稳定性数字：

```text
总体成功：62 / 68 = 91.2%
直接路径成功：45 / 45 = 100%
文件绕行成功：16 / 22 = 72.7%
文件绕行失败：6 / 22 = 27.3%
```

这证明当前主要不稳定点不是 Skill 追问、Context 重复读取或写回重复，而是 Claude Code 将大 MCP 结果改为临时文件后，模型自主执行 Read/Bash/Grep 的不确定过程。

## 8. 已确认问题

### P0：Digest 完整存在但 Agent 误判为内容缺失

影响：技术状态和写回均成功，但用户得到空泛的错误报告。该事故已由 Skill `1.0.16` 止血，仍缺少固定大 Context 回归和业务内容质量门禁，不得仅凭 `succeeded/saved` 关闭。

### P0：大 Context 依赖模型自行处理临时文件

影响：22 个样本进入绕行，6 个失败，已有成功状态但报告质量退化的实例。

本期优化必须在不删减 Digest 内容的前提下，消除“单次超限后任由模型自行拆文件”作为默认成功路径。

### P1：失败 Session 缺少引擎原生 JSONL

影响：6/6 个失败 Session 的 Archive 都缺少 Claude Code 原生 Session JSONL，只剩平台事件 fallback，会弱化失败根因、Token 和引擎细节复盘。

需要在 Agent Platform 讨论中单独处理 Archive 为什么在 terminated 路径没有收集引擎原生 JSONL，不与 Aida 的 Context 传递修复混成一个代码改动。

## 9. 后续对照验收基线

优化后必须使用本地冻结的同一批 `report-context.json` 做对照，不得重新读取已经变化的生产数据代替原样本。

固定验收项：

1. Skill 每个 Session 最多加载一次；
2. `get_report_context` 或其确认的替代契约只执行一次初始绑定；
3. 不调用旧报告读取工具重新扫描范围；
4. 不向用户追问 Context、Selection、期间或报告目标；
5. 成功 Run 只写回一次，失败 Run 不写入伪成功报告；
6. Run 与 Session 最终状态一致；
7. 不依赖页面、用户回复或前端重试推进；
8. 大 Context 不再触发无契约的 Read/Bash/Grep 自由绕行；
9. Context 的完整性、Context hash 和证据覆盖不弱化；
10. 对照同时记录成功率、总工具次数、耗时、Token、成本和人工质量。
