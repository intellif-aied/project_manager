# 报告内容组织与目标归并（2026-07-23）

> 状态：生产用户高频反馈已复现并定位
> 样本：本地脱敏样本 `S0232`
> 范围：仅分析报告的目标归并、成果表达和结构重复，不修改代码

## 1. 用户反馈

当前日报能够把工作内容描述出来，但容易把围绕同一目标的课程设计、文档、部署、验证、可读性改造和运行排查分成多个并列的小功能。

用户需要的不是“今天做了哪些小功能”清单，而是：

```text
今天推进了哪些主要目标
  -> 每个目标最终形成了什么成果
  -> 哪些功能、文档、部署和验证共同支撑该成果
  -> 当前状态和真实未解决项是什么
```

## 2. 样本证据

`S0232` 使用 Codex Engine + GPT-5.5，Context 约 1.99MB。它的工具序列只有：

```text
command_execution（读取 Skill）
  -> get_report_context
  -> write_report_result
```

该样本没有出现 Claude Code 的大工具结果落盘，没有 Read/Bash/Grep 绕行，也没有输入缺失。因此，该报告的组织问题不属于：

- 模型能力不足；
- Context 未传递；
- Digest 内容缺失；
- 文件绕行导致的丢读；
- Skill 向用户追问后未继续。

## 3. 报告结构的实际问题

该报告的“今日工作”包含 6 个并列主题：

1. 多 Agent 框架学习材料；
2. 教学结构和可读性；
3. 端到端使用视角；
4. 学习站点部署；
5. showboat 源码讲解文档；
6. Runtime、安装和 E2E 排查。

前五项的上位目标是同一个：建设并交付可使用的多 Agent 学习体系。课程内容、结构、术语、端到端视角、walkthrough 和静态站点都是这个交付的不同组成部分，不应自动升格为六个并列成果。

报告末尾又使用 6 条“当前状态”重述前文已表达的结果，造成结构性重复。

更合理的目标结构是：

```text
主要目标 A：多 Agent 学习体系建设与交付
  - 最终成果：课程体系、对比材料、walkthrough 和可访问学习站点
  - 内容建设：四个框架、统一导论、综合比较
  - 质量改造：术语、可读性、端到端使用视角
  - 交付和验证：showboat 校验、站点部署和健康检查

主要目标 B：运行与安装链路核对
  - agent-browser E2E 实际运行方式
  - sap-runner 运行、服务化和 Runtime 复用边界
```

这里的两个目标只是对当前样本的合理组织示例，不是要求所有日报固定生成两个主题。

## 4. Digest 结构对问题的放大

该 Context 包含：

| 指标 | 数量 |
| --- | ---: |
| highlight | 1,140 |
| 唯一 `work_unit_ref` | 1,140 |
| 唯一 goal 文本 | 313 |
| `discussion` highlight | 820 |
| `document` highlight | 218 |
| `implementation` highlight | 67 |
| `investigation` highlight | 18 |
| `deployment` highlight | 17 |
| `status=unknown` | 682 |

Digest 将对话层的大量轮次直接展开为独立 highlight。goal 中包含 `continue`、“下一个问题”和连续追问等对话行为，而不是稳定的工作目标。

这证明当前 `report_period_summary.days[].highlights` 更接近“扁平的完整证据列表”，不是已经建立父子关系的工作目标树。

但 Digest 不应代替 Agent 决定报告最终应保留哪些内容。修复不得通过删除 highlight、Top-K、固定主题数或静默截断实现。

## 5. Skill 的直接偏置

当前 Skill 同时要求：

```text
Keep distinct work objects distinct.
Cover every materially distinct project, feature, bug, document,
decision, investigation, delivery, failure, blocker, and unresolved action.
Group only true duplicates or updates of the same object.
```

这三条规则用于防止遗漏，但它们将“完整性”等同于“不跨工作对象归并”。当同一目标同时产生课程、文档、站点、部署和验证时，模型会主动将它们拆成多个主题，以避免违反 Skill。

因此，这个样本不是 GPT-5.5 不会归纳，而是 Agent 被要求优先“保留工作对象边界”，没有被要求优先“恢复上位工作目标”。

## 6. 目标产品行为

Agent 在不丢弃任何有效证据的前提下，先构建“目标成果账本”，再写报告：

```text
扁平 highlights
  -> 识别稳定上位目标或工作主线
  -> 将同一主线的功能、文档、调查、部署和验证归并
  -> 提炼该主线的最终成果和当前状态
  -> 使用最少且足够区分独立目标的主题
  -> 每个主题先写成果，再用关键动作和验证支撑
```

必须保持分开的情况：

- 目标、对象或交付价值真正独立；
- 一项工作的状态、风险或责任边界与另一项不同；
- 归并后会使读者无法判断不同事项的实际结果。

必须归并的情况：

- 功能、文档、部署和验证共同完成同一交付；
- 多个工作对象是同一用户目标的组成部分；
- 后续修改、补充和验证是同一工作主线的连续推进；
- “当前状态”只是前文成果的重复摘要。

## 7. 核心缺陷定性

| 层级 | 缺陷 | 影响 |
| --- | --- | --- |
| Digest | 将对话轮次和稳定工作目标混在同一扁平 highlight 列表 | Agent 需要从数百个 goal 和大量 discussion 中重建目标主线 |
| Skill | 只允许合并真正重复或同对象更新 | 不同文档、功能、部署和验证即使支撑同一目标，也容易被拆分 |
| 报告组织 | 没有固定“目标、成果、支撑动作、验证和状态”的内部归并顺序 | 报告更像功能清单，而不是工作成果摘要 |
| 质量验收 | 只检查写回成功和事实不虚构，不检查过度拆分和结构重复 | 模型可以在所有技术指标成功时仍产出阅读价值低的报告 |

## 8. 不做项

- 不通过 Aida 切换、降级或覆盖平台规定模型规避该问题；
- 不删减 Digest highlight；
- 不设定固定项目数、主题数或报告字数；
- 不用 Top-K 代替完整证据；
- 不把不同独立目标强行压成一个主题；
- 不在 Digest 层直接生成最终报告结论；
- 不以 `succeeded/saved` 代替内容质量验收。

## 9. 后续对照验收

`S0232` 的三件套和用户反馈报告已保存为本地固定对照样本。修改后必须使用同一 Context 验收：

1. 报告仍覆盖现有报告中的所有有效事实；
2. 围绕同一学习体系交付的课程、文档、walkthrough、站点、部署和验证不再自动拆成并列主题；
3. 每个主题第一段先表达成果和当前状态，再使用关键动作支撑；
4. 不再使用独立“当前状态”区块重复前文；
5. 独立的运行与安装排查仍能保持边界，不被误合并；
6. 修改前后固定使用 Agent 平台规定的同一模型，确认改进来自契约而不是模型变化；
7. 人工验收同时评估事实完整、目标归并、成果导向、重复度和可读性。
