# 测试与验收

## 1. 验收原则

- 自动化验证结构、冻结、权限、事务和兼容；
- 真实 Agent 验证 Summary 是否有用、目标归并是否正确和事实是否完整；
- Schema 通过不能代替事实质量验收；
- 修改前后使用相同冻结 Context 和 Agent Platform 规定的同一模型；
- 六类原有 Context 来源逐字段对照，不允许 Profile 改变来源集合；
- 不以报告变短作为成功标准，不设置事实数量或 Content 长度上限。

## 3. 六类真实报告验收

每类至少选择两个测试服样本：一个原本正常样本，一个内容复杂或较长样本。个人日报额外使用用户给出的多 Agent 学习材料同类样本。总数不少于 12 个 Run。

| 报告类型 | 必须观察的内容结果 |
| --- | --- |
| 个人日报 | Summary 能说明当天主要目标与成果；相关课程、文档、部署、验证不被拆成无关小项；不生成独立计划章节 |
| 个人周报 | 跨天同一目标被合并并使用最新状态；不按日期复述日报；不生成独立计划章节 |
| 小组日报 | Summary 表达小组共同目标和交付；正文不默认逐人罗列；职责或阻塞需要时允许署名 |
| 小组周报 | 团队里程碑、协作状态和风险清晰；不按成员或日期堆叠；Evidence 已明确记录的后续动作在对应主题保留 |
| 部门日报 | Summary 提供部门级进展和管理关注项；正文不机械复制每个小组日报 |
| 部门周报 | 部门成果、关键进度和跨团队依赖清晰；不同小组围绕同一部门目标正确归并 |

每个 Run 固定记录：

- run_id、report_type、Context Hash、Profile 两字段；
- Agent 写回的 Summary、正文 Content、后台组合后的最终 Content 和报告 ID；
- Context 字节、模型输入/输出/缓存 Token、耗时和 MCP 调用次数；
- 原 Context 实质事实清单与报告覆盖结果；
- 是否存在虚构、遗漏、错误合并、过度拆分、重复总结、成员/小组机械罗列；
- 是否只调用一次 get_report_context 和一次成功 write_report_result。

## 4. Summary 人工通过标准

每份 Summary 必须同时满足：

1. 不阅读后续正文也能说清本期主要推进了什么；
2. Evidence 非空时至少说明一个由 Evidence 支持的核心成果或明确状态；Evidence 为空时明确说明本期无可核验工作记录；
3. 不只是复制 Content 的标题；
4. 不逐项重述 Content；
5. 不新增正文 Content 和 Evidence 中不存在的结果、风险或计划；
6. 不包含内部字段、ID、路径、命令、模型、MCP 或生成过程；
7. 与报告对象层级一致：个人讲个人目标，小组讲共同目标，部门讲部门目标。

任一条件失败，该 Run 的 Summary 验收失败。

## 5. Content 人工通过标准

- 最终 Content 只有一个“工作总结”章节，且后续正文不重复总结；
- 正文直接使用真实工作主题的动态二级标题，不出现固定“重点工作”标题，也不对事项作重点/非重点判断；
- 原 Context 中所有实质性成果、失败、阻塞和明确未完成事项均可定位到报告；
- 同一目标下的相关工作被归并，但不同目标没有强行合并；
- 状态使用最新且有证据的事实；
- 没有单独重复一份与前文相同的“当前状态”总结；
- 风险只来自明确风险、阻塞、失败或期限事实；
- 六类报告均不生成独立计划章节；
- Evidence 已明确记录的后续动作只能写入对应工作主题，不得扩写成预测性计划；
- 小组和部门内容按目标综合，不默认按成员或下级组织逐项复制；
- 报告不泄露 Context/MCP 字段和私有技术定位信息。
- Git commit、分支切换和同步操作不形成工作项或成果结论；有独立 Evidence 时只表达工作结果，独立 Evidence 不足时完全忽略 Git 信息。

## 6. 异常与兼容场景

1. Profile 缺字段：新 Context 构建失败；
2. Agent 返回空 Summary：写回拒绝，Content 不落库；
3. Agent 返回空 Content：沿用现有拒绝；
4. Agent 重复写回形成相同最终 Content：幂等成功；
5. Agent 重复写回形成不同最终 Content：拒绝覆盖已完成结果；
6. 用户在 Agent 写回前编辑已有报告：沿用现有编辑冲突，不覆盖用户 Content；
7. 历史报告：读取、编辑、复制和提交行为不变；
8. 历史 Context 无 Profile：继续走通用兼容规则，不强制 Summary、不改变旧 Hash；
9. 用户关闭页面：后端继续执行，最终 Content 写回；
10. Agent Platform 固定模型失败：Run 按现有失败流程结束，不切换模型；
11. Digest 或 Projection 失败：Run 按现有阶段失败，不生成残缺最终 Content。

## 7. 发布门禁

以下条件全部满足才允许发布：

- T-01～T-20 自动化通过；
- 12 个以上六类真实 Run 全部成功或失败原因明确且与本改动无关；
- 每类至少一个复杂样本 Summary 和 Content 人工通过；
- 六类 Context 来源对照无变化；
- 没有新增模型调用、模型配置或模型切换；
- Digest 队列、Projection 性能、上传和 Token 指标无回归；
- 后端和 Skill 的发布与回退记录完整，确认无数据库迁移和前端产物；
- Skill 实际版本由系统资源管理文档记录，不由代码或本方案擅自指定。

## 8. 验收失败后的处理

- Summary 结构缺失：修复 Schema、服务端校验或 Skill 通用契约；
- 单一报告类型组织错误：只修改该类型的 Profile 映射并重新创建 Run，不扩大全局 Skill；
- 多类型共同事实错误：检查通用 Skill 证据规则或 Context Evidence；
- Profile 导致事实遗漏：停止发布，回退 Profile/Skill，不通过增加模型调用规避；
- Agent Platform 问题：单独记录外部问题，不修改 Aida 模型和来源规则。
