# 架构与数据契约

> 唯一需求基线：[01-需求与现状差距.md](01-需求与现状差距.md)

## 1. 三层职责

```text
后端确定性规则
  report_type -> 唯一 presentation_profile
  Context 冻结、权限、Summary/Content 必填和最终 Content 组合

Report Context
  presentation_profile：本次报告如何组织
  Evidence：本次报告允许使用的全部事实

Agent
  理解 Profile 和 Evidence
  归并目标、生成内部 Summary 和正文 Content
```

删除任意一层后的结果：

- 删除后端校验会把 Summary 是否存在交给模型，不能满足必填验收；
- 删除 Profile 会迫使 Skill 重新携带六类互斥规则；
- 删除 Agent 语义归并会迫使确定性代码判断工作目标，当前代码和需求均不支持。

因此三层均为本期必要，且各自只承担一种职责。

## 2. Report Context 模块

### 2.1 小 Interface

调用方继续只使用现有 Context Build/Get Interface。Profile 选择隐藏在 `reportcontext` 模块实现内部，不增加公开参数、配置或调用步骤。

模块内部只增加一个纯函数：

```go
func presentationProfileFor(reportType string) (PresentationProfile, error)
```

`BuildRequest` 不接受 Profile。调用方不能传入或覆盖 Profile。函数只接受已经冻结并通过校验的 `report_type`。

### 2.2 最小数据结构

```go
type PresentationProfile struct {
    SummaryFocus    string `json:"summary_focus"`
    ContentGrouping string `json:"content_grouping"`
}

type Payload struct {
    PresentationProfile *PresentationProfile `json:"presentation_profile,omitempty"`
}
```

不增加 `profile_id`：`run.report_type` 已经是唯一身份。不增加 Profile schema/version：完整 Profile 文本已经冻结在 Context 并参与 `context_hash`，历史 Run 无需重新解释当前配置。

新 `work_evidence` Context 固定结构：

```json
{
  "schema_version": "report-context/v1",
  "run": {
    "run_id": "...",
    "report_type": "personal_daily",
    "period": {"start": "2026-07-24", "end": "2026-07-24"},
    "target": {"type": "self", "user_id": "..."}
  },
  "presentation_profile": {
    "summary_focus": "概括个人当日推进的主要目标、关键成果、验证和整体状态；只有存在明确证据时才提及风险或阻塞。",
    "content_grouping": "按个人工作目标组织正文并直接使用动态工作主题标题；同一目标下的开发、文档、部署、验证和修复合并表达，不判断是否重点，不增加重复的当前状态总结。"
  },
  "work_evidence": {},
  "source_reports": [],
  "requirements": [],
  "tasks": []
}
```

Profile 字符串的唯一内容以需求文档第 5 节表格为准。代码测试逐项比对六类映射。

### 2.3 冻结和失败

- Profile 在 `assemble` 完成后、Context 序列化前加入 Payload；
- Profile 与 Evidence 一起规范化、计算 `context_hash` 并写入现有 `report_run_contexts.context_payload`；
- 同一 Run 已存在 Context 时直接返回已有 Payload，不重新选择 Profile；
- 新 `work_evidence` Run 找不到唯一 Profile、Profile 任一字段为空或 report_type 不支持时，Context 构建失败，不启动 Agent；
- 历史无 `report_context_representation=work_evidence` 的 Run 保持旧 Context，不回填 Profile、不修改 Hash。

## 3. 默认 Agent Prompt 与 Skill Interface

### 3.1 四层唯一职责

当前代码把相同协议复制到四层。本期固定收敛为：

| 层级 | 唯一职责 | 固定内容 | 禁止包含 |
| --- | --- | --- | --- |
| 默认 Agent Instructions | 保证绑定 Skill 被真实加载 | 保留系统识别 Marker；要求实际加载当前绑定的 `aida-report` 并观察到 Skill tool_result；声明其余规则以 Skill 为准 | Context 读取步骤、旧工具名单、凭据槽、报告范围、内容结构、写回参数 |
| Start Prompt Template | 触发 Skill 并传递唯一系统业务参数 | 仅 `/aida-report` 和 `run_id={{ run_id }}` | Context、MCP、凭据、范围、写回和内容规则 |
| 运行时 Message | 承载一次用户补充 | 有用户 `initial_message` 时原样传递一次；为空时固定为“生成本次 Aida 报告。” | 重复 Skill 加载、Context、MCP、凭据、范围或写回协议 |
| Report Skill | 完整报告执行契约 | Context 读取、Evidence 安全、Profile 使用、归并、Summary/正文生成和成功/失败写回 | Agent 身份 Marker、部署配置和报告类型路由 |

`StartPromptValues` 发给 Agent Platform 时只包含 `run_id`。用户 `initial_message` 不再复制进 `StartPromptValues["message"]`，只进入运行时 Message。普通按钮生成当前不提交用户补充，因此实际输入固定为 `/aida-report + run_id + “生成本次 Aida 报告。”`。

删除系统 Marker 后，三层可读文本固定为：

```text
Agent Instructions:
你是 Aida 报告执行 Agent。每次运行必须实际加载当前绑定的 aida-report Skill，并观察到对应的 Skill tool_result 后再继续。除 Skill 加载要求外，本 Prompt 不定义报告流程、来源、结构或写作规则。

Start Prompt Template:
/aida-report
run_id={{ run_id }}

运行时 Message（无用户补充）:
生成本次 Aida 报告。

运行时 Message（有用户补充）:
用户补充说明：
{initial_message}
```

该收敛只修改 Aida 管理的默认报告 Agent。用户自定义 Agent 的 Instructions、Start Prompt 和普通 Agent Run 不修改。用于识别、修复默认 Agent 的 Marker 保留，但 Marker 不承载报告规则。

### 3.2 默认 Agent MCP Toolset

默认 Agent 创建或修复时，其现有 `ManagedMCPServer.Headers` 固定增加：

```text
X-Aida-MCP-Toolset: managed-report
```

Report MCP `tools/list` 收到该 Header 时，只返回：

```text
get_report_context
write_report_result
write_report_failure
```

未携带 Header 时继续返回当前完整工具集。该 Header 只控制 Tool Schema 展示，不参与认证和授权；`tools/call` 路由、用户 Token 校验和所有旧工具实现均不修改。新默认 Agent 使用精简 Toolset；已创建的历史 Agent 和用户自定义 Agent 没有该 Header，继续使用原工具集。

禁止新建 MCP Endpoint、MCP 版本或第二套工具实现。自动化必须证明 Agent Platform 创建请求携带 Header，并分别验证有/无 Header 的 `tools/list`。

### 3.3 Skill Interface

全局 Skill 不再列出六类来源和六套结构，只保留以下通用职责：

1. 输入只读取 `run_id`；
2. 只调用一次 `get_report_context({"run_id": run_id})`；
3. Profile 只决定组织方式，Evidence 是唯一事实来源；
4. 完整阅读 Evidence，按 Profile 建立目标—成果台账，不虚构状态或风险，不推测未来计划；
5. 生成纯文本 Summary 和不重复 Summary 的完整 Markdown Content；
6. 不根据 Git 操作判断成果；只有独立 Evidence 已明确支持工作目标和结果时才表达该结果，按需求文档第 4.2 节忽略 Git 流水；
7. 成功调用一次 `write_report_result`，失败调用 `write_report_failure`。

安全、隐私和证据约束继续保留为通用规则，但不重复六类来源。Skill 不包含日期、周期、目标、Selection 或 Profile 的选择逻辑。

对于历史 Context 没有 Profile 的情况，Skill 使用一个通用兼容规则：Summary 概括主要目标、成果和整体状态，Content 按真实工作目标归并。该规则不枚举报告类型，只用于历史 Run。

Git 降噪只发生在 Agent 表达层。Projection 不识别、不删除 commit、分支或仓库相关事实，保留冻结 Context 的事实完整性；Profile 也不增加 Git 专用字段。Skill 不把 Git 信息视为成果证据，不从 commit message 推断工作结果，也不设置发布、回滚或冲突处置例外。可写入报告的独立 Evidence 必须同时具备需求文档第 4.2 节定义的非 Git 目标关联和明确结果/状态事实；只有标题或目标而没有结果/状态同样不能宣称完成。该规则是六类报告共用的一条证据判断规则。

## 4. 写回 Interface

### 4.1 MCP 参数

新 `work_evidence` Run 的成功写回固定为：

```json
{
  "run_id": "...",
  "summary": "非空纯文本总结",
  "content": "非空 Markdown 正文"
}
```

MCP Tool Schema 保留 `summary` 字符串属性，但为兼容历史 Run，不把它加入全局 required；`run_id` 和 `content` 继续 required。服务端根据 Run 已冻结的 `report_context_representation` 执行条件校验：新 `work_evidence` Run 的 Summary Trim 后必须非空，历史 Run 允许为空。Summary 必填由服务端保证，不依赖模型和全局 Schema。

`report_context_representation` 当前保存在 `ai_runs.execution_input_json`，而 `aiRunGuard` 只读取 `input_ref_json`。本期扩展 Guard 的现有查询，直接读取 `execution_input_json ->> 'report_context_representation'` 到 `reportAIRun.ContextRepresentation`；不复制字段、不增加数据库列。Summary 条件校验只使用这个数据库冻结值，不接受 MCP 参数覆盖。

失败写回仍为：

```json
{"run_id":"...","error_message":"...","error_code":"可选"}
```

日期、周期、报告类型、目标、Selection 和 Profile 均不得成为写回参数。服务端继续从 Run 冻结身份解析。

### 4.2 最终 Content 组合

`summary` 和 Agent 返回的 `content` 只存在于写回处理过程中。新 `work_evidence` Run 固定组合为：

```text
normalized_summary = strings.Join(strings.Fields(summary), " ")
body = strings.TrimSpace(content)
final_content = "## 工作总结\n\n" + normalized_summary + "\n\n" + body
```

约束：

- `normalized_summary` 和 `body` 均必须非空；
- Summary 被归一为一个自然段，不要求 Agent 自己精确处理换行；
- `body` 的第一条非空行不得等于 `## 工作总结`；命中时返回 `REPORT_CONTENT_DUPLICATE_SUMMARY`，避免重复章节；
- 最终报告 Upsert 只接收 `final_content`；
- `ai_runs.output_ref_json.summary` 可以继续作为内部执行记录，但报告表、公开接口和前端不读取它；
- 历史无 `work_evidence` 表示的 Run 继续将原 `content` 作为 `final_content`，不要求 Summary、不改变结果。

### 4.3 结果 Hash 与幂等

继续复用现有算法：

```text
report_result_hash = SHA-256(strings.TrimSpace(final_content))
```

新 Run 的 Summary 已经进入 `final_content`，因此 Summary 或正文变化都会改变 Hash。历史 Run 的 `final_content` 仍等于原 Content，历史已成功 Run 的重试 Hash 不变。不得改为 `JSON(summary, content)` Hash，也不新增 Hash 版本字段。

Hash、报告 Upsert、`ai_runs.output_ref_json` 和 Run succeeded 继续处于同一数据库事务。重复提交形成相同 `final_content` 时返回 `already_written=true`；形成不同最终内容时仍拒绝。

## 5. 持久化与产品接口

- 六张报告表现有 `content` 是唯一报告正文存储；不新增 `summary` 或 `submitted_summary`；
- 六类 Agent Upsert 继续只写现有 Content，传入值改为组合后的 `final_content`；
- 报告详情、列表 DTO 和公开接口不新增字段；
- 前端、编辑、复制、飞书和提交接口不修改；
- 现有 `submitted_content` 会自然冻结已经组合完成的“工作总结 + 正文”；
- 无独立提交快照的报告继续沿用现有 Content 语义；
- 下级报告仍作为一个 Content 进入上级 Context，不新增 SourceReport 字段或读取分支。

## 6. 权限和安全

- `run_id` 仍不是凭据；
- Profile 读取复用 `get_report_context` 当前用户与 Run 归属校验；
- 写回复用 `aiRunGuard`、报告身份解析、Selection 完整性和写冲突校验；
- Agent 传入的日期、周期、类型、目标和 Profile 不被读取；
- Profile 是服务端字段，Evidence 继续作为不可信数据处理；
- 最终 Content 使用现有报告内容安全边界，不新增 HTML 执行能力。

## 7. 兼容与发布顺序

本分支的 `work_evidence` 表示尚未发布，因此 Profile 与 Summary 契约随该表示一次发布。固定顺序：

1. 按系统资源管理流程发布新的不可变 Skill 资源，但不修改当前生产配置、不提前切换默认 Skill；
2. 在同一次后端部署中发布支持 Profile、Summary 条件必填和最终 Content 组合的镜像，并将 `MANAGED_AGENT_REPORT_SKILL_VERSION` 切换到刚发布的 Skill；新代码与新 Skill 同时对新 Run 生效；
3. 创建新 Run 做六类验收；
4. 未通过时使用旧 Skill 版本配置回退后端镜像；新 Skill 资源保留但不再被引用；无数据库和前端回退步骤。

历史 Run 和历史报告：

- 无 `work_evidence` 表示的历史 Context 不要求 Profile 和 Summary；
- 历史报告 Content 原样展示，不批量增加“工作总结”章节；
- 不回填、不调用模型补 Summary；
- 新生成 Run 使用 Profile、内部 Summary 和最终 Content 组合契约。

## 8. 复杂度预算

本期新增：一个 Context 字段、一个包内纯函数、写回阶段的 Summary 校验和最终 Content 组合。

本期不新增：数据库字段或迁移、公开报告接口字段、前端改动、配置项、进程、队列、Worker、模型调用、状态机、Profile 管理能力或工作流框架。
