# 需求与现状差距

## 1. 用户问题

当前 Agent 可以生成事实完整的长报告，但完整正文缺少独立的高层总结。用户需要再次人工概括“今天或本周主要做了什么”，才能用于汇报。

当前全局 Report Skill 还同时说明六类报告的来源路由、证据判断、内容组织和写回规则。继续在同一 Skill 中增加六套 Summary 和正文模板，会让模型在一次运行中同时接收五套无关规则。

## 2. 产品目标

1. 六类托管 Agent 报告均以“工作总结”开头，随后保留完整正文；
2. Agent 内部同时生成 Summary 和正文，后端组合后仍只保存并返回现有 `content`；
3. 相关开发、文档、部署、验证和修复按真实工作目标归并，不按操作类型拆散；
4. 小组和部门报告按组织目标归并，不默认逐人或逐小组罗列；
5. Agent 每次只接收当前报告类型的展示规则；
6. 六类报告既有 Context 来源、冻结、权限和写回身份保持不变；
7. 不增加模型调用，不改变 Agent Platform 规定的模型。
8. 删除默认 Agent Instructions、Start Prompt、运行时 Message 与 Skill 之间的重复协议，每条规则只有一个归属位置。
9. Git 提交、分支和同步操作不能单独证明工作成果，不得成为日报中的独立工作项、结果或操作流水。

## 4. Summary 与 Content 的产品定义

### 4.1 Summary

Summary 是 Agent 写回的内部纯文本段落，不是报告产品字段。后端会将其放入最终 Content 的“工作总结”章节。Summary 必须：

- 说明本期主要推进的工作目标；
- 说明已经形成的核心成果或交付；
- 说明整体状态；
- 只有存在明确证据时才提及风险或阻塞；
- 不包含 Markdown 标题、列表、内部字段、ID、路径、命令或诊断信息；
- 只生成一个自然段，不设置字符数或 Token 数硬限制；
- 不复制正文标题，也不把正文每一项重新罗列一遍。

### 4.2 Content

Agent 返回的 Content 是不含 Summary 的完整 Markdown 正文，固定结构为：

```text
## {按真实目标形成的动态工作主题}
目标、成果、必要行动、验证和当前状态

## 风险与待处理
仅在 Evidence 明确支持时出现
```

正文不设置“重点工作”总标题，也不要求 Agent 判断事项是否重点。每个真实工作主题直接使用动态二级标题；Content 不再自行生成开头或结尾总结，也不增加重复的“当前状态”总表或独立计划章节。状态以及 Evidence 已明确记录的后续动作应进入对应工作主题，不得推测未来计划。

Git 信息采用“保留溯源、不得据此判断成果”的固定规则：

- commit message、commit hash、分支名、`commit/push/pull/checkout` 等操作不得单独形成工作主题或提交清单；
- Git 操作不能单独支持“功能完成、问题修复、验证通过、已经发布、服务恢复或风险解除”等结论；
- 只有 Context 中另有明确的工作目标、结果、状态或验证证据时，正文才表达该工作成果；Git 信息只在后台辅助关联，不进入正文；
- 不为发布合并、回滚、冲突处置或仓库治理预设例外。若这些内容本身是用户明确的工作目标，也必须由非 Git 操作流水的目标和结果证据支持，正文描述工作结果而不是 Git 过程；
- 无法从其他 Evidence 确认有效工作内容时，忽略 Git 信息，不根据 commit message 推断成果。

本规则中的“独立 Evidence”固定指：存在不来源于 Git 命令、Git 输出、commit message、commit metadata 或分支状态的明确工作目标关联，并且至少存在一项明确的结果、状态、验证、失败或阻塞事实。只有需求/任务标题、只有用户提出目标、只有 commit message 或只有仓库状态，均不足以支持“已完成”或其他工作结论。

### 4.3 最终报告 Content

新 `work_evidence` Run 写回成功前，后端固定执行：

```text
final_content = "## 工作总结\n\n" + normalize(summary) + "\n\n" + trim(content)
```

- `normalize(summary)` 将首尾空白删除，并将内部换行和连续空白归一为单个空格，保证 Summary 是一个自然段；
- Agent Content 不得自行包含“工作总结”章节；
- 最终只将 `final_content` 写入报告现有 `content`；
- 历史 Run 继续原样写入其 Content，不执行组合；
- 报告接口、页面、人工编辑、复制和提交快照继续处理一个 Content 字段。

### 4.4 无有效 Evidence

当 Context 没有可报告的实质工作事实时，不让模型虚构成果，也不新增失败状态：Summary 明确说明“本期无可核验的工作记录”，正文只说明没有形成可报告事实，不生成成果、风险或计划。

## 5. 六类报告的唯一展示口径

| report_type | Summary 聚焦 | Content 归并 |
| --- | --- | --- |
| `personal_daily` | 个人当日推进的主要目标、关键成果、验证和整体状态 | 按个人工作目标归并；同一目标下的开发、文档、部署、验证和修复合并表达 |
| `personal_weekly` | 个人本周核心进展、里程碑、最新状态和明确风险 | 跨日期归并持续目标，不按星期或日报逐条复述 |
| `team_daily` | 小组当日共同目标、团队交付、整体状态和共享阻塞 | 按小组共同目标归并，不默认逐人罗列；只有解释职责或阻塞归属时提及成员 |
| `team_weekly` | 小组本周交付、关键里程碑、协作状态和明确风险 | 按小组业务目标与里程碑归并，不按成员或日期罗列 |
| `department_daily` | 部门当日重要进展、整体状态和需要管理关注的跨团队问题 | 按部门级目标归并，不机械罗列小组；只有解释责任或依赖时提及小组 |
| `department_weekly` | 部门本周整体成果、关键进度、跨团队依赖和管理关注项 | 按部门级目标和关键里程碑归并，不按小组逐份复述 |

六类 Profile 只改变表达层级，不得：

- 修改第六阶段已经确定的来源；
- 删除或筛选 Evidence；
- 改变 Scope、Coverage、Selection、周期或目标；
- 生成成员排名、贡献评分或缺报通报；
- 决定模型或修改模型参数。

## 6. 用户流程

用户流程不变：

```text
点击生成
  -> 获得 run_id 并看到生成中
  -> 后端完成 Context、Agent 和写回
  -> 页面通过现有 content 显示工作总结和完整正文
```

前端不展示 Profile，不让用户选择 Profile，也不依赖页面持续在线推动流程。

## 7. 验收标准

1. 六类新托管报告的现有 `content` 均以非空“工作总结”章节开头，并包含非空完整正文；
2. 报告表、公开接口和前端不新增 Summary 字段，现有页面无需修改即可展示最终 Content；
3. 每个 Context 只包含与 `run.report_type` 对应的一份 Profile；
4. 同一 Run 重复读取的 Profile、Evidence 和 Context Hash 不变；
5. Skill 不再包含六类来源路由和六套结构说明；
6. Summary 能独立说明主要目标、成果和整体状态，不是正文标题拼接；
7. Content 覆盖原 Context 的所有实质性成果、失败、阻塞和明确未完成事项；
8. 个人报告不按操作类型拆分，小组和部门报告不默认按成员或组织逐项罗列；
9. 无明确证据时不生成风险，也不推测未来计划；
10. Agent 仍只读取一次 Context、写回一次结果，后端只组合一次；
11. Digest、Projection、Selection、权限、上传、Token 统计和原报告来源不变；
12. 同一 Agent 执行同时生成 Summary 与 Content，不新增模型调用、不切换模型。
13. 默认 Agent Instructions、Start Prompt、运行时 Message 和 Skill 中不存在重复的 Context、凭据、范围或写回协议。
14. 默认 Agent 只收到 `get_report_context`、`write_report_result`、`write_report_failure` 三个 MCP Tool Schema；自定义和历史 Agent 工具集不变。
15. Git 提交、分支和同步操作不会形成独立工作主题、结果或操作清单；Git 信息不能单独支持任何成果判断，有独立证据时只表达工作结果，独立证据不足时忽略。

## 8. 明确不做

- 不新增六份 Skill 或六个 Agent；
- 不新增 Profile 数据表、管理页面、动态配置、版本平台或模板服务；
- 不把 Profile 放进 Digest；
- 不修改六类来源 SQL 和组织范围；
- 不让 Agent 选择 Profile；
- 不分页读取 Context；
- 不增加第二次 Summary 模型调用；
- 不新增 Summary 数据库列、DTO、报告接口字段或前端改动；
- 不修改用户自定义 Agent 的 Instructions 或 Start Prompt；
- 不限制 Digest 或 Content 长度；
- 不改变 `next_day_plan` 的人工维护规则；
- 不切换、降级、备用或覆盖平台模型。
