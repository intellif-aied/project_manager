### 3.1 Context 内存在一份 Digest 的完整重复

| 有 `sessions` 但不存在上述完整重复 | 20 | 5,158 | 18,527 |

34 个重复样本中，两个字段的 Digest JSON 是逐字段相等，不是仅内容相似。重复部分合计 8,628,469 bytes，占这些 Context 总字节的 49.9%；p90 单份重复为 1,019,239 bytes。

两个代表样本的实际构成：

| Context 总字节 | `sessions` | `sources` | 两处 Digest |
| ---: | ---: | ---: | --- |
| 3,880,408 | 1,939,854 | 1,939,783 | 完全相同 |
| 2,039,329 | 1,019,310 | 1,019,239 | 完全相同 |

重复来源已在代码中定位：

- `api/internal/reportcontext/service.go` 将同一份 Digest 同时写入 `assembled.Sessions` 和 `assembled.Sources.SessionDigest`；
- `api/internal/reportcontext/types.go` 明确记录 `Sources` 是第五阶段兼容字段，用于默认 Skill 切换到完整 V1 字段前的过渡；
- 当前默认 Skill 已使用完整 Context，但过渡字段仍被写入新 Context。

因此，“新 Context 完整复制一次 Digest”是已确认的本地结构问题。但生产中仍有旧 Context 仅包含 `sources.session_digest`，不能在未定义 schema 兼容规则前直接删除读取支持。

### 3.2 去除重复后，部分 Digest 仍然很大

重复不是唯一原因。对有 `sessions` 的最大样本继续按 JSON 字段分解：

| 单份 Digest 字节 | `report_period_summary` | `items` | `items` 数 | `highlights` 数 |
| ---: | ---: | ---: | ---: | ---: |
| 约 1,939,700 | 1,882,453 | 56,622 | 60 | 2,140 |
| 约 1,019,100 | 997,871 | 20,664 | 22 | 1,140 |
| 约 810,100 | 757,646 | 51,845 | 55 | 829 |
| 约 3,813,600（旧形态） | 3,695,491 | 117,456 | 125 | 4,148 |

前三个日报样本的 `report_period_summary` 内部只有一天，字节几乎全部来自该日的 `highlights` 数组。第四个周报样本包含 7 天、4,148 条 highlight，其中单日最多 3,018 条。四个样本的单条 highlight 平均约 873～959 bytes，数组包含目标、结果陈述、时间、工作单元引用、状态和证据等完整字段。

三个样本的 2,140、1,140 和 829 条 highlight 均为完整 JSON 不重复，`work_unit_ref` 也均一一不同。它们不是同一条记录的简单重复写入。其中目标数分别为 78、313 和 41，说明后续可以按目标组织读取，但不能以目标数代替工作单元事实。

这是真实的高密度工作证据，本阶段不会通过限制 Digest 条数、Top-K、静默截断或删除字段来规避传递问题。即使去除上述 49.9% 的结构重复，大 Digest 仍然需要稳定的完整传递和消费机制。

四个代表样本：

| --- | --- | ---: | ---: | ---: | ---: |
| 小 Context 成功 | Claude Code / GLM-5.2 | 124,800 | 0 | 2,257 | $0.408255 |

### 6.1 Claude Code 的大 MCP 结果边界

Anthropic 当前官方文档明确：

- Claude Code 在 MCP 工具输出超过 10,000 Token 时告警，默认最大输出是 25,000 Token；
- MCP 工具可通过 `_meta["anthropic/maxResultSizeChars"]` 声明单工具文本结果容量；此前把 500,000 字符写成平台固定硬上限不准确，当前实现只把它作为 `get_report_context` 的明确工具契约；
- 超过当前上限的工具结果会保存到磁盘，对话中只保留文件引用。

官方说明：<https://code.claude.com/docs/en/mcp#MCP-output-limits-and-warnings>。

生产大 Context 为 1.62～3.88MB，不能只靠提高工具容量解决。当前固定先做确定性 Projection，再为 `get_report_context` 声明 500,000 字符容量；容量声明只承接已收敛的 Context，不允许原始 Digest 直接进入模型。

MCP 规范允许工具返回 Resource Link 或 Embedded Resource，但 Resource Link 不保证客户端自动读取；Claude Code 的官方交互是通过 `@server:uri` 引用后获取资源。MCP 内建游标分页仅覆盖 `resources/list`、`resources/templates/list`、`prompts/list` 和 `tools/list`，不会自动对某个 Tool Result 分页。因此，单独改成 Resource Link 或声称 MCP 自带工具结果分页，都不能构成确定的后台执行契约。

MCP 规范说明：<https://modelcontextprotocol.io/specification/draft/server/tools#tool-result>、<https://modelcontextprotocol.io/specification/draft/server/utilities/pagination>。

  -> Worker 下载对象

代码证据：

Aida 当前 `api/service/managed_agent.go` 的 `CreateManagedSessionRequest` 没有 `InputFiles`，`api/handler/report_run_submitter.go` 也没有上传或附加 Context 文件。这表明“在 Agent 启动前把冻结 Context 挂载为 Session 输入文件”有现成平台边界，不需要新建文件系统。

但输入文件只解决“完整 Context 可靠到达 Sandbox”，不自动解决“普通模型在可控轮次和成本内完整消费”。本阶段只将它作为已确认可验证的平台通道，在对照试验前不定为最终方案。

## 7. 当前可确认结论

### C-01：标准短 Context 链路能够成立

S01 证明当前 `run_id -> get_report_context -> write_report_result` 主链路本身可正常完成，不需要重新引入旧报告参数或额外数据扫描工具。

### C-02：模型不可用必须与生成流程优化分开

S02 在工具调用前终止。它属于模型目录、权限或服务可用性问题，不能通过修改 Digest、Context 或 Skill 修复。

### C-03：大 Context 的首要问题是传递和消费方式，不是内容应被删除

S03、S04 的 Context 均已完整冻结；故障发生在工具结果超过执行引擎单次返回能力后。后续设计必须保持完整事实，不得通过 Digest Top-K、静默裁剪或人为内容硬限制规避问题。

### C-04：依赖 Claude Code 模型自行读取临时文件不稳定

同一份约 1.99MB Context 在不同模型和执行引擎组合上表现明显不同：Codex + GPT-5.5 可较快完成，Claude Code + MiniMax 可以写回但质量异常，Claude Code + GLM 长时间处理后失败。当前 Claude Code 的“超限后保存文件，再要求模型自行分块读完”不能作为普通模型稳定完成报告的可靠契约。

### C-05：Context 大小需要拆成两个独立问题处理

1. 新 Context 将同一 Digest 写入两次，使受影响 Context 增大约一倍，这是确定的 schema 迁移收尾问题；
2. 真实 Digest 可包含数百至数千条 highlight，去重后仍可达 0.8～1.94MB，这是必须被完整支持的产品数据规模。

前者应在保持旧 Context 可读的前提下消除新 Context 重复；后者需要改造大结果传递契约，不得让 Digest 代替 Agent 决定哪些证据可以丢弃。


2026-07-23 后续决策：完整支持指 Digest 已冻结的所有报告结果事实均被覆盖并可追溯，不表示必须把重复结构和存储字段原样交给 Agent。Digest 当前只为结果型 Work Unit 保存完整报告事实，其他 Work Unit 仅保留覆盖计数；Projection 不恢复或伪造源中不存在的正文。传递方案固定为 Report Context Builder 内的确定性 Projection，不分页、不新增 LLM、Job 或队列；语义归并仍由最终 Report Agent 完成。

2026-07-24 修订验证：列式结构已删除。Projection 输出普通 `facts[]`，完全相同结果正文只出现一次并保留不同日期/状态观察；原始 Goal、交接 Prompt 和内部审计引用不进入 Agent Context。31 份冻结样本的 8,713 次结果出现归并为 2,134 条不同事实，最大 MCP 包装为 133,066 字符；旧失败 Run `dac01e5c-...` 等价回放由 581,393 降至 339,762 字符。独立结果正文未截断、改写或语义归并。
## 8. 尚不能确认

- 不能仅凭首批样本确定最终采用分块、索引、附件或其他传递方式；
- 不能把 GLM 的所有失败都归因于 Context 大小；
- 不能根据 `cost_usd` 或字符数替代精确 Token；
- 不能确认 MiniMax 成功状态等于报告质量合格；
- 不能把 Codex + GPT-5.5 与 Claude Code + GLM/MiniMax 的差异单独归因于模型；
- Langfuse Trace 与 Run/Session 的稳定关联方式尚未验证。
- 在完成 schema 读写面盘点前，尚不能确定新 Context 只写 `sessions`、只写 `sources`，还是通过明确的 schema 版本分界。
