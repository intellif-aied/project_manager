# 报告 Agent Session 摘要优化发布、运维与回退方案

> 状态：代码已具备发布条件；上线预案尚未执行
> 原则：先 shadow、再 canary、后 enforce；任何阶段不满足门禁立即停止。

## 1. 发布对象

- API 数据库 migration；
- `sessiondigest` Reconciler、Builder/worker；
- report source 与 Report MCP；
- 默认 Aida Report Skill 和 Agent 指令；
- 配置、指标和告警；
- 不发布独立 `session-digest` Skill；
- 不修改 Agent Harness 或 `sandboxed-agent-platform`。

## 2. 模式

| 模式 | Builder | Agent 实际读取 | 用途 |
| --- | --- | --- | --- |
| `full` | 可关闭或仅新数据构建 | 原文分页 | 初始兼容与紧急回退 |
| `shadow` | 开启 | 原文分页 | 验证构建稳定性、压缩率和覆盖，不改变报告 |
| `digest_v1` | 开启 | 单页 Digest | canary 与正式 enforce |

模式在创建 run 时冻结。切换环境变量不能改变已附着 run，避免同一报告执行中途更换来源格式。

`digest_v1` 灰度使用测试用户 allowlist 和稳定用户分桶。未命中灰度而冻结为 full 属于计划内路由；命中后因错误改读 full 才属于 raw fallback。两者必须使用不同指标和审计事件。

## 3. 发布前检查

- 目标分支干净或变更已明确归属；
- 重新确认 migration 编号无冲突；
- 数据库备份和恢复点可用；
- full 回归、Digest 自动化、Golden、安全、性能和回退测试通过；
- 14.157 的 API、前端 pnpm 服务和 Docker 服务健康；
- 测试环境 MCP/Skill 确认来自本次代码；
- 默认 Skill 内容已验证 digest/full 双模式和禁止回退规则；
- Token/成本基线已保存；
- 指标、Dashboard 和告警先于 enforce 上线；
- canary allowlist、稳定分桶算法、rollout 比例和计划内 full 指标已验证；
- 发布负责人已经冻结告警窗口与具体阈值，不能在告警发生后临时放宽；
- 生产发布批准已获得。

## 4. 阶段化发布

### 阶段 A：数据库与 full 模式

1. 应用仅新增表、nullable 字段和索引的向前 migration；
2. API 保持 `MANAGED_AGENT_REPORT_SESSION_READ_MODE=full`；
3. 验证旧 full 报告、Session 上传、Token/成本和组织报告；
4. 观察数据库锁、索引构建和错误率。

门禁：旧功能零回归，migration 无长时间阻塞。

### 阶段 B：shadow

1. 切换 `shadow`；
2. 新切片实时构建，历史切片限速回填；
3. 观察 24 小时以上，覆盖一个报告高峰；
4. 对 Golden 和真实样本比较 source bytes、digest bytes、coverage 和 hash 稳定性；
5. Agent 仍读取 full，不影响用户报告。

门禁建议：

- 构建成功率 >=99.9%；
- queue oldest pending age 在约定阈值内；
- >=1 MiB 样本压缩 >=90%；
- 无敏感信息告警；
- API/DB/上传 P95 无明显回归；
- 所有 selection item 可找到 ready Digest。

### 阶段 C：测试账号 canary

1. 设置 `digest_v1`、rollout percent=0，并通过 allowlist 仅让 14.157 指定测试账号的新 run 使用 Digest；
2. 完成 6 账号、四角色、六类报告和 A/B Token 测试；
3. 人工 Review 个人报告关键事实；
4. 演练 full 回退。

门禁：关键事实 100%、无幻觉/泄漏、input tokens 中位数降低 >=70%、raw fallback=0。

### 阶段 D：生产小流量

- 清空测试专用 allowlist后，使用稳定分桶依次设置 5%、25%、50%，每档至少覆盖约定观察窗口；
- 仅新 run 生效；
- 每次扩容抽查上一档命中用户仍保持命中，且非命中 full 只出现在 rollout decision 指标中；
- 每档检查错误、Token、时延、用户反馈和报告质量抽样；
- 不允许通过自动 full fallback 掩盖错误。

### 阶段 E：全面 enforce

- 新托管个人报告全部 `digest_v1`；
- 保留 full 代码作为人工回退路径一个稳定周期；
- 达到保留期后再单独评审是否移除，不在本次发布立即删除。

## 5. 监控与告警

### 5.1 Dashboard

至少展示：

- Digest pending/building/ready/failed 数量；
- Reconciler scan 时延、eligible/created/conflict 和 oldest missing age；
- build QPS、P50/P95/P99、attempts、oldest pending age；
- source/output bytes 分布和压缩率；
- detailed/compact 数量；
- MCP digest P50/P95/P99 和响应大小；
- NOT_READY、FAILED、LIMIT_EXCEEDED、MODE_MISMATCH；
- report input/output tokens、总生成时延和成功率；
- rollout decision（计划内 full/digest）数量与原因；
- raw fallback 计数；
- Session 上传、content projection、Token worker、DB 连接池对照指标。

### 5.2 告警

| 告警 | 建议条件 | 动作 |
| --- | --- | --- |
| Digest 构建失败 | 5 分钟失败率超过阈值 | 停止扩大灰度，检查错误码 |
| 队列积压 | oldest pending age 持续超阈值 | 限制回填，检查 worker/DB |
| 响应超限 | 任一 actual_bytes >128 KiB | 阻断发布，按缺陷处理 |
| raw fallback | enforce 中 >0 | 立即停止灰度并审计 |
| 敏感信息 | 扫描命中 | 停止、隔离证据、按安全事件处理 |
| 质量下降 | 抽样关键事实失败 | 切回 full，仅影响新 run |
| 业务性能 | API/DB/上传 P95 明显恶化 | 暂停回填或切 full |

指标 label 禁止使用用户、Session、run、文件名或摘要文本。

发布前必须把表中的“阈值”“超阈值”和“明显恶化”替换为环境对应的数值与持续窗口并归档。建议起点为：构建失败率 15 分钟窗口高于 0.1%、实时任务 oldest pending age 连续 15 分钟高于 10 分钟、API/上传 P95 连续 15 分钟比冻结基线上升超过 10%；最终阈值以容量测试和现网基线为准。

## 6. 运行手册

### 6.1 NOT_READY

1. 查看 Digest Revision 状态和 job attempts；
2. 确认 content projection 已 active、epoch 未变化；
3. 临时错误等待现有重试；
4. 稳定失败按 error_code 修复后重新入队；
5. 不手工把 run 改成 full，不跳过来源 item。

### 6.2 LIMIT_EXCEEDED

- 显式来源：提示用户减少选择切片；
- 自动来源：记录阻断，检查 compact 算法和异常超长元数据；
- 不截掉整个 item，不临时提高生产硬上限；
- 如需调整上限，必须重新执行性能、安全和 Token Review。

### 6.3 CONTENT_CLEARED / VERSION_MISMATCH

- 不复活旧 Digest；
- 按现有 Session 恢复和新 epoch 规则处理；
- 已附着 run 失败后重新创建新 run/selection；
- 不直接修改 selection 快照引用。

## 7. 回退方案

### 7.1 应用回退

1. 将 `MANAGED_AGENT_REPORT_SESSION_READ_MODE` 切为 `full`；
2. 重启/滚动 API，使新 run 使用 full；
3. 已附着 digest run 保持原 mode，允许完成；若因缺陷必须终止，明确标记失败并由用户重建；
4. 确认新 run 的 required mode、MCP 响应和报告成功率；
5. 保留 Digest 表和 nullable 字段，不执行破坏性 down migration；
6. 暂停历史回填 worker，保留新数据便于复盘。

### 7.2 Skill 回退

默认 Skill 应同时支持 full/digest，因此正常模式切换不需要 Skill 回退。如果 Skill 本身有缺陷，按仓库既定 `aida-report@1.0.0` 刷新流程恢复上一份已验证内容，并核对平台实际生效的 `skill_md`。

### 7.3 数据库回退

- 新表和 nullable 列保留；
- 旧代码不得依赖或写入它们；
- 不删除仍被 selection 引用的 Revision；
- 只有经过独立数据清理评审且无引用时才可后续删除。

## 8. 数据保留与清理

- Digest 不延长原始 Session 的保留期；
- selection-level Digest payload 与 selection 同生命周期，过期后按既有 selection 清理策略删除；
- content clear 后旧 Digest 不可读，按同一生命周期清理；
- superseded Revision 在无 selection 引用并超过保留期后批量清理；
- 清理使用小批次、短事务和可恢复游标；
- 不在业务请求中同步批量删除；
- 审计只保留版本、hash、计数、状态和时间，不保留正文副本。
