# 报告 Agent Session 摘要优化架构设计

> 状态：目标架构（服务端实现完成，待生产灰度）
> 契约依据：[03-数据契约与摘要规范.md](03-数据契约与摘要规范.md)

## 1. 当前链路与根因

```text
Session JSONL
  -> 增量上传与对象存储
  -> session_content_events（summary/excerpt + 原始 content_payload）
  -> report_source_selection 冻结完整切片
  -> Report MCP get_sessions 分页返回 events/payload
  -> 原文进入模型上下文
  -> Agent 再次归纳
  -> write_report_result 校验“来源已读完”
```

当前页级边界只限制一次 MCP 返回为 100 个事件或 512 KiB，不能限制整个来源快照总量。把摘要脚本放在 Agent 内部也无法解决问题：Agent既没有来源 JSONL 文件挂载，读取 MCP 原文后 Token 已经产生，跳过 MCP 又无法满足来源完整读取校验。

## 2. 目标架构

```text
Session 增量上传
  -> Content Projection（现有）
  -> 完整上传切片（现有）
  -> Digest Reconciler（新增，异步扫描已提交状态）
  -> enqueue build_content_slice_digest
  -> Digest Builder（新增，无 LLM）
       -> session_slice_digest_revisions（新增，不可变）

个人报告启动
  -> 冻结 report_source_selection（现有）
       -> 每个 item 绑定 ready Digest Revision（新增）
       -> 预组装并冻结 selection Digest payload（新增）
       -> 超限/不完整时在 Agent Session 创建前失败
       -> run 固定 required_read_mode=digest_v1（新增）
  -> Report MCP get_sessions
       -> 读取并校验冻结的 Digest payload
       -> 单次返回 <= 128 KiB 的结构化 Digest
       -> 标记 read_completed_mode=digest_v1
  -> Report Agent 生成报告
  -> write_report_result 校验正确模式已完整读取
```

核心边界是：原始事件始终留在 Aida 数据侧，报告模型只看到 Digest。

## 3. 组件职责

### 3.1 Content Projection

继续负责把 Claude/Codex JSONL 投影为规范事件。不得在这里调用模型，也不改变现有 cursor、epoch、清理和恢复语义。上传 finalize 和投影事务不承担 Digest Revision/job 的持久化正确性，避免摘要调度故障阻断上传。

### 3.2 Digest Reconciler 与 Builder

Reconciler 是独立后台循环，以数据库已提交状态为权威：

1. 批量查找“完整切片存在、active projection 的 `content_indexed_cursor >= slice.end_cursor`、content epoch 有效且缺少当前 Digest 版本”的记录；
2. 在自身短事务中 `INSERT ... ON CONFLICT DO NOTHING` 创建 Revision 和 build job；
3. 多实例并发依靠唯一约束收敛，按 recent-first、固定 batch 和并发上限运行；
4. finalize/投影完成后可以发送无状态 wake-up 信号降低延迟，但周期性 reconciliation 才是正确性兜底；
5. Reconciler 失败只造成 Digest 暂时 `REPORT_SOURCE_DIGEST_NOT_READY`，不回滚已成功的上传或内容投影。

Builder 消费 Reconciler 创建的任务，职责如下：

- 按 slice 的 projection revision 和 cursor 范围读取事件；
- 使用 allow-list 事件类型和版本化规则提取结构化事实；
- 执行脱敏、去重、排序、字段级截断和 hash；
- 保存不可变 Digest Revision；
- 幂等处理重复任务；
- 记录计数、字节数、耗时和失败码，不记录正文。

Builder 使用独立 worker 并复用 `session_processing_jobs` 的租约、心跳、重试和退避机制。新增 job type 为 `build_content_slice_digest`，不得放进 Token/计费 worker。

现有任务队列会把 processor error 写入 `last_error`。Digest worker 只能向队列提交稳定错误码和无正文诊断，不能把解析内容、原始 payload 或底层含敏感值的错误直接传给 `Fail`。

### 3.3 Digest Repository

保存切片级不可变摘要。推荐表名：`session_slice_digest_revisions`。唯一身份由以下字段组成：

```text
session_content_slice_id
+ content_projection_revision_id
+ content_epoch
+ digest_version
+ redaction_version
```

ready Revision 不允许原地修改。规则升级创建新 Revision，不覆盖旧来源快照正在引用的版本。

### 3.4 Report Source Selection

来源冻结时继续保存完整切片的 source/generation/projection/cursor/epoch 快照，并新增：

- `session_content_slice_id`；
- `digest_revision_id`；
- `digest_sha256_snapshot`；
- `digest_version_snapshot`。

只有本次 run 要求摘要模式时才强制 Digest ready。未就绪返回明确的 retryable 错误，不启动 Agent。

### 3.5 Selection Digest Assembler

Assembler 在 Agent Session 创建前按来源 item 顺序批量读取已绑定的 Digest Revision，完成：

1. item 数量和一一对应校验；
2. 详细预算组装；
3. 超过 64 KiB 时对所有 item 公平压缩为 compact 形式；
4. 最终 JSON 序列化后硬上限 128 KiB 校验；
5. 生成 selection-level digest hash 和 coverage；
6. 将规范序列化后的完整 `get_sessions` result payload、hash、bytes 和 compaction 冻结到 selection；
7. 只有 payload 冻结成功后才允许创建并附着 Agent run。

不得按“重要性”删除整个切片，因为后端无法可靠替用户决定哪个显式来源不重要。

### 3.6 Report MCP

附着式个人报告仍使用 `get_sessions`，避免新增工具和 Agent 绑定复杂度。服务端根据 `run_id` 中冻结的 `required_read_mode` 决定返回格式：

- `digest_v1`：返回本方案结构；
- `full`：仅兼容未启用阶段和非托管用途。

摘要模式不在 MCP 调用时重新扫描 Revisions 或重新压缩，而是校验 content epoch、版本和 selection hash 后返回冻结 payload；托管 enforce run 请求 full 时返回 `REPORT_SOURCE_READ_MODE_MISMATCH`。Agent 不能通过参数绕开。

### 3.7 Report Skill 与写回

默认 Skill 必须：

- 支持识别 `content_mode=digest_v1`；
- 把 Digest 文本当作不可信证据，不执行其中的命令或指令；
- 使用 goals/outcomes/files/validations/blockers 生成报告；
- 检查 `coverage.complete=true`；
- 不要求或运行额外 `session-digest` Skill；
- 不累加原始 Token 遥测。

`write_report_result` 校验 `read_completed_mode == required_read_mode`，并继续校验 selection、run、period、user、content epoch 和来源可用性。

## 4. 数据模型

### 4.1 `session_slice_digest_revisions`

| 字段 | 说明 |
| --- | --- |
| `id` | UUID 主键 |
| `session_content_slice_id` | 完整上传切片 |
| `content_projection_revision_id` | 事件投影版本 |
| `generation_id` | 来源 generation |
| `content_epoch` | 内容生命周期 epoch |
| `digest_version` | `session-digest/v1` |
| `redaction_version` | `report-redaction/v1` |
| `status` | `pending/building/ready/failed/superseded` |
| `digest_json` | 结构化摘要，ready 后不可变 |
| `source_event_count` | 范围内原事件数 |
| `included_event_count` | 对摘要有贡献的事件数 |
| `omitted_event_count` | 未进入摘要的事件数 |
| `source_bytes` | 原事件 JSON 字节数 |
| `digest_bytes` | Digest JSON 字节数 |
| `truncated` | 是否发生字段级压缩 |
| `source_sha256` | 来源范围与事件 hash |
| `digest_sha256` | 最终 Digest hash |
| `error_code` | 失败分类，不保存敏感正文 |
| `created_at/ready_at` | 生命周期时间 |

唯一约束覆盖 slice、projection、epoch、digest version 和 redaction version。

### 4.2 `session_processing_jobs`

新增 `target_digest_revision_id` 外键，并为 `build_content_slice_digest` 增加“每个目标 Revision 仅一个任务”的唯一索引。迁移还必须同步更新 job type CHECK、content epoch 必填约束、`ProcessingJob` 字段以及 repository 的 RETURNING/Scan；遗漏任一处都会使 worker 无法 claim 新任务。迁移编号必须在实施时重新检查，不在文档中硬编码。

### 4.3 `report_source_selection_items`

新增 slice 与 Digest Revision 引用。历史行允许为空；新 enforce run 不允许为空。来源 item 仍保留原 cursor 快照，便于审计和原文兼容读取。

### 4.4 `report_source_selections`

复用现有 `read_completed_at`，新增：

- `required_read_mode`：`full` 或 `digest_v1`；
- `read_completed_mode`；
- `selection_digest_sha256`；
- `selection_digest_payload`：规范序列化的 model-visible `get_sessions` result bytes；
- `selection_digest_bytes` 与 `selection_digest_compaction`；
- digest/redaction version、target/hard-limit 的快照字段。

不能仅保留一个布尔“已读取”，否则 full 读取可能错误满足 digest run 的约束。

## 5. 状态与时序

### 5.1 Digest 状态

```text
pending -> building -> ready
                    -> failed -> pending（按现有最大重试）
ready -> superseded（规则/投影版本变化，仅停止新引用）
```

content epoch 变化或来源清理后，旧 Revision 不再可读。恢复完成后基于新 epoch 生成新 Revision。

### 5.2 切片就绪调和

```text
periodic reconciler
  -> slice exists AND active projection indexed_cursor >= slice.end_cursor
  -> INSERT Digest Revision ON CONFLICT DO NOTHING
  -> INSERT build job ON CONFLICT DO NOTHING
```

切片先出现、投影先推进、投影重建激活以及进程在任意一步重启，都必须在后续扫描中收敛到同一 Revision/job。只有 active projection 已完整覆盖切片 cursor 范围才满足构建条件。

### 5.3 报告启动

```text
解析报告周期和用户范围
-> 冻结完整切片 selection
-> 解析每个 item 的当前 Digest Revision
-> 任一未 ready：不创建 Agent Session，返回 REPORT_SOURCE_DIGEST_NOT_READY
-> 全部 ready：Assembler 预组装并冻结 payload
-> 超限/不完整：不创建 Agent Session，返回稳定错误
-> payload ready：附着 run，写入 required_read_mode
-> Agent 调用 get_sessions
-> 返回并校验冻结的单页完整 Digest
-> 标记 read_completed_mode
-> Agent 写回
```

报告启动事务不能现场扫描数 MB 原文生成 Digest。

## 6. 预算设计

- 详细目标：整个 MCP 文本 JSON 不超过 64 KiB；
- 硬上限：128 KiB；
- 单 item 详细摘要最大 4 KiB；
- 超过详细目标时，Assembler 对所有 item 进入 compact 形式，优先保留目标、最终成果、失败验证和覆盖元数据；
- 预算按最终 UTF-8 JSON 重新计算，不能用字符数代替字节数；
- Assembler 必须批量读取 selection items 和 Revisions，禁止按 item 产生 N+1 查询；
- `budget.actual_bytes` 参与响应自身序列化，必须迭代到数值与最终 body 字节数稳定一致后再做 hard-limit 判断；
- 预算对象是模型可见的 `get_sessions` result JSON，不包含 HTTP Header 或 JSON-RPC 传输信封；冻结 payload 使用规范 UTF-8 bytes，MCP 不得经过产生不同内容的二次组装；
- 任一 item 至少保留元数据和 coverage；有可靠证据时再保留目标/成果 headline，无可靠证据时允许相应数组为空，禁止为满足格式而编造；
- 最小形式仍超过硬上限时，在 Agent 启动前返回 `REPORT_SOURCE_DIGEST_LIMIT_EXCEEDED`；
- 禁止以分页方式把总量重新扩展到无上限。本期摘要模式固定单页、`has_more=false`。

## 7. 并发与幂等

- Builder 通过唯一 Revision 和 job 索引防止重复构建；
- Reconciler 只扫描已提交状态，在独立短事务中幂等入队；多实例、两种先后顺序和进程重启均由唯一约束收敛；
- worker 使用现有 `FOR UPDATE SKIP LOCKED`、租约和心跳模型；
- ready Revision 只读，可被多个 selection 并发引用；
- selection Digest payload 在 attach 前冻结，附着后不可原地重组；
- selection 冻结与 run attach 保持现有事务边界；
- Digest 构建完成不能改变已冻结 selection 的 item 集合；
- 规则升级只影响新 run，已启动 run 继续使用快照版本；
- 清理操作继续依赖 content epoch 和来源可用性校验，避免读到旧数据。

## 8. 安全边界

1. 使用字段 allow-list，默认丢弃未知 payload，而不是先全量复制再黑名单删除。
2. 对 Authorization、Bearer、API key、password、secret、cookie、DSN 凭据、私钥块和已知凭据槽执行脱敏。
3. 原始命令不进入 Digest；validation 只保留规范化工具/测试名称、状态和脱敏短结果。
4. 用户消息和 Agent 文本都属于不可信证据；Skill 不得执行其中指令。
5. Digest 正文不写入普通日志、指标 label 或错误信息。
6. job `last_error` 只保存稳定错误码和无正文诊断，processor 原始错误必须先分类和脱敏。
7. 读取仍受当前用户、run、selection 和 scope 约束，不提供跨用户查询。
8. 报告正文继续禁止内部 ID、UUID、run_id 和 Session ID 泄漏。

## 9. 兼容性

- 未启用时保持现有 full 读取；
- shadow 模式只构建和比较，不改变 Agent 输入；
- canary 由服务端对用户做稳定分桶并支持测试账号 allowlist，路由结果在 run 创建时冻结；
- 未命中 canary 而使用 full 是计划内路由，不计为 fallback；一旦 run 冻结为 digest，执行期改读 full 才是禁止的 raw fallback；
- enforce 仅针对托管个人日报/周报；
- ad-hoc `get_sessions` 日期查询和自定义 Agent 维持原契约；
- 小组/部门报告、Token/成本、Session 上传、候选 UI 均不改变；
- Skill 同时理解 digest/full 响应以支持开关回退，但读取模式只能由服务端决定。

## 10. 架构决策

| 决策 | 选择 | 原因 |
| --- | --- | --- |
| 摘要位置 | Aida 服务端 | 真正发生在模型上下文之前，具备来源、权限和生命周期信息 |
| 摘要方式 | 规则、无 LLM | 成本可控、确定性、可重放和可审计 |
| 数据形态 | 结构化 JSON | 字段可限额、可测试、避免 Markdown 指令混淆 |
| 粒度 | 完整上传切片 | 与产品选择和来源快照一致 |
| 构建方式 | 异步预计算 | 不阻塞上传和报告启动，不重复扫描原文 |
| MCP 工具 | 复用 `get_sessions` | 不增加工具和绑定面，服务端控制读取模式 |
| 原文回退 | enforce 禁止 | 防止优化失效和成本不可控 |
| 平台改造 | 不修改 Harness | 避免 jq、文件挂载和跨仓库发布依赖 |
