# 报告 Agent Session 摘要优化需求方案

> 状态：需求基线（服务端实现完成，待 shadow/canary 上线验收）
> 上位产品基准：`doc/v2/Session增量上传与报告来源/产品需求.md`

## 1. 背景与问题

托管个人日报和个人周报使用不可变来源快照。当前 `get_sessions` 快照模式按页返回完整 Session 事件及原始 payload，报告 Agent 必须读完所有页后才能写回报告。原始 Session 可达到数 MB 甚至更大，导致以下问题：

1. 大量工具输入输出、reasoning、遥测和重复消息进入模型上下文；
2. Agent 在获得原文后仍需再次提炼工作事实，输入 Token 和生成时间显著增加；
3. `include_summary=true` 不能改变快照分支返回原始事件的事实；
4. 在 Agent 读取原文之后再运行本地摘要脚本，不能追回已经消耗的上下文 Token；
5. Agent 沙箱没有用户原始 JSONL 文件挂载契约，也不能依赖 `jq` 等非 Harness 保证工具。

因此必须把压缩边界前移到 Aida 后端，使模型第一次接触 Session 来源时收到的就是有界摘要。

## 2. 产品目标

- 显著降低个人报告生成的 Session 来源输入 Token、MCP 响应体和生成时延；
- 保留用户显式选择及后端自动选择的所有完整切片，不改变来源快照语义；
- 保留生成报告必需的目标、成果、改动文件、验证结果和阻塞信息；
- 对摘要覆盖、截断、脱敏、版本和来源提供可审计证据；
- 不使用额外 LLM 生成摘要，不把成本从日报模型转移到另一次模型调用；
- 支持安全灰度和快速回退，但生产托管报告不得由 Agent自行回退到原文。

## 3. 范围

### 3.1 本期范围

- 个人日报、个人周报的附着式来源快照读取；
- Claude Code 和 Codex Session 的已投影事件；
- 每个完整上传切片的版本化 Digest；
- 来源快照级预算组装、MCP 返回和完整读取标记；
- 默认 Aida Report Skill、Agent 指令和回写一致性校验；
- 摘要构建、读取、失败、压缩比和真实模型 Token 的可观测性；
- 14.157 测试环境真实回归、灰度和回退。

### 3.2 非本期范围

- 改变 Session 上传、cursor 连续性、切片形成或内容清理规则；
- 改变 Token、成本、价格和日期归属统计；
- 让小组或部门报告读取成员原始 Session；
- 使用 LLM 生成或补写 Digest；
- 在 Agent 沙箱挂载用户 JSONL、安装 `jq` 或修改 `sandboxed-agent-platform`；
- 删除原始 Session 内容；
- 改变 Report MCP 授权、用户范围或六类报告 scope 矩阵；
- 把 Digest 作为用户可编辑的日报正文。

## 4. 用户场景

### 4.1 手动个人报告

用户显式选择一个或多个 Session 切片。Aida 冻结相应完整切片及其 Digest Revision，Agent 只收到摘要结构。用户未选择的切片不得进入本次来源。

### 4.2 自动来源个人报告

用户未选择切片，Aida 按现有报告周期与切片活动区间相交规则冻结来源。所有相交完整切片分别保留并提供 Digest，不按事件日期重新裁剪。

### 4.3 定时个人报告

定时任务沿用现有周期推导和来源冻结规则。Digest 尚未就绪时按现有失败/重试机制处理，不新增另一套定时任务状态机。

### 4.4 个人周报来源优先级

个人周报继续以已保存的个人日报为主要来源，Session Digest 只处于既有的固定补充位置。摘要优化不得让 Session 越过已保存日报，也不得把周报变成对一周 Session 原文或 Digest 的重新汇总。

### 4.5 组织报告

小组报告继续汇总个人报告，部门报告继续汇总小组报告，默认不调用 Session Digest。本功能不得改变其来源层级和权限。

## 5. 功能需求

| 编号 | 需求 |
| --- | --- |
| SDR-FR-001 | Session 内容必须在进入报告模型上下文之前完成摘要；不得先通过 MCP 返回原文再在 Agent 内压缩。 |
| SDR-FR-002 | Digest 必须由确定性、版本化规则生成，不调用 LLM；相同输入、提取器版本和脱敏版本必须得到相同结果与 hash。 |
| SDR-FR-003 | Digest 必须绑定完整上传切片、内容投影 Revision、content epoch 和 cursor 范围；来源快照冻结后不得混入后续上传。 |
| SDR-FR-004 | 来源快照中的每个 item 必须在响应中有对应记录；不能为了预算静默删除整个切片。 |
| SDR-FR-005 | Digest 至少提供 goals、outcomes、files_changed、validations、blockers 和 coverage；空字段使用空数组，不得编造。 |
| SDR-FR-006 | 托管个人报告的读取模式由服务端附着到 run 并校验；Agent 不得自行选择原文模式或在摘要失败时回退原文。 |
| SDR-FR-007 | 摘要未就绪、来源已清理、版本不匹配、预算无法满足时必须返回稳定错误码，并区分可重试与需用户处理。 |
| SDR-FR-008 | 摘要模式完整读取后，现有 `write_report_result` 来源完整性校验仍然成立；未完成读取不得写回。 |
| SDR-FR-009 | 个人周报仍以已保存个人日报为主、Session 仅作固定补充；组织报告来源层级、scope、权限、已有报告优先级和写回语义保持不变。 |
| SDR-FR-010 | 所有文本在进入 Digest 前必须经过敏感信息脱敏，并在结构和 Skill 中标记为“不可信工作证据”，不能作为 Agent 指令执行。 |
| SDR-FR-011 | Digest Revision 必须可复用、幂等构建、可追踪版本；重复上传无新增内容时不得产生重复 Digest。 |
| SDR-FR-012 | Session 内容清理、恢复或 content epoch 变化后，旧 Digest 和旧来源快照必须按现有生命周期规则失效，不得继续读取。 |

## 6. 非功能需求

| 编号 | 指标 |
| --- | --- |
| SDR-NFR-001 | 正常响应目标不超过 64 KiB，任何摘要响应硬上限为 128 KiB；字节数按最终 UTF-8 JSON 计算。 |
| SDR-NFR-002 | 对原始 Session 来源大于等于 1 MiB 的 Golden Fixture，MCP Session 来源响应字节数至少降低 90%。 |
| SDR-NFR-003 | 对原始 Session 来源不小于 1 MiB 的真实配对运行，使用同一来源快照、模型和提示词时，Claude 与 Codex 各自的平台既有口径整次报告模型输入 Token 中位数至少降低 70%，同时关键事实召回必须通过。 |
| SDR-NFR-004 | 已就绪 Digest 的 `get_sessions` 摘要读取在 14.157 基准数据上 P95 不高于 500 ms，不增加业务请求中的 LLM 调用。 |
| SDR-NFR-005 | Digest 构建异步执行，不阻塞 Session 上传成功响应；构建失败不得拖慢其他上传、Token 处理和报告来源查询。 |
| SDR-NFR-006 | 不扩大用户可见范围，不在日志和指标中记录 Digest 正文、密钥、Authorization 或原始 payload。 |
| SDR-NFR-007 | 缺失 Digest 时禁止静默使用原文；所有降级与开关变化必须可审计。 |
| SDR-NFR-008 | 兼容当前最多 200 个显式切片选择；若最小结构仍超过硬上限，必须在启动 Agent 前失败。 |

## 7. 摘要质量要求

1. 同一 Session 中后续用户任务不得因“只取第一条请求”而丢失。
2. 产出不得通过“取最长 Agent 文本”决定；应优先最终结果、完成事件和验证结论。
3. 文件路径保留可区分的仓库相对路径，不能只留最后两级造成碰撞。
4. 测试命令仅保留规范化名称、状态和短结果，不保留可能包含密钥的完整参数。
5. reasoning/thinking、系统/开发者提示、完整工具输出、二进制/base64 和累计 Token 遥测不得进入 Digest。
6. 无法可靠识别的内容宁可省略并增加 omitted 计数，不得推断事实。
7. 每个 item 都要报告 source、included、omitted 事件数以及是否被压缩。

## 8. 用户可见行为

- 正常情况下，生成入口和报告正文没有新增操作步骤；
- 摘要处理中，手动生成返回“Session 摘要处理中，请稍后重试”；
- 来源过大且最小摘要仍无法满足硬上限时，显式选择提示用户减少切片；自动来源记录明确失败原因；
- 摘要失败不会偷偷改用原文，也不会生成来源不完整但看似成功的报告；
- 报告正文不得展示 Digest 版本、内部 ID、hash、cursor 或脱敏计数。

## 9. 验收标准

只有同时满足以下条件才可认定需求完成：

1. 所有 SDR-FR 和 SDR-NFR 均有通过证据；
2. Claude/Codex、多任务、跨日、多切片、大文件、恶意内容和敏感信息 Golden Fixture 全部通过；
3. 真实 Agent 的关键事实与原文基线一致，不出现来源遗漏或新增幻觉；
4. 14.157 六账号、四角色、六类报告回归通过；
5. Token/成本统计对账无变化；
6. shadow 与灰度指标达标，原文回退计数为 0；
7. 回退演练通过且未产生不可逆数据；
8. 测试环境验证完成前不得发布生产。
