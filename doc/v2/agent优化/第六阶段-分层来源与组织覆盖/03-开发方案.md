## 3. 设计分层

### A. 本期必须完成

- 六类 Report Context 的确定性来源、组织覆盖和不可变冻结；
- 六类 Report Run 接入 Context 构建与失败归属；
- 完整 Context 的容量提醒、同一 Run 确认和 Aida 平台保护；
- 有效执行用户、当前 Run、报告对象的读取与写回一致性；
- 默认 Skill 收敛到一次 Context 读取；
- Session、Digest 和 Token 统计回归。

### B. 代码事实触发的必要保障

- 来源必须在服务端内部读完所有分页，不能复制旧 Agent 的分页失控问题；
- Context 规范化、稳定排序和 Hash 只用于保证冻结结果可校验；
- Context 已存在时不得覆盖，外部 Agent 失败也不得回滚冻结输入；
- 重复下级报告使本次构建失败，不任意选择；
- 构建失败记录到当前 Run，且不启动 Agent。

### C. 后续增强

本次没有 C 类开发任务。需求文档列出的降级、下钻、多轮取数、精确 Token、用户自定义 Skill 产品化等内容继续作为非目标，不在本文规划后续实现。

## 4. 变更边界

### 4.1 计划修改

- `api/internal/reportcontext/`：扩展六类 Context 的构建、规范化、冻结和读取；
- `api/handler/managed_agent.go`：六类 Run 统一接入 Context 构建、容量判断和 Agent 启动；
- `api/handler/report_mcp.go`：读取和写回采用一致的 Run 身份校验；
- `api/service/daily_report_skill.go`：默认 Skill 收敛为读取 Context、生成、写回；
- 上述模块的聚焦测试和必要文档。

### 4.2 明确不修改

- Session 上传、Digest 算法与版本；
- usage、metering、Token Analytics；
- 需求、任务、组织和报告的业务归属模型；
- 用户自定义 Skill 产品能力；
- 降级、下钻、多轮取数及其他未来工作流。

### 4.3 新增资源

当前没有已确认的新表、迁移、服务、状态机或配置项。A-04/A-05/A-06 的验证若改变这一结论，必须先回到架构评审。

## 7. 开发顺序

1. D-01：先完成一个深的 Report Context 模块及六类模块级测试；
2. D-02：把六类 Run 接入 Context 构建，先跑通非容量分支；
3. PV-01～PV-03 可与 D-01、D-02 并行完成，并更新对应架构决策；
4. D-03、D-04：只在各自决策确认后接入容量与 Run 级安全；
5. D-05：最后切换默认 Skill，避免 Context 和安全校验未完成时提前移除旧路径；
6. D-06 贯穿各步骤，最后执行真实 Agent 验收。

## 8. 停止条件

出现任一情况立即停止对应实现并回到架构或需求评审：

- 需要新增未确认的表、迁移、服务、协议、状态或配置；
- 当前数据无法实现需求规定的来源范围；
- 容量确认无法复用同一 Run 和冻结 Context；
- 现有认证链无法提供可由 Aida 验证的 Run 作用域，且替代方案尚未单独确认；
- 为完成生成需要静默裁剪、Top-K、自动降级或多轮取数；
- 开发发现必须改变《01-需求文档》的产品行为。
