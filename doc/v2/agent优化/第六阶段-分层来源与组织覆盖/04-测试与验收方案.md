## 1. 测试原则

- 产品验收只从需求文档派生；
- 技术风险验证只引用已确认架构决策；
- 通过 Report Context 的公开构建/读取入口和真实报告链路验证，不绑定内部 Reader、类或包拆分；
- 构建成功不能替代真实 Agent 生成和最终报告人工检查；
- 六类报告各自运行成功不能替代分层来源验收。必须按“个人报告 → 小组报告 → 部门报告”的真实组织依赖顺序生成，并逐级核对本轮下级 `report_id` 已进入上一级冻结 Context；
- 测试前必须从目标环境的当前组织数据确认成员、小组、直属成员和部门关系，禁止仅凭历史测试账号文档或角色名称推断归属；
- 上下级报告必须使用完全一致的日报日期或周报周期。不得使用不同账号、不同组织或历史遗留报告拼成一组验收证据；
- A-04、A-05、A-06 未确认前，只保留目标级用例，不伪造接口字段或状态码。

## 2. 六类报告主链路

### 2.1 强制执行顺序

六类真实 Agent 验收必须是一条连续的来源链，不是六个相互独立的冒烟任务：

```text
真实小组成员个人日报
→ 同一成员个人周报
→ 该成员所属小组的小组日报 / 小组周报
→ 该小组所属部门的部门日报 / 部门周报
```

执行前必须记录并核对：

- 个人报告用户确实属于目标小组；
- 小组报告用户确实有权代表目标小组生成报告；
- 目标小组确实属于目标部门；
- 部门报告用户确实有权代表目标部门生成报告；
- 日报日期一致，周报起止日期一致。

严格按以下顺序执行：

1. 成员生成个人日报，记录本轮个人日报 `run_id`、`report_id`；
2. 同一成员生成个人周报，断言其 Context 的 `source_reports` 包含步骤 1 的 `report_id`；
3. 小组负责人生成小组日报，断言其 Context 的 `source_reports` 包含步骤 1 的 `report_id`；
4. 小组负责人生成小组周报，断言其 Context 的 `source_reports` 包含步骤 2 的 `report_id`；
5. 部门负责人生成部门日报，断言其 Context 的 `source_reports` 包含步骤 3 的 `report_id`；
6. 部门负责人生成部门周报，断言其 Context 的 `source_reports` 包含步骤 4 的 `report_id`；
7. 对六个 Agent Session 分别核对：Skill 加载 1 次、`get_report_context` 1 次、`write_report_result` 1 次、旧读取工具 0 次；
8. 人工核对上级报告正文确实表达下级报告中的代表性事实，并正确表达其他缺失或无效来源。

以下任一情况均不得判定分层主链路通过：

- 个人报告用户不属于随后测试的小组；
- 部门报告读取的是测试前已有的历史小组报告，而非本轮刚生成的小组报告；
- 只检查六个 Run 都是 `succeeded`，未检查逐级 `report_id`；
- 只验证 Context 构建成功，未检查真实 Agent 调用与最终写回；
- 上一级报告通过旧 MCP 工具重新扫描数据完成生成。

## 10. 发布门禁

- A-04、A-05、A-06 已验证并确认；
- R-01～R-06 全部通过真实 Agent 链路；
- 本轮个人日报 `report_id` 进入个人周报和小组日报 Context，本轮个人周报 `report_id` 进入小组周报 Context；
- 本轮小组日报 `report_id` 进入部门日报 Context，本轮小组周报 `report_id` 进入部门周报 Context；
- S、SS、F、A、C、M、G 各组无未解释失败；
- 同一 Run 的 Context 可复现，确认容量后不重新取数；
- 默认 Agent 没有自由扫描基础数据；
- 没有静默裁剪、自动降级或第六阶段外能力；
- Session、Digest、usage、metering 和 Token Analytics 回归通过。

### 11.1 生产验收复用要求

生产验收不得直接复用上述测试账号和 ID，但必须复用同一验证方法：

1. 先从生产当前组织关系选定一名真实小组成员、一名对应小组负责人和一名对应部门负责人；
2. 记录三者实时组织关系，确认属于同一“成员 → 小组 → 部门”链；
3. 按 2.1 的顺序生成六类报告；
4. 逐级核对本轮下级 `report_id`，不得用历史报告、同名报告或仅凭正文相似度代替；
5. 任一逐级关联不成立，立即停止并判定分层主链路失败，不继续用其他独立成功任务补齐结果。
