> 文档状态：六类分层主链路已完成测试环境验收；容量与 Run 级安全用例待对应决策补齐协议细节

> 架构基线：[02-架构设计](02-架构设计.md)

## 1. 测试原则

- 产品验收只从需求文档派生；
- 技术风险验证只引用已确认架构决策；
- 通过 Report Context 的公开构建/读取入口和真实报告链路验证，不绑定内部 Reader、类或包拆分；
- 构建成功不能替代真实 Agent 生成和最终报告人工检查；
- 六类报告各自运行成功不能替代分层来源验收。必须按“个人报告 → 小组报告 → 部门报告”的真实组织依赖顺序生成，并逐级核对本轮下级 `report_id` 已进入上一级冻结 Context；
- 测试前必须从目标环境的当前组织数据确认成员、小组、直属成员和部门关系，禁止仅凭历史测试账号文档或角色名称推断归属；
- 上下级报告必须使用完全一致的日报日期或周报周期。不得使用不同账号、不同组织或历史遗留报告拼成一组验收证据；
- A-04、A-05、A-06 未确认前，只保留目标级用例，不伪造接口字段或状态码。

## 2. 六类报告主链路

### 2.1 强制执行顺序

六类真实 Agent 验收必须覆盖两条不同小组的连续来源链，再由同一位部门负责人汇总，不是六个相互独立的冒烟任务：

```text
小组 A 成员个人日报 / 个人周报 → 小组 A 的小组日报 / 小组周报 ┐
                                                               ├→ 部门日报 / 部门周报
小组 B 成员个人日报 / 个人周报 → 小组 B 的小组日报 / 小组周报 ┘
```

执行前必须记录并核对：

- 目标部门只有一名当前有效的部门负责人；不得仅凭账号角色字段认定部门负责人；
- 小组 A、小组 B 是目标部门当前直属的两个不同小组，且各自只有一名当前有效的小组负责人；
- 两名个人报告用户分别属于小组 A、小组 B，不得由同一成员或同一小组替代两条链路；
- 小组报告用户确实有权代表对应小组生成报告，部门报告用户确实有权代表目标部门生成报告；
- 部门直属但不属于小组的成员单独记录，不得错误归入任一小组；
- 历史测试小组、已解绑小组、角色脏数据和其他部门数据不得进入本次组织范围；
- 日报日期一致，周报起止日期一致。

严格按以下顺序执行：

1. 小组 A、B 的成员分别生成个人日报，记录两个 `run_id`、`report_id`；
2. 两名成员分别生成个人周报，断言各自 Context 只包含本人的步骤 1 报告；
3. 两位小组负责人分别生成小组日报，断言各自 Context 包含本组步骤 1 报告且不包含另一组报告；
4. 两位小组负责人分别生成小组周报，断言各自 Context 包含本组步骤 2 报告且不包含另一组报告；
5. 部门负责人生成部门日报，断言其 Context 同时且仅包含步骤 3 的两个直属小组日报；
6. 部门负责人生成部门周报，断言其 Context 同时且仅包含步骤 4 的两个直属小组周报；
7. 对十个 Agent Session 分别核对：Skill 加载 1 次、`get_report_context` 1 次、`write_report_result` 1 次、旧读取工具 0 次；
8. 通过公开报告查询接口核对冻结来源已回写到报告来源字段，部门列表的总小组数、已有数和缺失数与 Context 一致；
9. 人工核对上级报告正文确实表达两组下级报告中的代表性事实，并正确表达其他缺失或无效来源。

以下任一情况均不得判定分层主链路通过：

- 个人报告用户不属于随后测试的小组；
- 两条成员链实际属于同一小组，或由错误角色账号代替真实负责人；
- 部门报告读取的是测试前已有的历史小组报告，而非本轮刚生成的小组报告；
- 只检查十个 Run 都是 `succeeded`，未检查逐级 `report_id` 和跨组隔离；
- 只验证 Context 构建成功，未检查真实 Agent 调用与最终写回；
- Context 来源正确，但公开列表的来源计数仍为 0 或与冻结来源不一致；
- 上一级报告通过旧 MCP 工具重新扫描数据完成生成。

## 10. 发布门禁

- A-04、A-05、A-06 已验证并确认；
- R-01～R-06 通过两个不同小组、十个真实 Agent Run 的完整链路；
- 本轮个人日报 `report_id` 进入个人周报和小组日报 Context，本轮个人周报 `report_id` 进入小组周报 Context；
- 本轮小组日报 `report_id` 进入部门日报 Context，本轮小组周报 `report_id` 进入部门周报 Context；
- S、SS、F、A、C、M、G 各组无未解释失败；
- 同一 Run 的 Context 可复现，确认容量后不重新取数；
- 默认 Agent 没有自由扫描基础数据；
- 公开报告详情中的来源 ID 与冻结 Context 一致，部门列表的总数、已有数和缺失数正确；
- 没有静默裁剪、自动降级或第六阶段外能力；
- Session、Digest、usage、metering 和 Token Analytics 回归通过。

- 测试小组和测试小组2是两个不同的有效小组；

### 11.2 生产验收执行流程

#### 阶段一：冻结验收基线

1. 确定唯一日报日期 `D` 和包含 `D` 的唯一周报周期 `W`；十个 Run 必须使用相同日期和周期边界；
2. 保存生产组织接口返回的部门、小组、负责人、成员关系，形成验收前组织快照；
3. 查询 `D`、`W` 当前已有的七个测试账号报告；优先选择没有历史测试报告的周期。若已有报告会干扰来源判断，则更换验收周期或停止确认，不删除生产记录，也不得把历史报告当成本轮来源；
4. 为 `t03`、`t09` 准备可明确区分的 Session 来源，分别记录 Selection ID 和所选切片；
5. 确认默认报告 Agent、Skill 版本和 Report MCP 均为本次待验版本；
6. 任一组织关系、权限或版本门禁不成立时停止，不启动 Agent。

#### 阶段二：生成两个成员的个人报告

1. `t03` 生成个人日报，记录 `run_id`、Agent Session ID、Context Hash/Bytes 和 `report_id`；
2. `t03` 生成个人周报，确认 Context 引用步骤 1 的个人日报；
3. `t09` 生成个人日报，记录同样证据；
4. `t09` 生成个人周报，确认 Context 引用本人的个人日报；
5. 交叉检查：`t03` 的个人周报不得引用 `t09` 报告，`t09` 的个人周报不得引用 `t03` 报告。

#### 阶段三：生成两个小组的报告

1. `t05` 生成测试小组日报，Context 必须包含本轮 `t03` 个人日报，不得包含 `t09` 个人日报；
2. `t05` 生成测试小组周报，Context 必须包含本轮 `t03` 个人周报，不得包含 `t09` 个人周报；
3. `t08` 生成测试小组2日报，Context 必须包含本轮 `t09` 个人日报，不得包含 `t03` 个人日报；
4. `t08` 生成测试小组2周报，Context 必须包含本轮 `t09` 个人周报，不得包含 `t03` 个人周报；
5. 覆盖检查：测试小组 Context 中必须存在 `t07` 的成员覆盖记录；若 `t07` 本轮没有报告，应为 `missing`，不能从成员列表消失，也不能表述为没有工作。

#### 阶段四：生成部门报告

1. `t10` 生成测试部部门日报；Context 必须同时且仅引用本轮测试小组、测试小组2的两份小组日报；
2. `t10` 生成测试部部门周报；Context 必须同时且仅引用本轮两个小组的两份小组周报；
3. 部门覆盖必须包含直属 PM `t06`。若 `t06` 本轮没有对应个人报告，应保留为 `missing`，不能从覆盖中消失；
4. 部门 Context 不得直接读取 `t03`、`t07`、`t09` 的 Session 或个人报告代替已有小组报告；
5. 不得出现测试部以外的小组、历史小组或第二个总监。

#### 阶段五：公开接口与 Agent 链路核对

1. 对十个 Run 分别确认最终状态为 `succeeded`；
2. 对十个 Agent Session 分别确认：Skill 加载 1 次、`get_report_context` 1 次、`write_report_result` 1 次、旧读取工具 0 次；
3. 通过个人、小组、部门公开报告详情接口核对来源 ID 与冻结 Context 完全一致；
4. 通过部门报告列表核对：`team_count=2`、`submitted_team_count=2`、`missing_team_count=0`；
5. 通过成员报告接口核对 `t10` 的部门成员范围，以及 `t05`、`t08` 各自只能看到本组成员；
6. 人工检查十份报告正文，确认两个小组的事实没有串组，部门报告同时覆盖两组事实，missing 来源没有被写成“没有工作”；
7. 保存全部 Run ID、报告 ID、Context Hash/Bytes、Agent Session ID、Skill 版本、MCP 调用计数、接口响应摘要和人工结论。

### 11.3 生产验收停止条件

出现以下任一情况必须立即停止，不得用其他成功任务拼凑通过结论：

- 测试小组2无法确认直属测试部；
- `t05`、`t08`、`t10` 的真实管理权限与预期不符；
- 生产存在重复总监、重复有效小组或历史组织污染；
- 上一级 Context 未引用本轮下一级 `report_id`；
- 两个小组之间发生成员报告串读；
- Context 来源正确，但报告详情来源字段或列表汇总计数不一致；
- Agent 未调用 Context、调用旧读取工具、未写回结果或被平台错误标记成功；
- 任一测试使用了不同日期、不同周周期或验收前历史报告。

只有两个小组的十次真实 Agent 生成、逐级来源、跨组隔离、部门覆盖、公开接口和最终正文全部通过，才能判定本轮生产分层主链路验收通过。
