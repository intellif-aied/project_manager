## 1. 测试原则

- 产品验收只从需求文档派生；
- 技术风险验证只引用已确认架构决策；
- 通过 Report Context 的公开构建/读取入口和真实报告链路验证，不绑定内部 Reader、类或包拆分；
- 构建成功不能替代真实 Agent 生成和最终报告人工检查；
- 六类报告各自运行成功不能替代分层来源验收。必须按“个人报告 → 小组报告 → 部门报告”的真实组织依赖顺序生成，并逐级核对本轮下级 `report_id` 已进入上一级冻结 Context；
- 测试前必须从目标环境的当前组织数据确认成员、小组、直属成员和部门关系，禁止仅凭历史测试账号文档或角色名称推断归属；
- 启动真实 Agent 前必须验证目标 API 容器的镜像 ID、Compose 配置文件和工作目录确实来自待验收工作区；不得仅因端口可访问或容器健康就认定新代码已部署；
- 上下级报告必须使用完全一致的日报日期或周报周期。不得使用不同账号、不同组织或历史遗留报告拼成一组验收证据；
- A-04、A-05、A-06 未确认前，只保留目标级用例，不伪造接口字段或状态码。

## 2. 六类报告主链路

### 2.1 强制执行顺序

六类真实 Agent 验收必须覆盖两条不同小组的连续来源链，再由同一位部门负责人汇总，不是六个相互独立的冒烟任务：

```text
小组 A 成员个人日报 / 个人周报 → 小组 A 的小组日报 / 小组周报 ┐
                                                               ├→ 部门日报 / 部门周报
小组 B 成员个人日报 / 个人周报 → 小组 B 的小组日报 / 小组周报 ┘
```

执行前必须记录并核对：

- 目标部门只有一名当前有效的部门负责人；不得仅凭账号角色字段认定部门负责人；
- 小组 A、小组 B 是目标部门当前直属的两个不同小组，且各自只有一名当前有效的小组负责人；
- 两名个人报告用户分别属于小组 A、小组 B，不得由同一成员或同一小组替代两条链路；
- 小组报告用户确实有权代表对应小组生成报告，部门报告用户确实有权代表目标部门生成报告；
- 部门直属但不属于小组的成员单独记录，不得错误归入任一小组；
- 历史测试小组、已解绑小组、角色脏数据和其他部门数据不得进入本次组织范围；
- 日报日期一致，周报起止日期一致。

严格按以下顺序执行：

1. 小组 A、B 的成员分别生成个人日报，记录两个 `run_id`、`report_id`；
2. 两名成员分别生成个人周报，断言各自 Context 只包含本人的步骤 1 报告；
3. 两位小组负责人分别生成小组日报，断言各自 Context 包含本组步骤 1 报告且不包含另一组报告；
4. 两位小组负责人分别生成小组周报，断言各自 Context 包含本组步骤 2 报告且不包含另一组报告；
5. 部门负责人生成部门日报，断言其 Context 同时且仅包含步骤 3 的两个直属小组日报；
6. 部门负责人生成部门周报，断言其 Context 同时且仅包含步骤 4 的两个直属小组周报；
7. 对十个 Agent Session 分别核对：Skill 加载 1 次、`get_report_context` 1 次、旧读取工具 0 次、最终成功写回且只形成一份业务报告；若 `write_report_result` 参数校验失败后安全重试，必须单独记录失败调用和成功调用，不得把失败调用算作成功写回，也不得产生重复报告；
8. 通过公开报告查询接口核对冻结来源已回写到报告来源字段，部门列表的总小组数、已有数和缺失数与 Context 一致；
9. 人工核对上级报告正文确实表达两组下级报告中的代表性事实，并正确表达其他缺失或无效来源。

以下任一情况均不得判定分层主链路通过：

- 个人报告用户不属于随后测试的小组；
- 两条成员链实际属于同一小组，或由错误角色账号代替真实负责人；
- 部门报告读取的是测试前已有的历史小组报告，而非本轮刚生成的小组报告；
- 只检查十个 Run 都是 `succeeded`，未检查逐级 `report_id` 和跨组隔离；
- 只验证 Context 构建成功，未检查真实 Agent 调用与最终写回；
- Context 来源正确，但公开列表的来源计数仍为 0 或与冻结来源不一致；
- Context、公开接口和最终正文对报告对象、小组负责人、成员角色、来源状态或统计数量的表达互相矛盾；
- 上一级报告通过旧 MCP 工具重新扫描数据完成生成。

### 2.3 最终正文事实一致性硬门禁

每个 Run 必须分别保存并对照四份证据：验收前组织快照、冻结 Report Context、公开报告详情响应、最终报告正文。只核对 Run 状态、MCP 调用次数或来源 ID，不能判定该 Run 通过。

| 报告类型 | 必须逐项核对的事实 |
|---|---|
| 个人日报 | 报告用户、业务日期、Session Selection、Digest 中的主要工作事实、需求任务归属与状态 |
| 个人周报 | 报告用户、周周期、所引用个人日报 ID、需求任务范围；不得混入其他成员报告或自动读取整周 Session |
| 小组日报 | 小组 ID/名称、当前小组负责人 ID/名称、完整成员名单、每名成员 available/missing/invalid 状态、个人日报来源 ID、需求任务范围 |
| 小组周报 | 小组 ID/名称、当前小组负责人 ID/名称、完整成员名单、每名成员周报状态、个人周报来源 ID、需求任务范围 |
| 部门日报 | 部门 ID/名称、唯一部门负责人、直属小组及各组负责人、直属成员、两组小组日报来源 ID、覆盖与缺失统计 |
| 部门周报 | 部门 ID/名称、唯一部门负责人、直属小组及各组负责人、直属成员、两组小组周报来源 ID、覆盖与缺失统计 |

正文事实核对必须满足：

1. 正文出现“负责人”“成员”“部门”“小组”“来源状态”或数量时，必须与 Context 和公开接口一致；
2. Context 已知负责人时，正文不得写“负责人未提供”“无法确定负责人”或使用其他成员代替；
3. `missing`、`invalid` 只描述报告来源状态，不得写成成员没有工作、没有产出或没有参与；
4. available/missing/invalid 数量、成员总数、小组总数和来源 ID 数量必须能够逐项复算；
5. 需求任务负责人、所属小组、状态、进度和周期范围不得凭正文自行改写；
6. 每份正文必须单独记录“通过/失败”和失败证据。十份中任一份失败，完整链路整体失败；
7. 未打开并读完十份最终正文，不得在文档中写“人工核对通过”。
8. 正文不得出现 Context、Digest 或运行协议的内部字段、枚举值、生成机制和政策解释，包括但不限于 `reports_only`、`dependency_ready`、`report_not_found`、“来源可用性事实”或“本报告基于已保存来源生成”；默认报告也不得把来源覆盖、提交率、缺失报告表格或催报建议作为正文内容。
