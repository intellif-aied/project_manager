## 2. 已实现能力清单

后续方案提出前必须先检查本清单。已有能力不得换名称重复设计。

### 2.1 容量与稳定性

- 服务端读取并投影 Session，Report Agent 不再分页读取超大原文；
- 选择级快照冻结，Agent 只能读取本次报告绑定的来源；
- Digest 单页返回，包含完整性、覆盖率、字节预算和版本信息；
- 大 Session 不再因为完整原文分页而在十分钟运行窗口内超时；
- Digest Worker、ready 状态和失败状态由服务端维护；
- 原始事件、Session 上传游标、usage、metering、Token analytics 不被 Digest 改写。

### 2.2 内容完整性

- 不做 Top-K，不把成果固定限制为 3～5 项；
- 选择的 Session 必须全部进入 coverage；
- 报告期内 canonical highlights 必须满足 `source_count = represented_count`；
- 失败、阻塞、决策、实现、发布和明确待跟进可进入成果投影；
- 服务端保留结构化事实，Agent 负责跨来源语义归并和日报表达；
- 当前 Extractor 会把 `OK`、`Agree` 等少量确认信号挂到前一实质 Work Unit；如未来生产问题涉及完成状态，应将“用户反馈”与“客观完成”分开验证，不应简单删除原信号；
- 空结构、二进制、图片结果、工具大输出、遥测和精确重复属于可确定性技术噪声。

### 2.3 Agent 与 Skill

- Report Skill 决定报告内容、结构和表达；
- 默认 Agent Prompt 只负责运行参数、MCP 范围、凭据和写回协议，不额外裁剪用户内容；
- 手动报告运行和定时报告运行都会在任务提交前修复默认 Agent 的 SkillRef 和报告 MCP；
- 历史 Managed Agent Session 固化创建时的 Agent Version，不做事后改写；
- 新报告任务必须创建使用当前 Agent Version 的新 Session，不得复用旧 Session。

### 2.4 最终报告

- Agent 必须读取完整 Digest coverage 后生成报告；
- 报告必须通过 MCP `write_report_result` 真正回写，平台 `completed` 不能替代回写成功；
- Digest 完整性、Agent 生成质量和正文安全属于三个独立问题，禁止用加强某一层的强制裁剪替代另一层修复；
- 用户可以编辑生成结果，平台不应为了统一格式过度限制用户自定义 Skill。

当前最新阶段为 [第四阶段：默认 Report Skill 结果质量优化](第四阶段-Agent-Skill结果质量优化/README.md)。该阶段冻结 Digest、样本与模型，只优化平台默认 Skill 及其确定性加载协议。十样本真实链路已通过，但内部定位信息的模型遵循度未达到本阶段生产验收线，因此候选未发布生产。

当前开发候选为 [第五阶段：Report Context V1](第五阶段-Report-Context-V1/README.md)。个人日报/周报已在 14.157 实现按 Report Run 构建冻结 Context、一张轻量表和 `get_report_context(run_id)`，B01-B10 真实链路 10/10 通过；团队/部门报告仍保持旧路由。Evidence 回查、对象存储、置信度系统和定制 Agent 开放均不在本期。该能力尚未发布生产，不得描述为生产基线。

当前待设计方案为 [第六阶段：通用 Report Context V1](第六阶段-分层来源与组织覆盖/README.md)。本阶段覆盖个人日报、个人周报、小组日报、小组周报、部门日报和部门周报，由平台按报告类型确定性准备并冻结下级报告、需求、任务、组织覆盖和实际采用的 Session Digest；标准 Agent 每个 Run 只读取一次 Context，不再自由编排基础取数。平台只维护基准线以上的默认 Skill，报告结构、风格和业务侧重点可由用户自定义 Skill 决定。该阶段尚未开发，不得描述为当前能力。

第七阶段 [Digest 样本验证与确定性策略增强](第七阶段-Digest样本验证与确定性策略增强/README.md) 已于 2026-07-21 评审封板，不进入开发。首个样本证明继续按命令种类细化 Digest 容易与 Report Agent/Skill 的语义筛选职责重复，低“命令召回率”也不能直接解释为日报质量问题。因此停止批量 Golden 标注、命令白名单扩充和独立 LLM 归并设计。已有分析仅作历史证据；只有生产故障或可复现报告问题明确归因到 Digest 时，才按最小问题重新立项。

## 4. 当前已知问题

以下问题已识别，但尚未自动等同于下一版本需求：

1. 真实运行返回的 Digest `target_bytes/hard_limit_bytes` 为 64 MiB，而历史产品讨论中的 1 MiB 是用户成本提醒阈值；需要明确“提醒阈值”和“服务端硬上限”是否应为两个不同值。
2. 当前 `resolveUnit` 会把“有文件修改、最后一次验证通过或用户确认”直接推断为 `completed`，没有将修改、验证、Agent 自述和用户反馈拆成独立客观维度。
3. 最终日报可能保留内部版本、路径、主机、迁移和测试细节；应优先通过 Skill 表达规则与模型评测改进，不得回到服务端 Top-K 或大范围语义删除。
4. Web 大上下文确认交互尚未随统一前端版本发布。
5. 当前上传/内容投影会按 cursor 增量推进，但 Digest 为每个 Slice 新建 Extractor；开放 Work Unit 和 `call_id -> work_unit` 不跨 Slice 持久化，一次上传与分批上传的最终客观事实尚无等价保证。
6. Revision Digest 中的详细 `Evidence/Changes/Validations` 在报告期投影时会被简化为 highlights；必须同时验证“Digest 已提取”和“Report Agent 实际可见”，不能混为一个结论。

## 5. 后续优化准入规则

新建 Agent 优化任务前必须回答：

1. 问题发生在上传、Digest、Skill、Agent Prompt、模型生成、MCP 写回还是 Web 展示？
2. 当前生产基线是否已具备相同能力？
3. 是真实缺陷、样本偏差、模型能力问题，还是历史 Session 固化导致的观察误差？
4. 是否会影响 Session 原始数据、Token 统计、上传协议、来源权限或用户自定义 Skill？
5. 是否提供至少三个不同类型的真实 Session 样本，而不是只为单一样本调规则？
6. 是否保持“不做 Top-K、不静默遗漏、允许一定噪音”的产品边界？

未完成以上检查，不得直接修改 Digest 提取规则。

## 6. 新阶段文档要求

后续优化在 `doc/v2/agent优化/` 下新建独立阶段目录，至少包含：

- 问题与真实证据；
- 与本总纲能力矩阵的差异；
- 产品边界与非目标；
- 架构和模块影响；
- 测试样本与人工校对结果；
- 对 Session 上传、Token、MCP、Skill、Agent 和 Web 的兼容性结论；
- 三轮 Review 与发布记录。

任何 Agent 优化如果修改报告 MCP 工具、参数、返回结构、权限、数据路由或写回语义，必须在同一次变更中同步更新 [`doc/v2/mcp文档/README.md`](../mcp文档/README.md)。未同步更新时，该阶段不得标记为完成。

每次完成发布后必须先更新本总纲的生产基线和已实现能力，再归档该阶段文档。

1. 本总纲；
