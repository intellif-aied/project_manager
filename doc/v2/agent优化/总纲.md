## 2. 已实现能力清单

后续方案提出前必须先检查本清单。已有能力不得换名称重复设计。

### 2.1 容量与稳定性

- 服务端读取并投影 Session，Report Agent 不再分页读取超大原文；
- 选择级快照冻结，Agent 只能读取本次报告绑定的来源；
- Digest 单页返回，包含完整性、覆盖率、字节预算和版本信息；
- 大 Session 不再因为完整原文分页而在十分钟运行窗口内超时；
- Digest Worker、ready 状态和失败状态由服务端维护；
- 原始事件、Session 上传游标、usage、metering、Token analytics 不被 Digest 改写。

### 2.2 内容完整性

- 不做 Top-K，不把成果固定限制为 3～5 项；
- 选择的 Session 必须全部进入 coverage；
- 报告期内 canonical highlights 必须满足 `source_count = represented_count`；
- 失败、阻塞、决策、实现、发布和明确待跟进可进入成果投影；
- 服务端保留结构化事实，Agent 负责跨来源语义归并和日报表达；
- 用户的 `OK`、`Agree` 等确认信号可以作为前一实质 Work Unit 的完成度依据，不应简单删除；是否作为独立日报成果由 Agent 结合上下文判断；
- 空结构、二进制、图片结果、工具大输出、遥测和精确重复属于可确定性技术噪声。

### 2.3 Agent 与 Skill

- Report Skill 决定报告内容、结构和表达；
- 默认 Agent Prompt 只负责运行参数、MCP 范围、凭据和写回协议，不额外裁剪用户内容；
- 手动报告运行和定时报告运行都会在任务提交前修复默认 Agent 的 SkillRef 和报告 MCP；
- 历史 Managed Agent Session 固化创建时的 Agent Version，不做事后改写；
- 新报告任务必须创建使用当前 Agent Version 的新 Session，不得复用旧 Session。

### 2.4 最终报告

- Agent 必须读取完整 Digest coverage 后生成报告；
- 报告必须通过 MCP `write_report_result` 真正回写，平台 `completed` 不能替代回写成功；
- Digest 完整性、Agent 生成质量和正文安全属于三个独立问题，禁止用加强某一层的强制裁剪替代另一层修复；
- 用户可以编辑生成结果，平台不应为了统一格式过度限制用户自定义 Skill。

## 4. 当前已知问题

以下问题已识别，但尚未自动等同于下一版本需求：

1. 真实运行返回的 Digest `target_bytes/hard_limit_bytes` 为 64 MiB，而历史产品讨论中的 1 MiB 是用户成本提醒阈值；需要明确“提醒阈值”和“服务端硬上限”是否应为两个不同值。
2. `OK`、`Agree` 等确认信息具有完成度价值，但缺少与前一实质 Work Unit 的显式关联字段，可能被 Agent 表达成“已完成：OK”。
3. 最终日报可能保留内部版本、路径、主机、迁移和测试细节；应优先通过 Skill 表达规则与模型评测改进，不得回到服务端 Top-K 或大范围语义删除。
4. Web 大上下文确认交互尚未随统一前端版本发布。

## 5. 后续优化准入规则

新建 Agent 优化任务前必须回答：

1. 问题发生在上传、Digest、Skill、Agent Prompt、模型生成、MCP 写回还是 Web 展示？
2. 当前生产基线是否已具备相同能力？
3. 是真实缺陷、样本偏差、模型能力问题，还是历史 Session 固化导致的观察误差？
4. 是否会影响 Session 原始数据、Token 统计、上传协议、来源权限或用户自定义 Skill？
5. 是否提供至少三个不同类型的真实 Session 样本，而不是只为单一样本调规则？
6. 是否保持“不做 Top-K、不静默遗漏、允许一定噪音”的产品边界？

未完成以上检查，不得直接修改 Digest 提取规则。

## 6. 新阶段文档要求

后续优化在 `doc/v2/agent优化/` 下新建独立阶段目录，至少包含：

- 问题与真实证据；
- 与本总纲能力矩阵的差异；
- 产品边界与非目标；
- 架构和模块影响；
- 测试样本与人工校对结果；
- 对 Session 上传、Token、MCP、Skill、Agent 和 Web 的兼容性结论；
- 三轮 Review 与发布记录。

每次完成发布后必须先更新本总纲的生产基线和已实现能力，再归档该阶段文档。

1. 本总纲；
