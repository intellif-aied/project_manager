# V1 需求与产品边界

## 1. 当前问题

当前默认 `aida-report` Skill 同时说明 MCP 参数、scope、来源路由、Digest 完整性、事实判断和日报表达。模型需要先完成大量机械路由，才开始语义归并，导致：

- 同一输入可能因模型差异读取不同来源；
- Skill 越来越长且存在重复规则；
- MCP 调用错误容易被误判为日报写作问题；
- 相同 Run 的输入范围不容易复现。

## 2. V1 需求

### 2.1 平台

- 按用户、report_type、period、target、selection 和权限稳定构建 Context；
- 相同冻结 Run 返回相同 `context_hash`；
- 校验 selection、Digest coverage、必要来源和 Context 非空；
- 不按重要性筛选或固定事实数量；
- 构建失败时复用现有 Run 失败状态。

### 2.2 Agent

- 只通过 `get_report_context(run_id)` 读取本次完整上下文；
- 不再自行选择 `get_sessions/get_tasks/get_requirements` 等低层读取工具；
- 继续判断成果、跨 Session 合并、完成度、冲突、失败和阻塞；
- 使用 Report Skill 生成最终 Markdown；
- 继续调用现有 `write_report_result` 写回。

### 2.3 数据

- 原始 Session、Slice 和 Digest 不复制；
- Context 只保存规范化事实、来源引用、版本和 hash；
- 任务、需求等可变对象只保存本次真正使用的字段；
- 不做逐字、逐句和逐事件血缘。

## 3. 完整性优先

V1 的 Context 是低损事实集合，不是服务端写好的报告大纲：

- 所有实质且彼此不同的成果、决策、失败、阻塞和明确待办都必须保留；
- 允许去除确定性技术噪声和合并真实重复项；
- 不做 Top-K；
- 不把十项工作压缩成五项“重点工作”；
- 相互冲突的来源必须同时保留，由 Agent 判断和表达。

## 4. 权限边界

Report Run 冻结用户、报告参数、selection 和允许的数据范围。每次读取 Context 和写回时仍重新校验当前认证和 Run 归属，不能把 run_id 当作凭据。

Agent 不得通过 Context 接口修改：

- 用户或组织范围；
- 报告日期和类型；
- selection；
- Session 或业务来源。

## 5. 非目标

- 不修改 Digest 提取规则；
- 不增加 LLM 预总结层；
- 不开发证据回查；
- 不设计通用低置信度评分；
- 不建设对象存储；
- 不开放定制 Agent；
- 不废弃旧工具；
- 不限制用户自定义 Skill 正文；
- 不增加服务端正文质量门禁。

## 6. V1 验收

1. B01-B10 的实质工作对象 coverage 不降低。
2. 同一冻结 Run 重复读取的 `context_hash` 一致。
3. 默认 Agent 只需一次 Context 读取即可进入生成。
4. Context 不允许越权或扩大来源。
5. Context 构建失败不会启动 Agent。
6. Session、Token、上传和现有报告写回语义不变。
