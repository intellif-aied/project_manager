## 1. 测试目标

使用本机真实 Codex session 数据和四个不同角色账号，验证以下链路：

1. 新版 AIDA CLI 的 session 分页、选择和上传。
2. 首次上传与重复上传的幂等行为。
3. 上传后的解析、索引、指标重建是否完成。
4. 个人 token、成本、未定价状态是否与 session 明细一致。
5. TL/总监的管理范围统计和普通角色的权限边界。
6. 管理排行榜汇总是否等于管理范围总量。

## 3. CLI 实际结果

- 本机发现 152 条 session，默认显示 `1 / 16` 页，每页 10 条。
- 实际执行了页码切换、下一页、上一页、修改每页数量、全选、取消。
- 终端使用 alternate screen 重绘，操作过程中不会持续向终端追加整页内容。
- 首次扫描建立本地索引，后续扫描复用索引并只检查新增或变化的 session。
- 四个账号均使用真实登录、真实 session 选择、真实上传完成。
- 重新上传同一个 session 时，CLI 返回 `SKIP ... unchanged chunks=0`，没有重复提交未变化内容。

- `t02` 管理排行榜中非零成员为 `t03=179,337,382`、`t05=15,532,886`、`t02=12,315,563`、`t01=6,322,878`，合计 `213,508,709`，与管理总量一致；其余管理成员显示 0，不影响合计。

## 6. 后台处理状态

四个目标 session 的 `index_content_chunk`、`parse_usage_chunk`、`rebuild_content_revision`、`rebuild_metrics_revision` job 均为 `completed`，对应 metrics state 均为：

- `status=ready`
- `source_high_water_cursor = active_usage_parsed_cursor`
- `last_error` 为空

因此本轮没有发现“CLI 显示上传成功但后台指标尚未完成”的目标 session。

`t03/t02` 的管理摘要仍显示 `pending_source_count=1`，原因是管理范围包含其他历史 session，其中存在未完成/待处理来源；该 pending 不属于本轮四个目标 session。个人摘要中 `t03` 也会受到其个人历史未定价数据影响，表现为 `partially_priced`，这是数据状态提示，不是本轮上传失败。

## 7. 结论

本轮真实流程通过：

- CLI 分页与交互行为符合预期。
- 四角色真实上传链路完成。
- 重复上传具有幂等性。
- 目标 session 的解析、索引、指标重建完成。
- 精确 session token 与成本明细可对上。
- 普通角色不能越权查看管理统计。
- TL/总监管理统计与排行榜汇总一致。
- 未定价数据没有被伪装成 0 成本。

## 8. 遗留风险与后续测试

1. 本轮使用真实历史 session，无法作为固定 token 金丝雀数据；仍需要用固定 JSONL fixture 执行测试用例方案中的 F01-F15，验证边界和回归。
2. 管理范围仍有 1 个历史 pending source。它不影响本轮目标 session，但正式验收前应单独定位该来源，避免管理页面长期显示 `pending`。
3. 本轮没有发布生产，也没有清理或修改生产数据。
