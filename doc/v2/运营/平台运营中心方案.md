> 本文已按 `fea.0.0.1` 当前代码于 2026-07-15 重新评审。方案只覆盖“用户使用统计”和“运维生产异常监控”，不包含 Bug/反馈工单平台。
>
> 状态：三轮评审通过，等待 `OPS-000` 预检。

配套执行文档：

- `平台运营中心需求文档.md`：产品范围、指标口径和验收需求；
- `平台运营中心架构设计.md`：组件、数据、接口和故障隔离；
- `平台运营中心开发方案.md`：任务卡、文件白名单、Gate 和回退；
- `平台运营中心测试用例.md`：功能、迁移、权限、性能、故障和浏览器用例。

五份文档均位于 `v2/doc/运营/`，不与 `doc/v2` 文档建立依赖。发生冲突时必须先修正文档，不允许实现自行选择更大范围。

## 1. 目标与边界

运营中心只回答两类问题：

1. 用户是否在使用 Aida，主要使用哪些页面和核心功能。
2. 生产环境是否稳定，是否出现服务不可用、接口退化、前端异常或后台任务积压。

```text
运营中心
├─ 用户使用统计
└─ 运维生产异常监控
```

本方案明确不包含：

- AI Session 正文、命令、提示词或工作内容分析；
- 日报、周报、Token 数量、金额等业务内容统计；
- 用户反馈、Bug 工单、人工运营记录或任务管理；
- 全量 DOM 点击、鼠标轨迹、键盘记录、用户行为回放；
- 请求正文、响应正文、Cookie、Authorization、Token 或用户输入采集；
- 因接入运营能力而改变需求、任务、日报、Session、Token 分析等现有业务流程。

页面被访问、按钮动作成功或失败可以统计，但不得读取或分析页面中的业务内容。

## 2. 当前代码基础与本次调整

### 2.1 当前真实基础

| 当前实现 | 对方案的影响 |
| --- | --- |
| 后端为单个 Go/Chi API，业务、后台 worker 共用 PostgreSQL | 运营采集必须旁路、限流，并使用独立受限连接池 |
| MinIO 已是 Session 内容和用量处理的核心依赖 | readiness 必须检查 PostgreSQL 和 MinIO，不能再把 MinIO 描述成可选依赖 |
| API 同进程运行 Managed Agent 调度、运行状态同步、Session 内容投影、Session 用量投影和计量生命周期 worker | 生产监控必须覆盖这些后台链路，不能只监控 Managed Agent |
| `session_processing_jobs` 已保存 Session 任务状态、重试、租约和错误 | 直接聚合现有事实表，不复制每条任务失败，不把运营事件塞进该任务表 |
| 已有 `api/internal/usage`、`session_usage_*` 和 `/token-analytics` | “平台使用行为”不得再使用含义模糊的 `usage` 包或裸表名 |
| 前端使用 React Router、React Query 和统一 Axios 请求层，认证 Token 在 LocalStorage 并通过 Bearer Header 发送 | 页面键复用路由配置；上报使用独立带认证的 transport，不能使用 `sendBeacon` |
| 当前 `/health` 固定返回 200，无 request ID、Error Boundary 和前端全局错误采集 | 这些是新增能力，不能假设已有；第一期也不承诺一次性重构全部后端错误处理 |
| 当前权限是基于角色的 RBAC，没有独立的“运营只读”权限节点 | 第一版固定 `admin only`，不模糊承诺总监单独授权 |

### 2.2 已确定的调整原则

1. Go 模块使用 `api/internal/operations`，数据表使用 `platform_*` 或 `ops_*` 前缀，避免与 AI Session Token usage 混淆。
2. 已存在于 `ai_runs`、`managed_agent_schedules`、`session_processing_jobs` 的失败直接查询聚合，不重复写一份异常事件。
3. HTTP 请求路径只做内存计数和固定桶累加，不同步写运营数据库。
4. 前端事件只进入内存队列，业务操作、路由跳转和错误展示不等待上报。
5. 所有采集、查询、告警和 Webhook 均受功能开关控制，默认关闭并逐步灰度。
6. API 进程不能负责自己的宕机告警；API/Web 可用性由独立轻量探针检查。

### 2.3 迁移基线

当前源码已将历史 `017` 至 `025` 合并为 `017_session_upload_report_source_and_token_analytics.sql`，但共享数据库的 `schema_migrations` 已记录到 `25`。迁移执行器只按版本号判断是否跳过。

因此运营中心首个迁移必须是 `026_operations_center.sql`：

- 不修改已经合并的 `017`；
- 不使用源码目录表面上空缺的 `018` 至 `025`；
- `026` 只新增运营中心独立表，不给现有业务表加触发器，不回填或重写业务数据；
- 开发开始前再次确认没有其他会话占用 `026`；如已占用，Codex 必须停止并汇报，只有用户确认新编号且本文同步更新后才能继续；
- 同时验证“空库执行现有迁移后再执行 026”和“历史库已执行到 25 后执行 026”两条升级路径。

## 3. 用户使用统计

### 3.1 指标口径

日期边界直接复用现有 `api/internal/biztime`，第一期固定按 `Asia/Shanghai` 计算。

| 指标 | 定义 |
| --- | --- |
| DAU | 当日产生至少一个有效 `page_view` 或白名单动作的去重用户数 |
| WAU / MAU | 最近 7 / 30 个自然日的去重活跃用户数，不把每日 DAU 相加 |
| PV | 有效 `page_view` 总数 |
| 活跃团队 / 部门 | 至少有一名活跃用户的去重团队 / 部门数 |
| 新活跃用户 | 首次产生有效 `page_view` 或白名单 action 的用户数；`frontend_error` 不计入 first-seen |
| 页面使用人数 | 访问标准化页面键的去重用户数 |
| 关键动作次数 | 按唯一 `action_id` 的 `started` 计数，不按事件行数计数 |
| 关键动作成功率 | 终态 `success / (success + failure)`，未产生终态的动作单独显示 |

趋势对比使用明确的前一日、前 7 日或前 30 日环比，不使用含义不明确的“同比周期”。

DAU/WAU/MAU 的去重基于轻量的 `platform_user_active_days`，每日每用户最多一条；日聚合同时固化当日滚动 WAU/MAU，保证原始事件清理后仍能查看历史趋势。

为避免长期保存用户-页面/动作轨迹，跨日页面 UV、页面人均访问和动作使用人数只对最近 30 天精确计算。31 至 366 天仍支持汇总、趋势、页面 PV、动作次数和成功率，但上述跨日唯一人数返回 `null` 并明确显示“精确去重仅支持 30 天”；不能把每日 UV 相加伪装成跨周期 UV。

### 3.2 页面键与路由接入

在 `AppRoute` 增加稳定的 `telemetryPageKey` 和可选的 `telemetryDisabled`。创建页、详情页归入所属模块，不在采集器中维护第二套路由正则。

| 页面键 | 覆盖页面 |
| --- | --- |
| `dashboard` | 工作台 |
| `requirements` | 需求列表、创建、详情 |
| `tasks` | 任务列表、创建、详情 |
| `my_work` | 我的工作、添加文档 |
| `sessions` | AI 工作记录页面，仅统计访问，不采集 Session 内容 |
| `daily_reports` | 日报列表和个人/小组/部门详情 |
| `weekly_reports` | 周报 |
| `my_tokens` | 我的 Token 页面，仅统计访问，不采集 Token 数值 |
| `token_analytics` | 团队分析和成员详情，仅统计页面访问 |
| `pricing_management` | 价格管理 |
| `ai_assets` | Skill、MCP、Agent、运行和定时任务相关页面 |
| `organization` | 组织成员和成员编辑 |

`/reports` 归一为 `daily_reports`；隐藏的 `/notifications` 占位页、登录页、403/404 页和运营中心自身不采集。

`PageViewTracker` 放在 `PermissionGuard` 内部，只有登录成功、角色校验通过且路由有页面键时才入队。每次事件带唯一 `client_event_id`，避免 React StrictMode 开发环境重复 effect 造成重复统计；查询参数和动态 ID 不进入事件。

### 3.3 白名单关键动作

第一期只统计能体现平台实际使用的动作。精确注册表以《平台运营中心需求文档》7.4 节为唯一来源，当前固定为：

```text
auth.login / auth.logout
requirement.create / requirement.edit / requirement.status_change
task.create / task.edit / task.status_change
my_work.document_add
daily_report.save / daily_report.submit / daily_report.ai_generate
weekly_report.save / weekly_report.submit / weekly_report.ai_generate
ai_asset.skill_create / ai_asset.mcp_create / ai_asset.agent_create
ai_asset.agent_run / ai_asset.schedule_save
organization.member_add / organization.member_edit / organization.team_create
```

不采集普通查询刷新、列表翻页、筛选、展开、关闭弹窗等噪音动作。开发时使用独立的 `trackAction` 包裹明确列出的白名单 Mutation，只同步执行“入内存队列”的 `started/success/failure`；不修改全局 `MutationCache`，避免所有 Mutation 被隐式纳入。登录和退出由于不完全经过统一 Mutation，单独显式埋点。

动作失败只记录稳定错误类别、`request_id` 和动作键，不记录表单内容。查询 API 的 4xx/5xx 由后端请求指标作为真源，前端不重复上报同一 HTTP 错误。

每次 Mutation 调用在 `onMutate` 前生成一个新的 `action_id`，一次自动重试沿用同一个 ID，用户再次手动操作才生成新 ID。每个 ID 最多有一个 `started` 和一个终态；数据库分别用部分唯一索引约束 started 和终态，保证 `success/failure` 只能二选一。Mutation 最终 resolve/reject 后才写终态，超过 30 分钟仍无终态则标记为“未完成”，但不进入成功率分母。

### 3.4 前端批量上报

前端使用独立 `telemetryTransport`，不能复用当前会在 401 时清理登录态、跳转登录页的普通 `api.request`：

- 平时每 10 秒或累计 20 条触发一次批量发送；
- 内存队列上限 500 条，单批不超过 32 KB，并发固定为 1；
- 页面卸载时使用带 `Authorization` Header 的 `fetch(..., { keepalive: true })`；
- 不使用无法设置 Bearer Header 的 `sendBeacon`，也不把 Token 放入 URL 或请求体；
- 不写 LocalStorage，不弹 Toast，不触发认证副作用，不使用 React Query 自动重试；
- 失败最多在内存中有限重试，队列满时优先丢弃 `page_view`；
- 遥测接口自身失败不得再次产生遥测事件，防止递归。

统一使用已认证的 `POST /api/v1/operations/events/batch`，服务端限制单批条数和 32 KB 请求体。上报接口只接受预定义的页面键、动作键和错误类别。用户、角色、团队、部门以服务端认证和当前组织关系为准；请求一旦携带 `user_id`、角色或组织身份字段即返回 `400`，不能静默忽略。`client_event_id` 建唯一约束保证幂等。

这是面向运营分析的 best-effort 采集：`202` 只表示进入内存队列，不表示已经持久化；API 非正常退出可能丢失尚未 flush 的事件。系统不为追求绝对不丢而在接收路径同步查询数据库。响应中的 `duplicates` 只统计同一批内载荷完全相同的重复 id；跨请求或重启后的历史重复仍可显示为 accepted，由 writer 的数据库唯一约束丢弃并计入 `persisted_duplicates`。管理员页面必须展示 `received/accepted/rejected_full/dropped_low/dropped_high/persisted_duplicates/flush_failed/queue_depth/last_successful_flush_at`，并明确崩溃瞬间的未刷盘数量无法精确还原；因此使用统计是运营口径，不作为结算或审计数据。

### 3.5 用户使用页面

管理员可查看：

- 今日、近 7 天、近 30 天 DAU/WAU/MAU、PV、活跃团队/部门和新活跃用户；
- 页面 PV、UV 和趋势排行；
- 关键动作次数、使用人数、成功率、失败次数和未完成终态数；
- 按角色、团队、部门的聚合分布；
- 每日、每周、每月趋势，可用于阶段总结和述职数据支撑。

不提供个人行为时间线、用户回放或 Session 内容查看。

## 4. 运维生产异常监控

### 4.1 健康与可用性

保留现有 `/health` 兼容行为，新增：

- `/health/live`：只表示 API 进程可响应，不访问数据库；
- `/health/ready`：使用短超时检查 PostgreSQL 和 MinIO，二者任一不可用即未就绪；
- 管理员组件状态接口：展示 PostgreSQL、MinIO、Managed Agent、核心任务队列推断状态和外部探针结果。

组件 API 枚举统一为 `normal/degraded/error/unknown/not_configured/idle`；`not_configured` 只适用于可选 Managed Agent，`idle` 只适用于无待处理任务的队列，两者都不视为故障。Managed Agent 不阻断 readiness；依赖检查结果缓存10至30秒，页面不能每次刷新都直接探测依赖。

通用组件状态口径固定：最近探测成功且无阈值问题为“正常”；服务仍可用但依赖、性能或积压达到警告阈值为“降级”；连续探测失败或达到严重阈值为“异常”；超过两个探测周期没有有效数据或受限事实查询超时为“未知”。状态必须同时显示文字/图标，不能只依赖颜色。

生产 Nginx 当前只代理精确 `/health`，实施新增端点时必须同步允许 `/health/*`，且对外 readiness 只返回总体状态，具体依赖错误仅管理员可见。

### 4.2 独立轻量探针

API 宕机时无法由 API 自己计算和发送告警，因此增加一个独立的小型 `ops-probe` 进程或容器：

- 低频检查 Web 入口、`/health/live` 和 `/health/ready`；
- 自己维护连续失败、恢复和通知冷却状态；
- 可直接发送可用性与恢复 Webhook，不依赖被监控 API；
- 与 API 同机部署可发现 API/Web 容器故障，但不能发现整机掉电或网络完全中断；
- 需要覆盖整机故障时，将同一个探针部署到另一台机器，不引入完整 Prometheus/Loki/Grafana 栈。

探针使用独立共享密钥向 `POST /api/v1/internal/operations/probe-heartbeat` 推送心跳和最近一次状态变化；API 可用时写入运营表，API 不可用时不阻塞探针直接发 Webhook。探针用独立小数据卷原子保存当前 incident、首次失败时间和通知冷却时间，重启后继续原状态；恢复时把完整故障区间补发给 API。管理员页面显示最后心跳，超过两个探测周期则将“探针自身”标为失联。

probe 使用 Bearer 共享密钥，请求体最大 16 KB，固定包含 probe/heartbeat id、1~3 个受控 target check 和可选故障 transition；OPS-302 后才允许补报最多 20 条 delivery attempt。精确 DTO、时间约束和 401/400/413/204/429/202 语义以《架构设计》7.6 为准。

探针落表映射固定：心跳和组件状态写 `ops_component_metric_minutes`；故障区间写 `ops_alert_incidents` 并以 `source_external_id` 幂等；通知尝试写 `ops_alert_deliveries`。`OPS-105` 只实现记录态，禁止发送 Webhook。

### 4.3 API 请求指标

增加全局 `X-Request-ID`，服务端生成并在 CORS 中暴露；前端 `HttpError` 保存它用于关联。指标中间件位于 Recoverer 外层，在请求完成后读取 Chi 路由模板，禁止使用包含动态 ID 的原始 URL。

统计状态码和响应字节时不得缓存响应体。`ResponseWriter` 包装必须使用 Chi 的兼容包装或完整保留 `http.Flusher`、`http.Hijacker`、`http.Pusher`、`io.ReaderFrom` 等可选接口，并为普通 JSON、文件下载、流式响应和连接升级补兼容测试，防止观测中间件改变现有接口行为。

每个 `method + route_template + traffic_class` 统计：

- 请求数、响应字节数；
- 2xx、3xx、4xx、5xx 数量及错误率；
- 总耗时、最大耗时；
- P50、P95、P99；
- 最慢接口和错误最多接口排行。

`traffic_class` 至少区分：

- `web_api`：浏览器交互 API；
- `cli_session_sync`：Session prepare/chunk/finalize 上传；
- `mcp`：MCP 调用；
- `health_probe`：健康检查；
- `operations`：运营中心采集和查询。
- `unmatched`：没有匹配到 Chi route template 的请求。

总览中的“业务 API”不混入健康探针和运营中心自身流量，但这些流量可在独立分类中查看。

业务 API 成功率固定为“非 5xx 有效业务请求数 / 有效业务请求数”，有效业务流量只包含 `web_api/cli_session_sync/mcp`，排除 `health_probe/operations/unmatched`，4xx 单独展示；可用率固定为“成功探测次数 / 计划探测次数”，缺失探测不得从分母剔除。

P50/P95/P99 使用固定延迟桶近似计算，第一版无需引入 Prometheus SDK：

```text
5, 10, 25, 50, 100, 250, 500,
1000, 2000, 3000, 5000, 10000, +Inf ms
```

每分钟保存样本数、`sum_ms`、`max_ms`、`bucket_schema_version` 和完整 `bucket_counts`。跨分钟、日报或月报先合并各桶计数，再计算分位数，禁止对“每分钟 P99”求平均。样本不足时明确显示“样本不足”。

### 4.4 前端和后端异常

前端新增 root Error Boundary、`window.error` 和 `unhandledrejection` 监听，只做短窗指纹去重后入队。前端仅补充：

- React 渲染异常；
- JS 未捕获异常和未处理 Promise；
- 浏览器网络断开、CORS、超时等后端未必能看到的失败；
- 白名单动作的业务语义失败。

大多数业务请求可在统一 Axios 层补充网络失败信息；当前登录、`/auth/me` 和 Session 日志下载仍使用原生 `fetch`，这些入口需要显式接入同一非阻塞错误队列，不能假设 Axios 拦截器可以覆盖。

后端第一期可靠采集 HTTP 状态、路由模板、耗时、响应字节和 request ID。当前 handler 错误返回尚未统一，第一期不为了运营中心批量重构全部 500 返回点，也不承诺自动得到每个 5xx 的数据库根因或堆栈。

5xx 由 OPS-101 在内存中按 `method + route template + status + 固定类别` 做有界指纹累加，只保留次数、首次/最近和一个 sample request id；OPS-102 异步写 error event/group，OPS-104 只读查询。详细根因优先来自现有业务错误字段，容器日志仍作为兜底证据。后端指标中间件不能可靠获得下游认证替换后的用户 Context，因此后端 5xx 的 `affected_users` 允许为空；不为该字段重构认证链。后续可逐步引入统一 `writeError` 和结构化错误码，但不作为运营中心首期前置条件。

### 4.5 后台任务和队列

后台异常优先读取当前事实来源：

| 生产链路 | 事实来源 | 首期指标 |
| --- | --- | --- |
| Managed Agent 执行 | `ai_runs.status/error_message` | 运行数、失败/超时数、最近失败 |
| Managed Agent 定时调度 | `managed_agent_schedules.last_error` 和 `ai_runs` | 启用任务数、触发失败和最近失败；不推断循环心跳 |
| Managed Agent 状态同步 | `ai_runs` 的受限时间窗 | 运行/失败聚合；查询超时标记 partial |
| Session 内容投影 | `session_processing_jobs` 对应 job type | pending/leased/retry_wait/dead、最老等待时间、处理耗时 |
| Session 用量投影 | `session_processing_jobs` 对应 job type | pending/leased/retry_wait/dead、最老等待时间、处理耗时 |
| Session 计量生命周期 | `session_processing_jobs` 对应 job type | pending/leased/retry_wait/dead、最老等待时间、处理耗时 |

`session_processing_jobs` 只作为被监控的业务事实表，不作为运营任务队列。快照必须覆盖当前全部 job type，而不是只写死三个 worker 名称：`index_content_chunk`、`parse_usage_chunk`、`rebuild_content_revision`、`rebuild_metrics_revision`、`build_metering_envelope`、`delete_object` 和 `purge_session`。每 60 秒使用短超时做一次分组快照，只利用现有 status 前导索引查询 pending/leased/retry_wait/dead；V1 不扫描全部 completed 计算吞吐，不增加新的 2 秒轮询，不复制、删除或修改业务任务。

Managed Agent 定时调度必须接入 `main.go` 当前实际启动的 `handler.NewManagedAgentScheduleRunner`，不能误接未被主流程使用的旧 scheduler 实现。

V1 展示“任务队列推断状态”，不把它称为 worker 进程健康：没有待处理任务为 `idle`；存在到期 backlog、重试堆积或过期租约为 `degraded`；存在 dead 为 `error`；快照查询超时为 `unknown`。`ai_runs` 只做低频、限定窗口、短 `statement_timeout` 查询，超时标记 `partial`。V1 不展示无法可靠取得的“最后循环成功时间”。真正的循环观察器另设可选 `OPS-107`，不进入 V1，必须等并行业务完成并单独授权修改 worker。

## 5. 数据与处理架构

```text
浏览器 page_view / 白名单动作 / 前端异常
        └─ 独立静默 transport ─> 有界高低优先级队列 ─┐
                                                        ├─ 单 writer 批量写入独立运营表
API 中间件 ─> 内存计数 + 固定直方图 ─每分钟快照───────┤
                                                        │
现有 ai_runs / schedules / session jobs ─每分钟聚合────┘
                                                        └─ 日聚合 ─> 管理员页面
                                                                    └─ 告警规则 / Webhook

独立 ops-probe ─> Web/API/readiness ─> 独立可用性与恢复 Webhook
```

### 5.1 新增表

| 表 | 用途 |
| --- | --- |
| `platform_interaction_events` | 有限保留期的全部浏览器 page/action/frontend_error；client event 全局幂等，用户+action id 的 started/终态分别唯一 |
| `platform_user_first_seen` | 长期保存用户首次活跃时间，避免原始事件清理后“新用户”失真 |
| `platform_user_active_days` | 每日每用户一条轻量活跃事实，用于准确计算滚动 DAU/WAU/MAU |
| `platform_daily_usage_metrics` | 按天、页面、动作、角色、团队、部门的使用聚合；页面和动作维度互斥，不生成全量立方体 |
| `ops_http_metric_minutes` | 按分钟、进程实例保存可合并的请求计数、状态和延迟直方图；snapshot id 保证重试幂等 |
| `ops_component_metric_minutes` | 依赖、任务队列推断、probe 及采集器自身的分钟快照 |
| `ops_error_events` | 有限保留期的后端 5xx 脱敏样本；前端异常不双写，循环级错误不属于 V1 |
| `ops_error_groups` | 按指纹聚合首次、最近、次数、受影响用户和恢复状态 |
| `ops_daily_metrics` | 长期保存每日可用性、错误、性能和后台任务聚合 |
| `ops_alert_incidents` | 告警生命周期、次数、通知和恢复状态；probe 使用 source_external_id 幂等补报 |
| `ops_alert_deliveries` | Webhook 尝试、结果和重试记录 |

原始事件不承担长期报表职责；每日聚合才是月报、年度复盘和述职数据来源。新表不得通过触发器同步审计现有业务表。

用户活跃日按“当日首次有效事件”固化角色、团队和部门，避免一天内组织变化造成口径漂移。日聚合、告警、简报和清理任务使用 PostgreSQL advisory lock，避免未来多 API 实例重复执行。`026` 不给现有业务事实表增加索引；确有需要时另立 migration 评审。

### 5.2 数据保留默认值

| 数据 | 默认保留期 |
| --- | --- |
| 原始页面和动作事件 | 30 天 |
| 原始异常明细 | 30 天 |
| 分钟请求和组件指标 | 90 天 |
| 用户活跃日事实 | 400 天，历史滚动值同时写入长期日聚合 |
| 每日使用和生产聚合 | 长期保留 |
| 用户 first-seen | 用户存在期间长期保留 |
| 告警事件 | 至少 1 年 |

清理参数可配置。清理任务只在聚合成功后运行，采用小批次、短事务、低峰执行；敏感错误文本不进入长期聚合。

## 6. 告警

### 6.1 初始规则

第一周先收集基线不通知，确认噪音后再启用默认规则：

| 级别 | 初始触发条件 |
| --- | --- |
| 严重 | 独立探针确认 API 或 Web 连续 2 分钟不可用 |
| 严重 | PostgreSQL 或 MinIO readiness 连续 2 分钟失败 |
| 严重 | 核心 Session 任务出现 `dead`，或队列最老等待时间连续超过阈值 |
| 警告 | 单路由 5 分钟 5xx 数量和错误率同时超过阈值，且满足最小样本量 |
| 警告 | 单路由 P99 连续 5 分钟超过阈值，且满足最小样本量 |
| 警告 | 相同前端错误 10 分钟影响多个用户 |
| 警告 | `ai_runs` 失败/超时或 schedule `last_error` 连续达到阈值；任务队列出现 dead、持续 backlog 或过期租约 |
| 警告 | 运营高优先级队列丢弃事件，或连续多个 flush 周期失败 |
| 恢复 | 条件连续恢复后自动关闭并通知 |

阈值全部配置化。低流量接口必须同时判断数量、比率、最小请求数和连续窗口，不能因一次偶发失败刷屏。

V1 不存在 worker 循环失败/心跳告警；这类信号只有未来获授权实施 `OPS-107` 后才能增加。

### 6.2 收敛与通知

告警 evaluator 只读取已持久化且完整的时间窗；`partial/delayed` 窗口不得创建新 incident。同一 `规则 + 组件/路由 + 错误指纹` 只维护一个 incident：

- 未恢复期间合并次数和受影响范围；
- 默认通知冷却 30 分钟；
- 恢复后发送一条恢复通知；
- Webhook 失败只由独立通知队列有限重试，不影响业务请求；
- 第一期只配置一个飞书或企业微信 Webhook。

## 7. 性能与可靠性硬约束

### 7.1 功能开关

新增配置，默认全部为 `false`：

```text
OPERATIONS_ENABLED
OPERATIONS_INTERACTIONS_ENABLED
OPERATIONS_METRICS_ENABLED
OPERATIONS_PERSIST_ENABLED
OPERATIONS_UI_ENABLED
OPERATIONS_ALERTS_ENABLED
OPERATIONS_WEBHOOK_ENABLED
OPERATIONS_PROBE_ENABLED
OPERATIONS_PROBE_NOTIFY_ENABLED
```

各开关使用“配置值”和“生效值”两层，非法组合不能导致业务 API 启动失败，只记录一次告警日志并把子开关降为不生效：

| 配置组合 | 生效行为 |
| --- | --- |
| `ENABLED=false` | 所有子能力生效值均为 false；不开运营连接、不起 goroutine、不启动探针 |
| `METRICS=true, PERSIST=false` | 仅内存 shadow 指标；不写库、不开放生产页 |
| `INTERACTIONS=true, PERSIST=false` | 不接收事件，批量接口返回 `204`；避免返回 202 后必然丢失 |
| `PERSIST=true` 且 `METRICS/INTERACTIONS` 都为 false | `PERSIST` 生效值降为 false，不创建无用途连接 |
| `UI=true` | 仅在 `PERSIST=true` 时生效；production 还要求 `METRICS=true`，usage 还要求 `INTERACTIONS=true` |
| `ALERTS=true` | 仅在 `METRICS=true` 且 `PERSIST=true` 时生效 |
| `WEBHOOK=true` | 只开放通知 transport，本身不发送；告警通知还要求 `ALERTS=true` |
| `PROBE=true` | 仅在总开关开启时启动；`PERSIST=false` 时 API 心跳接收返回 `204` |
| `PROBE_NOTIFY=true` | 仅在 `PROBE=true` 且 `WEBHOOK=true` 时生效，不依赖 API 告警 evaluator |

运营数据库连接失败时，只把 `PERSIST/UI/ALERTS` 降级为 false 并暴露 `partial/disabled`，不能阻止现有 API 启动。

capability 返回生效值而不是原始环境变量：

```text
enabled             = ENABLED
production_enabled  = 当前用户为 admin && UI && METRICS && PERSIST
usage_enabled       = 当前用户为 admin && UI && INTERACTIONS && PERSIST
can_view            = 当前用户为 admin && UI && (production_enabled || usage_enabled)
events_accepting    = ENABLED && INTERACTIONS && PERSIST
brief_enabled       = usage_enabled && production_enabled && 内部 brief provider 已注册
```

`brief_enabled` 不是第十个环境变量；在 `OPS-303` 前或 usage/production 任一侧未生效时固定为 false。简报始终同时包含两侧摘要，不生成“半份简报”。

总开关关闭时，不启动运营 writer、聚合或告警 goroutine，前端不创建采集器、不发送事件，独立探针也不启动。部署顺序固定为：

```text
只建独立表
→ 后端带代码但全部关闭
→ METRICS 内存 shadow
→ PERSIST 异步落库
→ PROBE 仅记录
→ UI 管理员页面
→ INTERACTIONS 用户事件
→ ALERTS 至少 7 天静默
→ WEBHOOK / PROBE_NOTIFY
```

### 7.2 资源隔离

1. 业务请求不等待事件入库、异常入库、聚合或 Webhook。
2. HTTP 中间件只更新内存结构；正常业务请求路径不得执行运营 SQL。
3. 运营写入和运营查询使用独立 `*sql.DB` handle，`MaxOpenConns=1~2`、`MaxIdleConns=1`，短 context timeout；第一期不顺带调整现有业务连接池。
4. 只有一个批量 writer；后端默认低优先级队列 5000 条、高优先级队列 1000 条并允许配置。PostgreSQL 不可用时停止 flush、记录自监控计数并丢弃到上限，不能回压业务。
5. 分钟指标每 60 秒批量写入；后台事实表每 60 秒低频聚合，禁止新增高频 DB poller。
6. 运营查询默认只读预聚合表；唯一例外是≤30天的页面UV/动作人数，可通过独立运营连接、专用索引和2秒 statement timeout读取 `platform_interaction_events`。禁止查询业务原始表或无边界扫描；超时返回 null 并标记 partial。
7. 运营页面使用动态分包；只在页面打开时查询，`staleTime` 为 60 秒，关闭窗口聚焦刷新。
8. 生产监控固定 60 秒刷新，页面不可见时暂停；不得在 MainLayout 或全局 Provider 中常驻轮询运营接口。
9. 运营中心自身的接口、探针和轮询不进入产品使用及业务 API 总览。
10. 任意采集、写库、清理、告警或 Webhook 失败只能降低观测完整度，不能改变业务状态码、响应体或 worker 行为。
11. 路由、页面、动作、流量类别都必须来自有限枚举；404 统一归为 `unmatched`，禁止把原始 URL、错误全文或用户 ID 作为指标维度，防止高基数拖垮内存与数据库。

### 7.3 性能门禁

上线前用同一数据集、同一并发和同一请求组合分别测试“全部关闭”和“采集开启”：

- 业务吞吐回归不超过 2%；
- 业务接口 P95 回归不超过 2% 且绝对增加不超过 2 ms；
- P99 无持续性异常抬升；
- 运营连接数始终不超过配置上限；
- 队列满、运营库写入失败、聚合超时、Webhook 超时的故障注入下，业务接口状态码和响应内容保持一致。

若环境噪音导致单次结果不稳定，至少重复三轮取中位结果；门禁不通过则保持功能开关关闭，不带问题灰度。

## 8. 权限与隐私

- 采集接口仅接受已认证用户，服务端补全用户及组织快照；
- 查询接口统一放在 `/api/v1/admin/operations/*`，复用现有 `AdminOnly`；
- 前端运营路由第一版固定 `roles: ["admin"]`；
- 普通用户不能查询原始事件或聚合数据；
- 当前没有独立运营权限节点，因此本期不开放 director；以后确有需求再单独设计只读权限；
- 错误消息标准化、截断、脱敏；不存正文、用户输入、凭证和 Session/Token 业务内容。

## 9. 产品形态

### 9.1 导航、路由与权限

- 侧边栏只增加一个“运营中心”入口，放在现有“工作空间”分组的管理员入口之后，不增加新的菜单分组；
- 只使用一个前端路由 `/operations`，第一版仅 `admin` 可见；
- 页面内固定两个页签：`usage`（用户使用统计，默认）和 `production`（生产监控）；
- capability 两个页签都未生效时隐藏整个入口；入口一旦显示，始终展示 `usage/production` 两个页签，未生效页签显示明确的“未启用”，不能伪造零值数据；
- 页签及筛选条件写入 URL Query，例如 `/operations?tab=production&range=24h`，刷新、前进后退和复制链接后可恢复；
- 不增加“总览、日志、Bug、反馈、用户画像”等第三个入口。

公共页头固定为：

- 标题、最新数据时间、完整性状态和手动刷新；
- `brief_enabled=true` 时才显示“查看运营简报”，OPS-303 前不渲染该入口；

```text
运营中心
├─ 数据更新时间
├─ 数据完整性：正常 / 延迟 / 部分缺失 / 未启用
├─ 手动刷新
├─ 查看运营简报
└─ 用户使用统计 | 生产监控
```

“查看运营简报”打开只读抽屉，可选择日期并复制简报；不允许编辑、补录或填写人工运营记录。

### 9.2 用户使用统计页签

默认展示近 7 天，日期口径为 `Asia/Shanghai`。

筛选项固定为：

- 今日、近 7 天、近 30 天、自定义日期；
- 部门、团队、角色；
- 日、周、月粒度；
- 自定义日期最多 366 天，不提供用户姓名筛选。

页面从上到下固定为：

| 区域 | 展示内容 | 交互 |
| --- | --- | --- |
| 指标卡片 | DAU、WAU、MAU、PV、活跃团队、活跃部门、新活跃用户、关键动作成功率 | 点击只定位到对应图表或表格 |

| 异常聚合 | 来源、指纹、次数、可用时的影响用户数、首次和最近发生时间、状态 | 点击行打开聚合详情；后端 5xx 影响用户可为空 |

所有下钻统一使用抽屉，不再创建详情页：

- 接口抽屉只展示分钟趋势、状态分布和聚合错误指纹；
- 任务队列抽屉只展示状态数量、等待趋势、最后错误摘要和关联告警；
- 异常抽屉只展示脱敏摘要、次数、受影响人数和样例 `request_id`；
- incident 抽屉只展示触发、通知和恢复时间线；
- 不提供容器日志检索、请求/响应正文、Session 内容或任务正文。

### 9.4 运营简报

每日聚合完成后生成只读简报。简报是运营中心的展示结果，不是第三个业务模块：


### 10.1 V1 最小 API 契约

除批量采集和探针心跳外，所有查询接口都挂在现有 `/api/v1/admin` Route Group 下并复用 `AdminOnly`。响应沿用当前裸 JSON 风格，不新增全局 envelope。

| 方法与路径 | 权限 | 用途 |
| --- | --- | --- |
| `GET /api/v1/operations/capability` | 已认证 | 返回 `enabled/can_view/usage_enabled/production_enabled/events_accepting/brief_enabled` 生效值；用于隐藏菜单、页签、简报和采集器 |
| `POST /api/v1/operations/events/batch` | 已认证 | 接收页面、动作和前端异常批次；服务端补用户和组织信息 |
| `POST /api/v1/internal/operations/probe-heartbeat` | 探针共享密钥 | 接收探针心跳、故障开始和恢复区间 |
| `GET /api/v1/admin/operations/usage/overview` | admin | 指标卡片、趋势、页面/动作排行和组织分布 |
| `GET /api/v1/admin/operations/usage/export` | admin | 导出当前筛选条件下的聚合 CSV |
| `GET /api/v1/admin/operations/production/overview` | admin | 组件状态、HTTP 总览、趋势和活动告警 |
| `GET /api/v1/admin/operations/production/routes` | admin | 分页接口排行；指定 route key 时返回抽屉趋势 |
| `GET /api/v1/admin/operations/production/workers` | admin | 任务队列聚合；指定 `job_type` 时返回抽屉趋势 |
| `GET /api/v1/admin/operations/anomalies` | admin | 分页异常指纹；指定 fingerprint 时返回聚合详情 |
| `GET /api/v1/admin/operations/incidents` | admin | 分页告警；指定 incident id 时返回通知和恢复时间线 |
| `GET /api/v1/admin/operations/daily-brief` | admin | 返回指定日期的结构化只读简报 |

使用统计查询统一接受 `from`、`to`、`department_id`、`team_id`、`role`、`granularity`；生产查询统一接受 `window=1h|6h|24h|7d`、`traffic_class`、`component`、`severity`、`status`。分页使用当前项目的 `page/page_size`，`page_size` 最大 100。

除 CSV 外，所有查询响应都包含：

```text
generated_at      本次响应生成时间
data_through      数据已聚合到什么时间
completeness      normal / delayed / partial / disabled
completeness_note 延迟或缺失原因；正常时为空
```

批量采集请求固定为 schema version 1：

```json
{
  "schema_version": 1,
  "events": [
    {
      "client_event_id": "uuid",
      "occurred_at": "RFC3339",
      "kind": "page_view|action|frontend_error",
      "page_key": "daily_reports",
      "action_key": "daily_report.save",
      "action_id": "uuid",
      "phase": "started|success|failure",
      "duration_ms": 120,
      "error_category": "network|timeout|permission|validation|server|render|unknown",
      "error_name": "TypeError",
      "fingerprint": "sha256",
      "request_id": "string"
    }
  ]
}
```

字段按事件类型选填；每批 1 至 50 条。服务端记录自己的 `received_at`，并拒绝未来超过 5 分钟或历史超过 24 小时的 `occurred_at`；`error_name` 只允许安全名称且最长 64 字符。服务端必须拒绝未登记枚举。请求中禁止出现 `user_id`、角色、组织身份、用户名、原始 URL、查询参数、表单值、错误消息全文、stack、请求/响应正文、Session 内容或 Token 数据。

队列优先级固定：`page_view` 为低优先级，`action/frontend_error` 为高优先级。前端先发送高优先级批次，同一批不得混合优先级。服务端整批原子接收，不允许部分成功：

| 场景 | 状态码 | 响应/行为 |
| --- | --- | --- |
| 未认证 | `401` | 不处理 |
| 非法字段、枚举、时钟、身份字段或混合优先级 | `400` | 不入队 |
| 请求体超过 32 KB | `413` | 不解析、不入队 |
| `events_accepting=false` | `204` | 不入队 |
| 队列容量不足 | `429` | 整批不入队 |
| 有效新事件或幂等重试 | `202` | `{received, accepted, duplicates}`；duplicates 仅为同批相同载荷重复，历史重复可能先入队再由数据库幂等丢弃 |

不提供原始事件查询、删除、人工关闭告警或人工编辑简报的 API。

同批相同 `client_event_id` 但载荷不同视为非法并返回 400。`received` 是输入条数，`duplicates` 是同批重复条数，`accepted` 是实际原子进入内存队列的唯一事件数；容量判断只针对唯一事件。跨请求历史幂等由 `client_event_id` 唯一约束和 `ON CONFLICT DO NOTHING` 保证，不允许为了精确响应计数增加同步 SQL。

### 10.4 阶段停止门

| Gate | 必须满足 | 未通过时 |
| --- | --- | --- |

### 10.5 迁移和部署顺序

1. `026` 一旦在任何共享环境执行即冻结，后续修改只能新建 `027+`；
2. API 启动会自动执行迁移，因此“加入 026”和“rebuild/redeploy 157 API”是两个独立授权动作；
3. ops-probe 使用独立 compose profile，默认 `docker compose up` 不启动；
4. 生产首次部署所有开关为 false，随后按 `METRICS → PERSIST → PROBE（仅记录）→ UI → INTERACTIONS → ALERTS → WEBHOOK/PROBE_NOTIFY` 分步开启；
5. 任一阶段失败只关闭对应开关，不回滚或修改业务数据；
6. Prometheus、Loki、Grafana 只作为未来规模化选项，不属于任何当前 Task ID。

## 12. 验收标准

- 侧边栏只有一个“运营中心”入口，页面只有 `usage/production` 两个页签，刷新和复制 URL 后状态可恢复；

- 管理员能查看 DAU/WAU/MAU、PV、活跃组织、页面排行和关键动作成功率；
- 使用统计只能下钻到聚合趋势，导出文件只包含当前筛选下的聚合数据；
- 管理员能查看按流量类型和路由模板聚合的请求量、错误率、P50/P95/P99；
- 能看到 PostgreSQL、MinIO、Web/API、Managed Agent 和核心任务队列推断状态，不虚构 worker 心跳；
- 能查看前端异常、通用 5xx、Agent 失败及 Session 任务 pending/retry_wait/dead 聚合；
- 独立探针能在 API/Web 不可用时告警，并在恢复后发送恢复通知；
- 运营简报可按日期查看和复制，但不能编辑、补录或形成工单；
- 分位数由可合并直方图计算，低样本量不误导、不误报；
- 原始事件按默认保留期清理，每日快照可长期查询；
- 全部功能可独立开关并按既定顺序灰度；
- 管理员能看到采集 received/accepted/rejected/dropped/flush 状态，并能识别数据是否完整；
- 业务请求路径没有运营 SQL，运营连接池不超过 1 至 2 个连接；
- 开启采集后的吞吐和 P95 满足性能门禁；
- 队列满、运营库故障、探针故障和 Webhook 超时不会改变现有业务接口、页面交互或后台 worker 行为。

## 14. 评审结论

方案已经同时定义产品形态、最小 API、文件边界、任务卡和停止门，可以作为后续 Codex 开发的唯一运营中心主方案。最终产品固定为一个入口、两个页签和一个只读简报抽屉。

与旧版相比，最关键的变化是：

1. 迁移从 `026` 开始并兼容合并后的迁移历史；
2. 平台交互统计与现有 Session Token usage 完全分名；
3. 生产监控覆盖当前新增的 Session 投影和计量任务队列事实，但不虚构 worker 进程健康；
4. 复用现有后台事实表，不重复写失败记录；
5. 前端改用带 Bearer Header 的独立 keepalive transport；
6. 增加独立可用性探针，避免 API 宕机后无人告警；
7. 通过默认关闭、独立连接池、有限队列、动态分包和量化压测门禁保护现有平台；
8. 通过 `OPS-*` 单任务执行、文件白名单和 `G0-G4` 停止门防止 Codex 横向扩展。

开始编码时必须先单独执行 `OPS-000`。只有预检通过后才能进入 `OPS-001`，不允许直接一次性实现迁移、中间件、页面、埋点、探针和告警。
