# 平台运营中心需求文档

> 版本：V1.0  
> 状态：三轮评审通过，等待 `OPS-000` 预检  
> 适用分支基线：`fea.0.0.1`  
> 统计时区：`Asia/Shanghai`  
> 主方案：`平台运营中心方案.md`

## 1. 文档目的

本文定义平台运营中心 V1 的产品范围、用户角色、页面形态、指标口径、功能需求、非功能需求和验收边界，是产品行为的需求源。

配套文档：

- `平台运营中心架构设计.md`：说明系统如何实现；
- `平台运营中心开发方案.md`：说明按什么任务顺序实施；
- `平台运营中心测试用例.md`：说明如何证明需求已满足。

文档发生冲突时，先停止开发并修订文档，不允许 Codex 自行选择更大范围。

## 2. 背景与目标

当前平台无法直接回答：

1. 用户每天是否在使用平台，主要使用哪些页面和核心功能；
2. 生产环境是否稳定，接口是否退化，前端、依赖和后台任务是否出现异常；
3. 当负责人询问平台运营情况时，是否能快速提供可复用的日、周、月数据。

V1 目标：

- 提供可信的用户使用统计，不分析用户业务内容；
- 提供轻量的生产异常监控和 P50/P95/P99；
- 自动形成只读运营简报和聚合导出；
- 所有采集和查询均为旁路能力，不影响现有业务请求和 worker；
- 支持分阶段关闭、灰度、回退和数据完整性说明。

## 3. 产品边界

运营中心只包含：

```text
运营中心
├─ 用户使用统计
└─ 生产监控
```

V1 明确不做：

- Bug、反馈、工单、人工运营记录；
- 容器日志检索或完整日志平台；
- 用户画像、个人行为时间线、用户回放；
- 全量 DOM 点击、鼠标轨迹、键盘记录；
- AI Session 正文、命令、Prompt、任务正文或运行输出分析；
- 日报、周报正文和 Token 数量、金额等业务内容分析；
- 请求正文、响应正文、原始 URL、查询参数、Cookie、Authorization 或凭证采集；
- Prometheus、Loki、Grafana 等完整可观测性平台；
- 为运营中心改变现有业务流程、权限语义、worker 重试或数据库连接池。

## 4. 用户与权限

| 角色 | V1 权限 |
| --- | --- |
| `admin` | 查看两个页签、抽屉、简报和聚合 CSV |
| `director` | 不开放；后续若需要必须新增明确的只读权限模型 |
| 其他已认证角色 | 可在采集开启时上报自己的白名单事件，不能查询运营数据 |
| 未认证用户 | 不能上报或查询；登录成功事件在认证建立后上报 |
| 独立探针 | 只能使用独立共享密钥写入 probe heartbeat，不能调用管理员查询 |

前端隐藏不等于授权。所有管理员查询必须由后端 `AdminOnly` 再次校验。

## 5. 信息架构

### 5.1 导航

- 侧边栏只增加一个“运营中心”入口；
- 入口放在现有“工作空间”分组的管理员入口之后，不增加新菜单分组；
- 只增加一个路由 `/operations`；
- 页面内只有 `usage` 和 `production` 两个页签；
- 默认页签为 `usage`；
- 页签和筛选状态写入 URL Query；
- 两个页签都未启用时隐藏整个入口；入口一旦显示，始终展示两个页签，未启用页签显示明确状态而不是零值数据。

### 5.2 公共页头

公共页头包含：

- 标题“运营中心”；
- 最新数据时间；
- 数据完整性状态；
- 手动刷新；
- `brief_enabled=true` 时显示“查看运营简报”按钮；未生效前隐藏，不显示不可用的空抽屉；
- 两个页签。

数据完整性只有四种状态：

| 状态 | 含义 |
| --- | --- |
| `normal` | 数据已经按预期聚合 |
| `delayed` | 最新批次或聚合尚未完成 |
| `partial` | 发生队列拒绝、丢弃或写入失败 |
| `disabled` | 对应功能开关未生效 |

## 6. 指标口径

| 指标 | 口径 |
| --- | --- |
| DAU | 当日产生有效 page view 或白名单动作的去重用户 |
| WAU / MAU | 截至选择结束日，最近 7 / 30 个自然日的去重活跃用户 |
| PV | 有效 page view 数量 |
| 新活跃用户 | 首次产生有效 page view 或白名单 action 的用户；frontend_error 不计入活跃资格 |
| 活跃团队 / 部门 | 统计周期内至少有一名活跃用户的去重组织 |
| 页面 UV | 访问标准化页面键的去重用户 |
| 关键动作次数 | 唯一 `action_id` 的 started 数量 |
| 关键动作成功率 | `success / (success + failure)`；未完成不进入分母 |
| API 成功率 | 非 5xx 有效业务请求数 / 有效业务请求数；分母只含 `web_api/cli_session_sync/mcp`，排除 `health_probe/operations/unmatched`，4xx 单独展示 |
| P50/P95/P99 | 从所选周期内合并后的固定直方图桶近似计算 |
| 可用率 | 成功探测次数 / 计划探测次数；缺失探测不能从分母剔除 |

DAU/WAU/MAU 不得通过每日人数相加计算。跨周期分位数不得对“每分钟 P99”求平均。

精确跨日去重边界固定为 30 天：原始事件保留 30 天，`platform_user_active_days` 只保留平台级每日活跃和组织快照，不长期保存“用户-页面/动作”轨迹。查询范围 31~366 天时仍返回汇总、每日/周/月趋势、页面 PV 和动作次数，但页面 `UV/人均访问`、动作 `使用人数` 返回 `null`，页面显示“精确去重仅支持 30 天”。这不是数据丢失，不标记为 partial。

| ID | 优先级 | 需求 | 验收摘要 |
| --- | --- | --- | --- |
| `OC-OPS-001` | P0 | 默认展示最近 24 小时 | 支持 1h、6h、24h、7d |
| `OC-OPS-002` | P0 | 每 60 秒自动刷新 | 页面不可见时暂停，支持手动刷新 |

| `OC-OPS-005` | P0 | 展示请求量、5xx、P95/P99 趋势 | 可按 traffic class 过滤 |

| `OC-OPS-009` | P1 | 展示告警 incident | 包含级别、对象、持续时间、通知和恢复状态 |
| `OC-OPS-010` | P1 | 接口、worker、异常、incident 使用统一抽屉下钻 | 不增加详情页或日志查看器 |
| `OC-OPS-011` | P0 | 保留 `/health` 并新增 live/ready | PostgreSQL、MinIO 决定 ready；Managed Agent/worker lag 不阻断 |
| `OC-OPS-012` | P0 | API/Web 宕机由独立探针发现 | 探针不依赖被监控 API 发送可用性通知 |

组件状态统一判定：

| 状态 | 判定 |
| --- | --- |
| 正常 | API `normal`；最近探测成功，且错误、延迟和 backlog 未达到警告阈值 |
| 降级 | API `degraded`；组件仍可用，但依赖、性能、失败率或 backlog 达到警告阈值 |
| 异常 | API `error`；连续探测失败或达到严重告警阈值 |
| 未知 | API `unknown`；超过两个计划探测周期没有有效样本 |
| 未配置 | API `not_configured`；仅适用于可选 Managed Agent，不视为故障 |
| 空闲 | API `idle`；仅适用于没有待处理任务的队列，不视为故障 |

任务队列的四态映射固定为：无待处理任务为 `idle`；出现到期 backlog、重试堆积或过期租约为 `degraded`；存在 dead 为 `error`；事实快照查询超时为 `unknown`。这是队列事实推断，不代表 worker 循环存活。真正的循环观察器不属于 V1。

### 7.5 对外能力契约

capability 至少返回：

```text
enabled
can_view
usage_enabled
production_enabled
events_accepting
brief_enabled
```

`brief_enabled` 在 OPS-303 前或 usage/production 任一能力未生效时固定为 false；它不增加环境变量，V1 不生成部分简报。管理员查询接口、参数、响应字段、单位、空值、排序和错误码以《架构设计》第7节为准。

### 7.5 告警与简报

| ID | 优先级 | 需求 | 验收摘要 |
| --- | --- | --- | --- |
| `OC-ALT-001` | P1 | 阈值同时使用数量、比例、样本量和连续窗口 | 低流量单次错误不告警 |
| `OC-ALT-002` | P1 | 相同规则、对象和指纹合并为一个 incident | 未恢复期间只累加次数和影响范围 |
| `OC-ALT-003` | P1 | 告警恢复后自动关闭并通知 | 不支持人工关闭或工单流转 |
| `OC-ALT-004` | P1 | Webhook 有冷却和有限重试 | 失败不影响业务请求 |
| `OC-ALT-005` | P1 | 每日生成结构化运营简报 | 次日 02:00 前生成；只读、可复制、可选 Webhook 推送 |

告警只允许基于已持久化且完整的时间窗计算；`partial/delayed` 时间窗不能创建新 incident。

## 8. 非功能需求

| ID | 类别 | 要求 |
| --- | --- | --- |
| `OC-NFR-001` | 性能 | 正常业务请求路径不得执行运营 SQL |
| `OC-NFR-002` | 性能 | 开启采集后业务吞吐回归不超过 2% |
| `OC-NFR-003` | 性能 | 业务 P95 回归不超过 2%，且绝对增加不超过 2 ms |
| `OC-NFR-004` | 资源 | 运营数据库 handle 最大连接数 1 至 2，单 writer |
| `OC-NFR-005` | 可靠性 | 队列满、运营库失败、聚合或 Webhook 超时不能改变业务响应或 worker 行为 |
| `OC-NFR-006` | 灰度 | 总开关及 metrics、persist、UI、interactions、alerts、webhook、probe、probe notify 九个开关均默认关闭 |
| `OC-NFR-007` | 隐私 | 不存正文、凭证、原始 URL、message/stack、个人行为时间线 |
| `OC-NFR-008` | 可维护性 | 页面键、动作键、traffic class、组件和错误类别使用有限枚举 |
| `OC-NFR-009` | 查询 | 默认只查预聚合表；仅≤30天页面UV/动作人数允许通过独立运营连接、索引和2秒timeout查询运营原始表；禁止查询业务原始表 |
| `OC-NFR-010` | 前端 | 运营页面动态分包；不新增图表库或状态框架；生产轮询固定 60 秒且页面隐藏暂停 |
| `OC-NFR-011` | 兼容 | ResponseWriter 包装保留 Flusher/Hijacker/Pusher/ReaderFrom 等接口 |
| `OC-NFR-012` | 数据 | 原始交互/异常 30 天、分钟指标 90 天、活跃日 400 天、日聚合长期、告警至少 1 年 |
| `OC-NFR-013` | 可访问性 | 状态不能只依赖颜色，图表同时提供数值、表格或可读摘要 |

## 9. 数据与隐私规则

允许保存：

- 服务端 user id 和当时角色/组织快照；
- 标准化 page/action/component/route template；
- 时间、结果、耗时、状态码、request id；
- 受控 error category、error name 和不可逆 fingerprint；
- 聚合人数、次数、分位数、队列状态和 incident 生命周期。

禁止保存：

- 用户名作为指标维度或导出内容；
- Session/日报/周报/任务正文；
- Token 内容、金额和原始 usage 载荷；
- Prompt、命令、Agent 输入输出；
- HTTP 请求/响应正文、Cookie、Authorization；
- 原始异常 message、stack 或任意表单值。

## 10. 分期范围

| 阶段 | 产品结果 |
| --- | --- |
| P0 安全壳 | 表、开关、独立连接和关闭态能力，不向用户展示 |
| P1 生产可见性 | production 页签、健康、请求指标、worker/队列、探针 |
| P2 使用统计 | usage 页签、page view、动作、前端异常、聚合 CSV |
| P3 告警与简报 | 静默基线、incident、Webhook、只读简报 |
| 未来选项 | 多实例外部指标/日志平台；不属于 V1 |

## 11. 产品验收出口

V1 只有同时满足以下条件才算完成：

1. 一个菜单、一个路由、两个页签和一个只读简报抽屉；
2. admin 权限、URL 状态、空态/延迟/缺失状态均通过浏览器验收；
3. 使用统计口径通过独立样本对账；
4. P50/P95/P99 由可合并直方图计算；
5. 当前后台任务队列推断状态、依赖、异常和 incident 可见；
6. 聚合 CSV 不包含个人或业务内容；
7. 功能开关和停止门能够独立灰度；
8. 两轮性能门禁均通过；
9. 故障注入只降低观测完整度，不影响业务；
10. 不出现本文明确排除的第三模块或采集项。

## 12. 需求变更规则

- 新增页面、角色、采集字段、通知通道或第三方组件属于需求变更；
- 修改 page/action 枚举必须同步需求、架构、开发和测试四份文档；
- 任何涉及业务表、worker 状态机、Session 内容或用户个人行为的需求必须单独评审；
- Codex 不能根据实现便利自行放宽隐私、性能或范围边界。
