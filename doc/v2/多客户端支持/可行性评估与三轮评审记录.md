# Aida 多客户端支持可行性评估与三轮评审记录

> 调研与评审日期：2026-07-15  
> 评审对象：同目录 `产品需求.md`、`开发方案.md`、`测试与验收方案.md`。  
> 评审性质：基于当前 Aida 代码、既有产品口径和各客户端官方资料的三轮结构化自审；不是第三方厂商兼容性承诺。  
> 总结：方案可行，建议批准阶段 0/1；不建议一次性承诺所有客户端的完整 Token/成本能力。

## 1. 最终结论

### 1.1 是否可行

可行，但要拆成三种结论：

1. **OpenCode、Kimi Code：可作为第一批正式开发对象。** 两者都有官方机器可读 Session 来源和稳定 Session 身份入口，适合先实现报告内容能力。
2. **OpenClaw、harness.lol：可开发报告内容能力，但应第二批发布。** OpenClaw 隐私范围更广；Harness 是包装器，存在与底层原生 Session 重复的问题，首期都不应导入 Token/成本。
3. **ZCode：技术上可能可接，但目前不满足正式开发依据。** 官方资料确认本地会话和本地用量存在，却没有公开稳定 Session 正文导出协议；只能先获取官方格式或版本样本，不能把诊断日志或逆向私有数据库作为生产方案。

因此，“支持其他客户端”是可行需求；“一次性让所有客户端与 Claude/Codex 在内容、Token、成本上完全等价”当前不可行，也没有必要。

### 1.2 推荐范围

批准：

- 统一 adapter 接口；
- Aida Canonical Event v1；
- 服务端 `source_format` 分发；
- OpenCode、Kimi Code `content_capability=report`；
- Token 能力独立验收；
- OpenClaw、Harness 第二批 report；
- ZCode 保留门禁。

不批准：

- 服务端为每个客户端直接解析一套原生格式；
- 首期开放任意动态 adapter 插件；
- 直接读取所有第三方内部数据库；
- 用会话总量或第三方金额伪装精确 Token/成本；
- 在没有真实默认 Agent 回归时发布生产。

## 2. Aida 当前代码证据

| 代码位置 | 当前事实 | 对方案的影响 |
|---|---|---|
| `daemon/session_index.go` | `collectLocalSessionFiles` 只扫描 Claude/Codex 两个目录 | 需要 adapter registry，扫描层是主要改动点 |
| `daemon/device_client.go` | 已有共用 `SessionInfo`、活动切片和上传 metadata | 可复用内存模型，但需解除两客户端默认值 |
| `daemon/codex_scan.go` | Codex 已有独立原生 parser | 证明 adapter 拆分符合现有演进方向 |
| `daemon/session_sync_client.go` | 已有 Prepare/Chunk/Finalize、prefix hash、断点状态 | 新客户端不需要新上传 API |
| `api/db/migrations/017_session_upload_report_source_and_token_analytics.sql` | 已有 generation、chunk、projection、slice、job | snapshot 重写可走 generation rebuild |
| `api/internal/sessionsync/content_parser.go` | 内容 parser 要求 JSONL 顶层 type/timestamp | Canonical Event 可以复用现有投影架构 |
| `api/internal/usage/provider_parser.go` | 只支持 `claude_code`、`codex` | 必须把来源格式和客户端类型解耦；Token 不能自动继承 |
| `api/internal/reportsource/service.go` | 报告来源按 active generation、projection 和 slice 读取 | 新客户端标准化后对 MCP/Skill/Agent 可透明 |
| Session 唯一约束 | `(user_id, agent_type, session_ref)` | 已能隔离不同用户和不同客户端相同 ID |

代码层没有阻止新增客户端的根本障碍。最大风险不是上传，而是第三方格式变化、usage 语义和隐私边界。

## 3. 官方资料证据

以下资料于 2026-07-15 核对。第三方产品变化快，进入开发和发布时必须重新确认版本。

### 3.1 OpenCode

官方依据：

- [OpenCode CLI 文档](https://dev.opencode.ai/docs/cli/)：提供 `opencode session list --format json`、`opencode export [sessionID]`，导出格式为 JSON；同时提供 `--sanitize`。
- [OpenCode 官方仓库](https://github.com/anomalyco/opencode)：开源，可在格式变化时通过版本源码和 fixture 定位。

判断：

- Session 发现：有稳定命令。
- Session 身份：有正式 Session ID。
- 正文来源：有官方 JSON export。
- 增量：export 是快照，需要本地 canonical spool 做前缀比较和 rebuild。
- Token：官方有 stats，但是否能从 export 获得可逐事件去重的完整 usage，必须用真实样本验证。
- 可行性：高，第一批。

### 3.2 Kimi Code

官方依据：

- [Kimi Code 数据位置](https://www.kimi.com/code/docs/en/kimi-code-cli/configuration/data-locations.html)：明确 `$KIMI_CODE_HOME/session_index.jsonl`、`sessions/<workDirKey>/<sessionId>/state.json`、`agents/main/wire.jsonl` 和子 Agent wire；同时明确 credentials 和 logs 的位置。
- [Kimi 命令参考](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/kimi-command)：提供 `kimi export`，但默认导出可能包含全局诊断日志；非交互模式也支持 `stream-json`。
- [Kimi Code 官方仓库](https://github.com/MoonshotAI/kimi-code)：开源，可建立版本化 fixture。

判断：

- Session 发现：有官方 index。
- Session 身份：sessionId 稳定。
- 正文来源：wire.jsonl 是官方完整通信记录。
- 隐私：不能直接使用包含全局日志的 debug ZIP；应只读 index/state/wire，并排除 credentials/logs。
- Token：需要核对 wire usage 与 App Usage；不能因 UI 有用量统计就直接认为逐事件可对账。
- 可行性：高，第一批。

### 3.3 OpenClaw

官方依据：

- [OpenClaw Sessions CLI](https://docs.openclaw.ai/cli/sessions)：提供 `openclaw sessions --all-agents --json`、trajectory tail 和 `export-trajectory`；Session 可能来自多 Agent、多渠道，当前存储也涉及 SQLite/legacy 数据。
- [OpenClaw 官方仓库](https://github.com/openclaw/openclaw)：开源。

判断：

- Session 发现和导出：有官方 CLI，避免直读 SQLite。
- Session key：稳定但可能含渠道和对端信息，日志/路径必须脱敏。
- 内容：不一定都是编码工作，可能包括私人聊天。
- Token：官方存在模型/成本能力，但首期没有必要引入，先 report。
- 可行性：中高，第二批；`aida upload --all` 默认排除。

### 3.4 harness.lol

官方依据：

- [harness 产品说明](https://www.harness.lol/docs)：它包装 Claude Code、Codex、OpenCode、Cursor 并输出统一 NDJSON。
- [harness Event Stream](https://www.harness.lol/docs/reference/events)：定义 SessionStart、Message、ToolStart、ToolEnd、Result、Error 等事件，并说明每次运行自动记录到本地 Session NDJSON。
- [harness 官方仓库](https://github.com/ayshptk/harness-cli)：README 还列出 UsageDelta；这与文档“7 类事件”存在版本差异。

判断：

- 内容接入：NDJSON 已接近 Aida canonical，成本低。
- 身份：有 harness Session ID。
- 重复：它会启动底层 Agent，底层客户端通常也保存原生 Session；两份记录可能是同一次工作。
- Token：官方文档与仓库对 UsageDelta 的描述有漂移；首期不导入。
- 平台路径：文档给出 `~/.local/share/harness/sessions`，其他 OS 必须真实验证后再宣称支持。
- 可行性：中高，第二批 report。

### 3.5 ZCode

官方依据：

- [ZCode 安装文档](https://zcode.z.ai/en/docs/install)：支持数据迁移和本地桌面客户端，但没有公开 Session export 命令。
- [ZCode Usage Stats](https://zcode.z.ai/en/docs/usage-stats)：明确 App Usage 读取当前设备的本地 Session 记录。
- [ZCode Feedback](https://zcode.z.ai/en/docs/feedback)：反馈可携带 Session file path，提供“Export Logs”，但该导出是故障诊断用途。

判断：

- 存在本地 Session：可以确认。
- 稳定格式：无法从官方资料确认。
- Export Logs：可能包含诊断和跨任务信息，不能视为业务 Session API。
- 可行性：有条件；取得官方格式或版本样本前不正式开发。

### 3.6 “Harness”名称歧义

如果用户所说的是 Harness.io 而不是 harness.lol，官方 [Harness AI Chat History](https://developer.harness.io/docs/platform/harness-ai/memory-chat-history/) 描述的是服务端托管聊天记录和保留策略，没有提供本地 Session 扫描契约。这需要单独的云端 API、授权和数据合规方案，不应混入本需求。

## 4. 可行性矩阵

| 客户端 | 机器可读来源 | 稳定 Session ID | 报告内容 | 精确 Token | 主要风险 | 建议 |
|---|---|---|---|---|---|---|
| OpenCode | 官方 list/export JSON | 是 | 高 | 待样本 | export 快照和版本变化 | 第一批 report |
| Kimi Code | 官方 index/state/wire | 是 | 高 | 待样本 | wire 版本、日志/凭据边界 | 第一批 report |
| OpenClaw | 官方 list/export trajectory | 是 | 中高 | 首期不做 | 私人渠道、多 Agent、脱敏 | 第二批 report |
| harness.lol | 官方统一 NDJSON | 是 | 高 | 首期不做 | 底层 Session 重复、事件版本漂移 | 第二批 report |
| ZCode | 仅确认本地记录存在 | 未获契约 | 待定 | 不做 | 私有格式、诊断日志 | 保持 gated |
| Harness.io | 云端 Chat History | 云端 | 另案评估 | 另案评估 | OAuth/API/合规 | 不在本需求 |

## 5. 相对工作量

| 工作包 | 相对规模 | 说明 |

| 服务端 source_format + canonical content/usage | M-L | 复用现有 sync/job，但需迁移、兼容和去重 |

## 6. 第一轮评审：事实与可行性

**评审目标**：确认客户端事实、Aida 现状和总体方向是否成立。

**检查方法**：

- 核对上述官方文档和官方仓库；
- 阅读 Aida CLI 扫描/上传、服务端 content/usage parser、report source；
- 区分“本地记录存在”“可稳定导出”“可精确统计 Token”。

**发现与修订**：

| 编号 | 发现 | 修订 |
|---|---|---|
| R1-01 | 初始需求容易被理解为五个客户端一次性完全等价 | 改为内容与 usage 两个能力维度，逐客户端发布 |
| R1-02 | ZCode 只有本地记录和诊断日志证据，没有稳定正文导出契约 | 降为 gated Spike，不列入首期正式支持 |
| R1-03 | Harness 名称同时可能指 harness.lol 和 Harness.io | 文档明确本需求默认 harness.lol，Harness.io 另案 |
| R1-04 | Harness 文档与仓库对 UsageDelta 的事件数量描述不同 | 首期 report-only，不依据不稳定 usage 计算成本 |
| R1-05 | Aida content 通路可扩展，但 usage parser 只支持两种 Provider | 确定 `source_format` 与 `agent_type` 解耦 |
| R1-06 | Canonical usage 的 input/cache 原始语义可能因客户端不同 | 改为 uncached/cache-read/cache-create/output 归一化字段和固定总量公式 |

**结论**：通过。总体方案可行，但必须维持分阶段和 ZCode 门禁。

## 7. 第二轮评审：产品、架构、测试一致性

**评审目标**：确认三份文档没有相互冲突，并与现有 Session/报告口径一致。

**检查方法**：

- 自动提取 `MC-PRD-001` 至 `MC-PRD-012`，对比测试追踪矩阵；
- 搜索 `client_type/agent_type`、Token 能力、`--all`、默认 Agent、ZCode 等关键术语；
- 对照现有 generation 激活和 report source 查询条件。

**证据**：12 个需求编号全部出现在测试追踪矩阵，自动检查结果为 `requirements=12 traced=12 terminology=consistent`。

**发现与修订**：

| 编号 | 发现 | 修订 |
|---|---|---|
| R2-01 | 初稿同时提出 `client_type` 和现有 `agent_type`，会制造长期重复字段 | 普通 API 继续用 `agent_type` 表示客户端，只新增必要的 usage capability |
| R2-02 | 初稿把报告与 Token 状态写成一条线性等级 | 拆为 `content_capability` 与 `usage_capability` 两个正交维度 |
| R2-03 | rebuild finalize 后，新 generation 已活动但 projection 可能尚未 ready | 测试改为允许该 Session 短暂不可选，禁止新旧混合，不错误承诺旧候选持续可用 |
| R2-04 | 仅强调默认 Agent，缺少直接 MCP 的同 selection 对照 | 增加默认 Agent 通过后的直接 MCP 对照，但明确不能替代 Agent |
| R2-05 | Stage 2 客户端没有明确重复默认 Agent 门禁 | 增加 OpenClaw/Harness 个人日报、周报、混合来源和六类报告回归 |

**结论**：通过。产品口径、实现边界和测试追踪一致。

## 8. 第三轮评审：失败模式、安全与上线可控性

**评审目标**：假设第三方格式变化、旧服务端、重复事件、隐私数据和单客户端事故同时出现，检查是否可止损。

**检查方法**：

- 逐项推演首次、追加、历史重写、跨 generation usage、旧 API、kill switch、跨平台路径；
- 检查外部命令、ZIP、symlink、凭据目录和日志输出；
- 检查生产发布是否被 14.157 门禁阻断。

**发现与修订**：

| 编号 | 发现 | 修订 |
|---|---|---|
| R3-01 | canonical `event_id` 只在 Session 内唯一，直接按 provider 去重会误伤其他 Session | fingerprint 加入 user + agent type + session ref 命名空间，并对同 ID 内容变化报 conflict |
| R3-02 | 新 CLI 连接旧 API 时可能错误上传 canonical 文件 | 增加 session-sync capability 握手；旧 API 下只保留 Claude/Codex |
| R3-03 | 某个新 adapter 出现格式事故时缺少快速关闭路径 | 增加按 agent type 的服务端 allowlist/kill switch 和稳定错误码 |
| R3-04 | Harness 官方路径可能只代表一种 OS | 使用平台数据目录解析器，只宣称真实验证的平台 |
| R3-05 | 动态 adapter 虽扩展快，但会在用户机器执行任意第三方代码 | 首期只允许随 AIDA 发布的内置 adapter |
| R3-06 | 仅看 CLI/API 容易漏掉最常用默认 Agent 回归 | 发布门禁保留真实默认 Agent、直接 MCP 对照、四角色六类报告和浏览器验收 |

**结论**：通过。阶段 0/1 具备可控实施和回滚路径；生产发布仍明确禁止，直到 14.157 完整验收。

## 9. 三轮评审后的不变约束

1. 用户显式选择 Session 切片的优先级高于日期/type 默认筛选。
2. 未选择时仍按报告周期冻结相交的完整上传切片。
3. 小组和部门报告仍汇总下级已保存报告。
4. 默认 MCP/Skill/Agent 不按客户端分叉。
5. 报告内容能力与 Token/成本能力独立发布。
6. 现有 Claude Code/Codex 行为必须无回归。
7. 不读取凭据和全局诊断日志，不开放动态 adapter。
8. 不在本轮部署生产。

## 10. 开发启动前仍需获得的输入

这些不是方案缺陷，而是阶段 0 的必需样本：

- OpenCode 当前团队实际版本的 3 类脱敏 export JSON。
- Kimi Code 当前团队实际版本的 index/state/main wire/子 Agent wire。
- OpenClaw 一个纯编码会话和一个非编码渠道会话，用于验证隐私筛选。
- Harness 一个带底层 Session ID、一个不带底层 ID 的日志样本。
- 用户所说 Harness 是否确认为 harness.lol；若是 Harness.io，另开需求。
- ZCode 官方格式说明或可合法保留的多版本脱敏 Session 样本。

缺少某个客户端样本只阻塞该客户端，不阻塞 adapter 框架和其他已经满足条件的客户端。

## 11. 评审批复建议

- **需求一致性**：通过。
- **技术可行性**：通过，ZCode 除外并已明确 gated。
- **测试可执行性**：通过，真实客户端样本准备后执行。
- **上线风险**：可控，前提是服务端先行、逐客户端开关、14.157 门禁和不提前发布生产。
- **建议决策**：批准阶段 0 和阶段 1；阶段 2 按客户端独立复审；ZCode 等待输入契约。
