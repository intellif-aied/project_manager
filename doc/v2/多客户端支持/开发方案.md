# 多客户端 Session 支持开发方案

> 文档状态：P0 已实现，等待真实客户端人工验收；尚未发布。
> 评审日期：2026-07-21（增加腾讯 WorkBuddy）
> 产品依据：同目录 `产品需求.md`。
> 统一入口：同目录 `README.md`；Aida CLI 自身重构见 `../Aida客户端重构/README.md`。
> 原则：新增客户端在本地标准化，服务端只新增一种稳定格式；不为每个客户端复制整套上传协议。

## 1. 当前实现基线

### 1.1 AIDA CLI

当前 `daemon/` 同时承担客户端扫描、解析和上传：

- `daemon/session_index.go` 固定扫描 `~/.claude/projects` 和 `~/.codex/sessions`。
- `daemon/device_client.go` 的 `SessionInfo` 是两种客户端共用的内存模型，但 `AgentType` 注释和默认值仍只覆盖 Claude Code/Codex。
- `parseJSONL` 直接解析 Claude Code JSONL。
- `daemon/codex_scan.go` 直接解析 Codex rollout JSONL。
- `daemon/session_sync_client.go` 使用 Prepare、Chunk、Finalize 协议进行断点续传，并在 `~/.aida/upload-state.json` 保存游标。
- `~/.aida/session-index.json` 只按文件大小和修改时间缓存解析结果，当前版本为 1。

### 1.2 服务端

- Session 唯一键已经是 `(user_id, agent_type, session_ref)`，可以容纳新增客户端类型。
- `session_sources`、`session_source_generations`、`session_upload_chunks` 和内容切片已经支持增量、重建和活动版本切换。
- `api/internal/sessionsync/content_parser.go` 只能投影带顶层 `type`、`timestamp`、`payload/message` 的 JSONL，但对具体客户端相对宽松。
- `api/internal/usage/provider_parser.go` 只接受 `claude_code` 和 `codex`；未知客户端会成为不支持的 Provider。
- 报告来源读取活动 generation 的 `session_content_events` 和 `session_content_slices`，并不要求客户端只能是 Claude/Codex。

### 1.3 结论

上传和报告来源主体已经具备扩展条件，真正写死的是：

1. CLI 的目录发现和原生解析；
2. 服务端无法区分“原生 JSONL 格式”和“标准化 JSONL 格式”；
3. Token parser 只支持两种客户端；
4. 前端少量客户端名称和 Token 展示分支。

因此不应为每个新客户端新增一套 API。正确边界是：**客户端适配器在本地输出统一事件，现有增量协议上传统一事件，服务端按 `source_format` 处理内容和 usage。**

不增加独立服务、新 Token 表、动态 Provider/Adapter 插件或跨系统事务。现有 claims、contribution、family rollup 已能承载本期行为；新增复杂度仅限 Canonical 字段、解析校验和既有处理器的归属解析。

## 2. 总体架构

```text
                Command Router
                      |
                Update Gate
                      |
         +------------+------------+
         |                         |
   Bubble Tea TUI             Headless CLI
         |                         |
         +------------+------------+
                      |
             Application Service
                      |
第三方客户端本地数据 / 官方只读导出命令
                    |
                    v
              SessionAdapter
       discover -> inspect -> normalize
                    |
                    v
      Aida Canonical Event v1 JSONL
     ~/.aida/sources/<client>/<session>/events.jsonl
                    |
                    v
      现有 Prepare -> Chunk -> Finalize
                    |
        +-----------+-----------+
        |                       |
        v                       v
  Canonical Content Parser   Canonical Usage Parser
        |                       |
        v                       v
 Session 内容投影/切片       Token 归一化/成本
        |
        v
 现有报告来源快照 -> 默认 MCP/Skill/Agent
```

关键选择：

- Bubble Tea 只依赖 Application Service，不直接调用具体 Adapter 或拼接上传请求。
- Headless CLI 与 TUI 共用 Application Service，确保 JSON 和交互结果一致。
- Claude Code/Codex 保持现有扫描、上传和原生 parser 实现，不迁移到 Adapter 或 Canonical Event；它们只作为不可回归的行为基线。
- 新增客户端统一生成 `aida_event_v1`，服务端只维护一套新增内容/Token parser。
- 第三方客户端原生格式变化只影响本地适配器和 fixture，不扩散到报告 MCP。
- 标准化文件是可重建缓存，不是新的事实库；原生客户端数据仍是来源。
- Session Adapter 是客户端差异的 seam：调用方只使用现有 `Discover/Materialize` interface，各 Adapter 的实现内部负责本客户端 usage 身份、计数器和 fork 语义。服务端 Canonical Usage Processor 是统一去重、归属和汇总的深模块，Token Analytics 不理解客户端原生格式。

```text

  updategate/             # 每次启动版本检查、下载、校验、重启
```

依赖约束：

```text

```

多客户端 Adapter 随 Aida CLI 统一分发，不提供动态插件下载或第二套更新器。自更新的实现和发布门禁以 `../Aida客户端重构/客户端上传与升级方案.md` 为准。

## 3. CLI 适配器设计

### 3.1 包结构

将 `daemon` 中客户端相关代码拆成内部包，建议结构：

```text
daemon/
  internal/
    app/
    updategate/
    tui/
    sessionadapter/
      adapter.go
      registry.go
      claude/
      codex/
      opencode/
      kimicode/
      openclaw/
      harness/
      workbuddy/           # 仅在稳定输入契约通过门禁后加入
    canonical/
    sessionindex/
    uploadstate/
    sessionsync/
```

首期使用编译期注册表，不通过动态库、脚本目录或 PATH 自动执行第三方适配器。

### 3.2 核心接口

建议接口示意：

```go
type Adapter interface {
    ID() ClientType
    Detect(context.Context) Detection
    Discover(context.Context, DiscoverOptions) ([]Descriptor, []Diagnostic)
    Materialize(context.Context, Descriptor) (MaterializedSession, error)
}

type Descriptor struct {
    ClientType       ClientType
    NativeSessionRef string
    ParentRef        string
    ForkedAt         time.Time
    ForkSource       string
    StartedAt        time.Time
    LastActivityAt   time.Time
    CWD              string
    ProjectName      string
    Summary          string
    NativeVersion    string
    Capability       Capability
    OpaqueLocator    string
}

type MaterializedSession struct {
    Descriptor
    SourceFormat     string
    CanonicalPath    string
    AdapterVersion   string
    UsageCapability  UsageCapability
}
```

约束：

- `OpaqueLocator` 只能由同一适配器解释，不能直接输出到日志或 API。
- `NativeSessionRef` 必须来自客户端稳定 ID。
- `Materialize` 必须幂等；同一原生快照生成逐字节一致的 canonical JSONL。
- 一个适配器失败只产生自己的 diagnostics，不中止 registry 中其他适配器。
- Adapter interface 不增加按客户端暴露的 Token 方法；原生 Token、累计计数和 fork 规则由各 Adapter 实现隐藏，并由 `Materialize` 一次性输出内容与 Canonical Usage。
- 声明 `UsageCapability=exact` 时，Descriptor 的父子关系和每条 usage 的稳定身份、原始归属必须同时可验证；否则返回 `estimated` 或 `unavailable`。

### 3.3 发现与正文读取分离

`Discover` 尽量只读取索引、Session metadata 和少量摘要信息；`Materialize` 在用户选中上传后读取完整事件并生成标准事件文件。

当前首次建立 `session-index` 时会完整解析 Claude/Codex 文件。本期不迁移、不重构该行为；新增适配器独立按发现/正文分离实现。

### 3.4 本地索引升级

将 `sessionIndexVersion` 从 1 升为 2，缓存项增加：

```json
{
  "client_type": "opencode",
  "native_session_ref": "ses_xxx",
  "native_client_version": "1.18.1",
  "adapter_version": "opencode-v1",
  "source_fingerprint": "sha256:...",
  "usage_capability": "unavailable"
}
```

缓存失效条件：

- 原生文件大小或修改时间变化；
- 原生客户端版本变化；
- 适配器版本变化；
- canonical schema 版本变化；
- 适配器给出的 source fingerprint 变化。

旧 v1 索引直接重建，不做复杂迁移；上传游标文件独立保留。

## 4. Aida Canonical Event v1

### 4.1 格式

每行一个完整 JSON 对象，UTF-8，必须以换行结束：

```json
{
  "schema": "aida.session.event.v1",
  "event_id": "native-stable-id-or-derived-hash",
  "timestamp": "2026-07-15T08:01:02.123Z",
  "type": "message",
  "payload": {
    "type": "user_message",
    "role": "user",
    "message": "修复登录回调问题"
  }
}
```

允许的顶层 `type`：

- `session_meta`
- `message`
- `tool_call`
- `tool_result`
- `usage`
- `result`
- `error`

`payload.type` 用于细分，例如 `user_message`、`assistant_message`、`function_call`。

### 4.2 必填规则

- `schema` 固定为 `aida.session.event.v1`。
- `event_id` 在同一原生 Session 内稳定且唯一。
- `timestamp` 为 RFC3339Nano 绝对时间并转换为 UTC；原始时区不明确时适配器必须报质量降级，不能猜本地日期。
- `type` 必须在允许集合内。
- `payload` 必须是对象；不得包含凭据对象或诊断日志。

### 4.3 顺序与稳定性

- 保持原生事件顺序，不按 timestamp 重新排序。
- 原生有稳定事件 ID 时直接派生 `event_id`。
- 原生无事件 ID 时使用“原生 Session ID + 原生逻辑序号 + 规范化内容哈希”派生。
- 同一输入重复 Materialize 必须生成同样的行顺序、JSON key 顺序和字节内容。
- 历史编辑或 compaction 造成旧事件变化时，重建整个 canonical 文件；现有 prefix checkpoint 将触发新的 generation。

### 4.4 文本与大事件

- 单行最大值必须低于服务端 8 MiB 限制，建议适配器硬限制为 4 MiB。
- 超大 message/tool result 按稳定顺序拆成多个事件，`payload.part_index` 从 0 开始，并携带相同 `logical_event_id`。
- 二进制附件只保留类型、名称、大小等元数据，不内联二进制。
- 无效 UTF-8 替换为 U+FFFD，并记录 adapter diagnostic。

### 4.5 Usage 事件

只有客户端具备可核对 usage 时才生成：

```json
{
  "schema": "aida.session.event.v1",
  "event_id": "usage-native-request-id",
  "timestamp": "2026-07-15T08:03:00Z",
  "type": "usage",
  "payload": {
    "type": "token_usage",
    "usage_fact_id": "provider-call-or-message-stable-id",
    "owner_session_ref": "native-session-that-created-this-call",
    "identity_strategy": "provider_request_id",
    "model": "provider/model-id",
    "counter_mode": "delta",
    "uncached_input_tokens": 900,
    "cache_read_input_tokens": 300,
    "cache_creation_5m_input_tokens": 0,
    "cache_creation_1h_input_tokens": 0,
    "output_tokens": 180,
    "reasoning_output_tokens": 0,
    "total_tokens": 1380,
    "quality": "exact"
  }
}
```

规则：

- P0 上传契约只接受 `counter_mode=delta`。原生客户端若提供累计计数，必须由版本化 Adapter 在本地证明作用域、顺序、重置和 fork 基线后转换为逐事实 delta；服务端不接收未经归一化的 cumulative。
- `usage_fact_id` 表示一次真实计费调用，在同一用户和客户端 Session family 内跨 generation、主 Session、subagent 和 fork 保持一致；不同真实调用不得复用。Harness 首期不生成 usage，因此包装器重复由“只采用底层原生 Token 来源”避免。
- `owner_session_ref` 表示最初产生该调用的原生 Session。fork 复制的历史保留父 Session 归属；子 Session 新调用使用子 Session 自己的 ref。
- `identity_strategy` 记录事实身份来自 `provider_request_id`、`message_id` 或经过验证的客户端等价字段；游标、时间、标题、正文哈希不能支撑 `exact`。
- `uncached_input_tokens` 不包含 cache read；适配器必须根据客户端原始语义先完成拆分。
- `reasoning_output_tokens` 是 `output_tokens` 的子集，不得再次加入 `total_tokens`。
- 标准总量公式为 `uncached_input_tokens + cache_read_input_tokens + cache_creation_5m_input_tokens + cache_creation_1h_input_tokens + output_tokens`；不满足时 usage 降级为 conflict，不进入精确统计。
- 缺少必需计数或语义不明时不生成 usage，Session 保持 `unavailable`。
- 第三方给出的美元金额不进入 canonical usage 事实。
- Adapter 必须为不同 Session 中可能重复的原生短 ID 加入稳定原生作用域，生成不会误碰撞的 `usage_fact_id`；父子 Session 中复制的同一调用必须生成相同 ID。
- 服务端将 `usage_fact_id` 映射为现有 `provider_event_fingerprint`，复用 `(user_id, provider, provider_event_fingerprint)` claim 跨 source 去重；不得再把 `session_ref` 加入 fingerprint 隔离父子 Session。
- 同一 `usage_fact_id` 的 Token、模型或发生时间不一致时标记 conflict，不能静默选择一份。
- 原生 cumulative 只有在计数器作用域、稳定顺序、重置边界和 fork 前基线均可验证，并已由 Adapter 转成 Canonical delta 时才能为 `exact`；否则降为 `estimated`/`unavailable`。缺失的首段 Token 不得显示为 0。
- 客户端只有合并后的 cache creation 总量、无法区分现有价格模型要求的 5m/1h 写入时，Token 可以保留但成本质量不得标记 exact；不得凭默认比例拆分。
- `owner_session_ref` 必须能解析到同一用户、同一 `agent_type` 且已由同一批 family manifest 登记的 Session；祖先缺失、跨用户、关系不闭合或关系冲突时不激活 exact revision。

## 5. Canonical spool 与增量上传

### 5.1 路径

```text
~/.aida/sources/<client_type>/<sha256(session_ref)>/
  metadata.json
  events.jsonl
```

- 目录权限 0700，文件权限 0600。
- 路径使用 Session ID 哈希，避免把渠道 ID、项目名或用户内容暴露在文件名。
- 写入使用临时文件、`fsync`、原子 rename。

### 5.2 source key

```text
<client_type>:<native_session_ref>:main
```

子 Agent 使用自己的 Session ID 和 source key，并通过 `parent_session_ref` 关联。

### 5.3 追加与重建

1. Materialize 新快照。
2. 若旧 canonical 文件是新文件的逐字节前缀，则原子替换后沿用现有上传状态，Prepare 返回增量游标。
3. 若前缀不一致，则保留新 canonical 快照，Prepare 通过 checkpoint 决策创建重建 generation。
4. 新 generation 激活后，报告查询只读取活动 generation；旧切片自然退出候选列表。
5. 无变化时 canonical 哈希不变，Prepare 返回 `unchanged`，不形成切片。

不得用“只比较最后修改时间”判断增量。

## 6. 服务端协议调整

### 6.1 Prepare 请求

现有 Claude/Codex `/session-syncs/prepare` Handler、`SyncService.Prepare` 和 `uploadSessionGroupIncremental` 全部保持不变。新增客户端使用独立 `POST /canonical-session-syncs/prepare` interface；该入口内部复用现有 Session/source 数据模型，但不改变 legacy 调用路径：

1. `CanonicalUploader` 为一次上传涉及的主 Session、subagent 和可达祖先生成完整 family manifest；Session 可以只含关系元数据而暂时没有 source。
2. canonical handler 第一阶段在同一事务内登记全部 Session 身份和父子关系，校验同用户、同 `agent_type`、无环且 owner 可解析。
3. 第二阶段只为带 `source_format=aida_event_v1` 的成员执行 source prepare；第一阶段未整体成功前，不创建 generation，也不启动 content/usage job。
4. canonical 请求不得包含 Claude Code/Codex 原生 source，legacy 请求也不得携带 canonical source；混合请求直接拒绝。
5. 缺少可达 owner 的 canonical 请求可以保留报告内容能力，但 usage 不得标记 `exact`。

在 `PrepareSourceRequest` 增加：

```json
{
  "source_format": "aida_event_v1",
  "ingestion_metadata": {
    "adapter_version": "opencode-v1",
    "native_client_version": "1.18.1",
    "usage_capability": "unavailable"
  }
}
```

兼容规则：

- 老 CLI 继续调用原 `/session-syncs/prepare`，不增加 `source_format`，服务端继续按当前 `agent_type` 选择 Claude/Codex 原生 parser；不得借本需求修改其 fingerprint 或 Token 字段语义。
- 新客户端必须显式发送 `aida_event_v1`。
- 服务端维护 source format allowlist，不接受任意 parser 名称。
- capability handshake 只向新 CLI 宣告 canonical 入口；旧 CLI 不感知该入口。

### 6.2 数据库

新增 forward migration：

```sql
ALTER TABLE session_sources
    ADD COLUMN source_format TEXT NOT NULL DEFAULT 'legacy_native_v1',
    ADD COLUMN ingestion_metadata JSONB NOT NULL DEFAULT '{}';

ALTER TABLE session_metering_envelopes
    ADD COLUMN owner_session_ref TEXT;
```

`usage_fact_id` 直接写入现有 `provider_event_fingerprint`，`identity_strategy` 复用现有同名列；只新增 `owner_session_ref` 这一项处理和审计都需要的归属字段。现有 Claude/Codex envelope 为空时继续归属当前 Session，不回填历史数据。

为 `source_format` 增加受控 CHECK/服务层 allowlist；`ingestion_metadata.usage_capability` 只允许 `unavailable`、`estimated`、`exact`。未知值拒绝 Prepare，不能进入 worker 后再失败。

P0 不回填任何已有 source：Claude Code、Codex 和其他历史 source 均保持
`legacy_native_v1`，继续进入现有 parser。只有新增客户端创建的 canonical source
写入 `aida_event_v1`。待独立迁移方案、历史数据回归和回退演练完成后，才评估是否
细分 `claude_jsonl_v1` / `codex_rollout_v1`；本期不得借多客户端接入迁移旧链路。

`source_format` 在同一 `session_id + source_role` 上不可变；变化时必须创建新 source role 或明确迁移，不能原地换 parser。

### 6.3 内容投影

将内容 parser 改为 registry：

```go
type ContentParser interface {
    ParseChunk(io.Reader, int64, *time.Time) (ContentParseResult, error)
}
```

- `claude_jsonl_v1` 和 `codex_rollout_v1` 复用当前 parser 行为。
- `aida_event_v1` 严格校验 schema、event_id、type、timestamp 和 payload。
- 标准事件投影时优先提取 user/assistant message、工具名和 result；纯 usage、session_meta 和无可读内容的控制事件只推进解析游标，不写入报告内容投影。
- 任何 parser 都必须保持 chunk 边界不变性：整文件解析与按合法行边界分块解析结果一致。

### 6.4 Usage 处理

Usage parser 同样按 `source_format` 分发，不再把 `agent_type` 同时当“客户端”和“原始格式”。

- 现有 Claude/Codex parser 保持不变。
- `aida_event_v1` 只解析 canonical `usage` 事件。
- Canonical parser 将 `usage_fact_id` 写入现有 `provider_event_fingerprint`，继续复用 `session_usage_event_claims` 的跨 source claim；不新增去重表。
- 处理器通过 `(user_id, agent_type, owner_session_ref)` 解析已由本批 family manifest 登记的 Session，并把贡献写入现有 `session_usage_contributions.member_session_id`。父 Session 可以尚未上传正文，但不能在关系元数据中缺席；禁止在 usage worker 中临时猜测或创建 owner。
- 同一计费事实由父子 Session 乱序上传时，claim 最终只保留一份有效贡献；贡献归属由 `owner_session_ref` 决定，不由“谁先上传”决定。
- usage worker 查询 generation 时同时读取 `session_sources.source_format` 和 `sessions.agent_type`：前者选择 parser，后者作为客户端/统计来源标识。
- `usage_capability=unavailable` 时，usage job 应成功完成为空结果并记录不可用状态，不能反复重试为 dead job。
- `estimated` 和 `exact` 写入质量字段，Token 页面和成本计算保留质量差异。
- 成本仍由现有价格表计算，canonical 中的第三方金额字段即使出现也拒绝使用。

### 6.5 API 输出

Session、候选切片和 Token 明细继续使用现有 `agent_type` 表示客户端。只增加必要的可选能力字段：

```json
{
  "agent_type": "opencode",
  "usage_capability": "unavailable"
}
```

原生客户端版本和 adapter 版本保存在 `session_sources.ingestion_metadata`，只用于诊断和管理，不扩散到普通列表接口。这样可以避免为同一概念长期维护 `client_type`/`agent_type` 两套字段。

兼容默认值：现有 `claude_code`、`codex` source 分别保持当前 usage 能力；未知历史 source 默认 `unavailable`，不能因为缺字段显示为精确 0。

### 6.6 Capability 握手与关闭开关

新增只读能力接口，例如：

```json
GET /api/v1/session-syncs/capabilities
{
  "source_formats": ["claude_jsonl_v1", "codex_rollout_v1", "aida_event_v1"],
  "enabled_agent_types": ["claude_code", "codex", "opencode", "kimi_code"],
  "canonical_schema_versions": [1]
}
```

- 新版 CLI 上传新增客户端前必须校验该能力；列表仍可离线展示本地 Session。
- 老服务端没有接口时，新增客户端明确禁用，Claude/Codex 继续走兼容链路。
- 服务端提供按 `agent_type` 的 allowlist/kill switch。某个 adapter 出现格式事故时可停止新 Prepare，不影响其他客户端和历史只读数据。
- kill switch 返回稳定错误码和升级/联系提示，不返回内部配置。

## 7. 各客户端适配方案

### 7.1 OpenCode

正式入口：

- `opencode session list --format json` 获取 Session ID 和元数据。
- `opencode export <sessionID>` 获取官方 JSON 快照。

实现规则：

- 使用 `exec.CommandContext` 和固定参数，不拼 shell。
- 对 list/export 设置超时、最大 stdout 和最大 Session 数。
- 解析官方 JSON 导出，不直接依赖 OpenCode 内部 SQLite 表结构。
- 首期从导出中的 message、part、tool、时间、模型信息生成 canonical 事件。
- Token 字段必须通过当前支持版本的真实导出和 `opencode stats` 交叉核对后才能启用。
- OpenCode assistant message/step 的稳定 ID 只有在 export 中跨重复导出、subtask 和历史重写保持一致时才能生成 `usage_fact_id`；子 Session 必须保留真实 parent ID，复制历史沿用原 owner，新调用归属子 Session。
- `--sanitize` 会删减报告需要的内容，不作为默认上传来源；Aida 自己排除明确敏感结构并继续要求用户上传前检查。

风险：逐 Session 执行 export 可能较慢。Discover 只执行一次 list，只有选中项才 export；批量上传设置并发上限 2，避免压垮本机。

### 7.2 Kimi Code

正式入口：

- `$KIMI_CODE_HOME/session_index.jsonl`
- `sessions/<workDirKey>/<sessionId>/state.json`
- `agents/main/wire.jsonl` 及子 Agent `wire.jsonl`

实现规则：

- 尊重 `KIMI_CODE_HOME`，默认 `~/.kimi-code`。
- 只读 session index、state 和 wire；明确排除 `credentials/`、全局/Session `logs/`、tasks 输出和 cron 数据。
- 主 Agent 和子 Agent 使用各自稳定 ID；父子关系来自 Session 目录和 wire metadata。
- 不使用 `kimi export` 默认包含的全局诊断日志作为上传源。
- wire schema 按 Kimi Code 版本维护 fixture；未知版本先尝试兼容解析，关键字段缺失则拒绝上传。
- usage 只有在 wire 中存在稳定 request/event ID 且与客户端 Usage Stats 对账后启用。
- 主 Agent 和各级 subagent 的 wire 必须证明同一模型调用的 ID 不因复制/恢复而改变，并能区分继承历史与子 Agent 新调用；否则 Kimi Code 只发布 report 或 estimated，不发布 exact。

### 7.3 OpenClaw

正式入口：

- `openclaw sessions --all-agents --json`
- `openclaw sessions export-trajectory --session-key ... --output ... --json`

实现规则：

- 不直接读取或锁定其 SQLite session store。
- Session key 可能包含渠道和对端身份，Aida 本地路径、日志和错误信息必须脱敏。
- 导出目录必须位于 Aida 创建的私有临时 workspace，并校验所有文件不越界。
- 只提取本次 Session 的用户消息、Agent 结果、工具事件和模型元数据。
- 首期 capability 固定为 `report`，不导入 Token/成本。
- `aida upload --all` 默认跳过 OpenClaw，避免误上传私人聊天或非编码渠道。

### 7.4 harness.lol

正式入口：

- `~/.local/share/harness/sessions/<id>.ndjson`
- metadata sidecar。

实现规则：

- 解析 `SessionStart`、`Message`、`ToolStart`、`ToolEnd`、`Result`、`Error`。
- `~/.local/share` 只作为官方文档给出的默认路径；适配器使用平台数据目录解析器，并且只对阶段 0 已验证的 OS 宣称支持，不能把 Linux 路径硬编码到 Windows/macOS。
- `timestamp_ms` 转换为 RFC3339Nano。
- `SessionStart.agent` 保存为 `upstream_client_type`，Aida 现有 `agent_type` 写为 `harness`。
- 官方文档与仓库 README 对 UsageDelta 的描述存在版本差异，首期不解析 Token/成本。
- 若 metadata 明确给出底层 Session ID，则列表标记重复来源；无稳定 ID 时不做模糊自动去重。
- Harness 首期不生成 Canonical Usage，由已支持的底层原生客户端作为唯一 Token 来源；只有未来能稳定映射底层计费事实和 owner Session 时才单独评审 exact，不在本期增加跨客户端 claim 机制。

### 7.5 ZCode

当前只做技术验证：

- 官方文档确认 `~/.zcode`、本地 Session usage 和任务 Session 文件存在，但未提供稳定的 Session 列表/正文导出协议。
- “Export Logs”面向故障反馈，不是业务数据接口，不能作为正式适配依据。
- 需要至少取得：官方格式说明或版本化样本、稳定 Session ID、事件时间、正文/工具事件、usage 语义。
- 在上述条件满足前，不把扫描私有内部数据库或逆向 Electron 存储作为生产方案。

### 7.6 腾讯 WorkBuddy

当前只做技术验证：

- 官方产品文档确认任务内存在历史对话、执行过程、工具结果和生成文件；更新日志还明确提到本地数据库、历史会话迁移以及 transcript/replay 写入，但没有公布稳定、版本化的 Session 列表或正文导出协议。
- 官方隐私政策表明对话、coding/agentic session 输入输出和 Token/积分消耗记录会被处理，且部分数据保存在本地；这些事实不能替代字段定义、稳定 Session ID、增量语义和授权导出契约。
- 阶段 0 必须先确认普通任务、助理远程任务、自动化任务是否使用同一 Session 身份体系，以及子 Agent、工具调用、产物和时间字段能否按单个任务安全导出。
- 若官方提供只读 CLI、SDK 或版本化导出文件，优先使用该入口；仅发现内部 SQLite/LevelDB/应用缓存时不得直接开发生产 adapter。
- 在稳定契约和合法样本齐备前固定为 `content_capability=detected`、`usage_capability=unavailable`，不进入普通列表、不上传正文、不计算 Token/成本。
- `agent_type` 预留为 `workbuddy`；产品展示名为 `WorkBuddy`。本文所指为腾讯 WorkBuddy，不与开源 `work-buddy` 项目混用。

## 8. 前端改动

保持改动集中在现有 Session 和 Token 显示：

1. 建立统一 `clientTypeLabel`：Claude Code、Codex、OpenCode、Kimi Code、OpenClaw、Harness、WorkBuddy；未知值显示原值。WorkBuddy 未通过门禁前不进入普通列表，该映射仅保证诊断或后续启用时可读。
2. Session 页面和报告来源弹窗复用该映射。
3. Token 不可用时显示 `--` 和 tooltip，不参与合计；不得用 0 代替。
4. `estimated` 显示估算标记；精确值保持当前样式。
5. 不新增报告生成步骤、客户端设置页或嵌套卡片。
6. Web 端现有分页和日期筛选必须回归；CLI 使用 Bubble Tea 搜索、筛选、多选和虚拟滚动。

## 9. 默认 MCP、Skill 与 Agent

多客户端接入对默认报告链路应透明：

- MCP 继续读取冻结后的 `session_content_slices` 和内容投影。
- Skill 不按客户端类型选择来源，也不自行解析第三方格式。
- Agent 接收到的是统一的来源 item 和内容事件。
- 个人日报/周报可以混合多个客户端切片。
- 小组和部门报告仍按现有下级报告层级取数。
- 如果报告需要 Token，只读取后端结构化且能力允许的归一化值；不累加 canonical 原始 usage。

默认 Agent 回归是发布门禁，不因为本需求主要修改 CLI 就降低优先级。

## 10. 安全设计

- 所有外部命令使用参数数组，不使用 `sh -c`。
- 外部命令具有执行超时、stdout/stderr 上限和退出码检查。
- 只允许调用检测到的固定二进制名称；不执行 Session 目录中的脚本。
- 读取路径必须在该适配器允许的数据根内，解析 symlink 后再次校验。
- 导出 ZIP 解压前检查条目数、压缩后/解压后大小、压缩比和路径穿越。
- canonical 生成器采用字段 allowlist，不原样复制配置、环境变量、headers、credentials 等对象。
- 文本本身仍可能含秘密；上传前提示与用户显式选择不可取消。
- diagnostics 只记录客户端、版本、错误码和脱敏路径，不打印消息正文。

## 11. 发布与迁移

### 11.1 多客户端服务端先行

发布顺序必须是：

1. 先发布兼容新增 `source_format` 和 capability 的服务端。
2. 只为已通过真实验收的客户端开启独立服务端开关。
3. 再通过 Aida CLI 正式发布流程分发对应 Adapter。
4. 最后按客户端灰度开启报告内容能力。
5. Token 与成本使用独立开关，不随报告内容能力自动开启。

### 11.2 回滚

- 回滚 CLI：将发布清单的 `latest_version` 指向上一份经过验证的完整版本；所有不等于该版本的客户端都安装清单指定版本。
- 回滚 Web：API 新字段均为可选，不影响旧前端读取核心字段。
- API 不建议回滚到不认识 `source_format` 的版本；若必须回滚，先停止新 CLI 分发。
- 数据迁移只新增列和允许值，不删除历史内容。

### 11.3 观测与灰度

按 `agent_type` 和 `source_format` 记录：

- Discover/Materialize 成功、失败和耗时；
- canonical 合法、malformed、ignored 事件数；
- Prepare action、上传字节、chunk 数、rebuild 次数；
- content/usage job 完成、重试、dead 数；
- usage unavailable/estimated/exact Session 数。

指标和日志不包含 Session 正文、原生 ID、项目绝对路径或渠道对端。14.157 先只开启 OpenCode/Kimi Code；第二批 adapter 独立开启，不能用一个总开关同时放量全部客户端。

### 后续阶段 0：Spike 与协议冻结

5. ZCode、腾讯 WorkBuddy 只做资料/样本获取，不逆向生产数据或抓取内部云端接口。

退出条件：OpenCode、Kimi Code 可稳定生成 canonical；OpenClaw/Harness 可生成报告内容；Token 能力有明确支持或不支持结论。

## 14. 关键风险与控制

| 风险 | 影响 | 控制 |
|---|---|---|
| 第三方格式快速变化 | 上传空内容或错误正文 | 版本化 adapter + fixture + 关键字段缺失即拒绝 |
| Snapshot 重写被当作追加 | 重复内容和 Token | canonical 前缀比较 + generation rebuild |
| fork 历史在父子 Session 重复出现 | Token 翻倍或 self/subagent 归属错误 | 稳定 `usage_fact_id` + `owner_session_ref` + 现有跨 source claim |
| 累计计数缺少 fork 基线 | 漏计首段或把继承历史算入子 Agent | exact 门禁拒绝；降为 estimated/unavailable，不以 0 代替 |
| 未知客户端 usage job 持续失败 | 队列堆积 | `usage_capability=unavailable` 成功空处理 |
| Harness 与底层日志重复 | 报告重复、成本翻倍 | 首期 Harness 不统计 Token；稳定底层 ID 才标记重复 |
| OpenClaw 含私人渠道信息 | 数据泄露 | 显式选择、`--all` 排除、脱敏路径、只读导出 |
| Kimi export 携带全局日志 | 跨 Session 信息泄露 | 直接读取明确 session 文件，排除 logs/credentials |
| ZCode 内部格式无契约 | 版本升级即失效 | 不进入正式支持，等待官方协议/样本 |
| 腾讯 WorkBuddy 只有本地数据库和 UI 历史证据 | 逆向格式易失效，且可能跨普通任务、远程助理和自动化任务扩大读取范围 | 保持 `detected`，等待官方只读导出契约和逐任务授权样本 |
| 新 CLI 早于服务端发布 | 文件被错误解析 | 服务端先行 + capability handshake |

## 15. 方案决策

最终选择“本地内置适配器 + Aida Canonical Event + 现有增量协议”。不选择：

- 服务端逐客户端解析原始格式：格式变化会扩散到 API 和任务队列，维护成本过高。
- 直接读取所有客户端内部数据库：容易锁库，且缺少兼容契约。
- 首期开放动态适配器插件：会把供应链和任意代码执行风险带到用户机器。
- 只上传 Markdown 摘要：会丢失工具、时间、增量和 Token 事实，不能满足报告来源可追溯性。

该方案与现有 Session 切片、报告来源和默认 Agent 链路一致，新增面主要集中在 CLI adapter、一个服务端标准格式 parser 和少量能力展示。
