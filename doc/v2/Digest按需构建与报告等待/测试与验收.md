### 1.1 必须自动化覆盖

| 用例 | 对应需求 | 场景 | 通过标准 |
| --- | --- | --- | --- |
| T01 | R2 | Digest ready | Run 创建后自动进入原有 Agent 流程 |
| T02 | R1、R2 | Digest missing | HTTP 已返回 Run；Coordinator 创建 interactive Job，ready 后自动继续 |
| T03 | R2、R6 | Digest Job 在 background 队尾 | 更新同一 Job 为 interactive，不复制 Revision/Job |
| T04 | R2 | Digest 已 building，多个 Run 依赖 | 复用同一 Revision/Job，只发生一次实际构建 |
| T05 | R2 | Digest/数据库/AIHub 均健康，创建 Run 后立即关闭页面且无后续请求 | 原 Run 最终 succeeded，不创建第二个 Run |
| T06 | R2、R5 | API/Worker 在 waiting 阶段重启 | Reconciler 恢复原 Run，不创建新 Run |
| T07 | R6 | 预置 5000 个 background Job 后执行一次 interactive Claim | Claim 返回 interactive Job；查询候选和结果不包含 background Job；background Worker 仍可 Claim 最老 background |
| T08 | R2 | 多个 Run 依赖同一 Digest | Digest 一次构建，各 Run 分别恢复 |
| T09 | R5、R7 | 同一 Run 重复投递 | Context 只有一条；已有 `external_session_id` 时不再调用 CreateSession |
| T10 | R1 | idempotency key 缺失/非 UUID v4、相同 key 网络重试、相同 key 不同请求、两个实例并发 | 缺失/非法返回 400 `INVALID_IDEMPOTENCY_KEY`；相同 key + 相同 fingerprint 返回同一 Run；相同 key + 不同 fingerprint 返回 409 `IDEMPOTENCY_KEY_REUSED`；并发只创建一个 Run |
| T11 | R1 | 双击产生不同请求键但请求内容相同 | 活动去重返回同一 Run |
| T12 | R2 | 部分 Digest ready、部分 pending | 只创建或提权缺失项 |
| T13 | R2、R5 | Digest 自动重试耗尽 | Run failed，不无限等待 |
| T14 | R2、R5 | ready 事件与 Reconciler 并发 | 只有一次阶段迁移成功 |
| T15 | R3 | Run 创建后出现新 Generation | 使用创建时冻结的 Generation |
| T16 | R3 | 冻结 Generation 不再 active，但底层内容完整 | Run-pinned Digest 仍可构建 |
| T17 | R3、R9 | content epoch 改变或内容清理 | Run 失败，不读取新内容代替 |
| T18 | R5 | `EnsureRunDigests=waiting` | 同一事务设置 `next_attempt_at=NULL` 并清 lease，Worker 立即结束 |
| T19 | R3、R5 | Context Build 写入后进程退出并重试 | 返回同一 Context 和 hash |
| T20 | R5 | building/submitting 正常 heartbeat 与停止 heartbeat | 正常续租时不抢占；停止后仅 lease 过期才恢复 |
| T21 | R7 | Session ID 已保存但阶段未更新 | Reconciler 前移阶段，不重提 Session |
| T22 | R7 | CreateSession 调用前失败、HTTP timeout/network error/响应读取失败/5xx、4xx | 调用前失败最多重试 5 次，耗尽为 `EXTERNAL_SUBMISSION_PREPARE_FAILED`；timeout/network/read/5xx 均以 `EXTERNAL_SUBMISSION_STATE_UNKNOWN` failed 且不重提；任意 4xx 以 `EXTERNAL_SUBMISSION_REJECTED` failed 且不重试 |
| T23 | R5、R7 | 5000 个 waiting Run 与已有 Agent Run 并存 | Status Sync 只领取有外部 ID 的 Run；waiting Run 不进入其候选集 |
| T24 | R5、R7 | Digest 等待超过旧 10 分钟阈值 | 不被旧 pending timeout 错杀；Agent timeout 从 `started_at` 起算 |
| T25 | R4 | Selection attached 但 `digest_frozen_at` 为空 | Context Builder 和 MCP 均拒绝读取，不回退 full content |
| T26 | R4、R9 | frozen 后任一 Selection/Item/Revision/hash/version 不一致 | 统一冻结门禁拒绝读取 |
| T27 | R3 | Context 创建后业务事实发生变化 | 重试读取已存 Context，不重新取数 |
| T28 | R8 | 完整 Context 分别为 1_048_576 和 1_048_577 bytes | 等于阈值时无提醒；超过阈值时写入 warning/bytes、Run 继续提交 Agent；前端对同一 run_id 最多展示一次非阻断提醒；不存在 confirmation/retry 请求，Context 不截断 |
| T29 | R5 | 同阶段失败、阶段迁移、等待和 heartbeat | 仅同阶段可重试失败增加 `stage_attempts`，迁移后清零 |
| T30 | R4、R9 | Selection、Digest、Context 与 MCP 回归 | 完整读取、hash 和写回门禁全部保持 |
| T31 | R9 | Claude Code、Codex 上传、Token/Usage 和其他 Session Job 回归 | 原 Claim 语义和统计结果不变 |
| T32 | R5 | waiting/building/submitting 各 Stage 成功迁移，以及 Reconciler 根据已落库结果前移 Stage | 一次 Claim 只执行 claimed stage；迁移时清 lease、重置 attempts、设置下一次调度后返回；Reconciler 不执行下一 Stage；下一 Stage 必须有新的 Claim/owner 校验 |
| T33 | R1、R3 | 相同默认来源规则在两次请求间解析出不同 Generation/Slice，不同 Selection 解析出相同实际来源，以及来源为空/重复 | 不同实际 identity 集合产生不同 active key；相同集合产生相同 key；排序变化不影响 hash；重复 tuple 去重；空集合拒绝创建 Run |
| T34 | R2 | retryable Digest 首次构建 dead，旧 Run 失败，冷却内新 Run 请求 | 创建一条 `next_retry_at=failed_at+15m` 的新 interactive Job；旧 dead Job 的 attempts/error/`completed_at` 保持并由新 Job payload 链接；并发新 Run 只创建一个活动 Job |
| T35 | R2 | permanent Digest 失败，以及 retryable 连续两轮重建耗尽 | permanent 不创建新 Job并返回 `DIGEST_PERMANENT_FAILURE`；两轮耗尽返回 `DIGEST_REBUILD_EXHAUSTED`；前端重试不能清零计数 |
| T36 | R2、R6 | `retry_wait` background Job 被 Run 提权 | 只改变 urgency/raised_at；status、attempts、next_retry_at 不变；到期前 interactive Claim 取不到该 Job |
| T37 | R2、R5 | 5000 个非终态 waiting Run 连续经过多个 Reconciler 周期 | Run 的 `next_attempt_at` 均为 NULL；Reconciler 不调用 Ensure、不逐 Run 检查；只有终态、deadline 或 lease/已落库事实候选被推进 |
| T38 | R10 | 构造两类队列、构建成功/失败、各 Run stage、lease 过期、唤醒、Reconciler、受控重建和各档 payload 大小事件 | 架构 9.1 全部指标及固定 bucket 正确；超过 1 MiB 只增加 warning counter，不改变业务状态；所有 label 仅包含允许的低基数枚举，不出现任何对象 ID |
| T39 | R10 | 对架构 9.2 的告警规则执行规则测试 | 每条规则在阈值以下不触发、达到固定条件后按指定持续时间和级别触发；metrics missing 规则可触发 |
| T40 | R5 | 分别以缺失、1、20、256、空串、非整数、0、负数和 257 配置 `REPORT_RUN_PROCESSOR_COUNT`；同时模拟 hostname 失败 | 缺失时为 20；1/20/256 产生对应数量且 owner 唯一；其余值及 hostname 失败均阻止启动；该数量不改变两类 Digest Worker |
| T41 | R6 | 对两项 Digest Worker 配置分别测试缺失、1、20、256、空串、非整数、0、负数和 257；同时模拟 hostname 失败 | 缺失时均为 20；1/20/256 分别产生对应数量且 owner 唯一；其余值及 hostname 失败均阻止启动；源码不再用字面量 Worker ID 数组决定并发，配置名不含实现版本号 |
| T42 | R11 | 构造包含超过 1 MiB 的目标、结果、未解决事项、变更、校验和证据文本并生成 v2.10 Digest/Period/Selection payload | 所有已进入 Digest schema 的文本在完成既定脱敏和空白规范化后完整保留，不因大小截断或删除；Work Unit 数量不减少；`coverage.truncated=false`；payload 可超过 1 MiB；hash/bytes 按完整 payload 一致；不存在 ItemMaxBytes、Enforce/Compact 或 hard-limit 错误路径 |
| T43 | R9、R11 | 数据库同时存在已冻结 v2.9 Run 和同 identity 的新 v2.10 Run | 旧 Run 按 v2.9 snapshot/hash/旧 budget validator 正常读取；新 Run 只绑定 v2.10 Revision并使用 size validator；不修改或删除任何 v2.9 Revision/Selection/Context |

### 1.2 生产等价突发验收

生产等价验收使用测试服固定脚本和同一资源配额执行，结果随发布记录保存：

| 验收 | 对应需求 | 执行与通过标准 |
| --- | --- | --- |
| P01 容量隔离 | R6、R9 | 分别在 0 和 5000 个 background Job 下运行相同 interactive Claim/构建脚本；两次 Claim 均只扫描并返回 interactive，background Worker 同时持续领取 background；记录两组入队到 lease 的 p50/p95/max，不把测试值预写为生产 SLA |
| P02 后台自动推进 | R1、R2 | 在 Digest/AIHub/数据库均健康时，fresh Slice 创建 Run 后立即关闭页面且不再发送前端请求；Run 最终 succeeded |
| P03 崩溃恢复 | R2、R5 | 分别在 Revision ready 后、Context 写入后终止进程；重启后恢复同一 Run，Run/Selection/Context 均无重复 |
| P04 外部提交恢复 | R7 | Session ID 落库后、阶段更新前终止进程，恢复时不重提；请求结果未知时 Run 以 `EXTERNAL_SUBMISSION_STATE_UNKNOWN` failed |
| P05 完整性 | R3、R4、R8、R9 | 新 Generation、未冻结 Selection、Digest/hash 不一致和大 Context 提醒分别按 T15、T25、T26、T28 的结果处理 |
| P06 无回归 | R9 | 执行 API 全量测试、Web 构建及 Claude Code/Codex 上传与 Token 统计专项回归；原流程输出保持一致 |
| P07 生产可观测性 | R10 | 生产内部 metrics 可被监控系统连续抓取；架构 9.1 指标可查询；9.2 全部规则已加载；注入一条测试序列验证告警触发与恢复通知；告警链接到 9.3 运行手册 |
| P08 配置化扩缩容 | R5、R6、R10 | 使用同一镜像和同一数据库，以 Report Run=20、Digest background=20、Digest interactive=20 启动并核对分组日志及 `aida_worker_configured`；分别单独调整一项并滚动重启，其他两项实际数量不变；镜像 digest 不变、无代码提交和迁移，owner 唯一且原 lease 到期后可恢复 |
| P09 首发并发满载 | R5、R6、R9 | 使用首发 20/20/20 配置，同时保持三类执行角色持续有任务 10 分钟；期间 API/Worker 不重启、无数据库连接错误、无 AIHub 429/5xx、无新增上传和 Token 统计错误，PostgreSQL 活跃连接峰值不得超过 `max_connections` 的 70%；任一条件失败即阻塞发布 |
| P10 Digest v2.10 升级突发 | R6、R9、R11 | 预置 5000 个只有 v2.9 的 active Slice 和至少一个未完成 v2.9 历史 Run后部署新版本；background 幂等生成 v2.10 Job，新用户 Run 的 v2.10 Job 被提权并自动成功，历史 v2.9 Run 继续成功；无 v2.9 数据改写、无重复 v2.10 Revision/活动 Job、无上传和 Token 统计回归 |

API/DB CPU、I/O、连接池、Digest 内存和前台 p95 作为容量记录。P01 只验证 Digest 容量隔离，使用 D09 固定的 20 个 background 和 20 个 interactive Digest Worker；Report Run Processor 不计入 P01 的 Digest 并发。验收失败即阻塞发布并重新评审架构，不允许测试人员现场选择另一组并发数绕过。
