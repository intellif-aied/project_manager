## 1. `ai_run` 的职责与状态归属

### 1.1 四类状态严格分开

| 状态类别 | 真实来源 | 用途 | 是否前端可见 |
| --- | --- | --- | --- |
| Run 总体状态 | `ai_runs.status` | 用户的一次生成请求最终是否完成 | 是，保持现有五种状态 |
| Run 内部阶段 | `ai_runs.execution_stage` | 后端当前推进到哪一步 | 否 |
| Digest 产物状态 | `session_slice_digest_revisions.status` | Digest 内容是否可用 | 否 |
| Job 调度状态 | `session_processing_jobs.status` | Job 是否待领取、leased、重试或 dead | 否 |

不得用 Digest/Job 状态替代 Run 状态，也不得把内部阶段返回成新的前端业务状态。

### 1.2 Run 总体状态

| `ai_run.status` | 用户语义 |
| --- | --- |
| `pending` | 已提交，后端正在准备来源、Context 或提交 Agent |
| `running` | 外部 Agent 已创建并正在执行/写回 |
| `succeeded` | 报告已通过现有门禁写回 |
| `failed` | 任一不可恢复阶段失败 |
| `timeout` | Digest 等待或 Agent 执行超过各自时限 |

前端继续把 `pending/running` 统一展示为“生成中”。

### 1.3 Run 内部阶段

本期只增加报告链路实际需要的阶段：

```text
waiting_digest
  -> building_context
  -> submitting_agent
  -> agent_running
  -> writing_result
  -> completed
```

失败或超时不再创造一组平行阶段；使用 `status=failed/timeout`，并记录 `failure_stage`、`error_code` 和 `error_message`。

状态约束：

- `waiting_digest/building_context/submitting_agent` 对应 `status=pending`；
- `agent_running/writing_result` 对应 `status=running`；
- `completed` 对应终态；
- 非报告 Run 不使用这些内部阶段；
- 阶段只能通过带前置阶段条件的数据库更新迁移，不能无条件覆盖。

### 1.4 `ai_runs` 最小新增字段

现有 `input_ref_json` 会返回前端，不能承担私有执行数据或可靠 Claim。本期增加：

| 字段 | 作用 |
| --- | --- |
| `execution_stage` | 内部阶段 |
| `stage_updated_at` | 停滞检测 |
| `next_attempt_at` | 非空且到期才可领取；waiting Digest 时为空，终态事件/Reconciler 再写入当前时间 |
| `execution_lease_owner`、`execution_lease_until` | 多实例 Report Run Processor 单飞推进 |
| `stage_attempts` | 当前 `execution_stage` 的失败重试次数；进入新阶段后清零 |
| `digest_wait_deadline_at` | Digest 等待独立时限 |
| `idempotency_key` | 同一 HTTP 语义请求重放返回同一 Run |
| `active_dedupe_key` | 双击或不同请求键的同内容活动 Run 去重 |
| `source_identity_set_sha256` | 实际冻结来源 identity 集合的规范化 hash，供去重审计 |
| `request_fingerprint` | 防止同一幂等键被不同请求复用 |
| `error_code`、`failure_stage` | 稳定内部诊断，不依赖解析错误文案 |
| `execution_input_json` | 仅后端读取的冻结执行参数；不得经 `AIRun` 接口返回 |

不新增事件溯源表、工作流历史表或通用 transition 表。

### 1.5 最小架构与模块接口

本期架构只增加完成 R1-R11 所需的两个执行模块和一个可观测性模块，并加深四个现有模块；不增加独立服务或通用工作流抽象。

| 模块 | 对外接口 | 内部职责 | 对应需求 |
| --- | --- | --- | --- |
| Report Run 提交模块（现有 Handler + Report Source） | `CreateReportRun(request) -> run_id` | 在一个数据库事务中完成请求幂等、Run 创建、Selection 创建/绑定和第一阶段冻结 | R1、R3 |
| Digest Coordinator（新增） | `EnsureDigest(identity, urgency)`、`EnsureRunDigests(runID, urgency)` | 定位 Revision，幂等创建/提权 Job，分类失败并受控重建，汇总 Run 依赖；不创建 Run、不提交 Agent | R2、R6 |
| Report Run 执行模块（新增 `internal/reportrun`） | `RunOnce()`、`ReconcileOnce()` | 每次 Claim 只执行一个 Stage，负责续租、阶段迁移、等待释放和过期 lease 恢复；隐藏 SQL 与重试实现 | R2、R5、R7 |
| Report Source 模块（现有，加深） | `FreezeRunDigests(runID)`、`RequireDigestFrozen(selectionID, runID)` | 集中维护 attached/frozen 不变量、冻结 Digest 快照并校验 hash/version | R3、R4、R9 |
| Report Context 模块（现有） | `Build(runID)`、`Get(runID)` | 在 Digest frozen 后一次性构建并返回不可变完整 Context；不截断内容、不设置大小硬上限 | R3、R8、R9 |
| Digest/Report 可观测性模块（新增） | `/internal/metrics` | 从数据库状态和执行事件输出低基数指标；不参与业务状态推进 | R10 |
| Digest V2 产物模块（现有，加深） | `Extractor.Result()`、`PrepareForPeriod()` | 生成 v2.10 完整结构化 Digest；不执行字节预算压缩、固定长度截断或总大小拒绝；兼容读取历史 v2.9 | R9、R11 |

调用方不直接拼装 Digest/Selection 状态 SQL，也不自行推断冻结完成。测试通过相同接口验证模块行为，不建立只供测试使用的平行接口。

## 2. 两阶段冻结

### 2.1 第一阶段：创建 Run 时冻结

Run 创建必须在一个本地数据库事务内完成：

1. 按用户和请求校验报告类型、周期、目标、Agent、模型、MCP 绑定和输入，计算不含可变数据库结果的 `request_fingerprint`；
2. 先按 `user_id + business_type + idempotency_key` 查询：同 fingerprint 返回原 Run，不同 fingerprint 返回冲突；命中时不重新解析默认来源；
3. 未命中时在同一 Repeatable Read 事务内解析本次实际来源，得到 Slice、Session、source、Generation、Projection Revision、cursor 范围和 content epoch 的完整集合；集合为空时请求失败，完全相同的 identity tuple 去重后再进入下一步；
4. 对实际来源集合排序并计算 `source_identity_set_sha256`，再计算 `active_dedupe_key`；
5. 生成 `run_id` 并插入包含 `active_dedupe_key/source_identity_set_sha256` 和冻结运行配置的 `ai_run` 以取得唯一权；唯一冲突时回滚当前事务并返回已存在 Run，不创建 Selection；
6. 插入赢家按步骤 3 的同一来源集合创建 Selection/Items，写入 `attached_run_id=run_id`，再把 Selection ID 写入 Run 的冻结执行输入；事务提交前 Run 必须已绑定 Selection；
7. Run 写入 `status=pending`、`execution_stage=waiting_digest`、`next_attempt_at=now()`，`started_at` 保持 NULL；
8. 提交事务后返回 `run_id`，不等待 Digest、Context 或 Agent。

此阶段冻结以下字段：

- `user_id`；
- 报告类型、日期/周期、时区、目标；
- Selection ID；
- 每个来源的 Slice、Session、source、Generation、Projection Revision、cursor 范围和 content epoch；
- Agent ID；
- 明确解析后的 Model ID，不能在稍后提交时再取可能变化的默认值；
- Initial Message；
- 用户 Start Prompt Values；
- 由 Aida 管理的系统 Prompt Values 输入；
- `trigger_source`、可空 `schedule_id`、可空 `scheduled_trigger_at`；
- Digest schema/version、redaction version、Report Context schema version；
- 非敏感字段写入 `input_ref_json`；Credential Override ID 等私有执行参数写入 `execution_input_json`；
- 不保存原始 bearer token，Worker 使用现有 Token Mint 能力生成当前用户的后端调用凭据。

注意：当前创建 Session 的请求只有 `agent_id`，创建 Run 时拿不到且提交时不能指定 `agent_version_id`。因此本期创建 Run 时只冻结 Agent ID、模型和运行输入；`ai_runs.agent_version_id` 保持 NULL，直到 AIHub 在任务信息中返回实际 Version ID 后再由现有 Status Syncer 写入。不得声称用户点击时已经冻结 Agent Version。该限制不阻塞 Digest P0，发布说明必须记录。

### 2.2 第二阶段：Digest ready 后冻结完整 Report Context

Report Run Processor 只按第一阶段冻结的身份定位 Digest：

```text
session_content_slice_id
+ source_generation_id
+ content_projection_revision_id
+ content_epoch_snapshot
+ digest_version
+ redaction_version
```

全部 ready 后依次经过 Selection 冻结事务、Context Build 自有事务和阶段提交事务，不能把现有会自行开启事务的 `reportcontext.Build` 嵌入 Selection 冻结事务：

1. 事务 A 锁定 Run 和 attached Selection，再次确认 Run 为 `pending + building_context`；
2. 事务 A 确认 Selection 只属于该 Run、每个 ready Revision 与冻结身份完全匹配；
3. 事务 A 写入每个 Selection Item 的 `digest_revision_id/digest_sha256_snapshot/digest_version_snapshot`；
4. 事务 A 生成并冻结 Selection Digest payload、版本、hash 和预算，写入 `digest_frozen_at` 后提交；
5. 调用现有 `reportcontext.Service.Build`，由它自己的 Repeatable Read 事务读取已冻结 Digest，同时读取需求、任务、下级报告、组织信息等其他报告事实，一次性构建完整 Report Context，并幂等写入 `report_run_contexts`；
6. 事务 B 锁定 Run，确认 Context hash 与已存记录一致，将 Context schema/hash/bytes 写入 Run；
7. 事务 B 条件迁移 `building_context -> submitting_agent`、重置 `stage_attempts`、设置 `next_attempt_at=now()`、清理执行 lease 并提交；
8. 当前 Processor 返回；`submitting_agent` 必须由下一次 Claim 执行。

`report_run_contexts.run_id` 主键和 `ON CONFLICT DO NOTHING` 保证重复构建返回同一 Context，不重新读取后来变化的业务数据。Context 一旦创建，本次 Run 的 Context Builder、Report MCP 和 Agent 后续步骤都只能读取这份冻结结果，不得再次查询并拼接最新业务事实。

准确的产品口径是：

> 用户点击时冻结报告范围、Session 来源身份和运行配置；完整 Report Context 在 Digest ready 后构建并冻结。

因此不能声称用户点击时已经冻结了需求、任务、下级报告、组织信息等全部报告事实。本期接受这些事实取自“Digest 全部 ready 后、Context 构建事务”的一致性视图；不为追求用户点击时刻的全量事实快照增加部分 Context、历史快照表或其他复杂设计。

### 2.3 新 Generation 与清理规则

Run 创建后 Session 又上传新 Generation 时：

- 本次 Run 仍按 Selection Item 中旧 `source_generation_id` 和旧 Projection Revision 构建；
- Coordinator 不查询或替换成当前 active Generation；
- Digest Processor 对“存在非终态 Run 依赖”的冻结身份，校验 Slice/Generation/Projection/cursor/epoch 和底层内容仍存在，但不再要求它仍是 active；
- 普通 background 预生成仍只服务当前 active 身份；
- 若 Session 被 clear、content epoch 改变或旧投影物理不可用，Run 明确失败，禁止读取新 Generation 代替。

这是满足“Run 创建后来源不漂移”的必要代码调整，不是历史版本通用化。

## 3. Run 与 Digest 依赖表达

### 3.1 Selection attached 与 Digest frozen 严格分离

`Selection attached` 只表示来源选择已经归属于某个 `ai_run`：

```text
report_source_selections.attached_run_id = run_id
```

它不表示 Digest 已存在、ready 或已冻结。创建并绑定 Run 时，Selection Item 的 `digest_revision_id/digest_sha256_snapshot/digest_version_snapshot` 以及 Selection 的 Digest payload/hash 可以为空。

本期在 `report_source_selections` 增加显式 `digest_frozen_at`，并由 Report Source Repository 提供统一的强校验接口：

```text
RequireDigestFrozen(selectionID, runID)
  -> FrozenDigestSelection | not_frozen | invalid
```

冻结成立必须同时满足：

- `attached_run_id` 与调用 Run 一致；
- `required_read_mode` 是本次 Run 冻结的 Digest 模式，不能退回 full content；
- `digest_frozen_at IS NOT NULL`；
- Selection 的 Digest payload、schema/version、redaction version、hash、预算字段完整；
- 每个 Selection Item 都有与冻结来源 identity 完全匹配的 ready Revision、hash 和 version；
- 重新计算的 payload/hash 与快照一致。

`digest_frozen_at` 是明确的完成标记，但不是绕过内容校验的唯一依据。跨 Selection/Item/Revision 的完整性由同一个冻结事务和 Repository 强校验保证；禁止各模块分别根据 nullable 字段自行推断。

现有数据库约束也要允许合法过渡态：Digest 模式 Selection 在 `digest_frozen_at IS NULL` 时可暂缺 Digest 字段；一旦写入 `digest_frozen_at`，所有必需字段必须完整。过渡态仍保持 Digest read mode，因此任何读取都不能误落入 full content 路径。

真实读取位置的调整如下：

- `reportsource.ReadAttachedSelection`：attached 校验后必须调用统一冻结门禁，再进入 Digest 读取，禁止未冻结时回退读取 full content；
- `reportcontext.Service.loadSessions`：继续通过 Report Source 接口读取，不自行判断 nullable 字段；
- Report MCP 的 attached Selection contract 解析只负责确认 Run/Selection 归属，真正读取前必须通过统一冻结门禁；
- `ValidateAttachedSelectionTx`、`readFrozenDigestV2Selection` 和 `validateFrozenDigestV2SelectionTx` 当前已有部分 hash/version 校验，应收敛复用同一冻结不变量，避免多套判断漂移；
- MCP 写回仍必须同时满足 Selection 已完整读取、Digest 已冻结和 Context hash 一致。

因此，`attached_run_id IS NOT NULL` 在任何位置都不能作为 Digest 可读条件。

### 3.2 复用现有依赖结构

现有结构已经能够持久表达依赖：

```text
ai_run.id
  <- report_source_selections.attached_run_id
  <- report_source_selection_items.selection_id
  -> frozen Slice/Generation/Projection/cursor/content_epoch
  -> matching session_slice_digest_revisions identity
```

因此本期不新增 Run-Digest 依赖表。

需要增加一个面向反向唤醒的组合索引：

```text
report_source_selection_items(
  session_content_slice_id,
  source_generation_id,
  content_projection_revision_id,
  content_epoch_snapshot,
  selection_id
)
WHERE session_content_slice_id IS NOT NULL
```

同时增加 `ai_runs(business_type, status, execution_stage, next_attempt_at, execution_lease_until)` 的部分索引，供 Report Run Processor/Reconciler Claim。

### 3.3 Coordinator 接口与职责

保留一个小接口、深实现的 `Digest Coordinator`：

```text
EnsureDigest(identity, urgency)
  -> ready | waiting | failed

EnsureRunDigests(runID, urgency)
  -> ready | waiting | failed
```

调用方：

- Content Projection fully indexed 后的 background 预生成；
- Digest Reconciler 漏单修复；
- Report Run Processor 对 `waiting_digest` Run 的按需确保；
- 失败恢复的后端受控路径。

Coordinator 负责：

- 只按冻结 identity 定位 Revision；
- missing 时事务内幂等创建 Revision 和 Job；
- background Job 提升为 interactive，但不改变 `status`、`attempts` 或 `next_retry_at`；
- building/leased 时复用现有构建；
- failed/dead 时按第 3.4 节执行永久失败判断或受控重建；
- 汇总一个 Run 的全部依赖；
- 返回稳定内部结果和错误码；
- 不创建 Run、不设置前端状态、不提交 Agent、不承担通用工作流。

### 3.4 Digest failed/dead 的分类与受控重建

现有 Revision identity 唯一约束继续保留。现有“同一 Revision 永久只能有一个 Job”的唯一索引改为：

```text
同一 digest_revision_id
+ job_type = build_content_slice_digest_v2
+ status IN (pending, leased, retry_wait)
-> 最多一个活动 Job
```

completed/dead Job 不删除、不重置，保留 attempts、last_error、created_at、started_at，并在进入 dead 时把现有 `completed_at` 写为终态时间，作为构建审计记录。每次受控重建创建一条新 Job，其 `payload` 固定记录：

```text
rebuild_round
trigger_run_id
previous_job_id
previous_error_code
scheduled_by = report_run_coordinator
```

Revision 增加并持久化：

```text
failure_class = retryable | permanent
failed_at
rebuild_count
last_rebuild_at
last_rebuild_run_id
```

数据库约束固定为：`status=failed` 时 `error_code/failure_class/failed_at` 均非空；`failure_class` 只能是 retryable/permanent；`rebuild_count` 取值 0..2；`rebuild_count>0` 时 `last_rebuild_at/last_rebuild_run_id` 均非空。安排重建时将 `status` 改回 pending，并清理 `error_code/failure_class/build_started_at`；ready Revision 继续使用现有不可变触发器保护。

失败分类固定如下：

| failure class | 稳定错误码 | 后端行为 |
| --- | --- | --- |
| permanent | `digest_v2_source_unavailable`、`digest_v2_identity_mismatch`、`digest_v2_version_unsupported`、`digest_v2_payload_corrupt` | 当前和以后依赖同一 identity 的 Run 直接 failed；只有新 Generation/content epoch/schema version 形成新 identity 后才能重新构建 |
| retryable | `digest_v2_build_cancelled`、`digest_v2_dependency_unavailable`、`digest_v2_state_persistence`、`digest_v2_build_failed` | 当前 Run failed；以后新的 Run 可触发下面的受控重建；未识别的构建错误统一映射为 `digest_v2_build_failed` |

普通 background 构建发现 active identity 已变化时仍按现有 superseded 路径完成，不记 failed；Run-pinned 构建发现冻结 identity 与底层数据不一致时使用 permanent 的 `digest_v2_identity_mismatch`。
`digest_v2_source_unavailable` 只用于数据库确认来源/Generation/Projection 已删除或 content epoch 已失效；对象存储、数据库或网络暂时不可访问必须使用 retryable 的 `digest_v2_dependency_unavailable`。

受控重建规则固定为：

- 代码常量 `digestRebuildMaxRounds=2`，不包含首次构建；每一轮新 Job 仍使用现有 `max_attempts=5`；该值不是运行配置；
- 代码常量 `digestRebuildCooldown=15m`，从 Revision 的 `failed_at` 起算；该值不是运行配置；
- `run.created_at > revision.failed_at` 的新 Run 调用 `EnsureDigest` 时，Coordinator 在一个事务中锁定 Revision 和活动 Job；只有 `failure_class=retryable`、`rebuild_count<2` 且不存在活动 Job 时才能安排重建；创建时间不晚于 `failed_at` 的原等待 Run 直接失败，不触发重建；
- 冷却尚未结束时，Revision 重置为 pending，并创建 `status=retry_wait`、`next_retry_at=failed_at+15m` 的 interactive Job；冷却已结束时创建 pending interactive Job；
- 同一事务递增 `rebuild_count`，写入 `last_rebuild_at/last_rebuild_run_id`，并在新 Job payload 中链接上一条 dead Job；并发 Run 只能由一个事务创建活动 Job；
- 新 Run 在受控重建期间保持 `waiting_digest`，由新 Job 终态事件恢复；触发重建不复活已经 failed 的旧 Run；
- permanent 或重建两轮仍失败时返回稳定错误 `DIGEST_PERMANENT_FAILURE` 或 `DIGEST_REBUILD_EXHAUSTED`，不得由前端请求清零计数；
- background Reconciler 不自动循环重建 failed Revision；本期只有 `run.created_at > revision.failed_at` 的新报告 Run 通过 Coordinator 触发，前端和其他调用方没有重建接口。

该设计复用 Revision 和 Processing Job，不新增报告请求表或工作流表；历史 dead Job 即每轮重建的审计记录。

## 4. Report Run Processor 完整推进链路

### 4.1 Claim 方式

`ai_run` 本身是持久请求和待推进事实。新增 Report Run Repository 使用：

```sql
SELECT ...
FROM ai_runs
WHERE business_type = 'report_agent_run'
  AND status = 'pending'
  AND execution_stage IN ('waiting_digest', 'building_context', 'submitting_agent')
  AND next_attempt_at IS NOT NULL
  AND next_attempt_at <= now()
  AND (execution_lease_until IS NULL OR execution_lease_until <= now())
ORDER BY next_attempt_at, created_at, id
FOR UPDATE SKIP LOCKED
```

Claim 后条件写入执行 lease，并记录本次 `claimed_stage`。Report Run 不写入 `session_processing_jobs`，因为该表现有 schema 强制 `session_id NOT NULL` 且随 Session 级联删除，语义不适合 Run。

Report Run Processor 数量读取 `REPORT_RUN_PROCESSOR_COUNT`，默认值和测试服/生产首发显式配置值均为 `20`。每 2 秒 Claim 一次、每个 Processor 每次 Claim 1 个 Run。该配置只限制 Report Context 构建和 Agent 提交等 Run Stage 的并发，不属于 Digest 队列或 Digest Worker 容量。P02 未通过时阻塞发布并修改本架构，不允许实现者自行选择其他并发数。

`REPORT_RUN_PROCESSOR_COUNT` 的有效范围是 `1..256`。配置缺失时使用 `20`；空字符串、非整数、0、负数或大于 256 时进程启动失败，禁止静默回退。测试服和生产部署文件必须显式配置；调整数量只修改部署配置并滚动重启 API，不修改代码、不重建镜像、不执行数据库迁移。

Report Run lease 规则固定如下：

- Report Run lease 固定为代码常量 `reportRunLeaseTTL=5m`，不是运行配置；该值是失联回收窗口，不是阶段 timeout 或生产 SLA；
- `building_context`、`submitting_agent` 执行期间每 1 分钟 heartbeat；
- heartbeat 必须使用条件更新：`WHERE id=run_id AND execution_lease_owner=owner AND execution_stage=claimed_stage AND status=pending`；更新影响行数为 0 时，当前 Processor 立即停止后续推进，不能继续写阶段结果；
- 阶段完成并迁移、进入 `waiting_digest`、确定失败或 timeout 时，在同一事务中清理 `execution_lease_owner/execution_lease_until`；
- 只有 lease 已过期，其他 Worker 或 Reconciler 才允许重新 Claim；Reconciler 不得抢占仍在正常续租的 Worker；
- 阶段结果写入必须再次校验 `run_id + lease_owner + claimed_stage`，状态迁移、`next_attempt_at` 更新和 lease 清理必须在同一事务完成；
- 进程崩溃未清 lease 时，不做主动抢占，等待 TTL 到期后恢复。

一次 Claim 只执行 Claim 时记录的一个 Stage：

```text
Claim(stage=S)
  -> 只执行 S
  -> 成功时迁移到 S+1、重置 stage_attempts
  -> 设置 next_attempt_at=now()
  -> 清理 lease
  -> Processor 返回
  -> 下一次 Claim 才能执行 S+1
```

同一个 Worker 进程可以在下一轮 poll 再次 Claim 同一 Run，但不得持有原 lease 跨 Stage 调用下一阶段。heartbeat 只为 `claimed_stage` 续租；阶段变化后旧 heartbeat 条件更新必须返回 0。

将原草案中的 `execution_attempts` 收敛并命名为 `stage_attempts`：它只表示当前 `execution_stage` 已发生的可重试失败次数。正常 Claim、heartbeat、Digest 仍在等待都不增加次数；同阶段发生可重试失败时递增，成功进入新 stage 时重置为 0。这样 `waiting_digest` 的唤醒次数或 `building_context` 的历史失败不会消耗 `submitting_agent` 的重试额度。

### 4.2 `waiting_digest`

```text
Processor Claim Run
  -> EnsureRunDigests(run_id, interactive)

ready
  -> 条件更新 waiting_digest -> building_context
  -> 重置 stage_attempts
  -> 设置 next_attempt_at=now()
  -> 清除 Run lease
  -> 当前 Processor 返回；下一次 Claim 执行 building_context

waiting
  -> 保持 waiting_digest
  -> 设置 next_attempt_at=NULL，等待 Digest 终态事件
  -> 清除 Run lease
  -> 当前 Processor 结束，释放执行槽位

failed
  -> status=failed
  -> failure_stage=waiting_digest
  -> 写稳定 error_code 和内部诊断
  -> 清除 Run lease
  -> 当前 Processor 返回
```

禁止 sleep、循环轮询或占用 Report Run Processor/Agent Worker 等待 Digest。

### 4.3 `building_context`

```text
Processor Claim Run
  -> 事务 A 锁 Run + attached Selection
  -> 重新确认全部 Digest ready 且 identity/hash/version 匹配
  -> 幂等冻结 Selection Digest 并提交
  -> Build 使用自身事务幂等写 report_run_contexts
  -> 事务 B 校验 Context hash
  -> building_context -> submitting_agent
  -> next_attempt_at=now()、stage_attempts=0、清除 lease
  -> 当前 Processor 返回
```

只有数据库连接失败、事务序列化失败和数据库死锁按 `next_attempt_at` 有界重试；其他 Context 构建错误不重试并以 `REPORT_CONTEXT_BUILD_FAILED` 结束 Run。来源快照不可用、Digest/hash/version 不匹配分别以 `REPORT_SOURCE_DIGEST_FAILED` 结束 Run。Context 不截断、不设置大小硬上限；超过 1 MiB 只写入非阻断提醒字段并继续下一 Stage。

### 4.4 `submitting_agent`

```text
Processor Claim Run
  -> 若 external_session_id 已存在：直接修复为 agent_running
  -> 使用冻结 user/agent ID/model/prompt/message/config
  -> 后端 mint 用户 token
  -> 按 run_id 查找或创建 Report MCP Credential
  -> 调用 AIHub CreateSession
  -> 成功时保存 external_session_id
  -> status pending -> running
  -> execution_stage submitting_agent -> agent_running
  -> started_at = now()
  -> 清除 Run lease
  -> 当前 Processor 返回
```

Credential 创建可复用现有 `ListCredentials`，按 metadata `ai_run_id` 找回已创建 Credential。外部 Session 当前没有同等找回或幂等接口，因此本期采用保守提交语义：

- `external_session_id` 已落库：禁止再次调用 CreateSession，直接修复阶段；
- CreateSession 调用前的本地参数校验、凭据生成或请求序列化失败：属于明确未发送，允许按 `stage_attempts` 有界重试；
- 一旦调用现有 HTTP Client，任何网络错误、超时、响应读取失败或结果无法确认都按状态未知处理：不得盲目重试，Run 直接进入 `failed`，稳定错误码为 `EXTERNAL_SUBMISSION_STATE_UNKNOWN`；
- AIHub 返回任意 4xx，或 2xx 响应明确包含业务失败结果：以 `EXTERNAL_SUBMISSION_REJECTED` 失败且不重试；任何 5xx 都按“状态未知”失败，不自动重试。

这能避免在未知窗口中主动启动第二个 Agent Session，但不能宣称外部 Agent 已做到绝对“最多启动一次”。AIHub 后续支持 `client_request_id = "aida-report-run:" + run_id` 的幂等创建/查询后，才可安全覆盖“外部已创建但响应未落库”的窗口。

### 4.5 `agent_running`、`writing_result` 与完成

- 现有 Run Status Syncer 只处理已经有 `external_task_id/external_session_id` 的 Run；
- Agent 读取 Report Context 时继续使用现有 run/user/hash 门禁；
- `write_report_result` 开始时条件更新 `agent_running -> writing_result`；
- 报告表写入、Selection 完整读取校验和 `ai_run succeeded/completed` 保持同一数据库事务；
- `write_report_failure` 将 Run 置为 failed 并记录 `failure_stage=agent_running/writing_result`；
- 相同报告结果重复写回继续复用现有 `report_result_hash` 幂等逻辑。

## 5. Digest 完成自动恢复与 Reconciler

### 5.1 正常唤醒

Digest Worker 将 Revision 提交为 ready 或最终 failed 后，执行轻量条件唤醒：

```text
Digest Revision 进入终态
  -> 通过冻结 identity 反向查找 attached Selection
  -> 找到 status=pending + stage=waiting_digest 的 ai_run
  -> SET next_attempt_at=now()
  -> Report Run Processor 再次 Claim
  -> EnsureRunDigests 汇总全部依赖
```

一次 Run 依赖多个 Digest 时，任一完成事件都可以重复唤醒；只有全部 ready 才能迁移到 `building_context`。唤醒只是条件更新，不直接执行 Context 或 Agent。

### 5.2 Report Run Reconciler 兜底

Report Run Reconciler 默认每 30 秒执行一次、每批最多处理 100 个可恢复候选 Run，使用与 Report Run Processor 相同的条件更新和 lease 规则。它不得周期性调用 `EnsureRunDigests` 检查所有 `waiting_digest` Run。

Reconciler 只执行以下数据库可直接判定的恢复查询：

- `waiting_digest` 且全部 Digest 已 ready：设置 `next_attempt_at=now()`；
- `waiting_digest` 且任一 Digest 已 failed/dead：设置 `next_attempt_at=now()`；原等待 Run 由 Coordinator 按失败码终结，只有创建时间晚于 Revision `failed_at` 的新 Run 才能安排受控重建；
- `waiting_digest` 且 `digest_wait_deadline_at<=now()`：直接条件更新为 timeout；
- `building_context/submitting_agent` 且 execution lease 已过期：设置 `next_attempt_at=now()`；
- Context 已存在但仍为 `building_context`，或 `external_session_id` 已存在但仍为 `submitting_agent`：按已落库事实条件迁移并清 lease。

仍存在 pending/retry_wait/leased Digest 且未到 deadline 的 waiting Run 不进入 Reconciler 候选集，因此 5000 个 waiting Run 不会每 30 秒重复执行 Coordinator 或逐 Run 查询。正常推进只依赖 Digest 终态事件；Reconciler 只修复漏事件、终态未推进、过期 lease 和 timeout。

恢复动作只更新同一个 Run 的 `next_attempt_at` 或进行带前置条件的阶段迁移，不创建新 Run。正常回调、Digest 事件和 Reconciler 并发时，行锁/条件更新保证只有一个推进者成功。

Reconciler 对持有未过期 lease 的 Run 只观察、不修改；只有 lease 过期或当前阶段根本没有 lease 时才允许唤醒/Claim。对 `building_context/submitting_agent` 的恢复必须先依据已落库事实判断阶段结果：Context 已存在则校验后前移，Session ID 已存在则前移；否则按当前 stage 重新执行。任何迁移都要带原 stage/lease 条件并在同一事务清理旧 lease、重置新 stage 的 `stage_attempts`。

Reconciler 只确认已经落库的当前 Stage 结果并迁移 Stage，不执行迁移后的下一 Stage；迁移时设置 `next_attempt_at=now()` 并清 lease，下一 Stage 仍由新的 Worker Claim 执行。

Processing Job lease 过期继续由现有 `PostgresJobRepository.ClaimTypes` 回收；Run lease 过期由 Report Run Repository/Reconciler 回收，两者语义分离。

## 6. Digest interactive/background Claim 与容量隔离

### 6.1 数据和提权

在现有 `session_processing_jobs` 增加：

```text
urgency = background | interactive
urgency_raised_at
```

规则：

- Projection 主动预生成和 Digest Reconciler 使用 background；
- 非终态 Run 依赖的 Digest 使用 interactive；
- 已有 Job 只条件更新 urgency，不创建第二个 Job；
- pending/retry_wait 提权时只执行 `urgency='interactive', urgency_raised_at=COALESCE(urgency_raised_at, now())`，保留原 `status`、`attempts` 和 `next_retry_at`；已是 interactive 时不更新；
- retry_wait 即使已提升为 interactive，也必须等原 `next_retry_at<=now()` 后才能领取；
- leased/building 只记录 urgency，当前构建继续，不抢占、不重复；
- Revision/Job 唯一索引继续保证单飞。

### 6.2 P0 两类 Worker 与具体 Claim

为 `PostgresJobRepository` 增加带 urgency/worker role 的 Digest Claim，不修改 Session 内容、Usage 和 Token Worker 的现有 Claim。本期只保留两个确定性角色：

```text
interactive Worker:
  WHERE job_type=DigestV2 AND urgency='interactive'
  ORDER BY ready_at, created_at, id

background Worker:
  WHERE job_type=DigestV2 AND urgency='background'
  ORDER BY ready_at, created_at, id
```

部署和容量规则：

- background Worker 数量读取 `DIGEST_BACKGROUND_WORKER_COUNT`，默认值和测试服/生产首发显式配置值均为 `20`；
- interactive Worker 数量读取 `DIGEST_INTERACTIVE_WORKER_COUNT`，默认值和测试服/生产首发显式配置值均为 `20`；
- 任一环境不得把其中一类配置为 0。P01 失败时阻塞发布并重新评审本架构，开发者不得自行改并发数绕过验收；
- interactive Worker 只领取 interactive，background backlog 不能占用其容量；
- background Worker 只领取 background，持续 interactive 流量不会使 background 永久饥饿；
- pending/retry_wait Job 被提权后只会被 interactive Worker 领取；
- 已 leased/building 的同一 Digest 继续由当前 Worker 完成，即使 urgency 已提升也不抢占、不重建；
- 本期不实现 shared Worker，不设计空闲容量借用；
- 增加索引 `(job_type, urgency, status, next_retry_at, lease_until, created_at)`；
- 两类 Worker 均沿用现有 2 秒 poll interval、5 分钟 Processing Job lease 和 TTL/3 heartbeat；不修改 Digest `WorkerBatch=1`。

在 5000 个 background Job 排队时，新 interactive Job 的 Claim 查询必须只扫描 interactive 候选并使用匹配索引，其领取时间不得随 background 队列长度线性增长。测试服记录实际领取时延；首发并发配置固定为 20 个 background、20 个 interactive，P01 失败则阻塞发布。

### 6.3 Digest Worker 并发配置接口

Digest 容量只包含以下两项；Report Run Processor 的配置属于 4.1，不得在本节计入 Digest Worker：

| 配置键 | 默认值 | 有效范围 | 作用 |
| --- | --- | --- | --- |
| `DIGEST_BACKGROUND_WORKER_COUNT` | `20` | `1..256` | 只领取 background Digest 的 Worker 实例数 |
| `DIGEST_INTERACTIVE_WORKER_COUNT` | `20` | `1..256` | 只领取 interactive Digest 的 Worker 实例数 |

启动规则固定如下：

- 配置缺失时使用表中默认值；空字符串、非整数、0、负数或大于 256 时进程启动失败，禁止静默回退；
- 测试服和生产部署文件必须显式写出两项首发值，不能依赖默认值，使实际容量可审计；
- 配置只在进程启动时读取。调整并发只修改部署环境变量并滚动重启 API，不修改代码、不重建镜像、不执行数据库迁移；
- `api/main.go` 禁止保留 `digestV2WorkerIDs := []string{"1", "2"}` 或其他按字面量数组决定数量的实现；统一配置模块完成解析和校验，装配层只按已校验数量创建 Worker；
- lease owner 格式统一为 `<hostname>:<role>:<ordinal>`；`role` 仅允许 `report-run`、`digest-background`、`digest-interactive`，`ordinal` 从 1 到配置值；`hostname` 固定取 `os.Hostname()`，读取失败或结果为空时进程启动失败；同一部署内不得重复；
- `WorkerBatch=1`、两类 Digest Claim 隔离和一次 Report Claim 只执行一个 Stage 不随并发配置变化；禁止通过提高 batch 模拟提高 Worker 数量；
- 启动日志和指标必须分别输出两类 Digest Worker 的最终生效数量。P08 必须证明同一镜像仅修改配置并重启即可改变实际 Worker 数量。

### 6.4 Digest 不按大小删减内容

本期把新产物版本固定升级为 `session-digest/v2.10.0`。版本号属于数据库产物身份，不进入 Worker 环境变量名。

v2.10 生成规则固定如下：

- 删除 `sessiondigestv2.Config.ItemMaxBytes`、`DefaultItemBytes`、`DefaultPeriodItemBytes` 和 `minimumItemBytes`；
- `Extractor.Result()` 不再接收 `itemMaxBytes`，直接序列化完整 Digest；
- `PrepareForPeriod()` 不再接收 `maxBytes`，不再调用 `EnforceItemBudget`；
- 删除 V2 `EnforceItemBudget`、`CompactDigest`、`CompactReportPeriodSummary` 及其只为字节预算服务的辅助函数；
- 删除进入 Digest schema 后的固定长度截断：用户目标、Agent 最终结果、未解决事项、变更、校验和证据摘要均保留规范化后的完整文本；
- 继续执行现有脱敏规则、支持事件类型筛选、空白规范化、噪声事件排除和完全相同内容去重；这些规则决定“什么属于 Digest schema”，不得再根据产物大小对已进入 schema 的内容排序、截断或删除；
- `coverage.omitted_event_count` 只统计没有进入 Digest schema 的事件；`coverage.truncated` 对新 v2.10 产物固定为 `false`，不得因大小设为 `true`；
- `digest_bytes` 记录真实序列化大小，Digest SHA-256 继续按完整字节计算；数据库写入失败按 Digest 构建失败处理，不回退到压缩产物。

Selection Digest V2 组装规则固定如下：

- `assembleDigestV2Payload` 只组装并序列化一次，不调用任何 Compact 函数，不再返回 `ErrDigestLimitExceeded`；
- v2.10 payload 使用 `size.actual_bytes`、`size.warning_threshold_bytes=1_048_576` 和 `size.warning`，不再使用 target/hard limit 或 compaction 语义；
- v2.10 Selection 写入 `selection_digest_compaction='none'`，`digest_target_bytes_snapshot/digest_hard_limit_bytes_snapshot=NULL`；迁移必须调整约束，仅对 v2.10 允许这组确定值；v1/v2.9 历史行继续满足旧约束；
- `reportsource.ProductConfig()` 固定使用 v2.10 且 target/hard limit 均为 0；`reportsource.Config` 的 target/hard 字段只供 legacy v1 生成使用，v2.10 构建不得读取；v2.9 历史读取只相信 Selection 已冻结的 snapshot，不读取当前 ProductConfig；
- `ReadAttachedSelection` 按 Selection 已冻结的 `digest_version_snapshot` 选择 validator：v2.9 使用现有 budget/hash 校验，v2.10 使用 size/hash 校验；不得用当前配置版本拒绝历史已冻结 Selection；
- 新 Run 的 Digest Version 固定为 v2.10，只创建/绑定 v2.10 Revision；现有 v2.9 Revision、Job、Selection、Context 和 Run 不修改、不删除；
- 部署后 background Reconciler 为 active identity 幂等创建 v2.10 Job；用户新 Run 需要的 v2.10 Job按第 6.1 节提权为 interactive。v2.9 存量数量不得影响 interactive Claim 查询。

1 MiB 只作为第 10 节的提醒阈值，不是 Digest、Selection Digest 或 Report Context 的拒绝条件。

## 7. 事务、幂等、唯一性与并发控制

### 7.1 用户请求与 Run

在报告启动请求 JSON 增加必填字符串字段 `idempotency_key`：手工生成时前端在一次点击开始时生成 UUID v4，并在该次请求的网络自动重试中复用；缺失或不是 UUID v4 返回 HTTP 400 和 `INVALID_IDEMPOTENCY_KEY`。定时报告由服务端使用 `schedule_id + ":" + scheduled_trigger_at.UTC().Format(time.RFC3339Nano)` 生成，不接收前端值。生成按钮直接把现有 `selected_session_slice_keys` 提交给 Run 启动接口，不再先调用 Selection 创建接口。真正去重由数据库完成，不依赖按钮禁用。

数据库约束：

```text
UNIQUE(user_id, business_type, idempotency_key)

UNIQUE(active_dedupe_key)
WHERE business_type='report_agent_run'
  AND status IN ('pending', 'running')
```

`request_fingerprint` 与 `active_dedupe_key` 使用不同输入：

- `request_fingerprint` 固定包含 report type/target/period/timezone、排序后的 `selected_session_slice_keys`（默认来源时为显式 `null`）、agent/model、initial message、全部 prompt values、trigger source、schedule ID/trigger time 和 schema versions；它不读取数据库来源状态，只用于确认相同 `idempotency_key` 是否是同一次网络重放；
- `active_dedupe_key` 必须基于事务内实际解析并将写入 Selection Items 的来源 identity，禁止使用 Selection ID、“默认来源规则”或未解析的 Slice Key 代替实际来源。

实际来源集合的每一项固定包含：

```text
session_content_slice_id
session_id
source_id
session_ref_snapshot
agent_type
source_generation_id
content_projection_revision_id
content_epoch_snapshot
start_cursor
end_cursor
```

按上述 tuple 做字典序排序。Canonical JSON 固定使用 UTF-8、对象 key 字典序、无多余空白、UUID 小写字符串、整数十进制、空值显式 `null`；顶层格式为 `{"items":[...]}`。对该字节串计算 SHA-256 得到 `source_identity_set_sha256`。`request_fingerprint` 和 `active_dedupe_key` 使用同一编码规则；`active_dedupe_key` 再对以下字段计算 SHA-256：

```text
user_id + business_type
report_type + report_target + period_start/end + timezone
source_identity_set_sha256
agent_id + resolved_model_id
initial_message + start_prompt_values + system_prompt_values
trigger_source + schedule_id + scheduled_trigger_at
digest/redaction/context schema versions
```

去重规则：

- 同一 idempotency key + 同一 fingerprint：返回原 Run；
- 同一 idempotency key + 不同 fingerprint：返回 HTTP 409 和 `IDEMPOTENCY_KEY_REUSED`；
- 双击产生不同 idempotency key，但同内容 Run 仍在 pending/running：返回活动 Run；
- 原 Run 终态后，用户可再次主动生成新 Run；
- 定时报告使用 `schedule_id + scheduled_trigger_at` 作为确定性 idempotency key。

事务必须先查询 idempotency key，再解析实际来源并计算活动去重键；只有取得活动 Run 唯一权的事务才能按同一来源快照创建 Selection。冲突事务不得留下孤立 Selection。显式 Selection 继续依赖 `attached_run_id` 唯一约束，只能绑定一个 Run。

### 7.2 各阶段幂等保证

| 风险 | 保证方式 |
| --- | --- |
| 两个实例并发创建 Run | 幂等/活动去重唯一索引 |
| HTTP 返回前断网 | 相同 idempotency key 查询并返回已提交 Run |
| 同一 Digest 多个 Run 依赖 | Revision/Job 唯一索引 + lease |
| 两个 Worker 恢复同一 Run | Run lease + `FOR UPDATE SKIP LOCKED` + 条件阶段更新 |
| Digest 事件与 Reconciler 并发 | 都只做幂等唤醒/条件迁移 |
| Context 重复构建 | `report_run_contexts.run_id` 主键 + immutable Get/Build |
| Agent 请求明确未发出 | 当前 stage 有界重试 |
| Agent 请求结果不确定 | 不盲重试；Run 以 `EXTERNAL_SUBMISSION_STATE_UNKNOWN` 失败 |
| 已保存 external_session_id 后重复投递 | Worker 检测已有 ID，禁止再次 CreateSession |
| 报告结果重复写回 | 现有 result hash、Run/Selection/Context 门禁 |

### 7.3 本期 P0 与外部能力缺口

本次 Digest P0 必须完成：

- Digest 等待完全由后端推进，不依赖前端在线或重试；
- Run 创建和 Selection 绑定、Digest 单飞、冻结门禁、Context 构建均在本地幂等；
- 已落库 `external_session_id` 时绝不重复提交；
- Status Syncer 不处理 pre-Agent Run；
- 外部提交结果不确定时保守失败，不制造已知的重复 Session 风险。

已确认的 AIHub 外部能力缺口只有两项：CreateSession 不接受幂等请求键且不能按 Run 查询 Session；CreateSession 不接受 `agent_version_id`。这两项不进入本期开发任务，也不阻塞 Digest 排队 P0。在 AIHub 接口实际补齐前，本期固定执行上面的保守失败规则，不能声称外部 Agent Session 绝对最多创建一次，也不能声称 Agent Version 已在用户点击时冻结。

## 8. timeout、失败和重试

### 8.1 固定执行参数与 timeout 起算点

| 参数 | 本期值 | 语义 |
| --- | --- | --- |
| Report Run Claim interval/batch | 2 秒 / 每 Worker 1 个 | 只领取到期且无有效 lease 的 Run |
| Report Run lease/heartbeat | 5 分钟 / 1 分钟 | heartbeat 丢失后等待 lease 过期恢复 |
| Report Run Reconciler interval/batch | 30 秒 / 100 | 漏事件、崩溃和停滞 Run 的兜底扫描 |
| Digest wait timeout | 60 分钟 | 只计算 `waiting_digest`；到期置 `timeout` |
| `building_context` 单次执行 timeout | 10 分钟 | 单次超时计为一次当前 stage 可重试失败 |
| `building_context` 最大失败次数 | 5 | 耗尽后 Run failed |
| `submitting_agent` HTTP timeout | 沿用现有 30 秒 | 一旦进入 HTTP Client 后超时即按外部状态未知失败 |
| `submitting_agent` 明确未发送最大失败次数 | 5 | 仅限调用 HTTP Client 前失败 |
| 阶段重试间隔 | 5、10、20、40 秒 | 前四次失败写入 `next_attempt_at`，第五次失败后不再调度 |

- `created_at`：用户提交 Run 的时间；
- `digest_wait_deadline_at`：创建 Run 时固定为 `created_at + 60m`；
- `started_at`：外部 Agent Session 成功创建并落库的时间；
- 现有 Agent 执行 timeout 从 `started_at` 起算，不包含 Digest 排队和 Context 构建；
- `building_context` 和 `submitting_agent` 按上表使用 `stage_attempts`，不复用 Agent 执行 timeout；
- Status Syncer 不再把 `waiting_digest/building_context/submitting_agent` 当作“10 分钟未提交的遗留 pending Run”处理。

当前 Status Syncer 实际对外部执行使用 2 小时 timeout；`ManagedAgentSessionTimeout=30m` 只在定时任务活动 Run 检查中使用。P0 不顺带统一这两个既有口径，只确保 pre-Agent 等待不消耗它们。

### 8.2 失败分类

| 阶段 | 场景 | 自动处理 | Run 结果 |
| --- | --- | --- | --- |
| waiting_digest | Job `retry_wait` | 保留原 `next_retry_at`；提权不绕过退避 | 保持 pending |
| waiting_digest | Job dead / Revision failed，failure_class=retryable | 当前 Run 不自动复活；以后新 Run 按 2 轮、15 分钟冷却规则受控重建 | 当前 Run failed |
| waiting_digest | Job dead / Revision failed，failure_class=permanent | 同 identity 不重建；等待新 Generation/content epoch/schema version | failed，`DIGEST_PERMANENT_FAILURE` |
| waiting_digest | retryable 重建次数耗尽 | 不再自动创建 Job | failed，`DIGEST_REBUILD_EXHAUSTED` |
| waiting_digest | corrupt/version mismatch | 归类 permanent，不降级、不读新版本代替 | failed |
| waiting_digest | 超过 Digest deadline | 停止等待 | timeout |
| building_context | 数据库连接失败、事务序列化失败、数据库死锁 | Report Run Processor 最多重试 5 次 | 耗尽后 failed，`REPORT_CONTEXT_BUILD_FAILED` |
| building_context | 来源快照不可用、Digest/hash/version 不匹配 | 不重试 | failed，`REPORT_SOURCE_DIGEST_FAILED` |
| building_context | Context 构建的其他错误 | 不重试 | failed，`REPORT_CONTEXT_BUILD_FAILED` |
| submitting_agent | HTTP Client 调用前的参数校验、凭据生成或请求序列化失败 | 当前 stage 最多重试 5 次 | 耗尽后 failed，`EXTERNAL_SUBMISSION_PREPARE_FAILED` |
| submitting_agent | 请求结果不确定 | 禁止盲重试 | failed，`EXTERNAL_SUBMISSION_STATE_UNKNOWN` |
| submitting_agent | AIHub 返回任意 4xx | 不重试 | failed，`EXTERNAL_SUBMISSION_REJECTED` |
| agent_running | Agent 返回失败 | 复用现有状态同步/`write_report_failure` | failed |
| agent_running | 执行超时 | 复用现有 Agent timeout | timeout |
| writing_result | 完整性/hash/权限校验失败 | 当前写回事务回滚并将 Run failed | failed |
| writing_result | 外部任务已结束但 2 分钟内没有成功写回 | 复用现有 `ManagedAgentReportWritebackGrace=2m` | failed，`REPORT_WRITEBACK_TIMEOUT` |

所有失败对用户只表现为现有 Run failed/timeout 和现有结果展示；底层 failure class、failure stage、stage attempts、Digest Revision/Job ID 只用于日志和运维诊断。Digest 永久失败和重建耗尽使用统一的报告数据准备失败文案，不暴露 Digest 内部状态。Context 大小不属于失败条件。

## 9. 生产可观测性与告警

当前 API 没有 Prometheus metrics 接口。本期使用 `github.com/prometheus/client_golang/prometheus` 和 `promhttp`，在 API 进程增加独立内部 listener：环境变量 `AIDA_INTERNAL_METRICS_ADDR`，默认 `:9091`，路径 `/internal/metrics`，生产 scrape interval 固定为 15 秒。Compose 只对内部监控网络 expose 9091，不发布 host port，Nginx 不代理该端口。生产监控系统必须完成抓取和 `deploy/monitoring/digest-report-rules.yml` 规则加载后才能发布。

所有指标 label 只能使用枚举值 `urgency/status/stage/result/failure_class/reason/scope`，禁止使用 `user_id/run_id/session_id/job_id/revision_id`，避免高基数。具体对象 ID 只写结构化日志。

### 9.1 必须输出的指标

| 指标 | 类型 | 定义 |
| --- | --- | --- |
| `aida_digest_jobs{urgency,status}` | gauge | 两类 Digest Job 的 pending/retry_wait/leased 活动数量；历史 completed/dead 不进入 gauge |
| `aida_digest_oldest_eligible_wait_seconds{urgency}` | gauge | 当前已满足 `next_retry_at<=now()` 的最老可领取 Job 等待时间 |
| `aida_digest_claim_latency_seconds{urgency}` | histogram | `eligible_at` 到成功 lease 的时间；`eligible_at=max(created_at, urgency_raised_at, next_retry_at)` |
| `aida_digest_build_duration_seconds{urgency,result}` | histogram | 单次 Digest 构建执行时间 |
| `aida_digest_build_total{urgency,result,failure_class}` | counter | Digest 构建结果计数 |
| `aida_digest_rebuild_total{result,reason}` | counter | 受控重建 scheduled/rejected/exhausted 计数 |
| `aida_report_runs{status,stage}` | gauge | pending/running Report Run 各内部阶段数量；终态 Run 不进入 gauge |
| `aida_report_run_oldest_stage_seconds{stage}` | gauge | 各非终态 stage 最老停留时间 |
| `aida_report_run_lease_expired_total{stage}` | counter | Run lease 过期并被回收次数 |
| `aida_report_run_reconcile_total{reason,result}` | counter | Reconciler 候选、恢复成功和失败次数 |
| `aida_report_run_digest_wakeup_total{result}` | counter | Digest 终态唤醒 waiting Run 的成功/失败次数 |
| `aida_worker_configured{role}` | gauge | 当前进程已启动的 Worker 数量；role 仅为 `report_run/digest_background/digest_interactive` |
| `aida_digest_payload_bytes{scope}` | histogram | v2.10 完整 payload 大小；scope 仅为 `item/selection/context`；bucket 固定为 64 KiB、256 KiB、1 MiB、4 MiB、16 MiB、64 MiB、256 MiB、+Inf |
| `aida_digest_payload_over_warning_total{scope}` | counter | payload 大于 1 MiB 的次数；只告警和观测，不改变构建结果 |

队列数量、最老等待和 Run stage gauge 由带索引的只读聚合查询在 scrape 时计算；Claim、构建、重建、lease、唤醒和 Reconciler counter/histogram 在对应事务成功或操作失败后记录。指标失败不得改变业务事务结果，但必须写错误日志。

枚举固定为：Digest `result=completed|retry_wait|dead`，`failure_class=none|retryable|permanent`；rebuild `result=scheduled|rejected`，`reason=cooldown|permanent|exhausted|active_job|scheduled`；Reconciler `reason=digest_terminal|deadline|lease_expired|context_persisted|session_persisted`，`result=success|conflict|failure`；wakeup `result=success|noop|failure`；payload `scope=item|selection|context`。

### 9.2 首发告警规则

| 告警 | 固定触发条件 | 级别 |
| --- | --- | --- |
| `DigestInteractiveEligibleStuck` | interactive 最老可领取等待时间 `>30s`，持续 5 分钟 | critical |
| `DigestInteractiveClaimLatencyHigh` | interactive Claim latency p95 `>10s`，持续 10 分钟 | critical |
| `DigestBackgroundBacklogOld` | background 最老可领取等待时间 `>30m`，持续 15 分钟 | warning |
| `DigestBuildFailureRateHigh` | 15 分钟内构建数 `>=20` 且失败率 `>10%` | critical |
| `DigestInteractiveJobDied` | 5 分钟内 interactive `result=dead` 的构建计数增量 `>0` | critical |
| `DigestRebuildExhausted` | 10 分钟内 `reason=exhausted` 增量 `>0` | critical |
| `ReportWaitingDigestOld` | `waiting_digest` 最老停留时间 `>15m`，持续 10 分钟 | warning |
| `ReportBuildingContextStuck` | `building_context` 最老停留时间 `>10m`，持续 5 分钟 | critical |
| `ReportSubmittingAgentStuck` | `submitting_agent` 最老停留时间 `>5m`，持续 5 分钟 | critical |
| `ReportRunLeaseExpired` | 10 分钟内 lease expired 增量 `>0` | warning |
| `ReportRunReconcileFailure` | 5 分钟内 Reconciler failure 增量 `>0` | critical |
| `ReportDigestWakeupFailure` | 5 分钟内 Digest wakeup failure 增量 `>0` | critical |
| `DigestReportMetricsMissing` | 生产连续 5 分钟抓取不到 `/internal/metrics` | critical |

告警阈值是首发固定值，只能通过后续评审过的监控规则变更调整，不能由实现者或运行时自行选择。

### 9.3 告警运行手册

告警必须链接到同一运行手册，处理顺序固定为：

1. 查看 interactive/background 的数量、最老 eligible wait 和 Claim latency，区分 Claim 饥饿与构建变慢；
2. 查看 build failure class、最近 dead Job、Revision 和关联结构化日志；
3. 查看各 Run stage 最老停留、lease expired、wakeup 和 Reconciler 结果；
4. 检查数据库连接池/CPU/I/O、API 内存和外部 AIHub 状态；
5. 只调整对应角色 Worker 配置，不把 background Worker 临时改成 shared，也不清零 attempts/rebuild_count；
6. 需要重建时只能调用 Coordinator 的受控路径，禁止直接更新 Revision/Job 状态绕过冷却、次数和审计。

## 10. 前端边界

前端保持：

```text
点击生成
  -> 获得 run_id
  -> 保存 activeRunId
  -> pending/running 展示生成中
  -> 读取现有 Run 结果
```

允许的最小无感改动只有：

- 启动请求携带一次点击生成的 `idempotency_key`，网络重试复用；
- 将已选 Slice Keys 直接放入现有 `selected_session_slice_keys`，不再在启动前单独创建 Selection；
- 接受更快返回的 `pending` Run。

不得新增：

- Digest preparing 页面、进度或文案；
- missing/pending/building/failed/dead 展示；
- Selection 等待恢复；
- 定时重试启动接口；
- interactive/background 概念；
- 页面必须保持打开的逻辑。

当前生成控件会先调用 Selection 创建接口，而该接口又调用 `PrepareExplicitSelection` 提前冻结 Digest，这是本次竞态的另一个入口，也会让双击在 Run 去重前产生多个 Selection。生成控件改为直接提交已有 `selected_session_slice_keys`，由 Run 创建事务生成唯一 Selection。独立 Selection 接口保留给现有非生成调用方，但只创建来源选择，不冻结 Digest，也不因 Digest 未 ready 返回 409。

大上下文只保留一套产品行为：

- 用户点击一次即提交 Run，不在 Digest ready 后要求第二次确认；
- Digest 和完整 Report Context 均不设置大小硬上限，不截断内容，不因内容大将 Run 置为 failed；
- `building_context` 得到不可变 Context 后按现有阈值 `1 MiB` 判断：`context_bytes > 1_048_576` 时在现有公开字段 `ai_run.input_ref_json` 写入 `large_context_warning=true` 和 `report_context_bytes`，等于阈值时写入 bytes 但不写 warning；这两个字段不新增数据库列；
- 前端从现有 Run 轮询响应的 `input_ref_json.large_context_warning` 读到 `true` 后，每个浏览器对同一 `run_id` 最多展示一次非阻断提示：“报告上下文较大，可能消耗较多 Token，请确认所选模型支持足够的上下文长度。”已展示标记写入现有 Run 本地存储记录，页面刷新后不重复提示；提示不提供确认按钮、不停止生成、不重试启动接口；
- 页面关闭不会影响生成；用户未看到提醒也不会改变 Run 结果；
- 删除现有 `confirmation_required` 和 `confirmLargeReportContext` 报告启动分支；保留请求字段 `large_context_confirmed` 仅为兼容旧客户端，后端忽略其值。

## 11. 明确不做

- 不新增独立 Report Generation Request；
- 不依赖前端轮询推动流程；
- 不暴露 Digest 准备状态；
- 不在 HTTP 请求中同步构建 Digest；
- 不让 Report Run Processor sleep 或阻塞等待；
- 不重新读取未冻结的最新 Session/Generation；
- 不生成空 Digest、残缺 Context 或残缺报告；
- 不引入通用状态机、River、Temporal、Celery 或新任务框架；
- 不把 Report Run 塞进要求 Session 语义的 Processing Job；
- 不设计通用工作流平台；
- 不改造无关的普通 Agent 执行架构；
- 不让 Selection 承担 Run、等待或重试职责；
- 不把 `attached_run_id` 当作 Digest ready/frozen 条件；
- 不为用户点击时刻的全部业务事实增加部分 Context 或历史快照表；
- 不设置 Digest/Report Context 大小硬上限，不在 Digest ready 后增加大上下文二次确认；
- 本期不实现 shared Digest Worker；
- 不修改 Claude Code/Codex 上传和 Token 统计业务逻辑。
