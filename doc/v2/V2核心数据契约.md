# Aida V2 核心数据契约

## 1. 文档状态

- 状态：开发验证中；Session 与 Token 影子链路已有可执行契约测试，生产切换仍未开放
- 产品基线：`doc/v2/V2产品需求总稿.md`
- 适用专题：Session 增量上传与内容管理、个人报告来源选择、Token 统计与成本管理
- 用途：定义三个专题必须共同遵守的数据身份、状态、时间和统计不变量
- 非用途：不定义页面布局、CLI 交互细节和价格管理操作流程

本文是共享技术规则的唯一来源。专题文档不得复制后修改本文规则；需要变更时必须先修改本文，再同步专题验收项。

## 2. 最终架构

```text
Claude Code / Codex 本地日志
              |
              v
Aida CLI：发现来源、按完整行切 Chunk、上传原始内容
              |
              v
Session Source / Generation / Immutable Chunk
              |
              v
服务端结构扫描与处理任务
       |                         |
       v                         v
Session Content Projection   Provider Usage Parser
       |                         |
       v                         v
报告候选与 MCP 内容读取       Usage Observation Ledger
                                 |
                                 v
                         Logical Usage Event Fold
                                 |
                                 v
                       Versioned Token Normalizer
                                 |
                                 v
                       Active Metrics Revision
                                 |
                                 v
                  Daily/Model Usage -> 价格与汇率快照
                                 |
                                 v
                          Token/成本查询
```

权威边界：

1. CLI 负责可靠发现和上传原始 Chunk。
2. 服务端负责内容事件索引，以及权威 Usage 解析、观测折叠、累计值差分、Token 归一化和聚合。
3. CLI 可以显示本地 Token 预览，但预览不能写入服务端权威统计。
4. 服务端不能直接信任客户端提交的 Session 总 Token 或 Daily Usage。
5. 原始内容、内容投影、派生统计和成本是四个不同生命周期，不能使用一个状态字段代替。
6. 报告内容投影与 Token Usage 投影共同消费不可变 Chunk，但任何一方不得把自己的派生表作为另一方的事实来源。

### 2.1 数据所有权

| 数据/契约 | 唯一所有者文档 | 其他专题允许行为 |
|---|---|---|
| `sessions`、Source、Generation、Chunk、内容投影、处理任务、内容 tombstone | Session 增量上传与内容管理 | 只按稳定 ID、水位和状态读取 |
| Report Source Selection、运行来源快照、MCP 来源参数 | 个人报告来源选择 | Session 提供内容，Token 不读取 |
| Usage Parser Checkpoint、Usage Observation、Logical Usage Event、Metrics Revision、Usage Component、Metering Envelope | Token 统计与成本管理 | Session 只投递任务并读取清除门禁状态 |
| 组织有效期、Daily Usage、价格、汇率、Cost Component | Token 统计与成本管理 | 页面和报告只读聚合结果 |

一个表、接口或状态只能由所有者文档定义。其他文档需要新增字段时，必须先修改所有者文档和本文，不得在消费方创建同义字段。

## 3. 术语与稳定身份

| 名称 | 定义 | 稳定身份 |
|---|---|---|
| Session | 用户在一种 Agent 客户端中的逻辑会话 | `user_id + agent_type + session_ref` |
| Source | Session 对应的一条逻辑日志流，例如 main 或独立 sub-agent | `session_id + source_role` |
| Source Generation | Source 原始内容的一次连续版本；文件截断、重写才产生新 generation | 服务端生成的 `generation_id` |
| Chunk | generation 中连续、不可变的一段完整 JSONL 行 | `generation_id + start_cursor + end_cursor` |
| Content Projection Revision | 对 generation 中可读活动、消息和工具事件的一版服务端索引 | 服务端生成的 `content_projection_revision_id` |
| Usage Observation | Provider 日志中一次原始 usage 快照；同一消息可出现多次 | `revision_id + provider + source cursor + raw usage hash` |
| Logical Usage Event | 把同一语义消息的一个或多个 Observation 折叠后的计量事件 | `revision_id + provider + usage_event_key` |
| Metrics Revision | 对同一 generation 使用确定 parser/normalizer 规则产生的一版派生统计 | 服务端生成的 `revision_id` |
| Metrics Query Snapshot | 一次跨 Session 查询固定的 revision/cost 有效时间视图 | 服务端签发的 `query_snapshot_token` |
| Activity Date | 事件时间换算成 `Asia/Shanghai` 后所属的业务自然日 | `YYYY-MM-DD` |
| Report Source Snapshot | 一次报告运行固化的内容投影版本与 Source/cursor 范围 | 服务端生成的 `selection_id` |
| Cost Component | 一条归一化模型用量按照确定价格和汇率生成的成本记录 | `usage_component_id + calculator_version` |

内部数据库 UUID 不作为 CLI 或页面展示的 Session ID。用户界面展示真实 `session_ref`。

## 4. Source、Generation 与 Chunk

### 4.1 Source Generation

- generation 由服务端创建，客户端不能指定整数版本并覆盖已有 generation。
- 普通文件追加继续使用当前 active raw/write generation。
- 文件被截断、前缀 checkpoint 不一致或原始来源被重写时创建 staging generation。
- 同一 Source 同时最多有一个 active raw/write generation 和一个 staging generation。
- staging generation 未完成前不能被报告、Token 或 Session 内容查询读取。
- staging 完整上传并通过连续性校验后原子切换 active raw/write generation，旧 generation 标记 superseded；该切换不直接移动内容投影或 Metrics 指针。
- Source 分别维护 active Content Projection 指针和 active Metrics Revision 指针。新 generation 的内容/Token 派生结果各自 validated 后才原子换指针；准备期间旧可信投影/revision 继续服务并返回 pending/rebuilding。
- 消费方只能从自己的 active 指针读取，不能因为 raw generation 已切换就直接扫描新 Chunk，也不能把旧、新 generation 同时求和。

### 4.2 Chunk 幂等

必须同时满足：

```text
UNIQUE(generation_id, start_cursor, end_cursor)
```

- 新 Chunk 的 `start_cursor` 必须等于服务端 `expected_cursor`。
- 缺口返回 `CURSOR_GAP`，重叠返回 `CURSOR_OVERLAP`。
- Chunk 必须从完整 JSONL 行边界开始并结束。
- 相同范围、相同 hash 的重试返回 duplicate，不重复存储、不重复解析。
- 相同范围、不同 hash 返回 `CHUNK_CONTENT_CONFLICT`。
- 不同范围允许出现相同 hash；日志中重复出现相同原始字节是合法数据，不能把内容 hash 当作范围身份。
- 原始对象使用由 generation、cursor 范围和 hash 决定的确定性 key。服务端先写入并验证对象可读取，再在数据库事务中锁定 Session/generation，重新检查 `content_status/content_epoch`，并通过 `expected_cursor=start_cursor` 的 CAS 写 Chunk、推进 cursor 和创建处理任务；数据库提交后才返回 ack。
- 对象成功但数据库事务失败时不推进 cursor，由孤儿清理任务删除对象；数据库提交但响应丢失时，客户端重试返回 duplicate。

### 4.3 Checkpoint 与四级水位

以下 checkpoint/watermark 不得混用：

1. Upload checkpoint：`generation_id + expected_cursor + prefix_checkpoint_hash + algorithm_version`，表示原始字节已可靠接收。
2. Content projection checkpoint：`content_indexed_cursor + content_parser_version`，表示报告可读事件已完成索引。
3. Usage parser checkpoint：`usage_parsed_cursor + provider_state`，表示 Usage Observation 已完成解析和折叠。
4. Cost watermark：`cost_calculated_cursor + pricing_revision`，表示 active Usage 已完成计价。

Usage parser checkpoint 至少保存：

```text
parsed_cursor
previous_token_counters
counter_segment
active_model
usage_event_watermark
parser_version
normalizer_version
checkpoint_hash
```

约束：

- 始终满足 `cost_calculated_cursor <= usage_parsed_cursor <= expected_cursor`；内容索引与 Usage 解析可以独立推进，但都不能超过 `expected_cursor`。
- 报告候选范围的 `end_cursor` 不得超过 `content_indexed_cursor`。
- Token 查询必须返回实际统计到的 `usage_parsed_cursor` 和待处理状态，不能把旧值描述为已包含最新 Chunk。
- 成本查询在 `cost_calculated_cursor < usage_parsed_cursor` 时返回 `pricing_pending`，不能用旧成本搭配新 Token 冒充完整结果。
- CLI 本地状态只缓存 Upload checkpoint。换电脑或本地状态丢失时从服务端 `prepare` 重新获取；其余 checkpoint 始终由服务端维护。
- `prefix_checkpoint_hash` 使用服务端规定算法计算 `[0, expected_cursor)` 的原始字节摘要。本地状态可信时沿用最近 ack 的 checkpoint；换电脑、本地状态丢失或服务端发起校验时重新读取该前缀计算。算法版本不匹配或摘要不一致时进入 staging generation，不能继续追加。
- 服务端必须保存版本化的内部增量 hash 状态，用已验证的未压缩 Chunk 推进完整前缀 SHA256；该状态不暴露给客户端，也不能采用客户端提交的累计 hash 作为权威值。内部状态缺失、格式不兼容或与已保存 checkpoint hash 不一致时，从 available 原始对象按 cursor 顺序重放恢复，恢复完成前不接收后续 Chunk。

## 5. 服务端内容投影与 Usage 账本

### 5.1 两条派生链路

- 原始 Chunk 接收成功后分别创建内容投影任务和 Usage 解析任务。
- 两条链路都必须按 generation 和 cursor 顺序处理，重试结果必须幂等。
- 内容投影生成活动事件、summary、excerpt、消息、工具和提交等报告可读索引，不生成 Token。
- Usage Parser 只提取计量字段及其必要上下文，不把 summary 或报告索引作为事实来源。
- 内容 Parser 或 Usage Parser 升级都使用独立 staging revision，从原始 Chunk 或允许的计量信封重建后原子切换。
- 原始 Chunk 不因任何 parser 升级重复上传。
- 两类 staging revision 都必须记录构建起点并追赶对应 Source 高水位；激活事务锁定 Source 或使用等价 compare-and-swap，高水位变化时继续 catch-up，不能带缺口切换消费者指针。

### 5.2 Usage Observation 与 Logical Usage Event

每一条含 Usage 的原始日志记录先写为不可变 Usage Observation。一个逻辑消息允许存在多个 Observation；只有 Logical Usage Event 当前指向的有效 Observation 生成 active Usage Component。

Provider 逻辑事件键：

| Provider | 首选 `usage_event_key` | 回退规则 |
|---|---|---|
| Claude Code | `message.id` | generation + 事件字节范围 + usage payload hash，并标记 `estimated` |
| Codex | generation + token_count 事件字节范围 | generation + 规范化事件 hash |

Observation 唯一约束至少包含：

```text
UNIQUE(revision_id, provider, generation_id, source_start_cursor, source_end_cursor, raw_usage_hash)
```

Logical Usage Event 唯一约束：

```text
UNIQUE(revision_id, provider, usage_event_key)
```

Claude 同一 `message.id` 的折叠规则：

1. 先把 Provider 定义的 Usage 数值字段规范成比较向量；缺少必需字段的 Observation 标记 incomplete，不能参与静默大小比较。
2. 与任一历史 Observation 的 raw usage hash 完全相同，记录 duplicate 并忽略，不改变当前 Observation。
3. 新 Observation 的所有比较字段均不小于当前值且至少一项增大，视为 Provider 单调推进；Logical Event 原子指向新 Observation，旧 Usage Component supersede，只计算最新完整快照。
4. 新 Observation 各字段有增有减，或在来源顺序中整体回退且不等于任一历史 Observation，标记 conflict，当前 revision 不得激活。
5. 不允许简单累加同一 `message.id` 的多个快照，也不允许无审计地选择第一条、最后一条或逐字段最大值。
6. Logical Event 的发生时间、Activity Date 和模型由稳定 Provider 消息语义确定；Observation 推进只更新 Usage 数值，不得因为记录到达时间改变日期、组织归属或模型。相同 key 的语义元数据分叉必须标记 estimated/conflict。

通用规则：

1. Observation 保存原始 usage JSON、原始模型、事件时间、来源 cursor、parser version 和 hash。
2. Logical Event 保存当前 Observation、折叠状态和折叠原因；历史 Observation 不修改、不删除。
3. Chunk hash 幂等不能替代 Usage 语义去重。
4. Parser 修正为新 Metrics Revision 创建独立 Observation/Event，不修改旧 revision。
5. active Component 更新必须与 Logical Event 指针、日期聚合和 checkpoint 在同一事务提交，失败不得留下新旧 Component 同时生效。
6. 具有稳定 Provider 事件 ID 的事实必须建立跨 active Source claim；同一用户/Provider 的同一事实同时只能由一个 active Logical Event 贡献。相同 Source 的 generation/revision 切换转移 claim，父/子或不同 Source 同时声明则阻止新 revision 激活并要求 fixture/归属规则判定。
7. 缺少跨 Source 稳定 ID 的 Provider，只有 Golden Fixture 证明父/子来源不重叠时才能同时标记 exact；否则相关聚合至少为 estimated，发现相同事实指纹时为 conflict。

### 5.3 解析质量

统一质量状态：

| 状态 | 含义 | 是否作为精确统计 |
|---|---|---|
| `exact` | 所有已知 usage 事件成功解析、去重并对账 | 是 |
| `estimated` | 可计算但存在时间、模型或回退身份假设 | 单独标识 |
| `incomplete` | 存在无法解析或缺失的 usage 事件 | 否 |
| `conflict` | 同一语义事件出现互相冲突的 usage | 否 |

每个 generation/revision 必须记录：

```text
scanned_event_count
usage_event_count
usage_observation_count
advanced_observation_count
duplicate_usage_event_count
malformed_event_count
unknown_usage_event_count
conflict_usage_event_count
```

非法 JSON、未知 usage schema 和数值溢出不得静默跳过。原始内容可以保存，但错误 Metrics Revision 不激活，页面继续展示上一个可信 revision，并提示存在待解析活动。

## 6. Token 原始值与归一化

### 6.1 两层字段

每条 Logical Usage Event 同时关联：

1. Provider 原始 usage：原样 JSON，不参与页面直接求和；
2. 归一化 usage component：供聚合和计价使用。

归一化字段必须互斥：

```text
uncached_input_tokens
cache_read_tokens
cache_write_5m_tokens
cache_write_1h_tokens
output_tokens
```

规范总量：

```text
normalized_total_tokens
= uncached_input_tokens
+ cache_read_tokens
+ cache_write_5m_tokens
+ cache_write_1h_tokens
+ output_tokens
```

单条 Usage Component 的 Token 字段使用非负 64 位整数。跨事件/Session/人员聚合必须在数据库显式转换为至少 `NUMERIC(38,0)` 或等价高精度整数，禁止依赖 BIGINT/JavaScript Number 静默溢出。API 中 Token 整数字段使用十进制字符串；前端使用 BigInt/decimal 解析，出现负数、溢出或无法解释的差值时不得截断为零继续计算。

### 6.2 Claude Code

- `input_tokens`、`cache_creation_input_tokens`、`cache_read_input_tokens` 和 `output_tokens` 按 Provider 分立口径解析。
- cache creation 无法识别 5m/1h 时使用已审核的默认计费假设，并将成本标记 estimated；Token 总量仍保留原始 cache creation 数量。
- 同一 `message.id` 的完全重复 assistant Observation 不重复计算。
- 同一 `message.id` 的 Usage 单调推进按第 5.2 节折叠，只计算当前最终快照；非单调分叉才进入 conflict。

### 6.3 Codex

- Codex token_count 是累计快照，必须使用 Parser checkpoint 与上一快照做差分。
- `uncached_input_tokens = input_tokens - cached_input_tokens`。
- `cached_input_tokens` 计入 `cache_read_tokens`。
- `reasoning_output_tokens` 是 `output_tokens` 的明细子集，不得再次加到 output 或 total。
- 累计字段下降只有在 Golden Fixture 已证明存在明确 Provider reset/turn boundary 时，才能创建新 counter segment。
- 有明确 reset 证据时，新段第一条快照相对零基线计算，并保留 reset 原因和原始边界。
- 没有明确 reset 证据的下降不得直接按新段精确计费；可解释但无法精确拆分时标记 estimated，字段分叉或无法解释时标记 conflict。
- 事件区间跨越模型/日期边界且无法精确拆分时标记 estimated。

### 6.4 Provider 适配版本

每个归一化结果保存 `parser_version` 和 `normalizer_version`。Provider schema 变化不能通过修改旧记录解决，必须创建新 Metrics Revision 重放原始事件。

外部开源项目的 usage 字段映射和价格表只能作为实现参考，不能替代真实 Claude/Codex 日志 Golden Fixtures。

## 7. Metrics Revision

### 7.1 状态和唯一性

状态：

```text
building -> validated -> active
building -> failed
active -> superseded
```

约束：

- 同一 generation 同时只能有一个 active Metrics Revision。
- building、failed、superseded revision 不进入 Token、成本和排名查询。
- Usage Component、每日聚合和成本组件必须可追溯到 `revision_id`。
- Token 查询必须从 Source 的 active Metrics Revision 指针开始，不允许直接按 raw active generation 或全部历史 Chunk 求和；该 revision 在 generation 重建期间可以暂时指向旧 generation。
- revision 必须记录 `build_start_cursor`、`validated_through_cursor` 和激活时的 `source_high_water_cursor`。

### 7.2 普通追加与解析修正

- 普通追加在相同 parser/normalizer version 下向 active revision 增加已验证贡献。
- 相同原始内容重试结果必须不变。
- 普通新增活动只能增加受影响日期，不能移动或删除旧日期贡献。
- Parser 修正、完整重建和 generation 切换使用 staging revision，校验通过后原子替换。
- staging revision 首轮重放后必须追赶构建期间新增 Chunk；只有 `validated_through_cursor == source.expected_cursor` 时才允许进入 validated。
- 激活事务必须锁定对应 Source/generation 或使用等价 compare-and-swap，再次确认高水位未变化；变化时继续 catch-up，不能带缺口切换。
- 短暂激活窗口内的新 Chunk必须等待锁释放后进入新 active revision，或同时路由到旧/新 revision 并完成对账；实现只能选择一种并写入专题方案。
- Parser 修正允许正确总量低于旧错误总量，必须记录原因、修正前后值和操作者/版本。
- 旧 revision 保留审计但退出所有 active 聚合。

## 8. 时间、日期和模型归属

1. 有明确 offset 的事件转换为 UTC 保存，同时保留原始 offset。
2. 无 offset 的本地日志按 CLI 所在机器时区解释，并上传解释结果；禁止按服务器时区猜测。
3. 服务端统一按 `Asia/Shanghai` 生成 Activity Date。
4. Session `started_at` 不等于最近活动时间。
5. 长 Session 的新 Chunk 按每条事件实际时间补充历史或当日贡献。
6. 累计 Token 差值归属于当前 token_count 事件时间；如果该差值可能跨日期或模型且无法拆分，归属结果标记 estimated。
7. 多模型 Session 必须保存模型级 usage component，不得把整日 Token 归给最后一个模型。
8. 具有独立 Session ID 的 sub-agent 保存为独立 Session；父 Session 和子 Session 必须通过 Golden Fixture 证明 Token 来源不重叠后才能同时聚合。

## 9. 逐层对账不变量

每个待激活 revision 必须满足：

```text
每个 Logical Usage Event 当前 Observation 的归一化总量
= Chunk 模型贡献总量
= Activity Date 聚合总量
= Session 聚合总量
= Provider 可对账总量
```

同时满足：

- 各模型之和等于 Session 总量；
- 各日期之和等于 Session 总量；
- 同一 Logical Usage Event 同时最多一组 active Component，历史 Observation/Component 不得参与聚合；
- Token 整数对账使用零误差；
- Provider 没有可用总量时明确记录 `provider_total_unavailable`，不能伪造对账成功；
- 对账失败的 revision 状态为 failed，不进入 active 查询；
- 成本聚合只能消费 active revision 的 usage component。

跨 Session/Source 查询不能返回单一 `metrics_revision_id` 冒充全局版本。首个请求必须固定 `metrics_snapshot_at`；Usage Component、Daily Usage、revision 和 cost 均保存 `valid_from/valid_to` 或等价有效区间，或在首请求事务内把命中的 Token、成本和组织显示值物化为短期查询快照。分页使用绑定用户、筛选条件和 snapshot 的不透明 `query_snapshot_token`，后续页不得混入 snapshot 之后追加、激活、重新计价、组织改名或 Session 删除的数据。只冻结 revision ID 而继续读取其当前可变聚合不满足查询快照。

## 10. 用户和组织归属

### 10.1 不可变使用者

每条 usage component 的 `user_id` 在生成后不可因为账号重命名、停用或调组而变化。

### 10.2 有效期组织关系

新增三类组织有效期记录：

```text
user_team_memberships(user_id, team_id, effective_from, effective_to, source)
team_department_memberships(team_id, department_id, effective_from, effective_to, source)
user_department_memberships(user_id, department_id, effective_from, effective_to, source)
```

其中 `user_department_memberships` 只记录 PM、总监等直接归属部门的用户。工程师和小组长通过用户小组关系与小组部门关系解析部门，不同时写直接部门归属。

每条 usage component 保存：

```text
team_id_snapshot
department_id_snapshot
department_attribution_source (direct|via_team|unknown)
```

- 同一用户的小组有效期、直接部门有效期以及同一小组的部门有效期分别不得重叠；直接部门和经小组解析出的部门不得冲突。
- `departments.director_user_id` 是当前总监权限的唯一权威来源；`teams.director_user_id` 不进入 V2 权限、Token 或 MCP 查询。
- 组织历史不能依赖当前 AIHub 用户资料同步自动推断；所有本地创建部门/小组、部门调整、批量导入、成员调组和移除入口必须在同一事务关闭旧区间并创建新区间。
- 初次迁移只从 V2 切换时刻建立已知当前区间；切换前无法证明的历史小组或部门归属为 unknown，不使用当前组织倒填。
- 管理脚本和直接 SQL 不得绕过同一组织归属服务；如确需批量修复，必须生成区间冲突报告和审计记录。
- 显式修正历史组织区间时重建受影响的组织归属和聚合，不修改 Usage 事实及个人 Token 总量；修正必须有影响预览和审计。
- usage component 根据事件时间匹配 `team_id_snapshot` 和 `department_id_snapshot`。PM/总监使用直接部门区间，工程师/小组长使用用户小组区间再匹配小组部门区间。
- 无法匹配历史组织关系时保留个人 Token，小组/部门归属为 unknown，并明确显示，不能静默使用当前用户或小组字段回填。
- 当前权限校验使用当前角色和 `departments.director_user_id`；历史组织分析使用活动发生时的 team/department snapshot。
- 停用人员不进入当前成员人数和当前成员排名，但历史 Token、趋势和成本不删除。

## 11. 内容、统计和成本生命周期

| 操作 | 原始内容 | Usage/Token | 成本 | 已保存报告 |
|---|---|---|---|---|
| 普通新增上传 | 增加 Chunk | 验证后增加 | 按活动日期新增 | 不变 |
| 重复上传 | 不重复 | 不变 | 不变 | 不变 |
| 用户清除内容 | 立即禁止读取，计量信封完成后删除原始对象和可读索引 | 保留且仍可重算计量字段 | 保留 | 保留 |
| 显式恢复 | 建立新内容 generation | 不得增加第二份既有统计 | 不得重复计价 | 不变 |
| Parser 修正 | 不变 | 原子替换 active revision，可升可降 | 对应 supersede | 不变 |
| 管理员彻底删除 | 删除 | 删除 | 删除 | 按影响预览处理 |

内容清除前必须建立通过水位校验的 Metering Envelope：保存所有潜在计量记录的 Provider 事件 ID、时间、模型、原始 usage/token 元数据、cursor、hash 和 parser 诊断，但不得保存用户/助手对话正文、工具输出正文或可还原对话的文本。约束：

1. 清除请求在锁定 Session 后将内容设为 `clearing`、递增 `content_epoch`，并立即拒绝新的 prepare/chunk、下载、报告选择和 MCP 内容读取。
2. 对 Session 下每个仍有原始对象的 Source Generation，都必须满足 `metering_exported_cursor == expected_cursor` 且信封 checksum/计数校验通过，才允许物理删除对应对象并进入 `cleared`。
   旧整包 `raw_log_url` 必须先被回填为同一 Session 的可验证 Chunk；若该对象没有对应 Chunk，清除请求必须返回迁移冲突，禁止仅清空 URL 却遗留物理对象。
3. 信封生成失败时原始对象保持不可读但不物理删除，状态为 `clearing_failed`，可由服务端重试；不得为了完成清除而丢弃未来 Token 修正能力。
4. 内容清除后的 Parser 修正只能修正信封中保留的计量字段；无法从信封恢复的内容语义不在支持范围内，页面和审计必须明确该边界。
5. Metering Envelope 与 Usage Observation 只能包含计量和审计字段，不得保留原始对话正文。
6. 内容索引、来源快照和内容删除任务创建时保存 `content_epoch`，写入前再次比较；旧 epoch 任务不得重新生成 summary、excerpt、可读事件或恢复内容状态。Usage 任务只允许完成清除门禁所需的计量结果。
7. 只有 `cleared` 状态允许显式恢复。每次恢复开始递增 `content_epoch`，创建 `restore_intent` 和新的 staging generation；恢复失败时 Session 继续保持 cleared，旧 epoch 恢复任务不得写入。内容投影 validated 后才能恢复内容读取，Metrics Revision 完成同 Source 原子替换和 claim 转移后才能切换 Token 指针。

## 12. 报告来源边界

- 报告来源身份是 Session 内容范围，不是 Token 日切片。
- 来源选择读取 Source 的 active Content Projection Revision 指针及其 generation，不读取 raw/write generation 或 Metrics Revision 作为内容身份。
- 候选与快照范围的 `end_cursor` 必须小于等于 `content_indexed_cursor`；仅上传成功但尚未完成内容索引的 Chunk 不能成为报告来源。
- 报告运行开始时将选择解析为不可变 `content_projection_revision_id + Source/cursor` 范围快照。
- selection item 同时固化 Session `content_epoch`；绑定、MCP 读取和未完成报告回写必须在事务内锁定来源 Session 并校验 epoch。内容清除或恢复后旧 selection 不得因状态重新变为 `available` 而复活。
- 后续上传和 Token Parser 修正不能改变已经开始的报告输入。
- Content Parser 修正不能原地改变已绑定运行的 projection revision；旧 revision 至少保留到关联运行结束和审计保留期届满。
- MCP 必须区分默认周期来源与显式 selection 来源；显式 selection 不得再次按 period 裁剪。
- MCP 分页或响应体限制不得静默丢内容，必须返回 `has_more/next_cursor` 或明确失败；默认 Skill 必须消费至 `has_more=false` 才能声称来源完整。
- 内容清除后不能创建新的来源快照；已经保存的报告正文继续保留。

## 13. 成本边界

- 成本只消费 active revision 的互斥 usage component。
- 模型价格、USD/CNY 汇率和计算器版本必须形成不可变快照。
- 外部模型价格只能作为待审核建议，平台已发布价格是唯一计算基准。
- 已发布价格和汇率不可原地修改。错误版本通过同一口径、同一有效区间的新发布版本显式 supersede，旧版本保留审计；只允许旧版本发生一次 `superseded_at` 状态转换。
- 同一 usage component 同时只能有一条 active 成本记录。
- 价格、汇率、分项成本和聚合成本使用固定精度 decimal；禁止二进制浮点参与权威计算。分项保留未展示舍入值，只有最终展示按明确规则舍入。
- 未映射模型、缺少价格或缺少汇率返回 unpriced/partially_priced，不得返回零成本冒充已计价。
- 重新计价使用 supersede，不原地覆盖历史快照。
- 发布价格/汇率修正不自动重写既有成本；管理员必须先预览再以原因执行重算 apply，结果和操作者进入审计。已签发查询快照继续展示签发时的成本，新快照才看到重算结果。

## 14. 共享错误码

| 错误码 | 含义 |
|---|---|
| `CURSOR_GAP` | 上传游标存在缺口 |
| `CURSOR_OVERLAP` | 上传范围与已确认范围重叠 |
| `SOURCE_DIVERGED` | 本地前缀与服务端 generation 不一致 |
| `CHUNK_CONTENT_CONFLICT` | 相同范围出现不同内容 |
| `INVALID_CHECKPOINT` | checkpoint 的算法、游标或摘要格式不合法，客户端必须重新扫描来源 |
| `INVALID_CHUNK` | Chunk 范围、hash 或完整行边界不合法，服务端不得保存或推进游标 |
| `CONTENT_CLEARED` | 内容已清除，普通上传不能恢复 |
| `CONTENT_NOT_WRITABLE` | 内容正在清除、清除失败待处理或已彻底删除，当前不允许写入 |
| `CONTENT_PROJECTION_NOT_READY` | 原始 Chunk 已接收但报告可读索引尚未覆盖请求范围 |
| `METERING_ENVELOPE_NOT_READY` | 清除前计量信封尚未覆盖全部已接收内容 |
| `LEGACY_CONTENT_MIGRATION_REQUIRED` | 旧整包原始对象尚未回填为增量 Chunk，不允许假清除 |
| `USAGE_EVENT_CONFLICT` | 同一逻辑事件出现非单调或不可解释的 usage 分叉 |
| `TOKEN_RECONCILIATION_FAILED` | Token 逐层对账失败 |
| `REVISION_HIGH_WATER_CHANGED` | revision 激活时 Source 高水位发生变化，需要继续追赶 |
| `REPORT_SOURCE_MISMATCH` | selection 与当前用户、run、报告类型或周期不匹配 |
| `REPORT_CONTEXT_MISMATCH` | MCP 读取参数与服务端保存的 run scope/target/period 不匹配 |
| `AMBIGUOUS_REPORT_SOURCE` | 同时提交显式 selection 和默认日期来源参数 |
| `QUERY_SNAPSHOT_EXPIRED` | Token/MCP 分页快照已过期，必须从第一页重新查询 |
| `CLI_UPGRADE_REQUIRED` | 旧客户端不能覆盖 Chunk 模式 Session |

错误响应必须包含下一步操作，不能只返回内部错误码。

## 15. 核心验收标准

- `CORE-001`：相同 Chunk 重试只保存一次。
- `CORE-002`：相同 Claude `message.id` 重复记录只计算一次。
- `CORE-003`：Claude 同一 `message.id` 的 `0 -> partial -> final` 单调 Observation 只计算 final；非单调分叉才进入 conflict。
- `CORE-004`：Codex 累计快照跨三个 Chunk 与一次完整解析结果一致。
- `CORE-005`：CLI 本地状态丢失和换电脑不改变 Token 结果。
- `CORE-006`：Codex reasoning 不重复加入 output。
- `CORE-007`：cached input 不同时计入 uncached input。
- `CORE-008`：Parser 修正可降低错误结果，旧 revision 不进入查询。
- `CORE-009`：非法 usage 事件不能被静默跳过并标记 exact。
- `CORE-010`：日期、模型、Chunk 和 Session 四层聚合精确相等。
- `CORE-011`：人员调组和停用不改写历史 Token。
- `CORE-012`：内容清除保留 Token/成本，恢复不重复计数。
- `CORE-013`：管理员彻底删除后对应 active 聚合被移除并有审计。
- `CORE-014`：revision 构建期间并发追加 Chunk，激活后统计覆盖最新 Source 高水位且不重不漏。
- `CORE-015`：原始内容物理删除前 Metering Envelope 覆盖全部已接收 cursor；删除后可从信封重建相同 Token。
- `CORE-016`：内容索引落后于上传水位时，报告候选与 MCP 不读取未完成范围。
- `CORE-017`：显式 selection 只能由绑定用户和 run 使用，且不会被 period 二次裁剪。
- `CORE-018`：MCP 多页读取直到 `has_more=false` 与同范围一次性基准内容一致。
- `CORE-019`：Token、内容索引和成本水位分别返回，任何页面/API 不把 pending 数据描述为完整。
- `CORE-020`：Codex 无明确 reset 证据的累计下降不能标记 exact。
- `CORE-021`：父 Session、子 Agent、generation 重建中相同 Provider 事实最多贡献一次；跨 Source claim 冲突时 revision 不激活。
- `CORE-022`：Logical Event 快照推进只更新 Usage 数值，不改变原发生日期、组织归属或模型。
- `CORE-023`：跨接口和分页查询复用同一 snapshot 时不混入后续追加、revision 切换或重新计价数据。
- `CORE-024`：raw generation 切换但新内容/metrics 尚未 ready 时，报告和 Token 继续读取各自旧可信指针并标记 rebuilding，不出现空窗或新旧双计。
- `CORE-025`：所有 MCP 读取工具校验 run context，显式返回完整性/分页状态，组织 inventory 与下级报告集合对账。
- `CORE-026`：超过 JavaScript 安全整数的 Token 聚合和高精度成本经数据库、JSON API、前端后仍逐位一致，无浮点或序列化精度丢失。
- `CORE-027`：两个客户端并发提交同一 cursor 时只有一个 CAS 成功；失败请求不推进 cursor、不创建重复任务。
- `CORE-028`：对象写入后数据库回滚不返回 ack；数据库提交后响应丢失的重试返回 duplicate，最终对象、Chunk 和 cursor 一致。
- `CORE-029`：clear-content 与上传、内容索引、selection 和 MCP 并发时，旧 `content_epoch` 任务不能重新写回已清除内容。
- `CORE-030`：恢复新 generation 覆盖全部清除前既有计量事实时原子替换；缺少/冲突时不激活，同一 Source 的旧、新 Metrics Revision 不同时进入查询，既有 Token 和成本不重复也不丢失。
- `CORE-031`：用户调组、小组调部门和总监变更后，历史 team/department snapshot 不变，当前权限立即按新部门关系生效。

上述验收全部通过前，核心契约不得标记为“可开发”，不得开始生产数据库迁移、发布 Chunk 模式 CLI 或切换 Token/MCP 查询。
