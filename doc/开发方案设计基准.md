# 开发方案设计任务：最小充分设计

请基于当前需求文档和现有代码，输出一份可直接开发的方案。

本任务采用“最小充分设计”，不是理论上的最小代码，也不是面向未来的最佳实践大全。

最小充分设计的定义是：

> 完整满足本期需求和验收标准，补齐已被代码事实证明必需的权限、一致性和失败边界；不为未经证实的未来风险提前增加机制。

## 一、工作顺序

必须按照以下顺序执行：

1. 阅读需求文档；
2. 提取明确的产品规则和验收标准；
3. 阅读相关代码；
4. 列出当前已经具备的能力；
5. 列出需求与现状的真实差距；
6. 为每个差距设计最小改动；
7. 最后才输出架构和开发任务。

不得先套用行业架构或最佳实践，再反向解释需求。

## 二、先输出需求差距表

在设计方案前，先输出：

| 需求/验收项 | 当前能力 | 代码证据 | 是否存在差距 | 最小改动 |
| ------ | ---- | ---- | ------ | ---- |

要求：

* 每个主要改动必须对应需求或验收标准；
* 已有能力直接复用；
* 当前没有差距的地方不得重构；
* 无法通过代码确认的事项必须明确标记，不得自行假设。

## 三、新增机制的准入条件

任何新增机制，包括新表、新状态、新接口、新凭据、新事务、新抽象或新配置，都必须回答：

1. 对应需求文档哪一条；
2. 当前代码已经确认存在什么问题；
3. 不增加该机制会导致哪个验收标准失败；
4. 现有机制为什么无法满足；
5. 最小替代方案是什么；
6. 是否可以推迟到后续阶段。

无法回答前 3 项的机制不得进入本期方案。

“业内最佳实践”“增强扩展性”“未来可能需要”“更加完整”不能单独作为新增理由。

## 四、默认复杂度预算

除非有代码证据证明无法满足需求，否则默认：

* 不新增独立服务；
* 不新增通用框架；
* 不新增 Provider、Adapter、Reader 插件体系；
* 不新增复杂状态机；
* 不新增分布式事务或补偿机制；
* 不新增通用版本系统；
* 不新增面向未来的扩展协议；
* 优先复用现有表、服务、接口和运行流程；
* 允许增加完成当前用户流程所需的最小字段、接口、状态和配置。

如果必须超出预算，请单独列出理由，并说明不这样做会失败的验收项。

## 五、设计分层

所有内容必须分为三类：

### A. 本期必须完成

直接影响本期功能、权限、数据正确性和验收。

### B. 代码事实触发的必要保障

只有真实代码证明存在风险时才进入本期，必须提供代码证据。

### C. 后续增强

不影响本期验收的优化、安全增强、扩展能力和规模治理。

C 类不得进入本期开发任务，不得阻塞 V1。

只记录本次代码核对和设计过程中已经实际发现、但不影响本期验收的事项；不得为了填写 C 类主动规划未来阶段或建立演进路线图。

## 六、一致性和失败处理原则

只设计完成本期所需的最小一致性：

* 本地数据库内需要原子写入时，可以使用普通数据库事务；
* 外部 Agent、MCP 或模型调用失败时，记录 Run 失败；
* 已冻结的 Context 不需要因为外部失败而回滚；
* 不设计跨系统分布式事务；
* 不设计两阶段提交；
* 不设计复杂补偿工作流；
* 重试复用已有冻结输入，不重新读取可变数据。

只有存在不可接受的数据破坏风险时，才允许增加更复杂机制。

## 七、安全设计原则

优先使用现有认证和服务端资源权限校验：

* 认证用户；
* 资源所有权；
* 业务类型；
* 数据范围；
* 读取与写回目标一致性。

只有现有身份链路无法满足明确安全要求时，才设计新的凭据体系。

安全增强不得因为理论上的更严格隔离而自动阻塞本期，除非可以证明当前方案存在真实越权路径。

## 八、输出内容

最终交付文档集必须完整覆盖以下内容。内容可以按照项目约定拆分到需求、架构、开发、测试与验收文档中，不要求重复塞进单一文件，但每项必须有唯一落点和可追溯链接：

1. 代码事实与差距；
2. 目标流程；
3. 最小架构；
4. 必要的数据和接口变化；
5. 失败与权限边界；
6. 开发任务和顺序；
7. 测试与验收；
8. 后续增强清单。

每个开发任务必须包含：

* 对应需求；
* 当前代码位置；
* 最小改动；
* 完成标准；
* 真实依赖。

不得加入与本期无关的长期演进设计。

## 九、自检

输出前检查：

* 是否有改动无法对应需求或验收标准；
* 是否重构了本来已经可用的能力；
* 是否因为“最佳实践”增加了未经证实的机制；
* 是否为了“最小闭环”遗漏权限、失败或一致性；
* 是否设计了跨系统事务或复杂补偿；
* 是否把后续增强放进本期；
* 是否设置了不必要的整体开发准入；
* 是否存在一个局部未决问题阻塞全部开发；
* 删除任一新增机制后，本期验收是否仍能通过。

如果删除后仍能通过，该机制应删除或移入后续增强。

最终方案应达到：

> 所有本期需求都被覆盖，所有新增复杂度都有代码事实和验收标准支撑，其余能力留到真实需求出现后再设计。
