## 1. 设计边界

- 本文只解释如何满足已确认需求，不新增报告类型或上传协议。
- 保留现有 Session Projection、Report Source、Digest、Report Context、Report Run 和 MCP 写回链路。
- 新模块只暴露运行时配置和一次调度入口；来源发现、防抖、单飞、已有日报判断与运行结果衔接保持内部实现。

## 2. 一页决策差异

| 类别 | 本阶段变化 |
|---|---|
| 产品行为变化 | 当日来源静默 2 分钟后自动生成个人日报；未被用户接管的自动日报可刷新 |
| 代码行为变化 | 扫描已 ready 的当日来源集合；按用户防抖；复用现有 Report Run；自动写回增加乐观保护 |

| 未决决策 | 无 |
| 明确不做 | 客户端改动、上传批次协议、新 Agent 执行链路、用户配置页、周报和组织报告自动化 |

## 4. 最小目标架构

新增深模块 `internal/autodailyreport`，外部接口保持为：

```text
Start(ctx)
RunOnce(ctx, now)
GetConfig(ctx)
SetEnabled(ctx, enabled, operator)
```

内部实现负责：

1. 读取运行时开关；
2. 查询与 `resolveDefaultItems` 相同口径的 `ready` 当日来源，计算确定性来源指纹；
3. 将变化合并到 `用户 + 报告日期` 唯一状态，按最后 `ready_at + 2 分钟` 防抖；
4. 领取到期状态并判断当天日报是否允许自动创建或刷新；
5. 通过注入的 Submitter Adapter 创建现有 Report Run；
6. 观察 Run 终态，在来源再次变化时补一轮，或进入 idle/blocked/failed；
7. 关闭功能时抑制未领取状态，重新开启只接受 `enabled_since` 之后出现的新 ready 来源。

`handler.ManagedAgentHandler` 作为 Submitter Adapter，解析系统默认 Report Agent 并调用现有 `reportsource.CreateReportRun`。Report MCP 写回继续是唯一报告落库入口。

## 6. 数据流与失败边界

```text
Catalog ready 来源变化
  -> Scheduler 发现用户当日来源指纹变化
  -> upsert 自动刷新状态，due_at = 最后 ready_at + 2m
  -> 到期领取状态
  -> 锁定并判断当天日报：absent / 可刷新 / 受保护
  -> 可执行时冻结 absent/replace 前置快照
  -> Submitter Adapter 创建 Report Run
  -> 现有 Report Run 等待 Digest、构建 Context、提交 Agent
  -> MCP 写回事务重新校验 absent/replace 快照
  -> 成功写入或以 REPORT_EDIT_CONFLICT 取消
  -> Scheduler 根据 Run 终态和最新来源指纹进入 idle / pending / blocked / failed
```

- 来源发现或自动 Run 失败只更新自动状态，不回写上传状态。
- 状态领取使用短 lease；进程退出后可重新领取。
- 同一用户日期只有一个活动自动 Run；新变化只更新 desired fingerprint。
- 功能关闭不取消已经存在的 Report Run。

## 7. 安全、容量与兼容性

- admin 接口沿用现有 `AdminOnly`；每次 PUT 记录当前值、`enabled_since`、操作者 ID 和变更时间。
- 自动 Run 使用 Session 实际 owner 作为 `ai_runs.user_id`；上传者不获得 owner 报告权限。
- 每次扫描只处理 `Asia/Shanghai` 当日、active/ready 来源，并使用现有索引口径；不扫描事件 payload。
- 默认关闭，旧客户端、手工报告、定时报告与上传响应完全兼容。
- 写回门禁仅在 `trigger_source=session_upload_auto` 时启用，不改变既有手工/定时 Run 行为。
