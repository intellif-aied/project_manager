# Report Agent 有界重试策略

> 日期：2026-07-27
> 状态：测试服实现并完成同批11组真实数据复测

## 1. 结论

允许多次修正符合Agent的工具循环机制，但必须由服务端持久化计数并强制上限，不能只依赖Skill提示。

- Report Brief：允许最多2次无效结果修正，即最多3次有效`write_report_brief`提交；第3次仍无效时返回`REPORT_BRIEF_RETRY_EXHAUSTED`。
- 最终日报：允许最多1次无效结果修正，即最多2次`write_report_result`提交；第2次仍无效时返回`REPORT_RESULT_RETRY_EXHAUSTED`。
- 非内容类错误（权限、run错配、Context错配、Brief Hash错配、来源失效）不进入重试，立即失败。
- 无`run_id`的协议错误无法安全归属到Run，不记入持久化次数，但仍返回参数错误。

## 2. 为什么采用这个上限

同批11组真实数据中，Brief首次通过2组、修正一次通过6组、修正两次通过3组；最终日报首次通过9组、修正一次通过2组。因此2次Brief修正和1次Result修正覆盖当前全部代表性样本，同时可以阻止Agent无限循环。

## 3. 减少重试的策略

当前校验器通常一次只返回第一项违规，Flash修正后才发现下一项，放大了工具调用次数。新策略要求：

1. 同一次提交内收集所有能够确定识别的字段、状态、环境、Fact覆盖和安全问题；
2. 以一条结构化错误响应一次返回全部问题；
3. Agent只根据错误列表和已接受的证据修正，不重新获取Context；
4. 每次无效提交原子增加计数，并发提交也共享同一上限。

## 4. Module与Seam

重试计数、并发原子性、错误聚合和最终读者文本安全规则全部位于`reportbrief` Module。它的Interface保持为：

- `Accept`：接受或拒绝Brief，并在语义无效时记录Brief尝试；
- `ValidateForWrite`：校验Brief绑定和最终文本，并在文本无效时记录Result尝试。

MCP Handler只把Module错误映射为稳定错误码，不保存计数、不复制上限、不解析校验细节。删除该Module时，复杂度会重新散落到Brief和Result两个Handler，说明该Module具有足够Depth。

## 5. 持久化

新增`report_run_generation_attempts`，按`run_id`唯一保存：

- `brief_invalid_attempts`；
- `result_invalid_attempts`；
- `updated_at`。

计数通过单条Upsert原子递增；数值封顶为“允许无效次数＋1”，既能表达耗尽又避免异常调用无限增长。记录随Run级联删除，不进入业务报告表。

## 6. 最终安全规则补充

在现有错误码、Token、地址、UUID、哈希和特定术语规则上增加三类确定性模式：

- 显式协议/端口表达，例如`UDP 123`、`TCP:8080`、`端口 8080`；
- 命令行参数，例如`--user`；
- 以空白、括号或反引号起始的内部绝对路由，例如`/agent`、`/internal/jobs`。

不全局禁止API、CSS、Agent等技术词，避免误伤个人技术日报的正常工作内容。

## 7. 对比验收

使用`07-批量真实Session测试-20260727.md`完全相同的11组、25个Session复测：

- 11组仍全部成功，或明确记录被上限终止的原因；
- Brief平均提交次数低于首轮，预期多数问题一次聚合后只需1次修正；
- Result最多2次提交；
- 最终内容不再出现端口、命令参数和内部绝对路由；
- 状态、环境、主题和正文质量不得低于首轮。

## 8. 实测结果

11组全部成功且没有触发重试耗尽；端口、命令参数和内部绝对路由均未再出现。Brief工具调用总数与首轮持平，Result修正从2组降为1组。内容语义质量仍有随机波动，因此本策略作为协议稳定性和安全边界保留，不作为内容质量提升手段。详细指标、逐组Run和人工对照见`10-Agent有界重试对比测试-20260727.md`，本轮完整日报见`11-Agent有界重试批量日报样本-20260727.md`。
