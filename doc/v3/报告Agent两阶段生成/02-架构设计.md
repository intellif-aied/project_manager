# V3 架构设计：Report Agent 两阶段生成

> 文档状态：已确认
> 日期：2026-07-27
> 唯一需求基线：[01-需求文档](01-需求文档.md)

## 1. 设计边界

本文只设计默认个人日报的 Report Brief 阶段。现有 Digest、Report Projection、Report Context、专用平台账号、当前用户 Report MCP Credential、报告权限和最终报告表保持原边界。

## 2. 一页决策差异

| 类别 | 本阶段变化 |
|---|---|
| 产品行为变化 | 默认个人日报必须先提交 Report Brief，再写最终报告 |
| 代码行为变化 | Context facts 增加稳定 `fact_ref`；Report MCP 新增 `write_report_brief`；个人日报写回增加 Brief 门禁 |
| 新增资源 | migration `028`与表`report_run_briefs`；migration `029`与表`report_run_generation_attempts`；配置`REPORT_TWO_PASS_ENABLED`；系统Skill新版本 |
| 未决决策 | 无 |
| 明确不做 | Digest/Projection LLM 化、双 Agent、双 Skill、双 MCP、其他报告类型切换、前端改版 |

## 4. 最小目标架构

```text
Session → Digest → Report Projection → immutable Report Context
                                            │
                                            ▼
同一个 Report Agent / Agent Session / Skill
  1. get_report_context()：服务端从本 Run Credential 解析 run_id
  2. LLM 第一次语义处理：Facts → Report Brief
  3. write_report_brief(brief_json)
                                            │
                                            ▼
ReportBrief Module：校验 run/user/context/fact coverage/state → 保存 → 返回 Brief + brief_hash
  4. LLM 第二次语义处理：只根据返回 Brief 写摘要和正文
  5. write_report_result(brief_hash, summary, content)
                                            │
                                            ▼
                                  现有报告写回和通知链路
```

新增 `reportbrief` 深模块，外部接口只负责“接受 Brief”和“为最终写回校验 Brief”。Handler 不复制 Schema、覆盖、幂等和 Context 绑定规则。

## 6. Report Brief V1 契约

Agent提交时只需提供序列化后的语义内容。run、用户、报告类型、周期、Context hash和schema均由服务端派生。managed tool 外层契约为：

```json
{"brief_json":"<下面这个 JSON 对象的序列化字符串>"}
```

`brief_json`解码后的内部契约为：

```json
{
  "workstreams": [
    {
      "title": "报告工作台改版",
      "objective": "统一日报和周报入口",
      "deliverables": [
        {
          "result": "统一工作台完成测试服验证",
          "state": "validated",
          "environment": "test",
          "validation": "核心交互验证通过",
          "next_action": "待生产发布",
          "fact_refs": ["fact-020", "fact-021"]
        }
      ]
    }
  ],
  "excluded_facts": [
    {"fact_ref": "fact-045", "reason": "preparation"}
  ],
  "no_reportable_work": false
}
```

服务端返回：

```json
{
  "status": "accepted",
  "schema_version": "report-brief/v1",
  "brief_hash": "sha256",
  "report_type": "personal_daily",
  "period": {"start": "2026-07-27", "end": "2026-07-27"},
  "workstreams": [],
  "excluded_facts": [],
  "no_reportable_work": false
}
```

约束：

- Workstreams 0～8，每个1～8个Deliverables；
- Deliverable状态仅允许 `released/validated/completed/in_progress/blocked`；
- environment仅允许 `production/test/development/none`；
- 排除原因仅允许 `preparation/discussion/trace/duplicate/low_reader_value`；
- Context内全部 `fact_ref` 必须至少被引用或排除，引用和排除互斥；
- 同一事实允许支撑同一或不同Deliverables，但服务端去除单个数组内重复引用；
- `no_reportable_work=true` 时Workstreams必须为空，全部Facts必须有排除原因；
- 服务端拒绝明显凭证、私网地址、UUID、绝对路径、原始错误码和禁用术语；不尝试用规则判断语义正确性。

## 7. 持久化、幂等与状态

新增 `report_run_briefs`，每个run最多一条：

| 字段 | 说明 |
|---|---|
| `run_id` | 主键并关联 `ai_runs(id)`，级联删除 |
| `schema_version` | 固定 `report-brief/v1` |
| `context_hash` | 绑定不可变 Context |
| `brief_hash` | 规范化 JSON SHA-256 |
| `brief_payload` | 规范化 JSONB |
| `model_id` | 本次run模型 |
| `created_at` | 首次接受时间 |

- 不新增 `ai_runs.execution_stage`，Brief期间run保持 `agent_running`；
- 相同run和hash重复提交幂等返回；不同内容返回 `REPORT_BRIEF_CONFLICT`；
- Brief成功但最终写作失败时保留记录；
- 成功写回后把 `brief_schema_version` 和 `brief_hash` 写入 `output_ref_json`；
- 不把Brief写入immutable Report Context，也不复用最终业务输出字段。

新增`report_run_generation_attempts`，按run唯一保存Brief和Result无效提交次数。计数通过单条Upsert原子递增并封顶，只约束模型纠错循环，不改变报告业务状态；记录随run级联删除。

## 8. 数据流与失败边界

| 错误码 | 含义 | Agent行为 |
|---|---|---|
| `REPORT_BRIEF_INVALID` | Schema、事实覆盖、安全或术语校验失败 | 根据错误修正一次 |
| `REPORT_BRIEF_REQUIRED` | 未提交Brief就写最终个人日报 | 返回Brief阶段 |
| `REPORT_BRIEF_MISMATCH` | hash、run、用户或Context不匹配 | 停止并写失败 |
| `REPORT_BRIEF_CONFLICT` | 同一run提交不同Brief | 停止，禁止覆盖 |

现有来源冻结、用户编辑冲突、结果幂等和失败写回继续生效。

## 9. 安全、容量与兼容性

- Brief沿用Report Context的run/user权限，不提供普通查询接口，不写入通用日志；
- 每个 Report Run 使用独立签名 Credential，包含用户身份与 `report_run_id`；服务端拒绝参数中的 Run 与凭证 Run 不一致；
- managed tool schema不暴露`run_id`，旧版普通MCP toolset继续要求`run_id`，避免影响其他报告和外部调用；
- 单个Brief规范化JSON上限128 KiB；字段和数量均有上限；
- 不设置最终日报服务端硬长度限制，避免截断事实；长度通过Skill和GT验收；
- 功能开关关闭时工具不向managed toolset暴露，个人日报恢复当前写回协议；
- 其他五类报告和普通Agent始终保持当前协议。
