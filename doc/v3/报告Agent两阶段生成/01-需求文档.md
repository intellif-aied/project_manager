# V3 需求文档：Report Agent 两阶段生成

> 文档状态：已定稿
> 日期：2026-07-27
> 适用范围：默认 Report Agent 生成个人日报 `personal_daily`

## 1. 背景

现有 Session Digest 和 Report Projection 会确定性保留报告事实，但长 Session 在 Projection 后仍可能包含大量语义相近的过程更新。当前 Report Agent 在一次最终写作中同时承担事实识别、主题归并、状态判断、噪声过滤和读者表达，中间结果不可见，也无法区分错误来自事实整理还是正文写作。

2026-07-27 代表性长 Session 的冻结 Report Context 包含 45 条 Evidence Facts。测试服实验表明，两阶段处理可以把事实归并成少量工作主题，并过滤准备、讨论、重复和轨迹信息；同时也证明，如果中间产物只有工作主题总状态，就会把“测试服验证”和“生产发布”混写。

## 2. 产品目标

1. 保持现有 Digest、Projection 和 Report Context 的事实链不变；
2. 同一个默认 Report Agent 必须先提交结构化 Report Brief，再生成最终个人日报；
3. Report Brief 必须可校验、可追溯、可回放，并准确区分每项交付物的状态和环境；
4. 最终日报只使用已接受 Report Brief 中的内容，不重新展开原始 Context；
5. 首期不影响其他五类报告、普通 Agent、模型额度归属和 MCP 用户身份。

## 3. 产品规则

### 3.1 单 Session 两阶段

- 全流程使用同一个默认 Report Agent、同一个 Agent Session、同一份系统 Report Skill 和同一个 Report MCP；
- Agent 调用 `get_report_context` 后，必须先调用 `write_report_brief`；
- MCP 接受 Brief 并返回标准化内容后，Agent 才能生成最终日报；
- 不创建独立“摘要 Agent”、第二个 Skill 或第二个 MCP。

### 3.2 Report Brief

- Brief 按 Workstream 组织，每个 Workstream 下包含一个或多个 Deliverables；
- 每个 Deliverable 必须包含结果、交付状态、环境、必要验证、明确下一步和引用的 `fact_refs`；
- `released` 只能来自明确生产发布证据；`validated` 只能描述测试环境验证；`completed` 不代表已发布；
- 所有 Evidence Facts 必须被 Deliverable 引用，或进入 `excluded_facts` 并标明排除原因；
- 准备工作、内部讨论、纯命令轨迹、重复表达和无读者价值的实现细节允许排除；
- Brief 不得新增 Context 未支持的结果、原因、环境、指标、风险或计划。

### 3.3 用户可读表达

- 用户可见业务词使用“报告、日报、周报”，禁止“报表”；
- `Report Agent`、`Report MCP`、`Report Context`、`Skill`、`Agent`、`MCP` 保留原名，不组成“报告Agent”“报告MCP”等混合词；
- 技术方案名转换为用户结果，例如“通知深链”写成“点击通知直接打开对应报告”；
- 账号、Token、内部地址、绝对路径、UUID、提交哈希、原始错误码、组件名和命令不得进入 Brief 或最终日报。

### 3.4 最终个人日报

- 最终正文必须携带当前 run 已接受的 `brief_hash`；
- 标题按工作主题组织，不按“生产上线、测试完成、开发完成”等状态分类；
- 同一主题内分别表达已发布、测试验证和待发布事项，不得整体提升状态；
- 个人日报顶部使用“工作概览”二级标题，摘要采用 Markdown 有序列表，按主要工作主题输出 1～5 条，每条独占一行并表达结果及必要状态；
- 个人日报正文使用“工作详情”二级标题，各工作主题使用三级标题，顺序与概览对应；“工作概览”和“工作详情”均由服务端统一补充；
- 正文通常为 2～4 个主题；长度是质量目标，不设置服务端正文硬截断；
- 没有可报告事实时，Brief 显式设置 `no_reportable_work=true`，最终只输出简洁说明。

### 3.5 强制门禁与失败行为

- 两阶段功能开启的个人日报，正常路径必须携带已接受的 Brief；只有 Brief 或最终结果的质量校验重试已耗尽时，才允许当前 run 不带 `brief_hash` 降级写回；
- `brief_hash`、run、用户或 Context 不一致时禁止写回；
- Brief 校验失败时服务端一次返回全部可识别问题，允许 Agent 在同一 Session 内最多修正 2 次；最终日报校验失败最多修正 1 次；超过上限后使用最后一版内容降级生成，不得仅因内容质量问题将 run 标记为失败；
- TypeScript 等正常技术术语不作为内部标识拦截；降级内容仍需通过凭证、内部地址、路径等安全检查，不安全时由服务端写入可编辑的保底日报；
- Agent 即使误调用 `write_report_failure`，服务端也必须在质量重试耗尽场景要求其改为降级写回；真实的来源不可用、身份错配和数据库写入失败仍按失败处理；
- 新产生的失败记录和前端提示只显示稳定中文文案，Agent 原始错误仅写内部日志，不直接展示给用户；
- Brief 已保存但最终写作失败时保留 Brief，便于复盘；
- 功能开关关闭时恢复当前单次个人日报链路。

## 4. 用户流程

1. 用户按现有方式选择 Session 并生成个人日报；
2. Aida 按现有流程冻结 Digest 和 Report Context；
3. Report Agent 获取 Context并生成 Report Brief；
4. Report MCP 校验、保存并返回标准化 Brief；
5. Report Agent 只根据返回的 Brief 生成摘要和正文；
6. Report MCP 校验 `brief_hash` 后按现有逻辑保存日报；
7. 前端继续显示现有生成进度和结果，不增加新的用户步骤。

## 5. 验收标准

| 编号 | 产品规则 | 可观察结果 |
|---|---|---|
| R-01 | 3.1 | 一次个人日报只产生一个 Agent Session，工具顺序包含 Context、Brief、Result |
| R-02 | 3.2 | 代表性 45 Facts Context 被归并为少量 Workstreams，全部 Facts 可追溯或有排除原因 |
| R-03 | 3.2/3.4 | 测试服验证、开发完成和生产发布状态不互相提升 |
| R-04 | 3.3 | 最终内容不含“报表、通知深链、报告Agent”等不自然表达或内部标识 |
| R-05 | 3.5 | 缺失、错配、跨 run 或跨用户 Brief 均无法写回 |
| R-06 | 3.4 | 最终日报由“工作概览”和“工作详情”构成；概览为 1～5 条连续编号列表，详情以三级主题标题展开且顺序对应 |
| R-07 | 3.5 | Brief、Context hash 和最终结果 hash 可按 run 追溯 |
| R-08 | 2.5 | 其他五类报告、普通 Agent、权限和身份链路无行为变化 |
| R-09 | 3.5 | Brief 或结果质量重试耗尽后，个人日报以降级内容成功写回，不出现失败 run |
| R-10 | 3.5 | 前端和失败记录不暴露 Agent 平台原始错误，真实非质量故障仍保持失败语义 |

## 6. 非目标

- 不给 Session Digest 或 Report Projection 增加 LLM；
- 不改变 Digest V2、Session 选择和 Report Context 冻结方式；
- 不创建第二个 Agent、Skill、MCP Server、Agent Session 或 Report Run；
- 不修改统一模型账号和当前用户 Report MCP 身份；
- 不修改前端报告交互和报告内容表；
- 不把纯手写日报直接当作端到端事实 GT；
- 不在首期强制其他五类报告使用 Report Brief。
