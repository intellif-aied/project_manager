# V3 日报项目成果契约

> 日期：2026-07-31
> 文档状态：开发、两日真实 Session 回归及概览通俗化回归完成，待人工确认；未发布生产
> 适用范围：系统默认 Report Agent 的个人日报 personal_daily

## 1. 核心结论

日报回答的是“今天在哪些项目上取得了什么工作成果”，不是代码、测试、部署和发布审计。

Session 中的 Git、目录、文件、测试、构建、合并、部署等信息仍然有价值，但只作为内部关联信号：它们帮助系统判断多段工作是否属于同一项目，不能直接成为日报事项，也不能据此推导“尚未合并”“未发布”“不建议上线”等结论。

系统默认个人日报继续使用一个 Agent Session、一个系统 Skill 和一个 Report MCP。第一次语义处理把冻结 Context 整理成项目成果 Brief，第二次只从已接受 Brief 写日报；不新增 Agent、Skill、MCP 或 LLM 调用。

## 2. 日报事实边界

### 2.1 可以进入日报

- 用户实际推进的产品、项目、协议、方案或工程能力；
- 有冻结证据支撑的设计结果、能力变化、问题解决和用户体验变化；
- 用户明确表达的决定、限制或问题。

### 2.2 只能用于项目关联

- Git commit、branch、diff、merge 和仓库信息；
- CWD、路径、文件名、命令和工具调用；
- 测试、构建、部署、发布及运行环境轨迹；
- Session、Thread 和 thread_refs。

这些信号可以帮助把不同 Session 片段归到同一个项目，但不会写入 Report Brief 的读者字段。

### 2.3 禁止推导

Session 是局部证据，缺少后续记录不等于后续动作没有发生，因此不得推导：

- 代码尚未合并；
- 功能尚未发布或部署；
- 工作尚未完成；
- 暂不建议上线或发布；
- 可以合并、可以发布或达到生产标准。

Agent 自己给出的建议、审计结论和对外部状态的猜测，不是用户工作成果。只有用户明确说出的决定，或冻结证据直接记录的成果，才可以进入 Brief。

## 3. 两阶段生成契约

    Session Digest
      ▼
    Report Projection
      └─ 项目线索、工作事实、threads/thread_refs
      ▼
    Immutable Report Context
      ▼
    系统 Report Agent / Pass 1
      ├─ 用操作信号关联项目
      ├─ 按稳定工作对象合并主题
      └─ 只输出项目成果 Brief
      ▼
    Report Brief 项目成果契约
      ├─ 结构、Fact 覆盖和隐私校验
      └─ 不判断发布、环境或完成状态
      ▼
    同一 Report Agent / Pass 2
      └─ 只根据已接受 Brief 写 Summary 与正文
      ▼
    write_report_result

### 3.1 Report Brief 项目成果子集

系统默认个人日报的新 Brief 只保留：

    {
      "workstreams": [
        {
          "subject": "AIDA 日报",
          "title": "AI 日报生成质量优化",
          "deliverables": [
            {
              "result": "优化日报工作主线关联，减少同一项目被拆分为多个事项",
              "fact_refs": ["fact-001"]
            }
          ]
        }
      ],
      "excluded_facts": [],
      "no_reportable_work": false
    }

该子集沿用 report-brief/v1 的数据库版本，不新增 migration，但系统默认个人日报不再输出 objective、state、environment、validation 或 next_action。因此第二次写作无法把测试状态、发布建议或缺失状态带入日报。

### 3.2 主题规则

- subject 是最短且稳定的产品、项目、协议或业务能力名称；
- 同一工作对象的开发、调研、文档、修复、测试和部署归入同一 Workstream；
- 只有能够被独立分派和验收的成果才拆成独立 Workstream；
- 默认一至三个主题，硬上限五个；
- Session、仓库、目录、文件类型和操作数量不能单独创建主题；
- 服务端按相同 subject 合并，模型负责语义归类。

### 3.3 输出格式

- Summary 每个 Workstream 一条 Markdown 编号项；
- 正文每个 Workstream 一个三级标题；
- 一个成果使用简短段落，多个成果逐条编号换行；
- 只写项目成果，不附加测试、提交、合并、部署、发布建议或 AI 推断；
- 不生成独立的建议、待发布、待部署或审计章节。

### 3.4 工作概览的读者语言

Brief 为了准确归类可以保留必要的专业对象，工作概览不能直接缩写或复制 Brief。Pass 2 需要额外完成一次读者语言翻译：

- 不了解实现细节的同事应能第一次阅读就明白；
- 每条用日常中文回答“解决了什么问题”或“带来了什么变化”；
- 保留必要的用户可识别项目、产品和协议名称，把内部架构名、方法名和新造概念翻译成普通表达；
- 每条优先使用一句话、最多两个分句，不在概览解释实现机制；
- 例如“优化日报工作主线关联与主题显著性”应写成“优化 AI 日报对项目工作的识别和筛选，减少同一件事被拆成多条”；“构建约束式评测体系”应写成“建立日报效果对比方法，用真实数据检验生成质量”。

该要求属于系统 Skill 的写作契约，不增加服务端语义硬校验；表达偶有不足时允许写回，不能因此让用户生成失败。正文详情仍可在确有必要时保留少量专业术语。

## 4. 稳定性设计

生成质量不足不能变成用户生成失败：

1. 服务端校验结构、Fact 覆盖、引用合法性、篇幅、敏感信息和通用项目成果边界；只拦截操作轨迹、Agent 判断及否定/限定范围说明，不根据缺失信息推断生产状态；
2. Brief 仍允许两次纠正，耗尽后沿用现有降级写回；
3. 最终稿结构校验失败时纠正一次，仍失败则无 brief_hash 降级写回；
4. 新 Skill 和 API 滚动更新期间，旧字段仍可解码；带 subject 的项目成果 Brief 会丢弃旧审计字段，历史 Brief 仍可读取；
5. 不修改数据库结构，不需要 migration。

## 5. 兼容边界

- 仅系统默认个人日报使用项目成果 Brief；
- 个人 Agent 使用自己的 Skill，不进入系统 Brief 流程；
- 周报、团队和部门报告保持原流程；
- 不修改前端、Session 选择、MCP 鉴权、系统/个人 Agent 路由和报告表结构；
- Git 等关联信号继续保留在 Digest/Projection，不向最终稿透传。

## 6. 验收标准

确定性测试需要覆盖：

- 相同 subject 合并、不同业务对象保持分离；
- 项目成果 Brief 规范化后只包含 result 与 fact_refs，旧审计字段全部被丢弃；
- 操作型 subject 不因服务端语义正则导致整次生成失败；
- Fact 全覆盖、排除原因、敏感信息和结果结构校验保持有效；
- Summary 编号数与正文三级标题数对应 Workstream 数；
- Summary 使用普通读者能理解的结果表达，不直接复制 Workstream 标题或 Brief 术语；
- 个人 Agent、周报和其他报告类型不受影响；
- 质量重试耗尽仍可降级写回。

真实回归使用冻结 Session 019fa16d-a222-7291-a6a5-d8ec4d5f026d，分别生成 2026-07-30 与 2026-07-31 日报。验收重点不是匹配单一人工稿，而是确认：

- 同一日报项目不再按评测、测试、合并和发布动作拆成多个事项；
- 正文只呈现项目成果；
- 不出现“代码尚未合并”“生产尚未发布”“暂不建议上线”等推导；
- 两日生成均成功且不会因 Brief 质量校验失败而让用户无日报。
