# 生产空参数故障与 Run 身份绑定修复

> 日期：2026-07-28
> 严重级别：P0
> 状态：已修复并发布生产

## 1. 用户故障

用户21的个人日报 Run `958458d9-8e65-489f-8bfc-0de80ff46752` 已成功读取包含46条Facts的 Report Context，但后续连续13次以空对象调用 `write_report_brief`。之后 Agent 调用了无关的文件写入工具，并声称日报已生成；Aida没有收到 Brief 或最终日报，最终以 `REPORT_WRITEBACK_MISSING` 失败。

Aida未保存错误日报，数据门禁有效；但用户没有得到日报，且 Agent Session 的成功叙述与Aida业务结果不一致。

## 2. 已确认根因

- Run ID没有在Aida、启动消息或Context阶段丢失；`get_report_context`首次调用携带正确Run ID。
- 原始模型工具事件的参数就是空对象，不是Agent平台转发时丢失。
- 旧协议要求模型在每次MCP调用中重复`run_id`，关键运行身份依赖模型输出。
- 空对象在Handler入口即因缺少`run_id`被拒绝，没有进入ReportBrief模块，因此run级无效尝试计数保持0，“最多两次纠正”未生效。
- `write_report_brief`使用多层数组和对象作为工具Schema；同一Session随后能向简单字符串工具传入大段正文，说明复杂工具参数是本次故障的直接触发面。

## 3. 修复决策

不以更换模型作为修复方案。系统必须在模型输出不可靠时仍保持Run身份、重试边界和业务结果一致。

1. `ReportRunSubmitter`为每个Run签发独立MCP Token，在签名Claims中加入`report_run_id`，保留当前Aida用户`uid`。
2. Auth Middleware验证签名后把`report_run_id`写入请求Context。
3. managed Report tools由服务端解析绑定Run，不向模型暴露`run_id`；若兼容参数中的Run与绑定Run不同，返回`REPORT_RUN_MISMATCH`。
4. `write_report_brief`外层只接收一个`brief_json`字符串，服务端解码后继续使用原ReportBrief Schema、事实覆盖、安全、状态和持久化校验。
5. 保留旧结构化Brief参数的服务端兼容读取，确保API与Skill滚动更新期间不中断；普通MCP toolset继续使用原`run_id`契约，不影响其他报告业务。
6. 空对象会使用绑定Run进入ReportBrief校验并计入无效尝试，不能再绕过run级重试上限。
7. 系统Skill明确禁止发送run_id、创建文件或使用无关工具，只允许通过Report MCP完成业务写回。
8. 畸形`brief_json`也必须先校验Run归属和可写状态，再计入同一无效尝试预算；第三次无效返回`REPORT_BRIEF_RETRY_EXHAUSTED`。
9. Report Brief、Report Result和Run错配错误码同时写入JSON-RPC message与data，兼容只显示message的Agent平台。

## 4. 必须通过的回归

- 运行绑定Token能同时恢复用户ID和Run ID。
- managed tools的Schema均不包含`run_id`；普通MCP toolset仍保留`run_id`。
- `write_report_brief({})`能进入绑定Run的Brief校验，而不是在入口返回“run_id缺失”。
- 参数Run与凭证Run不一致时拒绝。
- 原用户21、46 Facts来源在测试服原样生成：工具链只能是Skill → Context → Brief（有界纠正）→ Result，Aida产生真实日报记录。
- Agent Session不得调用文件、Shell或其他非Report工具；当前Agent平台没有per-Agent硬工具白名单，因此以实际工具事件和Aida写回门禁验收。出现无关工具调用或缺失写回时必须失败关闭并回退。
