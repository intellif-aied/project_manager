# V3 选择性 Brief 与自动 Fact 归档方案

> 日期：2026-07-31
> 状态：开发完成，测试服真实回归通过，待人工验收
> 适用范围：System Report Flow 的默认个人日报 `personal_daily`

## 1. 生产样本结论

2026-07-31 生产日报对比中，排除“所选 Session 与当日实际汇报完全无关”这一明确不处理的特殊情况后，可比较的同源样本暴露出三类问题：

1. 同一项目的实现、验证、文档和辅助工作被拆成多个事项；
2. 可核验但只起支撑作用的 Fact 被逐条写进日报，正文像工作审计；
3. Context 中已有可识别项目名，但工作概览只保留了泛化活动描述。

同源样本中既有可直接使用和仅需补项目名的结果，也有需要大量删减、合并的结果。这说明当前问题不是 Markdown 格式、Session 选择或事实缺失，而是 Report Brief 同时承担“事实守恒”和“最终选材”时，把事实覆盖错误地实现成了输出穷举。

本期不把任何一份手写日报当作标准答案，只用多用户生产形态判断方向：完整读取证据，按项目归并，最终只选择读者值得看到的成果。

## 2. 设计原则

### 2.1 Evidence 完整，Report 选择性输出

- Report Context 保留全部 Evidence Fact；
- Report Agent 必须先阅读全部 Fact，再按稳定工作对象归并；
- Report Brief 只提交可汇报主题、读者值得看到的成果和必要的显式排除；
- Final Report 只消费已接受 Brief，不重新扩大主题。

Truth Gate 继续约束未知引用、虚构事实、冲突归属、敏感内容和空结果，但不再要求模型为了通过校验而逐条输出所有 Fact。

当 `brief_json` 本身不是合法 JSON 时，MCP 返回标准解析错误帮助 Agent 定点修正，只记录并返回语法原因，不回显正文；服务端不猜测补括号或放宽结构校验。
System Report Skill 同时明确在根级 `excluded_facts` 前依次闭合 Deliverables 数组、Workstream 对象和 Workstreams 数组，避免单 Workstream 时漏关外层结构。

### 2.2 深化既有 Report Brief Module

模块 seam 仍是 `write_report_brief`，外部参数和返回结构不变。复杂度由 Report Brief Module 内部吸收：

```text
完整 Report Context
  → Agent 阅读、归并并选择少量成果
  → write_report_brief（现有 Interface）
  → 服务端校验已引用和显式排除
  → 未引用 Fact 自动归档为 not_selected
  → 存储完整 Brief
  → 向 Final Report 返回精简 Accepted Brief
```

调用方、MCP tool schema、数据库 schema、Digest 和 Projection 均不需要理解自动归档行为。

## 3. 契约调整

### 3.1 正常 Brief

当 `no_reportable_work=false` 且至少存在一个 Workstream：

- Agent 可只引用选中的 Fact；
- Agent 可继续用 `preparation`、`discussion`、`trace`、`duplicate`、`low_reader_value`、`secondary_activity` 显式说明必要排除；
- 服务端把其余未引用 Fact 确定性补入存储 payload，原因固定为内部值 `not_selected`；
- `not_selected` 不加入公开合法原因列表，Agent 主动提交仍会被拒绝；
- 存储结果按 `fact_ref` 排序，便于审计和评测复现。

### 3.2 空日报

当 `no_reportable_work=true` 且 Context 有 Fact 时，仍要求 Agent 用具体合法原因显式排除每条 Fact。空日报比少写一项风险更高，不能通过自动 `not_selected` 掩盖模型误判。

### 3.3 Final Report 输入

存储 payload 保留自动 `not_selected` 以维持 Fact 守恒和现有评测能力；`Accepted()` 返回给第二阶段时过滤这些内部归档项，只保留 Workstream 和 Agent 显式排除项，避免大量低价值 Fact 再次影响写作。

## 4. Skill 选材规则

1. 先按稳定项目、产品、协议或业务事项归并 Fact，再选成果；
2. 已存在可识别命名项目时，组件、UI 区域、质量维度或活动不能另建 Subject，除非证据明确表明它是独立管理的事项；
3. 命名项目的 Subject 必须只写项目名，不追加阶段、组件、能力或活动后缀；每个 Subject 只创建一个 Workstream，子方向放入标题或成果；
4. 同一项目的实现、调查、文档、验证和修复优先合并；
5. 评测工具、数据集、评审材料和文档默认作为支撑证据，不因可核验而自动成为 Deliverable；
6. 系统个人日报中每个 Workstream 最多保留三个读者值得看到的 Deliverable；这是 Skill 选材约束，不增加服务端失败门槛；
7. 一个成果可引用多个 `fact_ref`，禁止按一条 Fact 创建一条 Deliverable；
8. 可识别项目名存在时，工作概览以该名称起句，避免只写“完成优化”“整理方案”等泛化活动；
9. 未选 Fact 无需由 Agent 枚举，且 Agent 不得主动提交 `not_selected`。

以上均为 System Report Skill 的选材规则，不增加服务端主题数量或 Deliverable 数量的失败门槛，避免为了质量优化降低生成成功率。

## 5. 范围与非目标

本期只改：

- `api/internal/reportbrief` 的正常 Brief Fact 归档与 Accepted Brief 裁剪；
- System Report Skill 的归并、选材和项目名表达；
- 对应测试与本文档。

本期明确不改：

- Session Digest、Report Projection 和 Report Context schema；
- Session 选择与来源覆盖界面；
- Markdown 的“工作概览 + 工作详情”结构；
- Personal Report Agent、自定义 Skill 和第三方 MCP；
- 周报、团队日报等其他报告类型；
- 数据库 schema、前端和报告权限；
- Session 与当日实际工作完全无关的特殊情况。

## 6. 风险控制

| 风险 | 控制 |
| --- | --- |
| 模型遗漏重要成果 | 全量 Context 仍提供给第一阶段；Skill 先归并再选择；真实同源样本人工 Review |
| 模型误判为空日报 | 空日报必须显式排除全部 Fact，不能自动归档 |
| 自动归档不可追踪 | 存储 payload 保留排序后的 `not_selected` |
| 第二阶段再次受噪声影响 | Accepted Brief 不返回自动归档项 |
| 新规则造成生成失败 | 只增加软选材规则，不增加新的语义硬门槛或重试 |
| 影响个人 Agent 或其他报告 | 改动限定 System Report Flow 的默认个人日报 Skill；MCP Interface 不变 |

## 7. 测试与验收

确定性测试必须覆盖：

- 正常 Brief 自动归档未引用 Fact；
- 自动归档顺序稳定；
- `Accepted()` 隐藏自动归档、保留显式排除；
- Agent 主动提交 `not_selected` 被拒绝；
- 空日报缺少显式排除时继续失败；
- 现有未知引用、冲突引用、敏感内容、Brief hash 和结果门禁不回退；
- Report Evaluation 继续读取完整存储 Brief；
- Personal Report Flow 和其他报告类型行为不变。

测试服真实回归只选择来源相关的用户日，重点人工检查：

1. 同一项目是否合并；
2. 次要 Fact 是否不再逐条进入正文；
3. 工作概览是否保留可识别项目名；
4. 多主题真实工作是否没有被错误压成一项；
5. 生成是否一次成功，不因选材规则增加 Brief 重试。

## 8. 发布与回退

- 无数据库 migration，不需要数据库备份；
- 测试服先发布 API 与新的 System Report Skill，并用相同冻结样本重复生成；
- 回退时恢复上一版 API 镜像和上一版 System Report Skill；
- 未完成人工 Review 前不进入生产发布清单。

## 11. 专有名词与普通表达分界回归（2026-08-01）

用户确认的表达原则不是“日报尽量使用专业术语”，而是明确区分两类文字：

1. 已有项目、模型、硬件、协议、框架和 Skill 术语保持原样，例如 `Skill`、`RTL`、`CUDA`、`H20`，不翻译、不改写；同一证据同时出现规范原名和翻译昵称时，优先规范原名。
2. 其他工作描述使用普通、自然的中文，不为常规操作创造技术名词。例如“调整弹窗点击后的跳转”不能包装成“通知深链”。

该原则同时进入 Brief 阶段和 Final 阶段的 System Report Skill，只是软写作约束，没有增加服务端失败门槛、术语词库或型号替换 Case。测试候选为 `100866/aida-report@1.1.22`。
