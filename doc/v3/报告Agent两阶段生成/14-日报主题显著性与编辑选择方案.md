# V3 日报主题显著性与编辑选择方案

> 日期：2026-07-30
> 文档状态：首期实现完成，后续主题契约重复盲评已归档
> 适用范围：系统默认个人日报 `personal_daily`

## 1. 问题定义

当前 System Report Flow 更接近 Session 工作审计：只要 Evidence Fact 有明确结果，Report Agent 就倾向于把它组织成 Workstream。用户真正需要的是工作汇报：完整审阅当期事实，但只把最重要的少数工作主线写入日报。

2026-07-29 部门最终日报参考集提供了群体形态证据：41 名成员中 22 名有已保存日报，其中 15 份人工编写、4 份 AI 生成后人工修改、3 份 AI 生成且未修改。人工日报整体多采用简短编号或分层列表，主题颗粒度和篇幅明显不同于工作审计。某位员工只填写“baigong demo 协议设计”说明个人取舍可能与 Session 全量结果差异很大，但该单份反馈不是期望答案，也不能用于定制排除规则。

该问题不是单纯的格式问题，也不能只靠 Git 或 Session 关联解决。它包含两个独立判断：

1. 主题关联：哪些事实属于同一工作目标；
2. 编辑选择：哪些真实工作值得进入当期最终日报。

## 2. 已确认的领域口径

### 2.1 事实完整不等于报告完整

Report Context 必须保留完整证据，Report Brief 必须审阅并归属每条 Fact；Final Report 不需要逐条复述所有真实活动。可核验是进入候选集的条件，不是独立占用日报条目的充分条件。

### 2.2 员工最终稿不是事实真值

- 人工编写日报可用于观察主题选择、篇幅和表达习惯；
- AI 生成后人工修改的样本最适合分析用户删除、合并和改写行为；
- 未修改 AI 日报只能作为同期系统输出对照；
- 员工没有写某项工作，不足以证明该工作未发生或永远不应出现；
- 即使员工最终稿与冻结 Source Evidence 配对，事实质量仍由 Evidence Baseline 和 Gold Review 判定，员工稿本身不是标准答案；
- 禁止根据单个员工或单个用户日增加主题保留、合并或排除规则。

### 2.3 报告是编辑选择，不是审计日志

默认个人日报优先呈现一至三个可汇报主题；只有存在更多彼此独立、读者价值明确的主要成果或必须关注的问题时，才扩展到最多五个。准备、讨论、自动化过程、重复验证和跨项目低价值活动不得因为文本长或技术细节多而自动升级为主题。

### 2.4 优化目标来自群体形态

主题数量、结构、篇幅和表达方式应参考多用户、多日期生产日报的聚合分布，而不是复刻某一份日报。单个用户日适合暴露问题和做同源回归，只有多样本配对结果才能证明方案整体改善。

## 3. 目标与非目标

### 3.1 目标

1. 每条 Fact 继续被完整审阅并明确归属；
2. 同一目标的实现、文档、验证、修复和发布优先合并；
3. 支撑事实进入对应 Deliverable，不独立生成 Workstream；
4. 次要活动可以有依据地不进入 Final Report；
5. 默认输出一至三个主要主题，降低过度召回和同项目拆分；
6. 明确失败、阻塞和安全风险在具有当期读者价值时不能因精简而丢失；
7. 保持现有两阶段、单 Agent Session、单 Skill、单 MCP 和 Brief hash门禁。

### 3.2 非目标

- 不把手写日报直接训练成事实排除规则；
- 不使用 `cwd`、目录名或父子 Session 祖先链定义业务项目；
- 不在本期新增模型调用、Agent、Skill 或 MCP；
- 不在本期采集 Git repository identity；
- 不改变个人 Agent 流程、报告权限、Session 选择或写回协议；
- 不用字数、Session 时长或工具调用次数直接决定工作重要性；
- 不保证在缺少用户显式重点时完全复现每个员工的主观取舍。

## 4. 方案选择

### 4.1 方案 A：所有可核验结果都进入日报

优点是事实召回高；缺点是把日报变成工作审计，正是当前问题。否决。

### 4.2 方案 B：直接模仿员工最终稿

优点是篇幅接近人工习惯；缺点是员工稿可能遗漏事实，且没有 Source Evidence 时无法区分主动取舍与忘记填写。否决。

### 4.3 方案 C：在现有 Report Brief seam 增加编辑选择

保留完整 Context 和 Fact 覆盖门禁，由 Report Agent 第一次语义处理同时完成主题关联与编辑选择：

- 可汇报事实进入一至三个主要 Workstream；
- 支撑事实附着在对应 Deliverable；
- 确实发生但不值得独立汇报的 Fact 以 `secondary_activity` 明确归入 `excluded_facts`；
- 准备、讨论、轨迹、重复和低读者价值继续使用现有排除原因；
- 第二次处理只根据已接受 Brief 写作，不重新扩大主题。

该方案复用现有 `write_report_brief` Interface，不新增调用和身份面；复杂度集中在 Report Brief Module，调用方和 Final Report Module 不需要理解新的选择过程。确定采用。

## 5. 首期数据契约

本文件定义的首期编辑选择只扩展一个排除原因：

```json
{
  "excluded_facts": [
    {
      "fact_ref": "fact-012",
      "reason": "secondary_activity"
    }
  ]
}
```

`secondary_activity` 的准确含义是：该 Fact 有真实工作结果，但相对当期主要目标不值得进入独立日报主题。它不能用于掩盖以下内容：

- 会改变选中主题最新状态的事实；
- 选中主题的明确失败或阻塞；
- 对读者决策有直接影响的安全风险；
- Final Report 已经引用但 Brief 未提供依据的内容。

支撑事实不使用 `secondary_activity`，而是继续放入对应 Deliverable 的 `fact_refs`。因此不新增 `supporting_facts` 数组，也不扩大 MCP tool 的参数面。后续主题契约阶段在 Workstream 内增加可选 `subject`，但仍沿用同一个 `brief_json` Interface；具体约束见后续主题契约文档。

## 6. 编辑选择规则

Agent 在提交 Brief 前按以下顺序处理：

1. 阅读全部 Fact，并结合 Work Thread 形成候选工作主题；
2. 合并服务于同一用户目标的实现、文档、部署、验证、修复和后续动作；
3. 识别主要目标：用户持续直接推进、产生明确业务或工程结果、形成可交付状态，或存在必须关注的问题；
4. 把解释主要结果所需的事实作为支撑事实并入 Deliverable；
5. 把真实但相对次要的独立活动标为 `secondary_activity`；
6. 默认保留一至三个 Workstream，只有主题确实彼此独立且都具有高读者价值时才增加，硬上限仍为五个；
7. 检查每条 Fact 已进入 Deliverable 或 `excluded_facts`，且没有状态提升、事实重复或内部信息泄漏。

不得把以下信号单独视为显著性：文本更长、技术名词更多、Session 更久、包含部署操作、包含测试数字、位于单独仓库或由 Subagent 产出。

## 7. 数据流与模块责任

```text
Session Digest
  └─ 完整确定性证据
      ▼
Report Projection
  └─ 清理、去重、Fact/Thread 引用，不决定重要性
      ▼
Immutable Report Context
      ▼
Report Brief Module
  ├─ 主题关联
  ├─ 编辑选择
  ├─ 支撑事实归并
  ├─ 次要活动排除
  └─ 完整 Fact 覆盖与状态校验
      ▼
Final Report Module
  └─ 只根据已接受 Brief 写作，不增加主题
```

模块 seam 保持在 `write_report_brief`：外部 Interface 仍是一个序列化 Brief，新增行为隐藏在既有 Module 内。这样可以通过 Report Brief 的可观察输出测试主题数量、Fact 归属和排除原因，不需要测试 Agent 内部推理过程。

## 9. 测试与验收

### 9.1 确定性测试

- `secondary_activity` 被 Brief Module 接受并稳定归一化；
- 未知排除原因仍被拒绝；
- 每条 Fact 仍必须且只能进入 Deliverable 或排除列表；
- Final Report 继续受 Brief hash 和 Workstream 顺序约束；
- 非个人日报和 Personal Report Flow 行为不变。

### 9.2 真实数据回归

使用 2026-07-29 刘敬一 77 Fact 样本做同源对比：

- 当前基线：4～5 个主题，包含多个部署和 Walkthrough；
- 员工单项反馈只记录为个人取舍差异，不作为候选输出目标；
- 首期候选观察：主题数量是否收敛，同一目标是否减少拆分，过程性 Walkthrough 是否减少独立成项；
- camelAI、Symphony 等有证据的独立结果不能仅因员工未写而判定为多余，是否保留需在多用户配对 Case 和生产日报形态分布中判断；
- 本样本只能证明链路和局部行为变化，不能单独证明质量提升。

再从部门参考集中选择至少 4 个 `human_revised_ai` 和 6 个 `human_authored` 候选，后续补齐 Source Evidence 后形成 10 个正式配对 Case。未补齐前只做定性 Review，不宣称质量指标提升。

### 9.3 观察指标

- Supported Theme Coverage：Gold Review 确认的重要证据主题是否保留；
- Extra Theme Rate：AI 额外生成主题的比例；
- Fragmentation Rate：同一主题被拆成多个 Workstream 的比例；
- Wrong Merge Rate：不同主题错误合并的比例；
- Production Pattern Fit：主题数量、层级和篇幅是否接近多用户生产日报分布；
- State Accuracy：状态和环境是否保持；
- Directly Usable：用户是否可以直接保存或只做风格调整。

## 10. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 过度精简导致重要工作丢失 | 所有 Fact 必须显式归属；失败、阻塞和安全风险执行强保护 |
| 模型把次要活动当噪声 | `secondary_activity` 与 `low_reader_value` 分开定义，保留真实工作语义 |
| 只改 Skill 造成模型波动 | Brief Module 固定枚举、覆盖门禁和 Workstream 上限，真实数据重复运行比较 |
| 单人最终稿反向带偏规则 | 单份最终稿不是期望答案；只使用多用户聚合形态和 Evidence Baseline 形成评测结论 |
| 项目仍无法跨 Session 关联 | 后续单独采集匿名 `repository_key`，不使用 cwd 或父子 Session 替代 |
| 影响个人 Agent | 仅发布系统 Report Skill；个人 Agent 和 System Report MCP Interface 不变 |

## 11. 后续阶段

1. 聚合多用户、多日期生产日报的主题数量、层级、篇幅和合并颗粒度，形成 Production Report Pattern Baseline；
2. 为不同长度、不同主题数量的用户日补齐 Source Evidence Snapshot 和 Evidence Baseline，避免单样本偏置；
3. 采集端从原始 Git metadata 生成不可逆 `repository_key`，辅助跨根 Session 主题关联；
4. AI 后人工修改样本只用于统计删除、合并和改写类型，不把具体修改直接写成规则；
5. 固定 10 个 Evaluation Case 后，对基线与候选做配对 Version Comparison。

## 12. 发布与回退

- 首期无 migration，不需要数据库备份；
- 先发布新的测试 Skill 版本，再重建测试 API；
- 使用同一批冻结 Session 运行至少两次，人工 Review 主题选择与状态；
- 若多余主题没有下降或出现重要事实丢失，回退 Skill 版本和 API 镜像；
- 未形成配对评测结论前，不进入生产发布清单。
