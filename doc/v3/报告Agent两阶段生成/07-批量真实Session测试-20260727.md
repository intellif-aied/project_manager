## 1. 测试目标

验证两阶段个人日报在不同账号、不同 Session 数量和不同原始文件体量下的稳定性与内容表现。测试只使用测试服，不修改其他报告、普通 Agent、账号或权限链路。

## 2. 样本与分配

- 从本机近一周 Codex 日志中选取 25 个互不重复 Session；
- 测试账号：t05、t06、t07、t08、t09，每个账号 5 个；
- 单文件约 0.05～111.07 MB，总量约 295 MB；
- 上传后按真实活动日期生成切片，最终形成 11 个“账号＋日期”日报组，每组 1～5 个 Session；
- 25 个上传全部成功，25 个 Digest/Projection 全部进入 ready。

- 最终状态与 Brief 的 `state/environment` 基本一致，未发现把测试环境直接提升为生产发布的样本。

## 5. 结论

1. 原始 Session 文件大小与日报长度没有直接线性关系。61.54 MB 的样本投影后只有 1 Fact，正文 206 字；9.92 MB 的五 Session 组合产生 45 Facts，正文 1,390 字。当前链路确实以 Projection 后的有效证据决定输出，而不是按原始日志体量堆内容。
2. 多 Session 归并有效。4～5 个来源能够按工作目标合并为 2～4 个主题，没有按 Session 顺序逐条复述。
3. 状态分离有效。`released/production`、`validated/test`、`blocked` 和 `in_progress` 在最终日报中得到区分。
4. 并发稳定。11 个 Run 同时提交，全部成功，未出现身份串用、写错账号、来源错配或 Brief Hash 冲突。

## 6. 暴露的问题

### 6.1 Brief重试策略与真实模型能力不一致

当前文档写“Brief失败只修正一次”，但3/11样本需要两次修正才通过。原因通常是Flash每次只修复服务端指出的第一项违规。当前服务端没有记录或限制失败次数，因此实际行为与文档约束不一致。正式发布前必须二选一：服务端一次返回全部可识别违规并严格限制一次重试，或把协议明确调整为最多两次修正。

### 6.2 最终安全门禁仍有漏项

现有门禁成功拦截原始错误码、私网地址、UUID、哈希和“深链”，但批量样本仍出现以下读者价值较低的实现细节：

- `UDP 123`端口描述；
- `systemd --user`命令参数；
- `/agent`内部接口路径；
- 少量CSS、ARIA、Runtime ID等实现术语。

这些内容没有泄露凭据，但不满足需求文档中“端口、命令、内部路由不进入最终日报”的严格口径。建议下一轮只扩展确定性安全模式，不做大范围关键词封禁，避免误伤正常技术工作描述。

### 6.3 长报告仍偏实现清单

33～45 Facts样本的主题归并是正确的，但正文仍达到1,200～1,400字，部分段落保留了较多实施步骤。需要人工确认：个人技术日报是否接受该详细程度；若希望更管理化，应在Brief中增加`reader_value`或结果层级，而不是按原始Session大小截断。
