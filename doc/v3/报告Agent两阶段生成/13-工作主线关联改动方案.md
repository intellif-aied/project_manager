# V3 工作主线关联改动方案

> 日期：2026-07-29
> 文档状态：首期开发并完成真实 Session 回归；效果不足，Git 仓库关联进入下一阶段
> 所属范围：默认 Report Agent 的 `Session Digest → Report Projection → Report Context → Report Brief` 链路

## 1. 问题定义

当前 AI 日报经常把同一项工作的开发、修复、验证和发布拆成多个 Workstream。表面上是模型没有理解上下文，实际原因是 Report Projection 把 Digest 中已有的关联信息扁平化为互相独立的 Evidence Facts，Report Agent 只能根据事实文本相似度猜测它们是否属于同一工作。

本次需要解决的是“工作事实如何关联为同一条业务工作主线”，不是“如何根据本地目录划分项目”。

## 2. 已确认的代码事实

| 编号 | 代码事实 | 代码位置 | 影响 |
|---|---|---|---|
| F-01 | Session 已保存 `cwd`、`project_name` | `sessions`、`canonicalsync`、`sessionsync` | 只能说明采集位置，不能稳定代表业务项目 |
| F-02 | Digest 的 Work Unit 和 Daily Highlight 已包含 `goal`、`work_unit_ref`、`source_ref` | `api/internal/sessiondigestv2/model.go` | Digest 已经具备部分工作主线信息 |
| F-03 | `DigestV2ContentItem` 未携带业务项目或 Git 仓库身份 | `api/internal/reportsource/digest_v2.go` | 多个 Session 冻结后缺少结构化技术关联信息 |
| F-04 | Projection 读取 Highlight 时只输出结果文本、状态、分类和时间，没有输出 `goal`、`work_unit_ref`、`source_ref` | `api/internal/reportcontext/projection.go`、`types.go` | Agent 最终看到的是失去来源关系的孤立事实 |
| F-05 | Projection 会清理纯 Git 操作、分支、worktree 和 commit hash 等报告噪声 | `api/internal/reportcontext/projection.go` | Git 文本不能被可靠用于关联，且不应直接进入最终报告 |
| F-06 | Presentation Profile 只用自然语言要求“按个人工作目标归并” | `api/internal/reportcontext/projection.go` | 当前归并依赖模型根据事实文本自行推断 |
| F-07 | Report Brief 只按完全相同的 `title + objective` 合并 Workstream | `api/internal/reportbrief/service.go` | 服务端无法纠正模型已经拆开的近义 Workstream |

## 3. 目标与非目标

### 3.1 目标

1. 让 Report Agent 能判断多条 Evidence Facts 是否属于同一条工作主线；
2. 同一工作主线下的开发、文档、修复、测试和发布优先归并表达；
3. 保留完整事实、状态和环境边界，不因归并造成事实丢失或状态提升；
4. 允许工作主线跨 Session、跨仓库和跨日期延续；
5. 维持 Digest 和 Projection 的确定性，不在这两个阶段新增 LLM；
6. Git 和目录信息只作为辅助信号，不直接暴露在用户日报正文中。

### 3.2 非目标

- 不用 `cwd`、目录名或 `project_name` 直接定义业务项目；
- 不按 Git commit、branch 或 repository 强制合并所有事实；
- 不新增 Agent、Skill、MCP Server 或额外模型调用；
- 不改变 Session 选择、报告权限、系统/个人 Agent 路由和写回门禁；
- 不在本期建设全局项目管理或长期知识图谱；
- 不让服务端规则替代 Report Agent 做最终语义写作。

## 4. 核心判断

### 4.1 主关联信号

工作主线判断按以下优先级使用信号：

1. 显式业务关联：AIDA Requirement、Task、Work Item 或用户明确给出的项目/事项名称；
2. Digest 工作目标：`goal` 及同一 `work_unit_ref` 内的结果、验证和未解决项；
3. 跨 Session 语义关联：目标、对象、交付物和下一步存在明确连续关系；
4. 技术关联信号：规范化 Git 仓库身份、分支、模块路径和提交关系；
5. 采集位置：`cwd`、`project_name` 仅用于诊断和最低置信度提示，默认不参与自动归并。

### 4.2 Git 的合理边界

Git 信息可用于增强关联，但不能代表业务项目：

- 一个业务项目可能同时修改前端、后端和部署仓库；
- 一个代码仓库可能同时承载多个业务项目；
- branch 会变化，commit 过于细粒度；
- worktree 和不同检出目录可能属于同一仓库；
- remote 可能包含凭证或内部地址，不能原样进入 Context 或最终报告。

如果后续采集 Git 信息，应生成内部稳定的 `repository_key`，原始 remote 只在采集端规范化，移除凭证后再生成不可逆标识。`repository_key` 只能作为关联证据，不作为 Workstream 标题。

## 5. 目标数据结构

### 5.1 Report Context

在 `work_evidence` 中增加工作单元字典，Fact 只保存短引用。原始 `source_ref/work_unit_ref` 只在 Projection 内部用于生成稳定引用，不直接发送给 Agent：

```json
{
  "threads": [
    {
      "thread_ref": "thread-001",
      "goal": "修复日报来源选择与生成流程"
    }
  ],
  "facts": [
    {
      "fact_ref": "fact-003",
      "kind": "result",
      "text": "完成日报来源选择器的分页修复",
      "source": "agent_claim",
      "thread_refs": ["thread-001"],
      "observations": []
    }
  ]
}
```

约束：

- `thread_ref` 由 Projection 根据冻结 Digest 的来源和 Work Unit 确定性生成；
- Agent 只能看到短引用和经过现有 Projection 清理后的 `goal`，看不到原始 Session/Work Unit 标识；
- 同一 Fact 如果在多个 Work Unit 中重复出现，继续保持一条 Fact，并关联多个 `thread_refs`；
- `threads` 使用 Context 级字典，避免每条 Fact 重复携带完整目标；
- 内部引用只用于归并，不进入 Brief 契约和最终日报；
- 不把绝对路径、remote URL、commit hash直接发送给 Agent。

### 5.2 Report Brief

Report Brief 保持现有 Workstream/Deliverable 结构和 `fact_refs` 契约，不增加 `thread_refs` 参数：

```json
{
  "title": "日报生成流程优化",
  "objective": "提高日报来源归并和生成稳定性",
  "deliverables": [
    {
      "result": "完成日报来源选择器的分页修复",
      "fact_refs": ["fact-003"]
    }
  ]
}
```

Agent 在第一次语义处理中使用 `threads + fact.thread_refs` 理解关联，提交 Brief 时仍只引用 `fact_refs`。这样不扩大 `write_report_brief` 参数面，也不会增加模型因新引用字段填写错误而触发校验重试的概率。最终 Workstream 数量和标题仍由 Agent 决定。

## 6. 确定性关联策略

### 6.1 第一阶段：恢复现有关系

不新增采集协议，先恢复当前已存在但在 Projection 丢失的信息：

1. `DigestV2ContentItem` 保留每个 Session 的来源边界；
2. Projection 使用 `DailyHighlight.goal/work_unit_ref/source_ref` 建立 Context 级 `threads` 字典；
3. 同一来源内的同一 `work_unit_ref` 生成同一短 `thread_ref`，原始引用不出 Projection；
4. Fact 通过 `thread_refs` 关联一个或多个工作单元，精确重复事实继续去重；
5. 跨 Work Unit 不做服务端语义强制合并，由 Report Agent 根据 `goal` 的相同或连续关系形成 Workstream；
6. 更新系统 Report Skill：先解析线程字典和 Fact 关系，再生成 Workstream，Brief 继续只提交 `fact_refs`。

该阶段直接解决“同一 Work Unit 被拆散”，风险和改动范围最小。

真实数据回归后确认：该阶段能恢复 Fact 对原始工作目标的可见性，但 Digest 中的 Work Unit 实际接近单次对话目标，不能稳定代表业务项目，因此不能单独解决跨 Session、跨任务的项目归并。

### 6.2 第二阶段：显式业务关联

如果 Session 或工作事实能够关联 AIDA Requirement、Task、Work Item，则把这些引用写入 `explicit_links`。相同业务对象是跨 Session 归并的强信号，但仍需保留不同交付状态。

本阶段必须先确认现有 Session 事件中业务引用的来源和可信度，不允许从普通文本中的数字或名称强行识别业务 ID。

### 6.3 第三阶段：Git 辅助关联

仅在第一阶段效果不足时增加采集端 Git 元数据：

1. 采集 Git common directory、规范化 remote 和当前 branch；
2. 服务端只保存派生后的 `repository_key`、`branch_key`；
3. 同一 repository 只提高关联置信度，不直接生成同一 `thread_ref`；
4. commit hash 只用于证据追踪，不参与工作主线分组；
5. monorepo 结合模块路径和业务目标，避免把无关工作合并。

2026-07-30 真实数据回归已触发本阶段：Codex 原始 Session 元数据中存在 `git.repository_url`、branch 和 commit，但当前扫描、上传、Session 存储和 Digest 链路没有保留 repository identity。后续应在采集端规范化 repository URL 并生成不可逆 `repository_key`，只上传派生 key；禁止把原始 remote、凭据、路径或 commit hash传入 Report Context。

## 7. 数据流

```text
Session Events
  │
  ├─ 用户目标、结果、验证、未解决项
  ├─ 显式 Requirement/Task 引用（存在时）
  └─ Git 技术信号（后续可选）
  ▼
Session Digest
  └─ 保留 goal + work_unit_ref + source_ref
  ▼
Report Projection
  └─ threads 字典 + Fact.thread_refs + observations
  ▼
Immutable Report Context
  ▼
同一个 Report Agent 第一次处理
  └─ 先按 thread_ref/goal 归并，再生成 Report Brief
  ▼
Report Brief
  └─ Workstream + Deliverables + fact_refs（契约不变）
  ▼
Final Report
```

## 9. 兼容与发布策略

- `threads` 和 Fact 的 `thread_refs` 均为可选字段，旧 Context 可继续读取，Brief 契约完全不变；
- 首期只应用于系统默认个人日报，个人 Agent 不强制遵循系统归并规则；
- Report Context hash 会因结构变化而变化，只影响新建 Run，不修改历史 Run；
- 不重新构建历史 Digest；新 Projection 可读取现有 Digest 中的 `goal/work_unit_ref/source_ref`；
- 功能开关关闭时继续使用当前 Fact 结构和 Skill 行为；
- 首期不需要数据库迁移；若后续持久化 Git identity 或业务对象引用，再单独设计 migration。

## 10. 风险与控制

| 风险 | 场景 | 控制方式 |
|---|---|---|
| 错误合并 | 同一目标名称下实际存在多个独立事项 | `thread_ref` 只提供关联，不强制折叠 Deliverable |
| 仍然拆分 | 不同 Session 对同一目标使用完全不同表述 | 优先接入显式业务引用，Git 仅辅助；保留人工 GT 评测 |
| 状态被提升 | 测试、开发和生产事实被归并后写成“已上线” | Deliverable 继续独立保存状态和环境，沿用 Brief 校验 |
| 内部信息泄露 | remote、路径、commit进入报告 | Context 只提供派生 key，不提供原始敏感值 |
| 上下文膨胀 | 每条 Fact 重复携带大量元数据 | 使用短引用和 Context 级字典，设定字节预算并测试长 Session |
| 影响个人 Agent | 系统结构约束进入用户自定义 Skill | 首期只调整 System Report Flow |

## 11. 2026-07-30 真实 Session 回归结论

### 11.1 测试样本

- 来源：本机 `/home/aied/liujingyi` 在 2026-07-29 的真实 Session；
- 测试账号：测试服普通用户 t03；
- 上传：7 组 Session，报告冻结后包含 77 条有效 Fact；
- 对照：生产问题日报 `232d1b9f-e38c-4a88-aea6-c83caf6c3655`。

### 11.2 首期实现结果

- Run：`46b06bbe-7736-4c0d-b3d9-ecb106de7138`；
- 77 条 Fact 全部保留并带 `thread_refs`；
- 生成成功，Brief 正常接受，未发生降级；
- 仍输出 5 个 Workstream，camelAI/Symphony 的部署与各自 Walkthrough 仍被拆开；
- 结论：恢复 Work Unit 关系没有造成事实丢失，但对项目级归并帮助有限。

### 11.3 已否决的 Session 家族实验

测试中曾把父子 Session 归为同一主线，Context 的 Thread 数从 177 降至 7、字节数从约 184 KB 降至 133 KB，但 Fact 映射检查发现 Codex 历史 fork 会让 Symphony、Multi-agent 等不同业务工作共享祖先 Session。父子关系表示执行上下文继承，不等于业务项目关系，存在错误合并风险，因此该实验代码和测试部署已撤回，不进入当前方案。

### 11.4 下一步固定边界

1. 保留首期 `goal + work_unit_ref + source_ref` 恢复能力，作为局部上下文；
2. 不使用 `cwd`、`project_name` 或 Session 祖先链定义项目；
3. 新增采集端派生的 `repository_key`，作为跨根 Session 的辅助关联信号；
4. `repository_key` 只能提高同项目归并优先级，不能覆盖不同目标、状态和环境边界；
5. 使用同一批 77 Fact 再做 A/B 回归，验收重点是把 camelAI 的部署与 Walkthrough、Symphony 的部署与 Walkthrough分别归到各自连续工作中，同时不把 Multi-agent 工作误并入 Symphony。
