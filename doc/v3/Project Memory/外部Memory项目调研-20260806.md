# 外部 Memory 项目对 AIDA Project Memory 的启发

> 日期：2026-08-06  
> 范围：`coleam00/claude-memory-compiler`、`TencentCloud/TencentDB-Agent-Memory`  
> 结论：作为设计参考有明显价值，但不建议把任一项目直接接入 AIDA。

## 1. 总结

AIDA 当前的“原始 Session/Fact 保留、夜间 Project Memory Agent 整理、服务端校验 Proposal、日报只读少量历史候选、Memory 失败不阻塞日报”方向是正确的，与两个项目的核心思想一致。

后续最值得补齐的不是新的 Memory 中间件，而是：

1. 把现有 Project Memory 明确拆成“项目索引、项目画像、原子证据、原始来源”四层，并保持逐层回溯；
2. 增加 Memory lint/健康检查，持续发现别名污染、过期项目、冲突 Workspace、无来源项目和历史成果泄漏；
3. 召回先按用户和 Workspace 做强过滤，再做语义排序，设置数量、Token、耗时预算，失败直接跳过；
4. 为 Source 覆盖不足和旧项目错误吸附新工作建立负样本评测，不能只评“项目名有没有命中”。

## 2. claude-memory-compiler

该项目把对话视为不可变源码：SessionEnd/PreCompact Hook 抽取 daily log，随后由 LLM 把 daily log 编译成概念文章、关联文章与索引；SessionStart 只注入索引和最近日志。检索在个人规模下依赖结构化索引而不是向量库，并提供 broken link、orphan、stale、contradiction 等 lint。[README](https://github.com/coleam00/claude-memory-compiler/blob/54eddd709e83d3be244e9c56c9fc3a6cf375d534/README.md) [架构规范](https://github.com/coleam00/claude-memory-compiler/blob/54eddd709e83d3be244e9c56c9fc3a6cf375d534/AGENTS.md) [compile.py](https://github.com/coleam00/claude-memory-compiler/blob/54eddd709e83d3be244e9c56c9fc3a6cf375d534/scripts/compile.py) [lint.py](https://github.com/coleam00/claude-memory-compiler/blob/54eddd709e83d3be244e9c56c9fc3a6cf375d534/scripts/lint.py)

对 AIDA 最有价值的是“Compiler + lint”思路：

- Session/Fact 是不可变来源，Project Memory 是可重建编译产物；
- 夜间任务只处理 Source Hash 发生变化的用户日；
- 日报生成只读取小型项目索引，不加载历史日报全文；
- Memory 需要像代码一样有静态检查、构建记录和版本，而不是只观察 Agent 是否成功返回。

不适合照搬：它是单用户本地 Markdown 工具，LLM 可以直接写整份知识文件，缺少 AIDA 所需的多租户隔离、数据库事务、CAS、结构化 Proposal 校验和生产审计；其 query/compile 在规模较小时会读取大量现有文章，也不适合 AIDA 每次日报的严格 Context 预算。

## 3. TencentDB-Agent-Memory

该项目的长期记忆采用 L0 Conversation → L1 Atom → L2 Scenario → L3 Persona 的分层结构；短期记忆把原始工具输出外置，只在 Context 中保留 Mermaid 状态图和可回查的 `node_id`。README 强调顶层结构可以逐层回溯到底层原文。[README](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/fe3230f176f1bf5832fee79d12494bbc2d19a8aa/README.md)

召回实现支持 keyword、embedding、hybrid/RRF，分别注入动态 L1 记忆和相对稳定的 Persona/Scene 导航；有召回预算、超时后跳过 Memory、最多三次深查等保护。[auto-recall.ts](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/fe3230f176f1bf5832fee79d12494bbc2d19a8aa/src/core/hooks/auto-recall.ts) L1 抽取会限制每批消息、背景消息和每次记忆数量，并在写入前做冲突/去重。[l1-extractor.ts](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/fe3230f176f1bf5832fee79d12494bbc2d19a8aa/src/core/record/l1-extractor.ts)

对 AIDA 的映射：

| TencentDB 分层 | AIDA 对应层 |
| --- | --- |
| L0 Conversation | 原始 Session/Slice、生产只读 Evidence |
| L1 Atom | Digest/Projection Facts、Workspace Evidence |
| L2 Scenario | Project Profile：稳定名称、别名、工作线索、Workspace 关系 |
| L3 Persona/Navigation | 每用户小型 Project Index，仅用于候选导航 |

可借鉴：分层回溯、召回预算、超时跳过、强作用域过滤后再混合排序、冲突检测，以及“索引先行、详情按需”的渐进披露。

不适合照搬：通用 Persona 会推断用户特质和隐含信号，这对日报属于高风险噪声；AIDA 只应记项目身份，不应记“用户性格”或把历史状态当当天事实。Mermaid 压缩更适合长任务工具日志，不应替代 AIDA 的结构化 Fact Ref。直接引入其 Node/OpenClaw/SQLite 或 TencentDB 插件也会形成第二套持久化和用户边界。

## 4. 对 AIDA 的具体建议

### 4.1 保留现有主链路

继续由 AIDA DB 持久化、专用 Project Memory Agent 夜间整理、MCP 读取和写回、服务端验证 Proposal。不要把管理员 Agent 的沙盒文件或第三方 Memory Store 作为真相源。

### 4.2 把 Project Memory 做成分层编译产物

- Project Index：最多几个候选，只含 `project_ref`、稳定名称、最近确认日期、匹配原因；
- Project Profile：别名、稳定 workstream cues、Workspace links、状态与版本；
- Evidence Atom：明确来源、类型、权重和 `evidence_ref`；
- Raw Source：原始 Session、日报与 Selection，只在受控服务端按引用回查。

日报 Agent 默认只拿 Project Index 和关联的 Fact Ref，不需要读取历史成果正文。

### 4.3 新增 Memory lint

至少检查：

- 没有证据引用的项目或 alias；
- alias 是成果句、进度、测试/发布状态或普通动作；
- 同一 Workspace 同时高置信关联多个活跃项目；
- 仅由未修改 AI 稿长期维持的项目；
- 项目长时间未出现但仍高权重召回；
- Snapshot 与输入 Source Hash 不一致；
- Project Hint 引入当前 Fact 无法支持的历史结论。

### 4.4 收紧召回而不是增强强制归并

召回顺序建议保持：`user_id` 隔离 → Workspace/代码库身份过滤 → 明确名称和 alias 命中 → workstream cue → 语义排序。Workspace 单独命中只能提供候选；只有当前 Fact 的语义也匹配时才提高权重。若同 Workspace 当天出现新项目名或冲突目标，旧 Memory 必须降级为 `candidate_only`。

### 4.5 评测

在现有 Project Association v2 基础上增加三类门槛：

- Positive：模块名能否恢复稳定父项目；
- Boundary：同仓库新项目是否被旧项目吸附；
- Coverage：Source 没有项目证据时能否保持 unresolved，而不是编造关联。

同时记录 Recall 了什么、为什么命中、使用了多少 Context、最终是否采用，才能区分 Memory 未召回、Agent 未采用和 Source 本身不足。

## 5. 建议优先级

1. 先实现 Memory lint 和召回审计字段；
2. 再补 Project Profile 的稳定 workstream cues 与证据引用；
3. 用 v2 数据集做 Memory on/off、旧项目吸附和 Source Coverage 对照；
4. 数据规模明显增大后，再评估混合检索或按需 drill-down MCP；当前不需要引入第三方向量库或 Memory 服务。
