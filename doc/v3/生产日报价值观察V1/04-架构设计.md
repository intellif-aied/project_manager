## 4. 架构

```text
personal_daily Report Run 成功
  → 不可变 Generation Snapshot

用户保存 / 提交 / 删除
  → 追加式 User Outcome Event

Snapshot + Outcome + 当前日报 + Run
  → 确定性差异与按日聚合 API
  → 管理员“生产日报价值观察”
  → Production Observation Snapshot 导出
```

生产请求只保存事实数据，不调用 Reviewer。

## 5. Generation Snapshot

每个成功 `personal_daily` Run 一份：

- `run_id`、`user_id`、`report_date`；
- Generated Draft、Summary 和 Hash；
- Variant Manifest、`variant_hash`；
- 生成完成时间。

Variant Manifest 最小包含：

- Manifest schema 版本和 `pipeline_profile`；
- 实际阶段顺序；
- Agent ID、Agent Version ID 和实际模型标识；
- Digest、脱敏、Context、Brief 的 schema/实现版本；
- Report Skill 与 Report MCP 的标识及版本。

上述字段规范化后整体计算 `variant_hash`。某阶段不存在时不进入阶段顺序，对应版本字段为空并按 `not_applicable` 解释。代码 Revision、独立 Prompt Hash 和任意配置 Hash 不进入 V1；只有运行时能够稳定取得、且会影响当前链路结果的版本信息才进入 Manifest，避免保存无法验证的伪精度。

模型只是 Variant 配置，不作为 Variant 主键。Snapshot 与 Run 一对一，不随日报编辑或删除改变。

## 6. User Outcome Event

用户明确保存、提交或删除时追加：

- `daily_report_id`、`user_id`、`report_date`；
- `action`、`action_at`；
- 当时对应的 `run_id`；
- 保存或提交内容及 Hash。

事件只追加不覆盖；删除事件和此前 Outcome 在业务日报删除后继续保留。无法绑定 Run 的手写日报事件不形成 Comparable User Outcome。

## 7. 当前用户日归并

按 `observed_at` 依次确定：

1. 找到用户日最后一个成功 Run 及其 Snapshot；
2. 找到绑定该 Run、且发生在该 Run 之后的最新保存或提交 Outcome；
3. 存在则形成 Comparable User Outcome；
4. 不存在时，若之后有删除事件则为已删除；否则当前正文与 Draft 相同为 Observed Unchanged，不同为无明确结果；
5. 更早 Run 和 Outcome 只进入时间线、生成次数和历史行为，不进入当前结果分母。

## 8. 查询职责

管理员 API 以 `report_date` 和 `observed_at` 为边界，返回：

- 汇总指标的分子、分母和值；
- 用户日级全部 Run 和缺失状态；
- 全文、Summary Region 和主题确定性差异；
- Variant、组织和状态筛选；
- 14/30 日实时趋势；
- 带 `observed_at`、筛选条件和 Hash 的冻结文件导出。

列表不返回完整正文；详情按用户日返回 Draft 与用户稿。页面默认不展示 Session 正文。

## 9. 权限与兼容

- 页面和 API 只允许 `admin`；
- 普通用户报告接口和 Report MCP 协议不变；
- 只采集新的 `personal_daily`，不回填历史；
- 其他报告和普通 Agent 不变；
- 导出只供授权内部使用，不进入通用日志。
