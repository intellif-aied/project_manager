# 日报生成质量评估 V1：需求文档

> 文档状态：待确认
> 日期：2026-07-28
> 适用范围：默认 Report Agent 生成个人日报 personal_daily
> 前置基线：Report Agent 两阶段生成

## 1. 背景

默认个人日报已经采用同一 Report Agent、同一 Agent Session 内的两阶段生成：

1. 根据不可变 Report Context 生成并提交结构化 Report Brief；
2. 只根据服务端接受的 Report Brief 生成最终日报。

当前链路已经具备 Context、Brief、事实引用、Hash门禁和有界重试，但还不能完整回答以下问题：

- 一次日报生成是否在正确阶段完成或失败；
- Brief是否正确组织了Context事实；
- 最终生成稿是否被用户直接接受、编辑、重新生成或删除；
- 不同Report Agent模型、Digest版本、Skill版本之间的结果是否存在可观察差异；
- 人工评审时能否一次获得Context、Brief、生成稿和用户最终稿。

现有daily_reports.content会被用户编辑或后续生成覆盖，ai_runs只保存Result hash，不能保证历史生成稿可回放。现有无效尝试只保存次数，不能统计每次失败的确定性问题类型。

## 2. 产品目标

V1建立一个不改变用户生成流程的最小质量闭环：

1. 保存一次personal_daily Report Run的完整生成链路；
2. 自动记录可由确定性代码判断的Brief、Result和运行指标；
3. 记录用户现有保存、提交、编辑、重新生成和删除行为形成的质量信号；
4. 支持内部按条件抽样并进行轻量人工评审；
5. 支持按Report Agent模型和关键版本进行观察性效果对比。

质量评估只用于分析，不阻止用户查看、保存或提交日报。

## 3. 范围

### 3.1 首期覆盖

- 默认Report Agent；
- 报告类型personal_daily；
- 现有两阶段生成链路；
- 现有个人日报保存、提交、重新生成和删除行为；
- 内部查询、导出和人工评审结果。

### 3.2 不受影响

- personal_weekly；
- team_daily、team_weekly；
- department_daily、department_weekly；
- 普通Agent；
- 当前Report Agent账号、Report MCP用户身份和权限；
- Digest、Projection、Context、Brief和最终日报的生成顺序；
- 用户现有日报页面和操作步骤。

## 4. 统一口径

### 4.1 模型与版本

当前Session Digest V2由确定性Go代码生成，不使用LLM，因此V1不使用“Digest模型”概念。

- DSV4 Flash、MiniMax、GPT系列属于Report Agent模型；
- Digest按digest_version比较；
- Brief和最终日报由同一Report Agent模型生成，不虚构两个独立模型；
- 每个新Run必须冻结Report Agent模型、Digest版本、Skill版本和Prompt版本或Hash。

如果未来Digest引入LLM，应另立需求，不在V1预先设计。

### 4.2 自动检查边界

确定性代码可以判断：

- Fact是否全部被引用或排除；
- Deliverable是否缺少fact_refs；
- 明确的状态与环境组合是否违规；
- 是否命中现有禁止表达、内部标识或安全模式；
- Brief、Context、Run、用户和Hash是否匹配；
- Run是否成功以及失败阶段。

确定性代码不能可靠判断：

- 某个Fact是否重要；
- 被排除的Fact是否应该进入日报；
- 是否新增无依据的语义事实；
- 测试证据是否被语义提升为生产发布；
- Workstream归并是否正确；
- 是否过度压缩或保留无价值过程；
- 最终表达是否自然。

不能可靠自动判断的内容必须进入人工评审，不得用关键词启发式结果冒充硬指标。

### 4.3 用户行为边界

Report MCP生成成功后自动写入daily_reports并设置saved，不代表用户主动接受。

用户行为只来源于现有明确操作：

- 用户保存；
- 用户提交；
- 用户修改正文后保存或提交；
- 用户再次生成同一天日报；
- 用户删除日报。

“用户未修改”不等于内容完全正确，“用户修改”也不等于生成失败。

当前没有可靠的页面阅读、关闭或主动放弃事件。V1不记录“用户放弃”，只允许按指定观察窗口查询“生成后无明确用户动作”。

## 5. 完整生成链路

同一个新personal_daily Report Run必须可追溯到：

- Report Context及其schema和context_hash；
- Report Brief及其schema和brief_hash；
- 不可变的最终生成摘要和生成正文；
- report_result_hash；
- 用户最后一次明确保存或提交的正文；
- 最终日报记录；
- Report Agent模型；
- Digest版本；
- Skill owner、slug和version；
- Prompt版本或Hash；
- Agent version id；
- 各阶段关键时间；
- Run最终状态、失败阶段和错误码。

Context和Brief继续复用现有不可变记录，不要求复制保存。

生成稿必须按Run保留，不能只依赖可编辑、可被重新生成覆盖的daily_reports.content。

历史数据缺少生成稿时不得根据Hash反推或伪造回填，必须显式标记不完整。

## 6. 确定性指标

### 6.1 Fact与Brief

| 指标 | 定义 |
| --- | --- |
| fact_total | Context内唯一fact_ref数量 |
| fact_referenced_count | 至少被一个Deliverable引用的唯一Fact数量 |
| fact_excluded_count | excluded_facts内唯一Fact数量 |
| fact_unaccounted_count | 既未引用也未排除的唯一Fact数量 |
| workstream_count | 服务端接受并规范化后的Workstream数量 |
| deliverable_count | 服务端接受并规范化后的Deliverable总数 |

同一Fact被多个Deliverable引用时，fact_referenced_count只计一次。

接受后的Brief必须满足：

    fact_referenced_count + fact_excluded_count = fact_total
    fact_unaccounted_count = 0

### 6.2 校验与运行

| 指标 | 定义 |
| --- | --- |
| brief_invalid_attempts | 无效Brief提交次数 |
| brief_submission_count | 无效提交加最终成功提交；耗尽时等于无效提交次数 |
| brief_first_pass_accepted | Brief已接受且无效提交次数为0 |
| result_invalid_attempts | 无效Result提交次数 |
| generation_succeeded | Report Run最终是否成功 |
| failure_stage | 失败发生的阶段 |
| failure_code | 稳定错误码 |

无效Brief和Result提交应记录确定性问题类型及累计次数，不能只保存错误文本或最终修正后的0问题结果。

### 6.3 耗时

至少记录或可稳定计算：

- 来源与Digest准备耗时；
- Context构建耗时；
- Brief生成至接受耗时；
- 最终日报写作至保存耗时；
- Report Run总耗时；
- Digest是否直接复用已有结果。

历史数据或复用场景无法准确计算某项耗时时，该项为空，不以0代替未知。

## 7. 确定性异常

自动记录以下问题是否在任一次提交中出现及出现次数：

- FACT_UNACCOUNTED：Fact未引用且未排除；
- DELIVERABLE_FACT_REFS_MISSING：Deliverable没有fact_refs；
- STATE_ENVIRONMENT_INVALID：确定性的状态与环境组合违规；
- INTERNAL_PATTERN_DETECTED：命中确定性内部标识、安全或禁用表达规则；
- BRIEF_BINDING_MISMATCH：Brief、Context、Run或用户绑定不一致；
- RESULT_BINDING_MISMATCH：Result、brief_hash、Run、Context或用户绑定不一致。

接受后的Brief和Result不应存在上述硬门禁问题，但评估必须保留修正前的问题，才能比较模型首次生成质量。

语义上的状态提升、环境混写和事实幻觉不归入自动异常。

## 8. 用户反馈行为

每个成功生成的Run至少记录：

- 是否发生明确用户保存；
- 是否发生提交；
- 是否编辑正文；
- 生成稿与最后明确用户稿是否完全一致；
- 新增字符数；
- 删除字符数；
- 文本差异比例；
- 是否删除主题；
- 是否新增主题；
- 是否被后续Run重新生成覆盖；
- 是否被用户删除；
- 指定观察窗口内是否没有明确用户动作。

### 8.1 文本差异

计算前只允许：

- 统一换行符；
- 去除每行行尾空白；
- 去除全文首尾空白。

不修改标点、标题和正文语义。

完全一致通过规范化正文Hash判断。文本差异按Unicode字符计算新增和删除数量：

    diff_ratio =
      (inserted_runes + deleted_runes) /
      (generated_runes + user_runes)

结果范围为0到1，空文本必须有确定性处理规则。

### 8.2 主题差异

主题以Markdown二级标题识别：

- 生成稿存在、用户稿不存在：删除主题；
- 用户稿存在、生成稿不存在：新增主题。

标题改名会表现为一次删除和一次新增。该结果只是编辑信号，不直接解释为质量错误。

## 9. 人工抽样评审

V1不开发评审页面。内部人员必须能按以下条件查询或导出Run：

- Facts数量较多；
- Brief校验失败或发生重试；
- 用户正文差异较大；
- 被重新生成；
- 未提交；
- 指定观察窗口内无明确用户动作；
- 指定Report Agent模型；
- 指定Digest、Skill或Prompt版本；
- 指定日期范围；
- 尚未人工评审。

每个导出样本应包含：

- Context；
- Brief或明确缺失原因；
- 生成稿或明确缺失原因；
- 用户最后明确保存或提交的正文；
- 关键指标；
- Run状态和版本信息；
- 人工评审结果。

导出属于内部受控能力，不向普通用户开放。

## 10. 人工错误分类

| 错误类型 | 定义 |
| --- | --- |
| FACT_OMISSION | 重要事实在Brief或最终日报中遗漏，或被不合理排除 |
| FACT_HALLUCINATION | 新增Context或Brief不支持的事实 |
| STATUS_UPGRADE | 将证据支持的状态错误提升 |
| ENVIRONMENT_MIX | 测试与生产环境被混写 |
| WRONG_GROUPING | 不相关事实错误归并 |
| OVER_COMPRESSION | 过度压缩导致有价值信息丢失 |
| NOISE_RETENTION | 保留无读者价值的准备、轨迹或实现噪声 |
| INTERNAL_LEAKAGE | 出现规则未覆盖的内部标识或技术噪声 |
| REPETITION | 同一事实重复表达 |
| POOR_READABILITY | 表达不自然、结构混乱或难以阅读 |

人工结果只包含：

- severity：pass、minor、unacceptable；
- stage：brief、final、both；
- error_types：零个或多个错误类型；
- note：简短备注；
- reviewer和reviewed_at。

不设置自动总分。错误必须标明发生在Brief还是最终日报，否则无法定位两阶段中的问题来源。

## 11. 模型与版本对比

V1至少支持按以下维度分组：

- report_model_id；
- digest_version；
- skill_version；
- prompt_hash；
- 日期范围；
- Fact数量分桶。

至少可以查看：

- 样本量；
- Brief首次接受率；
- 各类确定性校验问题次数；
- Fact未覆盖数量；
- 用户修改率和平均diff_ratio；
- 重新生成率；
- 平均耗时；
- P95耗时；
- 生成成功率；
- 存在人工样本时的pass、minor、unacceptable分布。

V1只支持历史批次或不同发布窗口的观察性比较。没有同Context配对、随机分流或相同样本控制时，不得宣称模型存在因果优劣。

V1不自动选择模型，不自动切流，不自动生成模型排行榜。

## 12. 验收标准

| 编号 | 要求 | 可观察结果 |
| --- | --- | --- |
| R-01 | 完整链路 | 新Run可关联Context、Brief、生成稿、用户稿和全部Hash |
| R-02 | Brief覆盖 | 接受后的Brief满足Fact覆盖等式 |
| R-03 | 首次质量 | 修正前的确定性问题和无效次数可查询 |
| R-04 | 生成稿保护 | 用户编辑、重新生成或删除后仍可回放原Run生成稿 |
| R-05 | 用户动作 | AI自动保存不计为用户保存，明确动作和时间准确 |
| R-06 | 编辑差异 | 完全一致、字符Diff和主题差异可重复计算 |
| R-07 | 失败追踪 | 失败Run可查询失败阶段、错误码和已有中间产物 |
| R-08 | 人工抽样 | 可按规定条件导出完整配对材料 |
| R-09 | 模型对比 | 可按模型和版本计算样本量、成功率、重试率、修改率和P95耗时 |
| R-10 | 历史诚实性 | 无法恢复的数据保持缺失并明确标识 |
| R-11 | 范围隔离 | 其他五类报告和普通Agent行为不变 |
| R-12 | 用户无感 | 不增加页面、评分步骤或生成等待阶段 |

## 13. 明确非目标

- 在线或离线LLM Judge；
- 生成后再次调用大模型自动评分；
- 因评估结果阻止用户查看日报；
- 新的用户评分弹窗或日报页面；
- 新的日报生成流程或业务状态；
- 新的Agent、Skill、MCP或Report Run；
- 通用评测平台；
- 复杂Dashboard；
- 自动把用户编辑稿当作事实GT；
- 自动模型排名、选择或切流；
- 同Context多模型自动回放；
- 为其他五类报告和普通Agent增加评估；
- 在V1中把Digest改为LLM处理；
- 用关键词穷举代替人工语义评审。

## 14. 待确认事项

以下事项确认后再进入架构设计和开发方案：

1. “无明确用户动作”的默认观察窗口是否采用24小时；
2. 用户只修改next_day_plan、不修改正文时，是否记为“编辑日报”但正文diff_ratio保持0；
3. 人工评审是否允许后续覆盖，还是需要保留多次评审历史；
4. 内部导出是否只需要文件导出，还是同时需要数据库只读查询示例；
5. 历史数据是否执行尽力回填，还是只对方案上线后的新Run采集。
