# 日报生成方案评测 V2：固定数据集

> 文档状态：已确认
> 日期：2026-07-28

## 1. V2 Dataset

首版建立 10～20 个 Evaluation Case，覆盖：

- 短、中、长 Session；
- 单 Session 与多 Session；
- 多主题和跨 Session 归并；
- 测试/生产状态混合；
- 高噪声、内部标识和敏感信息；
- 空信息、易遗漏和易过度压缩。

每个 Case 包含：

- `case_id`、报告日期和用于回放的 Session Slice Key；
- Digest 前冻结的 Source Evidence Snapshot 文件及 SHA-256；
- 结构化 Evidence Baseline：Evidence Item 的 `required/optional/exclude` 取舍、Source 引用、状态、环境、主题关系和禁止断言；
- 标签、来源和用途授权。

Dataset Manifest 还必须引用 Production Report Pattern Baseline 的版本、统计文件和 SHA-256。Pattern Baseline 不进入 Evidence Baseline，也不参与事实正确性判断。

日报 Case 以 `Asia/Shanghai` 自然日为事实边界。`required`、`optional` 的每个 Source 引用必须发生在 `report_date`；跨日事件只允许作为 `exclude` 保存，用于证明为什么不应计入当日。

## 2. 样本来源

- 本机具有代表性的 Codex Session；
- 测试服已有可完整回放的 Source Evidence；
- 经明确授权后导入测试服的生产来源 Session。

生产来源样本进入测试服后只作为冻结测试 Evidence，不连接生产实时数据。选择具体 Case 在 V1 数据基础和 V2 Bundle 契约完成后进行。

### 2.1 Production Report Pattern Dataset V1

生产手写个人日报全集用于建立 Production Report Pattern Baseline。它回答生产日报通常有多少条、采用什么层级、篇幅多长、如何使用列表；不能在缺少 Source Evidence Snapshot 时判断某篇日报是否遗漏事实，或某个具体主题是否应当出现。

该数据集必须聚合使用。任何单份人工稿、AI 草稿或员工修改稿都不是 Evaluation Case 的期望答案。

Git 只版本化脱离正文的聚合 `statistics.json`。手写日报全文即使经过规则脱敏也可能残留内部语境或未识别人员信息，保留在受控数据位置，不进入代码仓库和 Evaluation Bundle。

## 3. 版本规则

- Dataset 发布后不原地修改；
- Case、Source 或 Baseline 变化时生成新版本；
- 开发集用于定位问题，不单独证明候选更优；
- 回归集每次必须全部执行；
- 经 Gold Review 确认的新失败类型进入下一 Dataset 版本；
- V2 不建设 Holdout。

## 4. 形成流程

1. 只读盘点并形成 20～30 个匿名候选；
2. 在已证明的测试 Runtime 从固定 Slice 冻结 Digest 前 Source Evidence；
3. 按标签选择 10～20 个 Case；
4. 人工标注结构化 Evidence Baseline，并验证所有 Source 引用；
5. 绑定聚合 Production Report Pattern Baseline；
6. 生成 Dataset Manifest、Source 文件和全部 Hash；
7. 发布 Dataset V1，后续只新增版本。
