# GitHub 同类 Agent 语义审核与有界纠错机制调研

> 日期：2026-08-07
> 范围：调研与架构输入，不修改业务代码。

## 1. 结论

AIDA 不应继续通过调大或调小 Project Memory 的提示强度解决日报质量问题。当前问题是架构职责混合：Memory 既召回项目，又在 Compiler 中替换标题、合并 Workstream；Generator 既选择事实，又自行判断结果是否忠实。

适合 AIDA 的不是开放式 Self-Reflection，而是服务端控制的有界流程：

```text
GENERATE → VERIFY → ACCEPT
                  ├→ PATCH_ONCE → RECHECK → COMPILE
                  └→ CONSERVATIVE_FALLBACK
```

- 当天 Facts 唯一决定“今天做了什么、做到什么程度”；
- Project Memory 只提供按 Fact 绑定的稳定项目候选；
- 独立 Verifier 检查项目误绑、错误合并、事实拔高、限定词丢失和主要成果遗漏；
- Verifier 只能输出结构化问题和白名单 Patch，不能自由重写全文；
- 最多一次审核、一次局部修复；超时、格式错误或仍不合格时保守降级，不能导致日报失败。

## 2. 一手项目调研

### 2.1 LangGraph：显式状态机与硬上限

LangGraph 的 Reflection 示例将生成和反思做成独立节点，通过条件边形成显式循环；节点异常另由包含 `max_attempts`、退避与抖动的 RetryPolicy 处理。[Reflection 示例](https://github.com/langchain-ai/langgraph/blob/23961cff61a42b52525f3b20b4094d8d2fba1744/docs/docs/tutorials/reflection/reflection.ipynb) [RetryPolicy](https://github.com/langchain-ai/langgraph/blob/f22af6248c93df08b553e9a264f6367797e0fddb/libs/langgraph/langgraph/types.py#L416-L435)

对 AIDA 的启发：`draft → verify → patch/fallback` 应成为服务端显式状态；网络异常重试和语义纠错必须分开计数。无需引入完整 LangGraph，可在现有 Run Processor 中实现同样的有限状态机。

### 2.2 CrewAI：独立 Guardrail Agent 与结构化反馈

CrewAI 的 Task Guardrail 在任务输出后运行；字符串 Guardrail 会创建独立 `Guardrail Agent`，结构化返回 `valid` 与 `feedback`，并有单独的 `guardrail_max_retries` 预算。[Task Guardrail](https://github.com/crewAIInc/crewAI/blob/18c52c4e1db20fecc1db1a8da53485d3d49314c6/lib/crewai/src/crewai/task.py#L252-L282) [LLMGuardrail](https://github.com/crewAIInc/crewAI/blob/18c52c4e1db20fecc1db1a8da53485d3d49314c6/lib/crewai/src/crewai/tasks/llm_guardrail.py#L39-L119)

AIDA 可借鉴独立 Reviewer 和结构化反馈，但不应照搬默认 3 次全文重跑。日报 Context 已冻结，应一次局部修复后立即收口。

### 2.3 OpenAI Agents SDK：Output Guardrail 是独立边界

OpenAI Agents SDK 在最终输出后运行 Output Guardrail；Guardrail 可以在内部运行另一个 Agent，并用结构化 `GuardrailFunctionOutput` 携带结果。默认 tripwire 会终止执行并抛异常。[工作流边界](https://github.com/openai/openai-agents-python/blob/47ff39bf7904bbc8c06681f5fa70c0c3025b882a/docs/guardrails.md#L10-L18) [Output Guardrail](https://github.com/openai/openai-agents-python/blob/47ff39bf7904bbc8c06681f5fa70c0c3025b882a/docs/guardrails.md#L40-L52) [独立 Guardrail Agent](https://github.com/openai/openai-agents-python/blob/47ff39bf7904bbc8c06681f5fa70c0c3025b882a/docs/guardrails.md#L73-L130)

AIDA 应把 Reviewer 放在 Draft 与 Compiler 之间并保存独立 Trace，但不能照搬 tripwire：质量审核失败必须转成降级结果。

### 2.4 PydanticAI：不同失败使用不同预算

PydanticAI 将工具重试和最终输出校验重试分开；ValidationError 或 ModelRetry 会转换为具体反馈，超过输出预算后收口。[独立预算](https://github.com/pydantic/pydantic-ai/blob/4be0d648c1a5ddbc127a4ba2407f9af7587812fe/pydantic_ai_slim/pydantic_ai/agent/abstract.py#L92-L113) [错误转换](https://github.com/pydantic/pydantic-ai/blob/4be0d648c1a5ddbc127a4ba2407f9af7587812fe/pydantic_ai_slim/pydantic_ai/_output.py#L132-L179) [预算收口](https://github.com/pydantic/pydantic-ai/blob/4be0d648c1a5ddbc127a4ba2407f9af7587812fe/pydantic_ai_slim/pydantic_ai/_agent_graph.py#L356-L373)

AIDA 应把系统异常重试、Schema 修复和语义 Patch 分成三个预算；语义预算耗尽后不能抛给用户，而应进入保守降级。

### 2.5 Self-Refine：反馈有效，但开放式全文重写不适合

Self-Refine 将流程拆成 Init、Feedback、Iterate，并提供 `max_attempts` 限制。[三阶段流程](https://github.com/madaan/self-refine/blob/9a206d41e5d2d0c241bb441f41eeadb945afaa55/README.md#L203-L230) [有界示例](https://github.com/madaan/self-refine/blob/9a206d41e5d2d0c241bb441f41eeadb945afaa55/README.md#L190-L198)

它证明“根据具体反馈修正”可行，但同一模型多轮全文重写容易延续偏差或引入新事实。AIDA 只保留一次独立审核和字段级 Patch。

### 2.6 Mem0：多信号召回可借鉴，事实同权不可照搬

Mem0 的官方 README 描述了 Semantic、BM25、Entity 与时间信号融合；同时把 Agent 生成事实作为同等权重的一等事实，并说明部分效果来自托管平台专有优化。[Memory 算法说明](https://github.com/mem0ai/mem0/blob/b05dc2740f9f7696d94ea06c3e04c64aac55997b/README.md#L45-L63)

AIDA 可借鉴 Workspace/Git、明确项目实体、关键词、语义和时间的多信号候选召回；不能让 `agent_claim` 与用户陈述、实现证据和人工日报同权，必须保留来源等级与证据引用。

### 2.7 Letta：小型只读 Memory 与外部检索分层

Letta 将常驻 Memory Blocks 与按需进入 Context 的 External Memory 分开；Block 有长度限制、描述和只读权限，其工具也区分局部 Patch 与整体 Rewrite。[Memory 分层](https://github.com/letta-ai/letta/blob/ff19ffeafeb54bd2a7dc5d4a552f10191732a235/letta/prompts/system_prompts/letta_v1.py#L3-L20) [只读 Block](https://github.com/letta-ai/letta/blob/ff19ffeafeb54bd2a7dc5d4a552f10191732a235/letta/schemas/block.py#L32-L40) [Patch 边界](https://github.com/letta-ai/letta/blob/ff19ffeafeb54bd2a7dc5d4a552f10191732a235/letta/functions/function_sets/base.py#L453-L490)

AIDA 的 Report Agent 只应接收小型、只读的项目候选；完整 Memory 和 Evidence Ledger 留在服务端。Report Agent 与 Reviewer 都不能写 Project Memory。

## 3. AIDA 目标职责

| 模块 | 只负责 | 明确禁止 |
| --- | --- | --- |
| Fact Projection | 当天事实、来源、状态、限定词 | 推导项目名和完成状态 |
| Project Resolver | 为具体 Fact 给出稳定项目候选 | 改标题、强制合并、补成果 |
| Report Generator | 选择 Facts，生成一次 Draft | 更新 Memory、删除事实限定词 |
| Semantic Verifier | 找出 Draft 的语义问题 | 自由重写、创造新 Fact |
| Patch Applicator | 校验并应用白名单 Patch | 接受整份自由文本 |
| Report Compiler | 确定性归一化、渲染、持久化、降级 | 根据 Memory 再做语义归并 |

最关键的架构调整是：从 Compiler 移除 Project Memory 的标题替换和跨 Workstream 强制合并。Memory 关联在生成前以候选出现，不能在 Agent 输出后再次改变语义。

Project Candidate 必须包含 `project_ref`、稳定 `name`、`related_fact_refs`、置信度和证据类型；“AIDA”是稳定项目名，“Project Memory 与 CLI 修复”是阶段工作项，不能成为后续父标题。高置信候选也只是建议，Generator 可拒绝，Verifier 不得强迫采用。

## 4. Verifier 与 Patch 契约

Verifier 不应读取 770KB 全量 Context，只接收 Draft、已引用及附近少量候选 Facts、每条 Fact 的来源/状态/限定词/Workspace，以及与这些 Facts 绑定的项目候选。

输出固定为：

```json
{
  "decision": "accept|patch_required|fallback",
  "issues": [{
    "code": "unsupported_project|cross_project_merge|overclaim|lost_qualifier|memory_injection|major_omission",
    "target": "workstream-1.deliverables[1]",
    "fact_refs": ["fact-407"],
    "reason": "事实写明尚未证明，正文改为稳定实现"
  }],
  "patches": [{
    "op": "replace_text|replace_subject|split_workstream|drop_deliverable|add_qualifier",
    "target": "workstream-1.deliverables[1].result",
    "value": "完成测试服样本验证，项目命名效果仍待进一步验证",
    "supporting_fact_refs": ["fact-407"]
  }]
}
```

Patch 只能修改已有字段、删除不可信内容或恢复 Fact 中已有的限定词；新增 Fact、引入新项目候选、整份 Markdown 重写一律拒绝。

每份日报固定：Generator 1 次、Verifier 1 次、必要时 Patch 1 次，随后只做确定性复核。Verifier/Patch 超时、空输出、Schema 无效或 Patch 不可应用时立即保守降级：删除无事实支持的项目名和结果，保留有直接证据的其他成果；“尚未证明、测试服、默认关闭、待验证”等限定词只允许保留或加强。全部不可用时复用现有 Context Fallback。

## 5. 开发顺序

1. 先移除 Compiler 的 Memory 强制改标题与强制合并，Projection 改为按 Fact 绑定的只读 Candidate。
2. 新增 `ReportSemanticVerifier`，先旁路记录审核结果、耗时和 Token，不改变正文。
3. 实现白名单 Patch 和确定性复核；失败直接降级，不再把错误反馈给模型循环重写。
4. 固化本次异常 Run、跨项目混合、测试服被写成生产完成、默认关闭被写成已支持等回归样本，每个样本重复 3 次。
5. 评测事实拔高率、Memory 污染率、错误合并率、主要成果遗漏率、降级率、成功率和额外 Token。

最终判断：先让 Project Memory 退回候选关联层，再引入独立 Verifier 作为语义安全网。循环必须显式且有硬上限；审核必须结构化；Memory 必须只读、可忽略。**质量审核永远不能阻断用户获得日报。**
