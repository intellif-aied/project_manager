# 需求看板与工作台分页方案

## 背景

当前开发期有几类接口仍然按全量数据返回：

- `GET /api/v1/requirements`
- `GET /api/v1/dashboard/risks`
- `GET /api/v1/dashboard/follows`
- `GET /api/v1/dashboard/my-items`
- `GET /api/v1/follows/followers`

生产运行时间变长后，需求、任务、风险、关注人员都会持续增长。继续全量返回会带来三个问题：

- 后端 SQL 和 Go 侧聚合耗时增长。
- 前端一次性渲染数据过多，需求看板和工作台会卡顿。
- Dashboard 摘要页被迫承载完整工作列表，产品定位会变形。

## 当前代码现状

### requirements

`api/handler/requirement.go` 的 `RequirementHandler.List` 当前直接查询符合权限的需求：

- 无 `LIMIT/OFFSET`。
- 前端 `requirementsBoardApi.listRequirements()` 直接调用 `fetchRequirements()`。
- 页面再在前端按 `scope / keyword / status / priority / risk` 做过滤。
- 阶段看板前端把全量需求按状态分列。

这意味着看板数据量越大，接口和前端都会变慢。

### dashboard risks

`api/handler/dashboard.go` 的 `DashboardHandler.Risks` 当前流程：

1. 查询全部需求逾期事实。
2. 查询全部相关任务风险事实。
3. 在 Go 内存里按需求聚合风险组。
4. 排序后全量返回。

风险数据越多，后端聚合压力越高，Dashboard 也会渲染过多风险卡片。

### dashboard follows / my-items

`DashboardHandler.Follows` 和 `DashboardHandler.MyItems` 当前会全量查出目标，再逐个调用 `requirementFollowItem` / `taskFollowItem` 拼装 item。

`DashboardPage` 目前主要消费的是 `dashboard/my-items`，不是旧的 `dashboard/follows`。

### follows/followers

`api/handler/follow.go` 的 `Followers` 当前按目标全量返回关注人员。关注人数上来后，hover/popover 这类轻量展示不应一次性拉全量。

## 主流做法

类似 Jira / Linear / GitHub 的常见处理方式不是“看板整体翻页”，而是区分视图：

- 列表视图：普通分页或 cursor 分页。
- 看板视图：每个阶段列独立分页或无限加载。
- Dashboard：只返回 Top N 摘要，附带 total / summary。
- 关注人员：默认取前 N 个，弹窗内加载更多或搜索。

看板如果做全局第 1 页、第 2 页，会导致不同阶段列的数据分布不可理解。所以阶段看板应该按列分页。

## 目标接口设计

### requirements 列表模式

用于“需求列表”视图。

```http
GET /api/v1/requirements?view=list&page=1&page_size=20&scope=mine&keyword=xxx&status=active&priority=high&risk=blocked
```

响应：

```json
{
  "items": [],
  "total": 120,
  "page": 1,
  "page_size": 20
}
```

### requirements 看板模式

用于“阶段看板”初始加载。

```http
GET /api/v1/requirements?view=board&column_page_size=20&scope=mine&keyword=xxx&priority=high&risk=blocked
```

响应：

```json
{
  "total": 120,
  "column_page_size": 20,
  "columns": [
    {
      "status": "todo",
      "total": 42,
      "items": [],
      "page": 1,
      "page_size": 20,
      "has_more": true
    }
  ]
}
```

### requirements 单列加载更多

用于看板列底部“加载更多”。

```http
GET /api/v1/requirements?view=list&status=todo&page=2&page_size=20&scope=mine&keyword=xxx
```

本轮不新增单独路由，复用 `view=list + status + page/page_size` 获取某列下一页。

### dashboard risks

```http
GET /api/v1/dashboard/risks?page=1&page_size=20
```

响应：

```json
{
  "items": [],
  "total": 87,
  "page": 1,
  "page_size": 20
}
```

Dashboard 默认只展示第一页，展开后在列表内部滚动。后续如需真正无限加载，可以继续使用同一分页契约。

### dashboard my-items / follows

```http
GET /api/v1/dashboard/my-items?page=1&page_size=20
GET /api/v1/dashboard/follows?page=1&page_size=20
```

响应：

```json
{
  "items": [],
  "total": 64,
  "page": 1,
  "page_size": 20
}
```

### follows/followers

```http
GET /api/v1/follows/followers?target_type=requirement&target_id=xxx&page=1&page_size=20
```

响应：

```json
{
  "items": [],
  "total": 128,
  "page": 1,
  "page_size": 20
}
```

## 本轮实现范围

本轮先落地项目现有风格的 `page/page_size/items/total`。

原因：

- 项目已有 `parsePagination` helper。
- 报告、session、token 等接口已经使用 `items/total/page/page_size`。
- 可以快速消除全量返回问题。

后续增强可以再把高频变化的看板列分页升级成 cursor：

```json
{
  "page_info": {
    "next_cursor": "...",
    "has_more": true
  }
}
```

当前 UI 不依赖 cursor 形态，因此后续升级不会重做交互。

## 过滤下推策略

`requirements` 需要把原本前端过滤下推到后端：

- `scope`
  - `mine`: 我创建 / 我负责 / 我关注 / 我相关任务。
  - `followed`: 需求或任务被我关注。
  - `assigned`: 需求负责人或任务负责人包含我。
  - `created`: 需求或任务由我创建。
  - `all`: 不额外过滤。
- `keyword`
  - 需求标题、描述、创建人、负责人、团队、验收标准。
  - 任务标题、任务负责人。
- `status`
  - 需求阶段。
- `priority`
  - 需求优先级。
- `risk`
  - `requirement_overdue`: 需求截止日期已过且未完成/取消。
  - `task_overdue`: 存在未完成且逾期任务。
  - `blocked`: 存在未完成依赖造成阻塞。
  - `dependency_conflict`: 存在依赖排期冲突。

风险筛选不能依赖前端全量任务，也不能先全量查出后再过滤；需要用 SQL `EXISTS` 下推。

## 前端交互策略

### 需求看板

- 初始请求 `view=board`，每列只加载第一页。
- 列头数量使用服务端 `total`。
- 每列底部展示 `已显示 N / total` 和 `加载更多`。
- 点击加载更多时调用 `view=list&status=xxx&page=n`，追加到对应列。
- 搜索、筛选、scope、优先级变化时重置所有列分页。
- 需求列表视图使用 `view=list&page/page_size`。

### Dashboard

- `my-items` 和 `risks` 改为读取分页对象。
- 默认展示第一页。
- 继续保留现有展开逻辑，不改整体结构。
- 展开状态下只展示已加载数据，本轮不追加“加载更多”按钮，避免 UI 过度改造。

### Followers

- 调用方改为读取分页对象的 `items`。
- 当前 follower hover/list 展示第一页即可。

## 风险评审

### 风险 1：任务接口仍然是全量

需求看板历史上依赖 `GET /tasks` 全量数据做卡片风险、任务完成数和展开任务列表。

本轮改造后：

- 卡片摘要优先使用 requirement 自带的 `task_summary/risk_summary`。
- 任务详情、抽屉和展开任务仍可按需求加载 `GET /tasks?requirement_id=xxx`。
- 不应该继续为了看板首页全量拉所有任务。

后续建议把 `GET /tasks` 也改成分页或强制要求 `requirement_id`，否则任务增长后仍有隐患。

### 风险 2：风险筛选 SQL 与 service 风险逻辑需保持一致

`service.DeriveTaskRisks` 是任务风险源头。本轮 SQL 需要尽量模拟：

- 未完成依赖 + 任务进行中/任务到期/依赖到期 => 阻塞。
- 任务逾期 => 任务逾期。
- 依赖到期不早于任务到期 => 排期冲突。

如果以后风险规则变复杂，建议落风险投影表，避免 SQL 和 service 重复逻辑。

### 风险 3：看板拖动后的列数据一致性

需求从一列拖到另一列后：

- 当前项状态更新成功后，应刷新看板查询。
- 本轮先用 refetch 保证正确，不做复杂 optimistic 列内重排。

### 风险 4：offset 分页在频繁变动数据中可能重复/漏项

本轮沿用项目 `page/page_size` 风格，足够消除全量返回问题。

后续如果生产数据变化频繁，应将看板列加载升级为 cursor，排序键建议：

```text
status, risk_priority DESC, deadline ASC NULLS LAST, updated_at DESC, id
```

## 自审结论

这次方案不是把全量数据前端切片，而是把分页能力落到后端接口：

- `requirements` 支持列表分页和看板列分页。
- `dashboard/risks` / `dashboard/my-items` / `dashboard/follows` 支持分页响应。
- `follows/followers` 支持分页响应。
- 前端消费分页对象，不再假设这些接口返回数组。

可接受的遗留点：

- 本轮先用 `page/page_size`，后续可升级 cursor。
- 任务接口全量问题本轮只在需求看板首页绕开，后续应单独收口。
- Dashboard 展开后暂不无限加载，先保持轻量摘要定位。

## 验收标准

- `GET /requirements?view=list&page=1&page_size=10` 返回分页对象。
- `GET /requirements?view=board&column_page_size=10` 返回列分页对象。
- 看板列可加载更多。
- `GET /dashboard/risks?page=1&page_size=10` 返回分页对象。
- `GET /dashboard/my-items?page=1&page_size=10` 返回分页对象。
- `GET /dashboard/follows?page=1&page_size=10` 返回分页对象。
- `GET /follows/followers?...&page=1&page_size=10` 返回分页对象。
- 前端需求看板和 Dashboard 正常渲染。
- TypeScript 通过。
- Go 测试通过。
