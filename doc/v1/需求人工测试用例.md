账号口径按 2026-07-03 生产环境 `/api/v1/users` 返回的 `t01` 到 `t07` 当前角色和小组整理。本文不使用 `t08`、`t09`，避免测试账号口径混乱。

## 1. 测试目标

1. 验证 PM、总监、TL、员工 4 类角色在需求和任务模块的入口、按钮、接口权限一致。
2. 验证需求从创建、编辑、拆任务、任务推进、依赖阻塞、完成、取消、恢复、删除的完整链路。
3. 验证跨团队数据可见范围和写操作越权控制。
4. 验证员工不是只读用户：员工能创建 / 编辑 / 推进自己的任务，但不能管理需求或别人任务。
5. 验证任务进度聚合到需求进度、依赖导致阻塞展示、完成状态自动同步进度。
6. 验证错误场景不会跳转 403 页面，只给出明确提示。

状态码辅助判断：

- 未登录：401。
- 详情无查看权限：404。
- 写操作无权限：403。
- 删除有关联数据的需求：409。
- 乐观锁版本冲突：409，提示刷新或内容已更新。
- 字段非法：400。

### 5.2 R1 详细内容

标题：

```text
{P}-R1 芯片仿真回归失败自动归因
```

描述：

```text
当前 nightly regression 中，DMA 子系统和 NoC 相关 case 偶发失败。平台需要把失败 case、commit range、仿真日志、波形路径、负责人和历史相似失败串起来，减少人工排查时间。
```

验收标准：

```text
1. 能按 regression 批次聚合失败 case、失败阶段、最近一次通过时间和失败日志入口。
2. 能识别同一 case 近 7 天内的重复失败，并展示疑似相关 commit range。
3. 对每个失败 case 能绑定负责人任务，并在任务完成后更新需求聚合进度。
```

优先级：高

截止日期：2026-07-24

参与团队：测试小组A

### 5.3 R2 详细内容

标题：

```text
{P}-R2 Agent 运行沙箱 MCP 凭据隔离
```

描述：

```text
报告 Agent 和调试 Agent 都会调用 MCP。当前需要验证运行时只注入当前用户允许使用的凭据，且默认报告 MCP 不暴露 token 配置，避免用户误填或越权读取。
```

验收标准：

```text
1. 默认报告 Agent 运行时能自动注入 Aida 凭据，不要求用户手动输入 token。
2. 自定义 MCP 凭据只能选择当前用户已保存且有权使用的凭据。
3. 运行记录中不得显示明文 token、credential slot 或内部 MCP 配置。
```

优先级：中

截止日期：2026-07-19

参与团队：测试小组A

```text
{P}-R3 端侧 NPU 性能数据统一看板
```

## 8. 接口辅助核对

人工主要走 UI，但以下接口可用于确认状态码和数据范围。把 `<TOKEN>` 换成对应账号 token，把 `{BASE_URL}` 换成实际环境地址。

```bash
curl '{BASE_URL}/api/v1/requirements' \
  -H 'Authorization: Bearer <TOKEN>'

curl '{BASE_URL}/api/v1/requirements/<REQ_ID>' \
  -H 'Authorization: Bearer <TOKEN>'

curl '{BASE_URL}/api/v1/tasks?requirement_id=<REQ_ID>' \
  -H 'Authorization: Bearer <TOKEN>'

curl '{BASE_URL}/api/v1/tasks/<TASK_ID>' \
  -H 'Authorization: Bearer <TOKEN>'
```

写接口辅助示例：

```bash
curl '{BASE_URL}/api/v1/tasks/<TASK_ID>/progress' \
  -X PUT \
  -H 'Authorization: Bearer <TOKEN>' \
  -H 'Content-Type: application/json' \
  --data-raw '{"progress":60,"base_version":<VERSION>}'
```

## 9. 重点验收判断

一轮完整人工测试通过时，应满足：

1. PM `t02` / 总监 `t01` 能完整管理所有测试需求和任务。
2. TL-A `t03` 不能看到仅测试小组B 的 R4 / T8，除非自己创建的 R6。
3. TL-B `t06` 不能看到仅测试小组A 的 R1 / R2。
4. A 组员工 `t04/t05` 不能看到或操作仅测试小组B 的 R4 / T8。
5. B 组员工 `t07` 不能看到或操作仅测试小组A 的 R1 / R2 / T1。
6. 员工不能创建需求，不能编辑需求，不能改派任务。
7. 员工能创建和推进自己的任务。
8. 员工能查看同组任务，但不能修改同组其他人的任务。
9. 跨团队详情不可见返回 404，写操作越权返回 403。
10. 删除有关联任务的需求返回 409；取消 / 恢复可正常使用。
11. 依赖阻塞是派生展示，不写入 `task.status=blocked`。
12. 版本冲突返回 409，前端只提示错误，不跳转 403 页面。
13. R3 跨团队需求下 TL 对其他小组任务的写权限需要记录实际结果；如允许编辑，需要产品确认是否符合预期。

## 11. 清理建议

测试结束后，按以下顺序清理：

1. 删除可删除的空需求，例如 R5。
2. 对无法硬删除的测试需求，统一改标题前缀为 `[已测] {P}-...`，或状态改为 cancelled。
3. 如果需要数据库级清理，必须先导出本轮 `{P}` 对应的需求 ID / 任务 ID，再由管理员确认执行。
4. 不要删除非 `{P}` 前缀的数据。
