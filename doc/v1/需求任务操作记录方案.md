# 需求 / 任务操作记录方案

生成日期：2026-07-06

## 1. 背景

当前需求看板和任务详情已经覆盖了需求创建、负责人分配、团队协作、任务拆解、状态流转、进度修改、依赖、关联 session 等核心流程。

但现在缺少一类主流项目管理系统都会提供的能力：**操作记录 / 动态历史**。

典型问题：

- PM 不知道需求是谁什么时候改了负责人。
- TL 不知道任务状态是谁从“进行中”改成“已完成”。
- 员工不知道自己被什么时候指派了任务。
- 总监只能看到当前状态，无法回溯需求推进过程。
- 出现误操作时，只能查数据库或靠口头确认。

因此需要为需求和任务补充一套统一的操作记录能力。

## 2. 目标

第一期目标是解决“可回溯、可解释、可追责”的基础问题。

需要支持：

- 需求详情中查看需求本身及其任务的关键操作记录。
- 任务详情中查看该任务的关键操作记录。
- 记录谁、什么时候、对哪个对象、做了什么操作。
- 对关键字段记录变更前后值。
- 前端以时间线方式展示，用户能快速理解推进过程。

不追求第一期就做完整审计平台。

## 3. 非目标

第一期不做以下内容：

- 不做复杂筛选器，例如按操作人、字段、时间范围筛选。
- 不做操作记录导出。
- 不做站内通知。
- 不做操作记录评论区。
- 不做全文搜索。
- 不做管理员审计后台。
- 不做所有数据库字段的逐字段审计。
- 不做关注/取消关注记录，避免动态流噪音过大。
- 不做版本回滚。

这些能力可以后续按实际使用情况再扩展。

## 4. 当前系统现状

当前代码里没有完整操作记录能力。

已有信息包括：

- `requirements.created_at`
- `requirements.updated_at`
- `requirements.version`
- `tasks.created_at`
- `tasks.updated_at`
- `tasks.version`
- `work_item_relations.created_by`
- session / token 关联关系

这些字段只能表示当前状态或更新时间，无法回答：

- 谁改了？
- 改了什么？
- 从什么值改成什么值？
- 是需求操作还是任务操作？
- 是状态流转、负责人修改、依赖变更，还是 session 关联？

因此需要新增专门的操作记录模型。

## 5. 总体设计

新增统一的工作项事件表：

```text
work_item_events
```

需求和任务共用一张表。

原因：

- 需求和任务是同一类业务对象，都是“工作项”。
- 需求详情需要聚合展示需求本身和需求下任务的动态。
- 任务详情只展示任务自己的动态。
- 共用模型后，后续可以自然支持需求依赖、任务依赖、session 关联等统一展示。

## 6. 数据模型

建议新增 migration：

```sql
CREATE TABLE IF NOT EXISTS work_item_events (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    target_type     TEXT NOT NULL,
    target_id       UUID NOT NULL,
    requirement_id  UUID,
    task_id         UUID,
    actor_id        BIGINT REFERENCES users(id),
    actor_name      TEXT NOT NULL DEFAULT '',
    actor_role      TEXT NOT NULL DEFAULT '',
    event_type      TEXT NOT NULL,
    event_title     TEXT NOT NULL,
    before_data     JSONB NOT NULL DEFAULT '{}'::jsonb,
    after_data      JSONB NOT NULL DEFAULT '{}'::jsonb,
    metadata        JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_work_item_events_requirement
    ON work_item_events(requirement_id, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_work_item_events_task
    ON work_item_events(task_id, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_work_item_events_target
    ON work_item_events(target_type, target_id, created_at DESC);
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `target_type` | 操作对象类型，`requirement` 或 `task` |
| `target_id` | 当前操作对象 ID |
| `requirement_id` | 所属需求 ID。任务事件也必须带上，方便需求详情聚合 |
| `task_id` | 任务 ID。需求事件为空 |
| `actor_id` | 操作人 ID |
| `actor_name` | 操作人展示名，冗余存储，避免用户改名后历史不可读 |
| `actor_role` | 操作人角色 |
| `event_type` | 结构化事件类型 |
| `event_title` | 展示用短文案 |
| `before_data` | 变更前结构化数据 |
| `after_data` | 变更后结构化数据 |
| `metadata` | 补充信息，例如依赖任务标题、session key |
| `created_at` | 事件时间 |

### 6.1 为什么同时存结构化数据和展示文案

只存中文文案会导致后续无法筛选、统计和重构展示。

只存结构化数据会导致前端每次都要理解复杂业务差异。

因此第一期建议两者都存：

- `event_type / before_data / after_data / metadata` 用于长期扩展。
- `event_title` 用于第一期快速展示。

## 7. 事件类型

第一期只记录推进流程中的关键动作。

### 7.1 需求事件

| event_type | 触发场景 | 是否记录 before/after |
| --- | --- | --- |
| `requirement_created` | 新建需求 | after |
| `requirement_updated` | 修改标题、描述、优先级等基础信息 | before / after |
| `requirement_status_changed` | 修改需求阶段 | before / after |
| `requirement_owner_changed` | 修改负责人 | before / after |
| `requirement_team_changed` | 修改参与团队 | before / after |
| `requirement_deadline_changed` | 修改截止日期 | before / after |
| `requirement_ac_updated` | 修改验收标准 | before / after |
| `requirement_cancelled` | 取消需求 | before / after |
| `requirement_restored` | 恢复需求 | before / after |
| `requirement_deleted` | 删除需求 | before |
| `requirement_session_linked` | 关联 session | after / metadata |
| `requirement_session_unlinked` | 取消关联 session | before / metadata |

### 7.2 任务事件

| event_type | 触发场景 | 是否记录 before/after |
| --- | --- | --- |
| `task_created` | 新建任务 | after |
| `task_updated` | 修改标题、优先级、验收标准等基础信息 | before / after |
| `task_status_changed` | 修改任务状态 | before / after |
| `task_progress_changed` | 修改任务进度 | before / after |
| `task_assignee_changed` | 修改任务负责人 | before / after |
| `task_deadline_changed` | 修改截止日期 | before / after |
| `task_dependency_added` | 新增上游依赖 | after / metadata |
| `task_dependency_removed` | 删除上游依赖 | before / metadata |
| `task_deleted` | 删除任务 | before |
| `task_session_linked` | 关联 session | after / metadata |
| `task_session_unlinked` | 取消关联 session | before / metadata |

### 7.3 暂不记录的事件

第一期暂不记录：

- 关注 / 取消关注。
- 页面查看。
- 筛选、搜索、展开、折叠。
- AI 生成提示词变化。
- 单纯刷新。

原因：这些事件噪音较大，会降低动态记录的可读性。

## 8. 后端设计

### 8.1 新增事件记录服务

建议新增：

```text
api/service/work_item_event.go
```

职责：

- 统一封装事件写入。
- 生成规范化 `event_title`。
- 过滤无变化字段。
- 保证需求事件和任务事件写法一致。

建议接口：

```go
type WorkItemEventRecorder struct {
    db *sql.DB
}

func (r *WorkItemEventRecorder) RecordRequirementEvent(ctx context.Context, event RequirementEvent) error
func (r *WorkItemEventRecorder) RecordTaskEvent(ctx context.Context, event TaskEvent) error
```

第一期不需要做复杂异步队列。事件写入可以和业务写入在同一个请求内完成。

如果事件写入失败：

- 核心业务是否回滚需要谨慎。
- 建议对“创建、编辑、状态流转、删除”等核心操作放在同一事务内，保证操作和事件一致。
- 对 session 关联这类弱关联，可以允许业务成功但记录失败时返回错误，避免用户误以为记录完整。

### 8.2 事件写入位置

需要在以下操作成功后写入事件：

需求：

- `RequirementHandler.Create`
- `RequirementHandler.Update`
- `RequirementHandler.Restore`
- `RequirementHandler.Delete`
- `RequirementHandler.AddDependency`
- `RequirementHandler.RemoveDependency`
- `RequirementHandler.RegenerateAC` 或 AC 保存逻辑

任务：

- `TaskHandler.Create`
- `TaskHandler.Update`
- `TaskHandler.UpdateStatus`
- `TaskHandler.UpdateProgress`
- `TaskHandler.Delete`
- `TaskHandler.AddDependency`
- `TaskHandler.RemoveDependency`

Session 关联：

- `SessionHandler.UpdateTask`
- `SessionHandler.UpdateRequirement`

### 8.3 before / after 获取方式

更新类操作需要记录变更前后。

建议做法：

1. 更新前查询当前对象关键字段。
2. 执行业务更新。
3. 更新后查询最新对象。
4. 对关键字段做 diff。
5. 只对发生变化的字段生成事件。

第一期不需要逐字段生成太多条事件，可以按业务动作合并。

例如一次需求编辑同时改了负责人、团队、截止日期：

- 可以生成 3 条更清晰的事件：
  - `requirement_owner_changed`
  - `requirement_team_changed`
  - `requirement_deadline_changed`
- 标题/描述/优先级等普通字段可以合并为：
  - `requirement_updated`

这样比一条“更新了需求”更有业务价值。

## 9. API 设计

### 9.1 需求操作记录

```http
GET /api/v1/requirements/{id}/events?page=1&page_size=20
```

语义：

- 返回需求自身事件。
- 返回该需求下任务事件。
- 按 `created_at DESC` 排序。

权限：

- 用户必须对该需求有查看权限。
- 权限规则复用现有 `canViewRequirement`。

### 9.2 任务操作记录

```http
GET /api/v1/tasks/{id}/events?page=1&page_size=20
```

语义：

- 只返回该任务自身事件。

权限：

- 用户必须对该任务有查看权限。
- 权限规则复用现有任务查看权限。

### 9.3 返回结构


## 10. 前端设计

### 10.1 需求详情抽屉

在需求详情抽屉中新增 Tab：

```text
动态
```

建议 Tab 顺序：

```text
任务 / 验收 / 关联 Session / 动态 / 信息
```

理由：

- “任务”仍是主入口。
- “动态”比“信息”更常用，应放在“信息”前面。
- “信息”保留为静态元数据。

动态 Tab 展示：

- 使用 Timeline / Activity List。
- 默认加载最近 20 条。
- 底部“加载更多”。
- 每条展示：
  - 操作人
  - 操作文案
  - 时间
  - 关联对象：需求 / 任务名
  - 关键 before / after

示例：

```text
测试03 将任务「NPU SDK freeze」状态从「未开始」改为「进行中」
2026-07-06 10:12
```

```text
测试01 将需求负责人调整为 测试03、测试05
2026-07-06 09:40
```

### 10.2 任务详情 Modal

任务详情 Modal 底部新增轻量区块：

```text
操作记录
```

展示规则：

- 默认展示最近 5 条。
- 如果超过 5 条，显示“查看更多”或分页。
- 不要让操作记录挤占任务基础信息和风险信息。

任务详情中每条记录只展示该任务相关事件。

### 10.3 文案风格

文案应偏业务化，不要像数据库日志。

推荐：

- `创建了需求`
- `将需求阶段从「待开始」改为「评审」`
- `将负责人调整为 测试03、测试05`
- `将任务进度从 30% 调整为 60%`
- `新增上游依赖「Agent 审计联调」`
- `关联了 2 条 session`

不推荐：

- `UPDATE requirements SET owner_ids`
- `field status changed`
- `task_progress_changed`

## 11. 测试方案

### 11.1 API 测试

覆盖：

- 创建需求后有 `requirement_created`。
- 编辑需求标题/优先级后有 `requirement_updated`。
- 修改负责人后有 `requirement_owner_changed`。
- 修改团队后有 `requirement_team_changed`。
- 修改截止日期后有 `requirement_deadline_changed`。
- 切换状态后有 `requirement_status_changed`。
- 创建任务后有 `task_created`。
- 修改任务状态后有 `task_status_changed`。
- 修改任务进度后有 `task_progress_changed`。
- 修改任务负责人后有 `task_assignee_changed`。
- 新增/删除任务依赖后有 dependency 事件。
- 关联/取消关联 session 后有 session 事件。
- 无权限用户访问 events 返回 404 或 403，和现有详情权限保持一致。

### 11.2 UI 测试

覆盖：

- 需求详情抽屉出现“动态”Tab。
- 动态 Tab 默认展示最近 20 条。
- 任务事件能在需求动态里出现。
- 任务详情 Modal 展示最近操作记录。
- 长任务名、长需求名不撑爆时间线。
- 操作记录加载中、空态、失败态显示合理。

## 12. 风险和边界

### 12.1 事件过多导致噪音

风险：

- 如果把关注、查看、刷新都记录，会导致动态流不可读。

控制：

- 第一期只记录推进相关关键操作。
- 关注类事件暂不记录。

### 12.2 写入点遗漏

风险：

- 某些修改路径没有写事件，导致历史不完整。

控制：

- 后端统一封装 recorder。
- 每个 handler 成功路径明确调用。
- 给关键路径补单测。

### 12.3 before / after 不准确

风险：

- 更新前后数据查询不一致，导致记录错误。

控制：

- 核心更新操作尽量在事务内完成。
- 更新前后都使用同一套对象加载函数或字段映射。

### 12.4 旧数据没有历史

当前仍处于开发期，可以接受旧数据没有历史记录。

上线后从功能启用时间开始记录即可。

### 12.5 操作记录删除问题

建议不提供单条操作记录删除。

原因：

- 操作记录承担追溯责任。
- 删除记录会降低可信度。

如果需求/任务被删除，事件可以保留，但详情入口是否可见按产品后续决定。

## 13. 分期建议

### 第一期

必须做：

- 新增 `work_item_events` 表。
- 需求事件记录。
- 任务事件记录。
- session 关联事件记录。
- `GET /requirements/{id}/events`
- `GET /tasks/{id}/events`
- 需求详情“动态”Tab。
- 任务详情最近操作记录。

不做：

- 关注记录。
- 筛选。
- 导出。
- 通知。
- 回滚。

### 第二期

根据使用情况再考虑：

- 按操作类型筛选。
- 只看任务动态 / 只看需求动态。
- 操作记录全文搜索。
- 重要变更通知。
- 记录 AI 生成日报/周报和需求任务之间的关系。

## 14. Review 结论

这个方案是必要的，不属于过度设计。

原因：

- 当前需求/任务流程已经有多人协作、跨团队、负责人、依赖和状态流转。
- 没有操作记录时，PM/TL/总监很难回溯责任和推进过程。
- 只靠 `updated_at` 无法解释具体变更。

方案没有过度设计的点：

- 只新增一张统一事件表，没有拆多张审计表。
- 不做通知、导出、筛选、回滚。
- 不记录低价值行为，例如查看、刷新、关注。
- 前端只做时间线展示，不做复杂审计后台。
- 第一阶段只覆盖关键推进动作。

需要注意的点：

- 必须后端记录，不能前端拼。
- 必须存结构化 before/after，不能只存中文文案。
- 必须把任务事件聚合到需求动态里，否则需求动态价值不足。
- 必须控制噪音，第一期不要记录关注/取消关注。

建议按本方案进入开发。
