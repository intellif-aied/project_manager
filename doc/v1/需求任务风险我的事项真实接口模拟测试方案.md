目标：用真实 HTTP API 和真实测试账号，覆盖需求、任务、风险、我的事项、关注、事件记录、权限、分页、异常输入、乐观锁的高覆盖回归。

## 1. 测试目标

这份方案不是人工逐条点击的用例清单，而是给 Codex / 自动化脚本执行的“生成型测试矩阵”。

核心目标：

- 覆盖 4 类角色：PM、总监、TL、员工。
- 覆盖需求 CRUD：创建、查询、分页、搜索、更新、状态流转、取消、恢复、删除。
- 覆盖任务 CRUD：创建、查询、分页、更新字段、更新状态、更新进度、删除。
- 覆盖依赖关系：任务依赖任务、任务依赖需求、需求依赖任务、需求依赖需求。
- 覆盖风险推导：需求逾期、任务逾期、依赖阻塞、依赖冲突、风险清除。
- 覆盖工作台：`dashboard/my-items`、`dashboard/risks`、`dashboard/follows`。
- 覆盖事件记录：需求事件、任务事件、依赖事件、删除事件、字段变更 before/after。
- 覆盖权限边界：可见、可创建、可更新、可删除、可改负责人、不可越权。
- 覆盖分页和筛选：需求看板列分页、需求列表分页、任务分页、Dashboard 分页。
- 覆盖错误输入：非法 UUID、非法负责人、非法状态、缺少 base_version、过期 base_version。

推荐测试规模需要分层理解，不能把“链路模板数”误认为“完整组合数”。

| 层级 | 用途 | 覆盖方式 | 预计真实接口用例数 |
| --- | --- | --- | ---: |
| L0 Smoke | 每次小改快速验证 | 关键 happy path + 1 条权限拒绝 + 1 条风险链路 | 250 - 400 |
| L1 P0 上线前回归 | 上线前必须跑 | 角色 / 小组 / 负责人 / 关注 / 风险 / 事件的核心组合展开 | 3,500 - 5,000 |
| L2 P1 高覆盖回归 | 大版本或权限改动后跑 | pairwise + 关键 3-wise 组合，覆盖多数交叉缺陷 | 8,000 - 12,000 |
| L3 穷举分析池 | 不建议日常全跑 | 全笛卡尔组合，仅用于生成缺口清单和抽样 | 30,000+ |

| PM | 非法 team_id | 400 |

### 7.2 查询需求

维度：

- `GET /requirements/{id}`
- `GET /requirements?view=list`
- `GET /requirements?view=board`
- `scope=mine/followed/assigned/created/all`
- `status=todo/review/active/completed/cancelled`
- `risk=requirement_overdue/task_overdue/blocked/dependency_conflict`
- `keyword` 命中标题、描述、负责人、团队、任务标题。

重点断言：

- PM / 总监能看到全局。
- TL 只能看到创建 / 负责 / 本团队。
- 员工只能看到创建 / 负责 / 本团队。
- `view=board` 返回 4 列：todo、review、active、completed。
- `column_page_size` 生效，列级 `hasMore` 正确。
- `view=list` 返回 `items/total/page/page_size`。

### 7.3 更新需求

字段组合：

- 单字段：title、description、priority、deadline、status、responsible_user_ids、team_ids、acceptance_criteria。
- 多字段：负责人 + 团队、状态 + 截止日期、标题 + 描述 + 验收标准。
- 空值：清空负责人、清空团队、清空截止日期。
- 乐观锁：正确 base_version、过期 base_version、缺失 base_version。

状态流转：

```text
todo -> review -> active -> completed
active -> cancelled
cancelled -> restore -> todo
completed -> active
```

断言：

- 状态更新后 `version + 1`。
- `completed` 设置 `completed_at`。
- 非 completed 清空 `completed_at`。
- 过期 base_version 返回冲突，不覆盖数据。
- 无字段更新返回合理错误。

### 7.4 删除 / 取消 / 恢复需求

场景：

- 无任务、无依赖、无 session 的需求删除。
- 有任务的需求删除，应按当前实现进入取消 / 软删除语义。
- cancelled 需求恢复。
- 非 cancelled 恢复返回 conflict。
- 越权角色删除返回 403 或 404。
- 删除后列表默认不出现 cancelled。
- 指定 `status=cancelled` 可查询。

## 8. 任务 CRUD 测试矩阵

### 8.1 创建任务

维度：

- 角色：PM、总监、TL、员工。
- 需求状态：todo、review、active、completed、cancelled。
- 负责人：空、自己、同组员工、跨组员工、多人、非法用户。
- 截止日期：空、过去、今天、未来、非法日期。
- 依赖：无、同需求任务、跨需求任务、需求依赖、非法 id、循环依赖。

核心用例：

| 角色 | 场景 | 预期 |
| --- | --- | --- |
| PM | 给任意有效用户创建任务 | 201 |
| 总监 | 给任意有效用户创建任务 | 201 |
| TL A | 在小组 A 可管理需求下，给 A 组人员创建任务 | 201 |
| TL A | 给 B 组员工创建任务 | 403 |
| 员工 | 创建分给自己的任务 | 201 |
| 员工 | 创建分给别人或多人 | 403 |
| 任意 | cancelled 需求下创建任务 | 409 |

### 8.2 更新任务

字段组合：

- title、priority、due_date、acceptance_criteria、responsible_user_ids、status、progress。
- 单字段和多字段组合。
- 负责人清空、多人负责人、跨组负责人。
- `status=todo/in_progress/done`。
- 非法 `status=blocked`。
- `progress=-1/0/45/100/101`。

断言：

- `done` 自动 progress=100 且 completed_at 有值。
- done 改回 todo/in_progress 后 completed_at 清空。
- employee 不能修改 `responsible_user_ids`。
- employee 作为负责人可改 title、status、progress、due_date、acceptance_criteria。
- progress 更新不改变 status，除非走 status 接口。

### 8.3 删除任务

场景：

- 创建者删除。
- 负责人删除。
- PM / 总监删除。
- TL 删除本团队任务。
- 同组非负责人删除。
- 跨组员工删除。
- 删除有 session / token / documents / activity slices 关联的任务。
- 删除有依赖关系的任务。

断言：

- 删除后任务详情返回 404。
- 需求动态出现 `task_deleted`。
- `event_title` 包含任务名。
- task events 对已删除任务不导致前端硬错误。
- 相关 session / token / document 的 task_id 被清理或保留到 requirement_id，按当前实现校验。

## 9. 依赖与风险测试矩阵

### 9.1 风险类型来源

| 风险 | 触发条件 | 清除条件 |
| --- | --- | --- |
| requirement_overdue | 需求未 completed/cancelled，deadline < today | 完成 / 取消 / 改未来日期 |
| overdue | 任务未 done，due_date < today | 任务 done / 改未来日期 |
| blocked | 任务依赖未完成，且任务 in_progress，或任务 due_date <= today，或依赖已逾期 | 上游完成 / 删除依赖 / 调整时间 |
| dependency_conflict | 未完成依赖 due_date >= 当前任务 due_date，且任务不逾期 | 上游完成 / 调整任务或依赖日期 / 删除依赖 |

注意：

- 如果任务已经逾期，当前 `DeriveTaskRisks` 会优先返回 overdue，不一定同时展示 dependency_conflict。
- 要单独制造未来截止但早于上游交付的任务，才能稳定验证 dependency_conflict。

### 9.2 依赖组合

| source | target | 预期 |
| --- | --- | --- |
| task | task | 支持 |
| task | requirement | 支持 |
| requirement | task | 支持 |
| requirement | requirement | 支持 |
| task | self | 400 |
| requirement | self | 400 |
| A depends B，B depends A | 400 或冲突错误 |
| target 不可见 | 403 / 404 |
| target 不存在 | 404 |
| 重复添加同一依赖 | 幂等或不重复生成关系 |
| 删除不存在依赖 | 200 幂等或 404，按当前实现固定 |

### 9.3 风险接口断言

`GET /dashboard/risks?page=1&page_size=N`

断言：

- `requirementId` 指向风险需求。
- `riskTypes` 包含结构化风险。
- `requirementOverdue` 与需求状态一致。
- `deadlineTaskCount` 与逾期任务数一致。
- `dependencyBlockerCount` 与阻塞任务数一致。
- `dependencyConflictCount` 与冲突任务数一致。
- `representativeTask` 选择最高优先级风险任务。
- `representativeTask.blockingDependencies` 返回阻塞来源。
- 阻塞来源包含负责人 `responsible_names`。
- 风险清除后该风险组消失或降级。

### 10.3 排序断言

1. 风险高的在前。
2. assignedToMe 在前。
3. 已逾期 / 截止更早在前。
4. 高关注在前。
5. 更新时间近的在前。
6. 原始顺序作为最终 tie-breaker。

如果后端排序已有固定逻辑，测试要记录“实际排序依据”，避免前端和后端口径分裂。

## 16. 执行器约定

建议生成 JSONL case 文件，每行一个真实接口用例：

```json
{
  "case_id": "API-TASK-EMP-UPDATE-OWN_PROGRESS-001",
  "setup": ["R-PM-CROSS", "T-SELF"],
  "actor": "t05",
  "request": {
    "method": "PUT",
    "path": "/tasks/{task_id}/progress",
    "body": {
      "progress": 45,
      "base_version": "$task.version"
    }
  },
  "expect": {
    "status": 200,
    "json": {
      "progress": 45,
      "can_update_progress": true
    },
    "events": [
      {
        "target": "task",
        "type": "task_progress_changed",
        "after.progress": 45
      }
    ]
  }
}
```

执行器职责：

- 自动登录 / 使用 token。
- 按前置数据工厂造数。
- 保存创建出的 requirement_id / task_id。
- 每次更新前自动获取最新 `base_version`。
- 对每个请求记录 request / response / status。
- 对每个写操作执行 post-assert。
- 对每个事件用例调用 events 接口断言。
- 每个 batch 结束输出 Markdown 和 JSON 报告。
- 失败时保留测试数据，不自动清理，便于人工复现。
- 全部通过时可按前缀清理测试数据。

## 21. 多角色协作链路测试矩阵

单角色 CRUD 只能证明接口能调用，不能证明真实项目推进过程是顺的。上线前必须增加多角色串联场景：一个需求从创建、关注、分配、拆任务、加依赖、触发风险、风险处理、完成关闭，至少经过 3-4 个角色。

协作链路必须按组合维度展开，不允许只跑固定账号：

| 维度 | 必测取值 |
| --- | --- |
| 需求创建者 | PM、总监、TL A、TL B |
| 需求负责人集合 | 空、PM、总监、TL A、TL B、员工 A、员工 B、TL A + 员工 A、TL A + 员工 B、员工 A + 员工 B、PM + TL + 员工 |
| 参与团队 | 空、仅 A、仅 B、A+B |
| 关注者集合 | 无、PM、总监、TL、员工、PM+TL、PM+总监、总监+TL+员工、多员工 |
| 任务创建者 | PM、总监、TL A、TL B、员工 A 负责人、员工 A 非负责人、员工 B 负责人、员工 B 非负责人 |
| 任务负责人集合 | 空、创建者自己、同组单人、同组多人、跨组单人、跨组多人、PM、TL、PM+员工、TL+员工 |
| 操作执行者 | 创建者、负责人、同组 TL、同组非负责人、跨组 TL、跨组员工、PM、总监、关注者、无关用户 |
| 依赖来源 | 同需求任务、跨需求同组任务、跨需求跨组任务、同需求已完成任务、同需求未完成任务、需求本身、已取消需求、不存在对象 |
| 状态阶段 | todo、review、active、completed、cancelled |
| 风险状态 | 无风险、需求逾期、任务逾期、依赖阻塞、依赖冲突、多风险叠加、风险清除后 |
| Dashboard 入口 | my-items、risks、follows、requirements board、requirements list |
| scope / view | mine、followed、assigned、created、all；board、list |
| 分页 | page_size=1、5、20、100；第一页、中间页、末页、空页 |

完整笛卡尔积会非常大，不能日常全跑。执行器应采用：

- 权限相关：角色 × 组 × 创建者/负责人/非负责人必须全量展开。
- 风险相关：依赖来源 × 截止日期 × 上游状态 × 当前任务状态必须全量展开。
- 展示相关：scope × 角色 × 风险等级采用 pairwise。
- 事件相关：每个 event_type 至少覆盖一次单字段、一次多字段、一次跨角色操作。
- 分页相关：每个接口至少覆盖 4 个 page_size 和空页。

### 21.1 协作链路 A：总监发起，PM 关注，TL 拆分，员工执行

目标：模拟“总监开会定方向，PM 跟进，TL 拆任务，员工执行”的真实流程。

步骤：

| 步骤 | 角色 | 操作 | 接口 | 预期 |
| --- | --- | --- | --- | --- |
| A01 | 总监 t02 | 创建跨小组需求，负责人先设 PM + TL | `POST /requirements` | 201，creator=总监，responsible 包含 PM/TL |
| A02 | PM t01 | 关注该需求 | `POST /follows` | 200，follow_summary 增加 |
| A03 | PM t01 | 将需求状态从 todo 改为 review | `PUT /requirements/{id}` | 200，事件 `requirement_status_changed` |
| A04 | TL t03 | 将需求状态改为 active | `PUT /requirements/{id}` | 200，TL 有管理权限 |
| A05 | TL t03 | 创建上游任务 T-source，负责人 t06 | `POST /tasks` | 201 |
| A06 | TL t03 | 创建主执行任务 T-main，负责人 t05，依赖 T-source | `POST /tasks` | 201，dependencies 返回 T-source |
| A07 | 员工 t05 | 更新 T-main 进度到 40 | `PUT /tasks/{id}/progress` | 200，事件 `task_progress_changed` |
| A08 | 员工 t05 | 将 T-main 状态改为 in_progress | `PUT /tasks/{id}/status` | 200，事件 `task_status_changed` |
| A09 | PM t01 | 查看工作台我的事项 | `GET /dashboard/my-items` | 包含该需求 / 任务，来源包括关注和负责 |
| A10 | PM t01 | 查看风险提示 | `GET /dashboard/risks` | 若 T-source 未完成且 T-main 到期，出现依赖阻塞 |
| A11 | TL t03 | 完成 T-source | `PUT /tasks/{id}/status` | 200 |
| A12 | PM t01 | 再查风险提示 | `GET /dashboard/risks` | 依赖阻塞清除，逾期风险按日期保留或清除 |
| A13 | 员工 t05 | 完成 T-main | `PUT /tasks/{id}/status` | 200，progress=100 |
| A14 | PM t01 | 完成需求 | `PUT /requirements/{id}` | 200，status=completed |
| A15 | 全角色 | 查询 events | `GET /requirements/{id}/events`、`GET /tasks/{id}/events` | 事件链完整，actor 分别正确 |

重点断言：

- `creator_name` 是总监，不应展示成负责人。
- PM 关注后，PM 的 `dashboard/my-items` 应包含该需求。
- TL 拆分任务后，任务 creator 是 TL，task responsible 是员工。
- 依赖阻塞来源必须能追溯到 T-source，并返回 `responsible_names`。
- 所有事件 actor_name / actor_role 必须对应实际操作人。

### 21.2 协作链路 B：PM 发起，TL 跨组协作，员工越权边界

目标：验证 PM 创建跨组需求后，A 组 TL 和 B 组员工参与时的权限边界。

步骤：

| 步骤 | 角色 | 操作 | 预期 |
| --- | --- | --- | --- |
| B01 | PM t01 | 创建 A+B 跨组需求，负责人 t03、t09 | 成功 |
| B02 | TL A t03 | 创建 A 组任务，负责人 t05/t06 | 成功 |
| B03 | TL A t03 | 尝试创建负责人为 B 组 t09 的任务 | 403 |
| B04 | PM t01 | 创建 B 组任务，负责人 t09 | 成功 |
| B05 | 员工 t05 | 尝试编辑 B 组任务 | 403 或 404 |
| B06 | 员工 t09 | 编辑自己负责的 B 组任务 | 成功 |
| B07 | TL B t04 | 编辑 B 组任务 | 成功 |
| B08 | TL A t03 | 尝试编辑 B 组任务 | 403 或 404 |
| B09 | PM t01 | 汇总查看需求详情 | 任务列表完整，权限字段正确 |

重点断言：

- TL 只能给本团队负责人创建 / 分配任务。
- PM 可跨团队创建任务。
- 跨团队员工不能编辑不属于自己的任务。
- 被分配员工能编辑自己的任务，但不能改负责人。

### 21.3 协作链路 C：无负责人需求先流转，后补负责人

目标：验证真实开会场景：需求创建时未指定负责人，后续状态推进时补负责人。

步骤：

| 步骤 | 角色 | 操作 | 预期 |
| --- | --- | --- | --- |
| C01 | 总监 t02 | 创建无负责人需求 | 成功 |
| C02 | PM t01 | 关注该需求 | 成功 |
| C03 | PM t01 | 状态流转到 review | 成功，事件记录状态变化 |
| C04 | PM t01 | 补负责人 t03、t05 | 成功，事件 `requirement_responsibles_changed` |
| C05 | TL t03 | 创建任务 | 成功 |
| C06 | 员工 t05 | 更新任务进度 | 成功 |
| C07 | PM t01 | 查看 my-items | PM 因关注可见；t03/t05 因负责可见 |

重点断言：

- 无负责人不是风险项，但字段为空时 UI / API 不应报错。
- 补负责人事件 before 为空数组，after 为多人 id。
- 补负责人后权限立即生效。

### 21.4 协作链路 D：依赖导致风险，责任人追溯

目标：专门验证“为什么阻塞、被谁阻塞、谁负责处理”。

步骤：

| 步骤 | 角色 | 操作 | 预期 |
| --- | --- | --- | --- |
| D01 | PM t01 | 创建需求 R-risk | 成功 |
| D02 | TL t03 | 创建上游任务 T-up，负责人 t06，截止未来 | 成功 |
| D03 | 员工 t05 | 创建下游任务 T-down，负责人自己，依赖 T-up，截止今天或过去 | 成功 |
| D04 | PM t01 | 查询 T-down 详情 | `risk_types` 包含 blocked/overdue，dependencies 包含 T-up 和负责人 t06 |
| D05 | PM t01 | 查询 dashboard/risks | representativeTask=T-down，blockingDependencies 包含 T-up |
| D06 | PM t01 | 查询 dashboard/my-items | T-down 行展示阻塞来源，负责人列不混乱 |
| D07 | TL t03 | 完成 T-up | 成功 |
| D08 | PM t01 | 再查 risks | dependency_blocker 清除 |

重点断言：

- 风险不是只显示“依赖阻塞”，必须能追到具体任务和负责人。
- `blockingDependencies[].responsible_names` 必须存在。
- 完成上游后，阻塞风险清除。

### 21.5 协作链路 E：多角色关注权重

目标：验证关注度不是简单 count，而是角色权重。

步骤：

| 步骤 | 角色 | 操作 | 预期 |
| --- | --- | --- | --- |
| E01 | PM t01 | 创建需求 | 成功 |
| E02 | 员工 t05 | 关注需求 | 关注度一般 |
| E03 | TL t03 | 关注需求 | 关注度提升 |
| E04 | PM t01 | 关注需求 | 关注度提升 |
| E05 | 总监 t02 | 关注需求 | 关注度达到高关注 |
| E06 | 任意 | 查询 `/follows/followers` | 关注人列表含角色 |
| E07 | 任意 | 查询需求详情 / 看板 / my-items | follow_summary count/score/level 一致 |

重点断言：

- follow_summary 在需求详情、看板、工作台口径一致。
- 关注人数和关注等级不混用。
- 取消关注后 count/score/level 回落。

### 21.6 协作链路 F：删除与审计追踪

目标：验证多人协作下删除操作不会丢审计信息。

步骤：

| 步骤 | 角色 | 操作 | 预期 |
| --- | --- | --- | --- |
| F01 | PM t01 | 创建需求和任务 | 成功 |
| F02 | 员工 t05 | 修改任务标题、截止日期、进度 | 成功 |
| F03 | TL t03 | 增加任务依赖 | 成功 |
| F04 | 员工 t05 | 删除自己负责的任务 | 成功 |
| F05 | PM t01 | 查询需求 events | 包含 `task_deleted`，event_title 有任务名 |
| F06 | PM t01 | 查询任务 events | 已删除任务不导致前端硬错误；若接口 fallback 返回事件则校验完整 |

重点断言：

- 删除事件必须保留任务名称。
- 删除前 before_data 必须包含核心字段。

### 21.8 组合展开规则

执行器生成用例时按以下规则展开：

1. 角色样本不能只取一个员工。至少使用：
   - PM：t01
   - 总监：t02
   - TL A：t03
   - TL B：t04
   - 员工 A 负责人：t05
   - 员工 A 同组非负责人：t06 或 t07
   - 员工 B 负责人：t09
   - 员工 B 同组非负责人：t10 或 t11
   - 跨组无关员工：从另一组选择非负责人。

2. 需求负责人集合至少覆盖：
   - 空负责人。
   - 单 PM。
   - 单总监。
   - 单 TL。
   - 单员工。
   - 同组多人。
   - 跨组多人。
   - PM + TL + 员工。

3. 任务负责人集合至少覆盖：
   - 空负责人。
   - 创建者自己。
   - 同组单人。
   - 同组多人。
   - 跨组单人。
   - 跨组多人。
   - TL + 员工。
   - PM + 员工。

4. 每个写操作至少用以下操作人跑一次：
   - 创建者。
   - 负责人。
   - 同组 TL。
   - 同组非负责人。
   - 跨组 TL。
   - 跨组员工。
   - PM。
   - 总监。

5. 风险链路必须覆盖：
   - 上游未完成 + 下游今天到期 -> blocked。
   - 上游未完成 + 下游已逾期 -> blocked + overdue。
   - 上游未来交付晚于下游 -> dependency_conflict。
   - 上游完成后 blocked 清除。
   - 下游完成后所有任务风险清除。
   - 需求 completed 后 requirement_overdue 清除。

6. Dashboard 断言必须在两个时点跑：
   - 风险存在时：验证 my-items / risks 能看到具体风险和阻塞来源。
   - 风险清除后：验证风险项消失或降级。

7. 事件断言不能只查最后一条：
   - 每个操作后记录当前 event count。
   - 操作后查询新增事件。
   - 校验 event_type、event_title、actor、before_data、after_data、metadata。
