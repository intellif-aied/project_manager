# 需求多负责人与关注权重测试方案

## 目标

验证需求从创建、负责人分配、关注权重展示、详情快捷编辑、任务拆解到权限可见性的完整链路。

本方案覆盖 4 个核心角色：

- PM：t01 / 303
- 总监：t02 / 304
- TL：t03 / 305（小组A）
- 员工：t05 / 307（小组A）

负向验证可追加员工 t09 / 311（小组B）。账号、密码、token 以 `doc/v1/测试账号文档.md` 为准。

## 测试环境

- 前端：`http://192.168.14.157:5173`
- API：`http://192.168.14.157:5173/api/v1` 或容器内 `http://127.0.0.1:18090/api/v1`
- 小组A：`3f05e6ed-c3bc-4900-8d7b-ea89843e157a`
- 小组B：`2ca74a00-a41f-40ff-a1c5-f2b7241be431`

## 关注权重规则

需求列表返回的 `follow_summary` 必须和 `/api/v1/dashboard/follows` 使用同一套规则：

| 角色 | 权重 |
| --- | ---: |
| director | 100 |
| team_leader | 50 |
| pm | 40 |
| employee | 10 |

level 规则：

| level | 条件 |
| --- | --- |
| high | score >= 150 |
| important | score >= 80 |
| notable | score >= 40 |
| normal | score < 40 |

注意：负责人会被自动加入关注，但移除负责人不会自动取消其关注，因为当前关注表没有区分“手动关注”和“系统自动关注”。如果要改变这个行为，需要单独设计关注来源字段。

## 接口测试

### 1. 鉴权基线

分别使用 PM、总监、TL、员工 token：

```bash
curl "$API/auth/me" -H "Authorization: Bearer $TOKEN"
```

预期：

- PM 返回 `role=pm`
- 总监返回 `role=director`
- TL 返回 `role=team_leader` 且有 `team_id`
- 员工返回 `role=employee` 且有 `team_id`

### 2. PM 创建多负责人需求

用 PM 创建：

```json
{
  "title": "芯片验证 Agent 日志归因闭环",
  "description": "把仿真失败日志归因到具体任务，并支持 PM 在需求层追踪负责人。",
  "priority": "high",
  "deadline": "2026-07-20",
  "owner_ids": ["305", "307"],
  "team_ids": ["3f05e6ed-c3bc-4900-8d7b-ea89843e157a"],
  "acceptance_criteria": [
    "需求详情能展示两个负责人",
    "需求列表能展示关注人数和关注权重 level"
  ]
}
```

预期：

- HTTP 201
- `owner_ids=["305","307"]`
- `owners` 包含 测试03、测试05
- 兼容字段 `owner_id="305"`、`owner_name="测试03"`
- `follow_summary.count=3`
- `follow_summary.score=100`
- `follow_summary.level="important"`

### 3. 角色可见性

用第 2 步创建的 `requirement_id` 分别请求：

```bash
curl "$API/requirements/$REQ_ID" -H "Authorization: Bearer $TOKEN"
```

预期：

- PM：200，可编辑
- 总监：200，可编辑
- TL 305：200，可编辑，可拆任务
- 员工 307：200，可创建自己负责的任务
- 员工 311：404，除非该需求也分配到小组B或其本人

### 4. 更新负责人集合

PM 更新：

```json
{
  "owner_ids": ["306", "308"],
  "base_version": 1
}
```

预期：

- HTTP 200
- `owner_ids=["306","308"]`
- `owners` 展示 TL B 和员工A
- `owner_id="306"` 仅作为兼容字段
- `version` 增加
- 新负责人会自动关注

边界预期：

- 旧负责人关注不会自动删除，`follow_summary` 可能因为历史关注继续增加。
- 同一个 owner 重复传入时，后端应去重。
- `owner_ids=[]` 可以清空负责人。

### 5. 总监跨团队创建

总监创建：

```json
{
  "title": "跨团队芯片回归稳定性专项",
  "description": "小组A负责 Agent 归因，小组B负责回归环境稳定性。",
  "priority": "urgent",
  "deadline": "2026-07-25",
  "owner_ids": ["305", "306"],
  "team_ids": [
    "3f05e6ed-c3bc-4900-8d7b-ea89843e157a",
    "2ca74a00-a41f-40ff-a1c5-f2b7241be431"
  ],
  "acceptance_criteria": ["两个小组都能看到需求并拆解任务"]
}
```

预期：

- 总监、PM、两个 TL 都可见。
- 小组A、B 员工因参与团队可见。
- `follow_summary.score=200`，level 为 `high`。

### 6. TL 创建跨团队需求

TL 305 创建小组A + 小组B 需求：

```json
{
  "title": "Agent 生成日报与任务状态联动",
  "description": "TL 发起跨组协作，PM 后续补充负责人和验收标准。",
  "priority": "medium",
  "deadline": "2026-07-22",
  "owner_ids": ["305", "306"],
  "team_ids": [
    "3f05e6ed-c3bc-4900-8d7b-ea89843e157a",
    "2ca74a00-a41f-40ff-a1c5-f2b7241be431"
  ],
  "acceptance_criteria": ["TL 可以创建跨团队需求"]
}
```

预期：

- HTTP 201。
- PM、总监可见。
- TL 305 和 TL 306 可见。
- 两组员工因参与团队可见。

### 7. 员工权限负向

员工 307 尝试创建需求：

预期：

- HTTP 403。
- 页面不跳 403 路由，只提示权限不足。

员工 307 对自己不是负责人且不属于参与团队的需求请求详情：

预期：

- HTTP 404 或列表不可见。

### 8. 任务拆解联动

对多负责人需求创建任务：

- TL 负责人创建任务，指派给本组员工：应成功。
- 员工负责人创建任务，指派给自己：应成功。
- 员工负责人创建任务，指派给别人：应失败。
- 非负责人、非参与团队成员创建任务：应失败。

预期：

- 任务创建后需求进度、风险摘要正常刷新。
- 需求列表展开任务行不显示关联 session 信息。

### 9. 关注权重一致性

步骤：

1. 用 PM 关注需求。
2. 用总监关注同一需求。
3. 用 TL 关注同一需求。
4. 请求 `/api/v1/requirements` 查看该需求 `follow_summary`。
5. 请求 `/api/v1/dashboard/follows` 查看同一需求的 `attentionScore/attentionLevel/followerCount`。

预期：

- 两处 count、score、level 一致。
- `follow_summary.level` 与 dashboard `attentionLevel` 一致。

### 10. 并发版本冲突

步骤：

1. A 用户读取需求，拿到 `version=N`。
2. B 用户更新需求成功，版本变成 `N+1`。
3. A 用户继续用 `base_version=N` 更新 `owner_ids`。

预期：

- HTTP 409。
- 返回当前版本信息。
- 前端提示“内容已被其他人更新，请刷新后再操作”。

## 前端操作测试

### PM 流程

1. 登录 t01。
2. 进入 `/requirements?favorite=1`。
3. 确认默认列表没有“参与团队”列，有“关注度”列。
4. 点击“新建需求”。
5. 负责人选择 测试03 + 测试05。
6. 参与团队选择 小组A。
7. 创建成功后回需求列表。
8. 打开详情抽屉。
9. 确认负责人区域展示多个负责人。
10. 点击负责人卡片右上角编辑 icon。
11. 改为 测试04 + 测试06 并保存。
12. 关闭详情，列表负责人列和关注度刷新。

### 总监流程

1. 登录 t02。
2. 创建一个跨小组需求，负责人选择 测试03 + 测试04。
3. 进入需求详情。
4. 修改截止日期、负责人、参与团队三个快捷入口。
5. 切换需求阶段：待开始、评审、进行中、完成。
6. 确认无负责人时阶段流转后只弹“建议补充负责人”，不叠加顶部成功提示。

### TL 流程

1. 登录 t03。
2. 创建小组A需求，负责人选择自己和测试05。
3. 打开详情，拆解任务并指派给测试05。
4. 列表展开任务行，确认任务行只展示任务、负责人、状态、进度、截止、关注。
5. 修改负责人为 测试03 + 测试06，保存后确认列表显示 `测试03、测试06`。

### 员工流程

1. 登录 t05。
2. 查看自己作为负责人之一的需求。
3. 打开详情，确认可创建指派给自己的任务。
4. 尝试指派给其他员工，预期失败。
5. 登录 t09，确认小组B员工看不到只分配给小组A且不含自己的需求。

## 回归检查

- `/requirements/create` 表单负责人多选样式正常，宽度不溢出。
- `/requirements` 列表横向不无限拉宽。
- 需求详情抽屉负责人、参与团队、截止日期三个快捷编辑入口均可关闭和保存。
- 编辑弹窗不会超过页面高度。
- 删除无关联数据的测试需求成功。
- 取消有任务的需求时不能物理删除，只能取消。
- Dashboard 我的关注、风险管理仍能打开对应需求详情。

## 清理

测试完成后删除无任务、无 session、无 token 关联的测试需求。

已有任务或关联数据的测试需求不要物理删除，改为“取消需求”，避免破坏历史数据。
