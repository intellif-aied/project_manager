# 平台运营中心方案

## 1. 目标与边界

运营中心用于回答两类问题：

1. 用户是否在使用 Aida，主要使用哪些页面和核心功能。
2. 生产环境是否稳定，是否出现需要处理的错误、性能退化或服务不可用。

它只包含以下两个模块：

```text
运营中心
├─ 用户使用统计
└─ 运维生产异常监控
```

本方案不包含：

- AI Session 正文、命令、提示词或工作内容分析；
- 日报、周报、Token 等业务内容统计；
- 用户反馈、Bug 工单、人工运营记录或任务管理；
- 全量 DOM 点击、请求正文、响应正文、Cookie、Token 等高噪音或敏感数据采集；
- 因接入运营能力而改变现有需求、任务、日报、AI 资产等业务流程。

## 2. 当前基础与问题

当前平台已有工作台、需求、任务、日报/周报、AI 资产、Token 用量和组织管理等页面。后端是单个 Go API 服务，使用 PostgreSQL 和 MinIO；后台还运行 Managed Agent 定时任务和状态同步。

现状的问题是：

- 没有页面访问或关键功能使用数据，无法回答用户是否在使用平台；
- 后端请求、后台任务和前端错误主要落在容器标准输出，排查依赖 `docker logs`；
- `/health` 只表示 HTTP 进程可响应，不能说明 PostgreSQL、MinIO 或可选的 Managed Agent 是否可用；
- 没有错误聚合、性能分位数、线上告警和每日运营快照。

## 3. 用户使用统计

### 3.1 统计口径

| 指标 | 定义 |
| --- | --- |
| UV | 当日登录后至少产生一次 `page_view` 的去重用户数 |
| PV | 当日 `page_view` 事件总数 |
| 新活跃用户 | 首次产生平台使用事件的用户数 |
| 活跃团队 | 当日存在至少一名活跃用户的团队数 |
| 页面使用人数 | 访问该标准化页面的去重用户数 |
| 关键动作成功率 | `success / (success + failure)`，仅统计有结果的关键动作 |

所有日期按服务配置时区计算；当前默认是 `Asia/Shanghai`。

### 3.2 自动采集的页面访问

前端路由变化时采集一次 `page_view`。只记录预定义页面键和标准化路径，不记录查询参数。

首批页面键：

| 页面键 | 页面 |
| --- | --- |
| `dashboard` | 工作台 |
| `requirements` | 需求看板及需求详情 |
| `tasks` | 任务列表及任务详情 |
| `daily_reports` | 日报 |
| `weekly_reports` | 周报 |
| `ai_assets` | AI 资产 |
| `tokens` | Token 用量 |
| `organization` | 组织成员 |

### 3.3 白名单关键动作

不采集所有按钮点击；只在动作开始、成功或失败处采集产品价值明确的事件。

| 模块 | 动作键 |
| --- | --- |
| 需求、任务 | 创建、编辑、状态变更 |
| 日报、周报 | 打开、保存、提交、AI 生成 |
| AI 资产 | 创建 Skill/MCP/Agent、运行 Agent、创建定时任务 |
| 组织管理 | 添加成员、编辑成员、创建团队 |
| 认证 | 登录成功、退出登录 |

动作事件的 `result` 为 `started`、`success` 或 `failure`。失败事件仅记录错误类别和关联请求 ID，不记录用户输入。

### 3.4 用户使用页面

管理员可查看：

- 今日、近 7 天、近 30 天 UV/PV、活跃团队、新活跃用户及同比周期变化；
- 页面访问排行：PV、UV、趋势；
- 关键动作排行：次数、使用人数、成功率、失败次数；
- 按角色、团队的聚合分布。

不提供用户行为回放、键盘记录、全量点击轨迹或 Session 内容查看。

## 4. 运维生产异常监控

### 4.1 服务健康

健康状态分为：

- `live`：API 进程存活；
- `ready`：API 可服务，PostgreSQL 与已配置的 MinIO 可连通；
- `managed_agent`：仅在配置了 Managed Agent 地址时检查，可用、不可用、未启用三态；
- `web`：前端入口可访问。

`/health` 保留现有语义；新增独立的 readiness 探针，避免把“进程活着”误认为“平台可用”。

### 4.2 API 指标

按路由模板统计，例如 `/tasks/{id}` 而不是每个具体 ID：

- 请求数；
- 2xx、4xx、5xx 数量及错误率；
- 平均耗时、最大耗时；
- P50、P95、P99；
- 最慢接口排行；
- 错误最多接口排行。

P95/P99 必须显示。平均值不能表达少数用户的长尾卡顿：平均耗时正常但 P99 明显升高时，仍需定位慢查询、超大响应或外部依赖问题。

### 4.3 前端、关键操作和后台异常

自动采集：

- 前端 `window.error`、未处理 Promise 异常和 React Error Boundary 错误；
- API 请求失败；
- 白名单关键动作失败；
- Managed Agent 定时任务、状态同步等后台任务失败。

错误事件的最小字段：

```text
发生时间、来源、级别、页面或路由、动作键、错误指纹、
关联 request_id、受影响用户数、首次发生、最近发生、恢复状态
```

错误指纹由来源、错误类别、标准化消息、路由或动作键构成。错误文本截断且脱敏，禁止写入授权头、Cookie、Token、请求/响应正文和用户输入。

## 5. 告警

### 5.1 初始规则

阈值配置化，先以如下默认值启动；运行两周后根据真实基线调整。

| 级别 | 触发条件 |
| --- | --- |
| 严重 | API、PostgreSQL 或 MinIO 连续 2 分钟不可用 |
| 严重 | 关键动作连续失败，或 10 分钟失败率超过阈值且样本量足够 |
| 警告 | 单接口 5 分钟内 5xx 超过阈值 |
| 警告 | 单接口 P99 连续 5 分钟高于阈值，例如 3 秒 |
| 警告 | 相同前端错误 10 分钟内影响多个用户 |
| 警告 | 定时任务连续失败 |
| 恢复 | 告警条件恢复后自动关闭并通知 |

低流量场景不能只看错误率；规则必须同时使用错误数量、错误率和最小请求数，避免一次偶发失败造成刷屏。

### 5.2 告警收敛

同一 `规则 + 服务/路由 + 错误指纹` 只创建一个告警事件：

- 未恢复期间合并次数和受影响用户；
- 设置通知冷却时间，例如 30 分钟；
- 恢复后发送一条恢复通知；
- 页面显示当前状态、首次发生、最近发生、次数和最近通知时间。

第一期通知通道为一个配置化的飞书或企业微信 Webhook。Webhook 失败仅重试和记录自身错误，绝不影响用户请求。

## 6. 数据与处理架构

```text
前端 page_view / 关键动作 ──后台批量上报──┐
                                           ├─ usage_events ──> 每日使用快照
API 中间件耗时/状态 ──内存直方图/计数器──────┤
                                           ├─ request_metric_minutes ─> P50/P95/P99
前端异常、后端异常、后台任务异常 ─异步队列──┤
                                           └─ operation_events ─> 告警计算
                                                              └─ alert_incidents / Webhook
```

建议的数据表：

| 表 | 用途 |
| --- | --- |
| `usage_events` | 有限保留期的页面访问和关键动作原始事件 |
| `daily_usage_metrics` | 长期保留的按天、页面、动作、角色、团队聚合数据 |
| `request_metric_minutes` | 每分钟按路由、状态类别的请求计数与延迟直方图 |
| `operation_events` | 有限保留期的异常事件与错误指纹 |
| `daily_operation_metrics` | 长期保留的每日错误、性能、可用性聚合数据 |
| `alert_incidents` | 告警生命周期、次数、通知和恢复状态 |

原始事件不承担长期报表职责；每日聚合快照才是月报、年度复盘和述职数据来源。

## 7. 性能与可靠性硬约束

运营中心是旁路能力，必须满足以下约束：

1. 业务请求不等待使用事件入库、异常入库或 Webhook 通知。
2. API 请求仅在中间件内做计时、状态码记录和内存计数；不能为每个正常请求同步写 PostgreSQL。
3. P50/P95/P99 使用内存延迟直方图按路由、状态类别聚合，并按分钟异步批量写入数据库。当前单实例规模下可提供足够精度；未来多实例时可接 Prometheus 或兼容聚合器。
4. 前端事件采用内存缓冲、定时批量发送和页面卸载时 `sendBeacon`；业务按钮和页面跳转不等待上报结果。
5. 异步队列必须有容量上限。队列满时允许丢弃低优先级 `page_view`，绝不能阻塞业务接口；错误、健康状态和关键动作失败优先保留。
6. 异步写库使用受限并发和批量写入，避免挤占现有业务 SQL 连接。
7. 运营查询使用预聚合、时间范围、分页和索引；禁止对原始事件做无时间边界的全表扫描。
8. 运营中心自身的接口、健康探针和告警轮询不计入产品使用和业务接口指标。
9. 所有采集失败只能降低观测完整度，不能改变用户请求返回结果。

## 8. 数据保留与权限

| 数据 | 建议保留期 |
| --- | --- |
| 原始使用事件 | 30 至 90 天 |
| 原始异常事件 | 30 至 90 天 |
| 分钟级请求性能数据 | 30 至 90 天 |
| 每日使用与生产聚合快照 | 长期保留 |
| 告警事件 | 长期保留 |

运营中心仅 `admin` 可访问。总监如需查看，使用现有角色体系明确授予只读访问，不开放给普通用户。

## 9. 每日运营简报

每日聚合完成后生成只读简报；页面可随时查看，后续可定时推送到飞书。

```text
平台运营日报｜YYYY-MM-DD

用户使用
- UV：42，较昨日 +12%
- PV：536
- 热门页面：工作台、日报、需求看板
- 日报保存：31 次，成功率 96.8%
- AI 生成：12 次，成功率 100%

生产状态
- API 成功率：99.8%
- P50/P95/P99：120ms / 420ms / 1.8s
- 5xx：2 次；前端异常：1 类
- 当前未恢复告警：0
```

日报只展示自动采集的使用和生产数据，不要求人工填写运营记录。

## 10. 分期实施

### 第一期：采集与可见性

1. 前端页面访问与白名单关键动作埋点；
2. 后端请求计时、状态码和分钟延迟直方图；
3. 前端异常、后端错误、后台任务异常的异步采集；
4. 用户使用页、生产监控页、每日快照；
5. readiness 健康检查。

### 第二期：告警与日报

1. 告警规则、事件收敛、恢复状态；
2. 飞书或企业微信 Webhook；
3. 每日运营简报和定时推送；
4. 基于首两周数据调整告警阈值。

### 第三期：规模化选项

仅在多实例、日志量或查询压力明显增长时，再评估 Prometheus/Loki/Grafana 等外部组件。第一、二期不依赖它们。

## 11. 验收标准

- 正常使用需求、任务、日报、AI 资产等现有功能时，不需要等待运营采集请求；
- 能在管理员页面看到 UV/PV、页面排行、关键动作次数和成功率；
- 能看到按路由的请求量、错误率、P50/P95/P99 和慢接口排行；
- 能查看前端错误、后端错误和后台任务失败的聚合事件；
- 依赖不可用、关键动作连续失败、5xx/P99 异常能创建合并告警并发送通知；
- 告警恢复后自动关闭并通知；
- 每日快照可长期查询，原始事件按保留期清理；
- 采集、写库、Webhook 或告警查询故障不会影响现有业务接口返回。
