# Token 分析成员下钻交互审查

审查页面：`/token-analytics` → `/token-analytics/member/:userID`

## 结论

当前点击成员会进入独立路由，团队或部门分析页随之卸载，用户此前的日期、组织范围、列表筛选、分页、展开状态和滚动位置都可能丢失。更合适的交互是“页内下钻”：视觉上进入个人详情，但保留团队或部门页实例及其状态。

## 审查步骤

1. 团队/部门分析页（健康度：良好）
   - 页面承担汇总指标、人员对比、趋势和成员入口，当前上下文有较高保留价值。
   - 证据：`01-team-context.png`。
2. 点击成员进入个人详情（健康度：较差）
   - 当前 URL 切换到 `/token-analytics/member/:userID`，父页面被路由替换。
   - 返回后需要依赖页面自行恢复筛选和滚动位置，交互连续性较弱。
   - 证据：`02-member-route.png`；代码中的 `navigate('/token-analytics/member/...')` 与独立路由配置。

## 推荐方案

- 团队/部门页保留挂载，通过 `selectedMember` 进入页内个人详情。
- 个人详情继续复用现有 Token 详情布局，不使用空间受限的抽屉。
- “返回团队分析/返回部门分析”只清除当前成员选择，原日期、组织筛选、搜索、分页和滚动位置原样恢复。
- 浏览器后退优先退出个人下钻，再离开 Token 分析页。
- 保留 `/token-analytics/member/:userID` 作为外部分享、书签和直接访问入口；它不再是团队页内部查看成员的默认路径。
- 返回后将焦点恢复到刚才点击的成员入口，保证键盘操作连续性。

## 不建议的方案

- 右侧抽屉：个人页包含多张图表和 Session 表格，抽屉会压缩有效宽度并产生更多内部滚动。
- 仅把全部筛选写入 URL：可以恢复部分状态，但滚动、展开和临时列表状态仍需额外处理，复杂度高于页内下钻。

## 证据边界

截图证明了团队页与成员页的布局差异及 URL 路由切换；代码确认两者是独立路由。尚未逐一验证所有筛选项在浏览器返回后的恢复行为，因此“可能丢失”是基于组件卸载和当前路由结构的风险判断。
